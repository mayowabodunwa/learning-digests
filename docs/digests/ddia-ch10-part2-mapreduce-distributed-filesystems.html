MapReduce and Distributed Filesystems

Part 1 ended with a tidy five-command Unix pipeline and one honest limitation: it only runs on one machine. This part is the answer to "okay, but what if the data doesn't fit on one machine?" It covers where the data lives (a distributed filesystem, with HDFS as the running example) and how a job runs over it (MapReduce, which is a lot like that pipeline stretched across a cluster). I'll keep going back to the log-counting pipeline from Part 1, because the whole trick is spotting that it's the same shape wearing bigger clothes.

In one line

MapReduce takes the "extract a key, sort, then combine adjacent records" shape of a Unix pipeline and runs it across many machines, reading from and writing to a distributed filesystem, with the framework (not you) handling the splitting, moving, and sorting of data.

The big idea

A Unix pipeline reads from files, passes bytes through small programs, and writes to a file. MapReduce keeps that spirit and swaps out two things. The files now live on a distributed filesystem, which stitches together the disks of many ordinary machines into what looks like one big filesystem. And the work of "break the input into pieces, process the pieces in parallel, bring matching records together" is done by a framework, so that you only write two small functions: a mapper that pulls a key and a value out of each record, and a reducer that handles all the values that share a key. Everything between those two functions (partitioning, sorting, copying data between machines) is the framework's job. A single job is limited, so real work is usually several jobs chained together, with each job's output directory feeding the next job. I'm calling that "bigger clothes", not magic: it is deliberately blunt and brute-force, and that bluntness is a big part of why it scales.

Key terms

  • Distributed filesystem: software that makes the disks of many machines behave like one big filesystem. You ask for a file by name and don't care which machines hold the bytes. e.g. HDFS.
  • HDFS (Hadoop Distributed File System): the open source distributed filesystem that Hadoop's MapReduce reads from and writes to. It is an open source reimplementation of the Google File System (GFS).
  • Shared-nothing: an architecture where each machine uses its own CPU, memory, and disks, and machines only talk over an ordinary network. The contrast is shared-disk storage (NAS, SAN), where a central storage appliance serves everybody.
  • Daemon: a program that runs in the background on a machine, waiting to do work for others. In HDFS, a daemon on each machine serves up the files stored on that machine.
  • NameNode: HDFS's central server. It doesn't hold the file contents, it keeps the map of which blocks of which files sit on which machines.
  • Block: a chunk of a file. HDFS splits files into blocks and spreads them over machines.
  • Replication: keeping several copies of the same block on different machines so a dead machine or disk doesn't lose data.
  • Erasure coding (e.g. Reed-Solomon codes): a smarter alternative to plain copies. You store extra computed "parity" data so lost pieces can be rebuilt, using less extra storage than full replication.
  • RAID: redundancy across several disks inside one machine. Distributed filesystems do a similar job across machines, over a normal network.
  • MapReduce: a programming framework for processing big datasets stored in a distributed filesystem by writing a mapper and a reducer.
  • Record: one unit of input, such as one line of a log. An input parser splits files into records.
  • Mapper: a function called once per input record. It emits zero or more key-value pairs and remembers nothing between records.
  • Reducer: a function called once per distinct key, given that key plus an iterator over all the values collected for it.
  • Map task / reduce task: one running instance of the mapper or reducer logic working on one slice of the data. A job has many of each, running in parallel.
  • Partition: one slice of a dataset that can be handled independently of the other slices.
  • Shuffle: the whole step of splitting mapper output by reducer, sorting it, and copying it from mappers to reducers. (The name is confusing: there is no randomness in it.)
  • Workflow: several MapReduce jobs chained so that one job's output becomes the next job's input.
  • Workflow scheduler: a tool that runs a set of jobs in the right order and manages the dependencies between them (the source names Oozie, Azkaban, Luigi, Airflow, and Pinball).

How it works

Grounding first. Part 1 showed that a batch job is "read a big fixed pile of data, produce output", and that Unix tools do this well but on a single machine. Once your input is hundreds of gigabytes or more, you hit two separate problems. First, where does the data live, if no single disk can hold it comfortably and you also don't want one dead disk to destroy it? Second, how do you run code over it without hand-writing all the logic for splitting work among machines, moving data around, and coping with parts of the job running at different speeds? A distributed filesystem answers the first. MapReduce answers the second. The framing from the source is that a MapReduce job is comparable to a single Unix process: it takes one or more inputs and produces one or more outputs. And, like most Unix tools, running a job normally doesn't modify its input and has no side effects beyond producing the output files.

1. Where the data lives: a distributed filesystem (HDFS)

Unix tools read and write files through stdin and stdout. MapReduce jobs read and write files on a distributed filesystem instead. In Hadoop's version of MapReduce that filesystem is HDFS, an open source reimplementation of the Google File System. HDFS isn't the only one: the source names GlusterFS and the Quantcast File System (QFS), and says object storage services like Amazon S3, Azure Blob Storage, and OpenStack Swift are similar in many ways. The source uses HDFS as the running example, and says the principles carry over to any distributed filesystem. I'll do the same.

Shared-nothing. HDFS is built on the shared-nothing idea. In a shared-disk design (NAS and SAN are the names the source gives), one centralized storage appliance, often with custom hardware and special network gear like Fibre Channel, serves all the machines. HDFS goes the other way: it needs no special hardware, just ordinary computers connected by an ordinary datacenter network, each with disks of its own.

How it's put together. A daemon process runs on every participating machine and exposes a network service so other machines can reach the files stored on that one. A single central server, the NameNode, keeps track of which file blocks are stored on which machine. Put together, you get what looks like one huge filesystem built from the free disk space of every machine running the daemon. A mental model: the NameNode is the index card catalogue at a library, and the daemons are the shelves in different rooms. You ask the catalogue where a block is, then go fetch it from the right shelf.

Surviving failures. Machines and disks die, so blocks are replicated on multiple machines. That can be as simple as several full copies (the same idea as replication in the earlier replication chapter), or it can be erasure coding such as Reed-Solomon codes, which lets you rebuild lost data with less storage overhead than keeping whole extra copies. The source compares this to RAID, which spreads redundancy over several disks inside one machine. The difference is that a distributed filesystem does its file access and replication across a conventional datacenter network, without special hardware.

Scale and cost. The source says HDFS has scaled well: at the time of writing (the book is from 2017), the biggest deployments ran on tens of thousands of machines with a combined capacity of hundreds of petabytes. It credits commodity hardware plus open source software for making the cost much lower than an equivalent dedicated storage appliance. Treat those numbers as a snapshot of when the book was written, not as current limits.

One footnoted nuance worth keeping. With HDFS, compute tasks can be scheduled on the machine that stores a copy of the file they need, while object stores usually keep storage and computation separate. Reading from a local disk helps when network bandwidth is the bottleneck. The caveat from the same footnote: if erasure coding is used, that locality advantage goes away, because data from several machines has to be combined to reconstruct the original file.

Write-once files. The source also notes that job output files are written once, sequentially, without modifying any existing part of a file after it is written. That fits the "inputs are treated as immutable" habit from the Unix tools.

2. The MapReduce recipe, step by step

The easiest way into MapReduce is to line it up with the log pipeline from Part 1. A MapReduce job does four things:

  1. Read the input files and break them into records. In the log example, one record is one line (the newline is the record separator). The framework's input format parser does this, not you.
  2. Call the mapper on each record to pull out a key and a value. In the pipeline, awk '{print $7}' played this role: it extracted the URL as the key and left the value empty.
  3. Sort all the key-value pairs by key. In the pipeline, the first sort did this. In MapReduce you never write this step: mapper output is always sorted before the reducer sees it.
  4. Call the reducer to walk the sorted pairs. Because sorting put identical keys next to each other, combining their values is easy and doesn't need much memory. In the pipeline, uniq -c did this by counting adjacent equal records.

So you write steps 2 and 4. Steps 1 and 3 come with the framework.

The mapper and the reducer, precisely

The mapper is called once for every input record. Its job is to extract a key and a value. For one input it may emit any number of pairs, including none (handy for skipping junk lines). It keeps no state from one record to the next, so each record is processed independently. The reducer is handed a key together with an iterator over all the values the framework collected for that key, and it can emit output records, for example the count of how many times a URL was seen. It can run arbitrary logic over those values.

A way to hold both in your head: the mapper's role is to prepare the data into a form that can be sorted, and the reducer's role is to process the data once sorted. One consequence: counting hits per URL is one job. Ranking URLs by how many hits they got needs a second round of sorting, which in MapReduce means a second job that reads the first job's output. That's the "second sort" from the Part 1 pipeline, now as its own job.

3. Running it on many machines

The big difference from a Unix pipeline is that MapReduce can spread a computation over many machines without you writing any parallelism code. That works because the mapper and reducer only look at one record (or one key's values) at a time and don't care where their input came from or where their output goes. That's the loose-coupling idea from Part 1 again, and it frees the framework to shuffle data between machines however it likes.

What do you write the functions in? The source says you can use standard Unix tools as mappers and reducers in a distributed job, but more commonly they're functions in an ordinary programming language: in Hadoop MapReduce each is a Java class implementing an interface, whereas in MongoDB and CouchDB they're JavaScript functions.

Map side: partitioning and putting computation near the data

Parallelism comes from partitioning. The input to a job is typically a directory in HDFS. Each file, or each file block, in it counts as a separate partition that its own map task can process. The source's figure labels them m1, m2, and m3. The source says input files are typically hundreds of megabytes each (a typical-case remark, not a rule).

The scheduler tries to run each map task on a machine that already holds a replica of its input block, as long as that machine has spare RAM and CPU. This is called putting the computation near the data. It saves copying big input files over the network and so cuts network load and improves locality. Usually, the code to run isn't on the chosen machine yet, so the framework first copies it there (a JAR file, for a Java program), then starts the task, which reads its block and passes records one at a time to the mapper.

Reduce side: partitioning by key

The reduce side is partitioned too, but with a twist. The number of map tasks follows the number of input blocks. The number of reduce tasks is configured by the job author and can differ. Here's the crucial requirement: all pairs with the same key must reach the same reducer. So the framework takes a hash of the key and uses it to pick which reducer gets each pair. Think of sorting letters into numbered pigeonholes by running the recipient's name through a formula: same name, same pigeonhole, every time.

The shuffle: sorting in stages

Mapper output is probably too large to sort with an ordinary sorting algorithm on one machine, so sorting happens in stages. First, each map task splits its output by reducer (using that key hash), and writes each piece into a sorted file on the mapper's own local disk. The source says this uses a technique similar to the SSTables and LSM-trees from the storage chapter.

When a mapper finishes reading its input and writing its sorted output files, the scheduler tells the reducers they can start fetching. Each reducer connects to every mapper and downloads the sorted file for its own partition. The overall process of partitioning by reducer, sorting, and copying from mappers to reducers is the shuffle. It's a confusing name, since nothing is randomized.

The reduce task then merges the files it downloaded, preserving sort order, so if different mappers emitted the same key, those records end up adjacent. The reducer is called with a key and an iterator that scans through all records with that key one at a time (the source notes they might not all fit in memory, which is why it's an iterator and not a list). The reducer can emit any number of output records. Those are written to a file on the distributed filesystem, usually one copy on the local disk of the machine running the reducer and replicas on other machines.

4. Chaining jobs into workflows

A single job can only do so much. Counting page views per URL is one job. Finding the most popular URLs needs a second round of sorting, so it needs a second job. That's why jobs are very commonly chained into workflows, where one job's output becomes the next job's input.

The way Hadoop MapReduce does this is almost embarrassingly plain, and I find that comforting. The source says the framework has no particular support for workflows, so the chaining is done implicitly by directory name: you configure the first job to write to a directory in HDFS, and you configure the second job to read that same directory. From the framework's viewpoint they are two independent jobs.

That makes chained jobs less like a Unix pipeline (where one process feeds the next directly through a small in-memory buffer) and more like a sequence of commands where each writes to a temporary file that the next reads. The source says this has advantages and disadvantages and says it comes back to them in a later section on materializing intermediate state. I'll leave that for a later part rather than guess at it here.

Success and dependencies. A batch job's output is considered valid only once the job has finished successfully, and MapReduce discards the partial output of a failed job. So a job in a workflow can only start after the jobs that produce its input directories have completed successfully. To manage those dependencies, various workflow schedulers were built for Hadoop, which the source lists as Oozie, Azkaban, Luigi, Airflow, and Pinball. They also help with managing a big collection of batch jobs. The source says workflows of 50 to 100 MapReduce jobs are common when building recommendation systems, and in a large organization, different teams may run jobs that read each other's output, which is why tooling matters. Finally, higher-level tools on top of Hadoop (the source names Pig, Hive, Cascading, Crunch, and FlumeJava) set up multi-stage workflows and wire them together automatically.

Simplification flag: I've described the shuffle as "sorted files, fetched by reducers, merged". That's the mental model from the source. Real implementations have a lot more engineering in them (what to buffer, when to spill, how to retry), and the source doesn't go into that, so I'm not going to either.

Why it matters

You may never write a line of Hadoop, but the shape keeps showing up. "Pull a key out of every record, bring matching keys together, then summarize each group" is behind a huge amount of data work, and knowing it lets you read other systems (including SQL group-bys) more easily. The design choices here also explain a lot of the vocabulary you'll meet next: why joins in batch jobs are done by sorting, why job outputs are files that other jobs read, and why workflow schedulers exist. This part sets up the next one, where the source returns to joins and asks how they're really implemented when there are no indexes.

It also gives you a cleaner way to think about cloud storage. Services like S3 are described by the source as similar in many ways to distributed filesystems, with the nuance that storage and computation are usually kept apart there, so the "computation near the data" trick has less to work with.

Remember this

  • A distributed filesystem like HDFS joins the disks of many ordinary machines into one big filesystem: a NameNode tracks block locations, daemons on each machine serve blocks, and blocks are replicated (or erasure coded) to survive failures.
  • MapReduce is the Unix log pipeline at cluster scale: you write the mapper (record -> key, value) and the reducer (key, values -> output). Splitting, sorting, and moving data is the framework's job.
  • Parallelism comes from partitioning: roughly one map task per input block, and a number of reduce tasks you pick, with a hash of the key making sure equal keys land on the same reducer.
  • The shuffle is partition, sort, and copy from mappers to reducers, with nothing random about it. Reducers merge sorted files so equal keys are adjacent.
  • One job is limited. Real work is a workflow of chained jobs, linked by output and input directory names, where a job starts only after its inputs' jobs finished successfully.

Try it yourself

  1. Build a mini MapReduce in one file. In any language, write a function that takes input files, a mapper, a reducer, and a reducer count. It should (a) call the mapper on every line, (b) split the output into one bucket per reducer using a stable hash of the key, (c) write each bucket sorted to its own file, then (d) merge the files per reducer and call the reducer once per key. A reference sketch is below. Done when: running it on three small log files gives the same top counts as awk | sort | uniq -c | sort -rn on the concatenated logs.
  2. Prove the "same key, same reducer" rule. Print which reducer each key went to under 2, 3, and 5 reducers. Done when: for any given run, no key shows up in the output files of more than one reducer, and you can explain why your hash must give the same answer in every mapper (hint: in Python, the built-in hash() on strings is randomised per run, so I used zlib.crc32 in the sketch).
  3. Chain a second job. Make the first job count hits per URL, then run a second job on its output directory to list the top 3. Done when: the second job only reads files the first job wrote, and deleting the first job's output makes the second job fail loudly instead of producing a wrong answer.
  4. Add a failed-job rule. Make your job write to a temporary directory and only rename it to the final name after every reducer finishes. Kill it halfway through on purpose. Done when: after a failed run, the final output directory doesn't exist (or is unchanged), and the next job in the chain refuses to start.
  5. Sketch a block map by hand. Take a pretend 1 GB file, pretend a block size, and a cluster of five machines. Write a NameNode table (block -> machines) with 3 copies of each block, then "kill" one machine and mark which blocks still have enough copies. Done when: you can say which blocks have fewer copies than you wanted and what the system would need to do about it. (Block size and copy count here are your choices for the exercise, not HDFS defaults.)
  6. Read a real directory of output. If you have access to any Spark, Hadoop, or Hive output, or you just run project 1, look at the output directory. Done when: you can explain why there's one file per reducer instead of one file total, and how you'd merge them into one if you needed to.

Reference sketch for project 1, which I ran against three generated 1000-line logs (python3, standard library only). It matches the Unix pipeline's top-3. It's deliberately single-process: it imitates the data movement, not the parallelism.

import sys, os, zlib, itertools, heapq, tempfile, collections

def partition_of(key, n):
    # stable hash (Python's built-in hash() is randomised per run for strings)
    return zlib.crc32(key.encode()) % n

def run_job(input_files, mapper, reducer, n_reducers, workdir):
    # MAP: one task per input file; each writes one sorted spill file per reducer
    for m, path in enumerate(input_files):
        buckets = collections.defaultdict(list)
        with open(path) as f:
            for line in f:
                for k, v in mapper(line.rstrip("\n")):
                    buckets[partition_of(k, n_reducers)].append((k, v))
        for r in range(n_reducers):
            with open(os.path.join(workdir, f"map{m}-part{r}.txt"), "w") as out:
                for k, v in sorted(buckets[r]):
                    out.write(f"{k}\t{v}\n")
    # SHUFFLE + REDUCE: each reducer merges the sorted files for its partition
    outputs = []
    for r in range(n_reducers):
        files = [open(os.path.join(workdir, f"map{m}-part{r}.txt")) for m in range(len(input_files))]
        streams = [(tuple(l.rstrip("\n").split("\t", 1)) for l in fh) for fh in files]
        merged = heapq.merge(*streams)          # keeps sort order, like the real merge step
        outpath = os.path.join(workdir, f"out-part{r}.txt")
        with open(outpath, "w") as out:
            for key, group in itertools.groupby(merged, key=lambda kv: kv[0]):
                for rk, rv in reducer(key, (v for _, v in group)):
                    out.write(f"{rk}\t{rv}\n")
        outputs.append(outpath)
        for fh in files: fh.close()
    return outputs

# job 1: count hits per URL (log line: ip time url status)
def map_url(line):
    parts = line.split()
    if len(parts) >= 3:
        yield parts[2], 1
def reduce_count(key, values):
    yield key, sum(int(v) for v in values)

# job 2: rank. Everything goes under one key so one reducer sees all counts, sorted by key
def map_rank(line):
    url, count = line.split("\t")
    yield "all", f"{int(count):08d} {url}"
def reduce_top(key, values):
    for v in sorted(values, reverse=True)[:3]:
        c, u = v.split(" ", 1)
        yield u, int(c)

if __name__ == "__main__":
    inputs = sys.argv[1:]
    with tempfile.TemporaryDirectory() as w1, tempfile.TemporaryDirectory() as w2:
        j1 = run_job(inputs, map_url, reduce_count, 2, w1)
        print("job 1 output files:", [os.path.basename(p) for p in j1])
        j2 = run_job(j1, map_rank, reduce_top, 1, w2)
        print(open(j2[0]).read(), end="")
