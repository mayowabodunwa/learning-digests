AWS VPC · CONCEPT 10 DIGEST

VPC Sharing with RAM, Managed Prefix Lists, and Route Evaluation Order

Three tools for running networks at scale: let many accounts live in one VPC, give a list of CIDR blocks a single name, and know exactly which route wins when several could match.

In one line

With subnet sharing one account owns a VPC and shares subnets (through AWS RAM) with other accounts in the same organization; managed prefix lists let you refer to many CIDR blocks as one object; and route evaluation is longest prefix first, with a short tie-break order after that.

The big idea

As a company grows it ends up with many AWS accounts (one per team or environment is a common pattern) and each one tends to get its own VPC. That works until you're drowning in peering connections, NAT gateways and duplicated route tables. VPC subnet sharing flips the idea: one central network account owns the VPC and its plumbing, and other accounts just launch their resources into shared subnets. Prefix lists solve a related pain, the same ten CIDR blocks repeated across dozens of security group rules and route tables. And the route-priority rules are the fine print you need whenever a table gets crowded with peering, VPN, endpoint and prefix list routes. All three are about managing complexity rather than adding new connectivity.

Key terms

  • VPC subnet sharing: the account that owns a VPC (the owner) shares subnets with other accounts (participants) in the same AWS Organization, who then create their application resources in them.
  • AWS RAM: AWS Resource Access Manager, the service that shares resources across accounts, organizational units or an entire organization.
  • Resource share: the RAM object listing the resources shared, the principals receiving them, and a managed permission.
  • AWS Organizations: the service that groups accounts under one management account; an OU is an organizational unit within it.
  • Managed prefix list: a named set of one or more CIDR blocks that you reference in security group rules and route tables.
  • Customer-managed vs AWS-managed prefix list: one you define and manage, versus a set of ranges AWS maintains for a service (you can't edit or share those).
  • Longest prefix match: the most specific route wins. e.g. 10.10.2.15/32 beats 10.10.2.0/24.
  • Propagated route: a route added automatically from a VPN or Direct Connect connection when route propagation is on.

How it works

Grounding: the multi-account problem

Suppose a company has a networking team and six application teams, each with its own AWS account. Without sharing, each account builds its own VPC, subnets, NAT gateways and connections, then the networking team stitches them together with peering or a transit gateway. With sharing, the networking account owns one VPC and shares some subnets; the application teams launch instances and databases there. They still keep separate accounts for billing and access control, which is the docs' stated benefit: fewer VPCs to manage "while using separate accounts for billing and access control".

1. Subnet sharing: prerequisites and the cast

Prerequisites (from the docs). Owner and participant accounts must both be managed by AWS Organizations; resource sharing must be enabled in the AWS RAM console from the organization's management account; and you must create a resource share, adding the subnets either at creation or later. Subnets can only be shared with accounts or OUs in the same organization, and subnets in a default VPC can't be shared.

About RAM. RAM shares a resource you own across accounts, OUs or the organization (and for some resource types, individual IAM roles and users). A resource share holds the region, a name, the resources, the principals and a managed permission that sets the maximum a principal can do. The owner keeps ownership. For accounts outside your organization RAM uses an invitation process; inside it, once organization sharing is enabled, no invitation is needed. The RAM docs state there is no additional charge for RAM itself; resource usage charges follow the owning service.

Who may do what. The owner is responsible for the networking resources: subnets, route tables, network ACLs, peering connections, gateway and interface endpoints, Route 53 Resolver endpoints, internet gateways, NAT gateways, virtual private gateways and transit gateway attachments. Participants can create a limited set of VPC resources: network interfaces and security groups, and flow logs for network interfaces they own. Key restrictions:

  • Participants can't create, delete or modify route tables, NACLs, subnets, NAT gateways or internet gateways in a shared VPC; they can describe some of them.
  • Participants can't launch instances using the VPC's default security group because it belongs to the owner, nor using the owner's other security groups unless the owner shares them.
  • A participant's security group rule can reference another account's group in the form account-number/security-group-id.
  • Participants cannot see or modify each other's resources, and VPC tags aren't shared with them.
  • Only the owner can attach a transit gateway to a shared VPC.
  • VPC resources a participant creates count against the participant account's quotas, not the owner's.

Who pays. Per the billing page: participants pay for their application resources (EC2, RDS, Redshift, Lambda) and for inter-AZ data transfer plus transfer over peering, internet gateways and Direct Connect gateways. The owner pays for NAT gateways, virtual private gateways, transit gateways, PrivateLink and VPC endpoint charges (hourly, data processing, data transfer), and for public IPv4 addresses used in the shared VPC. Data transfer within the same Availability Zone (identified by AZ-ID) is free regardless of account ownership.

Simplification: I say "one network account, many app accounts". That's a common pattern, not a requirement; the docs only require the same organization and an owner/participant relationship, and an owner can also run its own workloads.

2. Managed prefix lists

What they are. A set of CIDR blocks (each with an optional description) that you reference as one object in security group rules and route tables. The docs' pitch: you can consolidate security group rules with different CIDR blocks but the same port and protocol into one rule, and when you add a block, every security group using the list updates.

Rules for customer-managed lists (from the docs):

  • One address family per list: IPv4 or IPv6, never mixed.
  • Regional: a list applies only to the Region where you created it.
  • You must set a maximum number of entries at creation. That maximum, not the current count, counts against the quota of the resource that references it. The docs' example: a list with 20 maximum entries referenced by a security group rule counts as 20 rules.
  • Editing creates a new version; resources always use the latest version. You can restore an older version's entries (which creates yet another version).
  • You can share a list with other accounts through RAM.

AWS-managed lists cover service IP ranges (you met one with gateway endpoints). You can't create, modify, share or delete them, and different ones carry different weights when used.

CLI from the reference page:

aws ec2 create-managed-prefix-list --address-family IPv4 --max-entries 10 --entries Cidr=10.0.0.0/16,Description=vpc-a Cidr=10.2.0.0/16,Description=vpc-b --prefix-list-name vpc-cidrs
name must not start with com.amazonaws; --address-family, --max-entries and --prefix-list-name are the required options

This pairs naturally with the multi-account theme: a central team can publish a list of corporate ranges and share it, so other accounts reference it instead of copying CIDRs.

3. Route evaluation order

Here's the VPC route table priority summary from the docs, most preferred first:

  1. Longest prefix (10.10.2.15/32 beats 10.10.2.0/24). IPv4 and IPv6 routes are independent of each other.
  2. Static routes (such as peering and internet gateway targets).
  3. Prefix list routes.
  4. Propagated routes, in this order: Direct Connect BGP, then VPN static, then VPN BGP.

Read it as: step 1 decides almost everything, and steps 2 to 4 only break ties when destinations are identical. Details that make it concrete:

  • The docs' example: 0.0.0.0/0 to an internet gateway plus 172.31.0.0/16 to a peering connection means traffic for 172.31.0.0/16 uses the peering connection, because it's more specific. Traffic inside the VPC uses the local route.
  • If a propagated route has the same destination as a static route, the static one wins. Static targets named by the docs: internet gateway, NAT gateway, network interface, instance ID, gateway VPC endpoint, transit gateway, VPC peering connection, Gateway Load Balancer endpoint.
  • If a propagated VPN or Direct Connect route overlaps the VPC's local route, the local route is most preferred even if the propagated route is more specific (from the VPN docs).
  • For prefix lists: a route that references a prefix list takes priority over a matching propagated route, but more specific routes always win regardless of type. If a table references multiple prefix lists with overlapping CIDRs pointing to different targets, AWS picks one at random and then keeps choosing the same one thereafter, so avoid that overlap.

This is a good moment to revisit earlier topics. The gateway endpoint (Concept 4) works because its prefix list route is more specific than 0.0.0.0/0. Note that the two lists look slightly different because they cover different places (VPC route table versus the gateway's own path selection).

Why it matters

Subnet sharing is one of the main ways larger AWS environments cut down the number of VPCs, NAT gateways and endpoints they pay for and operate, while keeping accounts as the unit of billing and access. Prefix lists keep security rules and routes readable as the number of CIDRs grows. And knowing route priority is how you stop guessing when a peering route, a VPN route and a default route all seem to apply. These are also the last concepts in the VPC area, so they draw on almost everything before them.

Remember this

  • Subnet sharing needs AWS Organizations, RAM sharing enabled, and a resource share; default-VPC subnets can't be shared.
  • Owner runs the network plumbing; participants create their own ENIs, security groups and application resources.
  • A prefix list holds one address family, is Regional, versions on every edit, and counts its maximum size against quotas.
  • Route choice: longest prefix first; ties go static, then prefix list, then propagated.
  • Overlapping prefix lists to different targets in one route table give you a random but stable winner, which is a design smell.

Try it yourself

  1. Create a prefix list. Run create-managed-prefix-list with two documentation CIDRs and a max of 5. Done when: aws ec2 describe-managed-prefix-lists shows Version 1.
  2. Use it twice. Reference the list in a security group rule and in a route table. Done when: you can explain what quota each reference consumed (hint: the max entries, not the count).
  3. Edit it. Add a third CIDR with modify-managed-prefix-list and confirm the version number moved. Done when: you can describe what happens to resources that reference the old version. (I'm using the docs' description that resources follow the latest version; I haven't checked that command's syntax for this digest, so read its CLI page first.)
  4. Route-order simulator. Write a function that, given a list of routes (CIDR, kind: local/static/prefix-list/propagated, propagated source) and a destination IP, returns the winning route using the order in this digest. Done when: it passes the docs' two examples (the peering vs internet gateway one and the static-vs-propagated 172.31.0.0/24 one) plus a local-route case you add.
  5. Diagram a shared VPC. Draw an organization with one network account and three app accounts, mark which subnets are shared, and list who pays for the NAT gateway and the instances. Done when: your answers match the billing section above.
  6. Read-only RAM tour. In an organization where you're allowed, open the RAM console and inspect, without changing anything, the "Resource shares" and "Settings" pages. Done when: you can say whether sharing with AWS Organizations is enabled. Enabling it is done from the management account and changes organization-wide behavior, so only do it deliberately.
