SYSTEMS · CH.11 DIGEST (PART 2)

Databases and Streams: Change Data Capture and Event Sourcing

Part 1 borrowed ideas from databases (durable logs) to improve messaging. This part goes the other way and asks: what if a database's own writes are just a stream of events? That one observation explains how to keep a search index, cache and data warehouse in step with a main database without the race conditions of "just write to all of them", and it leads to event sourcing, where the log of what happened is the real source of truth and the database is a convenient view of it. It stops right before "Processing Streams".

In one line

If you treat the sequence of changes to one system of record as an ordered stream, every other data system can be a follower that replays it, and if you go further and store the events themselves as the truth, the current state becomes something you derive.

The big idea

A replication log (Chapter 5) is already a stream of database write events: the leader produces it and followers apply it, which is why replicas end up identical. The same trick works for the other systems around a database. Real applications use several stores (an OLTP database, a cache, a search index, a warehouse), each holding its own copy of the data in its own shape. Keeping them aligned by having application code write to all of them is fragile. Letting one system be the leader and the others consume its ordered change log is robust. Event sourcing pushes the idea to the application level: record immutable facts about what users did, and derive whatever views you need.

Key terms

  • System of record: the store that holds the authoritative version of the data; other stores are derived from it.
  • Derived data system: a cache, search index, warehouse or similar that holds a transformed copy of the system of record's data.
  • Dual writes: application code writes to each system itself when data changes.
  • State machine replication: if every replica processes the same events in the same order (and processing is deterministic), all replicas end in the same state.
  • Change data capture (CDC): observing all changes written to a database and extracting them in a form other systems can replicate, ideally as a stream.
  • Initial snapshot: a consistent copy of the database tied to a known log position, used to start a new derived system.
  • Log compaction: keeping only the latest record for each key in a log and discarding older ones.
  • Tombstone: a special null record marking a key as deleted.
  • Event sourcing: storing all changes to application state as a log of immutable events written by the application itself.
  • Command vs event: a command is a request that may still be rejected; an event is a fact after the command has been accepted.
  • CQRS (command query responsibility segregation): separating the form in which data is written from the forms in which it is read.
  • Changelog: the log of all changes, representing the evolution of state over time.
  • Human fault tolerance (from Chapter 10): being able to recover from buggy code because history is intact.
  • Excision / shunning: Datomic's and Fossil's names for truly deleting data from an otherwise immutable history.

How it works

Grounding first. An event is a record of something that happened. A user typing a search query is an event, a sensor reading is an event, and so is a write to a database. The fact that something was written can be captured, stored and processed. The source calls the connection between databases and streams "quite fundamental", not just a matter of both putting logs on disk.

The problem: keeping systems in sync

Most non-trivial applications combine technologies: an OLTP database for user requests, a cache for common requests, a full-text index for search, a data warehouse for analytics. Each has its own copy of the data in its own representation, so when an item changes it must change everywhere. Warehouses are usually synced by ETL, often a batch process that copies the whole database, transforms it and bulk-loads it. If full dumps are too slow, a common alternative is dual writes: the application writes to the database, then updates the search index, then invalidates the cache (maybe concurrently).

Dual writes have two serious problems per the source. First, a race condition: two clients update item X at nearly the same time, client 1 to A and client 2 to B. Both write to the database, then to the search index, but unlucky timing interleaves them so the database sees A then B (final B), while the index sees B then A (final A). The two stores are now permanently inconsistent even though no error occurred, and unless you have extra concurrency detection like version vectors you won't even notice. Second, partial failure: one write succeeds and the other fails, again leaving them inconsistent; making both succeed or both fail is the atomic commit problem, which is expensive. The root issue is that there are two "leaders" (the database and the index), neither following the other. It would be better if there were only one leader, the database, with the index as its follower.

Change data capture (CDC)

The obstacle: databases have long treated their replication log as an internal detail, not a public API, so for decades there was no documented way to get the log of changes. CDC is the process of observing all changes written to a database and extracting them so they can be replicated elsewhere, especially as a stream as they are written. Apply the same changes in the same order to a search index and it will match the database. The index and other derived systems are simply consumers of the change stream. CDC essentially makes the source database the leader and the others followers, and a log-based broker (Part 1) is a good transport because it preserves order and avoids the reordering of Figure 2 in Part 1.

Implementation options. Triggers can record changes to a changelog table, but the source says they tend to be fragile and have significant performance overhead. Parsing the replication log can be more robust, though it has its own challenges such as schema changes. The source lists LinkedIn's Databus, Facebook's Wormhole and Yahoo!'s Sherpa as large-scale users of the idea; Bottled Water (PostgreSQL write-ahead log decoding); Maxwell and Debezium (MySQL binlog); Mongoriver (MongoDB oplog); and GoldenGate (Oracle). CDC is usually asynchronous: the source database doesn't wait for consumers before committing. That means a slow consumer barely affects the source, but all the replication-lag issues from Chapter 5 apply.

Initial snapshot. Replaying the entire history rebuilds the database state, but keeping all changes forever takes too much space and replaying takes too long, so the log is truncated. To build a new search index you need a complete copy, and recent changes alone would miss rarely updated items. So you start with a consistent snapshot tied to a known log position (as when setting up a follower), then apply changes after that position. Some CDC tools include snapshots; others leave it manual.

Log compaction offers an alternative. Recall from storage engines: periodically find records with the same key, drop duplicates, keep only the latest, with a tombstone (null value) meaning the key was deleted. The space needed depends only on the current contents, not on how many writes ever occurred. If every CDC event carries a primary key and each update replaces the previous value for that key, then keeping just the latest write per key is enough. To rebuild a derived system, start a new consumer at offset 0 of the compacted topic and scan sequentially: you are guaranteed the latest value for every key (and maybe some older ones), so you get a full copy without another snapshot. The source says Kafka supports this, and that it lets the broker act as durable storage and not just transient messaging.

API support for change streams. Increasingly databases offer change streams as a first-class interface rather than a reverse-engineered one. The source cites RethinkDB (subscribe to query result changes), Firebase and CouchDB (sync based on a change feed), Meteor (uses the MongoDB oplog to update the UI), VoltDB (an output stream modeled as an insert-only table whose committed tuples form the stream), and Kafka Connect (integrating CDC tools for many databases with Kafka).

Event sourcing

Event sourcing came out of the domain-driven design community and shares CDC's idea of storing all changes as a log, but at a different level of abstraction:

  • CDC: the application uses the database mutably (update and delete at will); the log is extracted at a low level, which preserves actual write order and avoids the dual-write race; the application doesn't need to know CDC is happening.
  • Event sourcing: the application logic is built explicitly on immutable events written to an event log. The store is append-only; updates and deletes are discouraged or prohibited. Events reflect things that happened at the application level, not low-level state changes.

The source argues it's a powerful modeling technique: recording a user's action as an immutable event is more meaningful than recording its effect on a mutable database. It makes applications easier to evolve, helps debugging (you can see why something happened), and guards against application bugs. Example: "student cancelled their course enrollment" expresses intent neutrally, while "a row was deleted from enrollments and a reason added to feedback" bakes in assumptions about later use. A new feature like "offer the place to the next person on the waiting list" can be chained off the existing event. Specialized databases like Event Store exist, but a conventional database or log-based broker can be used.

Deriving current state. An event log alone isn't useful to users, who want the current state (the cart's contents, not every change). The application transforms the log into state for display. The transformation can be arbitrary but should be deterministic so replaying gives the same state. Compaction differs from CDC: a CDC update event typically holds the whole new record, so the latest event per key determines the state and older ones can be discarded. An event-sourced event expresses intent ("user did X"), so later events generally don't override earlier ones and you need the full history; compaction isn't possible the same way. Applications typically store snapshots of derived state, but only as a performance optimization; the intent is to keep all raw events and be able to reprocess them.

Commands and events. A user's request starts as a command, which may still fail (an integrity condition is violated, a username is taken, a seat is already reserved). The application validates it; if accepted, it becomes an event, durable and immutable, a fact. Even if the customer later cancels, "they once held that seat" stays true, and the cancellation is a separate later event. A consumer isn't allowed to reject an event, since it's already part of the log and may have been seen by others. So validation must happen synchronously before it becomes an event (for example, a serializable transaction that validates the command and publishes the event atomically), or the request can be split into a tentative-reservation event and a later confirmation event, letting validation happen asynchronously.

State, streams, and immutability

Immutability is what made batch processing safe to experiment with, and it's what makes CDC and event sourcing powerful. How does it square with databases, whose whole nature is changing state? The source: mutable state and an append-only log of immutable events "are two sides of the same coin". State is the result of events over time (seats left are the result of reservations; a balance is the result of credits and debits; a response-time graph is an aggregation of individual response times). The changelog represents the evolution of state. In the source's mathematical framing, state is what you get by integrating an event stream over time, and the change stream is what you get by differentiating state with respect to time (an analogy with limits: the second derivative doesn't seem meaningful). The source quotes Pat Helland: "The truth is the log. The database is a cache of a subset of the log." Log compaction bridges the two by retaining only the latest version of each record.

Advantages of immutable events. Accountants have used append-only ledgers for centuries; mistakes are corrected by adding a compensating transaction, not by erasing the bad entry, which stays for auditing, and figures already published get corrected in the next period. The same helps outside regulated domains: if buggy code writes bad data, an append-only log makes it much easier to diagnose and recover than destructive overwrites. Events also capture more than the final state: a customer adding then removing an item cancels out for fulfillment, but the fact that they considered it may matter for analytics.

Several views from one log (CQRS). Separating mutable state from the event log lets you derive different read-optimized representations, like multiple consumers of a stream. The source cites Druid ingesting directly from Kafka, Pistachio (a key-value store using Kafka as a commit log), and Kafka Connect sinks to various databases and indexes. A new feature can use the log to build a new view and run alongside the old one without touching it, often easier than a schema migration; later you shut down the old one. Storing data is easy if you don't worry about how it will be queried; most schema complexity comes from supporting query patterns. Separating the write form from read forms is sometimes called command query responsibility segregation (CQRS). The source calls the traditional assumption that data must be written in the form it'll be queried "a fallacy"; normalization-versus-denormalization debates matter less when a translation step keeps denormalized views consistent with the log. (Twitter's home timelines, mentioned in Chapter 1, are an example of such read-optimized denormalized state kept in sync by a fan-out service.)

Concurrency control. The biggest downside: consumers are usually asynchronous, so a user may write to the log and then read a view that doesn't reflect it yet (the read-your-writes problem from Chapter 5). Fixes: update the read view synchronously with appending the event, which needs a transaction across both (same storage system, or a distributed transaction), or the linearizable-storage-over-total-order-broadcast approach from Chapter 9. On the plus side, event sourcing can simplify concurrency control: much of the need for multi-object transactions comes from one user action needing changes in several places. If you design an event as a self-contained description of the action, it requires one append, easy to make atomic. And if the log and application state are partitioned the same way, a single-threaded consumer needs no write concurrency control, because the log defines a serial order of events within a partition (events touching several partitions need more work, per Chapter 12).

Limits of immutability. Many systems rely on immutability without event sourcing (multi-version databases, Git and similar). How feasible is keeping all history forever? It depends on churn: mostly-append workloads are easy; workloads with many updates and deletes on a small dataset can make the history grow prohibitively large, with fragmentation and compaction/garbage collection performance becoming crucial. And sometimes you must delete: privacy regulation may require removing a user's personal data, erroneous data may need removal, or sensitive data may leak. Appending a "deleted" event isn't enough; you want to rewrite history as if it was never written. Datomic calls this excision; Fossil calls it shunning. Truly deleting is surprisingly hard since copies live in storage engines, filesystems, SSDs (which often write to a new location) and deliberately immutable backups: deletion is more "making it harder to retrieve" than "making it impossible".

Why it matters

"The cache and the search index disagree with the database" is one of the most common production bugs, and dual writes are a frequent cause. CDC and event logs are the standard remedy, and they underlie many modern pipelines (search indexing, cache invalidation, warehouse feeds, audit trails). Event sourcing also changes how you think about data modeling: store what happened, derive what you need.

Remember this

  • Dual writes can leave systems permanently inconsistent through races or partial failures, with no error to warn you.
  • CDC turns the system of record into the leader and derived systems into followers consuming its ordered change log; start new ones from a snapshot at a known offset, or from a compacted log.
  • Log compaction keeps the latest record per key (tombstones delete), so storage tracks current data size.
  • Event sourcing stores immutable application-level events and derives state deterministically; commands are validated before they become events; compaction doesn't apply the same way.
  • Mutable state and the event log are two views of the same thing; separate write and read forms (CQRS), but expect asynchrony and sometimes a real need to delete.

Try it yourself

  1. Reproduce the dual-write race. Two threads each write a value to a "database" dict and an "index" dict, with random sleeps between. Run until they disagree. Done when you catch a mismatch and can say why no error appeared.
  2. Fix it with a change log. Make the database append each change to a list and have the index consume that list in order. Done when no interleaving of the writers can make the index differ from the database.
  3. Compaction. Write a function that compacts a list of (key, value) records, treating None as a tombstone. Done when the compacted log rebuilds the same dictionary as the full log.
  4. Event-sourced cart. Store only "add" and "remove" events, derive the cart by replaying, and add a snapshot every N events. Done when the snapshot path and the full replay always give the same cart.
  5. Command validation. Build a seat-reservation function that validates a command against current state before appending a "reserved" event, and rejects duplicates. Done when two concurrent requests for the same seat produce exactly one event.
