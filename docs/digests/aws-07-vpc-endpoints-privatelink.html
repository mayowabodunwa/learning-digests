VPC Endpoints: Gateway vs. Interface, and PrivateLink

How a private subnet can talk to S3, DynamoDB or a partner's service without a NAT gateway or any trip through an internet gateway, and why AWS gives you two quite different tools to do it.

In one line

A VPC endpoint is a private doorway from your VPC to a service: a gateway endpoint works by adding a route (S3 and DynamoDB only), while an interface endpoint works by dropping network interfaces with private IPs into your subnets (this is the AWS PrivateLink way).

The big idea

In the earlier topics we built a VPC where a private subnet reaches the outside world through a NAT gateway and an internet gateway. That works for AWS services too, because they're normally reached through public endpoint names. The AWS docs point out that this traffic doesn't leave the AWS network, but it still takes a path through your internet gateway, and you pay for and manage the NAT in the middle. VPC endpoints give you a shorter, private path instead. There are two main flavours to learn first. Gateway endpoints are a routing trick (a special route-table entry pointing at the endpoint). Interface endpoints are real network interfaces sitting in your subnets, reached through DNS. Everything else in this topic (policies, DNS, security groups, costs) hangs off that one distinction.

Key terms

  • VPC endpoint: the object a consumer creates in their VPC to connect privately to a service or resource. There are several types; you pick the one you need.
  • Gateway endpoint: an endpoint type that sends traffic to Amazon S3 or DynamoDB via a route table entry. Per the docs, it does not use AWS PrivateLink.
  • Interface endpoint: an endpoint type that creates network interfaces in your subnets so TCP or UDP traffic reaches an endpoint service. It does use PrivateLink.
  • AWS PrivateLink: the technology that lets clients in your VPC reach services and resources in other VPCs using private IP addresses, as if they were hosted in your own VPC.
  • Endpoint service: what a service provider creates to offer their service in a Region. The provider has to put a load balancer in front of it, and by default nobody can connect until the provider grants permissions to specific AWS principals.
  • Service provider / consumer: the provider owns the service (AWS, an AWS Partner, or another account). The consumer is whoever connects to it from their VPC.
  • Endpoint network interface: a requester-managed network interface that AWS creates in each subnet you choose for an interface endpoint. You can see it in your account, but you can't manage it yourself.
  • Prefix list: a named set of CIDR ranges. For gateway endpoints, AWS owns a prefix list for the service and the route table's destination is that list.
  • Endpoint policy: an IAM-style resource policy attached to the endpoint that says which principals can use that endpoint to do what.
  • Private DNS: an interface endpoint option that makes the service's normal public name resolve to the endpoint's private IPs, using a hidden AWS-managed private hosted zone.
  • Route 53 Resolver: the DNS server Amazon provides for your VPC.
  • Longest prefix match: the rule that the most specific route wins when several routes match a destination.

How it works

Grounding: the problem endpoints solve

Almost every AWS service is reached by a public Regional name, written like service_code.region_code.amazonaws.com (the docs give monitoring.us-east-2.amazonaws.com for CloudWatch). Without endpoints, an instance in a public subnet reaches that name through the internet gateway. An instance in a private subnet needs a NAT gateway in a public subnet, then the internet gateway. The docs say this traffic traverses the internet gateway but does not leave the AWS network. So the point of an endpoint isn't "stop traffic going over the public internet" (the docs say it already stays on the AWS network). The point is that you can reach the service with no internet gateway or NAT device in the path at all, and get extra controls such as endpoint policies.

1. Gateway endpoints: a route, not a machine

What it is. A gateway endpoint gives you connectivity to Amazon S3 and DynamoDB without an internet gateway or NAT device. There is no additional charge for using it. When you create one you choose which route tables it applies to, and AWS adds a route to each: destination is the service's prefix list, target is the endpoint. You can look at that route, but you can't edit or delete it. It disappears when you disassociate the route table or delete the endpoint.

Example. You have a private subnet whose route table sends 0.0.0.0/0 to a NAT gateway, and your app uploads lots of files to S3. You create a gateway endpoint for com.amazonaws.<region>.s3 and select that subnet's route table. Now S3-bound traffic matches the more specific prefix-list route and bypasses the NAT. Other destinations still go through the NAT.

Why the more specific route wins. The docs say routing uses the most specific matching route (longest prefix match). So with a 0.0.0.0/0 route to an internet gateway, the endpoint route still takes precedence for that service in the current Region. Two details from the docs: traffic to the same service in a different Region goes to the internet gateway, because prefix lists are Region-specific; and a route that spells out the exact IP range for the service in the same Region would beat the endpoint route.

Who uses it. It's route-table based, so every instance in subnets tied to an associated route table uses it automatically. Subnets whose route tables aren't associated keep using the public service endpoint.

Your firewalls still apply. The instances still talk to the service's public endpoint address, so (per the docs) the security group must allow the traffic, and you can reference the service's prefix list ID in a security group rule. Network ACLs can't reference prefix lists, so there you list the CIDR ranges from the prefix list. This ties straight back to Topic 4.

Limits worth knowing. A gateway endpoint works only in the Region where you created it, so it must match your buckets' Region. The S3 page says gateway endpoints don't allow access from on-premises networks, from peered VPCs in other Regions, or through a transit gateway; endpoint connections can't be extended out of the VPC, so things across a VPN, peering connection, transit gateway or Direct Connect can't use it. The docs state a default quota of 20 gateway endpoints per Region (adjustable) and 255 per VPC. Creating or modifying one switches network routes and disconnects open TCP connections, so don't do it in the middle of something critical.

2. Interface endpoints and PrivateLink: a doorway in your subnet

What it is. An interface endpoint sends TCP or UDP traffic to an endpoint service, and traffic is directed to it using DNS. For each subnet you choose, AWS creates an endpoint network interface there with a private IP from the subnet's range. The docs say traffic between the endpoint and the service stays within the AWS network without traversing the public internet.

Who it's for. Many AWS services (CloudWatch is the docs' running example), services offered by partners or other accounts, and even your own: a provider creates an endpoint service backed by a load balancer, shares the service name, and adds permissions. The consumer creates the endpoint and the provider can accept or reject the connection request (AWS services accept automatically). The connection only goes one way: consumer to service, the service can't initiate requests back through the endpoint.

Costs. Unlike the gateway type, you're billed for each hour the endpoint is provisioned in each Availability Zone plus per GB processed. Check the AWS PrivateLink pricing page for numbers; I'm not quoting any here.

Security group and subnets. You attach security groups to the endpoint network interfaces (the VPC's default security group if you don't choose). It has to allow the expected traffic from your resources, for example inbound HTTPS if the CLI will call the service. You may pick one subnet per Availability Zone, not several in the same AZ. The docs recommend at least two AZs for production, and note that with a single AZ, if that AZ is impaired, resources in other AZs lose access. Endpoint IPs don't change for the endpoint's lifetime. Also: interface endpoints don't respond to ping, so use nc or nmap to test.

3. DNS: how your app finds the doorway

Creating an interface endpoint gives you Regional and zonal DNS names of the form endpoint_id.service_id.region.vpce.amazonaws.com (and the same with an AZ name added for zonal). You could point apps at those, but the nicer option is private DNS. With private DNS on (and DNS hostnames plus DNS resolution enabled on the VPC), AWS creates a hidden private hosted zone so the service's normal public name resolves to the endpoint's private IPs. Existing apps and SDK calls then use the endpoint with no code change. The docs recommend enabling it for AWS services. One more fact: the endpoint's DNS names are publicly resolvable, but they return private IPs, so they're useless without access to the VPC.

With the Regional name, traffic is spread across healthy endpoint interfaces with round robin; if you prefer to stay in the same AZ, use the zonal name or the interface's IP.

On-premises caveat. The VPC's Route 53 Resolver can't be used from outside the VPC. To reach an interface endpoint from on-premises by name you use Route 53 Resolver endpoints and rules.

4. Endpoint policies: a second lock on the door

An endpoint policy is a resource policy on the endpoint. By default it allows all actions by all principals on all resources through that endpoint. Important: per the docs it does not override or replace identity-based or resource-based policies. Think of it as one more gate that a request has to be allowed through, on top of IAM and, for S3, bucket policies. Details from the docs: it must include a Principal; max size 20,480 characters; changes can take a few minutes; not every service supports endpoint policies (if not, full access is allowed). For gateway endpoints the Principal must be * and you narrow who with the aws:PrincipalArn condition key. Writing the principal as just an account ID grants the account root user only, not all its users and roles.

S3 pairing. Buckets can also insist on your endpoint with a bucket policy: the docs show a Deny with StringNotEquals on aws:sourceVpce (a specific endpoint) or aws:sourceVpc (a VPC). They warn that such a policy also blocks access through the AWS console. And aws:SourceIp doesn't work for requests via a VPC endpoint; use aws:VpcSourceIp. This connects to the S3 access control concept coming up in the S3 rotation.

5. Choosing, and the S3 special case

For S3 and DynamoDB you can use either type. Simplification for beginners: use the free gateway endpoint for traffic from inside the VPC, and reach for an interface endpoint when you need what the gateway can't do (on-premises, other-Region peered VPCs, or via a transit gateway, per the S3 page). Caveat: the right pick depends on your network; read the S3 and DynamoDB comparison pages.

The docs also describe a cost optimisation for S3: with both endpoints present and private DNS enabled only for the inbound Resolver endpoint, on-premises requests use the interface endpoint while VPC requests use the free gateway endpoint. If you enable plain private DNS without that option, VPC traffic also goes through the interface endpoint, and you pay for it.

Other endpoint types exist (Gateway Load Balancer, Resource, Service network, Tunnel). They're named here so you recognise them; this digest doesn't go deep on them.

Comparison at a glance

  • Services: gateway = S3 and DynamoDB. Interface = many AWS services plus partner/own endpoint services.
  • Mechanism: gateway = route table entry to a prefix list. Interface = network interfaces in your subnets, found via DNS.
  • Cost: gateway = no additional charge (docs). Interface = hourly per AZ plus per GB.
  • PrivateLink: gateway = no. Interface = yes.
  • Reach beyond the VPC: gateway = no (not via VPN, peering, TGW, Direct Connect). Interface = it can be used from on-premises (with DNS set up as above).
  • Security groups: gateway = your instances' groups must allow the service (prefix list). Interface = a group on the endpoint interfaces.

Why it matters

Endpoints are how you build private-subnet architectures that don't need a NAT for AWS-service traffic, lock buckets down to your VPC, and consume or sell services across accounts safely. They also touch everything we've covered: route tables and longest-prefix routing (Topic 1), security groups and NACLs (Topic 4), and later DNS (the next VPC concept) and S3 access control.

Remember this

  • Gateway endpoint = a route to a prefix list, S3 and DynamoDB only, no extra charge, doesn't use PrivateLink.
  • Interface endpoint = ENIs with private IPs in your subnets, found via DNS, billed per AZ-hour plus data.
  • Private DNS lets unchanged apps use an interface endpoint through the service's normal name.
  • An endpoint policy adds a gate; it doesn't replace IAM or bucket policies. Default is allow all.
  • Use at least two AZs for interface endpoints in production (AWS recommendation).

Try it yourself

  1. Gateway endpoint for S3. In a test VPC with a private subnet, create a gateway endpoint (console, or aws ec2 create-vpc-endpoint --vpc-id <vpc> --service-name com.amazonaws.<region>.s3 --route-table-ids <rtb>). Done when: you can see the new prefix-list route in the route table and that you can't edit it.
  2. Prove the bypass. Remove the NAT route from that private subnet's route table (in a throwaway VPC) and, from an instance with an appropriate role, list a bucket in the same Region. Done when: S3 works but a call to some other service times out. Note: this one needs a live account, and I haven't run it for you.
  3. Read the DNS entries. Create an interface endpoint for a service of your choice with private DNS on, then run aws ec2 describe-vpc-endpoints --vpc-endpoint-id <id> --query VpcEndpoints[*].DnsEntries. Done when: you can label the Regional, zonal and private-hosted-zone entries. (Interface endpoints cost money while they exist: delete it afterwards.)
  4. Resolve from inside and outside. From an instance in the VPC and from your laptop, resolve the service's public name. Done when: you can explain why the VPC answer is a private IP, and what happens to the laptop's answer.
  5. Lock a bucket to your endpoint. Write a bucket policy with a Deny and aws:sourceVpce as in the docs' example, applied to a scratch bucket. Done when: access from the instance works and access from your laptop is denied. Warn yourself first that the console is blocked too; keep a way to remove the policy.
  6. Paper design. Draw a VPC with two AZs, a private app tier, S3 via gateway and CloudWatch via interface endpoint. Done when: you've marked every route-table entry, security group rule, and subnet involved.
