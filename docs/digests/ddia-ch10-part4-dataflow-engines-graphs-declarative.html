Beyond MapReduce: Dataflow Engines, Graphs, and Declarative Batch

Parts 1 to 3 built up MapReduce as a deliberately blunt tool. This final part is about what happened next. The same chapter says MapReduce is robust but sometimes orders of magnitude slower than alternatives, and it walks through why: writing every intermediate result to the distributed filesystem. Then come the replacements (dataflow engines), a special case MapReduce is bad at (graphs and iteration), and the move toward high-level, declarative APIs. It ends with the chapter's own Summary, which I use to tie the whole chapter together.

In one line

Dataflow engines treat a whole multi-step workflow as one job and pass intermediate data around in memory or on local disk, recomputing it after a failure instead of storing it durably; graph jobs need iteration, which has its own model; and high-level declarative APIs let the system choose the join algorithm for you.

The big idea

MapReduce's habit of fully writing each job's output to the distributed filesystem makes failures easy to recover from, but it forces waiting, redundant work and heavy replication. The newer engines keep the same basic recipe (functions applied record by record, work split by partitioning) while removing that forced bookkeeping. The cost is a different fault tolerance story: lost intermediate data must be recomputed, which only works smoothly if the computation is deterministic. Underneath all of it is the chapter's one durable insight: a batch job reads bounded input and produces derived output without modifying the input.

Key terms

  • Materialization: eagerly computing a result and writing it out (to files) rather than computing it on demand. Here, writing a job's intermediate output to the distributed filesystem.
  • Intermediate state: data passed from one stage or job to the next, not meant as a final product.
  • Straggler: a task that takes much longer than its peers; a following stage that must wait for all tasks is held up by it.
  • Dataflow engine: an execution engine (Spark, Tez and Flink are the source's examples) that handles a whole workflow as one job and models the flow of data through stages.
  • Operator: a generalization of map and reduce; a function in a dataflow job that can be wired to others in flexible ways.
  • DAG (directed acyclic graph): a set of nodes with one-way links and no loops. Dataflow engines arrange operators as a DAG; the data itself is typically relational-style tuples, which is not the same as graph processing.
  • RDD (resilient distributed dataset): Spark's abstraction for tracking the ancestry of data (which inputs and operators produced it).
  • Checkpoint: periodically saving state to durable storage so work can resume from there.
  • Deterministic: given the same input, always produces the same output.
  • Pipelined execution: passing output to the next operator incrementally, without waiting for the input to be complete.
  • PageRank: a graph algorithm estimating a web page's popularity from what links to it.
  • Pregel / BSP (bulk synchronous parallel): a model for graph batch processing in which vertices send messages to each other in rounds.
  • Superstep (iteration): one round in which every vertex processes the messages sent to it in the previous round.
  • Declarative: saying what you want (a join) and letting the system decide how.
  • Cost-based query optimizer: a component that estimates the cost of alternative execution plans and picks one, even reordering joins.
  • Vectorized execution: processing data in a tight loop over batches, friendly to CPU caches and avoiding per-record function calls.
  • Bounded / unbounded input: bounded means known, fixed size, so a job knows when it has read everything; unbounded means never-ending.

How it works

Grounding first. The chapter opened with the remark that MapReduce is a learning tool: clear and simple as an abstraction over a distributed filesystem, "simple" meaning easy to understand, not easy to use. Writing a complex job in raw MapReduce is laborious (you'd implement joins yourself), which is why Pig, Hive, Cascading and Crunch were built on top. But layering abstractions doesn't fix problems with the execution model itself, and that's where this part starts.

Materialization of intermediate state

Every MapReduce job is independent. Its contact with the outside world is its input and output directories; to chain jobs, point the second job's input directory at the first job's output, and have an external scheduler start the second only after the first completes. That's sensible when the output is a dataset you want to publish by name and reuse widely (even by other teams). But often a job's output is only used by one other job, maintained by the same team. Then the files are just intermediate state, and a workflow of 50 to 100 jobs (the source's figure for recommendation systems) has a lot of it. Writing it out in full is called materialization.

Compare the Unix pipe from Part 1: it streams output to input with only a small in-memory buffer. The source lists three downsides of the MapReduce approach by comparison:

  • No overlap. A job can start only when every task of the preceding jobs has finished, whereas piped processes start together and consume output as it is produced. Stragglers (due to skew or uneven load) slow the whole workflow.
  • Redundant mappers. Often a mapper just reads back the file a reducer just wrote and prepares it for partitioning and sorting. If the reducer output were already partitioned and sorted suitably, reducers could be chained directly.
  • Overkill replication. Intermediate files on the distributed filesystem are replicated across nodes, which is often more than temporary data needs.

Dataflow engines

Several engines were built to fix this; the best known are Spark, Tez and Flink. They differ in design but share one idea: handle an entire workflow as one job. Like MapReduce, they call a user-defined function on one record at a time on a single thread, parallelize by partitioning inputs, and copy one function's output over the network to become the next one's input. Unlike MapReduce, the functions (now called operators) needn't alternate strictly between map and reduce. The engine offers options for connecting operators:

  • Repartition and sort by key, like the MapReduce shuffle. This supports sort-merge joins and grouping.
  • Partition several inputs the same way but skip the sorting. This suits partitioned hash joins, where partitioning matters but order doesn't (building a hash table randomizes order anyway).
  • Send the same output of one operator to all partitions of the next, which is what a broadcast hash join needs.

The source lists advantages over MapReduce (this style is based on research systems like Dryad and Nephele):

  • Sorting and other expensive work happens only where actually required, not by default between every map and reduce.
  • No unnecessary map tasks, since a mapper's work can often fold into the preceding reduce operator (a mapper doesn't change partitioning).
  • Because joins and data dependencies are declared explicitly, the scheduler sees what data is needed where and can optimize locality, for example placing a consumer on the same machine as its producer so data moves through a shared memory buffer, not the network.
  • Intermediate state usually only needs to live in memory or on local disk, which needs far less I/O than writing replicated copies to HDFS. (MapReduce already does this for mapper output; dataflow engines generalize it.)
  • Operators can start as soon as their input is ready.
  • Existing JVM processes can be reused, cutting startup cost (MapReduce launches a new JVM per task).

The source says dataflow engines can implement the same computations and usually run significantly faster. Since operators generalize map and reduce, the same code can run on either: workflows written in Pig, Hive or Cascading can be switched from MapReduce to Tez or Spark by a configuration change, per the source. Tez is a fairly thin library relying on the YARN shuffle service to move data; Spark and Flink are big frameworks with their own network layer, scheduler and APIs.

Fault tolerance without durable intermediate files

MapReduce gets easy fault tolerance from the durable intermediate files: a failed task is restarted elsewhere and reads the same input again. Spark, Flink and Tez skip that, so when a machine dies and its intermediate state is lost, they recompute it from data still available (an earlier stage if possible, else the original input, normally on HDFS). To do that, the framework must remember how each piece was computed: which input partitions, which operators. Spark's RDD abstraction tracks that ancestry; Flink checkpoints operator state so a faulty operator can resume.

Here determinism matters. If a recomputed result differs from the lost one and some of the lost data had already gone downstream, downstream operators face contradictions. The usual solution for nondeterministic operators is to kill the downstream operators too and rerun them, which can cascade. So it's better to make operators deterministic, but nondeterminism sneaks in easily: many languages don't guarantee iteration order over a hash table, probabilistic algorithms use random numbers, and the system clock or external data sources vary. The source's suggested fix for the random one: pseudorandom numbers with a fixed seed.

And recomputation isn't always the right answer. If the intermediate data is much smaller than the source, or the computation is very CPU-heavy, it's probably cheaper to materialize it to files than recompute.

Pipelining and what still gets materialized

Using the Unix analogy: MapReduce is like writing each command's output to a temp file; dataflow engines look more like pipes, and Flink especially is built around pipelined execution. A sort is the exception: it can't produce output until it has consumed all input, since the last record read might belong first. So sorting operators must accumulate state, but many other parts of a workflow can pipeline. And inputs and final outputs still usually live on the distributed filesystem; inputs are immutable and the output is completely replaced, as with MapReduce. The saving is that intermediate state isn't written out as well.

Graphs and iterative processing

Chapter 2 treated graphs as a data model for OLTP-style queries (find a few vertices). In batch, you might process a whole graph offline: recommendation engines, ranking, and PageRank (estimating a page's popularity from what links to it, part of the formula that orders search results). Two naming traps. A dataflow engine's operators form a DAG, but that's the flow of data between operators; the data itself is typically relational-style tuples. In graph processing the data itself is a graph. The source calls this "another unfortunate naming confusion".

Many graph algorithms work edge by edge: join a vertex with its neighbour, propagate information, and repeat until a condition holds (no more edges to follow, or a metric converges). The chapter 2 example of finding all locations within North America (a transitive closure) was of this kind. You can store a graph in a distributed filesystem as lists of vertices and edges, but plain MapReduce does a single pass, so "repeat until done" has to be done by an external scheduler: run one step as a batch job, check the completion condition, and if not done, run another. It works, but MapReduce reads the entire input and writes a whole new output every round, even if only a small part of the graph changed.

The Pregel (bulk synchronous parallel) model

The popular optimization is BSP, known as Pregel after Google's paper; the source names Apache Giraph, Spark's GraphX and Flink's Gelly as implementations. The idea echoes the mapper-sends-messages picture: a vertex sends a message to another vertex, typically along an edge. In each iteration the framework calls a function for each vertex with the messages sent to it (like a reducer call). The difference: a vertex remembers its state in memory between iterations, so the function only processes new messages, and where no messages flow, no work is done.

The source compares it to the actor model, if each vertex is an actor, with two differences: vertex state and messages are fault-tolerant and durable, and communication happens in fixed rounds (all messages from the previous iteration are delivered in the next), which actors don't normally promise.

Fault tolerance. Vertices can only communicate through messages, never by querying each other directly, so messages can be batched and there is less waiting; the only wait is between iterations (the previous one must finish and its messages be delivered). The source says Pregel implementations guarantee messages are processed exactly once at the destination vertex in the next iteration, even though the underlying network may drop, duplicate or delay them. This works through periodic checkpointing of all vertex state at the end of an iteration. If a node fails, the simplest recovery is rolling the whole computation back to the last checkpoint; with a deterministic algorithm and logged messages, you can recover only the lost partition.

Parallel execution. A vertex doesn't know which machine it is on; it sends to a vertex ID, and the framework routes. Ideally vertices that talk a lot are colocated, but that's hard, so in practice graphs are often partitioned by arbitrary vertex ID. The result is a lot of cross-machine traffic, and intermediate state (messages) is often bigger than the original graph. The source's practical advice: if your graph fits in memory on one computer, a single-machine algorithm will quite likely beat a distributed one; if it fits on one machine's disks, single-machine tools like GraphChi are viable; only beyond that is a distributed approach such as Pregel "unavoidable".

High-level APIs and languages

The source says execution engines have matured so much that the physical operation of batch jobs is "more or less solved" (petabytes of data on clusters of over 10,000 machines), so attention moved to the programming model, efficiency, and the range of problems solved. High-level languages (Hive, Pig, Cascading, Crunch) exist because hand-written MapReduce is laborious, and could move to Tez without a rewrite; Spark and Flink have their own dataflow APIs, inspired by FlumeJava. These use relational-style building blocks (join, group, filter, aggregate), implemented internally with the algorithms from Part 3. Benefits: less code, and interactive use, where you write analysis incrementally in a shell and run it often, which is handy for exploring data and reminiscent of the Unix philosophy.

The move toward declarative query languages

If you state a join as a relational operator instead of coding it, the framework can inspect the inputs and choose the join algorithm itself. The source says Hive, Spark and Flink have cost-based optimizers that do this, even reordering joins to minimize intermediate state. That's convenient given how much the algorithm choice matters and how many there are to remember.

But the batch world is not fully declarative like SQL. MapReduce is built on callbacks to user-defined functions that may run arbitrary code, which lets you draw on a large ecosystem of libraries (parsing, language analysis, image analysis, statistics). The source says that freedom has long distinguished the MapReduce lineage from MPP databases, whose user-defined functions tend to be cumbersome and poorly integrated with package managers. Dataflow engines found value in adding declarative features beyond joins: a callback that merely filters or picks fields has per-record call overhead, whereas a declarative form lets the optimizer read only the needed columns from column-oriented storage and use vectorized execution (the source names Hive, Spark DataFrames and Impala; Spark generates JVM bytecode and Impala uses LLVM for native inner loops). The result, per the source: batch frameworks begin to look like MPP databases and achieve comparable performance, while keeping flexibility for arbitrary code and formats.

Specialization for different domains

Standard patterns repeat, so reusable building blocks emerge. MPP databases traditionally served business-intelligence reporting, but batch is used more widely: statistical and numerical algorithms for machine learning (the source names Mahout on MapReduce, Spark and Flink, and MADlib inside an MPP database) and spatial algorithms like k-nearest neighbours (finding items close to a given one in a multi-dimensional space), plus approximate string search for genome analysis. The closing observation: as batch systems gain declarative operators and MPP databases become more programmable, the two look more alike, "all just systems for storing and processing data".

The chapter in review (its Summary)

Using my own words on the chapter's summary:

  • Design philosophy carried over from Unix: immutable inputs, outputs that feed unknown future programs, and complex problems solved by composing small tools. In Unix the uniform interface is files and pipes; in MapReduce it is a distributed filesystem. Dataflow engines add pipe-like transport, but initial input and final output are still usually on the distributed filesystem.
  • Two main problems for batch frameworks. Partitioning: mappers are split by input blocks, their output is repartitioned, sorted and merged into a configurable number of reducer partitions so related data meets; post-MapReduce engines avoid sorting unless required. Fault tolerance: MapReduce writes to disk often (easy task recovery, slower when nothing fails); dataflow engines keep more in memory and recompute more after a failure, which deterministic operators keep small.
  • Joins recap: sort-merge, broadcast hash and partitioned hash. They are mostly used inside MPP databases and dataflow engines too.
  • A deliberately restricted model: callbacks are assumed stateless with no externally visible side effects beyond their output. That lets the framework retry safely and discard failed attempts' output (if several attempts at a partition succeed, only one becomes visible). The framework can then make the final output the same as if no faults happened, semantics the source calls much stronger than what online services get when they write to databases as a side effect.
  • The defining feature: input is bounded (known fixed size, such as a set of log files or a database snapshot at one moment), so the job knows when it's done and eventually completes. The next chapter handles unbounded streams, where a job never completes.

Why it matters

If you meet Spark, Flink or a SQL-on-Hadoop tool, you now know why they exist: they remove the per-step disk writes and forced sorts of MapReduce, and let an optimizer choose join algorithms. The determinism rule explains why seeded randomness and clock-free logic matter in data pipelines. And the "bounded versus unbounded" idea is the doorway to stream processing.

Remember this

  • MapReduce materializes every intermediate result on the distributed filesystem: easy recovery, but waiting for whole stages, redundant mappers, and heavy replication.
  • Dataflow engines (Spark, Tez, Flink) run a whole workflow as one job with flexible operators, keep intermediate state in memory or local disk, and sort only when needed.
  • Without durable intermediates they recompute lost data, so deterministic operators matter. Recompute is not always cheaper than materializing.
  • Iterative graph work fits the Pregel model: per-vertex state kept across rounds, messages along edges, checkpoints at round ends. If the graph fits on one machine, single-machine code may well be faster.
  • Declarative APIs let optimizers choose joins and read only needed columns, while arbitrary-code callbacks remain the batch world's flexibility. And batch input is bounded.

Try it yourself

  1. Materialize vs pipeline. Build the same three-step transform (parse, filter, count by key) two ways in a language you like: each step writing a full temp file for the next, and as chained generators. Measure time and peak memory on a large generated file. Done when you can explain which cost differences you saw, noting that one machine is not a cluster.
  2. Determinism check. Write a step that assigns a random bucket to each record. Run it twice and diff the output; then seed the generator and diff again. Add a second nondeterministic leak (iterate a set, or read the clock) and find it. Done when two runs produce identical output.
  3. Recompute from lineage. Represent a pipeline as a list of named steps, each with its input name. Delete an intermediate result and write a function that rebuilds it from the nearest surviving ancestor. Done when deleting any middle result gives back identical data.
  4. Mini Pregel. Implement rounds where each vertex keeps a label, receives messages, and forwards the smaller label to its neighbours only when it changes, to find connected components of a small graph. Done when it halts by itself (no messages left) and matches a plain graph search.
  5. Let the optimizer choose. Write a function join(a, b) that picks a broadcast hash join when one side has fewer than N records and a sort-merge join otherwise. Done when both paths agree on the same test data. Treat the threshold as yours; the source gives no number.
