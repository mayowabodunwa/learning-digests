EC2 Instances & AMIs

The template and the copy: an AMI is the frozen recipe, an instance is a running server baked from it. Once that relationship clicks, instance types, launching, and lifecycle states all fall into place around it.

In one line

An EC2 instance is a virtual server that boots from a template called an AMI, the instance type you pick decides its hardware, and understanding the states an instance moves through (and what an AMI actually freezes in place) is what lets you launch, rebuild, and tear down servers on purpose instead of by accident.

The big idea

Amazon EC2 (Elastic Compute Cloud) gives you on-demand virtual servers, called instances, that you can launch, configure, and shut down as you need them. Two choices define almost everything about a new instance before it even boots: which AMI (Amazon Machine Image) you launch from, which fixes the operating system and any software baked into the image, and which instance type you pick, which fixes the hardware (CPU, memory, network, and sometimes GPU) available to run it. From there, an instance moves through a small set of well-defined states (starting, running, stopping, gone), and you can also go the other direction: take a running, customized instance and freeze it back into a brand-new AMI so you can launch more copies of it later.

Key terms

  • Instance — a virtual server running in the AWS cloud. Per AWS's own definition, it's what you'd use "the way that you'd use a computer sitting in front of you."
  • Instance type — the hardware configuration you choose for an instance (compute, memory, storage, network, sometimes GPU). Every instance type belongs to an instance family that shares a general shape of capability, like general purpose or compute optimized.
  • AMI (Amazon Machine Image) — a template that provides the software needed to boot an instance, including the operating system and any additional software packaged in, plus a block device mapping describing what storage to attach.
  • Block device mapping — the part of an AMI (and of a launched instance) that specifies which storage volumes get attached, and how, when an instance boots from it.
  • Root volume — the volume that holds the image an instance boots from. It's either an EBS volume (an Amazon EBS-backed AMI) or an instance store volume built from a template in Amazon S3 (an Amazon S3-backed AMI).
  • Snapshot — a point-in-time copy of an EBS volume. Creating an AMI from an instance works by snapshotting that instance's root volume (and any other attached EBS volumes).
  • Launch permissions — who is allowed to launch an instance from a given AMI: public (any AWS account), explicit (specific accounts or organizations the owner named), or implicit (the owner's own, automatic permission on their own AMI).
  • Virtualization type — HVM (hardware virtual machine) or PV (paravirtual), baked into the AMI. It decides how an instance boots and whether it can use hardware extensions like enhanced networking or GPU passthrough.
  • Hypervisor — the underlying virtualization technology the physical host runs. AWS documents two: Nitro (all current-generation instance types) and Xen (older, previous-generation types).
  • Key pair — the credentials used to prove your identity when connecting to an instance. AWS stores the public key on the instance; you keep the private key.
  • Security group — a virtual firewall attached to an instance that controls which inbound and outbound traffic is allowed to and from it.
  • Instance state — where an instance sits in its lifecycle: pending, running, stopping, stopped, shutting-down, or terminated.
  • Hibernate — a special stop that also saves the instance's RAM contents to its EBS root volume, so a later start restores memory state, not just disk state.
  • Termination protection — a setting that blocks an instance from being terminated (through the console, CLI, or API) until you turn it off.
  • DeleteOnTermination — an attribute on an attached EBS volume controlling whether that volume is deleted automatically when the instance it's attached to is terminated. It defaults to true for the root volume.

How it works

Here's the grounding picture before the details: an EC2 instance isn't a single, monolithic thing you configure once. It's assembled from a small set of independent pieces, an AMI (what software boots), an instance type (what hardware runs it), storage, a key pair, and a security group, and each of those pieces has its own rules about what can and can't change after launch. AWS's own overview lists these as EC2's core features: instances, AMIs, instance types, EBS volumes, instance store volumes, key pairs, and security groups. Everything below is really just unpacking that list one piece at a time.

1. What an EC2 instance actually is

An EC2 instance is a virtual server in the AWS cloud. When you launch one, the instance type you specify determines the hardware available to it: AWS's own phrasing is that "each instance type offers a different balance of compute, memory, network, and storage resources." Amazon EC2 dedicates some of a host computer's resources (CPU, memory, instance storage) to a particular instance, while sharing others (network, disk subsystem) among the instances on that host; if every instance tries to use as much of a shared resource as possible, each gets an equal share, but an instance can burst above that share while the resource is underused elsewhere. That's part of why identical-looking instance types can occasionally feel like they perform slightly differently under heavy shared load.

Once launched, you reach an instance through a key pair (AWS holds the public half, you hold the private half, and you use it to authenticate an SSH connection on Linux or to decrypt an administrator password for RDP on Windows) and you control what can reach it at all through a security group, a virtual firewall that AWS describes as letting you "specify the protocols, ports, and source IP ranges that can reach your instances, and the destination IP ranges to which your instances can connect."

2. Instance types — the hardware knob

An instance type name isn't arbitrary. AWS's instance type naming guide breaks a name like c7gn.xlarge into positions: the first character of the family is the series (here, c for compute optimized), the next character is the generation (7), any characters after that are options describing extra capabilities (gn, in this example), and everything after the period is the size (xlarge, or values like small, 4xlarge, or metal for a bare-metal instance). Learning to read a name this way means you can look at almost any instance type and get a rough sense of its shape without looking anything up.

Per AWS's current instance types documentation, instance families group into broad categories: general purpose (for example the M and T series), compute optimized (the C series), memory optimized (the R and X series, among others), storage optimized (the D and I series), accelerated computing (G, P, Inf, and Trn series, built for GPU workloads and machine learning training or inference), and a dedicated high performance computing category (the Hpc series). Most current-generation instance types across these families run on the Nitro hypervisor; a handful of older, previous-generation types (documented separately) still run on the older Xen hypervisor.

3. What an AMI actually is, and how it relates to an instance

An AMI is the template you must specify to launch an instance: it "provides the software that is required to set up and boot" the instance, and it must be compatible with the instance type you're launching. An AMI is specific to a Region, an operating system, a processor architecture, a root volume type, and a virtualization type, which is why you sometimes can't reuse an AMI you found in one Region or built for one processor architecture somewhere else without copying or rebuilding it.

The relationship between an AMI and an instance is one-to-many by design: you can launch as many instances as you want from a single AMI when you need several servers with identical configuration, or launch from different AMIs when you need instances configured differently. Nothing about launching an instance changes or uses up the AMI; it's a read-only template you launch copies from, over and over.

Two characteristics decide how an AMI's storage and boot process behave. First, root volume type: an Amazon EBS-backed AMI boots from an EBS volume created out of an EBS snapshot (supported for both Linux and Windows), while an Amazon S3-backed AMI boots from an instance store volume built from a template stored in S3 (Linux only, and AWS documents these as end-of-life, only relevant on a handful of older instance types like C1, C3, D2, I2, M1, M2, M3, R3, and X1). The practical difference that matters most day to day: an EBS-backed instance can be stopped and later restarted, while an S3-backed instance can only be running or terminated, with no stopped state in between, and any data on its instance store root volume disappears the moment it stops being used. Second, virtualization type: HVM (hardware virtual machine) AMIs boot a fully virtualized hardware set and can use hardware extensions like enhanced networking and GPU processing; PV (paravirtual) AMIs use a special boot loader and can't use those extensions. All current-generation instance types support HVM only, and AWS recommends HVM for best performance.

Who can even use an AMI comes down to its launch permissions: public (any AWS account), explicit (specific accounts, organizations, or organizational units the owner named), or implicit (the owner's automatic permission on their own AMI). This is also the mechanism behind the huge library of AMIs AWS and the EC2 community publish publicly, and behind AMIs sold through the AWS Marketplace.

4. The instance lifecycle — where a running server actually sits

Every instance sits in exactly one of six documented states at any moment: pending (preparing to enter running, whether from a fresh launch or a restart), running (ready for use and billed by the second), stopping (preparing to stop), stopped (shut down, not billed for instance usage, can be started again at any time), shutting-down (preparing to terminate), and terminated (permanently deleted, can't be started, not billed). AWS's billing rule is blunt and worth remembering exactly: you're billed per second (one-minute minimum) the moment an instance enters running, and you stop being billed for instance usage as soon as it enters stopping or shutting-down, even before it fully reaches stopped or terminated. EBS volume storage, though, keeps costing money regardless of the instance's own state.

It helps to separate four actions that all sound similar but do different things to the instance underneath. A reboot stays on the same host computer, keeps the public and private IP addresses and any instance store data, and doesn't reset the per-second billing clock. A stop/start (EBS-backed instances only) moves the instance to a new host computer (though sometimes it stays put), erases instance store data, keeps the private IP (and any Elastic IP), but usually assigns a new public IPv4 address, and starts a fresh billing period when it runs again. Hibernate follows the same stopping-to-stopped path as a plain stop, but also signals the OS to suspend to disk, saving RAM contents onto the EBS root volume; AWS bills a hibernating instance while it's in stopping (unlike a plain stop), but not once it's fully stopped. Terminate is the one-way door: AWS's own warning is direct, "terminating an instance is permanent and irreversible," the instance can't be recovered, any EBS volumes with DeleteOnTermination set (true by default for the root volume) are deleted permanently, and all instance store data is lost. You can turn on termination protection to block an accidental terminate call through the console, CLI, or API until you explicitly disable it.

5. Building your own AMI from a running instance

You're not limited to AMIs AWS or someone else published. AWS documents a clear workflow for creating your own Amazon EBS-backed AMI: start from an existing AMI (from AWS, the Marketplace, or one you already have access to), launch an instance from it, customize that instance exactly the way you want (install software, copy data, attach extra EBS volumes), and then create a new image from it. When you do that, Amazon EC2 (by default) powers the instance down first so everything is stopped and consistent, though you can tell it not to reboot if you're confident the instance's file system is already in a safe state to snapshot. During image creation, EC2 takes snapshots of the instance's root volume and any other attached EBS volumes, and you're billed for those snapshots until you deregister the AMI and delete them. The whole process can take anywhere from a few minutes up to (per AWS's own documentation) 24 hours depending on volume size, and creating snapshots of your volumes ahead of time can speed up a later AMI creation since only the incremental changes need to be captured.

Once the new AMI's status shows available, launching from it creates a fresh EBS root volume (built from your new snapshot) and reattaches any additional volumes your block device mapping describes; instance store volumes on the new instance start empty, they never carry data over from the instance you originally customized. A related option worth knowing about: if you already have a snapshot of a root volume (say, from a backup routine), you can register an AMI directly from that snapshot instead of going through a live instance at all.

Why it matters

This is the foundation everything else in EC2 sits on top of. Auto Scaling Groups (covered next) launch new instances from an AMI you specify, using an instance type you specify, so a custom AMI with your application pre-installed is what lets a scaling event bring up a working server in minutes instead of running a setup script from scratch every time. Understanding the lifecycle states also saves real money and real headaches: knowing that a stopped instance still bills you for its EBS storage (but not compute), that terminated is permanent, and that termination protection exists, is the difference between a predictable AWS bill and an unpleasant surprise, or between "oops" and a recoverable mistake.

Remember this

  • An AMI is a read-only template (OS, software, block device mapping); an instance is a running server launched from one. Many instances can come from one AMI, unchanged.
  • An instance type name encodes series, generation, options, and size (like c7gn.xlarge); the family it belongs to (general purpose, compute optimized, memory optimized, storage optimized, accelerated computing, or HPC) tells you its general shape.
  • An instance moves through six states: pending, running, stopping, stopped, shutting-down, terminated. You're billed once it's running, and billing stops the moment it starts stopping or shutting down, before it fully reaches stopped or terminated.
  • Reboot, stop/start, hibernate, and terminate are four different operations with different consequences for IP addresses, instance store data, RAM, and whether you can undo it. Only terminate is permanent and irreversible.
  • You can freeze a customized instance back into a new AMI (via a root-volume snapshot), then launch as many new instances from it as you want, with the customization already baked in.

Try it yourself

  1. Launch your first instance from a public AMI. Using the free tier, launch a Free Tier-eligible instance type from a Free Tier-eligible Amazon Linux AMI, with a new key pair and the default security group, then connect to it over SSH. Done when: you're at a shell prompt inside the instance, and you can point to which part of the launch screen set the AMI versus the instance type. Cost caution: stay inside Free Tier eligible options and remember to stop or terminate the instance when you're done for the day.
  2. Watch the lifecycle states happen, not just read about them. Stop your instance, note its state moves to stopping then stopped, then start it again and watch pending turn into running. Done when: you've seen all four of those states appear for your own instance (in the console or via aws ec2 describe-instances), and you can explain in your own words why you weren't billed for compute time while it sat stopped.
  3. Compare reboot vs. stop/start on the same instance. Note the instance's public IPv4 address, then reboot it and check whether the address changed; then stop and start it and check again. Done when: you've observed the public IP survive a reboot but usually change after a stop/start, and you can explain why using the root-volume-vs-host-computer distinction from this digest.
  4. Create a custom AMI from a configured instance. On a running instance, install a package or write a marker file, then use the console's Actions -> Image and templates -> Create image (or the create-image CLI command) to snapshot it into a new AMI, and launch a second instance from that new AMI. Done when: the second instance already has your installed package or marker file present the moment it boots, with no manual setup step repeated.
  5. Turn on termination protection, then turn it off. Enable termination protection on an instance, attempt to terminate it (expect it to fail), then disable protection and terminate it for real. Done when: you've seen the termination attempt get blocked once, and successfully terminated the instance after removing the protection.
  6. Read an instance type name cold. Pick any three instance type names you can find in the console's launch wizard (not necessarily ones mentioned in this digest) and, without looking anything up, say out loud what family, generation, and size each one represents. Done when: you can do this for all three without checking a reference.
