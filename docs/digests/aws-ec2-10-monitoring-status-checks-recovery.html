AWS EC2 · CONCEPT 10 DIGEST

Instance Monitoring, Status Checks and Auto Recovery

Instances fail in two broad ways: the AWS side under them breaks, or the thing you put on them breaks. EC2 gives you built-in tests that tell those apart, metrics that show how busy an instance is, and two recovery mechanisms that can move a struggling instance to healthy hardware. This is the last EC2 concept in the series, and it ties together alarms, Systems Manager, Auto Scaling and storage.

In one line

EC2 runs status checks every minute (system, instance, attached EBS, plus opt-in application checks), publishes CloudWatch metrics (5-minute by default, 1-minute with detailed monitoring), and can automatically recover an instance when the system check fails, but recovery is a single-instance repair, not a substitute for a resilient design.

The big idea

The distinction that unlocked this topic for me: who has to fix it. EC2's two classic checks are named after the owner of the problem. A failed system status check means something is wrong with the AWS host the instance runs on, so AWS (or a move to another host) fixes it. A failed instance status check means something is wrong inside your instance (networking config, memory, file system, kernel), so you fix it.

Once you know that, recovery is easy to reason about: automatic recovery reacts to system check failures only. The docs say plainly that it "does not operate if only the instance status check fails".

Cost notes in words only: status check metrics are free at 1-minute frequency; detailed monitoring charges per metric sent to CloudWatch; CloudWatch action based recovery might incur CloudWatch charges; simplified automatic recovery has no additional cost. No dollar figures.

Key terms

  • Status check: an automated EC2 test of instance health, run every minute, giving pass or fail.
  • System status check: tests the AWS systems the instance runs on.
  • Instance status check: tests the software and network configuration of your own instance.
  • Impaired: the overall status when one or more checks fail (versus OK when all pass).
  • Basic / detailed monitoring: 5-minute vs. 1-minute metric periods for most EC2 metrics.
  • CloudWatch metric / alarm: a time series of measurements, and a rule that reacts when it crosses a threshold.
  • Instance recovery: moving an instance from a faulty host to a different host.
  • Simplified automatic recovery: the AWS-managed, on-by-default recovery mechanism.
  • CloudWatch action based recovery: a recovery you configure through a CloudWatch alarm action.
  • Volatile memory (RAM): working memory, emptied when the instance is moved.
  • Health Dashboard: where AWS posts events about your resources, including recovery successes and failures.

How it works

0. Grounding: what does "healthy" mean for a virtual server?

An instance can be "running" (in the lifecycle sense from the first digest) and still be useless: unreachable, out of memory, or on a sick host. State tells you what EC2 intends; status checks tell you what actually works. The CloudWatch metrics add the numbers (CPU, network) over time.

1. The five status checks

EC2 offers five types. Four are managed by EC2 and cannot be disabled or deleted; application checks are opt-in. All run every minute and return pass or fail; all pass means OK, otherwise impaired.

  • System status check (AWS side): examples of causes in the docs are loss of network connectivity, loss of system power, software issues on the physical host, and hardware issues on the host affecting reachability. Fix options: wait for AWS, or for an EBS-backed instance stop and start it, which in most cases migrates it to a new host. (Instance-store-backed Linux instances: terminate and replace.) Metric: StatusCheckFailed_System.
  • Instance status check (your side): EC2 sends an ARP request to the instance's network interface. Failures can come from incorrect networking or startup configuration, exhausted memory, a corrupted file system or an incompatible kernel (and from a failing system check, or from a reboot in progress). You typically fix it yourself, for example by rebooting or changing configuration. Metric: StatusCheckFailed_Instance.
  • Attached EBS status check: whether attached EBS volumes are reachable and can complete I/O. Metric StatusCheckFailed_AttachedEBS, available only for Nitro instances. Suggested responses: wait, replace the volume, stop and start the instance, or fail over; Auto Scaling groups can be configured to replace instances with impaired EBS volumes.
  • Application status check (opt-in): you configure an HTTP or HTTPS path and the response codes that count as healthy; failures increment StatusCheckFailed_Application. You can suppress them during deployments to avoid false alarms.
  • Performance status check: for supported accelerated-computing instances, spotting hardware issues that hurt performance without making the instance unreachable (the docs' example is a GPU memory error that a reboot can clear).

Aggregate metric StatusCheckFailed reports whether the instance passed all checks in the last minute (0 passed, 1 failed). Newly launched instances have status check data only after initialisation. Bare metal restarts can make checks fail temporarily.

2. Metrics: basic vs. detailed monitoring

EC2 sends metrics to CloudWatch in the AWS/EC2 namespace, kept for 15 months per the docs. Under basic monitoring, status check metrics arrive every minute and everything else every 5 minutes. With detailed monitoring (enabled at launch, or later with aws ec2 monitor-instances --instance-ids ... and turned off with unmonitor-instances), metrics come in 1-minute periods and you can aggregate across similar instances. Detailed monitoring is charged per metric; status check metrics are free.

Key metrics from the docs table:

  • CPUUtilization (percent of physical CPU time EC2 uses to run the instance, including hypervisor time; operating system tools may show a different number).
  • NetworkIn / NetworkOut (bytes), NetworkPacketsIn/Out (basic monitoring only). To get bytes per second with the Sum statistic, divide by 300 (basic) or 60 (detailed).
  • DiskReadOps/WriteOps/ReadBytes/WriteBytes: these cover instance store volumes only; with none, 0 or nothing is reported. EBS volumes have separate metrics (and Nitro instances add EBSReadOps and friends), which links back to the storage digest.
  • Burstable instance credit metrics (CPUCreditBalance, CPUCreditUsage, 5-minute only), and MetadataNoToken / ImdsV1Enabled to track IMDSv2 migration (the metadata digest).

What EC2 metrics don't include (my inference from the metric tables, which list no memory or file system usage metrics; the docs point to the CloudWatch agent for additional metrics): memory and disk-space usage need the CloudWatch agent, which is the topic of a later CloudWatch concept. Dimensions: InstanceId, AutoScalingGroupName, ImageId and InstanceType (the latter two need detailed monitoring).

Alarm actions on EC2 alarms can stop, terminate, reboot or recover an instance, per the monitoring topic list; see the earlier alarms digest for how alarms evaluate.

3. Automatic instance recovery

If AWS detects an instance is unavailable because of an underlying hardware or software issue (a system status check failure), recovery tries to move it to a different host. To the instance it looks like an unplanned reboot. Two mechanisms:

  • Simplified automatic recovery: enabled by default at launch on supported instances; fixed AWS-managed behaviour; basic notifications through the Health Dashboard (events AWS_EC2_SIMPLIFIED_AUTO_RECOVERY_SUCCESS / _FAILURE); no additional cost. Not supported for metal instances, instances with instance store volumes, Elastic Fabric Adapter, Dedicated Hosts, or Auto Scaling group members, among others. Toggle with aws ec2 modify-instance-maintenance-options --instance-id ... --auto-recovery disabled or default.
  • CloudWatch action based recovery: you create a CloudWatch alarm on StatusCheckFailed_System (alarm when the value is 1) with the recover action. More customisable, SNS notifications, the docs say faster recovery attempts, and it supports metal instances and selected instance-store types (data on instance store is lost). Not supported for Dedicated Hosts, EFA, Auto Scaling group members, or instances in scheduled maintenance. May incur CloudWatch charges. I read the concept page but not the alarm-creation procedure, so I don't give its steps.

What survives and what doesn't (docs): preserved are the instance ID, public/private/Elastic IP addresses, instance metadata, placement group, attached EBS volumes and the Availability Zone. Lost are RAM contents and the OS uptime counter (and instance store data with CloudWatch action based recovery). A manual stop and start, by contrast, gives you a new public IPv4 address unless you have an Elastic IP.

Limits of recovery: it only works if the instance is running, no AWS Health Dashboard service events apply, and capacity exists. There is a maximum number of recovery attempts per day, after which the instance might be retired if hardware degradation was the cause. Recovery must be configured before a failure happens.

The docs' own caveat: these mechanisms are for individual instances. For a resilient system, use Elastic Load Balancing and Auto Scaling so traffic fails over to healthy instances. That is the same architecture the earlier digests built toward.

Why it matters

Almost every incident review for an EC2-based service eventually asks "was it the host or us?" and "did we get alerted?" The status checks answer the first, alarms on status check metrics answer the second, and recovery narrows the window of downtime for single instances. It also completes the EC2 picture: instances (digest 1), what you pay (2), disks (3), traffic (4), scaling (5), operations (6), identity (7), hardware (8), network access (9), and now health (10).

Remember this

  • System check = AWS side (host), instance check = your side (OS and config); checks run every minute and can't be disabled; application checks are opt-in.
  • Basic monitoring: 5-minute metrics, 1-minute status checks. Detailed monitoring: 1-minute metrics, charged per metric.
  • Automatic recovery only reacts to system check failures, moves the instance to another host, keeps IDs, IPs and EBS, and loses RAM.
  • Simplified recovery is on by default (supported instances, not instance-store ones); CloudWatch action based recovery is alarm-driven and customisable.
  • Recovery repairs one instance; use load balancing and Auto Scaling for resilience.

Try it yourself

Projects 1 and 2 need no AWS account. Projects 3 to 5 use a small instance (it may cost money; terminate afterwards) and read-only or low-risk commands. describe-instance-status, monitor-instances, unmonitor-instances and modify-instance-maintenance-options appeared on the docs pages or CLI reference page I fetched, but I did not run any of them against a live account.

  1. Triage flowchart (no AWS). Write a function that takes (system_check, instance_check, ebs_check) as pass/fail and returns who should act and a first action, using only the docs' wording. Done when: system-fail returns "AWS / stop-start or auto recovery" and instance-fail-only returns "you / reboot or fix config, and recovery will not act".
  2. Per-second maths (no AWS). Given a Sum of NetworkOut over a period, compute bytes per second for basic (300 s) and detailed (60 s). Done when: your function matches the docs' divide-by rules and you can explain why packets metrics only exist at 5 minutes.
  3. Read your status. Run aws ec2 describe-instance-status --instance-ids <id> on a running instance. Done when: you can point to SystemStatus and InstanceStatus in the output, both with a reachability detail, and explain the possible Status values (ok, impaired, insufficient-data, not-applicable, initializing).
  4. Flip detailed monitoring. Enable it with aws ec2 monitor-instances, look at CPUUtilization in the console graphs after a few minutes, then turn it off with unmonitor-instances. Done when: you've observed the change in granularity and removed the extra charge.
  5. Build the alarm in the console. Create a CloudWatch alarm on StatusCheckFailed_System for one instance (alarm when the value is 1) with an SNS notification only, not the recover action. Done when: you can describe what would need to change to add the recover action, and which instance types or setups the docs say can't use it (for example Auto Scaling group members). Delete the alarm afterwards.
