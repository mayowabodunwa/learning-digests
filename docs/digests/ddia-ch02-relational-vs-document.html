Relational Model vs. Document Model

Part 1 of 2 on data models: why the shape of a single relationship (one-to-many, many-to-one, or many-to-many) quietly decides whether nesting your data as JSON or splitting it into relational tables is going to feel natural or painful.

In one line

Whether you should nest a piece of data inside its parent (the document model) or split it into its own table with a foreign key (the relational model) isn't a matter of taste, it comes down to whether that relationship is one-to-many, many-to-one, or many-to-many.

The big idea

Every application ends up choosing a data model: a general-purpose shape you store your objects in, like tables in a relational database, JSON documents, or a graph. That choice ripples through everything built on top of it, because each data model makes some operations natural and others awkward. This unit compares the two data models most people reach for first, the relational model (tables and rows, the SQL world) and the document model (self-contained JSON-like records, the world of databases like MongoDB), using a single running example: a person's résumé, which has one name but several past jobs. Nesting those jobs inside the profile is simple until the data grows more connected, and understanding exactly when and why it stops being simple is most of what this unit is about.

Key terms

  • Data model — the general-purpose structure you express your application's objects in when you store them: relational tables, JSON/XML documents, or a graph are all data models.
  • Relational model — data organized into relations (tables in SQL), each an unordered collection of tuples (rows). Proposed by Edgar Codd in 1970.
  • Document model / document database — stores each record as one self-contained document (usually JSON), instead of splitting it across separate tables. MongoDB, CouchDB, and RethinkDB are examples.
  • Object-relational mismatch (impedance mismatch) — the awkward translation work needed between objects in your application code and the tables/rows/columns of a relational database. The term is borrowed from electronics, where mismatched circuits lose signal at the connection.
  • ORM (object-relational mapping) — a library, like ActiveRecord or Hibernate, that automates a lot of that translation. It reduces the boilerplate but can't fully hide the difference between the two models.
  • One-to-many relationship — one record has many of another, e.g. one résumé, several past jobs.
  • Many-to-one relationship — many records point at the same shared record, e.g. many users living in the same region.
  • Many-to-many relationship — records on both sides can each point at several on the other side, e.g. users and the organizations they've worked for, once organizations become their own linkable entity.
  • Normalization — pulling duplicated, human-meaningful data (like a region's name) out into its own record, referenced everywhere else by an ID, so it lives in exactly one place.
  • Foreign key — an ID column in a relational table that points at a row in another table.
  • Document reference — a document database's version of a foreign key: an ID stored inside one document that points at another document.
  • Join — combining rows or documents from two tables/collections using a shared key, resolved at query (read) time.
  • Shredding — the traditional relational technique of splitting a document-like structure (like a résumé) across several tables, linked by foreign keys.
  • Hierarchical model — an older data model (used by IBM's IMS) that represents all data as a tree of nested records, where every record has exactly one parent.
  • Network model / CODASYL — a generalization of the hierarchical model where a record could have more than one parent, standardized by a committee called CODASYL (Conference on Data Systems Languages).
  • Access path — in hierarchical and network databases, the specific chain of pointers you had to follow, starting from a root record, to reach the record you wanted. There usually wasn't another way in.
  • Query optimizer — the part of a relational database that automatically works out how to execute a query (which indexes to use, what order to do things), so application developers don't hand-code access paths themselves.
  • Schema-on-write — the traditional relational approach: the schema is explicit, and the database rejects writes that don't match it.
  • Schema-on-read — the common document-database default: the database itself enforces no schema; the structure is only assumed by whatever code reads the data afterward.
  • Polyglot persistence — using more than one kind of database together in the same system, each picked for what it's good at, instead of forcing every kind of data into one.
  • Data locality — how physically close together the pieces of one record sit on disk or in memory. Better locality generally means fewer separate lookups to read the whole thing.

How it works

Here's the frame worth holding in mind before any of the specifics: an application is really a stack of data models, layered on top of each other. As a developer you model the real world (people, jobs, money) as objects in your code. Then you express those objects in terms of a general-purpose data model to store them, JSON, XML, relational tables, or a graph. The database engineers then represent that model as bytes on disk or in memory. And below that, hardware turns bytes into electrical signals. Each layer hides the layer beneath it behind a cleaner interface, which is what lets application developers and database engineers work independently of each other. This unit lives entirely at the second layer: given that you need a general-purpose way to store your data, should it be relational, or should it be documents?

1. Where the relational model came from, and why NoSQL pushed back

SQL and the relational model (tables of rows, formally proposed by Edgar Codd in 1970) grew out of 1960s and '70s mainframe business data processing: entering bank transactions, airline reservations, tracking warehouse stock, running payroll. By the mid-1980s it had become the default choice for anyone storing structured data, and it has stayed dominant for roughly 25 to 30 years, which is a remarkably long run in computing. Plenty of challengers came and went in that time: the network and hierarchical models in the 1970s and early '80s, object databases in the late '80s and early '90s, XML databases in the early 2000s. None of them displaced the relational model, and relational databases turned out to generalize far beyond their original business-processing use case, into most of what you see on the web today: publishing, social networking, ecommerce, and plenty more.

NoSQL is the most recent attempt to challenge that dominance. The name is a bit of an accident: it started as a Twitter hashtag for a 2009 meetup about open source, distributed, nonrelational databases, not a description of any specific technology. It's since been retroactively reinterpreted as "Not Only SQL." A few different pressures pushed people toward it: needing more scalability (very large datasets, very high write volume) than a relational setup could easily give them, a preference for free and open source tools, specialized query needs the relational model doesn't support well, and frustration with how rigid relational schemas can feel. Because different applications have different needs, it's common today to see relational databases used alongside nonrelational ones in the same system, a pattern sometimes called polyglot persistence, rather than one model winning outright.

2. The object-relational mismatch

Most application code today is written in an object-oriented style, and that creates real friction with the relational model: your code deals in objects, but a relational database deals in tables, rows, and columns, so something has to translate between them. That disconnect is called the object-relational mismatch, or impedance mismatch (a term borrowed from electronics, where connecting two circuits with mismatched impedance loses signal at the join). ORMs like ActiveRecord or Hibernate cut down the amount of boilerplate needed for that translation, but they don't make the underlying difference between the two models disappear.

3. The résumé example: modeling a one-to-many relationship

The clearest way to see this is a concrete example: a LinkedIn-style résumé. A profile has exactly one first_name, one last_name, easy columns on a users table. But most people have held more than one job, studied at more than one school, and have more than one way to be contacted. Each of those is a one-to-many relationship: one profile, many positions underneath it.

There are a few ways to represent that in a relational database. The traditional (pre-SQL:1999) approach is to put positions, education, and contact info in their own separate tables, each row carrying a foreign key back to the profile's user_id. Later SQL standards added structured and XML datatypes that let you store multi-valued data inside a single row while still being able to query inside it (supported to varying degrees by databases like Oracle, DB2, SQL Server, and PostgreSQL), and several databases, including MySQL and PostgreSQL, also support a JSON column type directly. A third, older option is to just dump a JSON or XML blob into a plain text column and let the application make sense of it, which usually means the database itself can't query inside that blob at all.

The alternative is to skip tables entirely for this piece and store the whole profile, positions and all, as one JSON document. For something that's mostly a self-contained record like a résumé, that fits naturally, and it's exactly the model document databases like MongoDB, RethinkDB, and CouchDB are built around.

The JSON version has one real, measurable advantage here: data locality. Fetching the whole profile from the relational version means either several separate queries (one per table, filtered by user_id) or a multi-way join; the JSON version needs exactly one lookup, because everything lives in one place. The one-to-many relationships from a profile to its positions, education, and contact info also form a tree shape, and the JSON representation just makes that tree explicit instead of hiding it behind foreign keys.

4. Many-to-one and many-to-many: where documents alone stop being enough

The résumé example also has fields like region_id and industry_id, stored as IDs rather than as the plain text "Greater Seattle Area" or "Philanthropy." That's a deliberate choice, and it's worth understanding why standardized, ID-referenced lists usually beat free-text fields: they keep spelling and style consistent, avoid ambiguity (several places can share a name), make updates easy since the human-readable name lives in exactly one place, support localization (the same ID can be shown in different languages), and make search better (a search for "Washington" can match a profile tagged "Greater Seattle Area" if the region list itself encodes that Seattle is in Washington).

Using an ID like this is a many-to-one relationship: many profiles can point at the same region record. And this is exactly where the document model starts to struggle, because many-to-one relationships don't nest neatly. In a relational database, joining on a foreign key is cheap and normal. In a document database, joins are often weak or unsupported, so if the database itself can't do the join, your application code ends up doing it by hand with multiple lookups (which is usually fine if the referenced list, like regions, is small and barely changes, since you can just keep it in memory, but the join work has still moved out of the database and into your code).

Worse, real applications tend to get more interconnected over time even when they start out looking document-shaped. Two natural feature additions to the résumé example show this clearly: if organizations and schools become their own linkable entities (so a company gets its own page, logo, and news feed), a job no longer just holds a company name string, it holds a reference to a company, and a company has many employees referencing it back, a genuine many-to-many relationship. Same thing if you add recommendations: one user writing a recommendation for another needs a reference to the author's profile, so that if the author updates their photo, every recommendation they've written can reflect it. Both features are entirely reasonable things to add to a "simple" document, and both quietly turn a one-to-many nesting problem into a many-to-many referencing problem.

5. Are document databases repeating history? Hierarchical and network models

This tension between simple nesting and complex references isn't new. The most popular database for business data processing in the 1970s was IBM's Information Management System (IMS), first released commercially in 1968 and originally built for stock-keeping on the Apollo space program. IMS used the hierarchical model: it represented everything as a tree of records nested within records, with every record having exactly one parent, which looks a lot like the JSON tree shape from the résumé example. Like document databases today, IMS handled one-to-many relationships well, but many-to-many relationships were genuinely hard, and joins weren't supported at all.

Two competing fixes were proposed. The network model, standardized by a committee called CODASYL, generalized the hierarchical model by letting a record have more than one parent (so, for example, one shared "Greater Seattle Area" region record could be linked to from every user who lived there). But the links in CODASYL weren't foreign keys, they worked more like pointers: the only way to reach a record was to follow a chain of links, called an access path, starting from a root. In a world with many-to-many relationships, several different paths could lead to the same record, and the programmer had to keep track of all of them by hand. It made querying and updating the database complicated, and changing your access paths later meant rewriting a lot of handwritten query code.

The relational model solved this differently: instead of nested structures and access paths, it just laid all the data out flat, as tables of rows you could read by any condition you liked, with no predetermined path required to reach a row. The genuinely important idea underneath that: a relational database's query optimizer figures out how to execute a query (which indexes to use, what order to join in) automatically, instead of a human hand-coding an access path for every query. You only have to build that optimizer once, inside the database, and every application using it benefits, which is a big part of why the relational model made it so much easier to add new features to an application later.

Where document databases land relative to all this: they brought back the hierarchical model's habit of nesting one-to-many data (positions, education) inside its parent record instead of a separate table. But for many-to-one and many-to-many relationships, document and relational databases aren't actually that different underneath, both resolve a reference (a foreign key in the relational model, a document reference in the document model) at read time, via a join or a follow-up query. What document databases have not done, at least as far as this comparison goes, is follow CODASYL's path of programmer-managed access paths; when they need to resolve references, they still do it by ID lookup, not by walking hand-maintained pointer chains.

6. Which model leads to simpler application code?

There's genuinely no universal answer here, it depends on the shape of your data's relationships. If your data is naturally document-shaped, a tree of one-to-many relationships that you typically load and use as a whole, the document model tends to be a good fit, and shredding it across several relational tables can produce a schema and application code that feels more complicated than it needs to be. The document model does have a real limitation worth knowing: you can't refer directly to a nested item inside a document (there's no clean way to say "just the second position"), you have to describe its position, similar in spirit to a hierarchical access path, though in practice this rarely bites as long as documents aren't too deeply nested.

Whether weak join support in a document database is actually a problem depends entirely on your application. An analytics system that just logs which events happened when may never need many-to-many relationships at all. But once your application does need them, the document model gets less appealing: you can reduce the need for joins by denormalizing (copying data instead of referencing it), but then your application has to do extra work to keep those copies consistent, and emulating a join yourself in application code is both more complex and usually slower than a join the database engine does internally. For highly interconnected data, relational modeling tends to hold up better than documents, and (a preview for later material) graph-based models are built specifically for data that's even more interconnected than that.

7. Schema flexibility: schema-on-read vs. schema-on-write

Most document databases, and the JSON support bolted onto relational databases, don't enforce any schema on what you write. Nothing stops a document from having arbitrary extra fields, or missing fields a reader expects. Calling this "schemaless" is a bit misleading though, because the code that reads the data almost always assumes some structure exists, it's just an implicit schema, enforced by your application instead of the database. That's why the more accurate label is schema-on-read: the structure exists, but it's only interpreted when data is read. That's in contrast to the traditional relational approach, schema-on-write, where the schema is explicit and the database itself refuses writes that don't match it. It's a similar flavor of debate to dynamic vs. static type checking in programming languages, and neither side is right in general.

The difference shows up clearly when your data's shape changes. Say you're storing a user's full name in one field and want to split it into first and last name instead. In a document database, you'd typically just start writing new documents with the new fields, and add a small bit of code that fills in the old shape when it's missing on read, something like checking whether first_name is present and deriving it from name if not. In a relational database, you'd typically run a migration: an ALTER TABLE to add the column, then an UPDATE to backfill it from the existing name field.

Schema changes have an unfair reputation for always being slow and disruptive. That's not really deserved in general: most relational systems run ALTER TABLE in a few milliseconds. MySQL is the one to watch out for here though: it's historically copied the entire table when you run ALTER TABLE, which on a large table can mean minutes or hours of real downtime, though tooling exists to work around this. Separately, the UPDATE step (rewriting every row) is likely to be slow on any database if the table is big, and if that's not acceptable, you can leave the new column NULL by default and fill it in lazily at read time instead, which is basically the document database's schema-on-read trick borrowed inside a relational system.

Schema-on-read tends to earn its keep when your records genuinely aren't all the same shape: many different object types that don't each deserve their own table, or a structure controlled by some external system you don't own and that can change without warning. When your records really are all the same shape, an enforced schema is useful precisely because it documents and guarantees that shape for you, rather than leaving it as tribal knowledge in application code.

8. Data locality: the one-read advantage, and where it runs out

A document is usually stored as one continuous encoded string (JSON, XML, or a binary variant like MongoDB's BSON). If your application often needs the whole document at once, say, to render a full profile page, that continuous storage is a genuine performance win: the relational version might need several separate index lookups (and disk seeks) to gather the same data from multiple tables. But that locality advantage only helps when you actually need most of the document at once. If you only need one small field, the database still typically has to load the entire document to get it, which can waste effort on large documents. Updates are similar: writing to a document usually means rewriting the whole thing (only edits that don't change its encoded size can be done in place), so it's generally worth keeping documents fairly small and avoiding updates that grow them.

It's also worth knowing that this "group related data together for locality" idea isn't unique to the document model. Google's Spanner allows a relational schema to declare that rows of one table should be physically interleaved inside a parent table's rows for the same effect. Oracle offers something similar with multi-table index cluster tables, and the column-family idea in Bigtable-style databases (used by Cassandra and HBase) serves a similar purpose. Locality is a storage-engine question as much as a data-model one.

9. Convergence: the lines are blurring

Relational and document databases have been borrowing from each other for a while now. Most relational database systems (MySQL has historically been the exception) have supported XML since the mid-2000s, including the ability to modify, index, and query inside XML documents, which lets applications work with something close to a document model on top of a relational engine. A native JSON datatype shows up in several relational systems too, including PostgreSQL and MySQL. On the document side, RethinkDB supports joins, unlike MongoDB, which shows the boundary between the two camps isn't as fixed as it might first look. This convergence keeps going, and picks back up on the query-language side in the next part of this material (roughly pages 64 onward), which is intentionally out of scope here.

Why it matters

This is the modeling decision you make before you write a single line of query code, and it's easy to get away with the wrong choice for a while before it bites. If you're reaching for a document database (or a JSON column in a relational one) because a résumé, a form submission, or an event log is naturally tree-shaped, that's usually the right instinct. But if you catch yourself adding a reference from one document to another, an organization, an author, a shared category, that's the moment to ask whether you've quietly grown a many-to-one or many-to-many relationship, because that's exactly the shape the document model handles worst and the relational model was built for. In practice, most production systems (including the kind you'd run on RDS or a managed MySQL/Postgres instance) don't pick one model and stay pure to it forever, they reach for a JSON column for the résumé-shaped parts of their schema and keep proper foreign-key tables for everything more interconnected.

Remember this

  • One-to-many nests well as JSON. Many-to-one and many-to-many usually don't, because joins are what resolves those references, and document databases tend to support joins weakly or not at all.
  • Document databases aren't schemaless, they're schema-on-read: the structure exists, it's just enforced by your application code instead of the database, at the moment you read the data.
  • The relational model's real breakthrough over its hierarchical and network predecessors wasn't tables themselves, it was the query optimizer automating what used to be a hand-coded access path.
  • A document's storage locality (everything in one contiguous read) is a genuine win only when you usually need most of the document at once, not for picking out one small field.
  • Relational and document databases increasingly borrow each other's features (JSON columns in MySQL/PostgreSQL, join support in RethinkDB), so the two camps are converging rather than staying fully separate.

Try it yourself

  1. Résumé modeler. Build a tiny profile object two ways: as one nested JSON document, and as three separate in-memory tables (profiles, positions, education) linked by an ID you assign yourself. Write one function per representation that renders a full profile view. Done when: both produce the same output, and you can point at exactly which lines are doing the "join" in the relational version.
  2. Hand-rolled join. Store users and regions as two separate collections (dicts keyed by ID work fine) with a region_id reference on each user. Write your own join function in application code that resolves it. Done when: passing it a user ID returns the region's full name, with no database join operator involved anywhere.
  3. Schema-on-read vs. schema-on-write, side by side. Build a tiny in-memory record store two ways: one that validates every write against a fixed shape (schema-on-write) and one that accepts anything (schema-on-read). Feed both an "old format" record missing a field that a newer version of your code expects. Done when: your schema-on-read version reads both old and new records without crashing, using a fallback default the way the source's own name-splitting example does.
  4. Locality timer. Build "load one full profile" two ways: as a single JSON blob under one key (one lookup), and split across three separate keyed lookups you fetch and reassemble. Time both over a few thousand full-profile fetches. Done when: you have printed numbers showing which is faster for "give me everything," and you can explain why in one sentence.
  5. Hierarchical toy break-test. Build a tree-only store where every record has exactly one parent and the only way to reach a record is to walk down from the root. Try to model a many-to-many relationship in it (say, one job that several different people have held). Done when: you can describe out loud exactly where and why it breaks, and why flat relational tables sidestep that specific problem.
  6. Denormalize on purpose. Take a small dataset with a many-to-one relationship (users and the city they live in) and store it two ways: normalized (city as an ID referencing a separate city list) and denormalized (the city name copied into every user record). Simulate one city getting renamed. Done when: you can show exactly how many records you had to touch in each version to keep the data correct.

Go deeper

If you reread one part slowly, make it the "Many-to-one and many-to-many" section: the résumé example starts out looking purely document-shaped, and the moment organizations and recommendations get added, it quietly stops being so. A natural next question to sit with, for any side project or app idea you have right now: pick one relationship in your own data (not the whole schema, just one) and ask whether it's one-to-many, many-to-one, or many-to-many, then notice which data model that answer points you toward, before you think about which specific database product to use.
