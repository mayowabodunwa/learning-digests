S3 Event Notifications and the EventBridge Integration: Making Uploads Trigger Things

S3 can tap you on the shoulder when something happens to an object: a file lands, a file is deleted, a restore finishes. You choose where the tap goes (a queue, a topic, a Lambda function, or EventBridge), and you decide how picky to be. This digest covers how that works, and the handful of behaviours that bite people: duplicates, ordering, filters that can't overlap, and loops.

In one line

S3 Event Notifications publish messages about bucket events to SNS, SQS or Lambda according to a notification configuration you attach to the bucket, while the EventBridge option sends all supported events to EventBridge, where rules decide what to do with them.

The big idea

Many systems follow the same pattern: a file arrives, and something should happen next (resize an image, scan a document, load a CSV, tell a human). Polling the bucket for new files is wasteful. Event notifications flip that around: S3 pushes a small message when the event occurs.

There are two flavours with different styles. The original S3 Event Notifications are configured per destination: "for these event types and key patterns, send to this queue." The EventBridge integration is all-or-nothing at the bucket: switch it on and every supported event goes to EventBridge, and from there you write EventBridge rules to filter and route. Which is better depends on your needs. The docs, for example, point to EventBridge as the route to an SQS FIFO queue, which S3 notifications don't support directly.

Simplification label: I don't cover Lambda, SQS, SNS or EventBridge in depth (each is a topic of its own). I cover S3's side, plus the minimal context needed. I quote no prices; the docs just point to EventBridge pricing.

Key terms

  • Event: something that happened to a bucket or object (an object created, removed, restored, replicated...).
  • Notification configuration: the bucket's notification subresource listing event types, filters and destinations.
  • Destination: where S3 publishes: an SNS topic, an SQS queue, a Lambda function, or Amazon EventBridge.
  • SNS (Simple Notification Service): a push messaging service that fans a message out to subscribers.
  • SQS (Simple Queue Service): a message queue where consumers pull messages at their own pace.
  • Lambda: AWS's run-code-on-demand service; S3 can invoke a function with the event as its argument.
  • EventBridge: a serverless event bus that matches events against rules and delivers them to targets.
  • Event type: a name like s3:ObjectCreated:Put identifying the kind of event.
  • Key name filter: a prefix and/or suffix filter limiting which object keys trigger a notification.
  • At-least-once delivery: a promise that a message arrives one or more times, meaning duplicates are possible.
  • Idempotent: an operation safe to repeat, so a duplicate event does no extra harm.

How it works

0. Grounding: events, configuration, destinations

By default, notifications aren't enabled for anything: the bucket's notification subresource starts empty. To turn some on, you replace that with a configuration saying which event types to publish and where. The configuration is stored on the bucket, and the docs say it usually takes about five minutes for a new or changed configuration to take effect. When you first enable a notification, S3 sends a test event (s3:TestEvent) to check the destination exists and you have permission; if enabling fails you won't get one.

Delivery semantics, straight from the docs: notifications are designed to be delivered at least once; typically they arrive in seconds but can take a minute or longer; they're not guaranteed to arrive in the order events occurred; and on rare occasions retries can produce duplicate notifications for the same event. So consumers should expect duplicates and reordering.

1. What events can S3 publish?

The docs' overview lists categories: new object created, object removal, restore events, RRS object lost, replication events, lifecycle expiration, lifecycle transition, Intelligent-Tiering automatic archival, object tagging, object ACL PUT, object annotation, and object retention events. In the SNS/SQS/Lambda style you name specific types (or wildcards):

  • s3:ObjectCreated:* or a specific API: :Put, :Post, :Copy, :CompleteMultipartUpload.
  • s3:ObjectRemoved:*, :Delete (permanent or unversioned delete), :DeleteMarkerCreated. Per the docs, these do not fire for automatic lifecycle deletes or failed operations.
  • s3:LifecycleExpiration:* and s3:LifecycleTransition for lifecycle-driven changes (this ties back to the lifecycle digest).
  • s3:ObjectRestore:* (Post, Completed, Delete) for Glacier-style restores.
  • s3:Replication:* events such as OperationFailedReplication, OperationMissedThreshold and OperationReplicatedAfterThreshold (these need replication metrics or RTC enabled; see the replication digest).
  • s3:ObjectTagging:*, s3:ObjectAcl:Put, s3:ObjectRetention:Put, s3:IntelligentTiering, and others.

2. Setting it up: destinations, permissions and the config

Rules for destinations (from the docs):

  • Each notification entry names one destination type. Destinations must be in the same Region as the bucket.
  • SNS: standard topics only (SNS FIFO isn't allowed). SQS: standard queues only; FIFO isn't supported (use EventBridge to reach a FIFO queue). Lambda durable functions aren't supported.
  • Messages can be up to 64 KB; the docs recommend setting an SQS queue's MaximumMessageSize to at least 64 KB, because otherwise SQS rejects the notification and it isn't delivered.

Permissions go on the destination. S3 needs permission to publish. For SNS or SQS you attach a resource policy to the topic or queue allowing the S3 service principal (s3.amazonaws.com) to SNS:Publish or SQS:SendMessage, with conditions on aws:SourceArn (your bucket) and aws:SourceAccount (the bucket owner) so only your bucket can use it. For Lambda, S3 needs permission to invoke the function (the console sets this up for you). If the queue or topic is encrypted with a customer managed KMS key, the key policy must let the S3 principal use kms:GenerateDataKey and kms:Decrypt.

The config shape. Stored as XML on the bucket (the CLI and SDK versions use JSON equivalents). The docs' SQS shape:

<NotificationConfiguration>
  <QueueConfiguration>
    <Id>optional-id</Id>
    <Queue>sqs-queue-arn</Queue>
    <Event>s3:ObjectCreated:Put</Event>
  </QueueConfiguration>
</NotificationConfiguration>

There are matching TopicConfiguration and CloudFunctionConfiguration blocks for SNS and Lambda. To remove all notifications, you save an empty NotificationConfiguration. One thing to take from the structure: it's a whole-document setting, so a change means sending the full intended configuration, not just the new piece (the docs show saving a replacement configuration; confirm the exact CLI behaviour in the reference).

3. Filtering by key name

You can limit a notification to keys with a given prefix and/or suffix (for example, only images/ keys ending .jpg). Rules from the docs:

  • No wildcards: * can't be used in a prefix or suffix. Spaces must be written as +, and other special characters must be URL-encoded.
  • No overlapping filters for the same event types. Two entries can't have overlapping prefixes, overlapping suffixes, or overlapping prefix and suffix combos. "Overlap" means some key string could match both. Example: suffixes jpg and pg overlap (a key can end in both), while .jpg and .png don't. You can have the same prefix twice if the suffixes don't overlap.
  • An entry without a filter counts as matching every prefix and suffix, so pairing it with any filtered entry for the same events is invalid.
  • Overlapping filters are fine across different event types (the docs' example: same prefix for ObjectCreated:Put and ObjectRemoved:*).
  • S3 returns an error if you try to save an invalid overlap.

4. The EventBridge route

EventBridge is configured differently. Enabling it on a bucket is a single on/off switch: the docs' CLI shape is a notification configuration containing an empty EventBridgeConfiguration:

aws s3api put-bucket-notification-configuration \
  --bucket {bucket} \
  --notification-configuration='{ "EventBridgeConfiguration": {} }'

After you enable it, the docs say it takes around five minutes to take effect. Unlike the other destinations, you don't pick event types: once on, all the supported events go to EventBridge (object created, deleted, restore initiated/completed/expired, storage class changed, access tier changed, ACL updated, tags added/deleted, annotations, retention updated). Then you create EventBridge rules that match on fields and send to targets, which can be more than the S3-native destinations; that's where the extra flexibility comes from.

The event arrives as JSON with an envelope (version, id, detail-type such as "Object Created", source of aws.s3, account, time, region, resources with the bucket ARN) and a detail object (bucket name, object key, size, etag, version ID, sequencer, requester, and a reason such as PutObject; for deletes a deletion-type of "Delete Marker Created" or "Permanently Deleted"). A trimmed shape in the docs' style:

{
  "detail-type": "Object Created",
  "source": "aws.s3",
  "resources": ["arn:aws:s3:::{bucket}"],
  "detail": {
    "bucket": {"name": "{bucket}"},
    "object": {"key": "example-key", "size": 5},
    "reason": "PutObject"
  }
}

The docs also advise your code to compare the major event-version for equality, check the minor version is at least what you need, and ignore fields it doesn't recognise, so additions don't break you.

5. Gotchas worth memorising

  • Infinite loops. The docs warn: if a notification triggers a Lambda that writes back to the same bucket, it can trigger itself. Use two buckets, or a trigger limited to an input prefix.
  • Duplicates and ordering. Make consumers idempotent; events carry a sequencer field, which is worth reading about for ordering (the docs point to an AWS Storage Blog post for the full guidance, which I did not read).
  • Lifecycle deletes don't raise ObjectRemoved events; use the LifecycleExpiration types.
  • Configuration delay. About five minutes before a change is live, so don't test instantly and conclude it's broken.
  • Deleted destinations leave failed notifications that can block cleanup ("Unable to validate the following destination configurations"); the docs suggest deleting them all together in the console.

Why it matters

Event-driven pipelines on S3 (thumbnails, virus scans, ETL kick-offs, audit trails) all rest on these notifications. Getting the model right (at-least-once, unordered, same-Region destinations, resource policies on the target, non-overlapping filters) separates a pipeline that works in a demo from one that survives production. It also connects to the earlier digests: lifecycle, replication and restore all have events, and versioning shapes what "deleted" means in them.

Remember this

  • S3 Event Notifications go to SNS, SQS or Lambda (one destination type per entry, same Region); EventBridge is an all-events switch with rules downstream.
  • Delivery is at least once and unordered, so duplicates and reordering must be tolerated.
  • Permissions are granted on the destination (resource policy for SNS/SQS, invoke permission for Lambda, KMS key policy if encrypted).
  • Prefix/suffix filters can't overlap for the same event types; no wildcards allowed.
  • Writing to the same bucket from the handler can loop; lifecycle deletes use their own event types; config changes take about five minutes.

Try it yourself

Projects 1 and 2 are offline. Projects 3 to 5 use a scratch bucket and one SQS queue in your own account. The EventBridge enabling command is from the docs; I did not verify the CLI JSON for SQS notification configurations or the SQS CLI commands, so check the CLI reference and the docs' notification walkthrough. Remove the configuration and delete the queue when done.

  1. Overlap checker (offline, ~1 hour). Write a function that takes two (prefix, suffix) filters and says whether some key could match both. Done when it agrees with every valid and invalid example in Fig 2 and treats "no filter" as matching everything.
  2. Idempotent consumer (offline, ~1 hour). Write a handler that processes a list of S3-style events containing duplicates and out-of-order entries, using the event's bucket, key, version ID and sequencer to avoid double work. Done when feeding it the same event five times does the side effect once.
  3. Queue notification. Create an SQS queue, attach the docs' queue policy pattern (S3 principal, SQS:SendMessage, source ARN and account conditions), and configure s3:ObjectCreated:* on your bucket for it using the console. Upload a file and read the message. Done when you've seen the s3:TestEvent and then a real ObjectCreated message.
  4. Add a filter. Restrict the notification to prefix incoming/ and suffix .csv; upload three files that match and don't match. Done when only the matching file produces a message, and you've tried saving an overlapping second entry and read the error.
  5. Try EventBridge. Run the docs' put-bucket-notification-configuration command with an empty EventBridgeConfiguration (note it replaces the whole notification configuration, so do this on a bucket where you can afford to lose the queue entry), wait the five minutes, then make a simple EventBridge rule on source aws.s3 that sends to a target of your choice. Done when an upload triggers your target and you can point to the detail-type in the event.
