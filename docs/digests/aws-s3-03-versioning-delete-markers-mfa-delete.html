S3 Versioning, Delete Markers & MFA Delete: Keeping Every Version and Protecting the Delete Button

By default, writing to an existing key in S3 replaces the old object, and deleting a key removes it. Turn on versioning and both of those become safer: overwrites add a new version, and deletes add a marker that hides the object instead of erasing it. MFA delete then puts a second lock on the truly permanent deletes.

In one line

S3 Versioning keeps multiple versions of an object under the same key in one bucket, a delete marker is the placeholder S3 inserts when you delete a versioned object without naming a version, and MFA delete is an optional setting that demands a one-time code from an MFA device before a version can be permanently deleted or the versioning state changed.

The big idea

In the first S3 digest we saw that a bucket is a flat list of keys. One thing that makes it risky is that a key points at one object: upload a new file to report.csv and the old one is gone, and delete report.csv and it's gone too. A typo in a script or a bug in an app can wipe out data in one call.

Versioning changes what those calls mean. A write now creates a new version next to the old one. A plain delete creates a marker on top of the stack. Nothing is lost until someone deletes a specific version on purpose. This digest walks through the three states a bucket can be in, what each request type does in each state, how you undelete something, the cost side effects, and the MFA delete lock.

Simplification label: I'll describe things from a single bucket's point of view. Other features (Object Lock, replication) interact with versioning too, and those come in later digests in this track. Where the docs I read say something specific, I say so, and I didn't quote prices.

Key terms

  • Version: one stored copy of an object under a key. A key can have many versions in a versioned bucket.
  • Version ID: the identifier S3 generates for a version. Only S3 generates version IDs and you can't edit them. The docs describe them as opaque, URL-ready UTF-8 strings of no more than 1,024 bytes.
  • Current version: the newest version of a key. A plain GET returns this one.
  • Noncurrent version: an older version that has been superseded by a newer write or by a delete marker.
  • Simple DELETE: a delete request that doesn't include a version ID.
  • Delete marker: a zero-data placeholder version that S3 inserts for a simple DELETE in a versioning-enabled (or suspended) bucket. It makes the key look deleted.
  • null version: the version ID given to objects stored while the bucket was unversioned, or stored while versioning is suspended.
  • Versioning subresource: the bucket-level configuration where S3 stores the versioning status (and the MFA delete setting).
  • MFA (multi-factor authentication): proving who you are with something beyond your password or keys, here a six-digit code from a hardware or virtual device.
  • MFA delete: a versioning setting that requires an MFA code to change the versioning state or permanently delete a version.

How it works

0. Grounding: why overwrite and delete are dangerous without versioning

Think of a bucket without versioning as a filing cabinet where every folder has a unique label (the key). Filing a new document under an existing label throws the old one in the shredder. Pulling a folder shreds it too. That's fine for scratch data and awful for anything precious.

The docs frame versioning as a way to keep multiple variants of an object in the same bucket so you can recover from unintended user actions and application failures. It is off by default: a new bucket is unversioned and you must turn versioning on yourself.

1. The three bucket states

A bucket is in one of three states: unversioned (the default), versioning-enabled, or versioning-suspended. You switch at the bucket level, and the state applies to all objects in the bucket, never just some.

  • One-way door. Once you enable versioning, the bucket can never go back to unversioned. You can only suspend it.
  • Existing objects aren't rewritten. Objects already there keep a version ID of null, with the same contents and permissions. What changes is how S3 treats them in later requests.
  • Suspending stops new versions piling up but doesn't delete the ones you have. Existing objects don't change.
  • Who can turn it on: the bucket owner (the account that created the bucket) and authorized users.

Under the hood, every bucket has a versioning subresource. An unversioned bucket stores an empty versioning configuration, and enabling it means sending a configuration with Status set to Enabled (or Suspended to suspend).

Practical caveat from the docs: after you enable versioning on a bucket for the first time, it can take up to 15 minutes to propagate fully. During that time you might see intermittent 404 NoSuchKey errors for objects created or updated after enabling, and the docs recommend waiting 15 minutes before issuing writes or deletes.

2. Version IDs and the stack of versions

Each object has a version ID whether or not versioning is on. If versioning isn't enabled, the ID is null. Once enabled, S3 gives every new write a unique ID, so one bucket can hold, for example, photo.gif version 111111 and photo.gif version 121212 side by side (that's the docs' own illustration of the idea).

I like to picture each key as a stack of sheets. The top sheet is the current version. Reads without a version ID see the top sheet; everything underneath is noncurrent but still there.

3. What each request does when versioning is enabled

  • PUT (overwrite): the old object isn't overwritten. S3 adds a new version with a new ID; the old one becomes noncurrent and you can restore it.
  • Simple DELETE: nothing is erased. S3 inserts a delete marker, which becomes the current version.
  • GET with no version ID: returns the current version. If that's a delete marker, you get 404 Not Found.
  • GET with a version ID: returns that exact version, even if it's noncurrent.
  • DELETE with a version ID: that version is permanently deleted and no delete marker is inserted. Only the bucket owner or an authorized IAM user can do this.

When do new versions appear? Only when you PUT a new object. Some actions work by doing a PUT under the hood (the docs name CopyObject), so they create versions. Actions that modify the current object without a PUT, such as changing tags, don't create a new version.

4. Delete markers in detail

A delete marker is a placeholder that makes S3 behave as if the object is deleted. It has a key and a version ID like any other version, but differs in a few ways:

  • It has no data and no ACL value.
  • A GET without a version ID returns 404 Not Found, and the response includes the header x-amz-delete-marker: true.
  • A GET with the marker's own version ID returns 405 Method Not Allowed, with x-amz-delete-marker: true and a Last-Modified header giving the marker's creation time.
  • Normal listings (ListObjectsV2, ListObjects) don't return objects whose current version is a delete marker. To see markers and all other versions you use ListObjectVersions (in the console, the "Show versions" or "List versions" toggle).
  • Only S3 creates delete markers, and it does so when you send a DeleteObject request on an object in a versioning-enabled or suspended bucket.
  • It costs a tiny amount to store: its size equals the size of its key name (the docs say the UTF-8 encoding adds 1 to 4 bytes per character), and it's kept in S3 Standard.

5. Undeleting, and the trap that adds a second marker

To "undelete" an object, you delete its delete marker, by sending a DELETE that includes the marker's version ID. Afterwards, a simple GET returns the newest remaining version. This is just the same permanent-delete-by-version-ID operation, aimed at the marker.

The trap: if you send a plain DELETE (no version ID) while the current version is already a delete marker, S3 doesn't remove the marker. It puts another marker on top with a new ID. So listing versions and using the marker's ID matters.

A related console limit from the docs: you can't use the console to undelete folders; use the CLI or an SDK.

Cleanup: an expired object delete marker is one where every other version is gone and only the marker remains. The docs say that if your lifecycle configuration is set to delete current versions, or the ExpiredObjectDeleteMarker action is set explicitly, S3 removes that leftover marker.

6. Suspended buckets (the confusing one)

Suspending versioning stops new versions piling up, which the docs say you might do if you only want one version or don't want charges for multiple versions. But it doesn't erase history. What the docs say about requests in a suspended bucket:

  • PUT, POST or CopyObject: the new object gets version ID null. If a null version already exists, it is overwritten (same key and ID, new contents). If other versioned objects exist for that key, they are not overwritten; the null version just becomes the current one.
  • Simple DELETE: it can only remove an object whose version ID is null, and it inserts a delete marker. If there's no null version it removes nothing but still inserts a marker. Because a marker has no content, you lose the null version's content when it's replaced this way.
  • DELETE with a version ID: still permanently deletes that version, even in a suspended bucket, unless permissions were explicitly denied. The docs note that to block deleting null-version objects you must explicitly deny s3:DeleteObject and s3:DeleteObjectVersions.

Beginner takeaway, labelled as a simplification: suspended is not the same as unversioned. Old versions remain and still cost money, and nulls can get overwritten.

7. Cost and lifecycle: versions are full copies

The docs are clear: normal S3 rates apply to every version stored and transferred, and each version is the entire object, not a diff. Three versions means you're charged for three objects. That's why versioning and lifecycle go together:

  • In a versioned bucket the lifecycle Expiration action applies to the current version and, instead of deleting it, adds a delete marker.
  • The NoncurrentVersionExpiration action applies to noncurrent versions and permanently removes them. The docs warn you can't recover permanently removed objects.
  • If you had an expiration rule on an unversioned bucket and want the same permanent-delete behavior after enabling versioning, you must add a noncurrent expiration rule.

The docs also mention that a key with millions of versions can show up as a rise in HTTP 503 responses on PUT or DELETE requests, which is one more reason to expire noncurrent versions.

8. MFA delete: the second lock

Versioning protects you from mistakes, but someone with valid credentials (or a stolen key) can still delete a version by ID. MFA delete adds a requirement: the bucket owner must include two forms of authentication in any request to permanently delete an object version or change the versioning state of the bucket. Those two forms are your security credentials plus the concatenation of the MFA device's serial number, a space, and the six-digit code it currently shows.

  • Who: only the bucket owner (the root account) can enable MFA delete. Per the docs, when MFA delete is configured only the root user can permanently delete versions or change the versioning configuration, authenticating with an MFA device.
  • Where: you can't enable it in the console. Use the AWS CLI or the API. Deleting versions in an MFA-delete bucket isn't available via the console either.
  • Header: requests carry x-amz-mfa, which must use HTTPS; without it the request fails. In the CLI it's the --mfa parameter.
  • Storage: the setting lives in the same versioning subresource as the status (an MfaDelete element next to Status).
  • Limit: the docs state you cannot use MFA delete with lifecycle configurations.
  • Device serial: for a physical device it's the device's serial number; for a virtual device it's the device ARN.

Don't confuse it with MFA-protected API access, a different feature that uses a bucket policy to require MFA-created temporary credentials for sensitive operations. MFA delete is about stopping accidental or unauthorized permanent deletes.

The CLI shapes from the docs (placeholders in braces):

aws s3api put-bucket-versioning --bucket {bucket} \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "{device-serial-or-arn} {six-digit-code}"

aws s3api delete-object --bucket {bucket} --key {key} \
  --version-id {versionId} --mfa "{device-serial} {code}"

Why it matters

Versioning is the first line of defense against the two classic S3 disasters: an overwrite that replaced good data with bad, and a delete (by a person, a script, or a buggy deploy) that wiped something out. It also underpins things coming up in this track, such as replication and Object Lock, and it makes lifecycle rules more interesting because you now manage current and noncurrent versions separately. The price is cost creep and some new ways to be confused (delete markers, null versions), which is why every versioned bucket should have a plan for expiring old versions.

Remember this

  • Versioning is off by default, set per bucket, and once enabled the bucket can only be suspended, never returned to unversioned.
  • With versioning enabled, a PUT adds a version and a simple DELETE adds a delete marker. Only a DELETE with a version ID destroys data.
  • To undelete, delete the delete marker by its version ID. A plain DELETE on a marker stacks another marker.
  • Every version is a full object billed normally, so pair versioning with noncurrent-version expiration.
  • MFA delete (CLI/API only, root account, not combinable with lifecycle) needs a device code to permanently delete versions or change versioning state.

Try it yourself

Project 5 skips MFA delete itself because it needs the root account, which I'd rather you not use casually. Empty and delete the scratch bucket afterwards (including all versions).

  1. Version-stack simulator (offline, ~1 hour). Model a key as a list of versions. Implement put, simple delete, delete-by-version-ID, and get (with and without a version ID) for the enabled state. Done when your simulator reproduces Fig 2 and Fig 3, returns 404 for a plain GET on a marker, and adds a second marker when you simple-delete twice.
  2. Add the suspended state (offline, ~45 min). Extend project 1 with an Unversioned/Enabled/Suspended state, null IDs, and the suspended PUT and DELETE rules from section 6. Done when a null version is overwritten in place while versioned ones stay, and the "enabled to unversioned" transition is rejected.
  3. Enable and observe. Create a scratch bucket, run aws s3api put-bucket-versioning --bucket NAME --versioning-configuration Status=Enabled, wait the docs' recommended 15 minutes, then upload a.txt twice with different contents. Run aws s3api list-object-versions --bucket NAME. Done when you can point at two versions with different IDs and identify which is current.
  4. Delete and revive. Run aws s3api delete-object --bucket NAME --key a.txt, confirm aws s3api get-object fails with a not-found error while list-object-versions shows a delete marker, then remove the marker with delete-object ... --version-id MARKER_ID. Done when a plain get-object works again.
  5. Cost guard rule. Write a lifecycle JSON with a NoncurrentVersionExpiration rule (for example 7 noncurrent days, as in the docs' Python example) and apply it with put-bucket-lifecycle-configuration. Done when get-bucket-lifecycle-configuration returns it, and you can explain in two sentences why a current-version Expiration rule alone would leave old versions behind.
