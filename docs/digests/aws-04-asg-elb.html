Auto Scaling Groups & Elastic Load Balancing

Part 1 was about a single server: an instance booted from an AMI. Part 2 is about what happens once one server isn't enough, an Auto Scaling group keeps the right number of instances running and swaps out anything unhealthy, and a load balancer sits in front of them so traffic only ever reaches the ones that are actually working.

In one line

An Auto Scaling group keeps a fleet of EC2 instances at a size you specify (between a minimum and a maximum, aimed at a desired count) by launching from a template and replacing anything unhealthy, while a load balancer gives clients one address to hit and forwards each request only to instances a target group's health checks currently consider healthy, and attaching the two together is what lets a fleet heal and reroute traffic automatically.

The big idea

Once you need more than one copy of a server, two new problems show up that Part 1 didn't have to deal with: keeping the right number of instances running as demand and failures come and go, and giving clients a single, stable way to reach whichever instances currently happen to be healthy. Amazon EC2 Auto Scaling solves the first problem: you group instances into an Auto Scaling group, tell it a minimum, maximum, and desired size, and it launches or terminates instances to keep the group at that size, using a launch template as the recipe for what to launch. Elastic Load Balancing solves the second: a load balancer is the single point of contact clients talk to, and it routes each request to a healthy member of a target group behind it, continuously checking each target's health so unhealthy ones stop receiving traffic. Attach an Auto Scaling group to a load balancer's target group and the two start cooperating: new instances the group launches get registered with the target group automatically, instances the group terminates get deregistered automatically, and (if you turn the option on) the load balancer's own opinion of an instance's health can trigger the Auto Scaling group to replace it.

Key terms

  • Auto Scaling group (ASG) — AWS's own definition is a "collection of EC2 instances" that Amazon EC2 Auto Scaling treats as a logical unit for scaling and management.
  • Launch template — the configuration template an Auto Scaling group uses to launch its instances: it "specifies instance configuration information" including the AMI ID, instance type, key pair, and security groups (the same pieces Part 1 covered for a single instance).
  • Minimum size / desired capacity / maximum size — the three numbers that bound a group: Amazon EC2 Auto Scaling "ensures that your group never goes below" the minimum or "above" the maximum, and (if you set one) keeps the group at the desired capacity in between.
  • Dynamic scaling policy — a rule that adjusts desired capacity automatically as demand changes. The three basic types are target tracking, step scaling, and simple scaling.
  • Health check grace period — how long Amazon EC2 Auto Scaling waits after an instance enters the InService state before it starts checking that instance's health.
  • EC2 status check — the default health check an Auto Scaling group uses: it checks that an instance is running and free of underlying hardware or software issues, and it "does not require any special configuration" (it's always on).
  • ELB health check (for an Auto Scaling group) — an optional, opt-in health check type where the group uses a load balancer's own healthy/unhealthy verdict on an instance to decide whether to replace it.
  • Instance lifecycle states (ASG) — the path an instance takes inside a group: Pending (launching), InService (in the group, counted toward desired capacity), Standby (temporarily pulled out of service on purpose), Terminating, and Terminated.
  • Load balancer — the resource that "serves as the single point of contact for clients" and distributes incoming traffic across multiple targets in one or more Availability Zones.
  • Listener — checks for connection requests on a protocol and port you configure, then applies rules to decide where to route them.
  • Target group — routes requests to one or more registered targets (commonly EC2 instances) "using the protocol and port number that you specify," with health checks configured per target group.
  • Target — a single thing a target group can route to. A target group's target type (set at creation and unchangeable afterward) decides whether targets are identified by instance ID, by IP address, or (for an Application Load Balancer) a Lambda function.
  • Health check (target group) — a periodic request the load balancer sends to each registered target; a target becomes unhealthy after enough consecutive failures and healthy again after enough consecutive successes.
  • Application Load Balancer (ALB) — a load balancer that "functions at the application layer, the seventh layer" of the OSI model, so it can read HTTP/HTTPS content and route on things like host or path.
  • Network Load Balancer (NLB) — a load balancer that "functions at the fourth layer" of the OSI model, routing raw TCP/UDP/TLS connections rather than reading HTTP content.
  • Deregistration delay (connection draining) — the time a load balancer waits after a target is deregistered before it fully stops sending it traffic, letting in-flight requests finish first.

How it works

Here's the grounding shift from Part 1: an instance on its own is just a server, and a server on its own is a single point of failure, if it crashes, nothing replaces it, and if it's overloaded, nothing helps it. Two AWS services exist specifically to remove those weaknesses. Amazon EC2 Auto Scaling watches a group of instances and keeps it at the size you want, launching replacements when something goes wrong. Elastic Load Balancing sits in front of that group and makes sure traffic only ever lands on instances that are actually able to handle it. They're separate services with their own jobs, but they're designed to be wired together, and the six pieces below build up to exactly that connection.

1. What an Auto Scaling group is, and its three capacity numbers

An Auto Scaling group is nothing more exotic than a named collection of EC2 instances that Amazon EC2 Auto Scaling manages as one unit. What makes it useful is three numbers you set on it: a minimum size the group is never allowed to drop below, a maximum size it's never allowed to exceed, and a desired capacity in between that the group actively tries to maintain. AWS's own worked example sets these to a minimum of four, a desired capacity of six, and a maximum of twelve instances, if a scaling policy asks for more than twelve or fewer than four, the group caps itself at that boundary instead of following the request exactly (as covered in section 3 below).

Every instance an Auto Scaling group launches comes from a launch template, the same kind of AMI-plus-instance-type-plus-security-group configuration Part 1 walked through for a single instance, just reused as a stamp for however many copies the group needs. AWS's guidance is to prefer launch templates (over the older, more limited launch configurations) because only launch templates support newer features like mixing Spot and On-Demand instances or multiple instance types in one group. A group can also span multiple Availability Zones, and AWS states plainly that it "balances your instances evenly across the Availability Zones as the group scales," which is a big part of why a properly configured group survives the loss of a single data center, not just a single server.

2. The instance lifecycle inside a group — how instances actually get added and removed

A scale-out event (you raise desired capacity manually, a scaling policy raises it, or a schedule raises it) tells the group to launch the extra instances it needs using its launch template. Each new instance starts in the Pending state; once it's fully configured and passes the built-in EC2 health checks, it's attached to the group and enters InService, counted toward desired capacity. If the group is attached to a load balancer, AWS's documentation is specific about the order of operations: "Amazon EC2 Auto Scaling automatically registers your instance with the load balancer before it marks the instance as InService," so an instance never shows as fully in-service without already being reachable through the load balancer.

A scale-in event runs the same idea backwards: the group picks which instance(s) to remove (using a termination policy), moves them into the Terminating state, and (if attached to a load balancer) deregisters the terminating instance from the load balancer first, so new requests stop being routed to it while any in-flight requests are given time to finish via the deregistration delay. Only after that does the instance finish terminating and reach Terminated. One billing detail carries over directly from Part 1's lifecycle section: AWS states plainly that "you are billed for instances as soon as they are launched, including the time that they are not yet in service," so a `Pending` instance is already on the clock.

3. How a group decides to add or remove instances — health checks and dynamic scaling

Two separate mechanisms decide when an Auto Scaling group's instance count changes, and it's worth keeping them apart in your head. The first is health-check-driven replacement: AWS states it directly, "when Amazon EC2 Auto Scaling determines that an InService instance is unhealthy, it replaces it with a new instance to maintain the desired capacity of the group." By default a group only listens to EC2 status checks (an instance is unhealthy if it's not running, or its EC2 status check comes back impaired); turning on ELB health checks for the group additionally lets a load balancer's own healthy/unhealthy verdict on an instance count too. Either way, the group waits out a health check grace period after an instance goes InService before it starts judging that instance's health, so a slow-booting application isn't mistaken for a broken one.

The second mechanism is dynamic scaling, which changes desired capacity in response to demand rather than health. AWS documents three policy types: target tracking (you pick a metric and a target value, and AWS's own comparison is that "it works similar to the way that your thermostat maintains the temperature of your home"), step scaling (capacity changes by different amounts depending on how far a CloudWatch alarm has been breached), and simple scaling (a single fixed adjustment, with a cooldown between each scaling action). AWS explicitly recommends target tracking as the default choice, for example a policy that targets 50% average CPU utilization across the group: as real traffic pushes CPU above 50%, the group's desired capacity rises; as traffic drops, it falls back down, always clamped between the group's min and max. One more nuance worth knowing: when a group is already close to its desired capacity and only a few instances are found unhealthy, AWS's docs describe a deliberately cautious default of replacing "only up to 10 percent of the group's desired capacity at a time," so a flaky health check or a genuine partial outage doesn't get "fixed" by tearing down the whole fleet at once.

4. What a load balancer is, and the ALB-vs-NLB basics

Elastic Load Balancing's own summary of what it does is worth quoting directly: it "automatically distributes your incoming traffic across multiple targets, such as EC2 instances, containers, and IP addresses, in one or more Availability Zones. It monitors the health of its registered targets, and routes traffic only to the healthy targets." A load balancer is the single, stable address clients connect to; behind it, you attach one or more listeners (a protocol and port to watch for connections), and each listener's rules decide which target group a given request goes to.

AWS currently documents four load balancer types (Application, Network, Gateway, and the older Classic, which AWS recommends migrating away from); this digest sticks to the fundamentals of the two most common current-generation types, leaving a deeper ALB-vs-NLB-vs-GWLB comparison for a future unit. An Application Load Balancer (ALB) "functions at the application layer, the seventh layer" of the OSI model, meaning it can actually read HTTP/HTTPS requests and route based on their content, like the URL path or the Host header, using a default routing algorithm of round robin (with least-outstanding-requests available as an alternative). A Network Load Balancer (NLB) "functions at the fourth layer" of the OSI model instead, routing raw TCP, UDP, or TLS connections without reading application content; AWS notes it "can handle millions of requests per second" and, unlike an ALB, supports a static IP address per subnet. As a simplification worth flagging plainly: in a common web-application setup, that basically comes down to "ALB for HTTP-aware routing, NLB for raw throughput or a fixed IP," but plenty of real architectures use both, or use them for different tiers of the same system.

5. Target groups and health checks — how a load balancer decides who's healthy

A target group is where a load balancer's routing decisions actually land: it "routes requests to one or more registered targets... using the protocol and port number that you specify." For an ALB, targets are commonly EC2 instances registered by instance ID (IP addresses and Lambda functions are also supported target types, but instance ID is the fundamental case for this digest). Health checks are configured per target group, not per load balancer, which is what lets one load balancer front several independently-monitored services at once.

The health check settings themselves follow a concrete, documented default: by default, an ALB target group checks each target roughly every 30 seconds, waits up to 5 seconds for a response, and needs 2 consecutive failures before marking a target unhealthy or 5 consecutive successes before marking it healthy again, requesting the path / unless you configure a different one. Concretely: if your instance's health check path is /health and that endpoint starts returning errors, the target flips to unhealthy after 2 failed checks (roughly a minute later, at the default interval) and the load balancer stops sending it new traffic; if it recovers, it takes 5 consecutive passes before traffic resumes. When a target is deregistered (for example, because an Auto Scaling group is terminating it), it doesn't vanish instantly either, it enters a draining state governed by the deregistration delay (300 seconds by default) so in-flight requests get a chance to finish.

6. How an Auto Scaling group and a load balancer actually connect

The connection point is deliberately simple: you attach a target group to an Auto Scaling group. From that moment on, AWS's docs describe the wiring as automatic in both directions: "instances that are launched by Auto Scaling are automatically registered with the target group, and instances that are terminated by Auto Scaling are automatically de-registered from the target group." You don't write code to keep the target group's membership in sync with the group's membership, the two services do it for you.

The other half of the connection is optional but valuable: turning on ELB health checks for the Auto Scaling group, covered in section 3. Once that's on, AWS is explicit that "Amazon EC2 Auto Scaling can replace a running instance if any of the Elastic Load Balancing load balancers you attach to the Auto Scaling group report it as unhealthy," not just when the instance itself fails an EC2 status check. Put together, a concrete end-to-end example: you run an Auto Scaling group with desired capacity 3 behind an ALB target group. One instance's application process hangs and stops responding to its /health path. The ALB's target group marks it unhealthy after 2 failed checks and stops routing traffic to it (section 5); because ELB health checks are turned on for the group, the Auto Scaling group treats that same instance as unhealthy on its next check and replaces it (section 3); the replacement launches from the launch template, passes its own health checks, and gets auto-registered with the target group before it's marked InService (section 2), and traffic resumes flowing to it, with no one touching a console in between.

Why it matters

This is the piece that turns Part 1's single instance into something closer to a real production system. A custom AMI from Part 1 is exactly what a launch template points at, so the work you'd do to bake your application into an image is what makes a scale-out event bring up a working server automatically, not a blank one. And the health check chain across sections 3, 5, and 6 is the actual mechanism behind the promise "if a server dies, the app stays up": nothing here is magic, it's a load balancer's health check flipping a flag, an Auto Scaling group reading that flag (if you told it to), and a launch template supplying the recipe for whatever gets launched next.

Remember this

  • An Auto Scaling group is bounded by three numbers: minimum size, maximum size, and desired capacity in between; it launches instances from a launch template to reach that number and replaces anything it judges unhealthy.
  • Health-check-driven replacement (is this instance broken?) and dynamic scaling (do we need more or fewer instances right now?) are two separate mechanisms; EC2 status checks are on by default, ELB health checks and scaling policies are opt-in.
  • A load balancer is clients' single point of contact; it forwards requests through a listener's rules to a target group, and only to targets the target group's health checks currently call healthy.
  • ALB works at layer 7 (it reads HTTP and can route by path or host); NLB works at layer 4 (it routes raw TCP/UDP/TLS connections and can push far higher throughput with a static IP).
  • Attaching a target group to an Auto Scaling group makes registration and deregistration automatic; turning on ELB health checks for the group additionally lets the load balancer's health verdict, not just EC2's, trigger a replacement.

Try it yourself

  1. Launch your first Auto Scaling group. Create a launch template from a Free Tier-eligible AMI and instance type (reusing what you launched in Part 1), then create an Auto Scaling group with min 1, desired 2, max 3. Done when: you can see two instances reach the InService state in the console, and you can point to which setting is the minimum, the desired capacity, and the maximum.
  2. Watch health-check-driven replacement happen. Manually terminate one of the group's instances (not through the group, directly on the instance) and watch the Auto Scaling group's activity history. Done when: you've seen a new instance launch on its own to bring the group back to desired capacity, and you can explain why it's not the same instance you deleted.
  3. Put a load balancer in front of your group. Create an Application Load Balancer and a target group, then attach the target group to your Auto Scaling group. Done when: refreshing the load balancer's DNS name in a browser reaches your instances (a simple page that prints the instance ID is enough to prove which one answered), and both instances show as registered targets.
  4. Break a health check on purpose. Stop the web server process (or the health check listener) on one instance without terminating it, and watch the target group console. Done when: you've seen that target flip to unhealthy after the unhealthy threshold's worth of failed checks, and confirmed traffic stopped going to it while the other instance kept answering.
  5. Turn on ELB health checks for the group and reproduce the end-to-end example from section 6. With the previous exercise's broken instance still unhealthy in the target group, turn on Elastic Load Balancing health checks for the Auto Scaling group. Done when: the Auto Scaling group replaces the broken instance on its own (not just the target group flagging it), and the replacement shows up registered and healthy in the target group without you registering it by hand.
  6. Set up one target tracking scaling policy. Add a target tracking policy on average CPU utilization (a round number like 50% is fine) to your group, then generate CPU load on an instance (a simple busy-loop script is enough). Done when: you've watched desired capacity rise as CPU climbs and fall back once load stops, and it never exceeds the group's max. Cost caution: a load balancer and its running instance-hours aren't covered by the same always-on Free Tier allowance as a single stopped/started EC2 instance from Part 1, so delete the load balancer, target group, and Auto Scaling group when you're done for the day rather than leaving them running.
