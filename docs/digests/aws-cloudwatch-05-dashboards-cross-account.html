CloudWatch Dashboards and Cross-Account, Cross-Region Observability

So far we've made metrics, alarms and logs. A dashboard is where you put them on one screen so a human can take them in at a glance. And once your company has more than one AWS account (very common), the next question is how to watch all of them from one place. This digest covers both: building dashboards, and the two CloudWatch features for looking across accounts and Regions.

In one line

A CloudWatch dashboard is a customisable page of widgets (graphs, numbers, alarm statuses, log query results, notes) described by a JSON document, and cross-account observability lets a central "monitoring account" see the telemetry of many "source accounts".

The big idea

Every piece of CloudWatch we've met answers one question at a time. A dashboard answers a whole situation: "is the checkout flow healthy right now?" You arrange widgets on a grid: a graph of latency, a number for error count, the status of the three alarms that matter, a Logs Insights table of the latest failures, and a text box that says what to do if it goes red. The page is saved under a name and anyone with permission can open it.

The second half is about boundaries. Many organisations split their workloads across several AWS accounts for security and billing reasons. That splits monitoring too, unless you connect the accounts. CloudWatch gives two ways: the newer cross-account observability (metrics, logs, traces and more, within a Region, using a monitoring account, sinks and links) and the older cross-account cross-Region console (mainly dashboards, alarms and metrics, using IAM roles). The docs recommend the newer one when you can use it.

Key terms

  • Dashboard: a named, saved page of widgets. Created in the console, with the CLI, or through the PutDashboard API.
  • Widget: one tile on a dashboard. Types in the dashboard JSON: metric, text, log, alarm, explorer, chart.
  • Dashboard body: the JSON string that defines the whole dashboard, including each widget's position and properties.
  • Grid: dashboards use a 24-column layout. A widget has x, y, width and height in grid units.
  • Dashboard variable: a dropdown on the dashboard (for example, "which Lambda function?") that changes what every widget shows.
  • Monitoring account: the central account that can view telemetry from other accounts.
  • Source account: an account that generates telemetry and shares it with a monitoring account.
  • Sink: the attachment point resource in a monitoring account. Source accounts link to it.
  • Observability link: the resource, managed by the source account, that represents the connection to a monitoring account.
  • Observability Access Manager (OAM): the API and CLI commands behind sinks and links.
  • Sharing account: in the older console-based approach, an account that shares its CloudWatch data through an IAM role.

How it works

Grounding: why a dashboard is more than a pretty graph

The docs describe three things dashboards are for: a single view of selected metrics and alarms across one or more Regions; an operational playbook (guidance for team members during incidents, which you can put right on the page as text); and a shared, common view of critical measurements so people in an incident are all looking at the same facts. That second use is easy to overlook. A dashboard with a text widget saying "if this graph is red, run the restart runbook" is documentation that sits next to the evidence.

1. Widgets: what you can put on a dashboard

From the docs' widget page:

  • Graph widgets of one or more metrics: line, stacked area, number, gauge, bar and pie.
  • Number widget: the latest value (with a sparkline of the trend). Good for "errors in the last 5 minutes".
  • Gauge widget: a value shown within a range, such as a percentage.
  • Alarm widget: either a single alarm's graph and status, or an alarm status widget, a grid of alarm names and current states (no graphs), holding up to 100 alarms.
  • Table widget: raw data points and a summary.
  • Metrics explorer widget: graphs of many resources sharing a tag or property, which updates as matching resources are created or deleted.
  • Text widget: a block of Markdown. The playbook tile.
  • Log widget: shows the results of a Logs Insights query (the JSON type is log).
  • Linked graphs: link them so zooming one zooms the others.

Caveat: the docs also describe a custom widget type that I'm not covering.

One practical note from the docs: if a metric hasn't published data in the past 14 days, you can't find it by searching when adding it to a graph, but you can add it manually.

2. The dashboard body: it's just JSON

Behind every dashboard is a JSON document, the dashboard body. The docs say it can hold between 0 and 500 widget objects, and the widgets array is required (though it can be empty). Each widget has:

  • type: metric, text, log, alarm, explorer or chart.
  • x and y: position on the 24-column grid (x is 0 to 23). If you leave them out, the default is the next available position.
  • width (1 to 24, default 6) and height (1 to 1000, default 6).
  • properties: details that depend on the type. For a metric widget that includes a metrics array, the stat, period, region, and title.

Top-level options include start (for example -PT6H for the last six hours), periodOverride (auto or inherit), and an optional variables array of up to 25 variables.

Create or replace one with the CLI. The docs' example shape:

aws cloudwatch put-dashboard --dashboard-name Dashboard-A --dashboard-body '{"widgets":[{"height":6,"width":6,"y":0,"x":0,"type":"metric","properties":{"view":"timeSeries","stacked":false,"metrics":[["Namespace","CPUUtilization","Environment","Prod","Type","App"]],"region":"us-east-1"}}]}'

Details from the CLI reference: the dashboard name allows up to 255 characters, using letters, digits, hyphen and underscore. If a dashboard with that name exists it is replaced entirely (not merged). The output has a DashboardValidationMessages list: empty means success, warnings mean it saved but some widgets might not render, errors mean it failed. Tags (up to 50) are only applied on creation. The docs also say "all dashboards in an account are global, not Region-specific", and suggest a tip: build one in the console, then use Actions, View/edit source to copy its JSON as a template, and add a text widget to scripted dashboards saying they're managed by script.

Simplification: a metric widget's metrics array has its own compact format (namespace, metric name, then dimension name/value pairs). The reference page covers it, along with metric math and annotations.

3. Cross-account observability: monitoring and source accounts

This is the newer feature. The docs say it lets you monitor and troubleshoot applications that span multiple accounts within a Region, searching, visualising and analysing metrics, logs, traces, Application Signals services and SLOs, Application Insights applications and Internet Monitor monitors across linked accounts "without account boundaries".

The vocabulary: a monitoring account is the central one. A source account generates telemetry and shares it. A sink is created in the monitoring account (each account can have one sink per Region, managed by the monitoring account). A source account creates an observability link to that sink (managed by the source account).

Rules and numbers from the docs:

  • Each monitoring account can be linked to as many as 100,000 source accounts; each source account can share with as many as five monitoring accounts.
  • A source account can also be a monitoring account, but it then sends only its own data onward, not its sources' data.
  • Both sides pick telemetry types. If the monitoring account allows more types than the source shares, the link works and only the types selected on both sides flow. If the source selects more than the monitoring account allows, link creation fails and nothing is shared.
  • A metric name doesn't show up in the monitoring account console until that metric emits new data points after the link is created.
  • You remove a link from the source account; to delete a sink you must first remove all links to it.
  • Sharing can be everything, or filtered: a subset of metric namespaces or a subset of log groups.
  • The docs recommend linking via AWS Organizations so new accounts are onboarded automatically, and recommend a new dedicated account as the monitoring account. They also describe a CloudFormation template or URL method for setup.
  • The docs state cross-account observability has no extra cost for logs and metrics, and the first trace copy is free. I'm not quoting anything else about price.

What you can do from the monitoring account (docs): graph metrics from source accounts (one graph can mix accounts), create alarms in the monitoring account that watch source-account metrics, view log events and run a single Logs Insights query across log groups in many source accounts, and see source-account nodes in an X-Ray trace map.

4. Cross-account dashboards in the JSON

Two optional properties make a widget point elsewhere: accountId (which account the widget or metric lives in; default is the signed-in account) and region (default is the console's current Region). They can be set on the whole widget or per metric, so one metric math expression can combine EC2 CPU from account A in us-east-1 and account B in eu-west-1. The docs show the same accountId/region properties on alarm and Logs Insights widgets.

5. The older option: the cross-account cross-Region console

This predates the above. A sharing account creates an IAM role (named CloudWatch-CrossAccountSharingRole in the docs) that trusts the monitoring account; the monitoring account gets a service role (ServiceRoleForCloudWatchCrossAccountV2). You then get an account selector in the console and can build dashboards from many accounts and Regions.

  • Cross-Region works automatically for metrics and dashboards in one account: no extra steps.
  • The docs list real limits of this older approach: it does not give cross-account or cross-Region visibility for logs, and it does not support creating alarms on metrics in other accounts or Regions from a monitoring account. They also say you cannot create an alarm in one Region that watches a metric in a different Region.
  • Sharing grants read-only access to every user who has matching permissions, so the docs warn to specify only accounts you know and trust.

This is why the docs steer you to cross-account observability when you can use it: it covers logs and alarms in monitoring accounts, which the older one doesn't.

Quick chooser (simplification). Need logs or alarms across accounts in one Region: cross-account observability (sinks and links). Only need metric graphs on a dashboard spanning accounts and Regions: either works, but the docs recommend observability where possible. Need a dashboard spanning Regions inside one account: nothing to set up, just set region per metric.

Caveat: "within a Region" in the observability docs means the sink and links are per Region; the docs' own dashboard section says cross-account dashboards can combine Regions. I haven't worked out exactly how those two statements combine in practice, so test before relying on it.

6. Permissions and cost hygiene

  • To view dashboards you need cloudwatch:GetDashboard and cloudwatch:ListDashboards; to create or modify, cloudwatch:PutDashboard; to delete, cloudwatch:DeleteDashboards. Alternatively the AdministratorAccess or CloudWatchFullAccess policies.
  • For cross-account observability, setting up a sink needs the oam:CreateSink-style permissions listed in the docs; viewing needs oam:Get* and oam:List* plus permission to see the resource types.
  • From the Insights docs: a Logs Insights widget re-runs its query on every refresh, and queries are charged by data scanned, so don't put a heavy query on a fast-refreshing dashboard.

Why it matters

During an incident, nobody wants to hunt for the right graph. A prepared dashboard is the shortest path from "something's wrong" to "this is where". And once an organisation grows past one account, the ability to see everything from one monitoring account is often the difference between having observability and having ten separate islands.

Remember this

  • A dashboard is a JSON document: widgets on a 24-column grid, up to 500 widgets, saved by name and replaced whole on update.
  • Text widgets make dashboards into playbooks; alarm status widgets give a one-glance health grid (up to 100 alarms).
  • Cross-account observability: sources link to a sink in a monitoring account; sharing is the overlap of what each side selects.
  • accountId and region on a widget or metric point it at another account or Region.
  • The older cross-account console doesn't cover logs or alarms on other accounts' metrics; the newer feature does.

Recall questions

  1. What happens if you run put-dashboard twice with the same name and different bodies?
  2. What are x and width measured in, and how many units wide is the dashboard?
  3. Who creates an observability link: the monitoring account or the source account? Who manages the sink?
  4. A source account shares logs, metrics and traces, but the monitoring account only allows logs and metrics. What happens? What about the reverse?
  5. Why would you choose cross-account observability over the older cross-account console for a team that needs cross-account log queries?

Try it yourself

  1. Hand-write a dashboard. Take the docs' put-dashboard example, change the namespace and metric to ones from your earlier digests (such as your custom metric namespace), and run it. Done when: the dashboard opens in the console and DashboardValidationMessages was an empty list.
  2. Make a playbook tile. Add a text widget at the top with three lines of Markdown ("What this shows / When it is red / First thing to try"). Done when: someone who has never seen your project could act on it.
  3. Round trip. Build a dashboard in the console, copy its JSON via View/edit source, change the title and width of one widget, and push it with a new name through the CLI. Done when: the two dashboards differ in exactly the ways you intended.
  4. Alarm status grid. Add an alarm status widget listing your alarms from the alarms digest, then use set-alarm-state to flip one. Done when: you've seen the widget's tile change state.
  5. Log tile. Add a Logs Insights widget with a small query against your lab log group from the previous digests. Done when: the table renders and you've noted what changes if the dashboard auto-refreshes (it re-runs the query).
  6. Paper design (no second account needed). Sketch an organisation with three accounts and decide which is the monitoring account, what each source shares, and which log groups you'd filter out of sharing. Done when: you can write the sentence "the link works and shares X" or "the link fails because Y" for two different configurations. If you do have two accounts and want to try it, follow the docs' console setup for monitoring and source accounts.
