Inference Optimization: Model-Level and Service-Level Techniques

Part 1 told you how to measure inference and where it gets stuck. This part is the toolbox. At the model level: compression (quantization, distillation, pruning), beating the one-token-at-a-time decoding bottleneck (speculative decoding, inference with reference, parallel decoding), making attention cheaper (the KV cache and the ways to shrink it), and kernels and compilers. At the service level: batching, separating prefill from decode, prompt caching and parallelism strategies. The chapter's Summary closes it, and it also closes the book's list of model-adaptation techniques.

In one line

Inference gets faster and cheaper by shrinking the model, dodging the sequential-decoding and attention bottlenecks, writing code that suits the hardware, and scheduling requests and chips more cleverly, and the model-level changes can alter quality while the service-level ones shouldn't.

The big idea

There are three places to optimize: the model (crafting better arrows, in the chapter's archery analogy), the hardware (training a better archer) and the service (refining the whole shooting process). The chapter covers the first and third. A key distinction to hold on to: model-level techniques often change the model and therefore can change its behavior, whereas service-level techniques generally leave the model as it is and shouldn't change output quality. The chapter shows evidence that quality can drift: the same Llama models scored slightly differently on benchmarks when served by different providers, plausibly because of different optimization choices. In production you usually combine techniques from several levels. And most application developers who use a model API will never implement these; they're worth understanding so you can evaluate the efficiency of the services you buy.

Key terms

  • Model compression: techniques that shrink a model (quantization, distillation, pruning).
  • Pruning: removing nodes, or zeroing the least useful parameters, to make a model smaller or sparser.
  • Speculative decoding: a fast draft model proposes tokens and the target model verifies them in parallel.
  • Draft model / target model: the cheap proposer and the model whose output you actually want.
  • Inference with reference: drafting tokens by copying spans from the input instead of using a model.
  • Parallel decoding: generating several future tokens at once, then verifying them (Lookahead decoding, Medusa).
  • KV cache: stored key and value vectors for earlier tokens, reused so they're not recomputed at each step.
  • Multi-query, grouped-query and cross-layer attention: designs that share key-value vectors to shrink the KV cache.
  • Local windowed attention: attending only to a nearby window of tokens.
  • PagedAttention: vLLM's way of managing the KV cache in non-contiguous blocks.
  • Kernel: code optimized for a particular hardware accelerator.
  • Operator fusion: combining several operations into one pass to avoid repeated memory access.
  • Compiler / lowering: a tool that converts model code into a form the hardware can run, ideally using specialized kernels.
  • Static, dynamic, continuous batching: three ways of grouping requests, explained below.
  • Prompt cache (context cache, prefix cache): stored processing of repeated prompt segments.
  • Replica, tensor and pipeline parallelism: copying the model; splitting operations across devices; splitting the model into stages.
  • Context and sequence parallelism: splitting a long input, or the operators applied to it, across devices.

How it works

Grounding: why LLM inference is expensive

The chapter names three traits of transformer-based autoregressive models that make inference resource-hungry: model size (billions of weights to hold and move), autoregressive decoding (one token at a time) and the attention mechanism (each new token must relate to all earlier ones). The model-level techniques below map onto these three. Note also that the cost is lopsided: across model APIs, the chapter says an output token costs roughly two to four times an input token, and an Anyscale experiment found one output token affects latency about as much as 100 input tokens.

Model compression

You already met quantization (Chapter 7: fewer bits per value) and distillation (Chapter 8: a small student imitates a large teacher). The new one is pruning, which comes in two senses: remove entire nodes (changing the architecture and shrinking the parameter count), or find the least useful parameters and set them to zero. The second makes the model sparse: the parameter count stays the same, but fewer are non-zero, which saves storage and can speed computation. Pruned models can be used as is or finetuned to recover lost quality. Research results look encouraging (the chapter cites a result that non-zero parameters in certain networks could be cut by over 90% with no loss in accuracy), but in practice pruning is less common: it demands understanding of the model's architecture, often gives a smaller boost than the alternatives, and sparse models only help on hardware that can exploit sparsity. By far the most popular approach is weight-only quantization (easy, works out of the box, very effective), with distillation also common. The chapter points out we're near quantization's limit, since you can't go below 1 bit per value.

The autoregressive decoding bottleneck

Generating one token at a time means a 100-token answer at 100 ms per token takes 10 seconds, and, as Part 1 explained, each step loads the whole model's weights from memory while using little of the chip's arithmetic. The techniques here are described as still evolving.

Speculative decoding

The idea: use a small, fast draft model to guess the next several tokens, and let the big target model check the guesses all at once. Steps, given tokens so far:

  1. The draft model proposes K tokens.
  2. The target model verifies those K tokens in parallel.
  3. It accepts the longest prefix (left to right) that it agrees with, say j tokens.
  4. It then generates one extra token itself, and the loop repeats from the new position.

If none are accepted you get one target-made token per loop; if all K are accepted you get K + 1 tokens in one loop. Why doesn't this just add overhead? The chapter gives three insights: verifying in parallel is cheaper than generating sequentially (it turns decode's profile into prefill's); some tokens are easy to predict, so a weaker model can get them right and have a high acceptance rate; and since decoding is bandwidth-bound, there are idle FLOPs available "for free" for verification. A side-effect: if your MFU is already maxed out, speculative decoding makes less sense.

Practical notes from the chapter: acceptance rates depend on the domain (higher for structured text like code); larger K means fewer verification calls but lower acceptance; the draft model can have any architecture but ideally shares the target's vocabulary and tokenizer; you can train a custom draft or reuse a weaker existing model. A reported example: DeepMind trained a 4B draft model for Chinchilla-70B that produced tokens about eight times faster (1.8 versus 14.1 ms per token) and cut overall latency by more than half without changing response quality. It's relatively easy to implement (the chapter says about 50 lines in PyTorch) and is available in popular inference frameworks (vLLM, TensorRT-LLM, llama.cpp).

Inference with reference and parallel decoding

Inference with reference is like speculative decoding but the draft tokens come from the input itself. If you ask a question about an attached document, the answer may quote it; if you ask for a bug fix, most of the code is unchanged. Instead of generating the repeated text token by token, copy the matching span from the context and verify it. No extra model is needed, but it only helps when outputs overlap heavily with the context (retrieval, coding, multi-turn chat); one paper reports roughly 2x speedup in such cases.

Parallel decoding tries to break the sequential dependency altogether: predict several future tokens at once, even before knowing the earlier ones. That can work because the preceding text often constrains the next few tokens (after "the cat sits", the word after the next is likely "the" whatever the preposition). Lookahead decoding generates the parallel tokens from the same decoder and verifies using the Jacobi method (generate K tokens, check consistency, regenerate only the failures, repeat). Medusa adds extra decoding heads, small trained layers where head k predicts the token k positions ahead, while the original model stays frozen, and it uses tree-based attention to pick the best combination of candidates. NVIDIA reported up to 1.9x faster Llama 3.1 token generation with Medusa on certain hardware. The chapter's honest note: parallel decoding is unintuitive and some techniques are hard to implement.

Attention and the KV cache

To generate each token, the model needs the key and value vectors of all earlier tokens. Rather than recompute them every step, it stores them in a KV cache and only computes the new token's vectors. The cache is used in inference only, not training, because in training all tokens are known in advance and can be processed at once.

The catch: the cache grows linearly with sequence length and also with batch size, and can be huge. The chapter cites an estimate that for a 500B+ model with batch size 512 and context 2,048, the KV cache is about 3 TB, three times the weights. Unoptimized size is:

2 x B x S x L x H x M

where B is batch size, S sequence length, L number of layers, H model dimension and M bytes per value. For Llama 2 13B (40 layers, dimension 5,120), batch 32, sequence 2,048 and 2 bytes: 2 x 32 x 2,048 x 40 x 5,120 x 2, which I computed at about 53.7 GB (the chapter rounds to 54 GB). The attention computation also grows with length: the chapter's text says it grows "exponentially" but its footnote gives the correct picture of quadratic growth, O(n squared), which is how I'd describe it. This is one reason long context is hard.

Three families of fixes, as the chapter groups them:

  • Redesign attention. Because this changes the architecture, it can only be done during training or finetuning. Local windowed attention attends only to a fixed window of nearby tokens (a 1,000-token window on a 10,000-token average cuts the cache by 10x), and can be interleaved with global attention. Cross-layer attention shares key-value vectors across adjacent layers. Multi-query attention shares them across all query heads, and grouped-query attention is the middle ground: groups of heads share a set. The chapter reports that Character.AI, whose average conversation history is 180 messages, combined multi-query attention, interleaved local and global attention, and cross-layer attention to cut KV cache by over 20x, so that memory stopped being the bottleneck for big batches.
  • Manage the cache better. vLLM popularized PagedAttention, which divides the cache into non-contiguous blocks to reduce fragmentation and allow flexible sharing. Others: KV cache quantization, adaptive compression and selective caching.
  • Write faster attention kernels. See next.

Kernels and compilers

A kernel is code optimized for a specific accelerator, typically for a heavy routine (matrix multiplication, attention, convolution) that runs repeatedly in parallel. Writing one requires knowing the chip's memory hierarchy and is done in lower-level languages such as CUDA (NVIDIA), Triton (OpenAI) or ROCm (AMD). It used to be a niche craft done by chip makers and framework teams, but more AI engineers are learning it. The best-known attention kernel is FlashAttention, which fuses several common operations to run faster; it was first built for the A100 and later versions for the H100, which illustrates that kernels must be redone for new hardware.

Four common techniques inside kernels:

  • Vectorization: process multiple contiguous elements at once rather than one at a time.
  • Parallelization: split an array into independent chunks processed on different cores.
  • Loop tiling: reorder data access to fit the hardware's memory and cache (a pattern good on a CPU may be poor on a GPU).
  • Operator fusion: merge multiple operations into one pass so data isn't read and written repeatedly. This needs the most knowledge of the model's operators.

A compiler bridges the model and the hardware: a model script is a series of operations that must be converted ("lowered") into something the hardware can run, replacing operations with specialized kernels where possible. Compilers can be standalone (Apache TVM, MLIR) or built into frameworks (torch.compile, XLA/OpenXLA, TensorRT's compiler). The chapter shows a case study from the PyTorch team on Llama-7B on an A100 80GB: compile with torch.compile, quantize weights to INT8, then INT4, then add speculative decoding, with throughput rising at each step. It notes it's unclear how each step affected output quality.

Service-level optimization: batching

Service-level techniques manage resources for dynamic workloads and generally leave the model, and its quality, untouched. The simplest cost-cutter is batching: process requests that arrive together as a group. The chapter's analogy is cars versus a bus: a bus moves more people but can lengthen each journey, and if done smartly the latency impact can be small.

  • Static batching: wait for a fixed number of requests. Like a bus that leaves only when full; the first request waits for the last, however late.
  • Dynamic batching: set a maximum wait. With batch size four and a 100 ms window, process when four requests are in or 100 ms has passed, whichever comes first. Latency stays controlled; batches may be partly empty, wasting compute.
  • Continuous (in-flight) batching: for LLMs, requests in one batch may need very different numbers of tokens. In naive batching, a 10-token reply waits for a 1,000-token one. Continuous batching returns each response as soon as it finishes and slots a new request into the freed place, like a bus that picks up a new passenger as soon as one gets off. It's from the Orca paper.

Decoupling prefill and decode

Because prefill is compute-bound and decode is bandwidth-bound, putting both on one machine makes them compete: a new prefill job can drain compute from decode jobs already running and slow their TPOT. A common fix is to disaggregate: run prefill and decode on different instances (different GPUs). Papers cited in the chapter show this can significantly increase the volume of requests handled within latency limits, and the cost of moving intermediate state between them isn't substantial on modern high-bandwidth GPU clusters. The right ratio of prefill to decode instances depends on workload and goals; the chapter's example: with long inputs and a TTFT priority, 2:1 to 4:1; with short inputs and a TPOT priority, 1:2 to 1:1. Those are examples from the chapter, not recommendations.

Prompt caching

Many prompts share segments, most commonly the system prompt, but also a long document that many queries refer to, or the earlier turns of a long conversation. A prompt cache (also called a context cache or prefix cache) stores the processing of those overlapping segments, so they're handled once. The chapter's illustration: a 1,000-token system prompt and a million API calls a day means about a billion repetitive input tokens avoided daily. But it isn't free: the cache takes memory, and building your own is a real engineering effort unless your model API provides it. The chapter reports provider features as of its writing: Google Gemini gave cached input tokens a 75% discount but charged extra for cache storage; Anthropic promised up to 90% cost savings and up to 75% latency reduction, with a table showing, for example, a chat with a 100,000-token cached book dropping time to first token from 11.5 s to 2.4 s and cost by 90%. Treat those as dated vendor claims; check current documentation for terms.

Parallelism

Accelerators are built for parallel work, and the chapter covers a few strategies:

  • Replica parallelism: run multiple copies of the model to handle more requests at once, at the cost of more chips. Fitting models of different sizes onto different chips becomes a bin-packing puzzle (for example, three 13B models on a 40 GB GPU or reserve it for a 34B?).
  • Tensor parallelism (intra-operator): split the tensors within an operator across devices, such as splitting one matrix column-wise for a multiplication. It lets you serve models that don't fit on one machine and can cut latency, though communication overhead trims the gain. It's the most common model-splitting approach for inference.
  • Pipeline parallelism: split the model into stages on different devices, passing micro-batches along so stages overlap. It enables serving large models across machines but adds communication and so total latency per request, so latency-sensitive applications usually avoid it in favor of replicas; it's common in training for throughput.
  • Context parallelism: split the input sequence across devices (first half on one machine, second half on another). Sequence parallelism: split the operators across machines (attention on one, feedforward on another). Both help long inputs and are less common.

Which techniques matter most, and the Summary

The chapter's closing guidance: choose by workload and goals. KV cache work matters far more for long contexts; prompt caching for long overlapping prompts and multi-turn chat; if latency beats cost, scale up replicas. Across use cases, it names the most impactful as typically quantization (works well across models), tensor parallelism (lower latency and larger models), replica parallelism (straightforward) and attention optimization (big gains for transformers). The Summary also restates the core metric vocabulary (TTFT shaped by prefill, TPOT by decode, throughput tied to cost, a latency versus throughput trade-off), that model-level changes can change behavior while service-level ones keep the model intact, and that inference optimization completes the book's list of model adaptation techniques. The next chapter assembles them into a cohesive system.

Why it matters

This is the part of the stack where your bill and your user's patience are decided. Even if you only call APIs, you can now read a provider's feature list (prompt caching, batch pricing, speculative decoding, quantized variants) and know what it does and what it might cost in quality. And if you self-host, you have a map of what to try first: quantization, replicas and tensor parallelism, then attention and caching work.

Remember this

  • Model-level techniques (compression, speculative or parallel decoding, attention changes, kernels) may alter quality; service-level ones (batching, prefill/decode split, prompt caching, parallelism) shouldn't.
  • Speculative decoding: a cheap draft model proposes, the big model verifies in parallel and keeps the agreeing prefix. It exploits idle compute during bandwidth-bound decoding.
  • The KV cache avoids recomputation but grows with sequence length and batch size (2 x B x S x L x H x M bytes); attention redesigns and better cache management shrink it.
  • Continuous batching returns finished responses immediately and refills freed slots; disaggregating prefill from decode stops the two from slowing each other.
  • The chapter says the most broadly impactful are quantization, tensor parallelism, replica parallelism and attention optimization.

Try it yourself

  1. KV cache calculator (under an hour). Implement 2*B*S*L*H*M and test it on the chapter's Llama 2 13B example (B 32, S 2,048, L 40, H 5,120, 2 bytes). Done when you get about 53.7 GB and can show how it changes as you double S, double B, or halve M. (Mine printed 53.69 GB.) Then compute the effect of a window of 1,000 tokens on a 10,000-token workload.
  2. Speculative decoding simulator. Write a toy where a "draft" guesses each next word correctly with probability p and the "target" is the ground-truth sentence. Implement the loop: draft K words, accept the longest correct prefix, add one target word, repeat, counting target calls. Done when you can plot or print average target calls for p = 0.5, 0.8 and 0.95 and compare against one call per token. (On a 13-word sentence with K = 4, I got roughly 7.2, 4.3 and 3.3 calls respectively.) This is a toy of the control flow, with no real models or timing. 
    def one_round(target, i, draft_guess):   # draft_guess: list of K proposed tokens
    accepted = 0
    for j, tok in enumerate(draft_guess):
        if tok == target[i + j]: accepted += 1
        else: break
    return accepted + 1                  # + the target's own extra token
  3. Batching simulator. Model eight requests with different output lengths and arrival times. Simulate static batching (batch of 4, wait for the longest) and continuous batching (4 slots, refill on completion), measuring average latency. Done when continuous batching shows lower average latency on your inputs and you can explain why. (My toy run: about 74.5 vs. 27.75 time units for the two schemes on one made-up workload; the exact numbers mean nothing beyond the pattern.)
  4. Prompt cache by hand. Write a tiny cache keyed on the leading text of a prompt: for each incoming prompt, find the longest cached prefix, "pay" only for the remaining tokens (count by words), and store the new prefix. Done when 100 prompts sharing a 200-word system prompt show about 99 times the prefix cost avoided, and you can describe what happens if one character of the prefix changes.
  5. Window attention mask. Print a 12 x 12 grid for full causal attention and for a local window of 4 (a cell is "x" if the query position may attend to the key position). Done when you can count attended cells in each, and relate the difference to the KV cache saving.
  6. Replica or split? A decision memo. You must serve a 70B model at 8-bit on GPUs of 80 GB each (use the weights-only estimate from Chapter 7). Write half a page on whether one GPU suffices, what tensor parallelism would add, and when you would prefer more replicas, using the chapter's trade-offs. Done when you've named one latency risk and one cost risk of your choice.
