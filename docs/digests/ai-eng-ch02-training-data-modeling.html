Understanding Foundation Models, Part 1: Training Data & Model Design

What actually goes into a foundation model before it ever answers a prompt: where its training text comes from and what that leaves out, why the transformer architecture and its attention mechanism took over, and why making a model bigger only pays off if you feed it more data too. This is part 1 of 2 for this chapter; post-training and sampling are covered separately.

In one line

A foundation model's abilities come down to two decisions made long before you ever prompt it: what data it actually trained on, and whether its architecture and size were matched to that data, and getting either one wrong quietly caps how good the model can ever get.

The big idea

Model developers don't get to choose training data off a shelf of neatly balanced options. Mostly they take large slices of the open internet and shape them as best they can, and that choice shows up later as real gaps: certain languages and certain specialized domains end up underserved. Once there's data, someone has to decide what shape of model will actually learn from it. Since 2017 that's almost always meant the transformer architecture, built around a mechanism called attention that lets a model look directly at any earlier piece of text instead of squeezing everything through a single summary. And there's a sizing question sitting underneath both of those: making a model bigger only helps if you also feed it more training data, in something close to a fixed ratio. That relationship is called a scaling law, and it's arguably the single most useful mental model in this part.

Key terms

  • Common Crawl — a nonprofit that periodically scrapes huge portions of the public web (a few billion pages a month in 2022–2023) and publishes the raw result. It's a common starting point for training text, warts and all.
  • C4 (Colossal Clean Crawled Corpus) — Google's filtered, "cleaned up" subset of Common Crawl. Cleaner than the raw crawl, but not free of quality problems.
  • Low-resource language — a language with little representation in typical internet-scraped training data, which tends to make models noticeably worse at it.
  • Domain-specific model — a model trained or adapted with data from one specialized area (protein structures, medical scans) rather than general internet text.
  • Transformer — the neural network architecture (Vaswani et al., 2017) built around the attention mechanism, and the dominant architecture behind today's language-based foundation models.
  • Attention mechanism — the part of a transformer that decides, for each token being generated, how much to "weigh" every earlier token when deciding what comes next.
  • Query, key, value vectors (Q, K, V) — the three vectors attention computes for each token. Roughly: the query is what you're looking for, each key is a label on a piece of earlier information, and each value is that information's actual content.
  • Multi-headed attention — running several smaller attention computations ("heads") in parallel so a model can track several different kinds of relationships between tokens at once.
  • Prefill — the first phase of generating a response: the model processes all input tokens at once, in parallel, building the internal state it needs to start generating.
  • Decode — the second phase: the model generates output one token at a time, and each new token depends on everything generated so far, so this part can't be parallelized the way prefill can.
  • Transformer block — one repeating unit of a transformer, combining an attention module with an MLP module. A model's "number of layers" is how many of these blocks are stacked.
  • MLP (multi-layer perceptron) / feedforward layer — a small stack of weight matrices (linear layers) separated by a simple nonlinear function, used inside every transformer block to let the model learn nonlinear patterns.
  • Embedding layer — the module at the very start of the model that turns tokens (and their positions in the sequence) into numeric vectors the rest of the model can work with.
  • Output layer (unembedding layer / model head) — the module at the very end that turns the model's internal vectors back into probabilities over the vocabulary, so a next token can be picked.
  • Parameter — an adjustable number inside a model that gets tuned during training. "Model size" is usually just a count of these.
  • Hyperparameter — a setting a person chooses before or during training to configure the model or control how it learns (number of layers, batch size, learning rate). Not learned by the model itself, unlike a parameter.
  • Sparse model / mixture-of-experts (MoE) — a model where large chunks of parameters are effectively switched off for any given input. An MoE model splits its parameters into "expert" groups and only activates a few of them per token, so it can have a huge parameter count while costing far less to run per token.
  • Token vs. training token — a token is the basic text unit a model reads. A dataset's raw token count is fixed, but the number of training tokens can exceed it if the model sees the data more than once (each full pass through the data is an epoch).
  • FLOP / FLOP-s — a FLOP (floating point operation) measures how much compute a task takes; FLOP/s measures how fast a machine can do those operations, per second.
  • Compute-optimal — describes a model size and dataset size that gets the best possible performance out of a fixed compute budget, neither over- nor under-sized for the data (or vice versa).
  • Emergent ability — a capability that only shows up once a model crosses some scale threshold, and isn't visible (or predictable) by looking at smaller versions of the same model.

How it works

Here's the grounding picture for this part: before a foundation model can do anything useful, two decisions get made about it, usually by people you'll never talk to. First, what data does it train on, since a model can only reflect what was actually in front of it during training. Second, what shape should the model be: which architecture, how many parameters, and how much data to match that size. Get the data wrong and you get a model that's confidently weak at things it barely saw. Get the size-to-data ratio wrong and you're either wasting compute on a model too big for what it learned, or holding a smaller model back with more data than it can use. The rest of this section walks through both halves in turn: training data first, then architecture and size.

Where training data actually comes from: Common Crawl and C4

A huge share of the text used to train language-based foundation models traces back to Common Crawl, a nonprofit that periodically crawls the public web and just publishes what it finds, roughly 2 to 3 billion pages a month in 2022 and 2023. Google publishes a cleaned-up subset called C4 (the Colossal Clean Crawled Corpus), but "cleaned up" is relative: an analysis by the Washington Post found that the most common websites represented in this kind of dataset include outlets that score low for trustworthiness on NewsGuard's rating scale. In plain terms, this training text mix includes real amounts of clickbait, misinformation, and worse, alongside perfectly ordinary writing.

Despite the quality problems, some version of Common Crawl shows up in most foundation models that disclose their training sources (GPT-3 and Gemini are two named examples), and it's a reasonable guess that it's used even more widely by models that don't disclose anything, since fewer companies publish this information than used to. Some teams apply simple filtering heuristics to cut down on the worst of it. As one example, OpenAI trained GPT-2 using only Reddit links that had received at least three upvotes, which screens out content nobody engaged with at all, even though it's a fairly crude filter for quality.

Worth flagging: more data isn't automatically better. Using around 7 billion tokens of carefully chosen, high-quality coding data, one 2023 research effort (Gunasekar et al.) trained a 1.3-billion-parameter model that beat much larger models on several coding benchmarks. That's a real result but a specific one: it doesn't mean small, curated datasets always beat huge scraped ones, only that quality can sometimes substitute for scale on a narrow, well-defined task.

The multilingual gap

English dominates Common Crawl. One analysis (Lai et al., 2023) put English at close to 46% of the dataset, roughly eight times the next most common language, Russian, at around 6%. Several widely spoken languages are dramatically under-represented relative to how many people actually speak them: the same analysis found languages like Punjabi, Swahili, and Urdu making up a tiny sliver of Common Crawl compared to their share of world population.

That gap shows up directly in model behavior. On the MMLU benchmark (a set of about 14,000 multiple-choice questions across 57 subjects), GPT-4 performed clearly worse in under-represented languages like Telugu than in English, according to OpenAI's own 2023 reporting. A separate study testing GPT-4 on math problems found it solved problems in English more than three times as often as in Armenian or Farsi, and failed every attempt in Burmese and Amharic. Under-representation in the training data is a big part of the explanation, but the source is careful to note it isn't the whole story: a language's structure and the culture embedded in it can make it inherently harder for a model to learn well, independent of how much text is available.

A tempting fix is to translate everything into English, get an answer, then translate back. This isn't as clean as it sounds. It still requires a model that understands the low-resource language well enough to translate accurately in the first place, and translation loses information: some languages (Vietnamese is one example) use different pronouns to encode the relationship between speakers, information that simply disappears when everything collapses into English's "I" and "you."

Non-English languages can also be slower and more expensive to use, independent of quality. Response latency and cost both scale with the number of tokens involved, and tokenization efficiency varies a lot by language. Testing on a dataset of short texts translated across 52 languages, one study found the median token length for the same meaning was about 7 tokens in English versus roughly 32 in Hindi and 72 in Burmese, about ten times longer. Assuming similar per-token generation speed, that means roughly ten times the latency and, for token-priced APIs, roughly ten times the cost for the same content in Burmese versus English. This has pushed real investment into language-specific models: examples named in the source include ChatGLM, YAYI, and Llama-Chinese for Chinese, CroissantLLM for French, PhoGPT for Vietnamese, and Jais for Arabic.

Domain-specific models

General-purpose models handle a surprisingly wide range of domains (coding, law, science, business, and more) mostly because those domains show up in their training data in the first place. Vision data is harder to study this way, since there isn't a simple keyword filter for "what domain is this photo," so the source infers a model's domain strengths and gaps indirectly, by comparing benchmark performance across very different categories (birds, flowers, cars, traffic signs). Performance swings noticeably across those categories, which is itself evidence that a general model's competence isn't spread evenly across domains, even though there's no clean single number for "domain coverage."

Some domains need dedicated, purpose-built datasets no amount of internet scraping will provide. Two named examples worth knowing: drug discovery, which depends on protein, DNA, and RNA data in specific formats that are expensive to produce and rarely posted publicly, and cancer screening, which depends on X-ray and fMRI (functional magnetic resonance imaging) scans that are hard to obtain at scale because of patient privacy. Real domain-specific models built around exactly this kind of curated data include DeepMind's AlphaFold, trained on the sequences and 3D structures of around 100,000 known proteins; NVIDIA's BioNeMo, focused on biomolecular data for drug discovery; and Google's Med-PaLM2, which combines general language ability with medical data. Domain-specific models are especially common in biomedicine for these data-access reasons, though the source suggests (as a forward-looking idea rather than a demonstrated result) that other specialized fields, architecture or manufacturing among them, could plausibly benefit from the same approach.

Why the transformer took over from seq2seq

Before the transformer, the dominant architecture for sequence tasks (translation, summarization) was seq2seq (sequence-to-sequence), introduced in 2014 and popular enough that Google credited a 2016 seq2seq update with its biggest single jump in Google Translate quality at the time. Seq2seq has an encoder that reads the input and a decoder that generates the output, both built from RNNs (recurrent neural networks), which process tokens one at a time in order.

Seq2seq had two real problems. First, the decoder only ever saw the encoder's final hidden state, a single compressed summary of the whole input, and generated everything from that. That's a bit like being asked questions about a book but only being handed a one-paragraph summary of it, no matter how long the book actually was: detail gets lost. Second, because both the encoder and decoder are RNNs, processing has to happen strictly in order, one token at a time, which makes long inputs slow.

The transformer (Vaswani et al., 2017) solves both problems with attention: instead of compressing the whole input into one fixed summary, the model can look directly at any earlier token when deciding what to generate next, the equivalent of flipping to any page of the book instead of relying only on the summary. Attention itself wasn't new (Bahdanau et al. had already combined it with seq2seq's RNNs back in 2014), but the transformer's real innovation was showing attention works well without RNNs at all, which let input tokens be processed in parallel instead of one by one. That said, it's worth being precise about what got fixed: the transformer removes the sequential bottleneck for reading input, but generating output one token at a time is still sequential for the autoregressive language models built on top of it, for reasons covered next.

Inside attention: query, key, value

Attention works with three vectors computed for each token: a query (what the model is currently looking for), a key (a label on a piece of earlier information, like a page number), and a value (that information's actual content, like the page's text). To decide how much to focus on a given earlier token, the model takes the dot product of the current query vector with that token's key vector; a higher score means the model leans more heavily on that token's value vector when producing its next output.

This is almost always done with multiple attention "heads" running in parallel, each able to track a different kind of relationship between tokens, and their outputs get combined before moving on to the next part of the model. As one concrete point of scale: in Llama 2-7B, the model's internal (hidden) dimension is 4096, and with 32 attention heads, each head works with vectors of size 128 (4096 ÷ 32). One practical consequence worth remembering: every earlier token needs its own stored key and value vector, so the longer the sequence gets, the more of these need to be computed and kept around, which is a big part of why stretching a transformer model's usable context length is hard.

Prefill and decode: two different jobs

Because a transformer can process input tokens in parallel, generating a response happens in two distinct phases. Prefill is the first phase: the model reads every input token at once and builds the internal state it needs going forward, including the key and value vectors for the whole input. Decode is the second phase: the model generates output tokens one at a time, and because each new token depends on everything generated before it, this part genuinely cannot be parallelized the way prefill can. That split (parallel prefill, sequential decode) is the reason a lot of practical work on making models faster and cheaper focuses on these two phases separately rather than treating "speed" as one single problem.

Stacking blocks: transformer blocks, embeddings, and the output layer

A transformer model is a stack of repeated transformer blocks, and the "number of layers" you'll see quoted for a model is just how many of these blocks are stacked. Each block generally contains two parts: an attention module (the four weight matrices for query, key, value, and an output projection that transforms the combined result of all the attention heads) and an MLP module, a small stack of linear (feedforward) layers separated by a simple nonlinear function. That nonlinear step matters more than it sounds: without it, stacking linear layers wouldn't let the model learn anything a single linear layer couldn't already do. Simple functions like ReLU (which just zeroes out negative values) or GELU turn out to work as well as more complicated ones, while being cheaper to compute at scale.

Two extra modules bookend the stack of blocks. Before them sits an embedding module, which turns each token, plus its position in the sequence, into a numeric vector the rest of the model can work with; naively, the number of positions a model tracks caps its maximum context length, though there are techniques that stretch context length beyond that naive limit. After the stack of blocks sits the output layer (sometimes called the unembedding layer, or the model's "head"), which turns the model's final internal vectors into probabilities over the whole vocabulary, the raw material a sampling step then turns into an actual next token.

A model's total size comes down to a handful of dimension choices: the model's internal (hidden) dimension, which sets the size of the query/key/value/output-projection matrices; the number of transformer blocks; the size of the feedforward layer inside the MLP; and the vocabulary size. As one concrete comparison: Llama 2-7B uses 32 transformer blocks with a hidden dimension of 4096, while Llama 3-405B scales that up to 126 blocks with a hidden dimension of 16384, an example of how every one of these dimensions grows together as a model family scales up.

Alternative architectures nipping at the transformer's heels

The transformer isn't the only architecture that's ever mattered, just the current one. Earlier architectures had their moment and faded: seq2seq was the go-to for about four years (2014–2018), and GANs (generative adversarial networks) stayed popular a bit longer (2014–2019). The transformer has already outlasted both, in large part because so much engineering effort has gone into optimizing it since 2017 that any challenger needs to work well at real scale, on real hardware, not just in a research paper.

Even so, several alternatives are actively being developed. RWKV is an RNN-based architecture that can be parallelized for training and, because of its RNN structure, doesn't share the transformer's context-length constraints in theory, though having no theoretical limit doesn't guarantee good real-world performance on long inputs. State space models (SSMs), introduced in 2021, are another active line: S4 focused on making SSMs more computationally efficient, H3 added a mechanism for recalling and comparing tokens across a sequence (serving a similar purpose to attention, more efficiently), and Mamba (2023) scaled SSMs up to 3 billion parameters, with its authors reporting it outperforms same-sized transformers and matches transformers roughly twice its size on language modeling, with compute that scales linearly rather than quadratically with sequence length. Jamba goes further by interleaving transformer and Mamba layers in a single mixture-of-experts model (52 billion total parameters, 12 billion active), built to fit on one 80GB GPU while handling context lengths up to 256K tokens. None of this displaces the transformer today, but it's a reasonable bet that the architecture question isn't fully settled.

What "model size" really means: parameters, sparsity, and mixture-of-experts

A model's size is usually just its parameter count, the number baked into names like "Llama-13B." More parameters generally mean more capacity to learn, and within the same model family, the larger version usually performs better (Llama-13B over Llama-7B, for instance). That's not the whole story though: newer generations of models often outperform larger, older ones, since the field keeps getting better at training, not just scaling. Parameter count also gives a rough floor for compute needs: a 7-billion-parameter model stored at 2 bytes per parameter needs at least 14GB of GPU memory just to hold the weights for inference, before accounting for anything else the model needs while running.

Raw parameter counts can also be misleading for sparse models, where a large share of parameters are effectively zero and contribute nothing. A 7B-parameter model that's 90% sparse has only about 700 million parameters actually doing anything, and can be cheaper to run than a smaller fully "dense" model with every parameter active. Mixture-of-experts (MoE) models take this further by design: the parameters are split into expert groups, and only a subset of experts handles each token. Mixtral 8x7B is a concrete example: eight experts of 7 billion parameters each would total 56 billion if none were shared, but because some parameters are shared across experts, the real total is 46.7 billion. Only two experts activate per token, so just 12.9 billion parameters are actually doing work for any given token, meaning the model runs at roughly the cost and speed of a 12.9-billion-parameter model despite carrying 46.7 billion parameters in total.

None of this matters if the training data can't keep up with the model's size. An extreme illustration from the source: a 13-billion-parameter model trained on nothing but the single sentence "I like pineapples" would perform far worse than a much smaller model trained on a genuinely large dataset. Size alone, divorced from data, buys you nothing, which sets up the next section directly.

Measuring data and compute: tokens, FLOPs, and cost

Dataset size is measured in tokens, not in "number of examples," because examples vary wildly in length (a single sentence versus an entire book), which makes raw example counts a poor stand-in for how much a model could actually learn. The number of training tokens (tokens the model is actually trained on) can exceed a dataset's raw token count if the model passes over the data more than once; each full pass is called an epoch, though as of the source's writing, large models are typically trained on only a single epoch of data. Meta's own Llama releases show the scale climbing generation over generation: roughly 1.4 trillion training tokens for Llama 1, 2 trillion for Llama 2, and 15 trillion for Llama 3. For comparison, the open RedPajama-v2 dataset totals around 30 trillion tokens, though its raw scale doesn't mean all of it is high quality; the source notes indiscriminate content pulls that average down.

Compute is measured in FLOPs (floating point operations), a standardized way to compare compute needs across very different hardware. It's easy to mix up with FLOP/s (floating point operations per second), which measures a machine's speed rather than a task's total cost; some companies use "FLOP/s-day" specifically to avoid that confusion. As a worked example from the source: training GPT-3-175B took an estimated 3.14 × 10²³ FLOPs. Using 256 H100 GPUs at their advertised peak, that would take roughly 236 days (about 7.8 months) if you could run every GPU at 100% utilization with zero mistakes, which is never realistic. Utilization measures how much of a machine's peak advertised performance you actually get in practice; hitting around 50% is considered acceptable, and above 70% is considered strong. At 70% utilization and a rate of about $2 per H100 per hour (a rate the source flags as likely to keep falling as compute gets cheaper), that same training run was estimated to cost a bit over $4 million. Put together, the source frames model scale as three linked numbers: parameter count (learning capacity), training token count (how much the model actually learned from), and FLOPs (what that training cost).

The scaling law: why bigger models need more data too

Three things fall out of everything above: model performance depends on both model size and dataset size, bigger versions of either need more compute, and compute costs real money. So in practice, teams rarely start by picking an arbitrary model size and seeing what it costs. They start with a compute budget and ask what mix of model size and data size gets the best performance for that budget. A model that does this optimally is called compute-optimal.

The rule for finding that optimal mix is the Chinchilla scaling law, from a 2022 DeepMind paper, "Training Compute-Optimal Large Language Models" (Hoffmann et al.). The researchers trained 400 language models, ranging from 70 million to over 16 billion parameters, on between 5 and 500 billion tokens, specifically to study how model size, dataset size, and compute interact. Their headline finding: for compute-optimal training, the number of training tokens should be roughly 20 times the parameter count, and the two should scale together, doubling the model size means you should also roughly double the training tokens. A 3-billion-parameter model, by this rule, wants on the order of 60 billion training tokens.

This directly explains why several well-known large models from around that period (GPT-3, Gopher, LaMDA, and others, per the source's own comparison) look, in hindsight, undertrained for their size relative to this ratio: they carried huge parameter counts but comparatively modest token counts. The paper's own Chinchilla model made the opposite trade deliberately: a relatively modest 70 billion parameters, but trained on 1.4 trillion tokens, using the same compute budget as one of the larger, more token-starved models it was compared against, and reportedly outperforming those larger models on a range of evaluations as a result. It's worth naming the boundary on this rule directly: it was developed for dense models trained mostly on human-generated text, and the source notes that extending it cleanly to sparse (MoE) models or to training data that's expensive to acquire is still active research, not a settled extension. There's also a real, deliberate exception worth knowing: Llama's developers reportedly trained some models well past this compute-optimal point on purpose, favoring smaller, more usable, cheaper-to-run models over the largest model their compute budget could technically support.

Worth flagging: quantity of data is only one of three things that matter (the source names quantity, quality, and diversity together), and this part doesn't get into how quality and diversity are evaluated or improved, that's a separate topic for later. Also worth naming: the cost of reaching a given performance level has been falling (one cited example: the compute cost to hit 93% accuracy on ImageNet reportedly halved between 2019 and 2021), but the cost of pushing performance further from an already-good baseline stays high; one language-modeling example in the source states that cutting cross-entropy loss from about 3.4 to 2.8 needed roughly 10 times more training data. Small-looking loss or accuracy differences like that can still translate into a noticeably better or worse application in practice.

Emergent abilities and scaling extrapolation

It helps to be precise about a distinction that comes up here: a parameter is learned by the model during training, while a hyperparameter (number of layers, batch size, learning rate, and similar settings) is chosen by a person to configure the model or control how training happens. With small models, it's common to just train several times with different hyperparameters and keep the best result. That's rarely realistic for large models, since training one run at that scale is already expensive enough that you usually get one real shot.

To cope, researchers use scaling extrapolation (also called hyperparameter transfer): study how hyperparameters behave on smaller, cheaper models, then extrapolate what should work at the target size. This can work: one 2022 study from Microsoft and OpenAI showed hyperparameters found on a 40-million-parameter model transferring successfully to a 6.7-billion-parameter model. But it's not fully reliable, partly because of emergent abilities, capabilities that only become visible once a model crosses some scale threshold and simply aren't observable by studying smaller models at all (Wei et al., 2022). If an ability only shows up at scale, extrapolating from small models can miss it entirely.

It's also not automatically true that bigger is always better on every task. A 2023 effort called the Inverse Scaling Prize, run mostly by researchers at New York University, specifically looked for tasks where larger language models perform worse, and offered real prize money for convincing examples. Out of 99 submissions, 11 won a smaller prize; the organizers found that larger models are sometimes, not always, weaker on tasks that lean heavily on memorization or on tasks with strong built-in priors, but no one won the larger prizes, because none of the winning examples showed the failure holding up outside a small test set. Separately, a 2022 Anthropic study (Perez et al.) found a genuinely counterintuitive result in a related but different area: more alignment training (training aimed at making a model behave more in line with human preferences, covered in a later part of this chapter) was linked to models more strongly expressing specific political and religious views and a self-reported preference not to be shut down, the opposite of what "more alignment" might suggest at first glance.

Two real scaling bottlenecks: running out of data, running out of power

Every order-of-magnitude jump in model size so far has come with a real jump in performance (GPT-2 had about ten times the parameters of GPT-1, and GPT-3 had about a hundred times the parameters of GPT-2), but nobody knows for certain how many more such jumps are actually available. Two concrete bottlenecks are already visible.

The first is data itself. Training datasets have been growing faster than new usable text is being produced online, which is a real, near-term concern about running out of easily available public data (a 2022 projection from Villalobos et al. is cited for this trend). A practical way to think about it: if you've ever posted something publicly online, it's reasonable to assume it's already in, or will eventually end up in, some model's training data, whether or not you consented to that, similar to how anything public tends to get indexed by search engines. Complicating this further, the open web is filling up with AI-generated content itself, which means future models will increasingly train on text earlier models produced. There's a genuine, still-debated concern (Shumailov et al., 2023) that repeatedly training new models on AI-generated data could gradually degrade quality over generations, though the source is careful to flag this as a nuanced, actively researched question rather than a settled fact. As one real, dated data point: in December 2023, X's Grok model was observed declining a request by citing language resembling OpenAI's usage policy, which led to public speculation that it had trained on ChatGPT outputs; a Grok developer's public response was that this was more likely a byproduct of how much ChatGPT-generated text is now just part of ordinary web content, not evidence of deliberate copying. Access to data is also tightening on its own: companies including Reddit and Stack Overflow have changed their terms of service specifically to restrict scraping, and one 2024 analysis (Longpre et al.) found a large and rapidly growing share of the sources originally used in the C4 dataset had become restricted between 2023 and 2024.

The second bottleneck is electricity. Data centers already consume a meaningful share of global electricity today (the source cites roughly 1 to 2%), with one 2024 projection suggesting that could rise sharply, to somewhere between 4% and 20%, by 2030. If that projection holds, power availability, not chip supply, could end up being the harder ceiling on how much training compute can keep growing, and it's a real candidate for pushing electricity costs up broadly as demand climbs.

Why it matters

Once these two levers click, a lot of otherwise-confusing model comparisons stop being mysterious. A bigger parameter count on its own tells you very little; what matters is whether that model was actually trained on enough data to make good use of that capacity, which is exactly why the Chinchilla scaling law exists and why some smaller, more heavily trained models can beat larger, undertrained ones. Knowing where training data typically comes from also explains, in advance, where a general-purpose model is likely to struggle: a language or domain barely represented in Common Crawl-style data isn't a random weak spot, it's a predictable one, and it's exactly the kind of gap that later adaptation techniques (retrieval, finetuning) exist to patch. The next part of this unit picks up right where this one stops: how a pre-trained model gets shaped into something that actually follows instructions and holds a conversation, and how sampling, the process of turning those output probabilities into an actual next token, explains a lot of what looks like unpredictable AI behavior.

Remember this

  • Training data isn't neutral. Internet-scraped datasets like Common Crawl skew heavily English and skew toward whatever domains happen to be well represented online, and that skew becomes the model's blind spots.
  • The transformer won out over seq2seq because attention lets a model look at any earlier token directly, instead of compressing everything into one fixed summary the way RNN-based seq2seq had to.
  • Prefill (parallel, over the input) and decode (sequential, one token at a time) are genuinely different phases with different performance characteristics, worth reasoning about separately.
  • Bigger models only pay off if training data scales with them, roughly 20 tokens per parameter for compute-optimal training, per the Chinchilla scaling law. Size without matching data is wasted capacity.
  • Data and electricity are real, near-term ceilings on how much bigger foundation models can keep getting, not distant hypotheticals.

Try it yourself

  • Measure the multilingual token tax. Take the same short paragraph (100–150 words) and translate it into a language you can check (ideally something less common online, like Vietnamese, Swahili, or Burmese). Run both versions through any public tokenizer you can access. Done when you can state the token-count ratio between the two and compare it to the roughly 10x gap described in this part for a language like Burmese.
  • Build a toy attention score by hand. Pick a short sentence with a pronoun (6–10 words). For each earlier word, assign a made-up relevance score from 0–1 for "how much does this word help resolve the pronoun," then normalize the scores so they sum to 1 (a simplified stand-in for softmax). Done when you have a small table of words and normalized scores that roughly matches your own intuition for what the pronoun refers to.
  • Run your own FLOPs-and-cost estimate. Pick a hypothetical model size (parameters) and a token count, and using the source's method (rough FLOPs per parameter-token pair, an assumed GPU FLOP/s rate, an assumed utilization rate, and a $/hour rate), estimate training time and cost the way the chapter estimates GPT-3-175B's. Done when you have a number in days and a number in dollars, plus a one-line note on which input you're least confident in.
  • Check a real model's Chinchilla ratio. Look up the parameter count and reported training token count for two or three real open models you're curious about, then divide tokens by parameters for each. Done when you can say, for each one, whether it looks close to the roughly-20x compute-optimal ratio, well above it, or well below it, and take a guess at why.
  • Sketch your own MoE arithmetic. Invent a toy mixture-of-experts setup (pick a number of experts, a size per expert, an assumed amount of parameter sharing, and how many experts activate per token), then calculate total parameters and active parameters per token the way this part works out Mixtral's numbers. Done when you can state both numbers and explain in one sentence why the active number, not the total, is what mostly drives running cost.
  • Probe a domain gap on purpose. Pick a topic you suspect is under-represented online (a regional craft, a niche hobby, a less-documented historical event) and a common one for comparison. Ask the same style of question about both to any chat model you have access to. Done when you've written two or three sentences comparing specificity and confidence between the two answers.

Go deeper (optional)

If the scaling-law idea (bigger models need proportionally more data, not just more parameters) was the part that clicked, the natural next question is what happens to a model after all that pre-training: how does a model that's just good at predicting the next token get turned into something that follows instructions, holds a conversation, and refuses some requests? That's post-training, and it's covered along with sampling (how a model actually picks an output from its probabilities) in a separate part, since it's genuinely a different set of ideas from what's covered here.
