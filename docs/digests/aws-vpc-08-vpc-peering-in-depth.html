VPC Peering in Depth: Limits, CIDR Overlap, Cross-Account and Cross-Region

How two VPCs get a private, direct link, what has to be true before the link can exist, and the list of things peering will not do for you (which is where most of the surprises live).

In one line

A peering connection links exactly two VPCs so they can route to each other by private IP, across accounts and Regions if needed, but only if their address ranges don't overlap, only for the two VPCs themselves (no passing traffic along to a third), and only after both sides add routes.

The big idea

In the Transit Gateway topic we saw a hub that many VPCs plug into. Peering is the opposite shape: a direct line between a pair. The docs describe it as using the existing infrastructure of a VPC; it is neither a gateway nor a VPN and doesn't rely on separate physical hardware, with no single point of failure or bandwidth bottleneck. That simplicity is the appeal, and also the catch: because it's pair-by-pair, you need a connection for every pair that must talk, and the connection itself doesn't do anything until both owners add routes. The topic is mostly about learning the rules (who requests, who accepts, what can't overlap, what isn't carried across) so a "pending" connection or a missing route doesn't stump you.

Key terms

  • VPC peering connection: a networking connection between two VPCs that lets you route traffic between them using private IPv4 or IPv6 addresses. Its ID starts with pcx-.
  • Requester VPC / accepter VPC: the VPC that asks for the connection and the VPC that must accept it. The accepter can be in your account or another.
  • Inter-Region peering: peering between VPCs in different Regions.
  • CIDR overlap: two address ranges sharing any addresses. e.g. 10.0.0.0/16 and 10.0.5.0/24 overlap because the second sits inside the first.
  • Transitive routing: A reaching C by going through B. Peering does not support this.
  • Full mesh: every VPC peered directly with every other VPC.
  • Stale security group rule: a rule that references a security group that no longer exists, or in a peer VPC after the peering was deleted.
  • MTU: maximum transmission unit, the largest packet size on a link.

How it works

Grounding: what a peering connection actually gives you

Imagine VPC A (an accounting system) and VPC B (a data platform) and you want an instance in A to reach a database in B at its private address. Without peering, you'd go out through a gateway and over the internet or a VPN. With peering, instances in either VPC "can communicate with each other as if they are within the same network", with traffic staying on private addresses. The docs add that for inter-Region peering the traffic stays on the global AWS backbone, never traverses the public internet, and is encrypted before leaving AWS facilities.

Pricing facts from the peering page: no charge to create a connection; data transfer that stays within an Availability Zone is free, even across accounts; charges apply to transfer that crosses Availability Zones or Regions. I'm not quoting rates; check the EC2 pricing page.

1. The handshake and the lifecycle

The docs' process: the requester VPC's owner sends a request; the accepter VPC's owner accepts it (this is how the connection becomes active, even if both VPCs are yours); then each owner adds routes; then you adjust security groups if needed; then optionally enable DNS resolution.

Statuses to recognise:

  • initiating-request, then pending-acceptance (the requester can delete it; the accepter can accept or reject). If nobody acts, it expires after 7 days. The quotas page says this expiry is 1 week (168 hours) and not adjustable.
  • provisioning, then active: traffic can flow, provided security groups and route tables allow it. Either owner can delete an active connection but can't reject it.
  • failed, expired, rejected, deleted: terminal states that remain visible for hours or days (the docs give 2 hours or 2 days depending on the state and who you are).

A useful detail from the docs: if an event in a Region prevents traffic flow, the connection's status stays Active. So "active" is a statement about the connection object, not a health check.

CLI shapes from the reference pages:

aws ec2 create-vpc-peering-connection --vpc-id vpc-1a2b3c4d --peer-vpc-id vpc-11122233
add --peer-owner-id <account> for another account and --peer-region <region> for another Region

aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id pcx-1a2b3c4d

For an inter-Region request, the docs say you must accept it in the Region of the accepter VPC, so run the accept command against that Region.

2. CIDR overlap: the hard rule

You cannot peer VPCs with matching or overlapping IPv4 or IPv6 CIDR blocks. A detail that catches people: if a VPC has several IPv4 CIDR blocks, none of them may overlap with the other VPC's blocks, even if you only intend to use the non-overlapping ones, and even if you only want IPv6. If you try anyway, the connection status becomes failed.

Why it makes sense: a route table sends traffic by destination range. If both VPCs claim 10.0.0.0/16, "send 10.0.1.5 to the peer" collides with "10.0.1.5 is local". Longest-prefix matching can't rescue you when both sides hold the same range.

Practical consequence: plan address space before building. This is exactly what IPAM (mentioned in the IPv6 topic) helps with. If a CIDR is added later to a VPC that is already peered, the docs have extra rules: with an active connection you can add a block as long as it doesn't overlap the peer; with a pending connection the requester can't add any block at all, and an accepter's overlapping secondary block makes the request fail.

3. Not transitive, and no borrowing of gateways

A peering connection is a one-to-one relationship. If A peers with B and A peers with C, B cannot reach C through A. To connect B and C you need a separate connection between them. A star of peerings gives each spoke access to the hub only.

The docs also list "edge to edge" limits. If VPC A has an internet gateway, a NAT device, a VPN connection, a Direct Connect connection or a gateway endpoint to S3, resources in VPC B cannot use those through the peering. So you can't build a shared egress or shared on-premises link by peering to the VPC that owns it. (Transit Gateway, from the earlier topic, is the usual answer to this need; the peering page itself notes that a transit gateway attachment can sometimes replace peering.)

Other limits from the same page: only one peering connection between any two VPCs at a time; you can't connect to or query the Amazon DNS server in a peer VPC; unicast reverse path forwarding is not supported; tags you set on a connection apply only in the account or Region where you created them; and only VPC owners can work with peering connections, not participants of a shared VPC.

The mesh math. With full mesh, N VPCs need N times (N minus 1) divided by 2 connections. That's my arithmetic, consistent with the docs' seven-VPC example, which lists 21 connections. At 7 VPCs it's tolerable; at 30 it's 435 connections, each with two route entries to maintain. That growth is the usual reason people move to a transit gateway. Quotas: per the docs, 50 active peering connections per VPC by default (adjustable up to 125), and 25 outstanding requests by default.

4. Cross-account and cross-Region details

  • Cross-account. Same steps, but the accepter's owner is a different person, so the request genuinely waits for them. To reference a security group of a peer VPC in the same Region but a different account, write account-id/sg-id (the docs' example is 123456789012/sg-1a2b3c4d). The peer's groups don't appear in the console picker.
  • Cross-Region. You can't reference a peer VPC's security group across Regions; use the peer VPC's CIDR block in the rule instead. The MTU for jumbo frames is 9001 bytes between peered VPCs in the same Region and 8500 bytes for inter-Region peering. DNS resolution support must be enabled for private DNS hostnames of the peer to resolve to private IPs, even in RFC 1918 ranges.
  • Security groups. The connection must be active before you can reference a peer's security group. If the connection or the referenced group is deleted, the rule becomes stale and isn't removed automatically; the docs point to the console's "Manage stale rules" and the CLI describe-stale-security-groups. If you recreate a peering between the same VPCs, the rule is no longer marked stale.
  • IPv6. Works if both VPCs have IPv6 CIDRs, instances are IPv6-enabled, and each side routes the peer's IPv6 range to the connection. The docs' three-VPC example shows a VPC without IPv6 simply having no IPv6 communication with the others.

5. Routes and DNS: the two things people forget

Routes. Each owner adds, to the route tables of the subnets that need it, an entry whose destination is the peer's CIDR and whose target is the pcx- ID. With several CIDRs or IPv6, you add an entry per range. Narrow the destination if you only want some subnets reachable; this works through the same longest-prefix logic as the other routes you've seen.

DNS. By default, if an instance in one VPC uses the public DNS hostname of an instance in the peer, it resolves to the public IP. Enabling DNS resolution on the connection makes it resolve to the private IP. Requirements: both VPCs have DNS hostnames and DNS resolution enabled (the two attributes from Concept 5), the connection is active (you can't enable it at creation), the requester's owner changes the requester options and the accepter's owner changes the accepter options (same-account owners can do both at once). CLI: modify-vpc-peering-connection-options.

Also from the docs: if a VPC's IPv4 range is outside the RFC 1918 private ranges, private DNS hostnames of that VPC can't resolve to private IPs unless you enable DNS resolution on the connection.

Peering vs. Transit Gateway at a glance

  • Shape: peering = pair by pair. Transit Gateway = hub with attachments (see Concept 2).
  • Transitive? peering = no. A transit gateway routes between its attachments according to its route tables.
  • Sharing a gateway: peering = no sharing of IGW, NAT, VPN, Direct Connect or gateway endpoints. A transit gateway is the usual alternative when you want that.
  • Charges: peering = no charge to create, data transfer charged across AZs and Regions. For the transit gateway side, see its own pricing page; I haven't compared figures here.

Why it matters

Peering is one of the oldest and simplest ways to join networks, and many real environments still use it for a handful of VPCs. Knowing the rules saves hours: a "pending-acceptance" that nobody noticed, a failed connection caused by a forgotten secondary CIDR, a missing return route on the accepter side, or a B-to-C path that was assumed to exist. It also sets up the next concepts, since Site-to-Site VPN and Direct Connect are exactly the kind of connection you cannot share through a peer.

Remember this

  • Request, accept, then add routes on both sides. The connection alone moves no traffic.
  • Overlapping CIDRs (IPv4 or IPv6, any block) mean no peering.
  • Peering is one-to-one and not transitive; a peer's gateways, NAT, VPN and endpoints can't be borrowed.
  • Security group references work same-Region only; across Regions use CIDRs.
  • Defaults from the docs: 50 active peerings per VPC (adjustable to 125), unaccepted requests expire after 7 days.

Try it yourself

  1. Peer two scratch VPCs. Create two VPCs with non-overlapping CIDRs (for example 10.0.0.0/16 and 10.1.0.0/16), then run create-vpc-peering-connection and accept-vpc-peering-connection. Done when: describe-vpc-peering-connections shows active.
  2. Route it. Add a route in each VPC's route table to the other's CIDR via the pcx- ID, put a small instance in each, allow ICMP in the security groups, and ping private IP to private IP. Done when: pings succeed in both directions. (Needs a live account and costs a little; delete the instances after.)
  3. Provoke a failure. Try to peer two VPCs whose ranges overlap. Done when: you've seen the failed status and can state in one sentence why.
  4. Prove non-transitivity. Peer VPC A with B and A with C, add routes only for those pairs, and try B to C. Done when: it fails, then succeeds after you add a B-to-C peering with its routes.
  5. Security group reference. Replace a CIDR-based inbound rule with a reference to the peer's security group ID. Done when: traffic still flows. Then delete the peering and use describe-stale-security-groups to find the stale rule.
  6. Mesh calculator. Write a tiny script that, for N VPCs, prints the number of connections and the route-table entries needed (one per peer per route table). Done when: N=7 gives 21 connections, matching the docs' example.
