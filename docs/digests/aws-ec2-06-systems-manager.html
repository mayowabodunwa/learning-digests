Systems Manager (SSM): Session Manager, Run Command, Patch Manager and Parameter Store

What do you do when you need a shell on a server but you don't want to open port 22, manage SSH keys, or run a bastion host? Or when you need to patch two hundred instances, or hand configuration values to an app without baking them into code? AWS Systems Manager is the toolbox for exactly that, and the four tools here are the ones you'll meet first.

In one line

Systems Manager lets you operate your instances (and other machines) through AWS APIs instead of through the network: open shells, run commands, patch fleets and store configuration, all controlled with IAM and powered by an agent on the machine.

The big idea

Traditional server admin means a network path to the server: an open SSH port, keys to rotate, a jump host to guard. Systems Manager flips it. A small program on the instance, the SSM Agent, reaches out to the Systems Manager service. When you want something done, you ask the service (authenticated by IAM), and the service relays the request to the agent. The docs list the payoff as secure access "without opening inbound ports", no bastion hosts, and no SSH keys to manage.

A naming note from the docs: Systems Manager used to be "Amazon Simple Systems Manager (SSM)", and "SSM" survives all over: SSM Agent, SSM parameters, aws ssm commands, ssm.region.amazonaws.com endpoints.

I quote no prices. Where the docs mention cost, I say so in words: for example, Run Command has no additional cost on EC2 nodes, and Parameter Store's standard tier has no additional charge while the advanced tier is charged.

Key terms

  • Managed node: a machine (EC2 instance, or a server/VM elsewhere) with SSM Agent installed that can communicate with the Systems Manager service.
  • SSM Agent: the Amazon software on the machine that receives requests from Systems Manager and runs them.
  • Session Manager: tool for interactive shell access (or port forwarding) to managed nodes.
  • Run Command: tool to run commands remotely on one or many managed nodes.
  • SSM document: a named definition of what to run, such as AWS-RunShellScript.
  • Patch Manager: tool that scans nodes for missing patches and optionally installs them.
  • Patch baseline: your rules for which patches count as approved, which defines "compliant".
  • Parameter Store: a central store for named configuration values called parameters.
  • SecureString: a parameter type whose value is encrypted with AWS KMS.
  • Instance profile: the container that passes an IAM role to an EC2 instance at launch.
  • Bastion host: a hardened server people SSH into to reach private servers.
  • IAM policy: a document of allowed and denied actions that controls who can do what.

How it works

0. Grounding: what makes an instance "managed"?

Two ingredients, per the docs: SSM Agent is installed and running, and the agent can communicate with the Systems Manager service. The agent sends status back through the Message Gateway Service (ssmmessages endpoints; in Regions launched before 2024, possibly ec2messages too). So the instance needs a network route out (internet, NAT, or VPC endpoints through PrivateLink: the docs mention VPC endpoints for instances without public IPs), plus permission.

Permission comes in one of two ways, from the setup page. Recommended: turn on the Default Host Management Configuration in an account and Region, which makes instances that use IMDSv2 and have SSM Agent 3.2.582.0 or later managed automatically, with no instance profile. It can take up to 30 minutes to take effect, and must be enabled per Region. Alternative: attach an instance profile whose role has the AWS managed policy AmazonSSMManagedInstanceCore. If you later change the instance profile, the agent may not process requests until credentials refresh (restarting the agent or the instance speeds that up). The deeper story of instance profiles and IMDS belongs to the next concept.

Debugging tip from the overview: Systems Manager offers a diagnosis and remediation runbook for nodes that aren't showing as managed, including networking misconfigurations. A read-only way to check: the CLI describe-instance-information lists managed nodes with a PingStatus of Online, ConnectionLost or Inactive (the docs say Inactive is deprecated). It does not return stopped or terminated nodes.

1. Session Manager: a shell without SSH

Session Manager gives you an interactive browser-based shell or a CLI session on a managed node. Docs-stated benefits: access controlled centrally by IAM policies (even temporary access, like an on-call rotation); no open inbound ports, bastion hosts or SSH keys; works on Windows, Linux and macOS; connects to EC2 and non-EC2 managed nodes; port forwarding and tunneling; and configurable shell profiles.

What happens when you start a session (the docs' walk-through): the service authenticates you, checks your IAM permissions and session configuration limits, then tells the agent to open a two-way channel. Traffic is encrypted with TLS 1.2, requests are signed with SigV4, and you can additionally encrypt with a KMS key.

Auditing: sessions integrate with CloudTrail (API calls), S3 and CloudWatch Logs (session log data, optionally KMS-encrypted), and EventBridge/SNS (notifications on start or end). Caveat from the docs: logging isn't available for sessions that use port forwarding or SSH, because the tool is only a tunnel for encrypted data. To use the CLI you need the Session Manager plugin installed locally. Also note: the docs say the legacy Session Manager page will be deprecated on December 31, 2026, with capabilities moving to the unified console.

2. Run Command: do this on many machines

Run Command remotely and securely runs commands on managed nodes: install or bootstrap apps, capture logs when an instance leaves an Auto Scaling group, join instances to a Windows domain, and one-off configuration changes at scale. No additional cost on EC2 nodes per the docs. Facts worth knowing:

  • The CLI's send-command needs --document-name. Target with --instance-ids (up to 50) or --targets (key/value criteria such as tags). --max-concurrency defaults to 50 nodes at a time and --max-errors defaults to 0.
  • The docs' CLI example runs the AWS-RunShellScript document with --parameters 'commands=["echo HelloWorld"]' against a target instance.
  • Command history is available for up to 30 days; copy logs to S3 or rely on CloudTrail for longer audit.
  • Do not put secrets in command text. The docs warn that API activity is logged to CloudTrail's S3 bucket, so anyone who can read it sees plaintext secrets. Use SecureString parameters instead.
  • The API is eventually consistent, so a call right after another may not see its effect yet. Commands can fail on nodes whose /var is mounted with noexec.

3. Patch Manager: define "compliant", then scan or install

Patch Manager patches operating systems and (with limits) applications across managed nodes. Core ideas:

  • A patch baseline is your rulebook: auto-approval rules (classification, severity, days after release), plus explicit approved and rejected lists. Each baseline targets one OS type. Predefined baselines exist, but the docs say they are examples and not recommended best practice, and suggest custom baselines.
  • Two operations: Scan (report missing patches only) or Scan and install.
  • Four ways to run them: a Quick Setup patch policy (recommended, org-wide), a Host Management option in Quick Setup (scan only), a maintenance window task, or an on-demand Patch now.
  • Compliance reports can be viewed in the console or exported to S3 as CSV; they are a point-in-time snapshot from the latest successful operation.

Boundaries the docs state: AWS doesn't test patches before making them available; Patch Manager doesn't upgrade major OS versions (for example Windows Server 2016 to 2019); and "compliant" does not mean "secure". Compliance only means the available, approved patches are installed. On Linux, severity comes from the publisher, not from CVSS.

4. Parameter Store: config outside your code

Parameter Store stores named values (parameters) so applications read config at runtime instead of hard-coding it. Types: String, StringList (comma-separated), and SecureString (encrypted with KMS). Features: hierarchies (like /dev/webserver/linux/approved-ami), versioning (the docs say the 100 most recent versions of each parameter are kept), IAM control by path, events, sharing across accounts (advanced tier), and use from Lambda, ECS, CloudFormation, CodeBuild and EC2 launch (you can reference a parameter instead of hard-coding an AMI ID, which ties back to launch templates).

Tiers (docs): standard: up to 10,000 parameters per account and Region, values up to 4 KB, no parameter policies, no charge. Advanced: up to 100,000, values up to 8 KB, policies and cross-account sharing, charges apply. Standard can be upgraded to advanced but not downgraded back.

Important boundaries the docs spell out: a parameter update "takes effect on the next read, with no validation, gradual rollout, or automatic revert". For config where a bad value could cause an outage, AWS AppConfig adds validation, gradual rollout and rollback. And for real secrets like database credentials or API keys, the docs recommend AWS Secrets Manager, which offers automatic rotation (the docs table lists credential rotation as "None" for Parameter Store). ECS-injected environment variables from Parameter Store are resolved at task start.

CLI facts I checked: put-parameter requires --name and --value, and you must give --type when creating; overwrite defaults to false; names are case sensitive and hierarchical names start with a slash; get-parameter --with-decryption returns the decrypted value of a SecureString.

Why it matters

Closing port 22 is one of the most visible security wins on EC2, and Session Manager is the docs' answer. Patching and config distribution are the other chronic pain points: Patch Manager and Parameter Store give you auditable, IAM-controlled versions of what teams often do with ad hoc scripts. It also connects: Auto Scaling lifecycle hooks can trigger Run Command, launch templates can reference Parameter Store AMI IDs, and Session Manager logs can flow to CloudWatch Logs and S3.

Remember this

  • A managed node = SSM Agent installed + able to reach the Systems Manager service + permission (Default Host Management Configuration or an instance profile with AmazonSSMManagedInstanceCore).
  • Session Manager replaces SSH/bastions with IAM-controlled, loggable sessions; logging does not apply to port-forwarded or SSH-tunnelled sessions.
  • Run Command runs documents on many nodes with concurrency and error limits; never put plaintext secrets in command text.
  • Patch Manager: baseline defines compliance, Scan reports, Scan and install changes; compliant is not the same as secure.
  • Parameter Store holds config (String, StringList, SecureString) with no validation or rollback; use Secrets Manager for credentials that need rotation.

Try it yourself

Projects 1 and 2 need no AWS account. Projects 3 to 5 need an account and a small EC2 instance that you delete afterwards; Parameter Store standard parameters carry no additional charge per the docs, but instances do cost money. I verified the options of the send-command, put-parameter, get-parameter and describe-instance-information commands against the CLI reference pages, but I did not run them against a live account. I did not verify the start-session command.

  1. Model a baseline (no AWS). Write a function that takes a list of patches (id, classification, severity, days since release) and a baseline (approved classifications and severities, wait days, reject list) and returns the approved set. Done when: a Security/Critical patch passes, a Bugfix is excluded, and a rejected ID is dropped even if it matches.
  2. Run Command rate control (no AWS). Simulate 120 nodes, max-concurrency 50 and max-errors 0, with a few random failures. Done when: you can explain why a max-errors of 0 stops the rollout at the first failure, and how raising it changes the outcome.
  3. Make an instance managed. Launch a small instance with the AmazonSSMManagedInstanceCore role attached (or enable Default Host Management Configuration), then run aws ssm describe-instance-information --query 'InstanceInformationList[].{Id:InstanceId,Ping:PingStatus,Agent:AgentVersion}' --output table. Done when: your instance shows Online. If not, use the diagnosis runbook idea from the docs and check the outbound path and permissions.
  4. Run one command. Use the console's Run Command with AWS-RunShellScript to run hostname, or the CLI form from the docs with your instance ID. Done when: you can read the output and find the command in the history.
  5. Parameter round trip. Create /lab/demo/greeting as a String and /lab/demo/token as a SecureString with put-parameter, then read both with get-parameter, with and without --with-decryption. Done when: you can show the encrypted vs. decrypted difference, and explain why the docs say credentials belong in Secrets Manager instead. Delete the parameters afterwards.
