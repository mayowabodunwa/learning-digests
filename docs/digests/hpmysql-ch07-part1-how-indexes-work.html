How MySQL Indexes Actually Work: B-Trees, Types, and Why They Help

Everyone tells you "add an index" like it's a magic incantation. This part is about what an index actually is under the hood, the shape of the data structure MySQL builds for you, and why that shape is exactly what makes lookups, ranges, and sorting all faster at once.

In one line

An index is a separate, sorted copy of some of your columns' data, organized as a tree, and that sorted-tree shape is the entire reason it can turn "scan everything" into "jump straight to it."

The big idea

Small tables are forgiving. You can run a query against a few thousand rows with no index at all and barely notice. But performance can fall off a cliff as a table grows, and a leading cause of that cliff, in practice, is indexing that was never set up (or set up wrong). The fix isn't "add more indexes everywhere." It's understanding the one data structure behind most indexes you'll ever create, the B-tree, so you can predict which queries it'll help and which ones it quietly can't.

Key terms

  • Index (key) — a data structure a storage engine builds and maintains alongside a table so it can find matching rows without checking every row. MySQL uses "index" and "key" interchangeably (that's why the SQL keyword is KEY in a CREATE TABLE statement).
  • Storage engine — the layer inside MySQL actually responsible for storing and retrieving data on disk (InnoDB, for example). Indexes are implemented at this layer, which is why different engines can support different index types or implement the "same" index type differently underneath.
  • B-tree index — the index type you'll use by default for most things: a balanced, sorted tree structure. When someone says "index" without naming a type, this is almost always what they mean.
  • B+ tree — the specific variant of a B-tree that most storage engines, including InnoDB, actually build, where every leaf node additionally links to the next one so scanning a range doesn't require climbing back up the tree between values. MySQL's own syntax still just calls it BTREE.
  • Root node — the single top node of the tree, where every lookup starts.
  • Node page (internal page) — a page in the tree, between the root and the leaves, that holds pointers to child pages plus the boundary values that tell the storage engine which child to follow next.
  • Leaf page — a page at the bottom of the tree. Unlike node pages, leaf pages point to actual rows (or, for InnoDB specifically, contain the row data itself, more on that distinction in Part 2 when we get to clustered indexes).
  • Leftmost prefix — the rule that a multi-column index can only be used efficiently starting from its first (leftmost) column and moving right, without skipping any. An index on (a, b, c) is not the same thing as three separate indexes; you'll see exactly why below.
  • Adaptive hash index — an automatic, in-memory optimization InnoDB applies on top of a B-tree index when it notices certain values are being looked up very frequently. You cannot configure how it works, only turn it off entirely.
  • Full-text index (FULLTEXT) — a completely different kind of index built for finding keywords inside text, used with MATCH ... AGAINST rather than an ordinary WHERE comparison.
  • Index-only query — a query MySQL can answer by reading only the index, never touching the underlying table storage. We'll go one level deeper on this (as "covering indexes") in Part 2.
  • Three-star index — a scoring idea (from a well-known indexing reference the chapter points to) for judging how good an index is for a specific query: one star for grouping relevant rows together, a second for sorting them in the order the query needs, a third for containing every column the query touches.

How it works

Start with the book-index analogy, because it's genuinely the right mental model and not just a cute comparison. When you want to find where a topic is discussed in a printed book, you don't read every page. You flip to the index at the back, which is sorted alphabetically, find your topic, and jump straight to the page number it lists. A database index does the same job for a table: it's a separate, sorted structure that a storage engine can search quickly, and once it finds a match it can go straight to the matching row instead of checking every row in the table one by one. Run SELECT first_name FROM sakila.actor WHERE actor_id = 5; against a table that has an index on actor_id, and MySQL searches that index for the value 5, finds it, and uses it to jump to the right row rather than scanning the whole actor table.

One detail worth internalizing early, because it changes how you design every index from here on: an index can cover more than one column, and when it does, column order matters enormously. An index on two columns is not a shortcut for having two separate single-column indexes; it behaves very differently, in ways this section will make concrete.

One quick aside worth stating plainly if you write queries through an ORM (object-relational mapper) rather than raw SQL: that doesn't get you out of learning this. ORMs are generally good at producing SQL that's logically correct, but they're not generally good at producing SQL that's index-friendly, beyond the simplest primary-key lookups. Nothing about the rest of this digest assumes you're hand-writing every query, only that you understand what's actually happening once your ORM's query hits the database.

1. B-tree indexes: the shape that makes lookups fast

Indexes are implemented inside the storage engine, not the general MySQL server layer, which is a simplification worth flagging: it means indexing isn't perfectly standardized across engines. Different storage engines can support different index types, and even when two engines both claim to support "the same" type, they can implement it differently underneath. This digest, matching the source material, assumes InnoDB, which is the default and by far the most common engine in modern MySQL, so when a claim below says "B-tree indexes work like this," read it as "in InnoDB," not as a law true of every storage engine everywhere.

The most common index type by a wide margin is the B-tree index. In MySQL's own CREATE TABLE syntax and documentation it's called BTREE, but most engines that use this label, InnoDB included, actually build a slightly different structure called a B+ tree, where every leaf page is additionally linked to the next leaf page in sorted order. That link is what makes scanning a range of values fast: once the storage engine finds the start of a range, it can walk sideways across linked leaves instead of climbing back up to the root and back down again for every value. (One storage engine, NDB Cluster, actually uses a completely different structure called a T-tree internally while still labeling it BTREE in SQL. The exact internal data structure varies by engine; the label in your CREATE TABLE statement is a category, not a strict promise of implementation.)

The overall shape is a balanced tree: every leaf page sits at the same distance from the root, no matter which value you're looking for. A lookup starts at the single root node at the top. Each slot in the root holds a pointer to a child page, along with the range of values that live under that pointer, so the storage engine can look at your search value, compare it against those ranges, and immediately know which child to follow. It repeats that same comparison at each node page it passes through, going one level deeper each time, until it either determines the value doesn't exist or lands on a leaf page. Leaf pages are different from node pages in one key way: instead of pointing to more pages inside the tree, they point to the actual row data (the specific mechanics of what a leaf page holds differ by engine and by whether the index is a table's primary index, which Part 2 covers under "clustered indexes"). A tree might only need one level of node pages between the root and the leaves for a small table, or many levels for a huge one; the exact depth just depends on how much data there is.

The reason this shape earns its keep: because values are stored in sorted order at every level, a B-tree is just as useful for ranges as it is for exact matches. Descending through an index built on a text column visits values in alphabetical order, so "find everyone whose name starts with I through K" is a contiguous walk across a handful of neighboring leaf pages, not a scan of the whole table.

2. What column order does to a multi-column index

Picture a table for tracking people, with a single index built across three columns together: last_name, then first_name, then date_of_birth. The index sorts its entries by last_name first; only among rows that tie on last_name does it then sort by first_name; only among rows that tie on both does it finally sort by date_of_birth. That's the whole trick, and it's also exactly why the column order you choose when you create the index isn't a cosmetic detail.

That sort order is what "leftmost prefix" means in practice, and it decides which queries this specific index can help with:

  • Match the full value — you supply all three columns, e.g. find the person named Chen, Wei, born 1988-03-11. Fully sorted and fast.
  • Match a leftmost prefix — you supply just last_name, e.g. everyone named Chen. This only uses the first column, but it's still a fast, contiguous slice of the index.
  • Match a column prefix — you supply the start of last_name's value, e.g. everyone whose last name begins with "C". Still only the first column.
  • Match a range — e.g. everyone with a last name between "Allen" and "Chen". Also only the first column.
  • Match one column exactly, then a range on the next — e.g. last name exactly "Chen", first name starting with "W". This uses both last_name and first_name.

And here's where it breaks, which trips people up constantly: this same index is no help at all for finding everyone with a given first name, or everyone born on a specific date, if you don't also specify the last name, because those columns aren't leftmost. You also can't skip a column: asking for a specific last_name and dob but no first_name only gets to use the last_name part of the index, because the index has no way to jump straight to a particular dob without first fixing first_name. And once your query uses a range condition on one column (rather than an exact match), MySQL can't use any columns to its right in the index for narrowing the search either; matching an exact last_name, a first_name LIKE 'W%' range, and an exact dob only actually uses the first two columns of the index for narrowing rows, because the range on first_name breaks the chain.

Because the tree's nodes are sorted, a B-tree index that can help find rows in a given way generally helps sort rows in that same way, too, so this same index can also speed up an ORDER BY last_name, first_name, avoiding a separate sort step after the rows are fetched. One more limitation worth naming plainly: none of the matching patterns above work backward. This index can't help you find people whose last name ends in a particular letter, because that's not how a sorted-by-prefix structure works. A caveat worth keeping in view: some of these limitations come from how MySQL's optimizer and storage engines currently choose to use a B-tree, not from anything mathematically impossible about the B-tree structure itself, so treat "MySQL can't do X with this index today" as a statement about MySQL's current implementation, not a permanent law.

3. The adaptive hash index: InnoDB's automatic shortcut

InnoDB has one more trick layered on top of ordinary B-tree indexes, called the adaptive hash index. If InnoDB notices that certain index values are being looked up unusually often, it can build a hash index for those specific values in memory, sitting on top of the existing B-tree. A hash index (a different index type, not covered in depth in this part) trades away range and sorting support for extremely fast exact-match lookups, so layering one on hot values gives those particular lookups some of that speed without you doing anything. The important caveat: this is fully automatic. You don't get to choose which values it targets or tune how it behaves; the only lever you have is turning the whole feature off if you decide it's not helping your workload.

4. Full-text indexes: a different kind of search entirely

Not every index is a B-tree. FULLTEXT is a distinct index type built for finding keywords inside a block of text, and it works in a fundamentally different way from ordinary value comparison. Instead of comparing your search value directly against stored values the way a WHERE column = 'x' lookup does, a full-text index deals with concepts like stop words (common words like "the" that get ignored), stemming (matching "running" when you searched for "run"), handling plurals, and boolean combinations of search terms. That makes it closer in spirit to what a search engine does than to a typical WHERE filter, with a lot of nuance this digest isn't going to compress into a paragraph (worth its own dedicated study if full-text search is something you need). One useful thing to know now: having a FULLTEXT index on a column doesn't replace the value of also having a normal B-tree index on that same column, because they answer different questions. A FULLTEXT index is for MATCH ... AGAINST keyword search; it's not used for an ordinary WHERE comparison on that column.

5. Why indexes help: three benefits, one root cause

Everything about why B-tree indexes speed things up traces back to the same handful of structural properties: the data is stored in sorted order, related values end up physically close together as a result, and the leaf level holds a genuine copy of the indexed column values, not just a pointer. From those properties, three concrete benefits follow:

  • Indexes reduce how much data the server has to examine. Instead of checking every row for a match, the storage engine narrows down to a small, sorted slice of the index and only reads the rows that slice points to.
  • Indexes help the server avoid sorting and temporary tables. If the index's stored order already matches what an ORDER BY or GROUP BY needs, MySQL can walk the index in order instead of pulling every matching row into memory (or onto disk) just to sort it afterward.
  • Indexes turn random I/O into sequential I/O. Because a B-tree stores related values near each other, reading a run of matching rows tends to mean reading physically nearby data, which is generally far cheaper for storage hardware than jumping around unpredictably. (This benefit is most pronounced on conventional spinning disks; solid-state drives handle random access far better than spinning disks do, so the same principle still holds directionally on SSDs, just with a smaller penalty for getting it wrong.)

Those three benefits are also exactly what a well-known indexing framework, the three-star system, uses to score how good a candidate index is for a specific query: one star if the index places the query's relevant rows next to each other, a second star if those rows come out already sorted the way the query needs, and a third star if the index alone contains every column the query touches (so MySQL never even has to visit the underlying row). It's a genuinely useful mental checklist to hold onto: whenever you're deciding whether an index is "good," ask which of those three stars it actually earns for the query you care about. Part 2 of this digest picks up exactly here, with the concrete strategies (prefix indexes, multi-column ordering, and more) for actually earning those stars.

Why it matters

Indexing is squarely on the short list of things that separate a database that feels instant from one that grinds to a halt as it grows, and the failure mode is common precisely because it's invisible until it isn't: a table with a few thousand test rows on a laptop can hide a missing or badly-shaped index for a long time, right up until real traffic and real data volume expose it. Understanding the B-tree shape, and specifically the leftmost-prefix rule, is what lets you predict in advance which of your queries a given index will actually help, rather than discovering it the hard way once things slow down. It also explains why "just add an index on every column in the WHERE clause" is such persistent, wrong advice: without thinking about column order, you'll end up with indexes that only ever earn one star.

Remember this

  • An index is a separate, sorted structure the storage engine searches instead of scanning the whole table; MySQL's default and by far most common type is the B-tree (technically a B+ tree in InnoDB).
  • A multi-column index is sorted by its first column, then its second column within ties on the first, and so on; this is the leftmost-prefix rule, and it decides which queries the index actually helps.
  • Skip the leftmost column, or hit a range condition partway through, and MySQL stops being able to use the remaining columns in that index for narrowing rows.
  • InnoDB's adaptive hash index is a fully automatic optimization for hot values; you can turn it off, but you can't steer it.
  • A full-text index is a different tool for a different job (keyword search via MATCH ... AGAINST), and it doesn't replace a normal B-tree index on the same column for ordinary WHERE lookups.

Try it yourself

  1. Build a toy B-tree by hand. In any language, write a tiny in-memory tree with a fixed branching factor (say, 4 children per node) that stores sorted integers, supports insert, and supports search by walking from root to leaf. Keep it under 100 lines; don't worry about balancing on delete. Done when: you can insert 20+ values and trace, printing each step, exactly which node your search function visits on the way to finding (or not finding) a value.
  2. Recreate the leftmost-prefix example and watch EXPLAIN prove it. Stand up a MySQL instance (or use the Sakila sample database), create a table with a multi-column index like (last_name, first_name, dob), insert a few dozen rows, then run EXPLAIN against a query that uses only the first column, one that uses all three, and one that supplies only first_name. Done when: you can point at the key and key_len columns in each EXPLAIN output and explain why one of them shows no index used at all.
  3. Prove the range-breaks-the-chain rule. On the same table, run EXPLAIN for a query with an exact match on column one, a LIKE 'X%' range on column two, and an exact match on column three. Done when: you can read key_len in the output and confirm it corresponds to only the first two columns, not all three.
  4. Watch an index kill a sort. Run the same query twice: once with ORDER BY matching your index's column order, once with ORDER BY on a column not in the index. Done when: you've found "Using filesort" in the Extra column of EXPLAIN for one version and not the other, and can explain why.
  5. Toggle the adaptive hash index and see if you notice. On a test instance, run SHOW VARIABLES LIKE 'innodb_adaptive_hash_index', then run a batch of repeated, identical point lookups against the same row, then flip the setting off with SET GLOBAL innodb_adaptive_hash_index = OFF and repeat. Done when: you've recorded rough timings for both runs, even if the difference on your machine turns out to be small or within noise; the point is confirming it's a real, toggleable setting rather than magic.
  6. Rate one of your own queries on the three-star scale. Pick any query you've written before (or one against Sakila) and its current index, and score it: one star if matching rows sit together, a second if they come out sorted the way the query needs, a third if the index alone has every column the query touches. Done when: you've written down the score and one concrete change to the index that would earn it an additional star.
