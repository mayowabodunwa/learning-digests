Covering Indexes, Index Sorting, Redundant Indexes and Maintenance

Parts 1 and 2 were about what an index is and how to shape one. This last part is about getting paid back for that work: answering a query from the index alone, letting the index do your sorting, cleaning out indexes that cost more than they give, and keeping the whole thing healthy. It ends with the chapter's own three-principle summary.

In one line

An index is judged by the whole query (finding rows, ordering them, and supplying the columns), and every index you add also has a running cost, so you tidy and maintain them on purpose.

The big idea

The common beginner rule is "index the columns in your WHERE clause." That's only the first third of the story. A query also has to produce its rows in some order, and it has to hand back some columns. If the index can supply all three (the lookup, the order, and the columns), the server never touches the table's rows at all. That's the dream.

But indexes aren't free. Each one is extra data that every insert, update and delete has to keep in sync. So the other half of this part is housekeeping: spotting duplicate, redundant and unused indexes, and keeping statistics and physical layout in good shape so the optimizer (the part of MySQL that picks a query plan) keeps making good choices.

This part covers the rest of the chapter: "Covering Indexes," "Using Index Scans for Sorts," "Redundant and Duplicate Indexes," "Unused Indexes," "Index and Table Maintenance," and the chapter Summary. It also finishes one line from the previous part, "When Primary Key Order Is Worse," which I'll mention briefly below.

Key terms

  • Covering index: an index that contains every column a query needs, so the query can be answered without reading the table row. Example: the query SELECT region, city ... WHERE region = 5 is covered by an index on (region, city).
  • Filesort: MySQL's name for sorting rows itself because no index gave them in the right order. Despite the name it does not always use a file; the source says it goes to disk only when the data can't be sorted in memory.
  • EXPLAIN: a statement that shows the plan MySQL intends to use for a query, without returning the query's rows. The Extra column has notes like Using index or Using filesort.
  • Leftmost prefix: the first column, or first few columns in order, of a multicolumn index. An index on (a, b, c) can serve lookups on a or (a, b), but not on b alone.
  • Duplicate index: the same type of index on the same columns in the same order.
  • Redundant index: an index that a different, longer B-tree index already covers as a leftmost prefix. An index on (A) is redundant if (A, B) exists.
  • Unused index: an index the server never picks for any query.
  • Invisible index: a MySQL 8.0 feature. The index still exists and is still maintained, but the optimizer ignores it.
  • Index statistics: the summary numbers (like estimated distinct values) the optimizer uses to guess how many rows a query will touch.
  • Fragmentation: pages that are poorly filled and/or stored out of order on disk, so reads do more work than they should.

How it works

Hold on to one picture from Part 2: in InnoDB, a secondary index's leaf entries hold the indexed columns plus the primary key value. Almost every trick in this part follows from "what is physically sitting in the index leaves, and in what order?"

A note on how I checked things. The book's examples use the Sakila sample database, and I don't reproduce them. I built small made-up tables on a local MySQL 8.0 server and ran EXPLAIN myself, so every plan I quote below is mine, from that one version and those one small tables. Treat them as direction, not as promises about your server. The source itself says (in a footnote about sorting) that the optimizer may not do what you expect and you should always check with EXPLAIN.

0. A quick tail from last time: when key order hurts

Part 2 taught that inserting in primary key order is usually good for InnoDB. The closing note of that section says the opposite can bite under heavy concurrency: if many sessions insert at once, they all land at the top end of the key, which becomes a hot spot where they contend for locks, and the AUTO_INCREMENT counter has its own locking, which the source says you can tune with innodb_autoinc_lock_mode (or by redesigning the table or application). Simplification: I'm only relaying the source's one-paragraph warning. How much this matters depends on your server version and workload, and I did not test it.

1. Covering indexes

Normally an index helps you find rows, then MySQL jumps to the table to read the row's other columns. But the index leaves already hold the indexed values. If those are all the columns the query asks for, the jump is pointless. An index that holds everything a query needs is a covering index, and EXPLAIN shows Using index in the Extra column when MySQL answers from one.

The source lists why this tends to be a big win:

  • Less data to read. Index entries are usually much smaller than whole rows. That matters when the data is cached (less to copy around) and when it isn't (smaller indexes fit in memory better).
  • Less random I/O. Indexes are sorted by value, at least within a page, so a range of index entries is read more sequentially than fetching each matching row from a scattered location.
  • Saves a second lookup in InnoDB. Because InnoDB secondary indexes carry the primary key, a secondary index that covers the query avoids going back into the primary key tree.

Two boundaries worth naming. First, per the source, only B-tree indexes can act as covering indexes. Second, a trap on naming: Using index in Extra (covered query) is a completely different thing from type: index in the type column (the access method, a full scan of an index). The source has a footnote warning about exactly this mix-up.

InnoDB's "free" extra column

The source points out that in most storage engines an index can only cover a query that uses columns in the index. InnoDB goes a step further: since the primary key is stored in every secondary index leaf, the primary key column counts as an extra, invisible member of every secondary index. I checked this on a made-up shop_orders table with 20,000 rows and an index only on region (primary key id):

  • EXPLAIN SELECT region, id ... WHERE region = 5 showed key: idx_region and Extra: Using index. Covered, even though id isn't in the index definition.
  • EXPLAIN SELECT region, city ... WHERE region = 5 showed the same index but no Using index, because city isn't available there.
  • After ALTER TABLE shop_orders ADD KEY idx_region_city (region, city), the same query switched to the new index with Using index.

Simplification: "add the SELECT columns to the index" is the idea, not a rule. The redundancy section below shows the cost: a wider index is bigger, and it makes inserts slower.

2. Using an index to sort

MySQL can produce ordered results two ways: sort the rows itself (a filesort), or read an index, which is already sorted. You can spot the plan: Using filesort in Extra means it sorted; its absence on an ORDER BY query means the index order was used.

A catch the source stresses: reading rows through an index, when the index doesn't cover the query, means one row lookup per index entry. That's mostly random I/O, so it is usually slower than a sequential table scan, particularly when the workload is I/O-bound. Index ordering pays off best when the query is covered, or when a LIMIT means only a few rows are ever fetched (the source calls ORDER BY plus LIMIT one of the most important uses).

The rules the source gives for when the index order can be used:

  • The ORDER BY columns must match the index order and all go in the same direction (all ascending or all descending), and form a leftmost prefix of the index.
  • If the query joins several tables, it works only when every ORDER BY column belongs to the first table in the join order.
  • Exception: if the WHERE (or join) gives a constant for the leading column(s), those columns "fill the gap" and the ORDER BY can start later in the index.

Here is what I saw on a made-up ev table (30,000 rows) with one index (day, user_id, kind). Each row is a different WHERE ... ORDER BY shape:

WHERE day = const ORDER BY user_id, kind → no filesort. The constant fills the first column; the rest is a leftmost prefix of what remains.

WHERE day = const ORDER BY user_id DESC, kind ASC → Using filesort. Mixed directions.

WHERE day = const ORDER BY kind → Using filesort. user_id is skipped, so there's a gap.

WHERE day = const ORDER BY user_id, pad → Using filesort. pad isn't in the index.

WHERE day = const AND user_id IN (1,2) ORDER BY kind → Using filesort. The source says a multi-value equality behaves like a range for sorting.

WHERE day = const ORDER BY user_id DESC, kind DESC → Backward index scan, no filesort. All columns descending reads the index backwards.

ORDER BY day, user_id LIMIT 10 (no WHERE) → used the index, no filesort.

One result went the other way from the book's text, and it's worth being honest about. In the source's example, a range on the first column followed by an ORDER BY on later columns can't use the index order. In my test, WHERE day > const ORDER BY user_id, kind chose a full table scan plus a filesort, which is consistent with the rule, but I can't separate "can't use the index for sorting" from "the optimizer judged a scan cheaper on a table this small." Small tables bend the optimizer's choices, which is another reason the source tells you to verify with EXPLAIN on your own data.

A version note on mixed directions

The source suggests that if you need mixed sort directions, a trick is to store a reversed or negated value. That is the book's advice. Beyond the source, I tried MySQL 8.0's descending index syntax: after ALTER TABLE ev ADD KEY idx_mixed (day, user_id DESC, kind ASC), the mixed-direction query used it with no filesort, but only once I forced it with FORCE INDEX. Left alone, the optimizer kept the old index on my tiny table. I'm flagging this as my own observation on one version, not something the chapter claims.

3. Duplicate and redundant indexes

Every index must be maintained separately and the optimizer considers each of them when planning, so extra ones cost both disk space and time. The source distinguishes two kinds:

  • Duplicate: same index type, same columns, same order. The source says MySQL lets you create them (it only warns). Sometimes it happens accidentally: declare a column PRIMARY KEY, add UNIQUE(id), and add INDEX(id), and you've made three indexes, because primary key and unique constraints are implemented with indexes. I confirmed on 8.0 that SHOW INDEX lists three separate indexes (PRIMARY, id, id_2) for that table. The source adds that different types (say a regular key plus a full-text key on one column) aren't really duplicates.
  • Redundant: an index on (A) when (A, B) exists is redundant, because (A, B) already works as an index on A. An index on (B, A) or on (B) is not redundant, since B isn't the leftmost prefix. Per the source, this prefix redundancy applies to B-tree indexes only, and different index types are not redundant with B-trees.

When a "redundant" index earns its keep

The source's case: a table of one million users, about 20,000 per state_id, with an index on state_id. A count query on one state was fast with it. A second query selecting state_id, city, address was slow, so extending the index to (state_id, city, address) to cover it sped that one up but made the count query a bit slower (the wide index is bigger to scan). Keeping both indexes made both queries fast, at the price of slower writes: the source measured inserting a million rows taking noticeably longer with both indexes than with one. I'm deliberately not repeating its benchmark numbers; the lesson is the direction. A redundant index can be a deliberate trade of write speed for read speed, and extending an index is not always free for the queries that used the narrow version.

There's a second warning from the source that I found surprising and tested. Because InnoDB appends the primary key to every secondary index, an index on (a) is really (a, id). So WHERE a = 5 ORDER BY id gets its order for free. If you "extend" to (a, b) it becomes (a, b, id) and the order by id is lost. On a made-up ext table, my EXPLAIN showed no special Extra with index (a) and Using filesort after swapping it for (a, b). Same query, same results, new sort step.

Finding and removing them safely

  • You can write queries against INFORMATION_SCHEMA, but the source recommends an easier route: pt-duplicate-key-checker from Percona Toolkit, which examines table structures and suggests duplicate or redundant indexes. (I did not install or run it.)
  • Validate planned changes carefully; the source names pt-upgrade (also Percona Toolkit) for comparing behaviour. I didn't run it either.
  • In MySQL 8.0 you can mark an index invisible first. I tried it: ALTER TABLE ev ALTER INDEX idx_day INVISIBLE made SHOW INDEX report Visible: NO, and EXPLAIN then used a different index for the same query. ALTER INDEX idx_day VISIBLE turns it back on instantly, with no rebuild. That makes "hide, watch, then drop" a much safer sequence than dropping and hoping.

4. Unused indexes

Beyond duplicates, some indexes are simply never chosen by any query. The source calls them dead weight and suggests dropping them, with one caveat in a footnote: some indexes exist to enforce uniqueness, so they matter even if no query reads them.

To find them, the source uses the sys schema view over Performance Schema data (the Chapter 3 topic): SELECT * FROM sys.schema_unused_indexes; lists schema, table and index name. I ran it. On my throwaway database it listed several indexes I'd only touched with EXPLAIN, and after I actually ran a real SELECT COUNT(*) that used idx_region, that index dropped off the list. Two lessons from that. One, EXPLAIN alone doesn't count as use in what I saw. Two, the list is only as trustworthy as the observation window: an index that serves a once-a-month report looks unused if the server has only been up for a week. I believe these counters reset when the server restarts, but that detail is from my own use of the view, not from the chapter, so confirm it in the MySQL docs for your version.

5. Index and table maintenance

The source says maintenance has three goals: find and fix corruption, keep index statistics accurate, and reduce fragmentation.

Corruption

Corruption is when a table or index is damaged, from hardware faults or bugs. Symptoms the source lists: wrong query results, duplicate-key errors when there's no duplicate, even lockups or crashes. The tools: CHECK TABLE to test (not every storage engine supports it), REPAIR TABLE to fix (again engine-dependent), or a "no-op" ALTER TABLE <table> ENGINE=INNODB to rebuild, or dump and reload. If damage is in the row data or system area rather than an index, those may not work and you may have to restore from backup.

The source is blunt about InnoDB: corruption there means something is seriously wrong, most likely bad hardware or memory, or an admin action like copying live files outside MySQL (it names backing up with rsync as a typical mistake), and only rarely an InnoDB bug. It says a normal query shouldn't be able to corrupt InnoDB, and that you should find the cause instead of merely repairing, or it may come back. It points to the innodb_force_recovery setting for recovery; I didn't test that and the source defers to the MySQL manual for details. I ran CHECK TABLE on a healthy table and got status OK, which is the happy path only.

Statistics

The optimizer is cost-based, and the main cost it estimates is how much data a query will access. It estimates row counts from index statistics. If those are missing or stale, plans can get worse. The fix is ANALYZE TABLE, which regenerates them. SHOW INDEX FROM <table> shows each index's Cardinality (the engine's estimate of distinct values). On my ext table, after analysis, the primary key showed a cardinality near the row count and index (a, b) showed a around 50 (I'd generated 50 values) and the combination higher. The primary key's number was close to, but not exactly, my 10,000 rows, which is a nice reminder these are estimates.

How InnoDB gets them, per the source: it samples a few random index pages and assumes the rest looks similar. The sample size variable it names, innodb_stats_sample_pages, has a default of 8 in the book. Be aware that this is version-specific: on my 8.0 server, that name wasn't what I looked at; I queried innodb_stats_persistent_sample_pages (20 here) and innodb_stats_transient_sample_pages (8 here). I'm flagging this as a boundary: the chapter's variable name and default may not match your version, so check the docs for yours.

The source also gives a performance warning: InnoDB recalculates statistics when a table is first opened, on ANALYZE TABLE, when the table size changes a lot, and also as a side effect of some INFORMATION_SCHEMA queries, SHOW TABLE STATUS, SHOW INDEX, and a client with autocompletion on. On big, busy or slow-disk servers that can create heavy load and locking, and you can't look at the statistics without disturbing them. The source's remedy is turning off innodb_stats_on_metadata. (On my server it was already 0, so this is another place where defaults vary by version.)

Fragmentation

B-tree leaf pages perform best when tightly packed and physically in order. If not, they're fragmented, and range scans and full index scans can be many times slower, especially covered ones. Data storage has three flavors, per the source:

  • Row fragmentation: one row stored in pieces in different places, which hurts even single-row reads.
  • Intra-row fragmentation (the source's label): logically sequential pages or rows aren't sequential on disk, which hurts full scans and clustered range scans.
  • Free space fragmentation: lots of empty space in pages, so the server reads data it doesn't need.

The fixes: OPTIMIZE TABLE, dump and reload, or the no-op ALTER TABLE <table> ENGINE=<engine> for engines without OPTIMIZE. When I ran OPTIMIZE TABLE on an InnoDB table in 8.0, MySQL answered with a note: "Table does not support optimize, doing recreate + analyze instead." In other words, it rebuilt the table, which is the same idea. A real caveat: rebuilding a big table is heavy work. Chapter 6's online schema change tools (the earlier digest) are the safer way to think about doing it on a live system; the chapter itself doesn't say more here.

6. The chapter's summary: three principles

The source ends the chapter with three ideas, and I find they tie all three parts of this chapter together:

  1. Single-row access is slow. Reading a whole block to use one row wastes work (the source says this holds even on SSDs, though they handle random I/O better). Prefer reading blocks full of rows you actually need.
  2. Reading ranges in order is fast. Sequential reads avoid seeks, and data that's already in the order you want needs no follow-up sort, and GROUP BY doesn't need to sort and group rows first.
  3. Index-only access is fast. If the index has every needed column, the engine skips the row lookups, which are the slow single-row accesses from principle one.

The source links these to a three-star ranking (from another book) mentioned at the beginning of the chapter: a query's index earns a star for grouping relevant rows together, one for ordering them as needed, and one for containing all the columns. You'd like three stars, but the source admits it's often impractical: it might take too many indexes, or be impossible (its example is ordering by one column ascending and another descending). Then you settle for the best you can, or look at denormalization or summary tables.

The closing advice I'd underline: reason from how indexes work instead of using slogans like "put the most selective column first" or "index every column in the WHERE clause." And judge your schema by response time. Find slow or load-heavy queries, then ask for each: does it examine too many rows, sort after retrieval or use temporary tables, do random I/O, or fetch full rows only to get columns missing from the index? If a better index doesn't help, a rewrite of the query may; that's where Chapter 8 starts.

Why it matters

This is the part of the chapter you'll use on an ordinary Tuesday. A slow list page is often "ordered and limited by something an index could have given for free." A bloated write path is often "five indexes, two of them redundant." A plan that suddenly flipped is sometimes "statistics went stale." Having words for these (covered, filesort, redundant, invisible, cardinality) lets you read an EXPLAIN and say what's happening, and it sets up Chapter 8, which is about reading plans and rewriting queries.

Remember this

  • A covering index answers a query from the index alone (Using index). In InnoDB the primary key is an automatic extra column in every secondary index.
  • Using index (Extra) and type: index are different things.
  • An index can supply sorted output only for matching direction and a leftmost prefix, where constants can fill earlier gaps. Otherwise expect a filesort.
  • Redundant means a B-tree prefix of another index. Sometimes you keep one deliberately, trading write speed for read speed. Hide with INVISIBLE (8.0) before dropping.
  • Maintenance has three jobs: CHECK TABLE for corruption, ANALYZE TABLE for statistics, OPTIMIZE TABLE (or a rebuild) for fragmentation.

Try it yourself

  1. Covering-index detective. Make a table with a few hundred thousand rows (a recursive CTE can generate them), an index on one column, and a query selecting that column plus a second one. Run EXPLAIN, add the second column to the index, run it again, and write down what changed in key and Extra. Then select the primary key instead of the second column and see why that case is already covered. Done when you can explain each Extra value.
  2. Sort-order matrix. Create an index on three columns and write ten WHERE ... ORDER BY variants (constants in the first column, a skipped column, mixed directions, an IN, a range, a column outside the index). Predict Using filesort yes or no before each EXPLAIN, then score yourself. Bonus: try a DESC column in the index definition (MySQL 8.0) and check whether you need FORCE INDEX to see it used.
  3. Redundancy audit script. Write a short script (any language) that reads SHOW INDEX FROM output for one table and flags any B-tree index whose columns are a leftmost prefix of another index. Test it on a table you deliberately made with (a), (a, b), and (b, a). Done when it flags only (a).
  4. The invisible-index experiment. Make an index invisible, run your key queries with EXPLAIN, and note which plan changes. Make it visible again. Write a one-paragraph "safe to drop or not" verdict, naming at least one query you didn't test that could still depend on it.
  5. The write-cost meter. Time inserting 200,000 rows into a table with one index, then the same table with three extra overlapping indexes. Record both timings and the ratio. Done when you've repeated each run at least three times and noticed how noisy the numbers are (a good lesson in why the source preaches measurement).
  6. Maintenance checkup. On a scratch table, run CHECK TABLE, ANALYZE TABLE, SHOW INDEX and OPTIMIZE TABLE, and read every line of each output. Delete half the rows first, then check the table's size before and after OPTIMIZE TABLE (information_schema.TABLES has the data length columns). Done when you can say what each command reported and why.
