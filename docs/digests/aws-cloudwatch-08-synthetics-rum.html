CloudWatch Synthetics Canaries and RUM: Testing Like a User and Watching Real Users

Every other CloudWatch tool in this track waits for something to happen: a server reports a metric, an app writes a log. But what if nobody is using your site at 3am and it's broken? And what if your servers say everything is fine while real users on slow phones are staring at a blank page? Synthetics canaries and RUM are the two answers: one pretends to be a user on a schedule, the other watches real ones.

In one line

CloudWatch Synthetics runs scripted "canaries" on a schedule to test your endpoints the way a customer would, while CloudWatch RUM (real user monitoring) collects performance and error data from actual user sessions in their browsers and apps.

The big idea

There are two ways to find out if your application is healthy from the outside in. Synthetic monitoring means you write (or generate) a script that does what a user does: load the page, log in, call the API. It runs every minute or every few minutes whether or not any real customer is around, and it reports pass or fail plus timing. Its strength is that it's predictable: the same test, the same way, so a change in the result means something changed. Its weakness is that it only tests what you scripted.

Real user monitoring is the opposite trade. A small piece of code in your web or mobile app reports how things went for real people: how long pages took to load, which JavaScript errors happened, which browsers and countries are affected. It sees reality, including things you never thought to script, but it needs real traffic to say anything and it's a sample of what happened, not a controlled experiment. Used together they cover each other's blind spots, and both publish into the same CloudWatch metrics and alarms you already know.

Key terms

  • Canary: a configurable script that runs on a schedule to monitor an endpoint or API, following the same routes and actions as a customer. Named after the canary in the coal mine.
  • Synthetic monitoring: testing with scripted, artificial traffic rather than real users.
  • Blueprint: a ready-made canary template in the console (heartbeat monitor, API canary, broken link checker, visual monitoring, canary recorder, GUI workflow builder, multi checks).
  • Runtime version: the Synthetics library version (and language) your canary runs on, for example syn-nodejs-puppeteer-9.1 in the docs' example.
  • Headless browser: a real browser engine with no visible window, driven by code. Canaries in the Node.js and Python runtimes can use Playwright, Puppeteer or Selenium for this.
  • HAR file: an HTTP archive, a record of every web request a page made and how long each took.
  • Artifacts: what a canary run saves: logs, screenshots, HAR files, stored in an S3 bucket.
  • RUM (real user monitoring): collecting client-side performance and error data from real user sessions.
  • App monitor: the RUM resource you create for an application; it generates the code snippet you add to your app.
  • Session sample: the percentage of user sessions the RUM client reports on.
  • Web vitals: standard measurements of page experience such as largest contentful paint and cumulative layout shift.

How it works

Grounding: what "from the outside" means

An EC2 instance can report CPU at 5 percent while a misconfigured load balancer, an expired certificate or a broken login form means no customer can actually use the site. Metrics from inside tell you machines are fine; they can't tell you the experience is fine. Canaries and RUM measure the experience directly. That is why they sit at the top of the monitoring stack, and why their metrics are good candidates for alarms.

1. Canaries: what they are

The docs describe canaries as configurable scripts, written in Node.js, Python or Java, that run on a schedule to monitor your endpoints and APIs. Under the hood they create Lambda functions in your account, and they use Lambda layers that contain the Synthetics library. Canaries work over HTTP and HTTPS. They can check availability and latency, store load-time data and UI screenshots, monitor REST APIs, URLs and website content, and the docs say they can check for unauthorized changes from phishing, code injection and cross-site scripting.

  • Browser support: Node.js and Python runtimes can drive headless browsers through Playwright, Puppeteer or Selenium (supported browsers include Chrome and Firefox, though the docs say canaries on Selenium support only Chrome). Java canaries have no browser support or frameworks.
  • Schedule: run once or on a schedule; the docs say canaries can run as often as once per minute, with rate or cron expressions. In the console, a continuous rate is between once a minute and once an hour (the CLI reference says a frequency between rate(1 minute) and rate(1 hour)).
  • Availability: the docs list it as available in all commercial AWS Regions and the GovCloud Regions.

2. Blueprints: the quick-start canaries

When you create a canary in the console you can start from a blueprint, then edit the generated Node.js script. From the docs:

  • Heartbeat monitoring: loads a URL and stores a screenshot, an HTTP archive (HAR) file and logs of accessed URLs. The simplest "is the site up and how fast" canary.
  • API canary: tests the basic read and write functions of a REST API. Each request has an endpoint, a method, headers and a body. The blueprint supports GET and POST and integrates with API Gateway. Not supported by Playwright runtimes.
  • Broken link checker: collects the links on a page and tests up to a number you set (the starting URL counts as the first link). It reports status code and failure reason for each and detects problems like 404s and invalid host names. Not supported by Playwright runtimes.
  • Visual monitoring: compares screenshots against a baseline run and fails if the difference exceeds a threshold percentage you set. Supported on specific runtimes only (not Python/Selenium or Playwright), per the docs.
  • Canary recorder: a Chrome extension that records your clicks and typing and generates a Node.js script. Not supported for Playwright canaries.
  • GUI workflow builder: you specify actions (click, verify selector, verify text, input text, click with navigation) so the canary can, for example, fill a login form and check the welcome message.
  • Multi checks: a JSON-configured blueprint offering HTTP, DNS, SSL certificate and TCP checks, up to 10 checks, run sequentially.

3. What a canary publishes

By default canaries publish metrics to the CloudWatchSynthetics namespace with CanaryName as a dimension. (Remember namespaces and dimensions from the first digest.) The ones worth knowing, from the docs' metrics table:

  • SuccessPercent: the percentage of runs that succeed and find no failures (Average, Percent). This is the natural thing to alarm on.
  • Duration: how long a run took, in milliseconds.
  • Failed: the number of runs that failed to execute, for failures related to the canary itself.
  • 2xx, 4xx, 5xx: counts of the canary's network requests by response code range (reported for certain runtime versions).
  • VisualMonitoringSuccessPercent and others for visual comparison.

Canaries that use the library's executeStep() or executeHttpStep() also publish SuccessPercent and Duration per step with a StepName dimension. So a multi-step login-then-checkout canary tells you which step broke.

Simplification: "Failed" and "SuccessPercent" are different on purpose. As I read the table, Failed counts runs that failed to execute because of the canary itself, while SuccessPercent reflects whether the run found no failures at all. If your site returns an error, I would expect that to lower SuccessPercent; check the docs for the exact behaviour in your runtime.

4. Creating a canary: the pieces involved

The console flow in the docs (Application Signals, Synthetics Canaries, Create Canary) asks for: a blueprint or your own script; a name; the URL to test (including the protocol); optionally extra Regions to run from (multilocation canaries); the runtime version; a schedule; an optional timeout (the docs recommend no shorter than 15 seconds to allow for Lambda cold starts); data retention for successful and failed runs; an S3 bucket for artifacts; an IAM role; optional default alarms; optional VPC settings; tags; and optional X-Ray active tracing.

  • Resources created: per the docs, potentially an IAM role and policy, an S3 bucket named cw-syn-results-<accountID>-<region>, alarms named Synthetics-Alarm-<canaryName>-<index> if you opt in, Lambda functions and layers prefixed cwsyn-, and a log group /aws/lambda/cwsyn-.... Remember to delete these when you clean up.
  • VPC: to test an endpoint on a VPC, the docs say you pick private subnets, because a Lambda function can't be given a public IP, and the canary must still be able to reach CloudWatch and S3 (NAT gateway or VPC endpoints; the VPC track again).
  • Be a good citizen: the docs warn to monitor only endpoints and APIs you own or have permission to test, because the schedule creates traffic.
  • CLI: aws synthetics create-canary requires --name, --code, --artifact-s3-location, --execution-role-arn, --schedule and --runtime-version. The reference's example uses --schedule Expression="rate(10 minutes)" and --runtime-version syn-nodejs-puppeteer-9.1. Canary names allow lowercase letters, digits, hyphens and underscores, and the docs say not to put secrets in the name.
  • Retention: the default for both success and failure data is 31 days per the CLI reference. The console docs state a range of 1 to 455 days, while the CLI reference's formal constraint shows a larger maximum. Check the live limit before relying on a number.
  • Events: the docs also have a page on monitoring canary events with EventBridge, connecting this back to the previous digest.

5. CloudWatch RUM: how it works

You create an app monitor for your application. RUM generates a code snippet that you add to your app (the docs recommend installing the web client with NPM as a JavaScript module; a CDN-hosted HTML option exists but the docs warn it's often blocked by ad blockers). The RUM client then captures data from a percentage of user sessions, which you choose, and shows it in a prebuilt dashboard. For web apps it can analyse page load times, client-side errors and user behaviour; for mobile it covers screen load times, app launch times, network errors, crashes, and Android ANRs and iOS app hangs.

Options when creating a web app monitor (docs): an application domain list (wildcards allowed); which telemetry to collect (performance telemetry, JavaScript errors, HTTP errors; choosing more generates more events and more charges); a checkbox to allow the web client to set cookies so user and session IDs can be collected; the session sample percentage (default 100 percent, and reducing it lowers cost and data); whether to store a copy of telemetry in CloudWatch Logs; authorization (a new or existing Amazon Cognito identity pool, a different identity provider, or a resource-based policy); which pages to include or exclude; and X-Ray active tracing. Even with nothing selected, the monitor still collects session start events and page IDs, so you can see how many users you have by OS, browser, device and location.

  • Retention: RUM end-user data is kept 30 days and then deleted, per the docs. To keep it longer, send a copy to CloudWatch Logs and set that log group's retention (default 30 days there, adjustable).
  • Privacy: because the client can set cookies for user and session IDs, think about consent requirements where you operate. The docs have a dedicated privacy page; I haven't summarised it.
  • Metrics: web metrics land in the AWS/RUM namespace with an application_name dimension (the app monitor name). Examples: JsErrorCount, Http4xxCount, Http5xxCount, PageViewCount, SessionCount, PerformanceNavigationDuration, and web vitals such as WebVitalsLargestContentfulPaint, WebVitalsCumulativeLayoutShift and WebVitalsInteractionToNextPaint.
  • Apdex-style buckets: the docs define navigation "satisfied" as under 2000 ms, "tolerated" between 2000 and 8000 ms, and "frustrated" above 8000 ms.

6. Canary or RUM?

Canary: you need to know the checkout is up at 3am with zero traffic, test a new endpoint before launch, or check a certificate or link. It's controlled and repeatable.

RUM: you need to know how real users on real devices experience speed and errors, and which browsers or regions are worse. It's real but depends on traffic and sampling.

Simplification: in practice you'd use both and alarm on a canary's SuccessPercent and a RUM error metric. The docs also integrate both with Application Signals and X-Ray tracing for deeper debugging, which belongs to the next concept.

Why it matters

"The servers are green" is not the same as "customers can buy things". Canaries give you an always-on customer stand-in, and RUM gives you the view from the customer's seat. Both feed ordinary CloudWatch metrics, so everything you learned about alarms, composite alarms and dashboards applies. They also cost money in ways that scale with how often you run canaries and how much RUM data you collect, so choose frequency and sample rate on purpose. I'm not quoting prices here.

Remember this

  • A canary is a scheduled script (run as a Lambda function) that acts like a user; it publishes SuccessPercent, Duration and more to CloudWatchSynthetics and saves artifacts to S3.
  • Blueprints (heartbeat, API, broken link, visual, recorder, GUI workflow, multi checks) get you started; you can edit the generated script.
  • RUM uses an app monitor and a code snippet to sample real sessions: page loads, JS errors, HTTP errors, web vitals; data kept 30 days unless copied to Logs.
  • Synthetic is controlled but only tests what you scripted; RUM is real but needs traffic and is sampled.
  • Both can be alarmed on like any other metric.

Try it yourself

  1. Heartbeat on a site you own. In the console, create a canary from the heartbeat blueprint for a personal page or a lab endpoint you control, running rate(5 minutes). Done when: you've opened a run's screenshot and HAR file, and can list which AWS resources it created (role, bucket, Lambda, log group).
  2. Alarm on it. Create an alarm on SuccessPercent for your canary (namespace CloudWatchSynthetics, dimension CanaryName) that goes to ALARM below 100 for 2 of 3 periods, with an SNS action. Done when: you've broken the target on purpose (for example point the canary at a URL that 404s by editing it) and received the email.
  3. A two-step API canary. Use the API canary blueprint (or the docs' sample scripts) with two HTTP steps. Done when: you can find StepName in the metrics and explain what each step's Duration tells you.
  4. Visual baseline. Create a visual monitoring canary on a page you control, let it set a baseline, change visible text on the page, and see it fail. Done when: you've adjusted the threshold or an ignore region and seen the effect.
  5. RUM on a toy page. Create a RUM app monitor for a static test page (an S3-hosted page is fine if you've done the S3 track), paste the snippet, set the session sample to 100 percent, and visit the page from a couple of browsers. Throw a deliberate JavaScript error. Done when: the error and your browsers show up in the RUM dashboard and you can find JsErrorCount under AWS/RUM.
  6. Cost thinking on paper. For a site with 100,000 sessions a day, write down what changes if you set the RUM sample to 10 percent, and what changes if you move a canary from rate(1 minute) to rate(5 minutes). Done when: you've written which knobs reduce cost and what visibility you lose with each. Clean up every resource afterwards.
