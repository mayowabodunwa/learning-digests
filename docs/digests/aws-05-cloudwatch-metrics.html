CloudWatch Metrics: Namespaces, Dimensions, Resolution, Custom Metrics

CloudWatch doesn't magically know that "CPUUtilization" from your app server and "CPUUtilization" from your database are different things. You tell it apart with four ideas: namespace, dimension, resolution, and the custom metric you publish yourself.

In one line

A CloudWatch metric is just a named, timestamped stream of numbers, and namespaces plus dimensions are the two things that keep a thousand different metrics from colliding into one meaningless average.

The big idea

Every resource in AWS is constantly generating numbers worth watching: CPU load, request counts, queue depth, error rates. CloudWatch is the service that collects those numbers, calls each stream a "metric", and lets you graph it, alarm on it, or query it later. The hard part isn't collecting the numbers, it's keeping them organized: if you have 50 EC2 instances all reporting "CPUUtilization", CloudWatch needs a way to know that instance A's number and instance B's number are separate things, not one number to blend together. That's what namespaces and dimensions are for. On top of that, every metric has a resolution (how often a new data point can exist) and you're not limited to what AWS ships by default: you can publish your own custom metrics for anything your own code cares about.

Key terms

  • Metric — a time-ordered set of data points published to CloudWatch, representing one thing you're tracking over time (e.g. the CPU usage of one EC2 instance). Think of it as a variable, and the data points as its value at each moment.
  • Namespace — a container that keeps metrics from different applications or services isolated from each other, so they never get accidentally aggregated together. There is no default namespace; you must name one for every metric you publish.
  • Dimension — a name/value pair that's part of a metric's identity (e.g. InstanceId=i-0abc123). Dimensions are how you split one metric name into many separate variations, like "CPUUtilization, but specifically for this one instance."
  • Data point — one value in a metric, at one point in time. Each data point has a timestamp and, optionally, a unit of measure.
  • Resolution — how granular a metric's data points are allowed to be. A metric is either standard resolution (one-minute granularity) or high resolution (one-second granularity).
  • Standard resolution — the default: data points at one-minute granularity. Every AWS-service metric is standard resolution by default.
  • High-resolution metric — a custom metric you explicitly publish at sub-minute granularity (as fine as one second), for cases where a full minute is too coarse to see what's happening.
  • Custom metric — any metric you publish yourself (as opposed to one an AWS service publishes automatically for you), using the PutMetricData API or the equivalent CLI command.
  • PutMetricData — the CloudWatch API action (and CLI command aws cloudwatch put-metric-data) used to publish one or more data points for a custom metric. If the metric name doesn't exist yet, CloudWatch creates it for you.
  • Statistic set — a pre-aggregated bundle (Sum, Minimum, Maximum, SampleCount) you can publish in one PutMetricData call instead of sending every raw data point individually. Useful when you have many events per minute and don't want to call the API once per event.
  • Period — the length of time (in seconds) over which CloudWatch aggregates data points when you retrieve statistics. Valid values are 1, 5, 10, 30, or any multiple of 60. The default is 60 seconds.
  • Unit — the unit of measure attached to a data point (e.g. Bytes, Seconds, Count, Percent). If you don't specify one, CloudWatch uses None.
  • Storage resolution — the specific API/CLI parameter (StorageResolution in the API, --storage-resolution in the CLI) you set to 1 to make a custom metric high-resolution, or 60 (the default) to keep it standard resolution.

How it works

Here's the grounding piece: a CloudWatch metric on its own is nothing more than a name plus a stream of timestamped numbers. What makes CloudWatch usable at scale, once you have hundreds of resources each reporting dozens of things, is how it tells one metric apart from a thousand others that happen to share the same name. That's the job of namespaces and dimensions. Layered on top of that identity system is resolution (how fine-grained the numbers can be) and the fact that you aren't limited to metrics AWS ships for you: anything your own application can measure, it can publish as a custom metric.

1. Namespaces: the top-level container

A namespace is the first, broadest way CloudWatch keeps metrics from colliding. It's just a string you attach to every metric you publish, and metrics in different namespaces are completely isolated from each other, even if they happen to share a metric name. AWS's own services follow the convention AWS/{service}: Amazon EC2's metrics live in AWS/EC2, Amazon S3's live in AWS/S3, and so on. There's no default namespace for anything you publish yourself, you have to pick one every time, and AWS explicitly recommends you avoid starting your own custom namespace with AWS/ so you don't collide with (or look like) an AWS-owned namespace.

Namespace names can be up to 255 characters, using ASCII letters, numbers, and a specific set of punctuation (period, hyphen, underscore, forward slash, hash, colon, and the space character), with at least one non-whitespace character. In practice, most people pick something simple and specific to their application, like MyStore/Checkout or PaymentsService, so their custom metrics don't get lost among AWS's own.

2. Dimensions: what actually makes a metric unique

A dimension is a name/value pair, like InstanceType=m1.small or Environment=production, and it's part of a metric's identity, not just a label stapled onto it afterward. A metric is uniquely defined by its name, its namespace, and its full set of dimensions; change any dimension value and CloudWatch treats it as a genuinely different metric, even though the metric name is identical. You can attach up to 30 dimensions to a single metric.

This is what lets one metric name mean many different things at once. Imagine you publish a metric called ServerStats in a namespace called DataCenterMetric, with a Server dimension (Prod or Beta) and a Domain dimension (Frankfurt or Rio). If you publish data for all four combinations of those two dimension values, CloudWatch is now tracking four completely separate metrics under one name: Server=Prod+Domain=Frankfurt, Server=Prod+Domain=Rio, Server=Beta+Domain=Frankfurt, and Server=Beta+Domain=Rio. You can only retrieve statistics for combinations you actually published; asking for just Server=Prod with no domain specified returns nothing, because that combination was never published as its own data point (metric math's SEARCH function is the one exception, since it can search across many metrics at once). One more subtlety worth knowing: for metrics that some AWS services publish (like EC2's), CloudWatch can aggregate across dimensions for you if you leave dimensions unspecified. For your own custom metrics, it does not do this automatically: you get back exactly the combinations you published, nothing more.

3. Resolution: standard vs. high-resolution

Every metric is either standard resolution, meaning its data points have one-minute granularity, or high resolution, meaning its data points can be as fine as one-second granularity. Metrics produced by AWS services are standard resolution by default; you can't make an AWS-service metric high-resolution. When you publish a custom metric yourself, though, you get to choose: standard (the default) or high-resolution, by setting the StorageResolution API parameter (or --storage-resolution on the CLI) to 1 for high-resolution, or leaving it at the default of 60 for standard.

Once a metric is stored at high resolution, you can retrieve it with a period of 1, 5, 10, or 30 seconds, or any multiple of 60. High-resolution metrics matter when a full minute would hide what's actually happening, a brief spike in error rate or a fast queue drain, but they cost more: every PutMetricData call is billed, so publishing every second instead of every minute means roughly 60x more calls, and CloudWatch also charges more for high-resolution alarms evaluated at a 10 or 30 second period specifically (exact current pricing isn't covered here; check the CloudWatch pricing page before you rely on a number).

Resolution also determines how long a data point sticks around before it gets aggregated away to a coarser resolution. CloudWatch's stated retention: data points stored at a period of less than 60 seconds (high-resolution custom metrics) are available for 3 hours; data points at a 60-second period are available for 15 days; at a 300-second (5-minute) period, 63 days; and at a 3600-second (1-hour) period, 455 days (about 15 months). Data originally published at a finer resolution doesn't just vanish once its retention window passes, it gets aggregated into the next coarser resolution automatically, so 1-minute data becomes 5-minute data after 15 days, and 5-minute data becomes 1-hour data after 63 days. A metric that stops receiving new data points is never deleted outright, but it does expire (and its old data points roll off) after 15 months of inactivity.

4. Publishing custom metrics with PutMetricData

Any AWS service metric (like EC2's CPUUtilization) shows up in CloudWatch automatically. A custom metric is one you publish yourself, from your own application or script, using the PutMetricData API action (or the CLI command aws cloudwatch put-metric-data). If you call it with a metric name that doesn't exist yet, CloudWatch creates the metric for you; you never have to "declare" one in advance.

A minimal example, publishing one data point for a custom metric with two dimensions:

aws cloudwatch put-metric-data --namespace MyNameSpace --metric-name Buffers --unit Bytes --value 231434333 --dimensions InstanceId=1-23456789,InstanceType=m1.small

To make that same metric high-resolution instead of standard, you'd add --storage-resolution 1 to the call. There are three ways to hand CloudWatch the actual numbers: a single --value for one data point at a time; a --statistic-values statistic set (Sum, Minimum, Maximum, SampleCount) when you've already aggregated many events into one summary, which is the recommended approach if you have many data points within the same minute and don't want to call the API once per event; or a Values/Counts array pair in a single call, which supports up to 150 values per metric per request and preserves enough raw information to compute percentile statistics later (a statistic set alone generally can't be used for percentiles unless its Min, Max, and SampleCount happen to satisfy specific conditions).

A few concrete limits worth knowing before you build against this API: each PutMetricData request is capped at 1000 different metrics and at 1 MB in size (you can gzip the payload); each metric can carry up to 30 dimensions; a data point's value must fall between -2^360 and 2^360, and special values like NaN or Infinity are rejected; and a timestamp can be up to two weeks in the past or up to two hours in the future. A freshly created metric can take up to 15 minutes to show up when you list metrics, and up to roughly 2 minutes before you can pull statistics for it, so don't panic if it doesn't appear instantly. Also worth knowing: data points with timestamps more than 24 hours old can take at least 48 hours to become queryable, and points from 3-24 hours ago can take up to 2 hours, so backfilling old data isn't instantaneous either.

Why it matters

This is the layer everything else in CloudWatch (dashboards, alarms, anomaly detection) sits on top of. If you get namespaces and dimensions wrong, either by publishing everything under one vague namespace or by forgetting a dimension that actually matters (like which instance, which customer, which region), you end up with metrics that are technically "there" but useless: you can't isolate the one server that's actually struggling, or you can't tell your staging traffic apart from your production traffic. Resolution matters because the default one-minute granularity is completely invisible to anything that happens and resolves in seconds, like a brief connection pool exhaustion or a Lambda cold-start spike; if you only ever look at 1-minute averages, short, sharp problems get smoothed away into "looks fine." And custom metrics are what let CloudWatch watch things AWS could never know about on its own, like your own application's queue depth, checkout failures, or a business metric like signups per minute. Together, these four ideas are what turn CloudWatch from "a dashboard AWS gives you" into "a system that reflects exactly what you decided was worth measuring."

Remember this

  • A metric's real identity is its name plus its namespace plus its full set of dimensions; change one dimension value and it's a different metric, even under the same name.
  • There's no default namespace: you must name one for every metric, and AWS recommends not starting a custom namespace with AWS/.
  • Standard resolution is 1-minute granularity and is what AWS services use by default; high resolution is 1-second granularity and is opt-in for custom metrics via StorageResolution / --storage-resolution 1.
  • Retention scales with the period the data was stored at: sub-minute data keeps for 3 hours, 1-minute data for 15 days, 5-minute data for 63 days, 1-hour data for 455 days (about 15 months), and older data is aggregated into coarser resolution rather than deleted outright.
  • Custom metrics are published with PutMetricData (CLI: aws cloudwatch put-metric-data); if the metric name doesn't exist yet, CloudWatch creates it the first time you publish to it.

Try it yourself

  1. Publish your first custom metric. Run aws cloudwatch put-metric-data --namespace "Learning/Digest" --metric-name PagesRead --unit Count --value 5 and then find it in the CloudWatch console under Metrics. Done when: you can see your custom namespace listed and a single data point graphed.
  2. Make one metric name become two metrics with a dimension. Publish the same metric name twice with a different dimension value each time (e.g. Server=A then Server=B). Done when: you can see both as separate rows under the same metric name in the console, and you can explain why querying with no dimension at all returns nothing for a custom metric.
  3. Publish a high-resolution metric and watch it tick every second. Write a tiny script (any language) that calls put-metric-data once a second for a minute or two with --storage-resolution 1, then graph it in the console with a 1-second period. Done when: you can see individual per-second data points instead of a flattened per-minute line.
  4. Publish a statistic set instead of individual points. Collect five made-up values yourself (e.g. 12, 8, 15, 9, 11), compute Sum/Minimum/Maximum/SampleCount by hand, and publish them in one call using --statistic-values. Done when: the resulting Average statistic in the console matches your own hand-computed average.
  5. Break a metric on purpose by mismatching dimensions. Publish under Env=prod, then try to retrieve statistics for the same metric name using Env=staging (a combination you never published). Done when: you've confirmed CloudWatch genuinely returns nothing, and you understand why that's different from "the value happens to be zero."
  6. Time-travel a timestamp. Publish one data point with a timestamp from 10 days ago, and try one from 3 weeks ago. Done when: you've observed the 10-day-old point get accepted and the 3-week-old one get rejected, and you can say why (the two-week limit).

Go deeper

Once this mental model feels solid, look at how CloudWatch alarms consume exactly this structure (an alarm watches one specific namespace + metric name + dimension combination, at a chosen period), and how metric math lets you combine several metrics (including, via the SEARCH function, metrics across a whole family of dimension values at once) into a single derived value worth graphing or alarming on.
