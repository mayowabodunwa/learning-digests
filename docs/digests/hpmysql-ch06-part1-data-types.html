Schema Design and Management: Data Types & Identifiers

Every column you create is a small bet: how big will this get, will it ever be empty, and how will it be compared? MySQL gives you a huge menu of overlapping types for making that bet, and this part walks through how to pick well, plus how to choose the identifier columns that everything else in a schema ends up leaning on.

In one line

Choosing a MySQL data type isn't just about "will this store my value correctly," it's about size, simplicity, and nullability, because those three things quietly control how much disk, memory, and CPU every single row costs you, and identifier columns matter most of all because their type choice ripples into every table that joins to them.

The big idea

MySQL supports a large number of data types, and several of them can store the exact same kind of value while differing in storage size, range, and behavior. A DATETIME and a TIMESTAMP column can both hold "date and time down to the second," for instance, but one uses twice the storage of the other and behaves completely differently around time zones. The chapter's core advice boils down to three habits: use the smallest type that can honestly hold your data, prefer simple types (like integers) over complex ones (like strings) wherever the meaning is the same, and avoid letting a column accept NULL (MySQL's way of representing "no value at all") unless you actually need to represent "unknown" or "not applicable." None of these are free-standing rules, they all trace back to the same fact: smaller and simpler values are cheaper for MySQL to store, compare, and move around.

Key terms

  • Data type — the rule MySQL uses to know what kind of value a column holds and how to store it (a whole number, a string, a date, and so on). It's a real lever on both correctness and performance, not just a formality.
  • NULL — MySQL's way of saying "no value here at all." It's different from zero, an empty string, or any other "real" value in that type's domain.
  • NOT NULL — a column constraint that refuses to let a row be saved without a value in that column.
  • Storage engine — the component underneath a table that actually reads and writes its rows. InnoDB is the default storage engine in current MySQL versions, and it's what this digest's storage details assume unless noted otherwise.
  • VARCHAR — a string type that uses only as much space as the value actually needs, plus a byte or two to record the length.
  • CHAR — a string type that always reserves the same fixed number of characters, however short the value is.
  • BLOB / TEXT — families of types built for large chunks of data: BLOB for raw bytes with no character set, TEXT for character data with one.
  • ENUM — a string column restricted to one value from a fixed list you define up front; MySQL actually stores it internally as a small integer.
  • SET — like ENUM, but a single column can hold several values from its fixed list at once, packed into bits.
  • DECIMAL — an exact, fixed-point numeric type for when you can't tolerate rounding error (money is the classic case).
  • FLOAT / DOUBLE — approximate, floating-point numeric types: fast and compact, but not exact.
  • DATETIME / TIMESTAMP — two different MySQL types that both store a date and time down to the second, with very different storage size, range, and time-zone behavior.
  • Identifier — the column (or columns) you use to uniquely point at one row, most often the table's primary key.
  • Primary key — the column or columns designated to uniquely identify every row in a table.
  • Foreign key — a column in one table that points at a primary key in another table, tying the two together.
  • AUTO_INCREMENT — a column attribute that has MySQL hand out the next integer automatically on every insert, so nothing has to compute the next ID itself.
  • UUID — a universally unique identifier: a long, effectively random value that can be generated independently on any machine with no coordination needed to avoid collisions.
  • Clustered index — in InnoDB, the actual row data is physically stored in primary-key order. That means where a new key value lands isn't just a lookup detail, it decides where the whole row gets written on disk.
  • Index page — the fixed-size block a storage engine reads and writes index (and, for a clustered index, row) data in. Inserting a value that doesn't land at the "end" can force an existing page to be split to make room.
  • Entity-attribute-value (EAV) — a schema pattern that stores every property as its own row (an entity id, an attribute name, a value) instead of as a column, trading a rigid schema for a very join-heavy one.

How it works

Here's the grounding idea before the details: a data type isn't just a correctness check MySQL runs on the way in. It's a physical commitment. Every column's type decides how many bytes each value takes on disk, how much of that gets pulled into memory when a query touches it, how it's compared during a WHERE or a JOIN, and whether it can even be indexed efficiently at all. A schema made of slightly-too-generous types isn't "wrong," it'll still return correct answers, it's just paying a small, compounding tax on every row, every query, and every index, forever. The rest of this part walks through where that tax shows up, one family of types at a time, then closes with the identifier columns where all of this matters most because their type choice spreads into every table that references them.

1. Why smaller and simpler wins (and what NULL quietly costs you)

Three habits do most of the work. First, smaller is usually better: pick the smallest type that can correctly hold your data, because smaller types are generally faster, using less space on disk, in memory, and in the CPU cache, and needing fewer CPU cycles to process. The catch is you have to be honest about future growth, since widening a type across a schema later (especially one used as a foreign key in several tables) can be a slow, painful operation, so when you're unsure, pick the smallest type you genuinely don't expect to exceed rather than the smallest type period.

Second, simple is good: fewer CPU cycles are typically needed to process simple types. Comparing two integers is cheap; comparing two strings is more expensive because character sets and collations (the rules that decide how characters sort and match) make the comparison more complicated. That's the reasoning behind two very concrete suggestions worth remembering on their own: store dates and times in MySQL's built-in date/time types instead of as text, and store an IP address as the plain integer it actually represents (an IPv4 address is really an unsigned 32-bit integer) rather than as a 15-character string like 203.0.113.42. Storing it as an unsigned integer with MySQL's INET_ATON() function shrinks it from roughly 16 bytes down to 4, and INET_NTOA() converts it back for display; if you're worried about readability, a view can show the human-friendly form without changing how the underlying column is stored.

Third, avoid NULL where you can. It's common to see nullable columns even when the application never actually needs to store "no value," simply because nullable was the path of least resistance when the table was created. That's usually worth resisting: a nullable column makes indexes, index statistics, and value comparisons more complicated for MySQL to optimize, and it needs a bit of extra storage and special handling internally. To be clear about the scale of this: the performance gain from converting an existing nullable column to NOT NULL is usually small, so it's not worth a special project to hunt down and "fix" nullable columns on a schema that's already working, unless you have evidence they're actually causing a problem. The bigger win is simply defaulting new columns to NOT NULL unless you have a real reason to store "unknown."

2. Whole numbers and real numbers

For whole numbers, MySQL offers five integer types: TINYINT, SMALLINT, MEDIUMINT, INT, and BIGINT, using 8, 16, 24, 32, and 64 bits of storage respectively. Each stores values from −2^(N−1) to 2^(N−1) − 1, where N is the number of storage bits, so a plain (signed) TINYINT covers −128 to 127. Adding the UNSIGNED attribute drops negative numbers entirely and roughly doubles the positive ceiling instead: a TINYINT UNSIGNED covers 0 to 255. Signed and unsigned versions of a type use the same storage space and have the same performance, so the choice is purely about which range fits your data, for example a column that will only ever hold a small positive count is a natural fit for UNSIGNED. One legacy quirk worth knowing: MySQL lets you write a display width like INT(11), but that number doesn't restrict the range of values you can store, it only tells interactive tools how many characters to reserve for display. For storage and computation, INT(1) and INT(20) are identical.

Real numbers (values with a fractional part) split into approximate and exact types. FLOAT (4 bytes) and DOUBLE (8 bytes) do standard floating-point math and typically use less space than DECIMAL for the same range, but they're approximate: MySQL actually uses DOUBLE internally for floating-point calculations regardless of which one you declared the column as. DECIMAL stores exact fixed-point values (and can even hold whole numbers too large for BIGINT), which is why it's the usual choice for money. But exactness has a real cost in extra space and computation, so for very high-volume cases it can actually make more sense to avoid DECIMAL altogether: store the value as a BIGINT scaled up by a fixed multiplier. For example, if you need to track a currency amount to the ten-thousandth of a cent, you can multiply every amount by a million before storing it as a BIGINT, sidestepping both floating-point imprecision and the cost of exact decimal math, as long as your application consistently divides back out on the way out.

3. String types: VARCHAR, CHAR, BLOB/TEXT, and ENUM

The two workhorse string types are VARCHAR and CHAR. VARCHAR stores variable-length values and only uses as much space as each value needs, plus 1 extra byte to record the length if the column's maximum length is 255 bytes or less, or 2 bytes if it's more (so, assuming a single-byte character set, a VARCHAR(10) uses up to 11 bytes, and a VARCHAR(1000) uses up to 1,002). That space saving is real, but because rows are variable length, updating a value so it grows can force MySQL to do extra work rearranging storage; the exact behavior is storage-engine dependent, and InnoDB specifically may need to split a data page to make room. VARCHAR tends to be the right call when the maximum length is much bigger than the typical length, when updates to the column are rare (so this fragmentation risk rarely bites), or when you're using a multi-byte character set like UTF-8.

CHAR is fixed-length: MySQL always reserves the full declared width, trims trailing spaces when it stores a value, and pads with spaces for comparisons. Say you create a small lookup table with a CHAR(6) code column and insert the values 'AB12', ' CD34', and 'EF56 '. Read them back and the trailing space on 'EF56 ' is gone, while the same values in a VARCHAR(6) column would come back with that trailing space intact, because VARCHAR stores exactly what you gave it. CHAR is a good fit for short, mostly-uniform-length values (a fixed-length hash like an MD5 digest is a textbook case) and for columns that change often, since a fixed-length row doesn't fragment the way a growing VARCHAR row can. For very short columns it's also just more compact: a CHAR(1) holding only Y or N uses 1 byte in a single-byte character set, while a VARCHAR(1) would need 2 bytes once you count its length byte.

One easy-to-miss trap: declaring a column much wider than you need doesn't cost extra space to store a short value (a VARCHAR(5) and a VARCHAR(200) both take the same space to store 'hello'), but it can still hurt, because MySQL often allocates memory for a value based on its declared maximum size, not its actual length, especially for sorting and for temporary tables built in memory or on disk. A generously-sized column you'll never fill can quietly make sorts and temp tables heavier than they need to be, so it's worth declaring only as much room as you realistically need.

BLOB and TEXT are each a family of types (TINYBLOB through LONGBLOB, TINYTEXT through LONGTEXT) built for large amounts of data, binary for BLOB, character data with a collation for TEXT. MySQL treats each value as its own object, storing 1 to 4 bytes in the row itself plus whatever external storage the value needs (InnoDB may keep large values in a separate storage area). They sort only by the first max_sort_length bytes rather than the full value, and MySQL can't build a full-length index on them or use an index to sort by them. A related, very MySQL-specific caution: if you're tempted to store uploaded images directly as BLOB data to keep everything in one place, that convenience tends to sour as the data grows, since operations like schema changes get slower as the table's BLOB payload gets bigger. Writing large binary assets to a separate object store and keeping only a reference (a URL or filename) in the row is usually the better trade.

ENUM lets a column hold one value from a predefined list, and MySQL stores it compactly, packed into 1 or 2 bytes depending on how many values the list has, as an integer representing that value's position in the list you defined. Define size ENUM('small','medium','large') NOT NULL and MySQL stores 1, 2, or 3 internally, not the text. That has a real, occasionally surprising consequence: an ENUM column sorts by its internal integer, not alphabetically by the string, so if you defined the values out of the order you want them to sort in, a plain ORDER BY won't give you what you expect. You can work around that with ORDER BY FIELD(column, 'value1', 'value2', ...) to force a specific order, though doing so stops MySQL from being able to use an index for that sort. The book ran its own benchmark joining a wide primary key across two copies of a real production-style table, once with two of the key columns left as VARCHAR and once with those same two columns converted to ENUM: joining ENUM to ENUM came out fastest, joining VARCHAR to VARCHAR was a bit slower, and mixing ENUM with VARCHAR in the same join was the slowest combination of the four (worth noting as a specific, hardware- and dataset-dependent result rather than a universal ranking). The conversion also shrank that table's on-disk size by roughly a third, since the primary key itself got about half as wide, which is significant in InnoDB because every secondary index also has to store a copy of the primary key value. The catch: changing what values are legal in an ENUM always requires an actual schema change (an ALTER TABLE), which can turn into a real operational headache if you don't yet have a smooth, automated way to run schema changes.

4. Date and time: DATETIME vs TIMESTAMP

MySQL has several date/time types, but for most of them (like YEAR and DATE) there's no real alternative to weigh. The interesting decision is when you need both a date and a time together, where MySQL offers two very similar-looking options. DATETIME covers a huge range, the year 1000 through 9999, at up to microsecond precision, storing the value packed into an integer independent of time zone, and it uses 8 bytes. By default MySQL displays it in a sortable, unambiguous format like 2008-01-16 22:37:08.

TIMESTAMP instead stores the number of seconds since midnight, January 1, 1970 GMT, the same idea as a Unix timestamp, in just 4 bytes, which is exactly why its range is so much smaller: 1970 through January 19, 2038 (this is the well-known "year 2038" ceiling). Unlike DATETIME, the value a TIMESTAMP displays depends on the time zone settings of the server, the operating system, and the client connection, so a stored value of 0 can display as very different wall-clock times depending on where you're looking from it. In practice: DATETIME preserves the textual date and time you gave it regardless of time zone, while TIMESTAMP preserves a point in absolute time and re-renders it per time zone, and that difference matters a lot if your data spans multiple time zones. TIMESTAMP also comes with special behavior nothing else has by default: MySQL can automatically set the first TIMESTAMP column to the current time on insert, and update it again on every update, unless you configure that off or set the value explicitly, and (in a distinct quirk from every other MySQL type) a TIMESTAMP column is NOT NULL by default. These auto-update rules have also changed across MySQL versions, so it's worth checking SHOW CREATE TABLE after touching a TIMESTAMP column to confirm you actually got the behavior you intended.

There's a third option worth knowing about even though the book is candid that it's more a matter of taste than a settled best practice: storing date and time as a plain integer holding the Unix epoch (seconds since 1970-01-01 UTC) yourself. A signed 32-bit INT gets you to 2038 (no better than TIMESTAMP); an unsigned 32-bit INT stretches that to 2106; a 64-bit integer goes well beyond either. The appeal is sidestepping MySQL's built-in time zone handling entirely and doing it explicitly in your own code instead, which some teams prefer and others don't; there's no single right answer here, only a set of trade-offs (range needed, how much storage space matters, whether you need fractional seconds, and whether you want MySQL or your application code to own time zone handling) to weigh for your own case.

5. Bit-packed types and JSON

MySQL has a small family of types built to pack data tightly at the bit level; all of them are technically string types under the hood regardless of how they're manipulated. BIT(N) stores N individual bits (up to 64) in one column, but in InnoDB specifically it's actually stored as the smallest integer type large enough to hold those bits, so it doesn't save any space there, and its dual "sometimes a string, sometimes a number" retrieval behavior is easy to get wrong. For most applications the book recommends avoiding BIT and reaching for TINYINT instead, even if you're trying to save space with a single true/false flag.

SET is the more useful sibling: it lets you combine many true/false flags into a single column, stored internally as packed bits, with functions like FIND_IN_SET() to query it conveniently. The alternative to SET is to pack flags into a plain integer column yourself and manipulate them with bitwise operators, defining named constants in your application code for each bit position. For example, a SaaS app might track which optional features an account has enabled with features TINYINT UNSIGNED NOT NULL DEFAULT 0, where each bit means something like "dark mode enabled" or "beta program opted in," set and checked with bitwise operators in code rather than in the column definition. The advantage over SET is that you can redefine what each bit means without an ALTER TABLE; the drawback is that the queries and the data itself become much harder for a human to read directly, since nothing in the schema tells you what bit 3 means.

MySQL's native JSON type stores a JSON document and lets you operate on parts of it directly from SQL, which is convenient when your data doesn't map neatly onto fixed columns, or when you're deliberately avoiding the ceremony of designing those columns up front. The book ran a direct comparison using a small real dataset (a couple hundred near-Earth object records from NASA) stored two ways: once as a single native JSON column per row, and once decomposed into individually typed columns (a VARCHAR for the designation, a DATE, several FLOAT columns, and so on). The decomposed, typed version came out roughly 40% smaller on disk in that test (three 16 KB pages versus five), which the book attributes mostly to the raw JSON syntax itself, the braces, brackets, colons, and whitespace, adding overhead the typed columns don't carry. Reading a single column back out was noticeably faster once cached in memory on the typed version too. Once both were properly indexed (which, for the JSON column, meant adding a generated virtual column extracted from the JSON path and indexing that), a single-row lookup came out close to even between the two approaches. The upshot, stated plainly: raw JSON storage tends to cost you real space and some query speed against the same data modeled as ordinary columns, and whether that trade is worth the convenience depends heavily on how often you'll actually query it and at what scale.

6. Choosing identifiers

An identifier is however you refer to one specific row, and it's frequently some or all of a table's primary key. It deserves outsized care for a structural reason: identifier columns get compared constantly (in joins and lookups), and because they're commonly reused as a foreign key in other tables, the type you pick for an identifier is very often also the type you're committing those other tables to. Once you've picked a type, keep it consistent across every related table, including matching properties like UNSIGNED, because mismatched types in a join can hurt performance and can also trigger implicit type conversions that produce hard-to-spot bugs, sometimes long after anyone remembers the columns don't quite match.

Integer types are generally the best identifier choice: they're fast to compare and work naturally with AUTO_INCREMENT, the attribute that has MySQL hand out the next integer automatically on every insert (useful for something like generating sequential invoice numbers). The one thing to get right up front is sizing the type for how much the table will actually grow; there are real, repeated stories of unplanned downtime caused by a table simply running out of room in its identifier's integer type.

ENUM and SET are usually a poor identifier choice, but there's a legitimate exception: a small, static "definition" or "lookup" table (say, one row per product category) can reasonably use an ENUM as its own primary key, mirroring an ENUM column used elsewhere, so you can hang descriptive text or display labels off that lookup table. Outside that narrow pattern, avoid using ENUM or SET as an identifier.

String identifiers should generally be avoided too, mainly because they take more space and are slower to compare than integers. The sharpest caution is around identifiers generated by MD5(), SHA1(), or UUID(): each new value lands at an effectively random position across a huge space, and that randomness is expensive in three separate ways. It slows inserts, because the new value has to be written into a random spot in every index built on it, which can force pages to split and scatter a clustered table's rows around on disk. It slows selects, because rows that are logically close together end up physically far apart. And it hurts caching broadly, because caches rely on recently- or frequently-used data clustering together (this is called locality of reference); if a random identifier spreads "hot" data evenly across the whole table, there's no small chunk of it that's worth keeping in memory, and if the active working set doesn't fit in memory at all, you get a steady stream of cache misses. If you do need to store UUID-style values, strip the dashes at minimum, or better, convert them to a compact 16-byte value with UNHEX() and store that in a BINARY(16) column, converting back for display with HEX(). It's also worth noting this isn't an absolute rule: on some very large, heavily-written tables, that same randomness can actually help spread writes out and avoid a single "hot" insertion point, so the trade-off can flip at extreme write volumes. For the overwhelming majority of schemas, though, a sequential integer identifier is the simpler and faster default.

7. Common schema design gotchas in MySQL

Beyond individual column choices, a few whole-schema patterns cause repeat trouble specifically in MySQL. Too many columns can be more costly than it looks: MySQL's storage engine layer moves rows between the server and the engine in a raw row-buffer format, and the server then has to decode that buffer into individual columns, a conversion InnoDB's row format always has to do. That conversion cost scales with the number of columns, not just the number actually used in a query, to the point that extremely wide tables (hundreds of columns) have been observed causing real, otherwise-hard-to-explain CPU pressure even when most of those columns go untouched.

Too many joins is the other big structural trap, and the entity-attribute-value (EAV) pattern, storing every property as its own row instead of its own column, is the classic offender because it leans on many self-joins to reassemble a single logical record. MySQL enforces a hard limit of 61 tables in a single join, and EAV-style schemas have genuinely hit that ceiling in practice; well before that limit, though, the cost of planning and optimizing a query with many joined tables can already become a real problem. A rough rule of thumb: aim for a dozen or fewer tables per query if you need it to run fast under real concurrency.

Two related traps involve ENUM and SET specifically. The first, sometimes called the all-powerful ENUM, is using an ENUM whose values are themselves just stringified numbers, something like country ENUM('0','1','2', ...). That's a sign the column should really just be an integer, foreign-keyed to a proper lookup table, in any database, not just MySQL. The second, the ENUM in disguise, is reaching for SET when you actually meant ENUM, for example a column defined as is_default SET('Y','N') NOT NULL DEFAULT 'N'. Since a flag almost never needs to be both "Y" and "N" at the same time, that should almost always be an ENUM (one value from the list) rather than a SET (any combination of values from the list).

Finally, don't over-correct on NULL. The earlier advice to avoid NULL where possible doesn't mean never using it: sometimes a genuinely unknown value is better represented as NULL than as a magic constant like -1 standing in for "unknown," since leaning on a fake sentinel value from inside the normal range of a type tends to complicate application code and quietly introduce bugs. A commonly seen anti-pattern in the other direction is a column like dt DATETIME NOT NULL DEFAULT '0000-00-00 00:00:00', where a bogus all-zero placeholder date causes its own headaches; MySQL's SQL_MODE setting can be configured to reject nonsense dates like that outright, which is especially worth doing on a new application before any bad data has a chance to accumulate. One more MySQL-specific detail worth knowing: MySQL does include NULLs in its indexes, which is different from Oracle, which excludes non-values from its indexes entirely; if you're used to another database's behavior around NULL and indexing, it's worth double-checking MySQL's on this point rather than assuming. It's also worth a quick word of caution about schemas nobody designed by hand: schema-migration tools and ORMs (object-relational mapping libraries) that autogenerate a schema for you have a track record of producing genuinely bad ones, oversized VARCHAR columns used for everything, or mismatched types on columns that get joined together, so a schema you didn't write yourself is worth a deliberate second look before it goes anywhere near production traffic at scale.

Why it matters

These choices compound. A column that's a few bytes too wide, multiplied across every row, every secondary index that copies it, and every table that references it as a foreign key, adds up to real disk, memory, and cache pressure at scale, even though nothing about it is technically "wrong." Identifier sizing is where this gets sharpest, because it's genuinely easy to underestimate growth when a table is new and small. As one real, independently verifiable example: GitLab's own public issue tracker shows that one of the busiest tables behind GitLab.com, ci_builds, was still running on a 32-bit integer primary key years into the product's life, and by their own tracked measurements it had already climbed past half of that type's roughly 2.1-billion-row ceiling, with their own forecast projecting the column could run out sometime between September 2021 and May 2022 if left alone. Fixing it meant a carefully staged migration of a live, massive, constantly-written table to a wider integer type, exactly the kind of "painful and time-consuming" schema surgery the smaller-is-better guidance warns you to plan around up front instead. (Worth flagging plainly: GitLab.com's database is PostgreSQL, not MySQL, so this isn't a MySQL-specific anecdote, but the underlying math, a fixed-width integer identifier has a hard ceiling that a fast-growing table can actually reach, applies identically to MySQL's own INT type.) This is also exactly the kind of thing the next chapters build on: how a schema is indexed (covered next) and how the query optimizer plans around it (covered after that) both depend heavily on the column types and identifier choices made here.

Remember this

  • Smaller and simpler types are usually faster and cheaper, but "smaller" means "sized for real growth," not "as small as possible today." Resizing a type across a live schema later is painful.
  • NOT NULL by default is a reasonable habit, but it's a small optimization, not an emergency; don't go hunting through a working schema for nullable columns without evidence they're actually a problem.
  • VARCHAR saves space but can fragment on update; CHAR avoids that fragmentation for short or frequently-changed fixed-length values.
  • Identifier types deserve extra care because they get reused as foreign keys everywhere: keep types matching exactly across related tables, size integer identifiers for real growth, and be wary of random string identifiers (UUID, MD5, SHA1) because of their effect on inserts, reads, and caching.
  • A few MySQL-specific patterns (very wide tables, EAV-style many-join schemas, ENUM/SET misuse, all-zero date placeholders) show up again and again as real-world performance traps.

Try it yourself

  1. Compare integer types by actual bytes, not theory. Create two copies of the same small table (a few thousand rows is plenty) that differ only in one column's type, once as INT and once as TINYINT UNSIGNED or BIGINT, load identical data into both, then run SHOW TABLE STATUS (or, on SQLite, compare file sizes with the same row counts) and compare Data_length. Done when: you can state the byte difference per row and multiply it out to the full table.
  2. Try to break NOT NULL on existing data. Create a nullable column, insert a few rows including at least one explicit NULL, then run ALTER TABLE ... MODIFY COLUMN ... NOT NULL. Done when: you've seen the exact error MySQL gives you, and you've fixed it two different ways, once by backfilling a real default value and once by deleting the offending row, and can explain why you'd pick one approach over the other in a real system.
  3. Watch CHAR strip trailing spaces and VARCHAR keep them. Create a CHAR(10) and a VARCHAR(10) column, insert the same handful of values with leading and trailing spaces into each, then retrieve both with CONCAT("'", col, "'") so the spaces are visible. Done when: you can show the two results side by side and explain, in your own words, why the difference exists.
  4. Benchmark a join before and after converting to ENUM. Build a small table (a few hundred thousand rows if you can generate them) with a narrow, low-cardinality VARCHAR column used in a self-join or a join to a second copy of the table, time it, then convert that column to ENUM and time the same join again. Done when: you have real, your-own numbers (not the book's) for VARCHAR-to-VARCHAR versus ENUM-to-ENUM on your own hardware, and you understand why they might differ from what a benchmark on someone else's machine and dataset showed.
  5. Store an IP address as a string and as an integer, and compare. Create one table with a VARCHAR(15) IP column and another with an INT UNSIGNED column, insert the same set of addresses (converting with INET_ATON() for the integer version), then compare storage with SHOW TABLE STATUS and try a range query (all addresses between two values) on each. Done when: you can explain, from what you saw, why "it's really just a number" changes both the storage and the query.
  6. Feel the difference between sequential and random primary keys. Create two tables, one with an AUTO_INCREMENT INT primary key and one with a CHAR(36) UUID-style primary key (or a BINARY(16) one if you want to try the compact form), insert the same large batch of rows (tens of thousands, generated in a loop) into each, and time the inserts. Done when: you've observed a real timing difference (however small on your machine) and can explain it using the "where does a new value land" idea from this digest, not just recite it.
