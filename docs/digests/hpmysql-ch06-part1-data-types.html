HIGH PERFORMANCE MYSQL · CH.6 DIGEST (PART 1)

Choosing the Right Data Type in MySQL

Every column you create is a small, permanent bet: how much space it uses, how fast MySQL can compare and sort it, and how painful it'll be to change later. Once you see the pattern behind MySQL's data types, most of the "which type should I use" questions answer themselves, and you'll also spot the schema habits that quietly cause trouble down the line.

In one line

MySQL gives you many ways to store the same kind of value, and the type you pick trades off storage space, comparison speed, and how much room you have to grow, so the smallest, simplest type that can honestly hold your data (and won't box you in later) is almost always the right call.

The big idea

Picking a data type isn't just a formality before CREATE TABLE works. The type decides how many bytes each value costs on disk, in memory, and in the CPU cache, how expensive comparisons and sorts on that column are, and what MySQL will and won't let you do with it later. Get it right and queries run faster with less hardware. Get it wrong (a string where an integer would do, a column so generous it wastes memory on every sort) and you pay for it quietly, row after row, until the table is too big to fix without downtime. This first half of the chapter is about making that choice well, and about the handful of specific schema habits that tend to bite people in MySQL.

Key terms

  • Signed / unsigned — whether an integer column can hold negative numbers (signed) or only zero and up (unsigned). Both use the same storage space; unsigned just spends the whole range on positive numbers, roughly doubling the usable ceiling.
  • VARCHAR — a variable-length string type. It only uses as much space as the actual value needs, plus 1 or 2 extra bytes to record the length.
  • CHAR — a fixed-length string type. MySQL always reserves the full declared width for it and strips trailing spaces when the value is stored.
  • BLOB / TEXT — string types built for large values (binary data for BLOB, character data with a collation for TEXT). MySQL treats each value as its own object rather than an ordinary column value.
  • ENUM — a column that can hold exactly one value from a small, predefined list of strings. MySQL stores it internally as a compact integer, not as text.
  • SET — like ENUM, but the column can hold zero or more values from the list at once, packed together as bits.
  • BIT — a type for storing raw true/false bits directly in a column, up to 64 of them.
  • DATETIME / TIMESTAMP — MySQL's two main "date and time together" types. They store the same kind of information but trade off storage size, date range, and time zone awareness against each other.
  • JSON (data type) — a native MySQL column type that stores a JSON document as a single value and lets you query and index inside its structure.
  • Generated column — a column MySQL computes automatically from other columns in the same row, instead of you writing to it directly. Useful for pulling a value out of a JSON column so it can be indexed.
  • Identifier — the column (or columns) you use to refer to a specific row, most often the primary key, and often copied into other tables as a foreign key.
  • AUTO_INCREMENT — a column attribute that has MySQL generate the next integer automatically each time a row is inserted.
  • EAV (entity-attribute-value) — a schema pattern that stores every property of every object as its own row instead of its own column. Flexible, but it multiplies the number of joins you need to reassemble one object.

How it works

Before picking any specific type, it helps to know the three habits of mind the chapter keeps coming back to. Smaller is usually better: a smaller type is generally faster because it uses less space on disk, in memory, and in the CPU cache, and needs fewer CPU cycles to process. The catch is that changing a type's range later, once it's used across a schema, can be a painful, time-consuming operation, so if you're unsure, pick the smallest type you're confident you won't exceed rather than guessing low on purpose. Simple is good: integers are cheaper to compare than characters, because character sets and collations (the rules for sorting and comparing text) make character comparisons more complicated. That's part of why the chapter recommends storing dates, times, and IP addresses in purpose-built types instead of as strings. Avoid NULL when you can: a lot of columns end up nullable by default even when the application never stores an absent value there. Nullable columns make indexes, index statistics, and comparisons harder for MySQL to optimize, and use a bit more storage, though the chapter is careful to note the performance gain from fixing existing nullable columns is usually small, so it's not worth chasing unless you know it's causing a real problem.

One more housekeeping note before the specifics: MySQL supports aliases for many types for compatibility, like INTEGER (maps to INT), BOOL (maps to TINYINT), and NUMERIC (maps to DECIMAL). These don't affect performance; running SHOW CREATE TABLE will show you the base type MySQL actually stored, not the alias you typed.

1. Whole numbers: the integer family

If you're storing whole numbers, MySQL gives you five integer types: TINYINT, SMALLINT, MEDIUMINT, INT, and BIGINT, using 8, 16, 24, 32, and 64 bits of storage respectively (1, 2, 3, 4, and 8 bytes). Each type can hold values from −2(N−1) to 2(N−1)−1, where N is the number of bits. Add the UNSIGNED attribute and you drop negative numbers entirely, which roughly doubles the positive ceiling: a plain TINYINT holds −128 to 127, while a TINYINT UNSIGNED holds 0 to 255. Signed and unsigned versions use identical storage and have identical performance, so the choice is purely about which range fits your data.

A subtlety worth knowing: your column's declared size decides how MySQL stores the value, but the computations MySQL performs on integers generally use 64-bit BIGINT math internally (with a few exceptions, like some aggregate functions that use DECIMAL or DOUBLE). Also, if you see something like INT(11), that number in parentheses is just a display width hint for MySQL's own interactive tools; it does not restrict the range of values the column can legally hold. For storage and computation, INT(1) and INT(20) are identical.

2. Real numbers: FLOAT, DOUBLE, and DECIMAL

Real numbers (numbers with a fractional part) come in two flavors: approximate and exact. FLOAT and DOUBLE do standard floating-point math, which is approximate; FLOAT uses 4 bytes of storage, and DOUBLE uses 8 bytes with greater precision and range. As with integers, the column's type controls storage, but MySQL uses DOUBLE internally for its own floating-point calculations regardless of which one you declared.

Because of its extra space and computational cost, the guidance is to reach for DECIMAL only when you need exact results for fractional numbers, the classic example being financial data. Interestingly, for very high-volume cases, the chapter points out an alternative: store the amount as a BIGINT representing a multiple of the smallest currency fraction you care about. If you need to track dollar amounts to the ten-thousandth of a cent, you can multiply every amount by a million and store the result as a BIGINT, which sidesteps both floating-point imprecision and the cost of exact DECIMAL math. DECIMAL can also simply store whole numbers too big for BIGINT, if you ever need that.

3. String types: VARCHAR vs. CHAR

A caveat before this section: exactly how string values are stored on disk and in memory depends on the storage engine, and this discussion (like the rest of this chapter) assumes InnoDB. If you're on a different engine, check its documentation.

VARCHAR stores variable-length strings and is the most common string type, because it only uses as much space as the value needs. It spends 1 or 2 extra bytes recording each value's length (1 byte if the column's max length is 255 bytes or less, 2 bytes above that): a VARCHAR(10) uses up to 11 bytes in the latin1 character set, and a VARCHAR(1000) uses up to 1,002 bytes. The trade-off is that because rows are variable length, updating a value can make the row grow and no longer fit where it was; what happens next is storage-engine dependent (in InnoDB, that can mean splitting a page to fit the row). VARCHAR tends to be the right call when the max length is much bigger than the typical length, updates are rare so fragmentation isn't a concern, or you're using a multi-byte character set like UTF-8.

CHAR is fixed-length: MySQL always reserves the declared number of characters, strips trailing spaces on storage, and pads with spaces for comparisons. That makes it a good fit for short, uniform-length values, the chapter's example is storing an MD5 hash of a password, where every value really is the same length. CHAR also resists fragmentation on frequent updates (in InnoDB) since the row size never changes, and for very short columns it can beat VARCHAR outright: a CHAR(1) holding only 'Y' or 'N' uses 1 byte in a single-byte character set, while the equivalent VARCHAR(1) uses 2 bytes because of its length byte. One behavior worth remembering: if you store 'string3 ' (with a trailing space) in a CHAR(10) column, MySQL strips the trailing space when it's stored, so you get back 'string3'; store the same value in a VARCHAR(10) and the trailing space survives.

Their binary siblings, BINARY and VARBINARY, store raw bytes instead of characters. MySQL pads BINARY with the zero byte (\0) rather than spaces, and doesn't strip it on retrieval, so be careful if the exact byte length matters to you downstream. Binary types compare byte by byte instead of character by character, which sidesteps collation rules entirely and is generally faster.

Generosity can be unwise. Storing 'hello' takes the same space in a VARCHAR(5) and a VARCHAR(200) column. But the bigger declared column can still cost you: MySQL often allocates fixed-size chunks of memory to hold values internally, so an oversized column can use far more memory than needed, especially for sorting or for operations that build in-memory (or on-disk) temporary tables. The chapter's advice is simple: allocate only as much space as you actually need.

4. BLOB and TEXT: large values, handled differently

BLOB (binary strings) and TEXT (character strings, with a character set and collation) are each really families of types by size: TINYTEXT, TEXT, MEDIUMTEXT, LONGTEXT, and the matching TINYBLOB, BLOB, MEDIUMBLOB, LONGBLOB (plain BLOB and TEXT are just synonyms for the smallest size in each family). Unlike other types, MySQL handles each BLOB/TEXT value as an object with its own identity; storage engines often store them specially, and InnoDB may move large values into a separate "external" storage area outside the row. Each value costs 1 to 4 bytes inside the row itself, plus whatever external storage the actual value needs.

Two limitations worth knowing before you reach for BLOB/TEXT: MySQL sorts these columns by only the first max_sort_length bytes, not the full value, and it can't index their full length or use an index for sorting on them. And a practical caution from the text: if you're tempted to store uploaded images as BLOB data to keep everything in one place, know that as that data grows, operations like schema changes get slower and slower because of it. The chapter's recommendation is to write large binary assets like images to a separate object store and keep only the location or filename in the table.

5. ENUM and SET: compact, but with sharp edges

An ENUM column stores one value from a predefined list of strings, packed internally into 1 or 2 bytes as an integer representing that value's position in the list you defined. This has a real, sometimes-surprising consequence: an ENUM column sorts by that internal integer, not alphabetically by the string. If you defined ENUM('fish','apple','dog'), ordering by the column sorts as fish, apple, dog (definition order), not alphabetically. You can work around it by defining the values in the order you want them to sort, or by forcing an explicit order with ORDER BY FIELD(...), though that prevents MySQL from using an index for the sort.

SET is the multi-value sibling: a column can hold zero or more values from the predefined list at once, stored as a packed set of bits, with helper functions like FIND_IN_SET() to query it.

The chapter backs the "compact but has overhead" trade-off with a real benchmark. Starting from a roughly 110,000-row, ~10 MB InnoDB table (small enough to fit entirely in memory) with a service column (5 distinct values, average length 4 characters) and a method column (71 distinct values, average length 20 characters), they compared joining two copies of the table on those columns, once as VARCHAR, once converted to ENUM:

  • VARCHAR joined to VARCHAR: 2.6 queries/second
  • VARCHAR joined to ENUM: 1.7 queries/second
  • ENUM joined to VARCHAR: 1.8 queries/second
  • ENUM joined to ENUM: 3.5 queries/second

ENUM-to-ENUM joins came out fastest, but mixing ENUM with VARCHAR was actually slower than plain VARCHAR-to-VARCHAR. Converting also shrank the table's Data_length by about a third and roughly halved the primary key's size, which (being InnoDB) shrinks every other index on the table too, since they all reference the primary key. Caveat: these are the book's own numbers from its own hardware and test table, meant to show the shape of the trade-off, not a guarantee you'll see the same ratios. The takeaway the chapter draws is practical: converting to ENUM is a good idea as long as you're not forced to join it against VARCHAR columns elsewhere. It's also worth flagging early: changing which values are legal in an ENUM always requires a schema change (an ALTER TABLE), which matters if that list changes often and you don't yet have a smooth way to run schema changes (more on that in Part 2).

6. Date and time: DATETIME vs. TIMESTAMP

MySQL's finest time granularity is the microsecond, and for most temporal types there's only one real option. The interesting choice is when you need date and time together: MySQL offers DATETIME and TIMESTAMP, which store the same kind of information but differ in range, storage size, and time zone behavior.

DATETIME covers the year 1000 to the year 9999 at microsecond precision, stores the date and time packed into an integer in YYYYMMDDHHMMSS format independent of time zone, and uses 8 bytes of storage. By default MySQL displays it in a sortable, unambiguous format like 2008-01-16 22:37:08.

TIMESTAMP stores the number of seconds elapsed since midnight, January 1, 1970 GMT (the same idea as a Unix timestamp), using only 4 bytes, which gives it a much smaller range: 1970 to January 19, 2038. The value you see also depends on time zone settings (server, OS, and client connection all play a part), so a stored value of 0 could display as 1969-12-31 19:00:00 in a five-hour-behind-GMT time zone. That's a meaningful difference from DATETIME: TIMESTAMP preserves the value relative to whatever time zone is in use, while DATETIME preserves the literal text you stored. By default, MySQL also gives the first TIMESTAMP column in a table special behavior: it's set to the current time on insert if you don't specify one, and updated to the current time whenever the row changes, unless you assign a value explicitly (both behaviors are configurable). TIMESTAMP columns are also NOT NULL by default, unlike every other type.

There's also a third path some teams take: skip both and store date/time as a plain integer, the Unix epoch in UTC (seconds since 1970-01-01). A signed 32-bit INT gets you to 2038, the same wall TIMESTAMP hits; an unsigned 32-bit INT stretches that to 2106; 64-bit goes well beyond either. The chapter is candid that this is more a matter of taste than a settled best practice, so treat it as one more option to weigh, not a default.

7. Bit-packed types: BIT and SET for flags

BIT lets a column store one or many true/false values directly as bits (BIT(1) is a single bit, up to BIT(64)). In InnoDB specifically, each BIT column is stored as the smallest integer type large enough to hold the bits, so you don't actually save storage space there. MySQL also treats BIT as a string type rather than a numeric one: retrieving a BIT(1) gives you a string containing the raw binary value, but in a numeric context you get the equivalent number, which the chapter calls out as genuinely confusing and generally recommends using BIT with caution, or avoiding it in favor of TINYINT for most applications.

SET is the more practical option for combining several true/false flags into one column: it's stored as a packed set of bits internally, uses storage efficiently, and comes with query helpers like FIND_IN_SET(). An alternative some teams prefer is packing bits into a plain integer column (say, a TINYINT) and using bitwise operators, with named constants defined in application code for each bit. The advantage over SET is you can change what each bit means without an ALTER TABLE; the drawback is queries get harder to read, since a bare integer doesn't tell you what bit 5 represents. A classic use case for either approach is an access-control list where each bit or SET element stands for a permission like "can read" or "can write."

8. The JSON data type

MySQL has a native JSON column type for storing a JSON document and querying into its structure directly, which is convenient when data genuinely varies in shape. The chapter tests it against typed SQL columns with a real, small dataset: 202 near-Earth asteroids and comets from NASA, tested on MySQL 8.0.22 on a four-core, 16 GB VM. One schema stored the whole record as a single json_data JSON column; the other broke it into 10 properly typed columns (varchar(30), date, several float columns, char(3), and so on).

On storage, the JSON version used more space: Data_length came out to 81,920 bytes (five 16 KB pages) for the JSON table versus 49,152 bytes (three 16 KB pages) for the typed-columns table, since JSON's braces, brackets, colons, and whitespace all cost extra bytes. On speed, a plain SELECT of one field ran close either way (about 1.14 ms uncached / 0.44 ms cached for the SQL column, versus about 1.13 ms uncached / 0.80 ms cached reading the same field out of the JSON document with the -> operator). The bigger gap showed up on indexed single-row lookups: after adding a normal index to the SQL column, a lookup ran in 0.33 ms. To give JSON a fair shot at the same trick, they added a generated column that extracts the field from the JSON document and indexed that instead; with that in place, an indexed JSON lookup ran in about 0.4 ms, close to (but still a bit behind) the SQL column's 0.33 ms.

The conclusion drawn isn't "never use JSON," it's that the decision comes down to whether the convenience of storing raw JSON is worth more to you than the extra space and the speed gap, and that the speed difference compounds fast if you're running the query millions or billions of times a day.

9. Choosing identifiers

An identifier is how you refer to a specific row, often some or all of the primary key. Because identifier columns get compared constantly (joins, lookups) and frequently get copied into other tables as foreign keys, the type you choose here matters more than for an average column, and it's usually worth using the exact same type (including UNSIGNED) in every related table, since mismatched types in a join can cause performance problems or confusing implicit conversions.

Integers are usually the best identifier type, since they're fast to compare and work with AUTO_INCREMENT, the attribute that has MySQL generate the next integer automatically on each insert (handy for something like sequential invoice numbers). Size it for where the data is actually headed: the chapter notes there's more than one real story of system downtime from unexpectedly running out of integers on an identifier column, which is exactly the kind of thing worth checking before a table grows large, not after.

ENUM and SET are generally a poor identifier choice, though they can work fine as the primary key of a small, static "definition" or "lookup" table holding things like status or type values.

String identifiers should generally be avoided because they cost more space and are slower to compare than integers. The chapter is especially pointed about "random" strings, the kind produced by MD5(), SHA1(), or UUID(): each new value lands in an arbitrary spot across a huge space, which slows INSERTs (the new value lands in a random spot in every index, causing page splits and random disk access, and fragmenting the clustered index in engines like InnoDB that physically store rows in primary-key order) and slows lookups too (logically related rows end up scattered across disk and memory instead of sitting near each other, which defeats the locality of reference that makes caching effective in the first place). One nuance worth keeping: for some very large, heavily-written tables, that same randomness can actually help by spreading writes out and avoiding "hot spots," so it's a genuine trade-off, not a flat rule. If you do need to store UUIDs, the chapter's tip is to strip the dashes or, better, convert the value to a 16-byte number with UNHEX() and store it in a BINARY(16) column, reading it back with HEX().

10. A caution about autogenerated schemas

Migration tools and frameworks that autogenerate a schema for you can produce real performance problems: the chapter mentions patterns like defaulting every column to a large VARCHAR, or using mismatched types for columns that get compared in joins. Its advice is to double-check any schema you didn't design by hand. ORMs (object-relational mappers) get a similar caution: some are flexible enough to store any kind of data in any kind of backend, which usually means they don't lean on the strengths of whichever database you're actually using, and some even store every property of every object as its own row (sometimes with timestamp-based versioning, multiplying that further). It's understandable why this appeals to developers who'd rather not think about storage, but the chapter's blunt take is that hiding that complexity usually doesn't scale, so it's worth testing on a realistically large dataset before you trust the abstraction.

11. A special case: IP addresses

People often reach for a VARCHAR(15) to store an IPv4 address, but an address is really an unsigned 32-bit integer; the dotted-quad notation (like 192.168.1.1) is just a human-readable way to write that same number. Storing it as an unsigned integer shrinks the space from around 16 bytes (VARCHAR) down to 4 bytes, and MySQL provides INET_ATON() and INET_NTOA() to convert between the two representations. If you're worried about losing readability when eyeballing the table, the chapter's suggestion is to build a view that presents the human-readable form.

12. Schema design gotchas in MySQL

Past good general database design, there are a handful of problems the chapter has specifically observed showing up in real MySQL schemas.

Too many columns. MySQL's storage engine API copies rows between the server and the storage engine in a row buffer format, which the server then decodes into columns; that decoding has a real cost, and it grows with the number of columns. InnoDB's row format always requires this conversion. The chapter mentions tracing high CPU consumption for a customer with tables that had hundreds of columns, even when only a handful of those columns were actually being used, so if you're planning for very wide tables, expect the server's performance characteristics to shift.

Too many joins. The entity-attribute-value (EAV) pattern, storing every property as its own row instead of its own column, is called out as a universally bad pattern that fits MySQL especially poorly, because EAV designs need many self-joins and MySQL has a hard limit of 61 tables per join; the chapter notes EAV databases sometimes hit that ceiling. Even well below 61 tables, the cost of planning and optimizing a heavily-joined query can become a real problem. As a rough rule of thumb, the chapter suggests a dozen or fewer tables per query if you need queries to run fast under high concurrency.

The all-powerful ENUM. The chapter shares a real example it calls out as a bad pattern: a column defined as something like country ENUM('0','1','2', ... ,'31'), sprinkled throughout a schema. That should almost always be an integer, foreign-keyed to a proper lookup ("dictionary") table instead.

ENUM in disguise. It's easy to reach for SET when you meant ENUM. The chapter's example is a column defined as is_default SET('Y','N') NOT NULL DEFAULT 'N': if the value genuinely can't be both true and false at once, that should be an ENUM, not a SET.

NULL, not invented here. The earlier advice to avoid NULL where possible doesn't mean avoid it always. Sometimes NULL genuinely is the right way to represent "unknown," and picking a magic constant instead (like -1 for an unknown integer) can complicate your code and quietly introduce bugs. One anti-pattern the chapter flags directly: a column like dt DATETIME NOT NULL DEFAULT '0000-00-00 00:00:00', where the all-zeros default is a bogus stand-in for "no value" that can cause real problems downstream (MySQL's SQL_MODE can be configured to reject nonsense dates like this, which is worth doing especially on a new application). One more difference worth knowing: MySQL does index NULL values, which the chapter contrasts with Oracle, which excludes them from indexes entirely.

Why it matters

This is the layer everything else in MySQL performance sits on top of. A table built from small, well-chosen types uses less disk, fits more of itself in memory and cache, and lets comparisons and sorts run faster, all without changing a single query. And because these choices are expensive to reverse (an identifier type used across a dozen foreign-key columns, an ENUM baked into application logic, a random UUID primary key already fragmenting a multi-terabyte table), getting them right early is far cheaper than fixing them once the table matters to production traffic. The next piece of this same puzzle, once your types are sound, is indexing: how MySQL actually finds the rows you asked for fast.

Remember this

  • Pick the smallest data type that can honestly hold your data's range, but size identifier columns for real future growth, since changing a type used across a schema later is a painful operation, and running out of room on an AUTO_INCREMENT id has caused real downtime.
  • VARCHAR trims to fit and CHAR doesn't; VARCHAR usually wins except for short, uniform-length, frequently-updated values (like a fixed-length hash).
  • ENUM and SET are compact but store integers under the hood: they sort by definition order, not alphabetically, and every new legal value requires a schema change.
  • DATETIME and TIMESTAMP look interchangeable but trade off storage size (8 vs. 4 bytes), date range, and time zone awareness against each other; pick based on which trade-off you can live with.
  • Integers make the best identifiers. Random string identifiers like UUIDs scatter rows across disk and memory, which slows inserts, lookups, and caching alike (with the narrow exception of deliberately spreading writes on very large, heavily-written tables).

Try it yourself

  1. Reproduce the CHAR vs. VARCHAR trailing-space behavior. Create one table with a CHAR(10) column and one with a VARCHAR(10) column, insert the same few strings with leading and trailing spaces into each, and select them back wrapped in quotes (for example with CONCAT). Done when: you've seen CHAR strip a trailing space that VARCHAR keeps, and can explain why in your own words.
  2. Find an integer type's ceiling for yourself. Create a table with one column per integer type (TINYINT, SMALLINT, MEDIUMINT, INT, BIGINT), then try inserting a value one past each type's documented max. Done when: you've triggered an out-of-range error on at least one column and can state that type's max value from memory afterward.
  3. Run your own mini ENUM-vs-VARCHAR comparison. Build two small tables that are identical except one status-like column is VARCHAR and the other is the equivalent ENUM, populate each with a few thousand generated rows, and time a query that filters or joins on that column. Done when: you have your own before/after timing, even on a tiny dataset, and can say which was faster for your test.
  4. Watch DATETIME and TIMESTAMP disagree across time zones. Create a table with one DATETIME and one TIMESTAMP column, insert the same moment into both in one row, then change your session's time zone (SET time_zone = ...) and select the row again. Done when: you've watched the TIMESTAMP value shift with the time zone change while the DATETIME value stays exactly as you entered it.
  5. Compare a JSON column to typed columns on a tiny dataset. Take 15-20 small JSON records of your own, load them once into a single JSON column and once into properly typed columns, then compare each table's size and the time of a simple SELECT against each. Done when: you have your own size and speed comparison written down, even if the numbers are small and noisy.
  6. Store an IP address the space-efficient way. Add one VARCHAR(15) column and one INT UNSIGNED column to a test table, insert the same address into both (using INET_ATON() for the integer version), and read the integer one back with INET_NTOA(). Done when: you can convert an address to its integer form and back again without looking anything up.

Go deeper

A natural next question once your types are solid: how does MySQL actually use them to find rows quickly? Several choices made here directly shape how well an index performs later, a small identifier type makes for a smaller, faster index; an ENUM's internal integer affects how it can be indexed and joined; a random string identifier fragments the very index built on top of it. That's the subject this chapter sets up next.
