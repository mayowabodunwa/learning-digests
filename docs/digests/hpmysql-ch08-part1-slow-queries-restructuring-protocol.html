SQL · CH.8 DIGEST (PART 1)

Why Queries Are Slow: Asking for Less, Splitting Work, and the Road a Query Travels

Chapters 6 and 7 gave you a schema and indexes. This chapter asks the next question: even with those in place, why can a query still crawl? Part 1 covers the mindset (it's all about response time), the two checks that find most slow queries, three ways to restructure a query, and the first half of "how MySQL actually runs a query": the conversation between client and server.

In one line

A slow query is almost always doing too much work (too many rows, too many columns, too many times), so you shrink, split, or reshape the work, and it helps to know the exact road a query travels from your app to the server and back.

The big idea

Think of a query as a to-do list the server has to get through, not a magic spell. Each item on that list (talking over the network, parsing, planning, asking the storage engine for rows, sorting, sending results) takes time. To make the query faster you have three options and only three: remove an item, do it fewer times, or do it faster. The source boils the whole chapter down to exactly that.

The most common reason for a slow query is also the simplest: it touches more data than it needs. So Part 1 starts with two questions you can ask of any slow query. First, is my application asking for more than it uses? Second, is the server reading more rows than it needs to produce the answer? After that we look at restructuring, and then at the protocol between client and server, which explains a surprising amount of everyday behaviour (like why LIMIT matters so much).

This part covers the printed pages 191 to 204 of the chapter: the opening, "Why Are Queries Slow?", "Slow Query Basics: Optimize Data Access," "Ways to Restructure Queries," and the start of "Query Execution Basics" up to and including "The MySQL Client/Server Protocol" and "Query States." The optimizer itself (parser, cost, join order, sorting) is Part 2, and the optimizer's limitations plus specific query types are Part 3.

Key terms

  • Response time: how long from sending a query to getting the answer back. The thing users actually feel.
  • Service time: the part of response time the server spends actually working on your query.
  • Queue time: the part spent waiting (for a disk read to finish, for a row lock, and so on). Example: a query that is stuck behind another transaction's row lock has plenty of queue time and almost no service time.
  • Rows examined: how many rows the server had to look at while running the query. Compare with rows returned: how many it sent back.
  • Slow query log: a log MySQL can keep of queries that took longer than a threshold; per the source it records response time, rows examined and rows returned.
  • Access type: how MySQL finds the rows in one table. It shows up as the type column in EXPLAIN output (for example ALL, index, range, ref, const).
  • EXPLAIN: a statement that shows the plan MySQL would use for a query. Example: EXPLAIN SELECT * FROM t WHERE a = 1.
  • Full table scan: reading every row in a table (access type ALL).
  • Covering index: an index that holds every column the query needs, so table rows never have to be read (see Chapter 7).
  • Join decomposition: replacing one multi-table join with several single-table queries and combining the results in your application.
  • Half-duplex: only one side can talk at a time, like a walkie-talkie.
  • Buffering (result set): your database driver pulls the whole answer into its memory before your code starts reading rows.
  • Thread state: a label for what a connection is doing right now (waiting for a query, sorting, and so on).

How it works

First, a grounding paragraph. Everything in a database performance conversation comes back to one number: how long the user waits. A query isn't one thing that is "fast" or "slow"; it's a trip. The request leaves your app, crosses a network, gets read and planned by the server, the server calls into a storage engine (InnoDB, usually) again and again to fetch rows, does any grouping or sorting, and then ships the results back. Each leg of that trip uses some mix of network, CPU, memory and disk. A query is slow because some legs are being done needlessly, too many times, or too slowly. The source is clear that this is a simplified picture, but it is the right habit: always ask where is the time going?

1. The first check: is the application asking for too much?

The source suggests analysing a slow query in two steps. Step one is about what your application requests. Wasted data costs the server extra work, costs network time, and eats memory and CPU on the application server too. The source lists four classic mistakes.

  • Fetching more rows than you need. A frequent assumption (especially from people used to other databases) is that you can run a query returning thousands of rows, read the first ten, and close it, and the server will stop early. In MySQL the server generates the complete result and the client library pulls it all, then your code discards most of it. The fix: add a LIMIT. (Why this happens is in the protocol section below.)
  • Fetching all columns from a join. Writing SELECT * over a three-table join returns every column of all three tables. If you only need one table's columns, write SELECT tablename.* or name the columns.
  • Fetching all columns at all. Treat SELECT * with suspicion. Per the source, it can block covering-index optimizations and adds I/O, memory and CPU overhead. It also makes code fragile when someone changes a table's columns. But the source is balanced: sometimes grabbing everything is a fine trade, for example when one shared piece of code serves many pages or when you cache whole objects in the application. The point is to know what it costs, not to ban it.
  • Fetching the same data repeatedly. Picture a comments page that looks up the profile-picture URL for the commenter on every single comment, even when the same person wrote ten of them. Remember it after the first lookup (cache it) instead of asking again.

Beginner simplification, and its caveat: "SELECT * is bad." It's a good default suspicion, not a law. The source explicitly lists cases where fetching extra columns is a sensible trade.

2. The second check: is the server examining too much?

Once the application only asks for what it needs, look at how much the server reads to build the answer. The source offers three simple cost yardsticks: response time, rows examined, and rows returned. None is perfect, but they roughly track how much data MySQL touches, and all three appear in the slow query log, which is why that log is a good hunting ground.

Response time is two things glued together

Response time = service time + queue time. Service time is actual work. Queue time is waiting. The catch: unless you can measure the two separately (which the source says is usually hard) you can't tell them apart from the total. Common waits are disk I/O and locks, but the source warns not to assume it's only those. A consequence worth remembering: the same query can show different response times under different load, because waiting on locks or a busy disk changes with traffic. So a slow time can be a symptom of a problem elsewhere as well as a cause. The question to ask is: is this response time reasonable for what the query does? The source mentions one method for an upper-bound estimate (called QUBE, from another book by Lahdenmaki and Leach): look at the plan, count the sequential and random I/O operations it implies, and multiply by what your hardware takes per operation. I haven't reproduced that method here; follow the source's reference if you want to learn it.

Rows examined versus rows returned

The ideal is that the server examines only the rows it returns. In practice that's rare. Building a joined row means reading several rows, for example. The source says the ratio of examined to returned is usually small (about 1:1 to 10:1) but can be orders of magnitude bigger. It also warns that rows examined is a rough metric: not all row reads cost the same (short rows are cheaper than long ones, and a row already in memory is far cheaper than one read from disk).

Access types: the ladder from "read everything" to "read one"

For each table in a query MySQL picks an access method, and EXPLAIN shows it in the type column. The source describes the range as: full table scan, then index scan, then range scan, then unique index lookup, then constant. Each is generally cheaper than the one before because it reads less data. You don't have to memorize the names, just the four ideas: scan the whole table, scan a whole index, read a slice of an index (a range), or jump straight to one value. When the access type is poor, the usual fix is to add an index that lets MySQL use a better one.

I checked this on a small made-up database on a local MySQL 8.0 server (an item table of roughly 90,000 estimated rows with an index on sku but not on qty). Same table, two different WHERE clauses:

  • WHERE sku = 'SKU0005': access type ref, using the sku index, estimated rows examined: 400.
  • WHERE qty = 3 (no index on qty): access type ALL (full scan), estimated rows examined: about 91,650, with Extra: Using where.

Those row counts are the optimizer's estimates, not exact counts, and they are from my one table on one version. The shape of the result (a much smaller number with the index) is the lesson.

Three places a WHERE clause can be applied

The source ranks, best to worst, how MySQL can use a WHERE:

  1. Inside the index lookup, at the storage engine layer, so non-matching rows are never touched.
  2. On a covering index (Using index in Extra): the server layer filters entries coming out of the index, but never reads table rows.
  3. After reading the row (Using where in Extra): the server layer reads whole rows from the table, then throws away the ones that don't match.

"Server layer" and "storage engine layer" refer to the two-layer MySQL architecture from Chapter 1: the server parses and plans, and the engine stores and fetches.

A trap: an index doesn't always shrink the work

Here is a point that surprised me. Take a grouping query with no WHERE clause: count the rows per customer. The result might be only 2,000 lines long, but the server still has to look at every row (or at every entry in an index) to count them. An index can make that cheaper per row, but it can't reduce how many rows must be visited, because nothing is being filtered out. I tried it on a made-up orders table (60,000 rows) with an index on customer_id:

  • SELECT customer_id, COUNT(*) FROM orders GROUP BY customer_id: access type index on the customer_id index, Extra: Using index, estimated rows about 60,345. So it read through the entire index to produce 2,000 groups.

Note EXPLAIN gives you only the total rows accessed; it doesn't tell you how many of them ended up contributing to the answer. You have to reason about the query to see that. The source lists these fixes when a huge number of rows is examined for few results: use a covering index, change the schema (for instance a summary table, from Chapter 6), or rewrite the query so the optimizer can handle it better.

3. Ways to restructure a query

The source's advice is to find another way to get what you need. That may mean an equivalent query, a query that returns something slightly different but cheaper, or moving part of the work into application code.

Complex query versus many queries

Old database wisdom says: do as much as possible in one query, because each round trip and each parse was expensive. The source argues this applies less to MySQL: it's designed to connect and disconnect cheaply and to answer small simple queries very fast, and networks are much faster than they used to be. So don't be afraid to split a monster query into a few simple ones if that means less total work. At the same time the source warns about the opposite mistake: 10 single-row queries when one 10-row query would do, or fetching one column at a time. Overall, with all else equal, fewer queries is still the better default, and the call should be made by weighing real costs. (The source quotes throughput figures for simple queries on commodity hardware; they depend on version and hardware, so I don't repeat them as numbers to rely on.)

Chopping up a query

Some jobs touch a huge number of rows, like purging old data. Doing it in one statement can hold locks for a long time, fill up transaction logs, hog resources, block small queries, and (when replicated) cause replication lag. The fix is "divide and conquer": do the same operation in chunks. The source's shape of this is a loop that deletes a limited number of rows (it uses 10,000 as an example) over and over until no rows are affected, optionally sleeping between rounds to spread the load. The source also notes transactional engines may like smaller transactions.

The pseudocode is simple enough to sketch in your own words: repeat: delete up to N old rows; stop when zero were deleted; pause briefly. I confirmed on my small server that DELETE ... WHERE ... LIMIT 50 is valid MySQL and reports 50 rows affected. I didn't measure lock or lag effects; those I'm taking on the source's word.

Join decomposition

Instead of one query joining tag, tag_post and post, you run three small ones: find the tag, find the post ids linked to it, then fetch those posts with an IN (...) list, joining in your application code. It looks wasteful, but the source gives reasons it can win:

  • Caching works better. If the tag object is already cached, skip query one. Posts already cached can be removed from the IN list.
  • Less lock contention in some cases, because each query is short.
  • Easier to scale out. Tables on different servers can't be joined by the database, but your application can combine them.
  • The queries themselves can be cheaper. The source says an IN list lets MySQL sort ids and fetch rows more optimally than a join might.
  • Fewer repeated row reads. A join can read the same row many times (it's a form of denormalization), while doing the join yourself retrieves each row once, which can also cut network traffic and memory.

The source's summary of when it pays off: you cache and reuse data from earlier queries, you spread data across several servers, you swap joins for IN lists on large tables, or the join mentions the same table more than once. Caveat: that is a list of situations where it can help, not a rule that application joins beat database joins. For a typical one-server join with good indexes, the database join is often the better choice, and I haven't measured the claims above myself.

4. Query execution basics: the road a query takes

The source says one of the best investments for getting performance is learning how MySQL optimizes and runs queries, because after that, tuning becomes reasoning from principles. The four-step road is:

  1. The client sends the SQL statement to the server.
  2. The server parses, preprocesses, and optimizes it into a query execution plan.
  3. The execution engine follows the plan by calling the storage engine's API.
  4. The server sends the result back to the client.

Part 2 digs into step 2 and step 3. The rest of Part 1 is about the conversation in steps 1 and 4.

The client/server protocol: one ball, two players

You don't need the protocol's inner details, but you do need the shape. It's half-duplex: at any moment the server is either sending or receiving, never both, and you can't cut a message short. The source's image is a ball tossed back and forth: only the side holding the ball can throw, and once it's thrown, the other side must catch the whole thing before it can answer. There is no flow control in the sense of asking the sender to slow down or stop mid-message.

  • The client sends the query as one packet. That's why the max_allowed_packet setting matters for very large queries (the source says that if a query is too large, the server refuses to receive more and raises an error). On my test server the default value was 67,108,864 bytes (64 MB); that's a default on this one build, not a universal number. I also tried to set it for just my session and MySQL refused, saying the session variable is read-only and to use SET GLOBAL.
  • The server's reply usually spans many packets, and the client must receive the entire result set. It can't say "that's enough." It either waits for all of it and discards what it doesn't need, or disconnects ungracefully. Neither is nice, so use LIMIT properly.

Here's how the source reframes it: the client believes it is pulling rows, but the server is really pushing them as it generates them. The client is drinking from a fire hose.

Buffered versus unbuffered results

Most database libraries let you either (a) fetch the whole result set into memory first, or (b) fetch each row as you read it. The default is generally (a), buffered. This has a subtle effect: until all rows have been fetched, the server can't release the locks and other resources the query holds, and during that time the query shows the "Sending data" state. Buffering lets the library pull everything quickly, so the server finishes and cleans up as fast as possible. Your loop of while (row = fetch()) looks like it's reading from the server row by row, but with a buffered result it's just walking the library's memory.

Buffering is fine for most queries and a bad idea for huge results (lots of memory, slow to start). Turning it off lets you start working on the first rows sooner and use less memory, but the trade-off is that server-side resources stay open while your application takes its time. The source shows how to do this with the old PHP mysql_* functions and with Perl's DBD::mysql. I'm not reproducing those snippets, and the PHP functions it uses belong to an old interface, so check your own language's driver documentation for its unbuffered or "streaming" option. As a harmless way to see the idea, I confirmed that the stock mysql command-line client has a --quick option whose help text says it doesn't cache the result and prints it row by row.

Simplification and caveat: "the default is to buffer." That's what the source says is generally true of client libraries; check your driver, because defaults differ.

Query states: who has the ball?

Every connection (thread) has a state showing what it's doing. The simplest way to see them is SHOW FULL PROCESSLIST. Dozens of states exist and the MySQL manual is the authority on them, but the source lists a handful worth knowing:

  • Sleep: waiting for the client to send a new query.
  • Query: running the query or sending the result back.
  • Locked: waiting for a server-level table lock. Locks implemented inside the storage engine, such as InnoDB row locks, do not put the thread in this state.
  • Analyzing and statistics: checking engine statistics and optimizing the query.
  • Copying to tmp table [on disk]: copying results into a temporary table, probably for a GROUP BY, a filesort, or a UNION. "On disk" means an in-memory temporary table was converted to a disk one.
  • Sorting result: sorting a result set.

The source's takeaway: knowing the basics tells you who has the ball. On a very busy server, a normally brief state (like the statistics one) taking a long time usually means something is wrong.

One discrepancy I found: the source says the states appear "in the Command column." When I ran SHOW PROCESSLIST on MySQL 8.0.46, the columns were Id, User, Host, db, Command, Time, State, Info: Sleep and Query showed up under Command, while the finer-grained states (like "Sorting result") belong in the State column. The state names themselves may differ by version, so verify against the manual for yours. I only saw "init" for my own command and an idle event-scheduler row; I did not reproduce the other states.

Why it matters

This is the "triage" half of query tuning. Before you reach for exotic tricks, ask whether the app is fetching too much, whether the server is reading too much, and whether one huge operation should be many small ones. Those three questions explain a large share of the slow queries you'll meet. The protocol detail also pays off every day: it's why LIMIT is a performance feature (not just a convenience), why a "streaming" driver changes memory use, and why a thread stuck in one state tells you where to look.

It also connects backward and forward. Backward: covering indexes (Ch.7) and summary tables (Ch.6) are the fixes the source names when too many rows are examined. Forward: Part 2 explains the optimizer that decides which access type and join order you actually get.

Remember this

  • Every optimization is one of three moves: do less, do it less often, or do it faster.
  • Two checks first: is the app fetching more than it uses, and is the server examining more rows than it returns?
  • Response time = service time + queue time, and you usually can't see the split without measuring each part.
  • In MySQL the server pushes the whole result and the client can't ask it to stop early, so use LIMIT.
  • An index only helps if it lets MySQL read fewer rows; a GROUP BY with no filter still visits everything.
  • Splitting a query (chunking a purge, decomposing a join) can beat one big statement, but it is a trade you weigh, not a rule.

Try it yourself

  1. The access-type ladder. Make a table of at least 50,000 rows (a recursive CTE can generate them) with one indexed and one unindexed column. Run EXPLAIN for an equality on each, a range on the indexed one, and the primary key. Write down type, key, rows and Extra in a small table. Done when you can explain each row without looking back.
  2. Rows examined vs returned meter. Write a tiny script that takes a query, runs EXPLAIN, and prints the estimated rows examined next to the count your query actually returns, flagging ratios above 10:1. Then try it on the unfiltered GROUP BY case from this digest. Done when it flags the grouping query and you can say why that one is expected.
  3. The purge loop. Make a table with 100,000 old rows. Write a loop (any language) that deletes 5,000 rows at a time with a short sleep, stopping when zero rows are affected. Print the elapsed time and rows deleted per round. Done when you have compared it to a single delete and can say what your measurement did and did not show (you probably won't see lock trouble on an idle laptop).
  4. Join decomposition race. Build three small tables shaped like tag / link / post. Time the one-query join against the three-query version, once with a cache (a plain dictionary) and once without. Done when you have numbers for both and a sentence about which situations favour each.
  5. Buffered vs streaming. Use your language's MySQL driver to read a million-row result twice: buffered and unbuffered (or streaming). Watch your program's memory use and how long until the first row. Done when you can describe the trade-off, and what the server is holding open in the unbuffered case.
  6. Processlist spotter. Open two sessions. In one, run a slow query (for example a big sort); in the other, run SHOW FULL PROCESSLIST repeatedly. Record which Command and State values you see. Done when you can match each observed value to a step of the four-step road in this digest, and note any state the source didn't list.

Go deeper (optional)

Take the slowest query in something you maintain, put it through both checks (what is the app asking for, what is the server reading), and write down the access type for each table. That exercise is the best preparation for Part 2, where the optimizer's choices become visible.
