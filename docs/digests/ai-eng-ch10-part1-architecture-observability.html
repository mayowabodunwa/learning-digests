AI Engineering Architecture: From a Single Model Call to a Full System

Nine chapters of techniques, and now the question every builder hits: how do these pieces fit together into a product? Chapter 10 answers by building an architecture step by step, starting with the simplest possible app (a query goes in, the model's answer comes out) and adding one component at a time, each in response to a real problem. This part covers that architecture (context, guardrails, router and gateway, caches, agent patterns and write actions), then monitoring and observability, then orchestration. Part 2 covers the other half of the chapter: user feedback.

In one line

A production AI application is a model plus a growing set of supporting components (context builders, guardrails, routers, gateways, caches, loops, monitors and an orchestrator), and the right way to build it is to add each one only when a problem justifies it.

The big idea

The chapter's pitch is gradual: start simple, notice what breaks, add a component. The author says this progression is what's commonly seen in production and has been validated at multiple companies, while also being clear that everyone's needs differ, so follow the order that makes sense for your application. Every component buys you something (capability, safety, speed, lower cost) and costs you something (complexity, latency, new ways to fail). So the second theme is visibility: the more parts you have, the more you need monitoring and observability designed in from the start, not bolted on afterwards.

Key terms

  • Context construction: assembling the information the model needs for a query (via retrieval and tools). The chapter compares it to feature engineering for foundation models.
  • Guardrails: checks on inputs and outputs that mitigate risks. Input guardrails protect what goes in; output guardrails catch bad results and decide what to do about them.
  • PII: personally identifiable information. A "PII reverse dictionary" maps placeholders back to the original values.
  • False refusal rate: how often a safety system blocks legitimate requests.
  • Router / intent classifier: a component that predicts what a user wants and sends the query to the right model, tool, FAQ page or human.
  • Model gateway: a unified, controlled layer between your applications and the various models.
  • Exact caching / semantic caching: reusing stored results for identical queries; reusing them for similar queries.
  • Eviction policy: the rule for removing items from a full cache (LRU, LFU, FIFO).
  • Write action: an action that changes the outside world (send an email, place an order, transfer money).
  • Monitoring vs. observability: tracking a system's outputs vs. designing the system so its internal state can be understood from what it emits.
  • MTTD / MTTR / CFR: mean time to detection; mean time to response (resolution); change failure rate.
  • Metrics, logs, traces: aggregated numbers; append-only event records; linked events forming one request's full timeline.
  • Drift: something in the system changing over time (prompts, user behavior, underlying models).
  • Orchestrator: a tool that defines your components and chains them into a pipeline.

How it works

Grounding: the simplest architecture

In its simplest form your application takes a query, sends it to a model, and returns the response. No extra context, no guardrails, no optimization. The "model API" box can be a third-party API or a self-hosted model (Chapter 9 covered building an inference server for the latter). The chapter then lists the progression it will follow:

  1. Enhance the context the model receives (external data and tools).
  2. Add guardrails to protect your system and users.
  3. Add a model router and gateway.
  4. Add caching to cut latency and cost.
  5. Add complex logic (loops) and write actions.

Monitoring/observability and orchestration come after, tying everything together.

Step 1: enhance context

The first expansion is usually helping the system build the right context for each query. As Chapter 6 covered, context can come from retrieval (text, image, tabular) and from tools that gather information through APIs such as web search, news or weather. The chapter calls context construction "like feature engineering for foundation models", and notes that model API providers almost universally support it (file uploads and tool use). They differ in details: how many and what kinds of documents you can upload, retrieval algorithms and chunk sizes, which tools are supported, and whether they run tools in parallel or support long-running jobs. A specialized RAG solution may handle many more documents than a generic model API.

Step 2: put in guardrails

Guardrails help reduce risk and should sit wherever there's exposure. The chapter splits them into input and output guardrails.

Input guardrails mainly address two things. First, leaking private information to external APIs, which is a risk specific to using third-party models. How it happens: an employee pastes secrets into a prompt (the chapter mentions a reported case of this), a developer puts internal data into a system prompt, or a tool pulls private data from an internal database into the context. There's no airtight way to eliminate leaks, but you can use sensitive-data detection tools that you configure with the classes you care about, such as personal information (ID numbers, phone numbers, bank accounts), faces, and company-specific keywords. When something is found, either block the query or mask the value, e.g. replace a phone number with a placeholder like [PHONE NUMBER], and use a reverse PII map to restore it in the response. Second, executing bad prompts that compromise your system (prompt attacks from Chapter 5). The chapter says risks can be mitigated but never fully eliminated.

Output guardrails have two jobs: catch failures, and set the policy for handling them. Failures come in two families: quality (malformatted responses such as invalid JSON, hallucinations, generally bad answers) and security (toxic content, leaked private information, responses that trigger remote tool or code execution, brand-risk responses). The easiest failure to catch is an empty response. Remember to track the false refusal rate as well, because a system that's too strict blocks legitimate requests and frustrates people.

Handling policies the chapter lists:

  • Retry. Models are probabilistic, so asking again may produce a better answer (retry if empty or malformatted). It costs latency and money, and doubles perceived latency if done after a failure. To limit that, send the query twice in parallel and pick the better response, trading extra API calls for latency.
  • Fall back to humans. Route tricky requests to people. The chapter's examples: transfer when a sentiment model detects anger, or after a number of turns so users don't get stuck in a loop.

Trade-offs. Guardrails add latency, and the chapter reports that some teams skip them for that reason (the author notes this made some early readers uneasy). Output guardrails also work badly with streaming: partial responses are hard to evaluate, so unsafe text may reach the user before the guardrail decides to block it. How many you need depends on whether you self-host (fewer input guardrails needed because nothing leaves your network) or use a third-party API (providers include many guardrails already). Guardrails can live at several levels: the model itself, your application, a standalone service, or a gateway. Tools named in the chapter include Meta's Purple Llama, NVIDIA's NeMo Guardrails, Azure's PyRIT and AI content filters, the Perspective API and OpenAI's content moderation API. (Vendor product names change; check current offerings.)

Step 3: add a router and a gateway

Router. Instead of one model for everything, use different solutions for different queries. Benefits: specialized models can beat a generalist at their niche (one for technical troubleshooting, one for billing), and you can save money by sending simple queries to cheaper models. The core piece is an intent classifier. The chapter's customer-support example: password reset goes to an FAQ page; billing corrections go to a human; technical problems go to a troubleshooting bot. A classifier can also refuse out-of-scope questions with a stock response without spending an API call, and detect ambiguity ("Freezing" could mean a frozen account or the weather) and ask for clarification.

Routers can also be next-action predictors for agents (use the code interpreter or search?) or predict which part of a memory hierarchy to read. They're typically small, fast models (some teams adapt small language models like GPT-2, BERT or Llama 7B, others train tiny classifiers from scratch) because they must not add much latency or cost. One practical wrinkle: when different models have different context limits, you may need to truncate the context or route to a model with a larger window. Routing often happens before retrieval (is this in scope? does it need retrieval?), but can also come after. The chapter says routing, retrieval, generation, scoring is the much more common order.

Gateway. A model gateway is an intermediate layer giving your organization a unified, secure interface to many models, whether self-hosted or behind commercial APIs. Benefits:

  • Maintainability. If a provider changes its API, you update the gateway, not every application.
  • Access control and cost management. Hand out access to the gateway instead of the raw provider keys (which can leak), set per-user or per-app permissions, and monitor and limit usage.
  • Fallbacks. If the primary API is down or rate-limited, route to an alternative or retry after a short wait.
  • A natural home for other features: load balancing, logging, analytics, sometimes caching and guardrails.

The chapter's sample is a simple wrapper function that picks the right provider call based on a request field, and says plainly it's not functional (no error checking). Off-the-shelf gateways exist (Portkey, MLflow AI Gateway, Kong, Cloudflare and others named). It mentions a similar "tool gateway" idea but says it isn't common yet.

Step 4: reduce latency with caches

This is about system caching (KV and prompt caching from Chapter 9 are model-side and usually provided by the API vendor). Two kinds:

Exact caching reuses a stored result only for the identical request. Examples: a product summary already generated, or a vector search result for a query seen before. It suits multi-step or slow operations (chain-of-thought, retrieval, SQL, web search). It can live in memory or in databases such as PostgreSQL or Redis, or tiered storage, and needs an eviction policy (LRU, LFU, FIFO). Not everything should be cached: user-specific queries ("What's the status of my recent order?") and time-sensitive ones ("How's the weather?") shouldn't be, and some teams train a classifier to decide. Danger: caching can leak data. The chapter's scenario: a generic-looking question about a return policy, whose answer actually depends on the asker's membership, gets cached after user X asks, and then user Y receives X's information.

Semantic caching reuses results for queries that are similar, not identical ("capital of Vietnam" and "capital city of Vietnam"). Typical approach: embed the query, do a vector search over cached query embeddings, and if the best similarity is above a threshold, return the cached result. It raises hit rate but is, in the chapter's words, of more dubious value: it depends on good embeddings, working vector search and a reliable similarity metric; the threshold needs trial and error; a false match returns a wrong answer; and the vector search itself costs time and compute. Only add it after weighing efficiency, cost and performance risks, and it's worthwhile mainly if the hit rate is high.

Step 5: add agent patterns and write actions

So far each query flows in one direction. With agent patterns (Chapter 6) the flow can loop, run in parallel and branch: after generating an output, the system may decide the task isn't done and retrieve more, feeding the response and the new context back to the same or a different model. The model's outputs can also invoke write actions: composing an email, placing an order, starting a bank transfer. Write actions make a system vastly more capable and also expose it to far more risk, so the chapter says to grant them with the utmost care. And the cost of all this: complex systems solve more tasks, but have more failure modes and are harder to debug.

Monitoring and observability

Observability should be part of the design, not an afterthought, and matters more the more complex the product. It's a big established industry, so the chapter focuses on what's unique to foundation-model applications. The goals of monitoring match those of evaluation: mitigate risks (application failures, security attacks, drift) and find opportunities for improvement and cost savings.

Three DevOps-derived measures indicate how good your observability is: MTTD (how long to detect a problem), MTTR (how long to resolve after detection) and CFR (the percentage of changes that cause failures needing a fix or rollback). The chapter says that if you don't know your CFR, it's time to redesign your platform to be more observable. A high CFR doesn't necessarily mean bad monitoring; it may mean your evaluation pipeline should catch bad changes before deployment. Evaluation and monitoring should work closely: evaluation metrics should translate into monitoring metrics, and issues found in monitoring should flow back into evaluation.

Monitoring vs. observability. Monitoring watches external outputs, with no guarantee they reveal what's wrong inside. Observability assumes a stronger property: that internal state can be inferred from outputs, so that when something breaks you can work out what from logs and metrics without shipping new code. The chapter uses "monitoring" for tracking and "observability" for the whole process of instrumenting, tracking and debugging.

Metrics. Metrics aren't the goal; their purpose is to tell you when something is wrong and where to improve. Start from the failure modes you want to catch and design metrics around them (if you fear hallucination, measure whether outputs can be inferred from the context; if you fear burning API credit, track tokens per request, cache cost and hit rate). Suggestions from the chapter:

  • Format failures (easiest): how often is the JSON invalid, and how many of those are easily fixable?
  • Quality: factual consistency, conciseness, creativity, positivity, often via AI judges.
  • Safety: toxicity, sensitive data in inputs and outputs, how often guardrails trigger and the system refuses, and unusual queries (which might be prompt attacks or interesting edge cases).
  • Conversation signals: how often users stop a generation halfway, turns per conversation, tokens per input and output, and how the output token distribution changes.
  • Component metrics: e.g. for RAG, context relevance and precision; for the vector database, index storage and query time.
  • Business correlation: relate metrics to your north-star metric (daily active users, session duration, subscriptions). Strongly correlated metrics suggest levers; uncorrelated ones suggest what not to optimize.
  • Latency (TTFT, TPOT, total, per user) and cost (query counts, input and output tokens, tokens per second, requests per second against rate limits).

You can run spot checks (sample a subset) or exhaustive checks (every request), ideally a mix, and break metrics down by users, releases, prompt or chain versions, types and time.

Logs. Metrics are aggregated; they can't tell you "has this happened before?" Logs are append-only event records. A typical debugging flow: metrics show something went wrong five minutes ago; you look at logs from that time; you correlate log errors with the metrics to confirm the cause. For fast detection, metrics must compute quickly; for fast response, logs must be available promptly (15-minute-delayed logs slow you down). The general rule: log everything, since you won't know in advance what you'll need: configuration (API endpoint, model name, sampling settings such as temperature, top-p, top-k, stop conditions, prompt template), the user query, the final prompt sent, the output and intermediate outputs, tool calls and their outputs, and component start, end and crash events, tagged with IDs so you know where each came from. AI-powered tools help with log volume, but the chapter still recommends manually inspecting production data daily: one study found developers' ideas of good and bad outputs shift as they look at more data, leading them to rewrite prompts and update evaluations.

Traces link related events into one timeline of a request: the actions taken, documents retrieved, final prompt, time and cost per step. Ideally you can follow each query step by step and pinpoint where it failed (processed wrongly, irrelevant retrieval, bad generation).

Drift detection. More parts, more things that can change without notice. The chapter names three:

  • System prompt changes: a template gets updated, a coworker fixes a typo. Simple logic can detect that the prompt changed.
  • User behavior changes: people adapt to the tool, e.g., learning to ask for concise answers, which gradually shortens responses. Metrics alone might not reveal why; you need investigation.
  • Underlying model changes: an API can stay the same while the model behind it is updated, sometimes undisclosed. The chapter cites a study that found notable benchmark differences between March and June 2023 versions of GPT-4 and GPT-3.5, and a report of a 10% performance drop when one team switched to a newer GPT-3.5-turbo version.

AI pipeline orchestration

An orchestrator specifies how components work together in an end-to-end pipeline and ensures data flows between them. Two steps: components definition (tell it which models, data sources, tools and even evaluation/monitoring tools you use) and chaining (function composition, the sequence of steps from query to completed task). The chapter's example chain: process the raw query; retrieve data; combine query and data into the prompt format the model expects; generate; evaluate the response; return it if good, otherwise send to a human. The orchestrator should help ensure each step's output matches the next step's expected input and tell you when the flow breaks. The chapter distinguishes AI pipeline orchestrators from general workflow tools like Airflow or Metaflow. For strict latency requirements, run independent steps in parallel (a router and a PII remover can run at the same time).

Tools named: LangChain, LlamaIndex, Flowise, Langflow, Haystack (many RAG and agent frameworks double as orchestrators). Advice: it's tempting to start with an orchestrator, but you may want to build without one first, since any external tool adds complexity and can hide details that make the system hard to understand and debug. When you do evaluate one, consider (1) integration and extensibility (does it support your current and future components, and how hard is it to add one?), (2) support for complex pipelines (branching, parallelism, error handling), and (3) ease of use, performance and scalability (good APIs and docs; avoid orchestrators that make hidden API calls or add latency).

Why it matters

This is the map for everything you'll build: when someone proposes adding a vector cache, a router, an agent loop or a gateway, you can ask what problem it addresses, what it costs and how you'd see it fail. And it gives you a checklist for operating AI features: log everything with IDs, trace requests, track format and safety failures, watch for drift, and measure how fast you detect and fix problems.

Remember this

  • Build up gradually: context, guardrails, router and gateway, caches, loops and write actions, adding each when a problem demands it. Each addition adds capability and complexity.
  • Guardrails can't remove risk; they trade latency for protection, and streaming makes output checks harder. Mask sensitive data before it leaves your system.
  • Exact caching is simple but must avoid caching user-specific or time-sensitive results; semantic caching depends on a similarity threshold that can return wrong answers.
  • Design metrics around the failures you want to catch; log everything with IDs; use traces to find which step of a request failed.
  • Watch for drift in system prompts, user behavior and the underlying model, and track MTTD, MTTR and CFR.

Try it yourself

  1. PII mask and unmask (under an hour). Write functions that replace phone numbers (or emails) in text with numbered placeholders and keep a reverse map, then restore them in a reply. Done when "Call me on 555-123-4567 tomorrow" becomes "Call me on [PHONE_1] tomorrow" and the reply "OK, I will call [PHONE_1]" unmasks correctly. (I ran a regex version; it handled that case, and a regex like this obviously misses many formats, which is the point to note.)
  2. Exact cache with eviction. Implement a small LRU cache with a capacity of 2 and a should_cache(query) check that refuses queries containing "my" or "today". Done when inserting a, b, reading a, then inserting c evicts b (mine printed keys a and c), and "What's my order status?" is never cached. 
    import collections
class LRU:
    def __init__(self, cap): self.cap, self.d = cap, collections.OrderedDict()
    def get(self, k):
        if k in self.d: self.d.move_to_end(k); return self.d[k]
    def put(self, k, v):
        self.d[k] = v; self.d.move_to_end(k)
        if len(self.d) > self.cap: self.d.popitem(last=False)
  3. Semantic cache threshold lab. Build a toy semantic cache using word-overlap (Jaccard) similarity and a threshold. Test 10 paired questions (5 true paraphrases, 5 different questions that share many words). Done when you've found a threshold that gets most right and listed the cases it can't separate. (My toy gave 0.86 for a true paraphrase and 0.71 for a different question, so a 0.7 threshold gave one wrong hit. Replace the score with real embeddings later if you like.)
  4. Mini gateway with fallback. Write a function that takes a list of provider functions (use stubs, one that raises an error and one that works) and returns the first successful answer, logging each failure. Done when your stub failure triggers the fallback and the log shows both attempts. No real API calls are needed.
  5. Retry on malformed JSON. Write a loop that calls a stub model up to 3 times until its output parses as JSON, tracking the number of tries. Done when a stub that fails once then succeeds returns on try 2 (mine did), and you've counted what that would cost in extra latency.
  6. Trace logger. Wrap a three-step fake pipeline (route, retrieve, generate) with a decorator that logs a request ID, step name, start and end time, and prints one trace line per step. Done when you can inject an error into one step and see exactly where it failed from the trace alone.
