Indexing Strategies: Prefix Indexes, Column Order, and Clustered Indexes

Part 1 was "what is an index." This part is "how do I design one on purpose." We cover shortening an index with a prefix, why one index on three columns is not the same as three indexes, the column-order question everybody gets wrong, and how InnoDB physically stores your rows (which quietly decides what a good primary key looks like).

In one line

Good indexes are designed around what the whole query needs (finding, ordering, and fetching rows), and in InnoDB the table itself is an index, which changes how you should think about primary keys.

The big idea

It's tempting to treat indexing as a checklist: "put an index on every column in the WHERE clause." The source calls that advice very wrong, and after poking at it on a real MySQL server while writing this, I get why. Index design is about shape. How long is each entry? Which column comes first? Do rows with similar keys end up stored near each other? A few decisions here can make a query many times faster or slower, and none of them are visible from just looking at column names.

This part covers the first half of the chapter's "Indexing Strategies for High Performance" section: prefix indexes and selectivity, multicolumn indexes (including index merge), choosing column order, and clustered indexes (how InnoDB stores rows, why secondary indexes are bigger than you'd guess, and why inserting in key order matters). Covering indexes, using an index for sorting, redundant and unused indexes, and maintenance are the second half, next time.

Key terms

  • Selectivity: the number of distinct values in an index divided by the number of rows. It runs from nearly 0 (almost every row has the same value) up to 1 (every value is unique). Higher means each lookup narrows down to fewer rows. Example: a status column with 3 possible values across 60,000 rows has a tiny selectivity.
  • Cardinality: the count of distinct values in an index. Selectivity is cardinality divided by row count.
  • Prefix index: an index built on only the first N characters (or bytes, for binary types) of a column, written like KEY (name(12)).
  • Multicolumn index (composite index): one index over several columns, sorted by the first column, then the second within ties, and so on.
  • Index merge: a MySQL strategy where the server uses two or more separate indexes on the same table for one query and combines their results (a union for OR, an intersection for AND).
  • Predicate: one condition in a WHERE clause, such as customer_id = 584.
  • Clustered index: not a separate index type, but a way of storing data where the rows live inside the leaf pages of the index itself. In InnoDB, that index is the primary key.
  • Secondary index: any index that isn't the clustered one. In InnoDB its leaf entries hold the indexed columns plus the primary key value.
  • Surrogate key: a primary key whose value has no meaning in your data, like an AUTO_INCREMENT counter.
  • Page split: what happens when a row has to go into a page that is already full, so the storage engine divides that page in two to make room.
  • Fill factor: how full a page is allowed to get. The source says InnoDB's initial fill factor is 15/16, leaving a little room for later changes.
  • I/O-bound workload: one where the data is bigger than memory, so response time is dominated by reading from disk. The opposite is a workload that fits in memory.
  • Random vs sequential I/O: reading scattered spots on storage versus reading neighbouring spots in order. The source treats random access as the more expensive one, especially on spinning disks.

How it works

Everything below builds on one fact from Part 1: a B-tree index is a sorted structure, so what you put in it and in what order decides what it can do. Keep the three-star idea in your pocket as well (rows grouped together, rows in the right order, and all needed columns inside the index). Each decision below earns or loses stars.

A note on how I checked things. The book's examples use the Sakila sample database. I don't reproduce those. Instead I built small made-up tables on a local MySQL 8.0 server and ran EXPLAIN myself, so the outputs I quote are mine and are only meant to show direction. Your numbers and plans will differ (the source itself warns the optimizer is hard to predict and to rely on EXPLAIN on your own workload).

1. Prefix indexes and selectivity

Indexing a long string column in full makes every index entry big, and big entries mean fewer entries per page and more memory used. A prefix index stores only the first few characters instead. The trade is simple: smaller index, but less selective, because different values can share the same first characters. For BLOB, TEXT, and very long VARCHAR columns it isn't even optional: the source says MySQL disallows indexing their full length, and I confirmed that a plain KEY(b) on a TEXT column fails with an error about needing a key length.

The craft is picking a length that is long enough that the prefix is nearly as selective as the whole column, but short enough to save space. The method is mechanical:

  1. Compute the full column's selectivity: COUNT(DISTINCT name) / COUNT(*).
  2. Compute the same ratio for candidate prefix lengths with COUNT(DISTINCT LEFT(name, N)) / COUNT(*). You can test many lengths in one query.
  3. Pick the shortest length where the prefix's selectivity gets close to the full column's, and notice the returns diminishing as you approach it.

The trap: average isn't worst case. A prefix can look fine on average and still be awful for common starts. In my table, a 4-character prefix gave one value, San , that covered 5,047 of 20,000 rows. Real place names make this worse ("San", "New", "Port"), and the source warns that a short prefix on real city names would give terrible selectivity for names beginning with those. So after the average check, also look at the most frequent prefixes at your candidate length (GROUP BY LEFT(col, N) ORDER BY COUNT(*) DESC) and ask whether the biggest bucket is acceptable.

The downsides, which I confirmed. The source says MySQL can't use a prefix index for ORDER BY or GROUP BY, and can't use it as a covering index. On my table with a 12-character prefix index forced, an equality lookup used it fine, but ORDER BY name LIMIT 5 fell back to a full table scan with Using filesort, whereas the full-column index answered the same query from the index alone (Using index). The reason is intuitive: the index only knows the first 12 characters, so it can't tell the true order of two values that share them, and it can't hand you the whole value.

One use case the source highlights: a packaged application you can't change that keys sessions on long hexadecimal strings. Indexing roughly the first eight characters often helps a lot and is invisible to the application. (An earlier chapter covers storing such identifiers more compactly when you control the schema.) Syntax is just ALTER TABLE t ADD KEY (col(8)).

2. Multicolumn indexes, and the "index every WHERE column" mistake

The source says multicolumn indexes are often poorly understood, and names two classic mistakes: indexing many columns separately, and putting columns in the wrong order. Here's the first.

Imagine a table with a separate single-column index on each of three columns. It looks tidy and thorough, and it usually comes from the vague advice "create indexes on columns that appear in the WHERE clause." The source is blunt: that advice produces one-star indexes at best, which can be orders of magnitude slower than well-designed ones. A one-star index groups rows by one column only. The query still has to deal with the other conditions, the sort order, and the row lookups.

Index merge is MySQL's partial rescue. If several single-column indexes exist, the server can use more than one for a single query: scan each and merge the results. Per the source there are three variants: union (for OR), intersection (for AND), and unions of intersections. You spot it in EXPLAIN with type index_merge and details in Extra. I reproduced both of the common ones on my orders table (single-column indexes on customer_id, status, region):

  • WHERE customer_id = 42 AND status = 2 showed Using intersect(customer_id,status).
  • WHERE customer_id = 42 OR region = 3 showed Using union(customer_id,region), with an estimate of about 12,000 rows to examine.

The source treats index merge as more often a symptom than a feature:

  • An intersection usually means you want one index containing all those columns, not several that must be combined.
  • A union can burn CPU and memory buffering, sorting, and merging, especially when the individual indexes aren't very selective.
  • The optimizer reportedly doesn't count that cost (it focuses on the number of random page reads), so it can "underprice" the plan, and the query may even run slower than a plain table scan. The load can also hurt other concurrent queries even though you won't notice it running the query alone.

If you see index merge, look at the query and table and ask whether a better multicolumn index exists. The source lists two escape hatches: disabling index merges through the optimizer_switch setting, or using IGNORE INDEX. It also notes that rewriting a union-style query with an explicit UNION is sometimes better. I didn't test these, so check the MySQL manual for exact syntax before relying on them.

3. Choosing a column order

Remember the Part 1 picture: a multicolumn B-tree is sorted by the leftmost column first, then the next within ties, and so on. That means the order you declare decides which queries can use the index to find rows, and also which ORDER BY, GROUP BY, and DISTINCT clauses it can serve (the source says the index can be scanned forward or in reverse when those match the column order exactly).

The old rule of thumb says put the most selective column first. The source's verdict: sometimes helpful, but "usually much less important than avoiding random I/O and sorting." It's most defensible when the index exists only to speed up WHERE lookups, with no sorting or grouping involved. Even then it depends on the actual values being looked up, not just overall cardinality, which is the same distribution problem as with prefix lengths.

The book's worked example asks whether a payment lookup on staff_id and customer_id should be indexed as (staff, customer) or (customer, staff). Two ways to decide:

  • Per-query counting. Count how many rows each predicate matches for the specific constants (SUM(col = value)), then count the second one within the first's matches. Handy when you have a real "worst query" from a tool like pt-query-digest. The caution: the answer depends on those exact constants, so tuning to one query can hurt others.
  • Across-the-board cardinality. Compare COUNT(DISTINCT col) / COUNT(*) for each column. In the source's sample, customer had far higher selectivity than staff, so customer goes first.

I ran my own version of the order test. With only (customer_id, status) present:

  • WHERE customer_id = 42 used the index (tight range, about 16 rows estimated).
  • WHERE customer_id = 42 ORDER BY status used the index and needed no sort step.
  • WHERE status = 2 ORDER BY customer_id couldn't use it: full table scan plus Using filesort.

Swap to only (status, customer_id) and it flips: the status filter with ORDER BY customer_id was served by the index (about 1,870 rows estimated, no filesort), while the customer_id-only queries fell back to scans. Lookups using both columns by equality were fast with either order. That's the real lesson: with both columns pinned by equality, order barely matters for finding rows, and it matters a lot as soon as you filter on one column alone or sort.

Outliers wreck averages. The source tells two stories to make this stick. Applications often have special rows, like a "guest" user ID shared by every logged-out session, or an administrative account that is "friends" with everyone. Queries involving those IDs behave nothing like the rest. In the larger story, a forum query slowed to a crawl because an import had assigned almost all 4.1 million rows to one admin group, and one user owned about 1.3 million of them. The source's conclusion: no index could help that case, and the fix was application code that recognized the special IDs and skipped the query. I saw the same shape in miniature: in my orders table one made-up "whale" customer owns about 30% of rows, so customer_id = 7 matches about 18,000 rows no matter which index you choose, while customer_id = 42 matches 16. Heuristics describe the average row. Your outage is caused by the weird one.

The source ends this thread by saying other factors, such as sorting, grouping, and range conditions, can matter much more than the selectivity rule.

4. Clustered indexes: the table is the index

This is the idea in the chapter that changes how you see InnoDB. A clustered index isn't a new kind of index, it's a storage approach. In InnoDB, the table's rows are stored in the leaf pages of a B-tree, so the row data and the index live in the same structure. "Clustered" refers to the fact that rows with adjacent key values are stored near each other (the source adds a small caveat, "this isn't always true"). A table can have only one clustered index, since you can't store the rows in two places at once. Not every storage engine supports clustered indexes; the source focuses on InnoDB.

Which index is it? In InnoDB, the primary key. The source says none of MySQL's built-in storage engines lets you choose a different one at the time of writing. If you don't define a primary key, InnoDB tries to use a unique non-nullable index instead, and failing that creates a hidden primary key for you. The source flags a downside of the hidden one: the counter behind it is shared across all tables that use hidden keys, which increases mutex contention.

5. Primary key lookups versus secondary index lookups

In a clustered table, the leaf entries of the primary key tree hold the whole row. Per the source, they also hold bookkeeping InnoDB uses for transactions and MVCC (a transaction ID and a rollback pointer). Internal (non-leaf) nodes contain only the key columns and pointers downward.

Now the surprising part. A secondary index doesn't store a physical address of the row. Its leaf entries store the indexed columns plus the primary key value. The primary key acts as the row pointer. The source gives the reason: when a row moves, or a page splits, secondary indexes don't need updating, because the primary key hasn't changed. The cost is that secondary indexes get larger (they carry a copy of the primary key in every entry) and a lookup through one takes two B-tree walks: first the secondary index to find the primary key, then the clustered index to find the row.

I verified one consequence on my own server. With a plain index on customer_id, the query SELECT id, customer_id FROM orders WHERE customer_id = 42 showed Using index, meaning the index alone answered it, even though id isn't a declared column of that index. That works because the primary key rides along in every secondary index entry. (Covering indexes get their full treatment next time.) The same fact explains why a wide primary key bloats every secondary index: a 36-character string key is copied into each one.

6. The clustered index trade-offs

The source lists clear advantages:

  • Related data stays close. Cluster a mailbox table by user and one user's messages sit together, so fetching them touches only a few pages rather than one page per message.
  • Fast access. Index and data are in one structure, so a primary key lookup is normally quicker than a comparable lookup via a non-clustered index.
  • Covering-index queries can use the primary key values found in leaf entries.

And disadvantages, which are the part beginners usually skip:

  • The biggest gain is for I/O-bound workloads. If everything fits in memory, access order barely matters, so clustering gives little.
  • Insert speed depends heavily on insertion order. Inserting in primary key order is the fastest way to load an InnoDB table; after a bulk load in other orders, OPTIMIZE TABLE may be worth running.
  • Updating clustered key columns is expensive, because the row has to physically move.
  • Page splits can happen on inserts, or when a key update forces a row into a full page, and can leave the table using more disk space.
  • Full table scans can be slower when pages are sparsely or non-sequentially stored.
  • Secondary indexes can be bigger than you expect, and secondary lookups take two walks.

A detail from the book's layout example: if the primary key is defined on a column prefix, InnoDB still includes the full column value in the leaf entry.

7. Insertion order, UUIDs, and page splits

If you don't need any particular clustering, the source recommends a surrogate key, typically an AUTO_INCREMENT column. New rows arrive in increasing key order, so each goes at the end of the tree. A page fills to its fill factor, the next row starts a new page, and you end up with pages packed nearly full, which is what you want.

Random keys, with UUIDs as the example, behave differently. Each new row lands "somewhere near the middle, on average." The source lists three costs:

  • The target page may not be in memory, so InnoDB reads it from disk first (random I/O).
  • When the page is full, InnoDB splits it, moving data around and touching at least three pages rather than one.
  • The split pages end up sparsely and unevenly filled, so the table fragments.

The source benchmarked a million-row load with an integer key against a UUID key and reported the UUID version slower with a bigger index, with the gap widening a lot once the indexes outgrew memory. It also notes that part of the size difference comes simply from the larger key. I won't quote its numbers (they're its own benchmark on its own hardware), but I ran a tiny version for direction: 300,000 rows loaded into one table keyed by AUTO_INCREMENT and another keyed by a 36-character UUID() string, on a small local server where everything fit in memory. The UUID table took about 2.1 seconds versus about 1.4 for the sequential one, and its data size was about 36.6 MB versus 27.6 MB. That is a single run and a bigger key was part of the difference, so treat it as a direction, not a result. After loading random keys, the source suggests an OPTIMIZE TABLE to rebuild and repack the pages.

8. When primary key order is worse

One caveat to the "always insert in order" advice (and yes, I'm bounding it): in very high-concurrency workloads, sequential keys can themselves create contention. All inserts go to the upper end of the key space, which becomes a hot spot where concurrent inserts can fight over next-key locks. A second hot spot is the AUTO_INCREMENT locking mechanism. The source says you may be able to redesign the table or application, or configure innodb_autoinc_lock_mode (or upgrade, if your version lacks that setting). I didn't test this; it's good to know it exists so a fast-looking design doesn't surprise you under heavy parallel writes.

Why it matters

These choices are hard to change later. A primary key type is baked into every secondary index, and a table that has grown to hundreds of millions of rows is painful to rebuild. Knowing that the primary key is the row's address in InnoDB lets you reason about size, insert speed, and lookup cost before you commit. Knowing that column order is a sorting decision lets you design one index to serve a lookup and its ORDER BY instead of stacking up single-column ones. And knowing how selectivity lies about outliers keeps you from trusting a heuristic that your hottest customer will happily break.

Remember this

  • A prefix index trades size for selectivity: pick the length by measuring, check the most common prefixes (not just the average), and remember it can't serve ORDER BY, GROUP BY, or covering.
  • "Index every column in the WHERE clause" gives you separate one-star indexes; index merge in EXPLAIN is often a hint that one multicolumn index is missing.
  • Column order decides which lookups and sorts an index can serve. The "most selective first" rule is a weak default that often loses to avoiding sorts and random I/O.
  • In InnoDB the primary key is the clustered index: rows live in its leaves, and every secondary index entry carries the primary key as its row pointer.
  • A small, steadily increasing key (such as AUTO_INCREMENT) usually loads fastest and packs pages best; random keys like UUID strings cause page splits and bigger indexes, though extreme concurrency can create hot spots at the end of the key range.

Try it yourself

  1. Prefix length picker. Write a script (any language) that reads a text file of one string per line and prints, for prefix lengths 2, 4, 6 and so on, the selectivity and the most common prefix with its count. Done when: you run it on a file of at least 10,000 strings (generate fake ones with deliberately repeated starts) and can state a length you'd choose and why, citing both the average and the worst-bucket number. A 12-line Python version of this took me a few minutes.
  2. Break a prefix index on purpose. On a local MySQL, create a table with a long string column, add a prefix index on it, and run EXPLAIN for an equality lookup, an ORDER BY col LIMIT 5, and a query that selects only col. Repeat with a full-column index. Done when: you've written down, for each query, whether the key was used and whether Using filesort or Using index appeared, and you can explain every difference between the two indexes.
  3. Catch an index merge. Build a table of at least 50,000 rows with three columns each indexed separately. Run an AND query and an OR query across two of them and find index_merge in EXPLAIN. Then add a single two-column index and re-run. Done when: you have before-and-after EXPLAIN output for both queries and one sentence on what changed.
  4. Column order experiment. Using the same table, create (a, b), then run one lookup on a only, one on b only, and one with WHERE a = ... ORDER BY b. Drop it, create (b, a), repeat. Done when: you've filled in a 3x2 table of "uses index / scan / filesort" and can predict the result for a third query before running it.
  5. Find your whale. Take any table you have (or generate one where one value owns about a third of the rows). Compare SUM(col = common_value) to SUM(col = rare_value) and the EXPLAIN row estimates for both lookups. Done when: you can explain, in two sentences, why the same index serves one query well and the other badly, and what the application could do about the special value.
  6. Page-split simulator. Write a toy that stores sorted keys in fixed-size pages (say 8 keys), splits a full page in half when a key must go into it, and loads 2,000 keys once in order and once shuffled. Done when: you print page count, split count, and average fill for both runs, and the shuffled run shows more pages and lower fill. (Mine gave 250 pages at 100% versus 351 pages at about 71%, but a different split rule will give different numbers. That's fine, it's a toy.)
