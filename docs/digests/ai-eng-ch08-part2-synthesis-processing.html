Dataset Engineering: Synthetic Data, Distillation and Processing

Part 1 said good data is the hard part and described how to judge and acquire it. This part is about manufacturing it: augmenting and synthesizing data (the old rule-and-simulation way, then the new AI-powered way), checking whether generated data is any good, where synthetic data falls short, distilling a big model into a small one, and finally the unglamorous pipeline of inspecting, deduplicating, cleaning and formatting. The chapter's Summary closes it.

In one line

You can generate a lot of training data programmatically or with AI, but it only helps if you can verify it, and whatever data you end up with still has to be inspected, deduplicated, cleaned and formatted exactly the way the model expects.

The big idea

Data, along with compute and talent, is the hardest part of AI, and producing it automatically has been a long-standing goal. Generating data is now practical because models can write realistic text, code, conversations and judgments. But "more data" isn't the point; verified, diverse data is. The chapter's pattern is that people synthesize the data they can check (code is the standout, since you can run it), use AI to cover gaps in coverage and quality, and keep real data in the mix. Then every dataset, real or synthetic, goes through the same plain processing steps, and the chapter's most practical advice is to look at your data by hand.

Key terms

  • Data augmentation: making new data from existing real data (for example flipping an image).
  • Data synthesis: generating data that mimics real data's properties. The chapter often uses "synthesis" to cover both.
  • Procedural generation: using algorithms rather than manual work to generate content.
  • Rule-based synthesis: filling templates or applying fixed transformations.
  • Perturbation: adding noise to existing data to make new examples.
  • Simulation: generating data by running a virtual version of an experiment.
  • Sim2Real: adapting models trained in simulation so they work in the real world.
  • Self-play: an AI learning by playing against copies of itself.
  • Back-translation: translating something into another language (or form) and back, then comparing with the original to check quality.
  • Reverse instruction: starting from existing high-quality responses and having AI write the instructions that would produce them.
  • AI verifier / AI judge: a model that scores or classifies data quality.
  • Model collapse: degradation when models are trained recursively on AI-generated data.
  • Data lineage: knowing where data (and the data behind it) came from.
  • Model distillation: training a small "student" model to mimic a larger "teacher" model.
  • Deduplication: removing repeated examples.
  • Chat template: the exact text layout a model expects for system, user and assistant turns.
  • Inter-annotator disagreement: how often annotators differ on the same example.

How it works

Grounding: augmentation versus synthesis, and why bother

Augmentation derives new data from real data (a flipped photo of a real cat is still a cat). Synthesis invents data that imitates the real thing (simulating how a mouse moves over a web page to create bot-like traces). The chapter notes the terms blur because both aim to automate data creation. Fake data has long been used in software testing; libraries like Faker generate names, addresses and so on so you can test, say, an address parser.

With AI able to produce text that's hard to tell from human writing, synthetic data now covers doctor's notes, contracts, financial statements and more. The chapter gives five reasons to synthesize:

  • Quantity. Scale, especially where real data is scarce: rare weather, deep-sea exploration, accidents for self-driving.
  • Coverage. Target what's missing: very short or very long texts, toxic examples for a toxicity detector, adversarial examples, rare classes. The chapter cites Anthropic's work on model-written evaluations covering 154 behaviors, which found model-written datasets approached, and sometimes exceeded, the quality of human-written ones.
  • Quality. Sometimes AI beats humans: tool-use sequences (humans and models work differently), complex math problems beyond what an average expert would write, and preference ratings (an individual person is roughly consistent but people vary with mood and motivation, while an AI judge can be more consistent).
  • Privacy. When you can't use real patient records or insurance claims, synthetic ones may be the only option.
  • Distillation. Training a cheaper model on a bigger model's outputs (see below).

But synthetic data doesn't fully replace human data. In many cases a mix gives the best value.

Traditional synthesis: rules and simulation

Rule-based. Templates plus random generators. The chapter's example is a credit card transaction template (ID, date, amount, merchant, category, location, status), filled with Faker; fraud-detection teams often prove feasibility on synthetic transactions before getting access to sensitive real ones. Templates also produce invoices, resumes, contracts, config files, regexes, math equations. DeepMind's AlphaGeometry was trained on 100 million synthetic examples. Transformations on existing data are rule-based too: rotate, crop or erase part of an image (AlexNet used this on ImageNet); replace words with synonyms in text (found via a thesaurus or nearby word embeddings). The chapter shows how swapping gendered words (she/he, mom/dad, even names) can help counter bias in a dataset.

Perturbation. Adding noise. It started as an attack: the "one pixel attack" paper reported that changing a single pixel could cause misclassification for a large share of test images (67.97% of natural CIFAR-10 test images and 16.04% of ImageNet test images in the chapter's numbers). Training on perturbed data can improve robustness; BERT's authors replaced 1.5% of tokens with random words and saw a small boost.

Simulation. Run the experiment virtually when the real one is expensive or dangerous: a self-driving car meeting a horse on the highway, a robot learning to pour coffee by trying many joint movements and keeping the successful ones, or financial and climate scenarios, manufacturing defects. Tool-use data can come from simulation too: try different action sequences, execute them, validate, and keep the most efficient as the "annotated" response. The caveat is that simulations are simplifications. A robot failing in simulation will likely fail in reality, but succeeding in simulation doesn't guarantee success. Sim2Real research works on that gap.

AI-powered synthesis

Strong models open new options:

  • Simulating programs and humans. A model can imitate what an API would return (StableToolBench) so you don't make real, slow or costly calls. It can imitate players: OpenAI's Dota 2 bot played the equivalent of roughly 180 years of games a day via self-play, and DeepMind used self-play for Go (AlphaGo). For general agents you can have one model play a customer with a problem and another play support.
  • Paraphrasing and translation. "How to reset my password?" becomes several rephrasings. The MetaMath work rewrote 15,000 math examples into almost 400,000 and reported that models trained on it beat larger models on related benchmarks. Translating from high-resource to low-resource languages helps small models for languages like Quechua or Lao; back-translation checks quality by translating back and comparing with the original, and a big mismatch suggests a bad translation. AI can translate programming languages as well.
  • Pre-training versus post-training. Synthetic data is used much more on purpose in post-training. One possible reason: pre-training aims to add knowledge, and it's harder for AI to synthesize genuinely new knowledge than to reformat existing knowledge. Post-training data (instructions, preferences) is also the most effort to produce by hand. Synthetic pre-training sets do exist (Cosmopedia, 25 billion tokens), and web-trained models likely already ingest some AI-generated text.
  • Preference data. Using AI to pick the better of two responses is straightforward, but judges have biases such as favoring the first option. NVIDIA researchers asked the judge twice with the order swapped and kept a (prompt, winner, loser) triple only if the same response won both times.

Synthesizing instruction data

Each instruction example has an instruction and a response; AI can write either or both. A common pattern: humans write one half, AI the other. To make instructions cover your use case, start from a list of topics, keywords or instruction types (which can themselves be AI-generated) and generate a set per item, or start from templates.

  • UltraChat (multi-turn): ChatGPT produced 30 everyday-life topics, then 30 to 50 subtopics each, then instructions and responses for those.
  • Alpaca: started with 175 seed (instruction, response) examples from Self-Instruct and used a GPT-3 model to produce 52,000 similar pairs.
  • Reverse instruction. Long, high-quality responses are hard for AI to produce without hallucinating. So take existing high-quality content (stories, books, Wikipedia articles) and have AI write the prompts that would elicit it. The responses are human-made, so fewer hallucinations. A bootstrap loop from the literature: train a weak model on seed data, use it to write instructions for high-quality content, finetune on that, and repeat. The chapter says that in theory this could allow continual self-improvement, but whether it works in practice is another matter.
  • Long-context data. To go from an 8K-token model to 128K, split long documents into short chunks, generate question-answer pairs for each chunk, then train with the original long document as the context for those pairs.

Llama 3 as a case study. The chapter walks through the coding-data pipeline: (1) AI writes a wide range of programming problem descriptions; (2) AI writes solutions in different languages (adding programming best practices and CoT improved quality); (3) parsers and linters catch syntax problems; (4) AI-written unit tests catch runtime errors; (5) failures are fed back, with the problem, the bad solution and the error messages, for the model to revise (the paper observed about 20% of solutions were initially wrong but self-corrected); (6) code is translated to other languages and filtered by tests; (7) AI writes explanations and documentation, which are kept only if regenerating code from them is faithful to the original (back-translation). Only examples passing every check enter the SFT set. Together this produced over 2.7 million synthetic coding examples for Llama 3.1, as the chapter reports.

Data verification

Evaluating generated data works like evaluating any AI output: functional correctness and AI judges. The chapter's observation (echoing evaluation-driven development): people synthesize the data they can verify, which is why coding examples are among the most common synthetic data and most of Llama 3's synthetic data is coding-related.

Where you can't run it, options include:

  • An AI verifier that scores each example (1 to 5) or labels it good or bad against written quality requirements.
  • Factual consistency detectors to filter likely hallucinations.
  • "Can I tell real from fake?" Train a detector; if it spots synthetic data easily, the data isn't realistic. Or train a classifier for a quality target, like whether a generated paper would be accepted at a major conference.
  • Topic classification to drop off-topic examples, and anomaly detection for outliers.
  • Heuristics: drop empty, too short, repetitive or over-long examples; filter by keyword, author, date, metadata or source. Self-Instruct's authors filtered repeated examples, instructions that were too long or short, same instruction with different responses, and outputs that merely repeat the input.

Evaluation remains hard. The ultimate test is whether training on it improves the model, which synthetic data has done for many models.

Limits of AI-generated data

The chapter says synthetic data will grow in importance but may never entirely replace human data, for four main reasons.

  1. Quality control. Garbage in, garbage out; if you can't verify, you can't trust.
  2. Superficial imitation. A study found imitation models copy the teacher's style but can fall short on factual accuracy and generalization. Worse, imitation can teach a student to produce answers that look like solutions it can't actually derive, which encourages hallucination. That study suggests improving the base model rather than imitating for better reasoning. The same issue arises with human labelers who use knowledge the model lacks.
  3. Model collapse. Recursively training on generated data has been shown to cause irreversible defects in some models. One explanation: models over-produce probable events and under-produce improbable ones, so rare things vanish over iterations. A follow-up paper argues collapse is unavoidable if all the data is synthetic but avoidable when mixed with real data; there's no firm recommended ratio. Counterpoints: one paper found synthetic math data nearly as effective as real for finetuning a 7B model, with no clear saturation up to about a million samples, and Nemotron-4-340B-Instruct used 98% synthetic data in its instruction and preference finetuning, though those results were for one model iteration. Feedback loops can also amplify biases.
  4. Obscured data lineage. If the generator model was trained on copyrighted material, your model may inherit the risk. If it saw a benchmark you later evaluate on, your result is contaminated, and you may not be able to tell.

Model distillation

Distillation trains a small student to mimic a larger teacher. Traditionally the point is a smaller, faster deployable model: DistilBERT is reported to be 40% smaller than BERT, retaining 97% of its language understanding and 60% faster. A student can be trained from scratch (DistilBERT) or finetuned from a pretrained model: Alpaca finetuned Llama-7B on examples from text-davinci-003 (a 175B model), reaching similar behavior at 4% of the teacher's size. BuzzFeed reportedly finetuned a Flan-T5 model with LoRA on text-davinci-003 outputs and cut inference cost by 80%, though how good the model was is unclear.

Important caveat: many model licenses prohibit using their outputs to train other (especially competing) models, so not every model can be a teacher. Check terms first.

Also, not all synthetic-data training is distillation. Distillation treats the teacher as the gold standard, but a student can exceed its teacher: Nemotron-4 (340B) was finetuned on data from a smaller teacher (Mixtral-8x7B-Instruct) and outperformed it on a range of tasks. The Llama 3 paper adds a warning and a fix: training indiscriminately on a model's own outputs doesn't improve it and can degrade it, but with mechanisms to verify the data and using only the verified examples, they could keep improving a model with its own generations.

Data processing: inspect, dedupe, clean, format

Tips for efficiency: order the steps by what saves compute (if cleaning is slower than deduplicating, dedupe first, and vice versa); run trial runs before processing everything; and don't modify data in place, keeping the original so other teams can reuse it and a buggy script can't corrupt it.

1. Inspect. Learn where the data came from, how it was processed and what it was used for. Plot token, input-length and response-length distributions; check special tokens, topics and languages and how relevant they are. Be creative: Microsoft researchers compared GPT-3 and GPT-4 generations using the distribution of (verb, direct object) pairs and response lengths, which showed GPT-4's outputs were broader and longer. Slice by source, time and annotator: do some annotators write much shorter answers or score high? Compute inter-annotator disagreement and resolve conflicts. And look at the data yourself: the author says that 15 minutes of staring at data usually surfaces something that saves hours, and quotes a well-known tweet calling manual inspection among the highest value-to-prestige activities in ML. Try labeling a few examples yourself to see whether you agree with the given labels; fact-check; look for same query with different responses, or the reverse.

2. Deduplicate. Duplicates skew distributions (a toy table with a repeated "red pencil costs $20" row teaches the model that red things are expensive), leak between train and test sets, and waste compute. Studies show the harm is real: an Anthropic study found repeating 0.1% of data 100 times could make an 800M-parameter model perform like a 400M one even though the rest of the tokens were unique. Define duplicates for your case: whole-document, within-document, cross-document; at document, paragraph, sentence or token level; exact match or, say, 80% overlap; is a reordered list a duplicate? Methods: pairwise comparison (exact, n-gram, fuzzy or semantic similarity; expensive at scale), hashing (bucket examples, compare only within buckets, as in MinHash and Bloom filters), and dimensionality reduction then compare. Libraries exist (the chapter names several).

3. Clean and filter. Remove extraneous formatting (Databricks reported removing extra Markdown and HTML tokens improved accuracy by 20% while cutting input length by 60%, per the chapter). Remove anything non-compliant: PII, sensitive, copyrighted or toxic material, fields you aren't allowed to use. Remove low-quality data, and manually find heuristics for it; one study found annotations from the second half of an annotation session were worse, likely from fatigue. If you have more data than you can afford to train on, select the most useful with techniques like active learning or importance sampling, which depend on being able to judge each example's value.

4. Format. Each model has a tokenizer and an expected chat template (see Chapter 5), and the wrong one causes strange bugs. SFT data is usually (instruction, response), with instructions possibly split into system and user prompts. Finetuning prompts often don't need the task description or examples that your prompt-engineering version had, since the examples now live in the training set. The chapter's example: a three-shot food classification prompt turns into training rows like "burger --> edible", and after finetuning the prompt is just "{INPUT} -->", which is shorter and cheaper. Whatever format you choose, inference prompts must match the training format exactly: "burger" (missing arrow), "Item: burger -->" (extra prefix) or "burger --> " (trailing space) can all cause trouble. Different formats can change performance, so test.

The chapter's closing thoughts

The Summary repeats the core: think through the behaviors you want, then design data that shows them. Dedicated data roles are emerging. Quality, coverage and quantity apply in every training phase. A small amount of high-quality data can beat a large noisy set, and diversity is key. Synthetic data became practical once AI could create realistic, complex data, but you must evaluate it, and people tend to use generated data that they can reliably evaluate. And some things don't automate: deciding what data you want, writing annotation guidelines, and paying attention to details. The next chapter turns to serving the model: optimizing inference for latency and cost.

Why it matters

Almost every team that finetunes or builds evals ends up generating or cleaning data. This part gives you the vocabulary (augmentation, synthesis, distillation, back-translation, reverse instruction) and the discipline: verify before you train, keep real data in the mix, mind licenses and lineage, and keep your processing steps and prompt formats consistent end to end.

Remember this

  • Augmentation derives from real data; synthesis invents data. Rule-based, simulation and AI-powered methods all exist, and AI-powered ones opened up instructions, preferences, translations and code.
  • People synthesize what they can verify. Code is the easy case because you can run it; other domains lean on AI judges, heuristics and spot checks.
  • Synthetic data has limits: quality control, superficial imitation, possible model collapse (especially if data is all synthetic), and unclear lineage.
  • Distillation trains a student on a teacher's outputs, but check the teacher's license, and a student can sometimes exceed the teacher.
  • Process data in the order that saves compute: inspect, dedupe, clean and filter, format, and make your inference prompts match the training format exactly.

Try it yourself

  1. Template data generator (under an hour). Write a script that fills a template (for example a fake support ticket with product, issue type and severity) from small lists, producing 100 rows. Done when you can show the first five and a count of how many unique combinations exist, and you've noted one way the data would look too uniform for real training.
  2. Dedupe workshop. Make a list of 20 short sentences with some exact repeats, some case/whitespace differences and some paraphrases. Implement (a) exact dedupe after normalizing case and whitespace, and (b) a similarity check using Jaccard overlap on word shingles. Done when you've seen which duplicates each method catches and which it misses. (When I tried this on five password-reset questions, normalization removed 2 of 5 rows, and a 3-word-shingle Jaccard score between a paraphrase pair was only 0.12, so exact matching and similarity scores catch different things.)
  3. Heuristic filter. Write a filter that strips HTML tags and drops examples that are empty, too short, too long, or whose response just repeats the instruction. Run it on a handful of hand-made rows. Done when each rule fires on at least one example and you've logged why each row was dropped. (I ran a small version with HTML, empty and echo cases and each rule fired as expected.) 
    import re, html
def clean(t): return re.sub(r"\s+"," ", re.sub(r"<[^>]+>","", html.unescape(t))).strip()
def reason_to_drop(ex, hi=2000):
    i, o = clean(ex["instruction"]), clean(ex["response"])
    if len(i) < 3 or len(o) < 3: return "empty/short"
    if len(i) > hi or len(o) > hi: return "too long"
    if o.lower() == i.lower(): return "output repeats input"
  4. Order-swap judge. Write a function that asks a judge twice with the answer order swapped and keeps the pair only if the same answer wins. Test it with a stub judge that always picks the first option (everything should be discarded) and a stub that prefers longer answers (pairs should be kept). Done when both behave that way. This uses scripted stand-in judges, not a real model API; swap in one later if you like.
  5. Back-translation check, by hand. Take five sentences, translate each into another language you know (or a translation tool), translate back, and compare. Done when you've scored each pair as faithful or not and written down what kind of meaning shifted. This is the manual version of the chapter's quality check.
  6. Prompt-format test. Define a training format like {item} -->. Write a validator that checks a prompt exactly matches the format and flags missing arrows, extra prefixes and trailing spaces. Done when your validator rejects the three bad variants from the chapter's example and accepts the right one (I ran this: all three variants were rejected). Then decide where in your own app you'd call it.
