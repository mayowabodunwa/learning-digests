CloudWatch Alarms: Static, Anomaly Detection, Composite and Alarm Actions

A metric on a graph only helps if someone is looking at it. An alarm is how you get CloudWatch to look for you, decide "that's bad", and do something about it. This digest covers how an alarm decides, the three flavours you'll meet (static, anomaly detection, composite), and what an alarm can actually do when it fires.

In one line

A CloudWatch alarm watches one metric (or a formula over metrics, or other alarms), compares recent data points against a rule, lives in one of three states, and runs actions only when that state changes.

The big idea

In the last CloudWatch digest we saw that a metric is a named stream of numbers. Alarms sit on top of that stream. You pick a metric, say how long each data point should cover, say what counts as "too high" (or too low), and say how many bad data points in a row you'll tolerate. CloudWatch then evaluates that rule over and over and keeps the alarm in one of three states: fine, bad, or "I can't tell".

Once you understand that loop, the rest is variations on it. A static alarm uses a threshold number you pick. An anomaly detection alarm lets CloudWatch learn what "normal" looks like and flags values outside a band. A composite alarm ignores metrics entirely and combines the states of other alarms with AND/OR/NOT logic so your phone buzzes once instead of fifteen times. And the actions (notify, scale, reboot, open a ticket) hang off state changes.

Key terms

  • Alarm — a CloudWatch object that watches something and moves between states based on a rule. The docs describe several kinds: metric alarms, composite alarms, and also PromQL alarms and log alarms (we only touch those in passing here).
  • Metric alarm — watches a single metric, or the result of a metric math expression, against a threshold over a number of time periods.
  • Threshold — the number your data point is compared with, using a comparison operator such as GreaterThanThreshold.
  • Alarm state — one of OK (within the threshold), ALARM (outside it), or INSUFFICIENT_DATA (just started, metric unavailable, or not enough data to decide).
  • Period — how many seconds of data are rolled into each single data point the alarm looks at.
  • Evaluation Periods (N) — how many of the most recent data points the alarm looks at.
  • Datapoints to Alarm (M) — how many of those N must be breaching to trigger ALARM. They don't have to be consecutive.
  • Breaching — a data point that violates the threshold. A data point is either breaching, not breaching, or missing.
  • Treat missing data — the setting that says how absent data points count: missing, notBreaching, breaching, or ignore.
  • Anomaly detection — CloudWatch builds a model of a metric's expected values (a "band") from past data, and an alarm can fire when the metric leaves that band.
  • Composite alarm — an alarm whose state comes from a rule expression over the states of other alarms, not from a metric.
  • Alarm action — something CloudWatch does on a state transition: send to an SNS topic, invoke Lambda, run an EC2 action, trigger a scaling policy, create an OpsItem or incident, and so on.
  • SNS topic — an Amazon Simple Notification Service channel. Subscribers (people or applications) receive whatever is published to it.

How it works

Grounding: what an alarm is for

Imagine you run a web service and care about CPU on one server. Without an alarm, you'd have to open a graph and stare at it. With an alarm, you say: "if average CPU is above 70 percent, tell me". CloudWatch does the staring. The AWS docs point out you can use alarms to notify people or to make changes automatically, for example to watch EC2 CPU and decide whether to launch more instances, or stop under-used ones.

An alarm is not the metric. It is a separate object that reads a metric. That matters for one detail from the docs: you can create an alarm for a custom metric before that metric exists, but for the alarm to be valid you must give the full identity (namespace, metric name, and every dimension). That is exactly the identity rule from the metrics digest.

1. The three states and the evaluation loop

A metric alarm is always in one of three states:

  • OK: the metric or expression is within the threshold.
  • ALARM: it is outside the threshold.
  • INSUFFICIENT_DATA: the alarm has just started, the metric isn't available, or there isn't enough data to decide.

Beginner point to hold onto: INSUFFICIENT_DATA is not "broken", and it is not "fine". It means CloudWatch can't tell. The docs give a gentle example: an EBS volume that isn't attached to an instance may not send metric data, so an alarm on it can drift to INSUFFICIENT_DATA, which may just mean the resource is idle.

How often does it evaluate? Per the docs, for a period of one minute or longer an alarm is evaluated every minute, over a sliding window of Period × Evaluation Periods. Their example: with a 5-minute period and 1 evaluation period, at the end of minute 5 the alarm uses minutes 1 to 5, and at the end of minute 6 it uses minutes 2 to 6. Periods of 10, 20 or 30 seconds (high-resolution alarms, used on high-resolution metrics) are evaluated every 10 seconds, and carry a higher charge. If periods × length exceeds one day, the alarm is evaluated once per hour instead.

Simplification: "evaluated every minute" describes the default sliding-window behaviour. The docs also describe an optional wall-clock-aligned evaluation window, which behaves differently; I'm not covering it here.

2. Static threshold alarms: Period, N and M

A static alarm is the classic one: you choose the number. Three settings control when it flips to ALARM:

  • Period: seconds of data rolled into each data point.
  • Evaluation Periods (N): how many recent data points to look at.
  • Datapoints to Alarm (M): how many of those must be breaching.

If M equals N, you've made a "N in a row" style alarm. If M is smaller than N, you've made an M out of N alarm: the breaching points need not be consecutive, only inside the last N. The docs' examples: 4 out of 5 points with a 1-minute period has an evaluation interval of 5 minutes; 3 out of 3 with a 10-minute period has an interval of 30 minutes.

Why bother with M of N? A single CPU spike for one minute is usually noise. Asking for 3 out of 3 (or 3 out of 5) bad points trades a little speed for far fewer false alarms. That trade-off is a judgement call, not a rule: a payments outage might deserve a faster, twitchier alarm than a nightly batch job.

A few more static-alarm settings worth knowing, all from the put-metric-alarm reference: the comparison operator is one of GreaterThanOrEqualToThreshold, GreaterThanThreshold, LessThanThreshold or LessThanOrEqualToThreshold; the statistic can be SampleCount, Average, Sum, Minimum or Maximum (percentiles go through --extended-statistic); and the period is 10, 20, 30 or a multiple of 60. There is a ceiling on how far back an alarm can look: the maximum evaluation period (period × evaluation periods) is seven days for alarms with a period of at least one hour, and one day for shorter periods.

3. Missing data: the setting that causes the most confusion

Real metrics have gaps. A server reboots, a connection drops, or the metric is only published when something happens. CloudWatch lets you choose what a gap means, per alarm. The four options and the documented default:

  • missing (the default): if all data points in the evaluation range are missing, the alarm goes to INSUFFICIENT_DATA.
  • notBreaching: gaps count as "good".
  • breaching: gaps count as "bad".
  • ignore: the alarm keeps whatever state it already has.

Which one is right depends on what silence means for that metric. The docs give two contrasting examples. For a rollback alarm on a metric that normally reports continuously, treating missing data as breaching can make sense, since silence may signal trouble. For something like DynamoDB's ThrottledRequests, which only produces data points when errors occur, silence is good news, so notBreaching fits.

How the fill-in works (a simplification, with the caveat below). When evaluating, CloudWatch actually fetches more data points than N, called the evaluation range, in case recent ones are missing. If there are still at least N real points in that range, it uses the most recent real ones and your missing-data setting is not needed at all. Only when there are fewer than N real points does it fill the gaps using your setting, and it uses fill-ins "as few times as possible". Some rows from the docs' table (N=3, M=3; 0 = fine, X = breaching, - = missing, newest on the right):

  • - - - - - (all missing): missing → INSUFFICIENT_DATA; ignore → keep current state; breaching → ALARM; notBreaching → OK.
  • 0 X X - X: ALARM under all four settings, because three real points are available and breaching, so the setting is ignored.
  • - - X - -: missing → ALARM, breaching → ALARM, notBreaching → OK, ignore → keep current state (the docs' "premature alarm state" special case).

Caveat: the real logic includes an "avoid premature transitions" rule and differs for wall-clock windows. The docs spell it out; treat my summary as a mental model, and re-read their tables before you rely on an edge case.

One safety note straight from the docs: alarms on EC2 metrics can briefly enter INSUFFICIENT_DATA if metric reporting is interrupted, even when the instance is healthy. For EC2 alarms that stop, terminate, reboot or recover an instance, AWS recommends treating missing data as missing and triggering only on ALARM. Otherwise a reporting hiccup could reboot a healthy server.

4. Anomaly detection alarms: no number, a learned band

Picking a static threshold is easy for "disk is 95 percent full", and awkward for something like request count that is naturally low at 3 a.m. and high at lunch. Anomaly detection handles that. You enable it on a metric and CloudWatch applies statistical and machine learning algorithms to the metric's past data to build a model of expected values. According to the docs the model accounts for trends and for hourly, daily and weekly patterns, it trains on up to two weeks of data (you can enable it with less), and it keeps adjusting over time.

The model is specific to a metric and a statistic: enable it with Average and the model is for Average. You choose an anomaly detection threshold, a number (it doesn't need to be whole) that sets the band's thickness. Higher means a thicker band that tolerates more wobble; lower means a thinner band that fires on smaller deviations.

The alarm's condition is not a number but a position relative to the band: greater than the upper bound, lower than the lower bound, or outside the band in either direction. In the CLI these are the operators GreaterThanUpperThreshold, LessThanLowerThreshold and LessThanLowerOrGreaterThanUpperThreshold (documented as anomaly detection only).

Practical details from the docs:

  • For a brand-new model it can take up to 3 hours for the real band to appear in the graph, and up to two weeks for the model to train so the band becomes more accurate. If a model already exists, up to 15 minutes. Until then the band shown is an approximation.
  • The alarm's period must be one minute or longer.
  • You can exclude time ranges (outages, deployments, holidays) from training. The docs call this critical for unusual events. You can also set a time zone for Daylight Saving sensitivity.
  • Anomaly detection models for alarms incur charges. The docs advise deleting the alarm first and the model second, because evaluating an anomaly alarm re-creates a missing detector on your behalf.
  • Anomaly detection also works on metric math expressions, and works on both AWS-vended and custom metrics. For cross-account alarms the ANOMALY_DETECTION_BAND function is not supported.

The documented CLI route is two steps: first put-anomaly-detector with a --single-metric-anomaly-detector JSON (namespace, metric name, dimensions, Stat), then put-metric-alarm with --threshold-metric-id pointing at an expression such as ANOMALY_DETECTION_BAND(m1, 2), where the 2 is that band-thickness number.

Simplification: "machine learning builds a model of normal" is the docs' framing. I'm not describing the internals because the docs don't, and a model can still raise false alarms or miss things; the console even has an "Improve this alarm" feedback flow for exactly that.

5. Composite alarms: one alarm built from alarms

If five separate alarms all fire during one incident, five notifications is noise. A composite alarm watches the states of other alarms (metric alarms or other composite alarms) and applies a rule. It doesn't look at metrics directly. Reference an alarm with one of three state functions, and combine them:

  • ALARM("name"), OK("name"), INSUFFICIENT_DATA("name"): each is TRUE when that alarm is in that state. You can use the name or the ARN.
  • Operators AND, OR, NOT, parentheses for grouping, and the AT_LEAST(M, STATE_CONDITION, (alarm1, alarm2, ...)) function (M can be a number or a percentage like 50%).

Examples from the docs: ALARM(CPUUtilizationTooHigh) AND ALARM(DiskReadOpsTooHigh) (both at once), and ALARM(CPUUtilizationTooHigh) AND NOT ALARM(DeploymentInProgress), which quiets a CPU alarm during a deployment window (where DeploymentInProgress is an alarm you maintain for that purpose).

Limits and rules to know (from the docs and the put-composite-alarm reference):

  • Rule length 1 to 10,240 characters; up to 100 child alarms and up to 500 elements in a rule. One alarm can be referenced by up to 150 composite alarms.
  • Child alarms must be in the same account and Region as the composite, with an exception for a cross-account observability monitoring account. The alarm docs also say creating cross-account composite alarms isn't supported in general, so check the current docs for your setup.
  • Composite alarms can notify SNS, invoke Lambda, create OpsItems and create Incident Manager incidents. They cannot run EC2 or Auto Scaling actions.
  • Don't make two composites depend on each other. The docs warn this stops both from being evaluated and blocks deletion; the escape hatch is changing one rule to FALSE.
  • Actions suppressor: an optional setting (--actions-suppressor, plus a wait period and an extension period, both required with it) that holds back the composite's actions while a named alarm is in ALARM. The CLI reference shows the options but gives no worked example, and doesn't state limits for the two periods, so treat the details as something to confirm in the live docs.

6. Alarm actions: what happens when the state changes

An alarm can run actions on a transition into OK, ALARM or INSUFFICIENT_DATA. In the CLI these are --ok-actions, --alarm-actions and --insufficient-data-actions, each accepting up to 5 actions. Supported actions, per the docs:

  • SNS notification: tell one or more subscribers (people or applications).
  • Lambda: invoke a function, which the docs call the easiest route to custom automation.
  • EC2 actions (alarms on EC2 metrics): stop, terminate, reboot or recover an instance.
  • Auto Scaling: trigger a scaling policy on an EC2 Auto Scaling group or an Application Auto Scaling target.
  • Systems Manager: create an OpsItem or an Incident Manager incident, only when the alarm goes into ALARM.
  • Start a CloudWatch investigation, also on ALARM.

Alarms also emit events to Amazon EventBridge on state changes, which lets you wire up further reactions. (EventBridge gets its own digest later in this track.)

The rule that trips people up: except for Auto Scaling actions, actions happen only on state transitions and are not repeated while the alarm stays in the state, even for hours or days. Auto Scaling actions are the exception: the alarm keeps invoking them once per minute while it remains in that state. So an alarm sitting in ALARM isn't re-paging you; it paged you once, when it changed.

For Auto Scaling, how the alarm comes to exist depends on the policy type: for simple and step scaling you create a metric alarm and attach it; for target tracking the Auto Scaling service creates and manages the high and low alarms for you, and the docs say not to edit or delete them.

Honest caveats from the docs: CloudWatch doesn't test or validate the actions you specify, nor detect SNS or Auto Scaling errors from invoking non-existent actions, so make sure the topic or policy really exists. And for temporary silence, the docs describe alarm mute rules (scheduled windows that mute actions automatically) as different from DisableAlarmActions, which stays off until you call EnableAlarmActions.

7. Useful day-to-day operations

  • describe-alarms lists alarms, including by state; describe-alarm-history shows past transitions (history is kept 30 days).
  • set-alarm-state forces an alarm into a state to test your actions. The docs note this change is temporary and lasts only until the next alarm evaluation.
  • put-metric-alarm creates or updates; if an alarm with the same name exists it is overwritten.

Why it matters

Every other monitoring habit you build (autoscaling on load, paging on-call, auto-recovering a stuck instance) hangs off alarm behaviour. Most "my alarm is flapping" or "my alarm never fires" stories come down to three things from this digest: M and N, the missing-data setting, and the fact that actions fire on transitions. Composite alarms are how teams keep alert volume humane once there are dozens of metrics.

Remember this

  • An alarm is a state machine (OK, ALARM, INSUFFICIENT_DATA) driven by Period, N, and M; "M out of N" points need not be consecutive.
  • Missing data is a setting, not a bug. Choose it by asking what silence means for that metric (default is missing).
  • Anomaly detection swaps your fixed number for a learned expected band; a bigger threshold number means a thicker band, and it takes time to train.
  • Composite alarms combine alarm states with AND/OR/NOT/AT_LEAST to cut noise, but can't run EC2 or Auto Scaling actions.
  • Actions run on state changes, except Auto Scaling, which repeats once a minute while the alarm stays in state.

Try it yourself

Use a throwaway test account or sandbox. I haven't run these myself against a live account; commands are taken from the CLI reference pages linked below, so check them before use. Alarms and anomaly detection models can cost money, so delete everything afterwards.

  1. Make a static alarm and force it to fire. Create an SNS topic and subscribe your email, then run aws cloudwatch put-metric-alarm on a custom metric you publish (reuse your namespace from the metrics digest) with a threshold of your choice, --alarm-actions pointing at the topic. Then run aws cloudwatch set-alarm-state --alarm-name ... --state-value ALARM --state-reason "test". Done when: you get the email, and you can explain why the alarm slid back on its own at the next evaluation.
  2. Prove M out of N. Create an alarm with --evaluation-periods 5 --datapoints-to-alarm 3 and publish values by hand with put-metric-data, one per period, mixing breaching and normal values. Done when: you've seen it go to ALARM with three non-consecutive breaches and can sketch which 5 points it was looking at.
  3. Compare the four missing-data settings. Create four otherwise-identical alarms on a metric you stop publishing, one per --treat-missing-data value, and wait. Done when: you've recorded each alarm's resulting state and matched it against the docs' table.
  4. Create an anomaly detection alarm. Follow the two-step CLI sequence from the docs (put-anomaly-detector, then put-metric-alarm with ANOMALY_DETECTION_BAND(m1, 2)) on a metric that already has history. Done when: the alarm exists, you can see the band in the console (allowing for the training delay), and you've changed the band number and noted what happens to the band's width. Then delete the alarm first, the model second.
  5. Silence a noisy pair with a composite. Create two metric alarms with no actions, then put-composite-alarm with --alarm-rule "ALARM(A) AND ALARM(B)" and an SNS action. Use set-alarm-state on each child. Done when: you get no email with only one child in ALARM and exactly one email when both are.
  6. Watch "actions only on transitions". Leave an alarm sitting in ALARM state with an SNS action and read describe-alarm-history. Done when: you can point to one state-change entry and explain why you were not notified again while it stayed there.
