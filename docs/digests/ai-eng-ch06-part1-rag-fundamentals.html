RAG: How Retrieval-Augmented Generation Actually Works

A model is only as good as the information it has in front of it when you ask it something. RAG is the main technique for handing a model exactly the right slice of information, out of a much bigger pile, for each individual question. This part covers what RAG is, how retrieval algorithms actually rank documents, and how real systems squeeze more accuracy out of the pipeline. Agents (the other big pattern in this chapter) get their own part next.

In one line

RAG fetches the small number of relevant documents (or chunks, images, or table rows) out of a much larger external store, and hands only those to the model, instead of hoping the model already "knows" the answer or trying to stuff everything into one giant prompt.

The big idea

A model needs two things to answer a question well: instructions on how to behave, and the actual information needed to answer correctly. Instructions are usually the same for every query (that's the system prompt), but the information a specific question needs is different every time. RAG is the standard way to build that per-query information on the fly: a retriever searches an external source (a document database, a user's chat history, the internet) for the pieces most relevant to this exact question, and only those pieces get added to the prompt before the model generates a response. It sounds simple, but almost all of the engineering difficulty in RAG lives in one question: out of everything in the database, how do you reliably find the handful of pieces that are actually relevant?

Key terms

  • RAG (retrieval-augmented generation) — a technique where a model's response is grounded by first retrieving relevant information from an external source and adding it to the prompt.
  • Retriever — the component that searches an external source and returns the pieces of data most relevant to a query.
  • Generator — the model that produces the final response, using the retrieved information plus the original query.
  • External memory source — wherever the retrievable data lives: an internal document database, a user's past chat sessions, the internet, a SQL table, and so on.
  • Context construction — the general job of assembling the information a model needs for a specific query. RAG is one way of doing this; it plays the same role for a foundation model that feature engineering plays for a classical ML model.
  • Indexing — processing your data ahead of time so it can be searched quickly later (the opposite of scanning everything from scratch on every query).
  • Querying — the act of sending a request to the index to fetch the data relevant to it.
  • Chunk — a manageable-sized piece of a larger document. Documents get split into chunks so you never have to retrieve (and pay for, and fit in context) an entire huge document at once.
  • Term-based / lexical retrieval — ranking documents by matching the literal words (terms) in the query, not their meaning.
  • Term frequency (TF) — how many times a given term appears in a document; used as a rough signal of relevance.
  • Inverse document frequency (IDF) — a measure of how rare (and therefore informative) a term is across the whole document collection; common words like "the" score low, rare words score high.
  • TF-IDF — a scoring formula that multiplies a term's frequency in a document by its rarity across all documents, so a document scores higher when it contains query terms often and those terms are actually distinctive.
  • Inverted index — a lookup table that maps each term straight to the list of documents that contain it, so you don't have to scan every document to answer "which documents contain X?".
  • BM25 — a widely used, improved version of TF-IDF that also accounts for document length, so a long document doesn't win purely by containing more words.
  • Tokenization — breaking text into individual units (terms) before indexing or searching it. A naive word-split can break multi-word phrases like "hot dog" apart and lose their meaning.
  • Embedding-based / semantic retrieval — ranking documents by how close their meaning is to the query's meaning, using embeddings, rather than by matching literal words.
  • Vector database — a database built to store embeddings (vectors) and search them efficiently.
  • Vector search / nearest-neighbor search — given a query embedding, finding the stored embeddings that are closest to it.
  • k-nearest neighbors (k-NN) — the exact (but slow) way to do vector search: compare the query to every single vector in the database and keep the closest k.
  • Approximate nearest neighbor (ANN) — a family of faster algorithms that find almost the closest vectors instead of guaranteeing the exact closest ones, trading a little accuracy for a lot of speed at scale.
  • Sparse vs. dense vector — a sparse vector is mostly zeros (a one-hot term vector is a classic example); a dense vector has mostly non-zero values (typical embeddings are dense).
  • Hybrid search — combining term-based and embedding-based retrieval in the same system, to get the strengths of both.
  • Reranking — taking an initial, cheaply-produced list of candidate documents and re-scoring them with a more precise (usually more expensive) method to improve the final order.
  • Reciprocal rank fusion (RRF) — a formula for merging several different ranked lists (say, one from a term-based retriever and one from an embedding-based retriever) into a single combined ranking.
  • Query rewriting — rephrasing a query (often using another model) so it stands on its own before it's used to retrieve documents, especially useful when a query only makes sense in the context of an earlier conversation.
  • Contextual retrieval — enriching a chunk with extra context (metadata, keywords, a short summary of where it sits in the original document) before indexing it, so it's easier to find later.
  • Context precision / context recall — precision asks "of what I retrieved, how much was actually relevant?"; recall asks "of everything that was relevant, how much did I actually retrieve?".
  • Multimodal RAG — RAG where the retrieved material can be images, video, or audio, not just text.
  • Text-to-SQL — automatically turning a natural-language question into a SQL query, so a model can pull an answer out of a structured data table instead of unstructured text.

How it works

Here's the grounding picture before the details: a model that lacks the right information is a lot like a person answering a question with no notes and no ability to look anything up. It'll do its best, and its best might be a confident, wrong answer (a hallucination). RAG's whole premise is that if you hand the model a short, accurate set of notes right before it answers, it doesn't need to know everything in advance, it just needs to be handed the right slice of information at the right moment. The one detail that shapes everything else in this section: the "right slice" has to be found automatically, out of a store that could hold anything from a few dozen documents to hundreds of millions, which is exactly why retrieval is a whole engineering discipline of its own.

1. What RAG actually is, and why a bigger context window doesn't replace it

RAG's original motivation, as introduced in the 2020 paper that coined the term, was straightforward: some tasks need knowledge that simply can't fit into a model's prompt all at once, so instead of trying to cram everything in, you retrieve only the pieces most relevant to the current query and feed the model those. An earlier 2017 paper had already shown the basic shape of this idea (called "retrieve-then-generate" there): given a question, first retrieve a handful of the most relevant documents, then have a second model read those documents and generate an answer from them.

A simple example: imagine a customer support assistant gets asked "Can Acme's fancy-printer-A300 print 100 pages per second?" The model has no way of knowing that answer on its own, it was never trained on Acme's product spec sheet. But if a retriever pulls up the actual printer-A300 spec document and hands it to the model alongside the question, the model can now read the real number and answer correctly. That's the entire trick: instead of a generic prompt, each query gets its own custom-built context.

It's tempting to think that as models support longer and longer context windows, RAG will simply become unnecessary; just paste everything in. Two things push back on that. First, however long a context window gets, the amount of data organizations want to draw on tends to grow just as fast (or faster), since people keep generating new data and rarely delete old data. There will pretty much always be applications with more relevant information available than fits in even a very large context window. Second, and just as important, a model that can technically accept a huge context doesn't necessarily use all of it well. Feeding a model more tokens than it needs adds cost and latency on every single call, and models can end up focusing on the wrong parts of a long context instead of the genuinely relevant bit. RAG's job is to hand over less, but make sure what's handed over is the right less. One useful data point: Anthropic has publicly suggested that if your entire knowledge base is under roughly 200,000 tokens (about 500 pages), you may not need RAG at all and can just put the whole thing in the prompt. That's a real, useful rule of thumb for a small knowledge base on a model with a large context window, but it's specific to Anthropic's own guidance and their models at the time it was written, not a universal cutoff for every model or every use case.

2. The RAG architecture: a retriever and a generator, doing two different jobs

Structurally, a RAG system has exactly two moving parts: a retriever that searches an external source and returns the most relevant material, and a generator (a regular language model) that turns that material plus the original query into a final answer. In the original RAG paper these two parts were trained together end-to-end. Most real systems today take a simpler, more modular route: pick an off-the-shelf retriever and an off-the-shelf model and wire them together, which is far less work, even though training the whole pipeline jointly can improve accuracy further if you have the resources for it.

A retriever itself does two separate jobs. Indexing happens ahead of time: it processes your raw data (say, a company's memos, contracts, and meeting notes) so it can be found quickly later. Because a single document could be 10 tokens or a million tokens, documents usually get split into smaller chunks first, so retrieval never has to hand over something unmanageably huge. Querying happens at request time: given the user's question, the retriever searches the index and returns the chunks judged most relevant, which then get merged with the user's original prompt (with a little formatting/cleanup) before that combined prompt goes to the generator.

3. Two families of retrieval algorithm: matching words versus matching meaning

Retrieval isn't new or unique to RAG, it's the same core problem search engines, recommender systems, and log search tools have solved for decades: given a query, rank a pile of documents by relevance. There are two broad families worth knowing well.

Term-based (lexical) retrieval matches literal words. Given the query "AI engineering," it looks for documents that literally contain those words. The obvious problem is that lots of documents might contain a term, so you need a way to rank them. Term frequency (TF) counts how often a term shows up in a document, on the assumption that a document mentioning "vietnamese" ten times is probably more about Vietnamese food than one mentioning it once. But raw frequency alone isn't enough, because some words (like "for" or "at") appear everywhere and carry little meaning. Inverse document frequency (IDF) fixes that by scoring a term higher the rarer it is across the whole collection: if 5 out of 10 documents contain a term, its IDF is 10/5 = 2; a term that appears in only 1 document scores far higher. TF-IDF multiplies the two together, so a document scores well when it repeats a term that's also genuinely distinctive. BM25, still an industry workhorse today, improves on plain TF-IDF mainly by normalizing for document length, so a long document doesn't automatically win just by containing more words overall. Term-based systems typically store an inverted index, essentially a dictionary from each term straight to the list of documents (and how often it appears in each) that contain it, which makes lookups fast. One wrinkle worth knowing: tokenization, the step of splitting text into terms, can break multi-word phrases apart (splitting "hot dog" into "hot" and "dog" loses the original meaning of either word), which is why some systems also track common multi-word phrases (n-grams) as their own terms.

Embedding-based (semantic) retrieval matches meaning instead of literal words. This matters because word overlap doesn't equal relevance: searching "transformer architecture" with a term-based system might return documents about the electrical device or the movie franchise, since they share the literal word "transformer." An embedding-based retriever instead converts both the documents and the query into embeddings (dense numeric vectors that aim to capture meaning) using the same embedding model, and then looks for document embeddings that sit close to the query's embedding in that vector space. The store for these vectors is called a vector database, and finding the closest vectors to a query is called vector search, framed as a nearest-neighbor problem. The exact way to do this, k-nearest neighbors (k-NN), compares the query to literally every vector in the database and keeps the closest k; it's precise but far too slow once a database gets large. That's why large-scale systems use approximate nearest neighbor (ANN) algorithms instead, which sacrifice a little precision for a lot of speed. A few well-known ANN approaches, so the names aren't a mystery if you run into them: LSH hashes similar vectors into the same buckets; HNSW builds a multi-layer graph and searches by walking its edges (generally high accuracy and fast queries, but slower and heavier to build); IVF clusters vectors with k-means and only searches the nearest clusters; product quantization compresses each vector into a simpler, lower-dimensional form to speed up distance calculations; and Annoy builds multiple random binary trees to narrow the search space. None of this usually needs to be built from scratch: libraries like FAISS, Google's ScaNN, Spotify's Annoy, and Hnswlib implement these for you.

Because each approach has real weaknesses, production retrieval systems commonly combine them, called hybrid search. One pattern runs them in sequence: a cheap, fast retriever (typically term-based) fetches a broad set of candidates first, then a more precise, more expensive method (typically embedding-based) re-scores just those candidates. This second step is called reranking. Another pattern runs both retrievers in parallel and merges their two ranked lists into one, using an algorithm called reciprocal rank fusion (RRF): intuitively, a document ranked #1 by a retriever contributes a score of 1/1 = 1, ranked #2 contributes 1/2 = 0.5, and so on, and a document's final score is the sum of its contributions across every retriever it appeared in. (The real formula divides by k + rank rather than just rank, where k is a constant, commonly 60, that keeps the fusion from being dominated purely by whoever ranked first and avoids dividing by zero — but the rank-1-beats-rank-2 intuition above is the core idea.) A document that two different retrievers both rank highly ends up outranking a document only one retriever liked, which is exactly the point of combining signals.

4. Squeezing more accuracy out of retrieval: chunking, reranking, rewriting, and enrichment

Beyond picking an algorithm, four practical tactics have an outsized effect on whether a retrieval system actually finds the right thing.

Chunking strategy. How you split documents up front shapes everything retrieval can do later. The simplest approach splits by a fixed unit (say, every 2,048 characters, or every 512 words, or every 20 sentences). A more careful approach splits recursively: try sections first, and only fall back to splitting a section into paragraphs (and a paragraph into sentences) if it's still too big, which keeps related text together longer. The catch with any hard split is that it can cut a chunk off mid-thought. Take the sentence "I left my wife a note": split naively into "I left my wife" and "a note," and neither half means anything on its own. That's why chunks are usually given a small overlap (say, 20 characters of overlap on a 2,048-character chunk) so a boundary detail doesn't just vanish. Chunk size itself is a real trade-off: smaller chunks let you fit more distinct pieces of information into the model's context window (halve the chunk size and you can fit roughly twice as many), but a chunk that's too small can separate a fact from the context it needs to make sense, and more chunks also means more embeddings to generate, store, and search, which costs more compute and can slow queries down. There's no universally correct chunk size; it has to be tuned per use case.

Reranking. Beyond the "cheap retriever, then precise reranker" pattern mentioned above, documents can also be reranked by recency, useful for anything time-sensitive like a news aggregator, an email assistant, or stock analysis, where a stale but topically-perfect match should often lose to a slightly-less-perfect but current one. Worth knowing: ranking position matters less in this "context reranking" setting than in classic search. In a search engine, whether a result is #1 or #5 is everything. In RAG, as long as a genuinely relevant chunk makes it into the context at all, exactly where it sits matters less, though models can still process information at the very start or end of a long context somewhat better than the middle, so order isn't completely irrelevant either.

Query rewriting (also called query reformulation or expansion) matters most in multi-turn conversations. Picture this exchange: "When did John Doe last buy something from us?" -> "He bought a hat two weeks ago." -> "How about Emily Doe?" That last question is meaningless on its own; used as-is to retrieve documents, it would likely return junk. A rewriting step (often just another model call, prompted with the conversation so far) turns it into a standalone query like "When did Emily Doe last buy something from us?" before it ever reaches the retriever. This gets genuinely tricky when it requires knowledge the system doesn't have yet, for example if someone asks "How about his wife?" and the system would need to first look up who "his wife" actually is. In that case, the honest and correct behavior is for the rewriting step to recognize the query can't be resolved yet, rather than guessing a name and confidently retrieving the wrong person's data.

Contextual retrieval means enriching a chunk before you index it, so it's easier to find later. The simplest version tags a chunk with metadata like keywords, product descriptions, or captions. A more targeted version pulls out specific entities that matter to your domain, for instance a distinctive error code, and adds it explicitly as searchable metadata, since converting a chunk into an embedding can otherwise bury an exact string like that inside a fuzzy vector where literal-keyword search can no longer find it. You can also enrich a support-article chunk with the actual questions it answers ("how do I reset my password," "I forgot my password," "I can't log in"), so a retriever matches on how users actually phrase things, not just the article's own wording. A more thorough version, described by Anthropic in 2024, uses an AI model to generate a short (roughly 50-100 token) note that situates a chunk within its original document (what document is this from, what's it about) and prepends that note to the chunk before indexing it, so an isolated-looking chunk still carries enough context to be found and understood correctly.

5. Judging whether your retriever is actually any good

Two metrics anchor most retrieval evaluation. Context precision (also called context relevance) asks: of everything retrieved, what fraction was actually relevant to the query? Context recall asks the reverse: of everything in the database that was relevant, what fraction did the retriever actually find? To measure these you build an evaluation set of test queries with documents labeled relevant or not (by humans or by an AI judge), then score the retriever against it. Recall is more expensive to compute in practice, since it technically requires labeling every document in the whole database against every test query, which is why some production RAG frameworks only track precision. If the exact order of results matters (not just whether the right document showed up, but whether it showed up near the top), ranking-aware metrics like NDCG, MAP, and MRR are used instead. For the embedding side specifically, embedding quality itself gets evaluated too, either independently (do similar things get similar embeddings?) or against benchmarks built for the purpose, like MTEB, which scores embeddings across many tasks including retrieval, classification, and clustering. Zooming out, a retriever should ultimately be judged three ways: on its own retrieval quality, as part of the whole RAG system's final output quality, and (for embedding-based systems specifically) on the embeddings themselves. It's also worth weighing cost and latency honestly: generating embeddings costs money and gets expensive fast if your underlying data changes often and needs re-embedding regularly, and vector storage and search have their own operating costs on top of whatever you're already paying for model calls.

6. RAG beyond plain text: images and tables

Everything above assumed the external source was text documents, but the same core idea, retrieve the relevant piece, then generate from it, extends to other data types. In multimodal RAG, if the generator model can understand images (or audio, or video), the retriever can fetch those too. For example, asked "what's the color of the house in the Pixar movie Up?", a multimodal RAG system could retrieve an actual picture of the house to hand to the model alongside the question, rather than relying purely on text descriptions. Doing this by content (not just by caption or tag) requires a multimodal embedding model, one that can place both images and text into the same shared embedding space, so a text query and an image can be compared directly. CLIP is a well-known example of this kind of model: everything (text and images) gets embedded into one shared space ahead of time, the query gets embedded the same way at request time, and the vector database returns whichever texts and images land closest to it.

RAG can also pull from structured, tabular data instead of unstructured documents. Picture a small e-commerce store with a Sales table (order ID, timestamp, product, price, units). A question like "how many units of a given product sold in the last 7 days?" can't be answered by retrieving a document, it needs an actual database query. The workflow here is: text-to-SQL (a model turns the natural-language question into a real SQL query, using the table's schema), then execution (that query actually runs against the table), then generation (a model turns the raw query result back into a natural-language answer). If there are more tables than could ever fit into the model's context at once, an extra step is usually needed first, to narrow down which specific tables are even relevant to the question, before generating SQL against just those.

Why it matters

Retrieval quality is very often the actual bottleneck in a "the AI gave a wrong answer" complaint, even though it's easy to blame the generator model instead. If the retriever hands over the wrong chunk (or nothing at all), a perfectly capable model has no real chance of answering correctly, since it's reasoning from missing or irrelevant information rather than the model being "bad." That's also why the tactics in this part (chunking, hybrid search, reranking, query rewriting, contextual retrieval) matter so much in practice: they're where the real, compounding gains in a RAG system's quality tend to come from, often more so than swapping to a bigger or newer generator model. And it sets up the next big idea directly: a text retriever and a SQL executor are both, quietly, examples of giving a model a tool it can call to go get information it doesn't already have. That's exactly the concept the next part (agents) builds on, just with a much wider range of tools than retrieval alone.

Remember this

  • RAG's whole job is context construction: finding the small subset of external information relevant to this specific query and handing only that to the model, instead of hoping the model already knows the answer.
  • Longer context windows don't make RAG obsolete. Data grows faster than context limits, and models don't necessarily use very long context well even when it fits.
  • Term-based retrieval (TF-IDF, BM25) matches literal words: fast and cheap, but blind to meaning. Embedding-based retrieval matches meaning via vectors: smarter about semantics, but slower, costlier, and can bury exact keywords. Real systems often combine both (hybrid search).
  • Chunking strategy, reranking, query rewriting, and contextual retrieval are where a lot of real-world RAG quality is actually won or lost, often more than which specific algorithm or model you pick.
  • A retriever should be evaluated on its own (precision, recall, ranking metrics), not just judged by whether the final generated answer sounded right.

Try it yourself

  1. Build a tiny TF-IDF retriever by hand. Take 8-10 short text snippets (a paragraph each), write a few test queries, and compute TF-IDF scores manually or in a short script (no library) to rank the snippets for each query. Done when: you can show, for one query, exactly which snippet won and why, using the actual TF and IDF numbers.
  2. Compare term-based vs. embedding-based retrieval on the same small dataset. Use the same snippets from the previous exercise. Run a keyword search library (or your own script) and an embedding-based search (any small embedding model or API) against the same queries. Done when: you've found at least one query where the two approaches disagree, and can explain why.
  3. Build a chunking-with-overlap demo. Take a multi-paragraph document, write a function that splits it into fixed-size chunks with and without overlap, and manually inspect a few boundary chunks. Done when: you can show a specific example where the no-overlap version loses meaning that the overlap version preserves.
  4. Implement reciprocal rank fusion. Manually create two different ranked lists of the same 6-8 items (pretend they came from two different retrievers), then write a short script implementing the RRF formula (with k=60) to merge them into one ranking. Done when: you can point to an item that moved up because both lists ranked it reasonably well, even though neither ranked it #1.
  5. Write a query rewriter. Simulate a short multi-turn conversation (3-4 turns) where later questions depend on earlier context (like the "How about Emily Doe?" example), and write a prompt that gets a model to rewrite each ambiguous follow-up into a standalone query. Done when: you have at least one example where the rewritten query would clearly retrieve something correct that the raw query would not.
  6. Measure context precision and recall on a toy retrieval set. Build a tiny document set (15-20 short documents) and 3 test queries, manually label which documents are relevant to each query, then run a retriever and compute precision and recall against your labels. Done when: you can report both numbers for at least one query and explain one concrete way you could change the retriever to improve recall.

Go deeper

If you build anything real with RAG, spend extra time on chunking strategy and contextual retrieval specifically. They're unglamorous compared to picking a fancier vector database or a newer embedding model, but they tend to move real-world answer quality the most, precisely because a great generator model still can't recover from being handed the wrong chunk, or a chunk missing the context it needed to make sense.
