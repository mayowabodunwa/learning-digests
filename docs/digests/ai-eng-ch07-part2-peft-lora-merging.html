Finetuning: PEFT, LoRA, Model Merging and Practical Tactics

Part 1 ended on a number: fully finetuning a model means paying memory for gradients and optimizer states on every single parameter. This part is the answer to that bill. We'll go from full finetuning to parameter-efficient finetuning (PEFT), take LoRA apart piece by piece, see how QLoRA stacks quantization on top, then look at model merging (combining models instead of training one), and finish with the practical choices: base model, method, framework and the handful of hyperparameters that matter. The chapter's own Summary closes things out. The author calls model merging "exciting but more experimental", and I've flagged where the ground is still shifting.

In one line

Instead of updating every weight, you train a tiny add-on (like LoRA's two small matrices) while the big model stays frozen, optionally squeeze the frozen part to 4 bits, and optionally blend several finetuned models into one.

The big idea

Memory scales with trainable parameters, so the whole field of efficient finetuning is a hunt for ways to get close to full-finetuning quality while training far fewer numbers. Adapter methods add small trainable modules; soft prompt methods add trainable tokens; LoRA does the adapter trick in a form that can be folded back into the original weights so it costs nothing extra at inference. Because the add-ons are small and separate from the base model, they're also modular: you can keep one base model and swap or combine many adapters. Model merging pushes that modularity further by combining whole models. The rest is operational: pick a base model, pick a method, pick a framework, set a few hyperparameters.

Key terms

  • Full finetuning: updating every parameter; trainable parameters equal total parameters.
  • Partial finetuning: updating only some parameters, such as freezing the early layers and training the last one.
  • PEFT: parameter-efficient finetuning. Getting close to full-finetuning performance with far fewer trainable parameters.
  • Adapter (additive method): a small extra module added to a model; only the adapter is trained.
  • Soft prompt: trainable, non-human-readable vectors fed to the model alongside the real input tokens. Contrast with a hard prompt, the readable text you write.
  • LoRA: Low-Rank Adaptation. Represents the weight change as the product of two small matrices.
  • Rank (r): the shared inner size of LoRA's two small matrices. Smaller r means fewer trainable parameters.
  • Alpha (α): a LoRA setting controlling how strongly the learned change is mixed into the original matrix.
  • Low-rank factorization: approximating a big matrix as the product of two smaller ones. Lossy.
  • Multi-LoRA serving: serving several LoRA-finetuned models that share one base model.
  • QLoRA / NF4: LoRA with the frozen base weights stored in 4 bits (NormalFloat-4 format).
  • Model merging: combining the parameters of multiple models into one new model.
  • Ensembling: combining the outputs of several models, each left intact.
  • Catastrophic forgetting: a network losing an old skill when trained on a new task.
  • Task vector (delta parameters): finetuned weights minus base weights; the "essence" of what the finetune changed.
  • SLERP: spherical linear interpolation, a way to blend two models along the shortest arc between them rather than a straight line.
  • Layer stacking (passthrough, frankenmerging): building a model by stacking layers taken from different models.
  • Hyperparameter: a training setting you choose (learning rate, batch size, epochs) rather than something the model learns.
  • Learning rate, batch size, epoch, gradient accumulation: defined in the tactics section below.

How it works

Grounding: why we can't just finetune everything

Early on, models were small enough that you just finetuned the whole thing. That's full finetuning: it looks like training, except it starts from already-trained weights instead of random ones. The problem is arithmetic you already know from Part 1. The chapter's worked example is a 7B model in a 16-bit format: 14 GB for the weights, plus 7B x 3 x 2 bytes = 42 GB for gradients and Adam's two states, so 56 GB, and that is before counting activations. Most consumer GPUs have 12 to 24 GB, with high-end ones reaching 48 GB (the chapter's figures, which will date). Full finetuning for supervised and preference tuning also wants a lot of high-quality labeled data that most people can't afford.

You can attack the memory problem two ways: shrink the footprint (quantization, fewer trainable parameters) or use the hardware's memory better. An example of the second is CPU offloading, where excess memory spills to the CPU, as DeepSpeed does. This part concentrates on the first.

From partial finetuning to PEFT

The first idea was partial finetuning: freeze most layers and train a few. With ten layers you might freeze nine and train the last (commonly the layers nearest the output, since they tend to be more task-specific and earlier ones more general). That cuts trainable parameters to 10%. But it's parameter-inefficient: the chapter cites a study showing BERT large needed to update about 25% of its parameters to match full finetuning on the GLUE benchmark.

The question became: how do you get near-full performance with several orders of magnitude fewer trainable parameters? Techniques that do are called parameter-efficient (the chapter notes there's no hard threshold). The idea, introduced by Houlsby et al. (2019), was to insert small adapter modules into the model (two per transformer block for BERT), freeze everything original, and train only the adapters. They reached performance within 0.4% of full finetuning on GLUE with only about 3% of the trainable parameters. The downside: adapters are extra layers, so every forward pass does more work and inference gets slower.

PEFT methods tend to be sample-efficient too. The chapter says full finetuning may need tens of thousands to millions of examples for notable gains, while some PEFT methods can do well with a few thousand. Caveat: these are broad ranges that vary with model and task.

Two families of PEFT

  • Adapter-based (additive) methods add parameters or modules to the model. LoRA is by far the most popular. Others named: BitFit, IA3 (attractive for multi-task finetuning, reported to beat LoRA and even full finetuning in some cases), and LongLoRA (a LoRA variant for longer context).
  • Soft prompt methods leave the model alone and add trainable tokens to the input. Unlike a hard prompt (readable discrete tokens like "write" or "a"), a soft prompt is a set of continuous vectors resembling embeddings, not readable, and it can be tuned by backpropagation. Some call it a crossover between prompt engineering and finetuning. Names you'll meet (prefix tuning, P-Tuning, prompt tuning) differ mainly in where the soft tokens go: prefix tuning puts them at every transformer layer, while prompt tuning puts them only on the embedded input. PEFT frameworks usually implement them for you.

To gauge what people actually use, the author counted over 1,000 open issues on the Hugging Face peft GitHub repository in October 2024 as a popularity proxy. LoRA dominated, soft prompts were less common but growing. That's a rough proxy by one analysis, not a market survey.

LoRA, step by step

LoRA's trick: it adds trainable parameters in a way that can be merged back into the original weights, so after training there are no extra layers and no extra inference latency. It works on individual weight matrices.

Take a weight matrix W of size n x m. LoRA:

  1. Picks a small number r (the rank) and creates two matrices, A (n x r) and B (r x m). Their product A x B has the same shape as W.
  2. Builds the new matrix W' = W + (alpha / r) x A x B, where alpha controls how much of the learned change gets mixed in.
  3. During finetuning updates only A and B. W stays frozen.

Why does this save parameters? Low-rank factorization. A 9 x 9 matrix has 81 numbers, but it can be approximated as a 9 x 1 times a 1 x 9, which is only 18 numbers. The catch (label this clearly): the approximation is lossy, and a higher rank preserves more information. A real example with numbers I computed: a 4096 x 4096 matrix has 16,777,216 parameters, but with r = 8 the pair A and B has 4096 x 8 x 2 = 65,536.

Results the chapter reports. In the LoRA paper, GPT-3 finetuned with LoRA matched or beat full finetuning on several tasks using about 4.7M trainable parameters, which is 0.0027% of full finetuning. Those are the paper's numbers for those tasks.

Why does LoRA work at all?

A fair puzzle: if a model needs billions of parameters and examples to learn a behavior, why can a few thousand examples and a sliver of parameters change it? The chapter points to research arguing that large models have a very low intrinsic dimension: pre-training seems to compress what matters for downstream tasks, and bigger models tend to compress further. So the better pre-trained the model, the easier it is to adapt with few parameters and little data. This is an argument from several papers, not a settled proof.

Why not use LoRA to pre-train too? People tried low-rank training for years, with real successes at small scale (the chapter cites SqueezeNet reaching AlexNet-level accuracy with 50 times fewer parameters) and recent LLM attempts (ReLoRA up to 1.3B parameters; GaLore comparable to full-rank at 1B and promising at 7B). It has not been shown at hundreds of billions of parameters, and if the compression argument is right, full-rank pre-training may still be needed first. Treat that as an open question.

Configuring LoRA

Which matrices? LoRA is mostly used on transformers, most commonly on the four attention matrices: query (Wq), key (Wk), value (Wv) and output projection (Wo), applied uniformly to all matrices of that type. With a fixed budget, what should you pick? The LoRA authors had an 18M trainable-parameter budget on GPT-3 175B (0.01% of the model) and compared spending it on one matrix at rank 8, two at rank 4, or all four at rank 2. All four at rank 2 did best on the two benchmarks they tested (WikiSQL and MultiNLI); if you can only choose two, query and value generally did best. I checked their arithmetic: (12,288 x 2 x 2) x 4 = 196,608 per layer, times 96 layers = 18,874,368. Later reports (Databricks, and others) found applying LoRA to the feedforward layers can help even more, though attention-based LoRA tends to give more per unit of memory.

Which rank? A small r, often between 4 and 64, is usually enough for many use cases. Surprisingly, raising r doesn't reliably improve results, and some argue a high r can overfit, though one reported experiment found r = 256 best on its tasks. So: usually small, but test.

Which alpha? The chapter says that in practice the alpha-to-rank ratio is often between 1:8 and 8:1, with small r wanting larger alpha and the reverse. The best combination comes from experiments.

Serving LoRA: merge, or keep separate

There are two ways to serve a LoRA model:

  1. Merge A and B into W before serving. No extra computation at inference, so no added latency. Generally best if you serve one LoRA model.
  2. Keep W, A, B separate and combine at inference. Slightly slower, but excellent for multi-LoRA serving, where many finetuned models share one base.

The storage math is striking. The chapter's scenario: a finetuned model per customer, 100 customers, W of size 4096 x 4096 (about 16.8M parameters), rank 8. Merging gives 100 full copies, about 1.68B parameters. Keeping adapters separate gives one W plus 100 small (A, B) pairs: 16.8M + 65,536 x 100, about 23.3M. I reproduced both numbers in code. Switching from one customer to another also means loading only a small adapter. The chapter notes Apple used multiple LoRA adapters on one roughly 3B-parameter base for different on-device features, with quantization to fit. LoRA adapters can also be shared publicly, for example on Hugging Face or AdapterHub.

The catch with LoRA. Its performance generally doesn't match full finetuning, and it's harder to implement because it modifies the model, so it needs an understanding of the architecture. That's mostly an issue for less popular base models; frameworks like Hugging Face PEFT, Axolotl, unsloth and LitGPT support LoRA for popular models out of the box.

QLoRA: quantize the frozen part

Further shrinking LoRA's few parameters barely helps: the chapter's table shows LoRA adapter memory is tiny next to the weights (for example, about 37.7 MB for GPT-3 175B's adapters versus 350 GB for its 16-bit weights, in its example configuration). The bigger win is quantizing the base. QLoRA stores the frozen weights in 4 bits and dequantizes them to BF16 when computing the forward and backward passes. Its 4-bit format, NF4 (NormalFloat-4), is designed around the observation that pre-trained weights usually follow a roughly normal distribution centered at zero. It also uses paged optimizers that shuttle data between CPU and GPU when the GPU runs out of memory. Together these let a 65B model be finetuned on a single 48 GB GPU, per the paper. The resulting Guanaco models were competitive in the authors' evaluation: in the chapter's table (May 2023, GPT-4 as judge) Guanaco 65B didn't beat GPT-4 but was often preferred to ChatGPT. Caveat: that evaluation is one setup with an LLM judge. And the limitation: NF4 quantization and dequantization are expensive, so QLoRA can lower memory but increase training time.

Model merging and multi-task finetuning

If finetuning customizes one model, model merging customizes by combining several, and you can finetune the pieces first or after. Merging without further finetuning needs no GPUs, which appeals to people with little compute. The chapter's motivations:

  • Better performance. Two models good at different things on one task might combine into something better than either. (The chapter's illustration: one answers the first 60% of questions, another the last 60%, together maybe 80%.)
  • Smaller footprint. Two single-task models merged into one multi-task model with fewer parameters; two adapters on the same base can become one adapter.
  • Multi-task finetuning. The usual options are simultaneous (mix all tasks in one dataset; typically needs more data and training) or sequential (one task after another; risks catastrophic forgetting). Merging offers a third: finetune per task in parallel, then merge, which lets each task be learned well and avoids sequential forgetting.
  • On-device deployment. Phones, laptops, cars and robots have limited memory, so one merged model beats several. On-device matters when data can't leave the device (often privacy), when connectivity is poor, or to cut inference costs.
  • Federated learning. Copies of one model learn separately on different devices' data, then get merged into a new base.

Ensembling vs. merging. Ensembling (an older idea) keeps each model intact and combines their outputs (for example by majority vote), which usually helps but multiplies inference cost because every request calls several models. Merging mixes the parameters and yields one model. The chapter notes many top Open LLM Leaderboard entries were merged models. It also warns many merging techniques are experimental and may become outdated, so it focuses on three high-level approaches.

Merging approach 1: summing

Add the constituent models' weights together, after rescaling if their value ranges differ widely.

  • Linear combination (a plain or weighted average). Surprisingly effective for something so simple, studied since the early 1990s. "Model soups" averaged whole finetuned models to improve accuracy without slowing inference, but it's more common to combine specific parts, such as adapters. It works best for models finetuned from the same base, and this connects to task vectors: subtract the base from a finetuned model and what's left captures what the finetune added (for LoRA, you can build it from the LoRA weights). That enables task arithmetic: add two task vectors to combine abilities, or subtract one to reduce an unwanted behavior. Different architectures or sizes can still be combined by projecting to a common dimension, and some proposals align parameters first, but that's harder and less common.
  • SLERP. Think of each model's vector as a point on a sphere. Rather than a straight line between them, you travel along the shortest arc on the surface (like the shortest flight path between two cities) and stop at a point set by an interpolation factor between 0 and 1: 0.5 is the midpoint, and smaller values stay closer to the first. SLERP is defined for two vectors, so for more you merge sequentially. Tools implement the math for you.
  • Pruning redundant task-specific parameters. Most finetuning changes are tiny and don't matter for the task. TIES-Merging and DARE reset many of those to their base values (zeroing the task vector entries) before merging; the TIES result the chapter shows is that keeping only the top 20% of task-vector parameters performed comparably to keeping all. The reasoning: redundant changes may be harmless in one model but interfere in a merged one, and the more models you merge, the more this matters. The point of pruning here is quality of the merge, not a smaller or faster model.

Merging approach 2: layer stacking

Take layers from one or more models and stack them (also called passthrough or frankenmerging). It can produce unusual architectures and parameter counts, and unlike summing it usually needs more finetuning afterward. Examples from the chapter:

  • Goliath-120B: assembled from two finetuned Llama 2-70B models, taking 72 of 80 layers from each.
  • Mixture-of-experts from a dense model ("sparse upcycling"): copy certain layers several times, add a router that sends each input to the best copy, and keep training. The paper reports this can beat an MoE trained from scratch. Together AI's Mixture-of-Agents, built by combining six weaker open models, reportedly matched GPT-4o on some benchmarks.
  • Model upscaling by depthwise scaling: copy a 32-layer model, sum some layers and stack the rest, then train further. SOLAR 10.7B was made this way, summing 16 layers so the result has 32 x 2 - 16 = 48 layers. Use case: you now have an 80 GB GPU where the old model was sized for 40 GB.

Merging approach 3: concatenation

Concatenate parameters, so the merged component has the sum of the parts. Merge two LoRA adapters of ranks r1 and r2 and you get rank r1 + r2. The chapter doesn't recommend it: there's no memory saving compared with serving the models separately, and the extra performance may not justify the parameters. It's included for completeness.

Finetuning tactics

The chapter's reassurance: much around finetuning is hard (deciding whether to, getting data, maintaining it) but the process itself is more straightforward. You choose three things.

Base model. Early in a project, start with the most powerful model you can afford: if it can't do the task, weaker ones likely can't. If it can, explore cheaper ones against it as a benchmark. Two paths from OpenAI's best-practices guidance as the chapter describes them:

  • Progression path: (1) test your finetuning code on the cheapest, fastest model; (2) test your data on a middling model (if the training loss doesn't go down with more data, something may be wrong); (3) push performance with the best model; (4) train all models to map the price/performance frontier and choose.
  • Distillation path: (1) finetune the strongest affordable model on a small dataset; (2) use it to generate more training data; (3) train a cheaper model on that.

Method. If you're new, try something like LoRA first and consider full finetuning later. Full finetuning typically needs at least thousands of examples (often many more), while PEFT can do well with far fewer; with a few hundred examples, full finetuning might not beat LoRA. Also think about serving: LoRA lets several finetuned models share one base.

Framework. The easiest route is a finetuning API (upload data, pick a base model, get a model back), offered by model providers, cloud providers and third parties. Limits: only the supported base models, and not every knob exposed. Alternatively use a framework such as LLaMA-Factory, unsloth, PEFT, Axolotl or LitGPT, which gives flexibility but means provisioning compute. The chapter says adapter-based finetuning can often run on a mid-tier GPU, and multi-machine training needs distributed tooling like DeepSpeed, PyTorch Distributed or ColossalAI.

Key hyperparameters

  • Learning rate: the step size of each update. Too small and training crawls; too big and it overshoots and may never converge. There's no universal best. The chapter says to experiment, typically in the range 1e-7 to 1e-3, and a common practice is to take the learning rate at the end of pre-training and multiply by a constant between 0.1 and 1. A loss curve that jumps around suggests too large; one that's stable but slow suggests too small. A learning rate schedule can change it during training, typically larger early and smaller later.
  • Batch size: how many examples per update. Very small batches (the chapter says fewer than eight) can give unstable training; bigger batches give steadier updates and faster passes through data but need more memory. When memory forces small batches, gradient accumulation sums gradients over several batches before updating the weights once.
  • Number of epochs: passes over the training data. For millions of examples, 1 to 2 may be enough; for thousands, 4 to 10 may still help. Compare training loss with validation loss: both falling means more epochs (or data) could help; training falling while validation rises means overfitting, so try fewer epochs.
  • Prompt loss weight: in instruction finetuning each example has a prompt and a response, and both can contribute to the loss. Since at inference the model mostly generates responses, prompts usually get less weight. At 100% prompts count as much as responses; at 0% the model learns only from responses; a default of about 10% is typical.

Simplification: the numeric ranges above are the chapter's rules of thumb, not guarantees. Check your base model's and framework's documentation for its recommended settings.

The chapter's own wrap-up

The Summary reinforces the shape of the chapter: finetuning itself is not hard (frameworks handle much and suggest sensible defaults), but the surrounding context is: whether to finetune at all, and data. Full finetuning became impractical as models grew, so techniques arose to cut memory: PEFT reduces the number of trainable parameters, quantized training reduces the bits per value. LoRA is popular because it's parameter-efficient, data-efficient and modular. Model merging combines models, with uses from on-device deployment to upscaling. And the practitioner refrain: finetuning is easy, getting good data is hard, which is what Chapter 8 tackles.

Why it matters

This is the practical menu. When someone says "we finetuned it on a single GPU," this part tells you what that probably meant: a frozen, possibly 4-bit base with small LoRA matrices on the attention layers. When someone says "we serve a model per customer," it tells you how that stays affordable. And the merging section is a map of a fast-moving area, so you can read new merging releases and know whether they're summing, stacking or concatenating.

Remember this

  • PEFT trains a small number of added or reparameterized weights; LoRA does it with two thin matrices (W' = W + alpha/r x AB) that can be merged back for zero extra inference latency.
  • LoRA's rank is usually small (the chapter says often 4 to 64), applied to attention matrices first; its factorization is lossy, and it usually doesn't quite match full finetuning.
  • Keeping adapters separate costs a little latency but makes serving many task-specific or customer-specific models cheap.
  • QLoRA keeps the frozen base in 4 bits (NF4) so big models fit on one GPU, trading some training speed.
  • Merging combines weights (summing, stacking, concatenating) into one model; ensembling combines outputs. Merging methods are still experimental.

Try it yourself

  1. LoRA parameter counter (under an hour). Write lora_params(n, m, r) returning n*r + r*m, and a loop printing the saving for several ranks on a 4096 x 4096 matrix. Done when it prints 65,536 for r = 8 against 16,777,216 for the full matrix, and your 100-customer storage comparison gives 1,677,721,600 vs. 23,330,816 parameters (my run matched both). Then reproduce the chapter's GPT-3 count: 96 layers, dimension 12,288, rank 2, four matrices gives 18,874,368.
  2. Low-rank approximation demo. Build a matrix that is truly low-rank (multiply a random 8 x 1 by a random 1 x 8, then add a little noise) and approximate it with a rank-1 factorization, using any linear algebra library's SVD if you have one. Done when you can print the reconstruction error for ranks 1, 2 and 3 and see that error drops as rank rises. This shows the "lossy, but good enough" idea only; real LoRA learns A and B by training, not by SVD.
  3. Learning-rate playground. Minimize (w - 3)^2 by gradient descent from w = 0 with learning rates 0.01, 0.1, 0.9 and 1.1. Done when you've seen slow crawling, smooth convergence, oscillation, and divergence. (I ran it: 0.1 got to about 2.97 in 20 steps, 0.01 only to about 1.0, and 1.1 blew up to about -112.)
  4. Toy model merger. Represent three "models" as short lists of numbers sharing a base. Compute task vectors, then build merged models by averaging, by adding task vectors, by subtracting one task vector, and by keeping only the largest entry of each task vector before adding. Done when you can explain, for your numbers, why adding beat averaging and when pruning would change the result. Add a SLERP function for two 2-D vectors and confirm the 0.5 midpoint of (1,0) and (0,1) lands at about (0.707, 0.707) rather than (0.5, 0.5). Toy data only, nothing here touches a real model.
  5. Gradient accumulation loop. Extend the one-weight training loop from Part 1 to compute gradients on mini-batches of 2 examples but apply the update only every 4 mini-batches (average the accumulated gradients). Done when you can show it behaves like a batch of 8 while holding only 2 examples at a time.
  6. Finetuning plan one-pager. For a task you care about, write which base model, which method (full, LoRA, QLoRA), what framework or API, learning rate range, epochs, and how you'd tell overfitting from under-training. Done when each choice has a one-sentence reason tied to this chapter.
