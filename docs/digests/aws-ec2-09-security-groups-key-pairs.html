Security Groups and Key Pairs from the Instance's Point of View

When you can’t connect to an instance, a security group rule or a key problem is one of the first things to check (my experience-based hunch, not a measured figure). This digest looks at both from the instance's side: what traffic is allowed to reach it, how the firewall remembers conversations, and how a key pair gets you in. The VPC-level view of security groups was covered in an earlier digest; this one stays with the instance.

In one line

A security group is a stateful, allow-only virtual firewall attached to an instance's network interface, and a key pair is a public/private key set where EC2 puts the public half on the instance and you keep the private half to prove who you are.

The big idea

Think of an instance as a house. The security group is the front-door policy: a list of who may knock, on which door (port), using which language (protocol). Nothing on the list means nobody gets in. The key pair is the physical key for the one door (SSH) that you chose to open for administrators: the house holds the lock (public key), you hold the key (private key).

The part that surprised me: because the firewall is stateful, it remembers conversations. If your instance starts a conversation, the reply is let back in automatically. That's why you don't have to write rules for return traffic, and also why deleting a rule doesn't always cut an existing connection immediately.

No prices here: the docs say there is no additional charge for using security groups. Key pairs are a feature of EC2 with a per-Region quota the docs state.

Key terms

  • Security group: a virtual firewall controlling inbound and outbound traffic for the resources it's associated with.
  • Inbound / outbound rule: ingress (traffic to the instance) and egress (traffic from it).
  • Stateful: response traffic to an allowed request is allowed back automatically.
  • CIDR block: a way to write an IP range, such as 203.0.113.0/24. A single IPv4 address is written with /32.
  • Security group referencing: using another security group as the source or destination of a rule.
  • Connection tracking: how the security group remembers a connection's state.
  • Network interface (ENI): the virtual network card; security groups are attached to these.
  • Key pair: a public key and a private key used to prove your identity to an instance.
  • SSH: Secure Shell, the usual way to open a command line on a Linux instance, on port 22.
  • RDP: Remote Desktop Protocol, the Windows equivalent, on port 3389.
  • PEM / PPK: file formats for the private key (OpenSSH uses PEM, PuTTY uses PPK).
  • authorized_keys: the file on a Linux instance that lists which public keys may log in.

How it works

0. Grounding: where the firewall sits

The docs say a security group acts as a virtual firewall for your instances. Per the EC2 page, security groups are associated with network interfaces: adding or removing a group on an instance changes the groups on its primary network interface, and you can set secondary interfaces separately. That's what "instance level" means, as opposed to a subnet-level control like a network ACL.

Associations are many-to-many: an instance can have several security groups and a group can serve many instances. If you don't choose one at launch, EC2 uses the VPC's default security group. You can change groups after launch while the instance is running or stopped. Rule changes apply automatically to every associated instance.

1. The rules

  • Allow rules only. You can specify allow rules, not deny rules.
  • New group, no inbound rules: no inbound traffic is allowed until you add some. It starts with one outbound rule allowing all outbound traffic (you can remove it; with no outbound rules, no outbound traffic is allowed).
  • Several groups combine: the rules from every attached group are aggregated into a single set, and traffic is allowed if that combined set allows it. For beginners: it's a union, so adding a group can only make the instance more reachable.
  • Rule parts: protocol (commonly TCP = 6, UDP = 17, ICMP = 1), port or range (like 22 or 7000-8000), ICMP type and code, and a source (inbound) or destination (outbound): a single IP (/32 for IPv4, /128 for IPv6), a CIDR range, a managed prefix list ID, or a security group ID. Optionally a description up to 255 characters.
  • Counting: a rule with a CIDR or a security group counts as one rule toward the per-group limit, while a prefix list counts as its size (customer-managed) or weight (AWS-managed). The docs say quotas exist (rules per group, groups per interface); look them up on the VPC quotas page for current numbers.

2. Referencing a group instead of an IP

A rule can name another security group as its source. Then the rule applies to all instances associated with that group, communicating via their private IPs. The docs' classic pattern: load balancer group allows HTTP/HTTPS from the internet; web server group allows HTTP/HTTPS only from the load balancer's group; database group allows database traffic only from the web server group. As instances come and go, you never edit an IP list. Details: no rules from the referenced group are copied into the referencing one; referencing across VPCs works over a peering connection (and inbound over a transit gateway) per the docs' conditions; a rule referencing a deleted group or removed peering becomes stale. One limitation to know: if traffic between two instances is routed through a middlebox appliance, referencing the other instance's group won't permit the flow; use the instance's private IP or its subnet's CIDR.

3. Stateful in practice: connection tracking

Security groups track connection state, so replies to allowed traffic go through regardless of rules in the other direction. Consequences from the docs:

  • Existing connections can survive a rule change. If you change a rule, tracked connections aren't interrupted immediately; packets continue to be allowed until the connection times out. To cut traffic immediately, the docs point to network ACLs (stateless).
  • Some flows aren't tracked. If a rule allows all traffic (0.0.0.0/0 or ::/0) for a TCP/UDP flow and a rule in the other direction allows all response traffic on any port, that flow isn't tracked, and removing the rule drops the connection at once. The docs' example: an open outbound rule plus an inbound rule for SSH from anywhere means existing SSH sessions are dropped immediately if you remove that inbound rule, while a narrower SSH rule (tracked) leaves the current session alive.
  • Non-TCP/UDP/ICMP protocols track only IP and protocol number; return traffic of the same type within 600 seconds is accepted.
  • Idle timeouts (Nitro-based instances; configurable per network interface): TCP established defaults to 432,000 seconds, or 350 seconds on Nitro v6 instance types (min 60, max 432,000); UDP 30 seconds (30 to 60); UDP stream 180 (60 to 180). Long-lived connections on Nitro v6 may need keep-alives, which the docs suggest sending at intervals under 5 minutes.
  • There's a per-instance maximum of tracked connections; when reached, packets are dropped. The metrics conntrack_allowance_available and conntrack_allowance_exceeded show this.

4. What security groups do not filter

Per the VPC page, security groups do not filter traffic to and from the Amazon DNS service, DHCP, instance metadata (the 169.254.169.254 endpoint from the previous digest), ECS task metadata endpoints, Windows license activation, the Amazon Time Sync Service, and reserved addresses used by the default VPC router. So a "block everything" security group still leaves the instance able to talk to its metadata service. To filter DNS queries use Route 53 Resolver DNS Firewall.

The docs' best practices: authorize specific IAM principals to change security groups; use as few groups as practical, grouped by function; for ports 22 and 3389 allow only specific address ranges (0.0.0.0/0 and ::/0 let anyone on the internet try); don't open large port ranges; and consider network ACLs as an extra layer. The EC2 console's "My IP" option fills in your current public IPv4 address.

5. Key pairs: how the lock and key work

A key pair is a public key and a private key. EC2 stores the public key and puts it on the instance; you keep the private key. For Linux, at first boot the public key you chose at launch is placed in ~/.ssh/authorized_keys; to SSH in you present the matching private key. For Windows, the private key is used to decrypt the administrator password you then use to connect.

  • Supported: 2048-bit SSH-2 RSA keys (Linux and Windows) and ED25519 keys (Linux only); DSA is not accepted. Imports also allow 1024 and 4096-bit RSA per the docs' requirements list.
  • Create in EC2 and the private key is shown once ("the only chance for you to save the private key file"). EC2 doesn't keep a copy, so a lost private key can't be recovered, though the docs describe workarounds. Anyone holding the private key can connect to instances that use that pair.
  • Formats: pem for OpenSSH, ppk for PuTTY. On macOS/Linux set permissions with chmod 400 <name>.pem or SSH refuses the key.
  • Up to 5,000 key pairs per Region (docs; can request an increase). Names up to 255 ASCII characters.
  • You can instead generate keys yourself (for example with ssh-keygen) and import only the public key.
  • CloudFormation-created key pairs store the private key in Systems Manager Parameter Store as /ec2/keypair/<key_pair_id> (nice link to that earlier digest).
  • The docs mention an alternative to key pairs: Session Manager, which needs no inbound port or key.

Why a key pair alone isn't enough: to SSH you need both the right key and a security group rule that lets your IP reach port 22 (plus a route and a public address if you're coming from the internet). A "connection timed out" usually points at the network path or firewall; "permission denied" usually points at keys or the user name. That mapping is my rule of thumb, not an official diagnostic.

Why it matters

This is the day-to-day security of EC2. Opening SSH to the world and losing private keys are both classic mistakes, and the stateful behaviour explains confusing moments such as "I removed the rule but my session still works". Referencing groups instead of IPs is how layered architectures (load balancer, web, database) stay maintainable, and it ties back to the target groups and Auto Scaling digests.

Remember this

  • Security groups attach to network interfaces, allow rules only, evaluated as a union across attached groups; a new group allows nothing in and everything out.
  • Stateful: replies are allowed automatically, and tracked connections can outlive a deleted rule until they time out (untracked "allow all" flows are cut immediately).
  • Reference a group instead of an IP for tier-to-tier rules; restrict ports 22 and 3389 to specific ranges.
  • Security groups don't filter DNS, DHCP, the metadata service, or Time Sync traffic.
  • Key pair: public key on the instance, private key with you, shown once, never recoverable from AWS; ED25519 is Linux only.

Try it yourself

Projects 1 to 3 need no AWS account. Projects 4 and 5 create a key pair and a security group, and a small instance for 5 (may cost money; delete everything afterwards). I did not run any AWS command here. The authorize-security-group-ingress and create-key-pair options were checked against the CLI reference pages. The --query KeyMaterial redirection is built from the documented output field, not a page example. Note that the docs' revoke examples on the "change security groups" page look swapped (ingress/egress) and I did not use them.

  1. Rule evaluator (no AWS). Model security groups as lists of (direction, protocol, port range, source CIDR). Write allowed(packet, groups) that unions all groups. Done when: an instance with two groups allows traffic that either group allows, and denies everything when there are no matching rules.
  2. Connection tracker (no AWS). Extend the evaluator with a tracked-connections table: allow replies to allowed requests, expire entries after an idle timeout, and treat "allow-all both ways" flows as untracked. Done when: removing a narrow rule keeps a live connection until timeout, while removing an allow-all rule cuts it immediately, matching the docs' SSH example.
  3. CIDR quiz (no AWS). Write a function that checks whether an IP falls in a CIDR block (use your language's standard library). Test /32, /24 and 0.0.0.0/0. Done when: you can explain why 0.0.0.0/0 on port 22 is a warning sign in the docs.
  4. Create a key pair. Run aws ec2 create-key-pair --key-name lab-key --key-type ed25519 --query KeyMaterial --output text > lab-key.pem then chmod 400 lab-key.pem. Done when: the file exists, you can say why it can't be downloaded again, and you have deleted the key pair in the console afterwards.
  5. Two-group instance (small cost). Create sg-admin with aws ec2 authorize-security-group-ingress --group-id <id> --protocol tcp --port 22 --cidr <your-IP>/32 and a second group allowing TCP 80 from anywhere. Launch an instance with both, SSH in using your key, and then remove the SSH rule while connected. Done when: you've observed what happens to the existing session and to a new connection attempt, and can explain it with connection tracking. Terminate the instance and delete the groups.
