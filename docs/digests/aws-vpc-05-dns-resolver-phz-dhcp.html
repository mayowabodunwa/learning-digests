DNS in a VPC: Route 53 Resolver, Private Hosted Zones, DHCP Option Sets

How a name like db.example.com turns into a private IP inside your VPC, who answers that question, and which dials (two VPC switches, a DHCP option set, a private hosted zone) change the answer.

In one line

Every VPC gets a built-in DNS resolver; a DHCP option set tells instances to use it, two VPC attributes switch its features on or off, private hosted zones teach it your own names, and Resolver endpoints plus rules stretch it out to your on-premises network.

The big idea

Computers talk using IP addresses, but humans (and config files) use names. DNS is the phone book that connects the two. In a VPC you don't have to run a phone book server yourself: AWS provides one, and it already knows the names of your instances. The interesting part is how much control you have around it. Instances learn which DNS server to ask through DHCP (a startup handshake), so a DHCP option set is the lever that decides who gets asked. Two VPC attributes decide what the built-in resolver is allowed to do. A private hosted zone decides which custom names it can answer. And Resolver endpoints decide whether the conversation can cross over to your own data center. If you can name those four levers, most VPC DNS puzzles stop being mysterious.

Key terms

  • DNS: the Domain Name System, which resolves names to IP addresses. e.g. db.example.com to 10.0.3.17.
  • DNS hostname: a name made of a host name plus a domain name that identifies a computer.
  • Recursive resolver: a DNS server that does the whole lookup on a client's behalf and hands back the final answer. The docs say Route 53 Resolver only supports recursive queries.
  • Route 53 Resolver (also called the Amazon DNS server or AmazonProvidedDNS): the DNS service built into each Availability Zone of a Region. The newest Route 53 docs have renamed it "Route 53 VPC Resolver"; the VPC User Guide still uses the older name. Same thing.
  • VPC+2 address: the resolver's address inside your VPC, the base of the VPC's primary IPv4 range plus two. e.g. 10.0.0.2 for a 10.0.0.0/16 VPC.
  • DHCP: Dynamic Host Configuration Protocol, the handshake where a machine gets its network settings automatically.
  • DHCP option set: a group of network settings (DNS servers, domain name, NTP servers, NetBIOS settings, IPv6 lease time) that resources in a VPC use.
  • enableDnsSupport / enableDnsHostnames: the two VPC attributes that control DNS resolution through the Amazon resolver and public DNS hostnames respectively.
  • Private hosted zone: a Route 53 container of DNS records that answers queries for a domain only inside the VPCs you associate with it.
  • Split-view DNS: using the same domain name internally and externally, with different answers depending on where the question comes from.
  • Inbound endpoint: lets DNS queries from your on-premises network (or another VPC) come into your VPC's resolver.
  • Outbound endpoint + forwarding rule: lets queries for chosen domains go out from your VPC to a DNS server on your network.
  • NXDOMAIN: the DNS answer meaning "that name doesn't exist".

How it works

Grounding: what happens when an instance looks up a name

Picture an EC2 instance running ping db.example.com. The operating system doesn't know the answer, so it asks whichever DNS server it was told to use. Where did it get that setting? From DHCP, when its network interface came up. In the default setup that server is the Amazon-provided resolver. The docs say it lives at 169.254.169.253 (IPv4), fd00:ec2::253 (IPv6), and at the VPC's primary IPv4 range plus two. The queries travel to it privately over a link-local address and aren't visible on the network.

The resolver then answers three kinds of question, per the Route 53 docs: names for EC2 instances in the VPC (like ec2-192-0-2-44.compute-1.amazonaws.com), records in private hosted zones, and public names, which it looks up recursively on the internet.

1. The Amazon DNS server and its limits

What you can and can't do to it. Per the docs, you cannot filter traffic to or from the Amazon DNS server with network ACLs or security groups. That surprises people after the earlier security group and NACL topic: DNS to the VPC resolver is not something those rules gate.

A hard ceiling. The docs state a limit of 1024 packets per second per network interface for services that use link-local addresses, and it's an aggregate: Resolver DNS queries, instance metadata requests, Amazon Time Sync (NTP) requests, and Windows licensing requests all share it. The page says the quota can't be increased. If you hit it, the resolver rejects traffic. A busy instance that does a lot of lookups without caching can run into this, which is one reason people cache DNS answers on the instance (that's an inference on my part, not a statement from the docs).

Instance names. Every instance gets a private DNS hostname that resolves to its private IPv4 address. If it has a public IPv4 address and the right attributes are on, it also gets a public DNS hostname. That public name resolves to the public IP from outside, but to the private IP from inside the network of the instance. That's a handy detail: two instances in the same VPC that use each other's public DNS names still talk over private addresses.

2. The two DNS attributes

These are properties of the VPC itself:

  • enableDnsSupport: whether DNS resolution through the Amazon DNS server works at all. Default is true.
  • enableDnsHostnames: whether instances with public IPs get public DNS hostnames. Default is false unless the VPC is a default VPC.

With both true, instances with public IPs get public DNS hostnames and the resolver can resolve Amazon-provided private hostnames. If at least one is false, neither of those happens. And the important rule: if you use private hosted zones or private DNS on interface VPC endpoints (last topic), both must be true. Forgetting this is a classic reason why a private DNS name "just doesn't work".

CLI, from the reference page: aws ec2 modify-vpc-attribute --vpc-id <vpc> --enable-dns-support "{\"Value\":true}", and the same with --enable-dns-hostnames. The reference states you can't change the two in the same request, and you can only enable DNS hostnames if DNS support is already enabled, so do support first. Read them back with describe-vpc-attribute.

Simplification: I'm treating "DNS support off" as "the resolver stops working". The docs describe it as the VPC not supporting resolution through the Amazon server; if your instances point at your own DNS server through a custom DHCP option set, they are not using the Amazon resolver anyway, which changes what you'd see.

3. DHCP option sets: telling instances who to ask

What it is. A DHCP option set is a group of network settings used by resources in your VPC. Each Region has a default one, and each VPC uses it unless you attach a custom set or none. The default set's domain name server is always AmazonProvidedDNS, and it includes the IPv6 preferred lease time (default 140 seconds). NTP servers, NetBIOS name servers and node type aren't used in the default set, though EC2 instances still default to the Amazon Time Sync Service for time.

Custom sets. You can set domain name servers, domain name, NTP servers, NetBIOS name servers and node type, and an IPv6 lease time. Rules from the docs worth remembering:

  • A VPC can have only one option set at a time; one set can serve many VPCs.
  • You can't modify a set after creating it. To change anything, create a new one and associate it.
  • New settings reach existing instances without restart, usually within a few hours depending on lease renewal, or sooner if you renew the lease in the OS.
  • Domain name servers: up to four IPv4 servers (or three plus AmazonProvidedDNS), and four IPv6. The docs say mixing AmazonProvidedDNS with custom servers might cause unexpected behavior.
  • If your VPC has an internet gateway, you must give it your own DNS server or AmazonProvidedDNS. Otherwise instances have no DNS, which disables internet access in practice (docs wording).
  • Choosing "no DHCP option set" disables domain name resolution for the VPC. Per the concepts page, Nitro instances then get 169.254.169.253 as default name server, while Xen-based instances get none.
  • The domain-name field: use only domain names you fully control; some Linux versions accept several names separated by spaces, but Windows and others treat the value as one domain.

Why you'd customize it. The usual reason is wanting instances to use your own DNS servers, such as ones that also know your corporate zones. Custom DNS servers you run on instances should forward private queries to the VPC+2 address, per the docs. Today there's a managed alternative, Resolver endpoints, covered below.

Flagged docs inconsistency: the "Create a DHCP option set" page gives the IPv6 lease time range as 140 to 2147483647 seconds, but the concepts page says 140 to 4294967295. I'm not picking one; check the live pages if you need that number.

4. Private hosted zones: your own names, visible only inside

What it is. A private hosted zone (PHZ) is a Route 53 container holding records for a domain, answered only for the VPCs you associate with it. You create a zone like example.com, associate a VPC, then add records. The docs example: an A record db.example.com pointing to a database instance's IP. Any app in the associated VPC that looks up db.example.com gets that IP.

Who can ask. Per the docs, you get answers from a PHZ by running an EC2 instance in an associated VPC, or by using an inbound endpoint in a hybrid setup. Query it from elsewhere and the query resolves recursively on the internet, where the private records don't exist. The docs also say PHZs don't support transitive relationships outside the VPC: you can't use the custom private names from the other side of a VPN connection (unless you set up Resolver endpoints).

Requirements. Both DNS attributes must be true. Creating a PHZ also needs EC2 IAM permissions in addition to Route 53 ones. You can associate more VPCs later, including VPCs in other accounts via a separate procedure in the Route 53 guide that this digest doesn't walk through.

Split-view DNS. Create a public and a private zone with the same name, associate your VPCs with the private one, and put different records in each. Inside the VPC, answers come from the private zone; outside, from the public one. The trap: if a matching private hosted zone exists but has no record for the name and type requested, the resolver does not fall through to public DNS. It returns NXDOMAIN. So if you shadow example.com privately, you must also recreate any public records your VPC needs (such as www).

Overlapping zones: most specific wins. For a query like seattle.accounting.example.com and zones example.com and accounting.example.com, the resolver picks accounting.example.com, because it's the more specific parent. And if a Resolver forwarding rule exists for the same domain as a PHZ, the rule takes precedence, so queries go to your network instead.

Records. Private zones support simple, failover, multivalue answer, weighted, latency, geolocation and geoproximity routing; other routing policies aren't supported there.

5. Hybrid DNS: Resolver endpoints and rules

Your VPC resolver is only reachable from inside the VPC, and your office DNS doesn't know AWS names. Resolver endpoints bridge the two, over a Direct Connect or VPN link (a later concept in this series).

  • Inbound endpoint: you pick IP addresses in your VPC; your on-premises resolvers forward queries for AWS-hosted names to those IPs. Those IPs aren't public, so you need a VPN or Direct Connect connection.
  • Outbound endpoint: the IPs that queries originate from when the VPC forwards a lookup to your network. You need Direct Connect, a VPN, or a NAT gateway for connectivity (docs wording). One outbound endpoint can serve multiple VPCs in the same Region.
  • Forwarding rule: one domain name per rule, associated with the VPCs that should forward it. E.g. forward internal.example.com to the on-premises resolver. The resolver picks a target IP at random and retries another if one doesn't respond; unreachable targets can lengthen lookup times.

The docs' own walk-through: an instance asks VPC+2 for internal.example.com; the rule matches; the query leaves through the outbound endpoint and the private connection; the on-premises resolver answers and the reply returns the same way. The inbound direction is the mirror image.

Why it matters

DNS is behind a huge share of "it can't connect" tickets. Knowing the chain (DHCP option set, then the resolver, then attributes, then zones and rules) gives you a checklist. It also connects to earlier topics: interface endpoint private DNS needs these attributes, security groups and NACLs don't filter Amazon DNS traffic, and hybrid DNS rides on the VPN and Direct Connect links coming up soon.

Remember this

  • The VPC resolver lives at VPC+2 (and 169.254.169.253); instances learn to use it through the DHCP option set.
  • Private hosted zones and endpoint private DNS need both enableDnsSupport and enableDnsHostnames set to true.
  • DHCP option sets can't be edited: create a new one and associate it. One per VPC at a time.
  • A matching private zone without a matching record gives NXDOMAIN, it does not fall back to public DNS.
  • Hybrid DNS = inbound endpoint (on-prem to VPC), outbound endpoint plus rules (VPC to on-prem).

Try it yourself

  1. Inspect the attributes. Run aws ec2 describe-vpc-attribute --vpc-id <vpc> --attribute enableDnsSupport and again with enableDnsHostnames on your default VPC and a custom VPC. Done when: you can explain why the two values differ.
  2. Find the resolver. On a test instance run cat /etc/resolv.conf and dig db.example.com (or nslookup). Done when: you can point to the nameserver address and match it to the VPC+2 or 169.254.169.253 address from the docs. (The exact file contents depend on your OS image; I haven't verified what yours shows.)
  3. Private zone. Create a private hosted zone for a made-up domain you control, associate a throwaway VPC, add an A record for db, and resolve it from an instance and from your laptop. Done when: the VPC returns the private IP and the laptop does not. Delete the zone afterwards (hosted zones have a monthly charge; check Route 53 pricing).
  4. Trigger NXDOMAIN on purpose. Make a private zone with the same name as a public domain you own, with no www record, and look up www from the instance. Done when: you've seen NXDOMAIN and added the missing record.
  5. Swap a DHCP option set. Create a second set with a different domain name, associate it, then renew the lease on the instance (OS-specific) and check the search domain. Done when: the change shows up without a reboot, and you've confirmed you can't edit the old set.
  6. Paper design. Draw a hybrid DNS setup: one VPC, an on-premises DNS, a VPN. Mark the inbound endpoint, outbound endpoint, and one forwarding rule. Done when: you can trace both directions of a lookup.
