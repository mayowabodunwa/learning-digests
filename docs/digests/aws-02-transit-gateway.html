Transit Gateway: The Hub That Replaces a Mesh of Peering Connections

VPC peering connects exactly two VPCs, and it never chains. The moment you need more than a handful of VPCs talking to each other, you either build an exploding mesh of one-to-one connections, or you put one hub in the middle and attach everything to it. That hub is a transit gateway.

In one line

A transit gateway is a regional virtual router you attach VPCs (and VPNs, and Direct Connect, and other transit gateways) to, so they can all reach each other through one shared hub instead of needing a direct peering connection between every single pair.

The big idea

Two VPCs can talk to each other by creating a VPC peering connection, but a peering connection is strictly one-to-one: it does not let traffic pass through a third VPC to reach a fourth. Once you have more than two or three VPCs that all need to reach each other, that one-to-one rule turns into a lot of individual connections to create and maintain, and the count grows faster than the number of VPCs. A transit gateway fixes this by acting as a single hub: every VPC (or VPN, or on-premises network via Direct Connect) attaches to it once, and the transit gateway's own route tables decide who can reach whom from there. You go from "every VPC needs a direct line to every other VPC" to "every VPC needs one line, to the hub."

Key terms

  • VPC peering connection — a private, one-to-one network connection between exactly two VPCs, set up by one side requesting and the other accepting.
  • Transitive peering — the (missing) property that would let traffic hop across peering connections, e.g. from VPC B to VPC C by routing through VPC A. VPC peering does not have this property.
  • Full mesh — a topology where every node has a direct connection to every other node. For VPC peering, this means every VPC directly peered with every other VPC.
  • Transit gateway — a regional virtual router that interconnects VPCs and on-premises networks, routing packets at layer 3 based on destination IP address.
  • Attachment — a connection from the transit gateway to something else: a VPC, a VPN connection, a Direct Connect gateway, a Transit Gateway Connect appliance, or a peering connection to another transit gateway.
  • Hub-and-spoke — a topology where every node (spoke) connects only to a central hub, and reaches every other node through that hub.
  • Transit gateway route table — a routing table that belongs to the transit gateway itself, separate from any VPC's own route table, that decides which attachment traffic gets forwarded to.
  • Association — the single transit gateway route table an attachment is tied to for making its own routing decisions.
  • Route propagation — the transit gateway automatically installing an attachment's routes (like a VPC's CIDR block) into a route table, instead of you adding them by hand.
  • Static route — a route you add to a transit gateway route table yourself, rather than letting it propagate automatically.
  • Blackhole route — a route you add on purpose that drops any traffic matching it, used to explicitly cut off a destination.

How it works

Here's the situation that makes a transit gateway worth learning: most real AWS setups don't stay at one VPC for long. You get a VPC for each environment (dev, staging, prod), maybe one for shared services like a central logging or CI system, maybe one per team or per application. As soon as two of those need to exchange traffic, the default AWS tool for that is a VPC peering connection, and peering connections have a rule that trips up almost everyone the first time they hit it.

1. Why VPC peering doesn't scale

A VPC peering connection only ever links the two VPCs on either end of it. AWS states this plainly: "VPC peering does not support transitive peering relationships. For example, if there are VPC peering connections between VPC A and VPC B, and between VPC A and VPC C, you can't route traffic from VPC B to VPC C through VPC A. To route traffic between VPC B and VPC C, you must create a VPC peering connection between them." So peering VPC A to both B and C does not connect B to C. If B needs to reach C, that's a third, separate peering connection, with its own pair of route table entries on each side.

Follow that rule out to a handful of VPCs and the number of connections you need grows fast. For 4 VPCs that all need to reach each other, you need 6 peering connections (every pair, once). For 6 VPCs, it's 15. For 10 VPCs, it's 45. The general formula for "every VPC talks to every other VPC" is n(n-1)/2 connections for n VPCs, and each one is a separate thing to create, route, and eventually clean up.

2. What a transit gateway actually is

AWS describes a transit gateway as "a network transit hub used to interconnect virtual private clouds (VPCs) and on-premises networks," acting as a Regional virtual router that routes packets at layer 3 based on destination IP address, and that scales elastically with traffic volume. The important shift is structural: instead of every VPC connecting directly to every other VPC, every VPC connects once, to the hub. You can attach VPCs, one or more VPN connections, an AWS Direct Connect gateway (for a connection back to an on-premises data center), a peering connection to another transit gateway, and a few more specialized attachment types. Each attachment is both a source and a destination for traffic passing through the hub.

Concretely, for 4 VPCs that all need to reach each other, a transit gateway design needs 4 attachments, not 6 peering connections, and a 5th VPC needs 1 more attachment, not 4 more peering connections. The connection count grows in a straight line with the number of VPCs instead of accelerating.

3. Transit gateway route tables — where the actual routing decision happens

Attaching a VPC to a transit gateway doesn't automatically mean it can reach every other attachment. Every transit gateway comes with a default route table, and it can have additional ones. Each attachment is associated with exactly one route table (that's the table it uses to make its own routing decisions), and any given route table can have anywhere from zero to many attachments associated with it. A route in the table is a pair, just like a VPC route table: a destination CIDR block, and a target attachment to send matching traffic to.

Routes get into a route table one of two ways. With route propagation, an attachment's routes are installed automatically: for a VPC attachment, that means the VPC's CIDR block shows up as a route once you enable propagation for that attachment into a table. With a static route, you add the entry by hand, which is required for some attachment types (a peering connection to another transit gateway only supports static routes, for example) and useful whenever you want a route that isn't just "the attachment's own CIDR," like sending all outbound internet-bound traffic to one shared VPC. You can also add a blackhole route, which deliberately drops traffic matching a destination instead of forwarding it, which is one way to explicitly cut a VPC off.

One more detail worth sitting with: you also need a route on the VPC's own route table pointing at the transit gateway (typically 0.0.0.0/0 → tgw-id or a more specific CIDR), the same way a private subnet needs a route to a NAT gateway. The transit gateway attachment doesn't automatically add that route for you; the transit gateway route table only controls what happens once traffic actually reaches the hub.

4. Common patterns built from the same pieces

A few named patterns show up repeatedly once you have a transit gateway. A centralized router setup just associates every attachment with the same default route table, so everything can reach everything, which is the simple starting point. An isolated VPCs setup uses a separate route table per group of attachments that shouldn't reach each other (attachments associated with one route table can't reach attachments associated with a different one, since there's simply no route between them), which is a routing decision, not a special "isolation mode." A shared services variant adds routes so isolated groups can still all reach one common VPC (for something like central logging) without reaching each other. There's also a centralized outbound routing pattern, where VPCs with no internet gateway of their own send their internet-bound traffic through the transit gateway to one VPC that has a NAT gateway and internet gateway, similar in spirit to the NAT gateway pattern from the core networking basics, just centralized for many VPCs instead of repeated in each one.

Why it matters

This is exactly the problem AWS built transit gateway to solve at scale: real organizations end up with many VPCs across teams, environments, and accounts, and point-to-point peering connections between all of them becomes an operational burden fast, both to set up and to keep straight later. A transit gateway turns that into "attach once, then manage routing centrally" and it extends past VPCs to VPN connections and Direct Connect gateways too, so an on-premises network can reach many VPCs through one attachment instead of a separate VPN per VPC. It isn't free to run (AWS charges hourly per attachment plus for data processed through the gateway), so for just two or three VPCs that will only ever need to talk to each other, plain VPC peering can still be the simpler and cheaper choice. The tradeoff tends to flip once the VPC count and the "who needs to reach whom" question start changing often.

Remember this

  • VPC peering is not transitive. A↔B and B↔C does not give you A↔C; you'd need a separate A↔C connection.
  • A full mesh of peering connections for n VPCs needs n(n-1)/2 connections, which grows fast: 6 for 4 VPCs, 15 for 6, 45 for 10.
  • A transit gateway is a hub: each VPC (or VPN, or Direct Connect gateway) needs just one attachment to it, and the attachment count grows one at a time as you add VPCs, not by a formula.
  • Every attachment associates with exactly one transit gateway route table, and that table (not the attachment itself) decides which other attachments it can reach.
  • Routes reach a transit gateway route table two ways: propagated automatically from an attachment, or added as a static route by hand (required for some attachment types, like peering to another transit gateway).

Try it yourself

  1. Build the naive mesh. Create 3 small VPCs and peer every pair (3 connections total), adding the matching route table entries on each side. Done when: an instance in each VPC can reach an instance in each of the other two.
  2. Prove non-transitivity yourself. Create a 4th VPC and peer it only with VPC A. Try to reach the 4th VPC from VPC B or C without creating any new peering connections. Done when: you've confirmed the connection fails, and you can say out loud how many new peering connections a fully-connected 4-VPC mesh needs (it's 6).
  3. Replace the mesh with a transit gateway. Create a transit gateway, attach the same VPCs to it, add a route to the transit gateway in each VPC's own route table, and let VPC CIDRs propagate into the default transit gateway route table. Done when: all VPCs can reach each other through the hub, and you've deleted the old peering connections.
  4. Build an isolated pair. Create a second transit gateway route table, associate two of your VPC attachments with it instead of the default table, and disable propagation between it and the rest. Done when: those two VPCs can reach each other, but not the other VPCs still on the default table.
  5. Add a blackhole route. In the transit gateway route table, replace one VPC's propagated route with a static blackhole route for its CIDR. Done when: traffic from other VPCs to that CIDR is dropped, while traffic inside that VPC (its own local route) still works fine.
  6. Do the cost math. For a 6-VPC full-mesh scenario, compute the peering connection count with n(n-1)/2, compare it to the 6 transit gateway attachments the hub design would need, then check the current transit gateway pricing page for the per-attachment-hour and per-GB rates. Done when: you can explain, in one sentence, at what VPC count the hub design clearly wins.

Go deeper

Two transit gateways can also be peered to each other (including across Regions), which is how this same hub pattern extends beyond one Region without going back to point-to-point peering between every gateway. If you're designing for more than a handful of VPCs, AWS's transit gateway design best-practices material is worth a dedicated read once the basics above feel solid, particularly around choosing when to split attachments across multiple route tables versus keeping one shared table.
