Transit Gateway & Multi-VPC Connectivity

What to reach for once "just peer the VPCs" stops working: one regional hub that every VPC, VPN, and Direct Connect link attaches to, plus a route table that decides who can talk to whom.

In one line

A transit gateway is a managed, regional router that VPCs and on-premises connections attach to once, so instead of wiring every network directly to every other network, everything routes through one shared hub whose route tables decide who can reach whom.

The big idea

VPC peering connects exactly two VPCs, one connection at a time, and that connection doesn't let traffic pass through a third VPC to get somewhere else (it's "non-transitive," in AWS's own words). That's fine for two or three VPCs. It gets painful fast once you have a dozen VPCs that all need to talk to each other, because the number of individual peering connections you need grows much faster than the number of VPCs. A transit gateway fixes this by acting as a single hub: every VPC (and VPN, and Direct Connect connection) attaches to it once, and a transit gateway route table decides where each packet goes next. Add a new VPC, and you add one attachment, not one connection to every existing VPC.

Key terms

  • Transit gateway — a regional virtual router you create that VPCs and other networks attach to, so traffic between them flows through it instead of through direct connections between each pair.
  • VPC peering connection — a direct, one-to-one networking link between exactly two VPCs. Covered briefly in Topic 1's context; the focus here is why it doesn't scale on its own.
  • Non-transitive — traffic can't "pass through" a middle network to reach a third one. If A is peered with B, and A is peered with C, B still can't reach C through A.
  • Attachment — the thing you connect to a transit gateway: a VPC, a VPN connection, a Direct Connect gateway, another transit gateway (via a peering attachment), a Transit Gateway Connect appliance, or a network function like a firewall. An attachment is both a source and a destination for traffic.
  • Transit gateway route table — a table of routes inside the transit gateway (separate from any VPC's own route table) that decides, for a packet arriving from one attachment, which attachment to send it to next.
  • Association — which single route table an attachment uses to look up where its outbound traffic should go. Each attachment is associated with exactly one route table at a time.
  • Propagation — how an attachment's own routes (like a VPC's CIDR block) get added, automatically, into a transit gateway route table, so other attachments know how to reach it.
  • Static route — a route you add to a transit gateway route table by hand, rather than one that showed up through propagation.
  • Blackhole route — a route you create on purpose that drops any traffic matching it, instead of forwarding it anywhere.
  • Full-mesh peering — connecting every VPC directly to every other VPC with its own peering connection, so the whole group is fully interconnected without a hub.
  • Direct Connect gateway — the AWS resource that lets an on-premises network, connected via AWS Direct Connect, reach VPCs; it can attach to a transit gateway like any other attachment.

How it works

Here's the problem a transit gateway exists to solve, in AWS's own terms: a VPC peering connection is "a networking connection between two VPCs that enables you to route traffic between them," and it's built one pair at a time. AWS's peering documentation is explicit that this doesn't chain together: "VPC peering does not support transitive peering relationships. For example, if there are VPC peering connections between VPC A and VPC B, and between VPC A and VPC C, you can't route traffic from VPC B to VPC C through VPC A. To route traffic between VPC B and VPC C, you must create a VPC peering connection between them." So if you want every VPC in a group to reach every other VPC, you don't get to reuse one VPC as a relay: you need a direct peering connection between literally every pair.

That's where the math turns against you. For N VPCs that all need full connectivity, the number of individual peering connections you need is N × (N-1) / 2 (every VPC paired with every other VPC, counted once). With 4 VPCs that's 6 connections, which is annoying but manageable. With 10 VPCs it's 45. With 20 VPCs it's 190. Each one of those is a separate connection to create, accept, and add matching routes for in both VPCs' route tables, and every new VPC you add means creating a new connection to every VPC that already exists. This is a simplification of the operational reality (some teams only need a handful of VPCs to talk, not all of them), but the general shape holds: pairwise peering scales quadratically, and a transit gateway is the way AWS documents connecting many VPCs (and on-premises networks) without that blowup.

1. What a transit gateway actually is

Per AWS's own description, "a transit gateway acts as a Regional virtual router for traffic flowing between your virtual private clouds (VPCs) and on-premises networks," and it "scales elastically based on the volume of network traffic." Routing happens at layer 3: a packet arrives from one attachment, the transit gateway looks at its destination IP address, checks a route table, and forwards it to the matching attachment. It's a single logical resource that lives in one AWS Region (though you can peer transit gateways across Regions, more on that below), and it works across AWS accounts too: you can share a transit gateway with other accounts using AWS RAM (Resource Access Manager), and once shared, the other account's owner can attach their own VPCs to it.

One useful mental model: a transit gateway doesn't replace your VPC route tables, it sits alongside them. Each VPC still has its own route table deciding what happens to traffic leaving its subnets; some of those routes just point at the transit gateway instead of at a NAT gateway, an internet gateway, or a peering connection. The transit gateway then has its own, separate route table (or tables) that takes over from there.

2. Attachments — how traffic actually gets onto the hub

An attachment is a resource of some type, connected to the transit gateway, that can both send and receive traffic through it. AWS's transit gateway concepts page lists what you can attach: one or more VPCs, a VPN connection, a VPN Concentrator, an AWS Direct Connect gateway, a Transit Gateway Connect attachment (for SD-WAN or third-party network appliances), a peering connection to another transit gateway, a Client VPN endpoint, and a network function attachment (for example, connecting an AWS Network Firewall directly to the transit gateway for traffic inspection).

The most common one for a "connect a bunch of VPCs together" setup is the VPC attachment. When you attach a VPC, you pick at least one subnet per Availability Zone you want the transit gateway to use; AWS places a network interface in that subnet, and that's the entry and exit point for traffic in that zone. A detail worth remembering: only resources in Availability Zones that actually have a transit gateway attachment subnet can reach the transit gateway at all, so if you only enable one AZ, resources in a second AZ of the same VPC are stuck.

A VPN attachment connects an AWS Site-to-Site VPN connection (typically to an on-premises network) straight to the transit gateway, so on-premises traffic can reach any other attachment the same way a VPC's traffic can. A Direct Connect gateway attachment does the same job for a Direct Connect connection (a dedicated network link into AWS, instead of a VPN over the public internet). Both are how a transit gateway becomes the single place where cloud VPCs and on-premises networks meet, rather than needing a separate VPN or Direct Connect setup wired into every VPC individually.

A peering attachment connects two transit gateways to each other (which can be in different Regions or different accounts). This is a different thing from VPC peering: here you're peering two hubs, not two VPCs, so that VPCs attached to one transit gateway can reach VPCs and other attachments on the other one, still without a direct connection between every individual VPC.

3. Transit gateway route tables — how routing decisions get made

This is the piece that actually decides who can reach whom, and it's separate from any VPC's own route table. A transit gateway "automatically comes with a default route table," and by default that same table is used for both association and propagation, meaning every new attachment lands there unless you tell it otherwise. You can create additional route tables to segment your network, similar to how you might use separate virtual routing and forwarding (VRF) tables in traditional networking; a common reason to do this is keeping, say, development VPCs unable to reach production VPCs even though both are attached to the same transit gateway.

Two mechanics decide what ends up in a route table:

  • Association — each attachment is associated with exactly one route table at a time. That table is what the transit gateway consults when deciding where to send traffic coming from that attachment.
  • Propagation — an attachment's own routes (a VPC's CIDR block, for example) get installed into one or more route tables so other attachments know how to send traffic to it. A VPC attachment's CIDR blocks propagate automatically once propagation is enabled for that attachment/table pair; a VPN or Direct Connect gateway attachment can propagate routes learned dynamically from an on-premises router over BGP (Border Gateway Protocol, the protocol routers use to exchange reachability information).

You can also add static routes by hand, and if a static route and a propagated route both exist for the same destination, the static route wins (the propagated one is dropped from that table until you remove the static one). One route type is worth flagging specifically: for a peering attachment between two transit gateways, only static routes are supported. There's no route propagation across a peering attachment, so you point traffic at the peered transit gateway with a static route yourself. You can also create a blackhole route, which deliberately drops any traffic matching it. That's useful when you want two attachments on the same route table to explicitly not reach each other.

To see why segmentation matters, it helps to compare that centralized setup with AWS's "isolated VPCs" example: instead of one shared route table, you create a second one. VPC A and VPC B's attachments stay associated with (and propagate to) the default table, while VPC C's attachment is moved to the second table. Now traffic from A or B that's destined for C's CIDR block has no matching route in the default table, so it goes nowhere, even though all three VPCs are attached to the exact same transit gateway. That's the association/propagation split doing real work: which table an attachment is associated with controls what it can send to, and which tables its routes propagate into controls who can reach it.

4. How this differs from plain VPC peering

Both peering and a transit gateway ultimately move private traffic between VPCs without going over the public internet, but they solve different shapes of problem. A peering connection is a direct, one-to-one link: it's simple to reason about for two or three VPCs, has no separate hub resource to manage, and (per AWS's peering pricing page) is free to create, with data transfer inside the same Availability Zone also free. What it can't do is act as a relay, and it doesn't give you a single place to see or manage routing across many VPCs at once: every pair needs its own connection and its own matching routes in both sides' VPC route tables.

A transit gateway trades that simplicity for a shared hub: one resource, with its own route tables, that every VPC attaches to once. That gives you a single place to add or remove a VPC from the group (one attachment, not N new connections), and a single place to enforce segmentation (route tables, association, and propagation) instead of hand-managing which VPC route tables have routes to which peering connections. It isn't free the way peering is: AWS's transit gateway pricing model charges an hourly rate per attachment plus a charge for the data processed through the transit gateway, with those data-processing charges allocated by default to the account that owns the source attachment. AWS's own peering documentation acknowledges this trade explicitly, noting that "in some cases, you can use a transit gateway attachment instead of a VPC peering connection" once the number of VPCs and the need for shared routing logic grows past what plain peering handles comfortably.

Why it matters

This is the difference between a networking design that gets harder to reason about with every new VPC, and one that stays roughly the same shape no matter how many VPCs you add. Real organizations end up with dozens of VPCs (one per team, one per environment, one per region) surprisingly fast, and "just peer them all" turns into a spreadsheet of connections nobody wants to audit. A transit gateway is also the natural place hybrid connectivity lands: instead of wiring a VPN or Direct Connect connection into every VPC that needs on-premises access, you attach it once to the hub, and every VPC already attached to that hub can reach it (assuming the route tables allow it). And because route tables can segment attachments into groups that can't reach each other, a transit gateway is also a real tool for network isolation (dev can't reach prod, a shared-services VPC can be reachable from everywhere without everything being reachable from everywhere), not just a bigger peering connection.

Remember this

  • VPC peering is non-transitive and one-to-one: if A is peered with B and A is peered with C, B still can't reach C through A.
  • Full-mesh peering for N VPCs needs roughly N(N-1)/2 connections; a transit gateway needs one attachment per VPC.
  • A transit gateway is a Regional layer-3 router; attachments (VPCs, VPN, Direct Connect gateway, another transit gateway) are both sources and destinations of traffic through it.
  • Association decides which single route table an attachment uses to send traffic; propagation decides which route tables learn how to reach that attachment. They're separate levers.
  • Static routes beat propagated routes to the same destination, and transit gateway peering attachments only support static routes, never propagation.

Try it yourself

  1. Sketch the math. For 3, 5, and 8 VPCs, calculate how many individual peering connections a full mesh needs using N(N-1)/2, then compare that to the number of attachments a single transit gateway would need for the same group. Done when: you have a written comparison table for all three VPC counts and can say out loud why the gap grows.
  2. Build a 3-VPC transit gateway lab. Using the free tier, create three small VPCs in the same Region with non-overlapping CIDR blocks, create one transit gateway, and attach all three VPCs to it. Done when: the console (or aws ec2 describe-transit-gateway-attachments) shows three attachments in the available state on the same transit gateway.
  3. Wire up and prove three-way connectivity. In each VPC's own route table, add a route sending traffic destined for the other VPCs' CIDR blocks (or a broader 0.0.0.0/0) to the transit gateway, then launch one small EC2 instance per VPC. Done when: each instance can reach the other two over their private IPs (ping or a simple TCP connection), and you can point to the propagated route in the transit gateway's route table that makes each path work.
  4. Read a real route table cold. Open your transit gateway's default route table in the console and, without looking anything up, explain each row out loud: which attachment it points to, whether it's static or propagated, and what happens to a packet that matches none of the rows. Done when: you could explain the whole table to someone who's never touched AWS.
  5. Prove isolation with a second route table. Create a second transit gateway route table, move one VPC's attachment association to it, and make sure its routes don't propagate to (or from) the default table. Done when: the two VPCs still on the default table can still reach each other, but neither can reach the VPC you isolated, and you can explain why using association and propagation rather than "it's just disconnected."
  6. Compare the pricing model, not just the topology. Read the transit gateway pricing page and the VPC peering pricing section side by side, and write two or three sentences, in your own words, about when a single peering connection stays the simpler (and cheaper) choice for just two VPCs, versus when the hub model starts paying for itself in complexity you're not managing by hand. Done when: you'd feel comfortable explaining that trade-off to a teammate without notes.

Go deeper

Two things worth a closer read on your own: appliance mode, which lets you route all inter-VPC traffic through a security appliance (like a firewall) sitting in a shared services VPC for centralized inspection before it reaches its destination, and transit gateway peering across Regions, which is how a hub-and-spoke design itself scales globally once one Region's transit gateway isn't enough. Both build directly on the association/propagation model covered here.
