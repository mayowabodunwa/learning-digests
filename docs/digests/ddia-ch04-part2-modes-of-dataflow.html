Modes of Dataflow

Part 1 covered how to turn an object into bytes and back without old code and new code misunderstanding each other. This part asks the next question: how do those bytes actually get from the process that wrote them to the process that reads them? It turns out there are really only three paths: through a database, through a direct service call, or through a message broker sitting in between. This part walks through all three, why remote procedure calls are a leakier abstraction than they look, and how rolling upgrades force every one of these paths to deal with old and new code running at the same time. It closes out Chapter 4.

In one line

Data doesn't just get encoded, it has to travel somewhere, and the three main routes (databases, service calls, and message brokers) each put the "can the reader understand what the writer meant" question from Part 1 into a different, very concrete shape.

The big idea

Whenever one process hands data to another process it doesn't share memory with, that data has to be encoded into bytes first, which is what Part 1 was about. This part is about the handoff itself: who's doing the encoding, who's doing the decoding, and how much time might pass in between. A database can hold a value you wrote five years ago next to one you wrote five milliseconds ago, so the "reader" might be a future version of your own code reading its past self's data. A service call expects an answer back almost immediately, and treats the two sides as separate parties that don't fully trust each other. A message broker sits in the middle, holding onto a message until someone's ready for it, without the sender ever needing to know who that someone is. Once you see data flow through these three shapes, "old and new code have to coexist for a while" (which is what a rolling upgrade is) stops being an edge case and starts looking like the normal condition your system lives in most of the time.

Key terms

  • Dataflow — the path data takes as it moves from the process that encodes it to the process that decodes it: through a database, a service call, or a message broker.
  • Rolling upgrade (staged rollout) — deploying a new version of a service to a few nodes at a time instead of everywhere at once, so a problem is caught before it reaches every user. It means old code and new code normally run side by side for a while, not just briefly.
  • RPC (remote procedure call) — a technique that tries to make a request to a service on another machine look and feel like calling an ordinary function in your own program.
  • Location transparency — the illusion RPC tries to create, that calling code on a remote machine is basically the same experience as calling code in your own process.
  • REST — not a protocol, but a design philosophy for web services that leans on HTTP's own features (URLs for resources, GET/POST, content negotiation, caching). An API built this way is called RESTful.
  • SOAP — an XML-based protocol for making network API requests, built around its own large family of standards (WS-*) rather than plain HTTP features.
  • WSDL (Web Services Description Language) — the XML-based language SOAP uses to describe a service's API, which tooling can turn into generated client code.
  • Service-oriented architecture / microservices — an architecture where a large application is split into smaller services, each owned by a team, each independently deployable, that call each other to get work done.
  • Web service — a service that uses HTTP as the protocol clients use to talk to it.
  • Middleware (in this context) — software that supports one internal service making requests to another, typically within the same organization or datacenter.
  • Idempotence — designing an action so that doing it two or more times has the same effect as doing it once, which is what makes it safe to retry a request you're not sure got through.
  • Service discovery — a way for a client to find out which IP address and port a service currently lives at, since that can change over time (especially in the cloud).
  • Futures / promises — a way some newer RPC frameworks represent an asynchronous action that hasn't finished yet and might still fail, instead of blocking and pretending it's a normal function call.
  • Message broker (message queue, message-oriented middleware) — an intermediary process that a sender publishes a message to; the broker holds onto it and delivers it to one or more consumers, rather than the sender talking to the recipient directly.
  • Topic / queue — the named channel a message broker moves messages through. Producers publish to it, consumers (or subscribers) read from it.
  • Actor model — a way of structuring concurrent code as independent "actors," each with private state, that only ever interact by sending each other asynchronous messages, never by sharing memory directly.

How it works

Zoom out for a second before the details. This part picks up exactly where the encoding formats left off: you already know how to turn an in-memory object into bytes and back, and what backward and forward compatibility mean for that translation. What's still open is the question of movement: how do the bytes actually get from the process that encoded them to the process that will decode them? There turn out to be three fairly different answers. A database, where the "other process" reading your data might just be a later version of yourself. A service call, where a client asks a server for something directly over the network and expects an answer quickly. And a message broker, where a message sits in an intermediary for a while before anyone picks it up. Every compatibility rule from Part 1 becomes concrete once you ask which of these three paths a particular piece of data is actually taking.

1. Databases as dataflow: a message to your future self

Start with the simplest case. In a database, whatever process writes a value is the one doing the encoding, and whatever process later reads that value is doing the decoding. If there's only one process using the database, the "reader" is really just a later run of the very same program, which makes storing something in a database a lot like leaving a note for a future version of yourself to find. Backward compatibility is obviously required here: if your future self can't decode what your past self wrote, you've lost the data.

In practice, it's rarely just one process. It's common for several different processes, or several parallel instances of the same service (running for scalability or fault tolerance), to be reading and writing the same database at once. In a system that's actively changing, it's likely that some of those instances are running newer code and some are running older code, for example because a rolling upgrade (deploying a new version to a few machines at a time, covered above) is in progress and hasn't reached every instance yet. That means a value can be written by newer code and then read, shortly after, by older code that's still running. So forward compatibility (older code coping with newer data) is often just as necessary for databases as backward compatibility is.

There's an extra snag worth knowing about. Say a new field gets added to a record's schema, and newer code writes a value into that field. If an older version of the code (which has never heard of the new field) later reads that record, updates something else in it, and writes it back, the desirable outcome is usually that the new field survives untouched, even though the old code never understood it. Formats like Thrift, Protocol Buffers, and Avro are built to preserve unknown fields like this by default. But it's still possible to lose that field by accident at the application level: if your code decodes a database value into an in-memory model object that only knows the old fields, and later re-encodes that model object to save it, the unknown field can quietly get dropped in translation, since it was never represented in the model object at all. This isn't a hard problem to fix, it just needs deliberate care, either by preserving unknown data through your model layer or by not round-tripping through an incomplete model in the first place.

2. Rolling upgrades and the archaeology of old data

A database generally lets you update any value at any time, which means a single database can genuinely hold a row written five milliseconds ago right next to one written five years ago. Deploying a new version of an application can replace the old version across your fleet within minutes. Database contents don't move that fast: five-year-old data just sits there, still in whatever encoding it was originally written in, unless you've gone back and explicitly rewritten it. This gets summed up as "data outlives code," and it's a genuinely different problem from just keeping your running code compatible, because a database can be carrying schema versions from years' worth of deploys, all at once.

Rewriting (migrating) every row into a new schema is possible, but it's an expensive thing to do across a large dataset, so most databases avoid it where they can. In a common pattern for relational databases, a simple schema change like adding a new nullable column doesn't require rewriting existing rows at all: when an old row is read, the database just fills in nulls for whatever columns are missing from that row's stored bytes. Worth flagging as a bounded claim rather than a universal rule, though: this varies by database engine, and MySQL in particular is called out as an exception that often rewrites an entire table for schema changes even when it isn't strictly necessary. LinkedIn's Espresso document database is one real example of leaning into this instead of fighting it: it stores data using Avro, and gets Avro's schema evolution rules for free as a result. Put together, schema evolution done well lets an entire database look, from the outside, like it was written with one single schema, even though the bytes on disk underneath are really a patchwork of historical versions.

Archival storage is a neat special case of this. If you periodically snapshot a database (for backups, or to load into a data warehouse for analytics), that dump is usually a good moment to clean house: even if the live database is a mixture of schema eras, you might as well re-encode the whole snapshot consistently under the current schema while you're copying it anyway. Because a data dump like this gets written once and is immutable afterward, a format built for exactly that shape, like Avro's own object container file format, fits well. It's also a convenient moment to switch to an analytics-friendly, column-oriented format like Parquet, since you're already paying the cost of a full rewrite.

3. REST vs RPC, and why RPC's "just like a local call" promise is flawed

Move from databases to services. When processes need to talk to each other over a network directly, the usual setup has two roles: a server that exposes an API (this exposed API is what's meant by a service), and clients that connect to it to make requests. The web itself works this way: browsers send GET requests to fetch pages and POST requests to submit data, using a standardized stack of protocols and formats (HTTP, URLs, TLS, HTML) that most browsers and servers agree on. Browsers aren't the only kind of client, though: a native mobile app, or client-side JavaScript using Ajax, can make the same kind of network request, usually getting back data (often JSON) meant for more processing rather than direct display.

A server can also be a client to some other service, and this is the basis for decomposing one large application into smaller services by area of responsibility, an approach traditionally called service-oriented architecture (SOA) and more recently rebranded as microservices. A key goal of that split is making each service independently deployable, so one team can ship changes to their service without having to coordinate a simultaneous release with every other team. That, in turn, means old and new versions of a service's clients and servers should be expected to run at the same time, which is exactly why the compatibility rules from Part 1 matter here too.

Services are a bit like databases in that clients submit and query data, but with one big restriction: a database will run more or less any query you throw at it, while a service only exposes whatever specific inputs and outputs its own application logic decided to support. That restriction is a deliberate feature, since it gives the service fine-grained control over what a client can and can't do.

When HTTP is the underlying protocol, a service is called a web service, and this shows up in a few different settings: a mobile or browser client calling a service over the public internet, one internal service calling another inside the same organization (sometimes supported by what's called middleware), or one organization's backend calling another's, as with a public payments API or OAuth. There are two well-known styles for building web services, and they take almost opposite philosophies. REST isn't a protocol at all, it's a design approach that leans on HTTP's own existing features: using URLs to identify resources, and HTTP's built-in mechanisms for caching, authentication, and content negotiation. An API designed this way is RESTful. SOAP, by contrast, is an XML-based protocol that tries to stay independent of HTTP even though it's usually carried over it, and comes with its own sprawling family of related standards (grouped under the name WS-*). SOAP describes its API using an XML-based language called WSDL, which supports generating client code automatically, useful in statically typed languages, less so in dynamic ones. Because WSDL isn't meant to be human-readable and SOAP messages get complicated fast, SOAP usage leans hard on tooling and IDEs, and even with everything nominally standardized, different vendors' SOAP implementations often don't interoperate cleanly. In a common pattern today, SOAP is still used inside many large enterprises but has fallen out of favor at smaller companies, while REST has become the more usual style, especially for services crossing organizational boundaries; a format called OpenAPI (also known as Swagger) is often used to describe and document RESTful APIs.

REST and SOAP are really just the latest chapter in a much longer history of technologies for calling an API over a network, and a lot of the earlier ones (Java's RMI, Microsoft's DCOM, the notoriously complex CORBA, which also never solved backward or forward compatibility) shared one underlying idea: the remote procedure call (RPC), dating back to the 1970s. RPC tries to make a request to a service on another machine look and feel just like calling an ordinary function inside your own process, an illusion called location transparency.

That illusion is appealing, but it's fundamentally flawed, because a network request is a genuinely different kind of thing from a local function call, in several concrete ways:

  • A local call is predictable: it succeeds or fails based only on inputs you control. A network request is unpredictable, since the request or response can get lost to a network problem, or the remote machine can be slow or simply unavailable, for reasons entirely outside your control. Because network problems are common, you have to plan for them, for example by retrying.
  • A local call returns a result, throws, or (rarely) never returns. A network request has a third outcome a local call doesn't: it can time out with no result at all, and when that happens you genuinely don't know whether the request got through or not.
  • If you retry after a timeout, it's possible the original request actually did get through and only the response got lost, meaning a naive retry can perform the same action twice. Local calls never have this problem; a network call only avoids it if you build in a way to make repeats harmless, which is what idempotence means.
  • A local call normally takes roughly the same amount of time on every call. A network request is not only slower, its latency is wildly variable: sub-millisecond when things are calm, many seconds when the network is congested or the remote service is overloaded, for the exact same piece of work.
  • A local call can cheaply pass a pointer to data already in memory. A network call has no such shortcut: every parameter has to be encoded into bytes first, which is fine for small primitives but gets awkward fast for larger objects, and if the client and server are written in different languages, the RPC framework also has to translate datatypes between them, which can get messy (recall JavaScript's trouble with integers past 253 from Part 1: that same mismatch shows up here too).

Put together, none of this means RPC is useless, but it does mean there's little point pretending a remote service is basically a local object. Part of why REST has appealed to people is that it doesn't try to hide that it's a network protocol in the first place, though that hasn't stopped some people from building RPC-style libraries on top of REST anyway.

4. Service evolution and API versioning

RPC hasn't gone away despite its problems, and newer RPC frameworks are noticeably more honest about a remote call not being a local one. Thrift and Avro both ship with built-in RPC support, gRPC is an RPC implementation built on Protocol Buffers, Finagle also uses Thrift, and Rest.li uses JSON over HTTP. Some of these use futures (promises) to represent an asynchronous action that might still fail, instead of blocking like a local call would, which also makes it easier to fire off requests to several services in parallel and combine the results. gRPC goes further and supports streams, where a single call can be a whole series of requests and responses over time, not just one request followed by one response. Some of these frameworks also offer service discovery, letting a client find out which IP address and port a particular service currently lives at, which matters more in cloud environments where instances come and go.

A custom binary RPC protocol can genuinely outperform something generic like JSON over REST. But REST has real advantages that often outweigh that: it's easy to experiment with and debug, since you can poke it with a browser or curl without any code generation or install step, it's supported by essentially every mainstream language and platform, and it has a huge surrounding ecosystem (caches, load balancers, proxies, firewalls, monitoring and testing tools). In a common pattern, that combination makes REST the predominant style for public-facing APIs, while RPC frameworks tend to be used more for calls between services owned by the same organization, often within the same datacenter.

Evolvability for services means clients and servers need to be changeable and deployable independently, and there's a useful simplifying assumption you can make for services that you generally can't make for databases: it's reasonable to assume all the servers get upgraded before the clients do. That means you typically only need backward compatibility on requests (so an already-upgraded server can still understand requests from not-yet-upgraded clients) and forward compatibility on responses (so a not-yet-upgraded client can still cope with responses from an already-upgraded server).

An RPC scheme's compatibility properties come straight from whatever encoding it's built on: Thrift, gRPC (Protocol Buffers), and Avro RPC each follow their own format's evolution rules from Part 1. SOAP requests and responses are described with XML schemas, which can evolve but have some subtle pitfalls of their own. RESTful APIs most commonly use JSON without a formally specified schema for responses, and JSON or URL/form-encoded parameters for requests; in a common convention, adding optional request parameters and adding new fields to response objects are both treated as changes that keep compatibility intact.

Compatibility gets harder once RPC crosses organizational boundaries, because the provider of a service often has no leverage to force its clients to upgrade at all. In that situation, compatibility may need to be maintained for a very long time, possibly indefinitely, and if a genuinely breaking change is unavoidable, the provider often ends up running multiple versions of the API side by side rather than picking one. There's no single agreed-upon way to do API versioning (that is, how a client signals which version of the API it wants). Common approaches for RESTful APIs include putting a version number in the URL or in the HTTP Accept header; for services that identify clients by an API key, another option is to store each client's requested version server-side and let that be changed through a separate administrative interface.

5. Message brokers and their properties

Message-passing sits between the two paths above: like RPC, a message usually reaches its destination with low latency; like a database, it doesn't travel over a direct connection but through an intermediary, called a message broker (also a message queue, or message-oriented middleware), that holds the message temporarily rather than handing it straight to the recipient.

Routing messages through a broker instead of calling the recipient directly buys you several things at once: the broker can act as a buffer if the recipient is currently unavailable or overloaded, which improves reliability; it can automatically redeliver a message to a process that crashed before finishing it, so messages aren't just lost; it means the sender never needs to know the recipient's IP address or port, which matters a lot in a cloud environment where machines come and go; it lets a single message reach several recipients at once; and it decouples the sender from the recipient entirely, since the sender just publishes and doesn't need to know or care who ends up consuming it.

The trade-off compared to RPC is that message-passing is usually one-way and asynchronous: the sender doesn't wait around for delivery, it just sends the message and moves on ("fire and forget"). A reply is possible, but it would typically travel back over a separate channel rather than as a direct return value. Commercial brokers (TIBCO, IBM WebSphere, webMethods) dominated this space historically; more recently, open source brokers like RabbitMQ, ActiveMQ, HornetQ, NATS, and Apache Kafka have become the common choice. Mechanically, a broker generally works like this: a process sends a message to a named queue or topic, and the broker delivers it to one or more consumers (or subscribers) of that queue or topic; a single topic can have many producers and many consumers at once. A topic only carries data in one direction, but a consumer can itself republish messages onward to a different topic (chaining brokers together) or to a reply queue that the original sender reads from, which recreates something like a request/response pattern on top of an inherently one-way system.

Message brokers generally don't enforce any particular data model of their own: a message is really just bytes plus some metadata, so whatever encoding format you pick (from Part 1) is entirely up to you. If that encoding is both backward and forward compatible, you get the most freedom to change publishers and consumers independently and deploy them in whatever order you like. And the same caution from the database section applies here too: if a consumer republishes a message onward to another topic, it needs to be careful to preserve any fields it doesn't recognize, for the same reason an application shouldn't silently drop an unknown field when re-encoding a database record.

6. Distributed actor frameworks

The actor model is originally a concurrency model for a single process, an alternative to dealing with threads directly (and the race conditions, locking, and deadlocks that tend to come with them). Instead of shared-memory threads, logic lives inside independent actors: each actor typically stands in for one client or entity, holds its own local state that no other actor can reach directly, and communicates purely by sending and receiving asynchronous messages. Message delivery between actors isn't guaranteed; in some error scenarios a message is simply lost. Because each actor only ever processes one message at a time, it never has to worry about concurrent access to its own state, and the framework is free to schedule each actor independently.

A distributed actor framework takes this same programming model and stretches it across multiple machines: the identical message-passing mechanism is used whether the sender and recipient happen to share a node or not. When they're on different nodes, the message is transparently encoded into bytes, sent over the network, and decoded on the other end, which means the encoding and evolution rules from Part 1 apply here too. Location transparency actually works noticeably better in the actor model than it does in plain RPC, and the reason is subtle but important: the actor model already assumes messages can be lost, even between two actors sitting in the very same process. So moving from local to remote messaging doesn't introduce a fundamentally new kind of failure the way it does for RPC, it just adds more latency and a longer distance for that already-expected message loss to happen over. In effect, a distributed actor framework is close to a message broker and the actor programming model bundled together into one piece of software.

That said, distributed actors don't get a free pass on rolling upgrades: if you want to roll out a new version of an actor-based application gradually, you still need to plan for forward and backward compatibility, since a message might travel from a node already running the new version to a node still running the old one, or the other way around. The three frameworks named handle this differently by default. Akka defaults to Java's own built-in serialization, which (as covered in Part 1) doesn't give you forward or backward compatibility at all, though you can swap in something like Protocol Buffers instead and get the ability to do rolling upgrades. Orleans defaults to a custom encoding that doesn't support rolling upgrades in the usual sense; deploying a new version means standing up an entirely new cluster, migrating traffic over to it, and then shutting the old cluster down, though (like Akka) you can plug in custom serialization instead. Erlang OTP is, somewhat surprisingly given how much of the platform is built for high availability, genuinely hard to change record schemas in; rolling upgrades are possible there but need careful planning, and an experimental "maps" datatype (a JSON-like structure introduced in Erlang R17 in 2014) may make this easier over time.

Why it matters

The reason this part exists at all is that "can a reader make sense of bytes a writer produced" isn't just an encoding-format question, it's a question that gets asked constantly, across every one of these three paths, any time your system changes. It's what decides whether you can roll a new version of a service out to a handful of machines at a time without those machines and the not-yet-upgraded ones misreading each other's data. It's what decides whether a database that's been accumulating records for years can still present them all consistently to whatever code reads them today. And it's what decides whether two teams' services, or a producer and a consumer sitting on opposite ends of a message broker, can actually ship changes independently instead of being forced into lockstep releases. Rolling upgrades in particular are worth internalizing as the normal state of a live system, not a brief transitional blip, because they're what let you ship small changes often (instead of rare, risky, big-bang releases) and catch a broken release on a handful of machines before it reaches everyone.

Remember this

  • Storing something in a database is a lot like sending a message to your future self: backward compatibility is required so that self can read it, and forward compatibility is often required too, since older and newer code commonly run against the same database at once.
  • Data outlives code. Rows written years apart can sit in a single database at once, each in whatever encoding was current when it was written, which is exactly why schema evolution matters more for stored data than for code that gets replaced in minutes.
  • RPC tries to make a remote call look like a local one ("location transparency"), but a network call has failure modes (loss, timeouts, wildly variable latency, no safe pointer-passing) a local call never has, so that illusion is fundamentally leaky. REST's appeal is partly that it never pretends otherwise.
  • Message brokers decouple sender from recipient: the sender doesn't need the recipient's address, doesn't wait for a reply, and the broker can buffer, redeliver, and fan a message out to more than one consumer.
  • Distributed actor frameworks bundle a message broker and the actor concurrency model together, and get location transparency to work better than RPC does, precisely because the actor model already assumes messages can be lost. But their default encodings differ a lot in whether rolling upgrades are even supported (Akka: swap it in; Orleans: not by default; Erlang OTP: possible but tricky).

Try it yourself

  1. Write a message to your future self. Write a small script that encodes a record (say, a user profile with 3-4 fields) under an "old" schema and saves it to a file. Then write a second, separate script simulating a newer version of your code, whose schema adds one more field with a default value, and have it read the old file. Done when: your "new" reader can open the "old" file without erroring, and the missing field comes back as the default you defined.
  2. Reproduce the dropped-field bug, then fix it. Decode a record that has one field your reading code doesn't know about into a plain object that only has the fields it expects, then re-encode that object and compare it to the original bytes. Confirm the unknown field is gone. Then rewrite the decode/re-encode step so unknown fields are captured and carried through untouched. Done when: you can show the field vanishing in the first version and surviving in the fixed one.
  3. Build a tiny RPC client/server and break it on purpose. Write a minimal HTTP client and server (any language) where the client calls one endpoint. Make the server randomly (say, 1 in 5 calls) accept the request but never send a response, simulating a lost response. Have the client retry on timeout, and add an idempotency key so a retried request that actually landed twice doesn't double up its side effect (like incrementing a counter). Done when: you can force the "response lost, request landed" case and show your idempotency key stops the action from happening twice.
  4. Version an API two different ways. Build a tiny REST endpoint, then make a breaking change to its response shape. Expose both the old and new behavior at once, once using a version number in the URL path, and once using a version indicated in the HTTP Accept header. Done when: hitting the same underlying server two different ways returns two different (and correctly versioned) response shapes.
  5. Build a minimal message broker. Implement a tiny in-memory broker: a producer publishes to a named topic, and two independent consumer processes (or threads) both receive their own copy of each message. Then simulate a crashed consumer that never acknowledges a message, and have the broker redeliver it. Done when: both consumers get every message, and a message aimed at a "crashed" consumer gets redelivered instead of silently disappearing.
  6. Build a one-actor toy and hammer it with concurrent messages. Implement a single "actor": an object with private state and a message queue (mailbox) that a background loop drains one message at a time. Fire messages at it concurrently from several threads or async tasks (e.g., "increment a counter"). Done when: the final state is correct with zero explicit locks in your code, because the actor only ever processes one message at a time.
