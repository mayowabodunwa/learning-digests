S3 Buckets, Objects, Keys: The Flat Namespace, Durability & Consistency

S3 looks like a hard drive full of folders, and that picture is exactly what trips beginners up. Underneath, it's a giant lookup table: you hand it a bucket name and a key, and it hands back your object. Once that clicks, the naming rules, the "folders", and the consistency behavior all make sense.

In one line

Amazon S3 stores objects (data plus metadata) in buckets (containers), finds each one by a key (its name) in a flat space with no real folders, keeps copies across several data centers, and tells you the truth about what you just wrote.

The big idea

Most of us grew up with file systems: folders inside folders, a path, a file at the end. S3 is a different animal. It's an object store. You don't mount it like a disk and you don't edit a file in place. You put a whole object in, you get a whole object out, and every object is found by a name (the key) inside a container (the bucket). The slashes you see in names like photos/2026/cat.jpg are just characters in that name. The console draws folders for you because it's convenient, not because they exist.

This digest covers four things that sit at the foundation of everything else in S3: what buckets and objects are, how keys work (including the flat-namespace idea), how safe your data is (durability), and what you can count on when you read something right after writing it (the consistency model). Later S3 topics (access control, versioning, storage classes, lifecycle) all build on these.

Key terms

  • Object storage: a way of storing data as whole, self-contained objects that you address by name, instead of as files in a directory tree on a disk. S3 is an object store.
  • Bucket: the container that holds objects. You pick a name and an AWS Region when you create it. e.g. my-photos-2026.
  • Object: the thing you store. It's the data itself (any sequence of bytes) plus metadata that describes it.
  • Key (key name): the unique name of an object inside its bucket. e.g. photos/2026/cat.jpg.
  • Metadata: name-value pairs attached to an object. Some are set by S3 (like last-modified date) and some are standard HTTP ones (like Content-Type). You can also add your own custom pairs when you store the object.
  • Prefix: the leading part of a key, used to group objects. In photos/2026/cat.jpg, photos/ and photos/2026/ are both prefixes.
  • Delimiter: a character (most often /) used with a prefix to make a flat list look like folders when you list objects.
  • Flat namespace / flat structure: there is no tree of sub-buckets or subfolders. A bucket holds objects directly, and any hierarchy you see is inferred from the key text.
  • Namespace: the space in which names have to be unique. For general purpose buckets by default, that space is shared globally.
  • Partition: a grouping of AWS Regions. The docs list four: aws (standard Regions), aws-cn (China), aws-us-gov (GovCloud US) and aws-eusc (European Sovereign Cloud).
  • Region: a geographic location where AWS runs infrastructure. A bucket lives in exactly one Region.
  • Availability Zone (AZ): one or more discrete data centers in a Region with their own power, networking and connectivity.
  • Durability: how unlikely it is that your stored data gets lost or corrupted over time. Different from availability, which is whether you can reach the data right now.
  • Availability: whether requests succeed at a given moment. Durability and availability are separate numbers in the docs.
  • Strong read-after-write consistency: once a write succeeds, any read you start afterward sees that write.
  • Eventual consistency: a change takes a little while to show up everywhere, so a read right after might still show the old state.
  • Atomic update: a change that happens fully or not at all. A reader never sees half of it.
  • Last-writer-wins: when two writes to the same key overlap, one of them ends up as the stored result, and S3 decides using the latest timestamp.
  • Conditional write: a write that only goes through if a stated condition holds. With --if-none-match "*" on a put, the upload only succeeds if that key doesn't already exist.

How it works

Here's the grounding piece. S3 is a storage service you talk to over HTTP, through the console, the CLI, an SDK, or the REST API directly. There's no disk to attach and no operating system to log in to. You do a small set of things: create a bucket, put an object into it, get an object out, list what's there, delete things. Every one of those requests names a bucket, and most name a key. So you can picture the whole service as a very large map from (bucket + key) to object. The docs describe it in nearly those terms, adding an optional version ID on top if versioning is on (versioning is a later topic).

Everything is private by default. A bucket and its objects can only be reached if you explicitly grant access, so a brand new bucket isn't something the whole internet can read. How you grant access (policies, IAM, ACLs, access points) is its own topic, so I'm leaving it alone here.

1. Buckets: the top-level container

A bucket is the first thing you create. You give it a name and pick a Region, and from then on every object you store goes into some bucket. Three facts about buckets are worth having in your head straight away.

A bucket belongs to one account and one Region. The AWS account that created the bucket owns it, and ownership can't be transferred to another account. After creation you can't change the bucket's name or its Region. If you need a different name, you make a new bucket. Objects stored in a Region don't leave it unless you explicitly copy or replicate them elsewhere, which is why people pick a Region for latency, cost or regulatory reasons.

Buckets are the unit of organization at the top. The docs describe a bucket as the highest-level organizer of the S3 namespace, the account responsible for storage and data-transfer charges, and the unit that usage reporting aggregates on. You can't create a bucket inside another bucket.

There are several bucket types. The docs list four: general purpose buckets (the original type, recommended for most use cases), directory buckets (for low-latency and data-residency uses, organized into real directories rather than a flat space), table buckets (for tabular data in Apache Iceberg format) and vector buckets (for storing and querying vectors). This digest is about general purpose buckets, which are the flat-namespace ones. When I say "bucket" from here on, that's what I mean.

On quantity: the docs say that by default you can create up to 10,000 general purpose buckets per account, and you can ask for an increase through Service Quotas. There's no maximum bucket size and no limit on how many objects a bucket can hold. You can put everything in one bucket or split things across many. A common pattern in the docs is using separate buckets to separate different datasets or workloads.

2. Bucket names: unique across a whole namespace

This is the part that surprises people. By default, a general purpose bucket lives in a global namespace. That means the name has to be unique across all AWS accounts in all Regions within a partition, not just within your account. If someone else already has photos, you can't have it. Once you create a bucket in that shared space, nobody else in the partition can take that name until you delete the bucket.

The naming rules for general purpose buckets, as the docs list them:

  • 3 to 63 characters long.
  • Only lowercase letters, numbers, periods and hyphens.
  • Must start and end with a letter or number.
  • No two periods next to each other.
  • Can't look like an IP address (the docs' example is 192.168.5.4).
  • Can't start with xn--, sthree- or amzn-s3-demo-.
  • Can't end with -s3alias, --ol-s3, .mrap, --x-s3 or --table-s3. Those endings are reserved for other S3 features (access point aliases, Object Lambda aliases, Multi-Region Access Points, directory buckets and table buckets).
  • The ending -an is only allowed for buckets in your account regional namespace (see below).
  • If you plan to use S3 Transfer Acceleration, the name can't contain periods.

Simplification, with a caveat: that list is the general purpose rule set as the docs presented it in October 2026. Directory buckets and table buckets have their own, different naming rules, and the docs mention an older exception (buckets created in US East (N. Virginia) before March 1, 2018 could follow looser rules). Treat the list above as "the rules for creating a new general purpose bucket today".

A few practical points from the same page. Bucket names show up in the URLs that point at your objects, so don't put sensitive information in them. The docs recommend avoiding periods in names except for buckets used only for static website hosting, because periods break the certificate match for virtual-host-style addressing over HTTPS. And if your code creates buckets automatically, the docs suggest appending a GUID (a globally unique identifier) so you're unlikely to collide with a name somebody already took.

One more thing that I found unexpectedly important: deleting a bucket in the shared global namespace frees its name, and the docs warn that another account in the same partition could then create a bucket with that name and potentially receive requests that were meant for yours. Their suggestion if you want to keep the name is to empty the bucket and keep it rather than delete it.

The account regional namespace. The docs also describe an alternative: a reserved slice of the global namespace that only your account can create buckets in. Names there follow a fixed shape: a prefix you choose, then your 12-digit account ID, then the Region code, ending in -an. Their example is amzn-s3-demo-bucket-111122223333-us-west-2-an. You opt in when creating the bucket (the CLI create-bucket page lists a --bucket-namespace option that accepts account-regional or global). The point is that nobody else can ever take names in your slice. This is a newer feature than the classic global behavior, so check the namespaces page below before relying on details.

3. Objects: data plus metadata

An object is the unit S3 stores. According to the docs, it has a key (its name), a value (the content), metadata, optionally a version ID, and a few other attachments like tags and access-control information. The value can be any sequence of bytes, so a photo, a log file, a JSON document and a database backup are all just objects. Objects can range from zero bytes up to 50 TB according to the objects overview page.

A caveat on that 50 TB figure: the same page adds a note that the true maximum is 53.7 TB (48.8 TiB), because multipart upload allows up to 10,000 parts of up to 5 GiB each. For beginner purposes, "up to 50 TB per object" is the number the docs lead with. I'm not covering multipart uploads in this digest, so I won't state the size limit of a single plain upload, since I didn't verify it.

Metadata is a set of name-value pairs. S3 fills in some of them (like the last-modified date), some are standard HTTP headers (like Content-Type, which tells a browser it's an image or a PDF), and you can attach your own custom pairs at the time you store the object. Think of it as the label on the box, separate from what's inside.

Whole objects, not edits. A mental model that kept me out of trouble: if you want to change an object, you write a new object to the same key. You don't open it and change byte 400. That's the "overwrite" the consistency section talks about.

4. Keys and the flat namespace

The key is an object's unique identifier inside its bucket. The docs say each object has exactly one key, and that the combination of bucket, key and (if versioning is on) version ID identifies it uniquely.

Key rules. A key is a sequence of Unicode characters encoded as UTF-8, with a maximum length of 1,024 bytes. Bytes, not characters: the docs note that in some locales a single character needs 2 bytes. Keys are case sensitive, so Report.txt and report.txt are two different objects. And the whole key counts toward the limit, including any prefix and the slashes.

What characters are safe? You can technically use any UTF-8 character, but the docs sort characters into groups. The generally safe set is letters, digits, and a small group of punctuation: ! - _ . * ' ( ). A longer list of characters (like &, $, @, =, ;, :, +, ,, ?, spaces and some control characters) might need special handling such as URL encoding. A third list (including backslash, {, }, %, #, |, ~ and a few others) is flagged as best avoided because applications handle them inconsistently. The docs also advise against path-looking segments that are just . or .., since tools may "normalize" them and then fail to find the object. My practical takeaway: stick to lowercase letters, digits, hyphens, underscores, periods and slashes, and you'll almost never hit a surprise.

The flat namespace. This is the big one. The docs state it plainly: the data model is flat. You create a bucket, the bucket stores objects, and there's no hierarchy of sub-buckets or subfolders. The console, SDKs and CLI infer a hierarchy by looking at prefixes and a delimiter in the keys. So if a bucket contains these four keys:

docs/notes/week1.txt, docs/notes/week2.txt, docs/readme.txt, logo.png

then S3 holds four objects and nothing else. There's no docs object and no notes object. The console groups them into what looks like folders because it sees the shared prefixes docs/ and docs/notes/.

How does a listing show a "folder" view? You ask S3 to list keys that start with a given prefix and tell it a delimiter. Keys that have the delimiter after the prefix get rolled up into one entry, and the CLI list command reports them in a separate CommonPrefixes list, which the CLI docs describe as acting like subdirectories. Everything else comes back in Contents. Same flat data, different view.

The "create folder" button. The docs explain that when you create a folder in the console, it makes a zero-byte object whose key is the prefix plus the delimiter (for example docs/). Those folder objects don't show in the console, but they behave like any other object and can be seen through the REST API, CLI and SDKs. That's a lovely little proof that folders are just names.

Sort order. S3 lists keys in lexicographic order by their UTF-8 bytes. A practical effect from the docs: uppercase letters sort before lowercase letters, and non-ASCII characters generally sort after ASCII ones. So Apple/ comes before apple/.

What flat means for you in practice: there's no "rename folder" or "move folder" operation in the sense a file system has. Any such action amounts to working on every object that shares the prefix, which is a different kind of job. I'm inferring that from the data model rather than quoting a statement in the docs, so treat it as the mental model and check how the console or tools you use behave.

5. Durability: how S3 keeps your data safe

Durability is the question "will my data still be there, and still be correct, years from now?" The docs describe S3's approach in a few parts.

Redundancy across devices and zones. For the S3 Standard storage class (the default, used if you don't choose one) and several others, S3 stores objects redundantly on multiple devices across a minimum of three Availability Zones in a Region. The docs add that AZs are physically separated by a meaningful distance (many kilometers) while all being within 100 km (60 miles) of each other. These classes are designed to keep your data even if an entire AZ is lost.

Detecting and repairing. The docs say the infrastructure is designed to handle concurrent device failures by quickly detecting and repairing any lost redundancy, and that it regularly checks data integrity using checksums. In plain terms, it keeps checking its copies and fixes the damaged ones.

The number. The docs say S3 Standard is designed for 99.999999999% durability and 99.99% availability of objects over a given year. That durability figure ("eleven nines") is the same for most storage classes in the docs' comparison table. I want to flag two bounding words: it's a design target ("designed for"), not a guarantee that nothing can ever go wrong, and it's per object over a year. Availability is a separate and lower number, and it differs by class (the table lists 99.99% for Standard, 99.9% for Standard-IA, 99.5% for One Zone-IA, and so on).

Not every class spreads across zones. S3 One Zone-IA stores data in a single AZ, and S3 Express One Zone also uses a single AZ that you pick. The docs say One Zone-IA data isn't resilient to the physical loss of that zone (they mention disasters like earthquakes and floods). Choosing among classes is a later topic. For now the useful point is that "stored in S3" doesn't always mean "stored in three zones": that's true for Standard, not for every class.

A durability caveat that matters. Durability protects against the storage system losing data. It does nothing about you deleting or overwriting an object by mistake. The docs point to versioning, Object Lock and replication as the extra layers for that, all of which come later. So don't read "eleven nines" as "I can't lose this file".

6. The consistency model: what you can rely on

Consistency is about what a reader sees right after a writer finishes. S3 stores data across many servers, so in principle a read could hit a place that hasn't caught up yet. The docs state the current behavior clearly.

Objects: strong read-after-write. In all Regions, S3 gives strong read-after-write consistency for PUT and DELETE of objects. That covers brand new objects, overwrites of existing objects, and deletes. Reads of object metadata (such as a HEAD request), object tags and ACLs are strongly consistent too. Once a PUT returns success, any GET or LIST you start after receiving that response returns what was written. The docs give examples:

  • Write a new object, list the bucket right away: the object is in the listing.
  • Overwrite an object, read it right away: you get the new data.
  • Delete an object, read it right away: nothing comes back.
  • Delete an object, list right away: it's not in the listing.

Updates to a single key are atomic. If one thread overwrites a key while another reads it, the reader gets either the old data or the new data, never a half-written mix.

Concurrent writers: last writer wins. S3 doesn't lock objects for concurrent writers. If two PUTs hit the same key at about the same time, the one with the latest timestamp wins. The docs also point out that you can't predict the order the writes arrive in or the order their acknowledgments come back (network latency and distance matter), so the safe way to know the final value is to read after both writes have been acknowledged. If this matters to your application, the docs say you need to build your own locking into it. They also describe conditional writes on the put-object CLI page: --if-none-match "*" makes the upload succeed only if the key doesn't exist yet, and S3 answers 412 Precondition Failed if it does.

No cross-key atomicity. Updates are key-based. You can't make one key's update depend on another's, or update two keys as one all-or-nothing change, unless you design that into your application. If you write orders/1.json and orders/index.json, a reader could in principle see one new and one old.

Bucket configuration is different: eventual. This is the exception worth memorizing. The docs say bucket configurations are eventually consistent. Two examples they give: if you delete a bucket and immediately list all buckets, the deleted bucket might still show up; and the first time you enable versioning on a bucket it may take a short time to propagate fully, so they recommend waiting 15 minutes after enabling it before sending writes or deletes to objects in that bucket.

One more operational hint from the bucket overview page: because bucket operations work against a centralized, global resource space, the docs recommend you don't create, delete or configure buckets in the high-availability code path of your application. Do it in a setup step that runs less often.

Why it matters

These ideas show up in almost every S3 decision you'll make later. Bucket naming and the global namespace explain why scripts that create buckets fail with "name already taken" and why teams adopt naming schemes. The flat-namespace idea changes how you design keys: because listing works on prefixes, how you structure key names decides how easy it will be to find, list and manage groups of objects later (the docs show, for example, that bucket policies can use wildcards to cover objects with a common prefix, and that access can be controlled at the prefix level). The durability story tells you what S3 protects you from (hardware and even a whole zone) and what it doesn't (your own mistakes), which is the whole reason versioning exists. And the consistency model tells you what to trust in your code: you can write then immediately read or list objects and expect to see your change, but you can't assume two writers to one key will merge, and you can't treat two keys as one transaction.

It's also worth knowing the older folklore. A real example, dated: on December 1, 2020, AWS announced on its News Blog that S3 now delivers strong read-after-write consistency automatically for GET, PUT and LIST operations (plus operations that change tags, ACLs or metadata), for new and existing objects in all Regions, at no extra charge and with no stated performance impact. Before that, S3 was eventually consistent for some of these reads, and big data tools like EMRFS Consistent View and the open-source S3Guard existed in part to paper over that. If you read older blog posts and forum answers about "S3 eventual consistency", they were written about the pre-2020 behavior, not today's.

Remember this

  • S3 is a map from (bucket + key, plus version ID if versioning is on) to an object. The slashes in a key are just characters; the folder tree is inferred from prefixes and a delimiter.
  • General purpose bucket names live in a global namespace by default: 3 to 63 characters, lowercase letters, numbers, periods and hyphens, unique across accounts and Regions within a partition. You can't rename a bucket or move it to another Region.
  • A key can be up to 1,024 bytes of UTF-8, is case sensitive, and the prefix and slashes count toward that. Objects can be up to 50 TB, and a bucket can hold any number of them.
  • S3 Standard is designed for 99.999999999% durability over a year by storing across a minimum of three AZs. That's a design target against storage failure, not protection against you deleting or overwriting something.
  • Object reads are strongly consistent after a successful write, deletes included. Bucket configuration is eventually consistent. Overlapping writes to one key resolve as last-writer-wins, and there are no multi-key transactions.

Try it yourself

Heads up: the AWS CLI projects below create real resources in your account, so use a throwaway bucket and do the cleanup step at the end. I checked every command and option below against the AWS CLI reference pages and the local aws ... help output, but I couldn't run them against a live account while writing this, so read each error message carefully the first time. Project 1 is plain Python with no AWS account needed, and I did run it.

  1. Build a pretend S3 listing in Python (no AWS needed). Write a function that takes a list of key strings, a prefix and an optional delimiter, and returns two lists: contents (keys that have no delimiter after the prefix) and common_prefixes (the rolled-up "folders"). Sort the keys by their UTF-8 bytes before processing. Try keys like Apple/a, apple/a, docs/notes/week1.txt, logo.png. Done when: listing with prefix "" and delimiter / shows logo.png in contents and the top-level folders as common prefixes, listing with prefix docs/ shows docs/notes/ as a common prefix, listing with no delimiter returns every key under the prefix, and Apple/ sorts before apple/.
  2. Write a bucket-name checker and break it on purpose. Implement the general purpose rules from the list above (length, allowed characters, start and end, double periods, IP-address shape, reserved prefixes and suffixes) as a function. Feed it good and bad names such as my-bucket-01, My_Bucket, a..b, 192.168.5.4, xn--abc, logs-s3alias. Done when: every bad example is rejected for the reason you expect, and you've written down at least one rule your checker can't test offline (uniqueness across all accounts), plus the one it skips unless you add it (the -an account-regional rule).
  3. Create a bucket with a unique name using the CLI. In us-east-1 the docs' example needs no location constraint: aws s3api create-bucket --bucket "$BUCKET" --region us-east-1. For any other Region add the location constraint, for example aws s3api create-bucket --bucket "$BUCKET" --region eu-west-1 --create-bucket-configuration LocationConstraint=eu-west-1. Generate the name the way the docs suggest for avoiding collisions, with a GUID: BUCKET="my-s3-lab-$(uuidgen | tr -d - | tr '[:upper:]' '[:lower:]')". Done when: the create call returns a Location, aws s3 ls shows the bucket, and you can say why the first name you'd think of probably wouldn't have worked, and why amzn-s3-demo- names are rejected.
  4. Prove the flat namespace with the CLI. Put three small files with slash keys, for example aws s3api put-object --bucket "$BUCKET" --key docs/notes/week1.txt --body week1.txt (repeat for docs/notes/week2.txt and logo.txt). Then compare aws s3api list-objects-v2 --bucket "$BUCKET" with aws s3api list-objects-v2 --bucket "$BUCKET" --prefix docs/ --delimiter /. Done when: the first call shows full keys under Contents, the second shows a CommonPrefixes entry for docs/notes/, and you can explain in one sentence why no folder was ever created. Bonus: create a folder in the console and list again to spot its zero-byte object.
  5. Inspect an object and its metadata, and test case sensitivity. Upload with custom metadata: aws s3api put-object --bucket "$BUCKET" --key Report.txt --body report.txt --content-type text/plain --metadata owner=me,env=lab. Read it back without downloading: aws s3api head-object --bucket "$BUCKET" --key Report.txt. Upload another file as report.txt (lowercase). Done when: head-object shows ContentLength, ContentType and your Metadata, and the listing shows two distinct keys that differ only by case.
  6. Watch strong consistency and a conditional write. Overwrite Report.txt with new content, then immediately fetch it with aws s3api get-object --bucket "$BUCKET" --key Report.txt out.txt (the output file is the last, positional argument) and diff out.txt against what you uploaded. Then delete a key with aws s3api delete-object --bucket "$BUCKET" --key logo.txt and immediately list. Finally try aws s3api put-object --bucket "$BUCKET" --key Report.txt --body report.txt --if-none-match "*". Done when: the overwrite is visible instantly, the deleted key is gone from the very next listing, and the conditional put on an existing key fails with a precondition error (the CLI docs name this as HTTP 412).
    Cleanup, don't skip: aws s3 rb "s3://$BUCKET" --force removes the bucket's non-versioned objects and then the bucket. The CLI docs note it won't remove versioned objects, which doesn't matter here because you never enabled versioning. Confirm with aws s3 ls.
