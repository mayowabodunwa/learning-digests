EC2 Storage: EBS Volumes, Snapshots and Instance Store

An EC2 instance is just compute until you give it somewhere to keep data. EC2 offers two very different kinds of local-feeling disk: network-attached volumes that outlive the instance (EBS), and disks bolted to the host that vanish with it (instance store). Then there's the backup mechanism, snapshots, which has one counter-intuitive billing behaviour worth understanding early.

In one line

EBS volumes are durable block disks you attach to an instance in the same Availability Zone, snapshots are incremental point-in-time backups of them, and instance store is fast temporary disk that is lost when the instance stops or terminates.

The big idea

When I first launched an instance I assumed "the disk" was one thing. It's really two families with opposite promises. EBS (Elastic Block Store) is storage that persists independently from the running life of the instance, so you can stop the instance, detach the volume, and attach it elsewhere. Instance store is storage on the physical machine your instance runs on; it exists only as long as the instance does. Choosing between them is mostly a question: "Would I be upset if this data disappeared?"

Snapshots sit beside EBS. AWS says plainly that it does not automatically back up the data on your EBS volumes, so backups are your job (by hand, with Amazon Data Lifecycle Manager, or with AWS Backup).

A note on numbers: the figures below (IOPS, sizes, throughput) are what the EBS User Guide stated when I read it on 2026-10-25. They change with new volume generations, so treat them as a snapshot of the docs, not eternal facts. I quote no prices.

Key terms

  • Block storage: storage presented as a raw disk made of fixed-size blocks. The operating system formats it with a file system and mounts it, like a hard drive.
  • EBS volume: a durable, block-level storage device you attach to an instance.
  • Instance store: temporary block storage from disks physically attached to the host computer.
  • IOPS: input/output operations per second, how many reads and writes a disk can do each second.
  • Throughput: how much data per second moves to or from the disk, measured here in MiB/s.
  • SSD / HDD: solid-state vs. spinning hard disk. The docs say SSD types are tuned for IOPS on small I/O, HDD types for throughput on large streaming I/O.
  • Snapshot: a point-in-time copy of an EBS volume.
  • Incremental: only blocks changed since the previous snapshot are saved.
  • Availability Zone (AZ): an isolated location inside an AWS Region. A volume and its instance must be in the same one.
  • DeleteOnTermination: a per-volume setting that decides whether the volume is deleted when its instance is terminated.
  • Elastic Volumes: the feature that lets you change size, performance or type of a volume without detaching it.
  • Volume initialization: the work of downloading snapshot blocks into a freshly restored volume.

How it works

0. Grounding: where does an instance's data live?

An EC2 instance is a virtual machine. Its operating system needs a disk to boot from (the root volume) and often more disks for data. In the common setup those disks are EBS volumes: they aren't inside the physical server, they're reached over the network, which is why they can outlive it. The alternative, instance store, is a disk inside the server.

Simplification: "EBS is over the network" is the beginner mental model; the docs describe EBS volumes as attachable block devices and don't need you to know the wiring. What matters for you: separate lifetime from the instance.

1. EBS volumes: the basics

Per the docs, an EBS volume is a durable block-level device. After attaching, you use it "as you would use a physical hard drive". Facts worth holding:

  • You can attach multiple volumes to one instance.
  • The volume and the instance must be in the same Availability Zone.
  • Depending on volume and instance types, Multi-Attach lets one volume attach to several instances at once. In the volume-type table, only the Provisioned IOPS SSD types (io1, io2) list Multi-Attach as supported.
  • Attaching isn't the end: you still format and mount the volume from inside the OS (the lifecycle page mentions formatting, mounting and partitions as tasks you do by connecting to the instance).
  • Your account has a total storage limit; the docs point to the EBS quotas page for the numbers.

Example. A web server has a root volume (the OS) and a second volume mounted for its database files. You can stop the instance, detach the second volume, and attach it to a replacement instance in the same AZ. Same AZ is the catch: to move the data to another AZ you go through a snapshot (section 4).

2. Volume types: pick by what limits you

The docs sort volumes into SSD (optimised for IOPS with small I/O) and HDD (optimised for throughput with large streaming I/O). Here's the table from the volume types page, paraphrased by me:

  • gp3 (General Purpose SSD): 1 GiB to 64 TiB, up to 80,000 IOPS, up to 2,000 MiB/s. Use cases listed: boot volumes, dev/test, medium single-instance databases, virtual desktops.
  • gp2 (older General Purpose SSD): 1 GiB to 16 TiB, up to 16,000 IOPS, up to 250 MiB/s.
  • io2 Block Express (Provisioned IOPS SSD): 4 GiB to 64 TiB, up to 256,000 IOPS, up to 4,000 MiB/s. Aimed at consistent sub-millisecond latency and very high IOPS or throughput. Listed durability 99.999%.
  • io1: 4 GiB to 16 TiB, up to 64,000 IOPS, up to 1,000 MiB/s.
  • st1 (Throughput Optimized HDD): 125 GiB to 16 TiB, up to 500 IOPS and 500 MiB/s. Big data, data warehouses, log processing. Not a boot volume.
  • sc1 (Cold HDD): 125 GiB to 16 TiB, up to 250 IOPS and 250 MiB/s. Infrequently accessed data where lowest cost matters. Not a boot volume.
  • standard (Magnetic): a previous-generation type, listed as 1 GiB to 1 TiB and for rarely accessed data. The docs recommend current-generation types if you need better performance.

Caveats the docs attach to those maximums: the max IOPS figures depend on I/O size; the gp3 and io2 top IOPS need Nitro-based instances (the docs say other instance types can attach volumes provisioned with up to 64,000 IOPS but achieve up to 32,000); io1 reaches its 1,000 MiB/s only with 64,000 IOPS on a Nitro instance; and volume performance is affected by instance configuration, so the docs advise EBS-optimized instances to use the full provisioned IOPS. Durability for most types is stated as 99.8%-99.9% (an annual failure rate of 0.1%-0.2%), which is why snapshots matter.

3. gp3 vs. gp2: how performance is decided

This is a neat piece of the docs because it shows two design styles.

gp3 decouples performance from size. Every gp3 volume has a baseline of 3,000 IOPS and 125 MiB/s included in the storage price. You can pay to provision more, up to 80,000 IOPS and 2,000 MiB/s, without growing the volume. Provisioned IOPS are capped at 500 IOPS per GiB (so you need at least 160 GiB for 80,000), and throughput at 0.25 MiB/s per provisioned IOPS. gp3 does not use burst credits; it sustains what you provisioned. The docs also say gp3 is priced 20 percent lower per GiB than gp2 (a relative statement from the docs; I give no actual price).

gp2 ties performance to size. Baseline is 3 IOPS per GiB, with a floor of 100 and a cap of 16,000 (reached at 5,334 GiB). Volumes under 1 TiB can burst to 3,000 IOPS using I/O credits: each volume starts with 5.4 million credits, spends them at the rate (burst IOPS minus baseline IOPS), and earns 3 credits per GiB per second when below baseline. Worked example from the docs' table: a 100 GiB gp2 volume has a 300 IOPS baseline, so bursting to 3,000 spends 2,700 credits/second, and 5,400,000 / 2,700 = 2,000 seconds of burst. You can watch the BurstBalance CloudWatch metric.

Simplification flag: the "decoupled" picture is the baseline story. Extra provisioned performance costs extra, and the max is still bounded by volume size ratios and by what the instance can drive.

4. Snapshots: incremental backups

A snapshot is a point-in-time copy of a volume. The docs' key rules:

  • The first snapshot of a volume is a full one; later ones are incremental, containing only changed and new blocks since the last snapshot.
  • Size and billing follow the data, not the volume size. A 200 GiB volume with 50 GiB written gives a 50 GiB first snapshot.
  • Snapshots are stored in Amazon S3 in buckets you cannot access directly. You manage them through EC2 (console or API), not the S3 console or API.
  • Snapshot data is replicated across all AZs in the Region, so you can restore into any AZ in that Region.
  • A volume created from a snapshot starts as an exact replica of the volume at snapshot time.

The docs' worked example. A volume has 10 GiB of data: Snap A stores 10 GiB. Then 4 GiB change: Snap B stores 4 GiB and references the other 6 GiB in A. Then 2 GiB are added: Snap C stores 2 GiB and references B and A. Total stored: 10 + 4 + 2 = 16 GiB.

Deleting is counter-intuitive. When you delete a snapshot, only data referenced exclusively by that snapshot is removed. Data a later snapshot needs is kept and its cost is attributed to the later snapshot. So deleting a snapshot might not reduce your storage bill. And you only need to retain the most recent snapshot to restore the volume; deleting earlier ones doesn't stop you restoring from later ones.

Other rules the deletion page lists: you can't delete the root-device snapshot of a registered AMI until you deregister the AMI; you can't delete snapshots managed by AWS Backup through EC2; and deleting a volume doesn't affect snapshots made from it (nor the reverse).

Caveat on incrementals: the docs note a snapshot becomes full instead if, for example, the source snapshot was shared from another account or the new volume used a different KMS key. Archiving a snapshot also converts it to a full snapshot in the cheaper-rate Snapshot Archive tier (different billing rate).

5. Restoring: the first-read penalty

Volumes created from snapshots must first have their blocks downloaded from Amazon S3; this is called volume initialization. During it, the volume might see higher latency and lower performance, and full performance arrives only once all blocks are loaded. Empty new volumes don't need this. The docs give three ways to soften it: a provisioned rate for volume initialization (100 to 300 MiB/s, costs extra), fast snapshot restore (volumes from enabled snapshots are fully initialized at creation), or manually reading every block (with dd or fio). I read the initialization page in full but only the overview of fast snapshot restore, so check its page before depending on it.

6. Changing a volume while it's in use

With Elastic Volumes you can increase size, change performance and change type without detaching. Order of work from the docs: optionally snapshot first (to roll back), request the modification, monitor it, and if you grew the size, extend the file system inside the OS so it uses the new space. Growing the disk doesn't automatically grow the file system. Example from the docs: aws ec2 modify-volume --volume-id vol-... --volume-type io1 --iops 10000 --size 200. This works for current-generation volumes on supported instance types; otherwise you may need to stop the instance for a root volume. The docs I read don't say whether you can shrink a volume, so I won't claim either way.

7. Instance store: fast, temporary, free-with-the-instance

Instance store gives block storage from disks physically attached to the host. Docs-stated facts:

  • Suited to buffers, caches, scratch data and other temporary content, or data replicated across a fleet (e.g. a load-balanced pool of web servers).
  • Not every instance type has it, and size and device count vary by instance type and size.
  • No additional charge; included in the instance's usage cost.
  • Attached only at launch. You can't attach later or move a volume between instances.
  • The device names run ephemeral0 to ephemeral23.

When does the data survive? From the persistence table: it survives a reboot (and an OS restart, and a power failure followed by reboot). It does not survive stop, hibernate, terminate, instance retirement, or the underlying disk failing, and not recovery actions or an instance-type change either. On stop, hibernate or terminate, every block is cryptographically erased. A subtle one: stop and termination protection do not protect you from an OS-initiated shutdown, which stops or terminates the instance (and, per the docs, instance store data does not persist in either case).

8. DeleteOnTermination: the EBS surprise

EBS survives stopping, but on termination each volume is deleted or kept per its DeleteOnTermination attribute. The docs' defaults table: root volume attached at launch: deleted; root volume attached after launch: preserved; data volume attached at launch via the console: preserved; data volume at launch via the CLI: deleted; data volume attached after launch: preserved. So the same data volume behaves differently depending on how it was created. The docs recommend verifying the setting after launch (Storage tab, "Delete on termination" column). Preserved volumes keep incurring charges until you delete them. You can set "DeleteOnTermination": false in a block device mapping at launch, or use modify-instance-attribute on a running instance.

Simplification flag: the defaults come from the AMI's attribute and can be overridden at launch, so the table is the default case, not a law.

Why it matters

Almost every "I lost my data" story on EC2 is one of three things: data on instance store, a root volume deleted at termination, or no snapshot. Understanding the split also drives design: stateless web servers can use instance store or just the root volume, while databases need EBS plus snapshots. It links to the earlier AMI digest too: an EBS-backed AMI is built from snapshots, which is why a root snapshot can't be deleted while its AMI is registered.

Remember this

  • EBS persists independently of the instance's running life and must be in the same AZ as the instance; instance store dies on stop, hibernate or terminate but survives a reboot.
  • Pick EBS types by bottleneck: SSD for IOPS (gp3 default-ish choice, io2 for extreme), HDD (st1, sc1) for throughput and cost, and neither HDD type can boot.
  • gp3 gives 3,000 IOPS and 125 MiB/s baseline at any size; gp2 ties IOPS to size and bursts with credits.
  • Snapshots are full once, then incremental, billed by data not volume size, and deleting one may not shrink your bill. AWS does not back up EBS for you.
  • Check DeleteOnTermination: defaults differ for root vs. data volumes and console vs. CLI.

Try it yourself

Projects 1 to 3 need no AWS account. Project 4 is a read-only CLI call and project 5 launches a small instance (it can cost money; clean up afterwards). I did not run any AWS CLI commands against a live account; their options were checked against the docs pages quoted above. The logic in projects 1 and 2 is simple arithmetic I cross-checked against the docs' own examples.

  1. Snapshot ledger (no AWS). Model a volume as a set of block numbers. Write snapshot() that stores only blocks changed since the last snapshot and records references for the rest, and delete(snap) that removes only exclusively-owned blocks. Done when: your ledger reproduces the docs' example: 10, then 4, then 2 GiB totalling 16, and deleting Snap A in the two-snapshot case leaves 10 GiB stored.
  2. gp2 vs. gp3 calculator (no AWS). Write functions for gp2 baseline IOPS (3 per GiB, floor 100, cap 16,000) and burst duration (credits divided by burst minus baseline). Done when: a 100 GiB volume returns 300 IOPS and 2,000 seconds of burst, and you can say at what size gp2's baseline reaches gp3's included 3,000.
  3. Persistence quiz (no AWS). Encode the instance-store persistence table as a dictionary and quiz yourself on ten events. Done when: you score 10/10 without peeking and can explain the stop-protection footnote.
  4. Inventory your volumes. Run aws ec2 describe-volumes --query 'Volumes[].{Id:VolumeId,Type:VolumeType,Size:Size,AZ:AvailabilityZone,State:State}' --output table (read-only). Done when: you can name any volume in the available (unattached) state, which still incurs charges per the docs' general note on preserved volumes.
  5. Prove the lifetimes (small cost). Launch a tiny instance with an extra EBS data volume, write a file to it, snapshot it, terminate the instance, then check whether the volume survived according to its DeleteOnTermination value. Restore a new volume from your snapshot in the same Region. Done when: you can show the file in the restored volume and have deleted the instance, volumes and snapshot afterwards.
