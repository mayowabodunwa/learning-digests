S3 Encryption: SSE-S3, SSE-KMS, DSSE-KMS, SSE-C and Bucket Keys

Every new object in S3 is encrypted at rest without you doing anything. The real choice is who holds the keys: S3 itself, AWS KMS where you get policies and an audit trail, two layers of KMS-based encryption, or a key you bring yourself. Bucket Keys then exist to keep the KMS option from getting expensive.

In one line

S3 server-side encryption has four mutually exclusive flavours (SSE-S3, SSE-KMS, DSSE-KMS, SSE-C) that differ in who manages the keys and how many encryption layers apply, and S3 Bucket Keys are a cost-saving layer on top of SSE-KMS.

The big idea

"Encryption at rest" means data is scrambled on the disks where it's stored. With server-side encryption, S3 does the scrambling when it writes your object and the unscrambling when you read it. The docs say that as long as your request is authenticated and you have permission, you access encrypted and unencrypted objects the same way. Presigned URLs, listings, all of it works the same.

So the question this digest answers isn't "is my data encrypted?" (for new objects the docs say yes, by default) but "who controls the key?" That decides who can read the data, what shows up in audit logs, and what it costs. I'll go option by option, then look at default encryption settings, Bucket Keys, and the order of operations when you want to change things.

Simplification label: this digest covers server-side encryption only. Client-side encryption (you encrypt before uploading) is a separate approach I haven't covered, and I don't quote any prices.

Key terms

  • Encryption at rest: protecting stored data so it's unreadable without the right key.
  • Server-side encryption (SSE): encryption done by the service that receives the data, here S3, at the object level as it writes to disk.
  • Key: the secret used to scramble and unscramble data.
  • Data key: a key used to encrypt the object's actual data. In SSE-KMS each object normally gets its own.
  • Envelope encryption: encrypting your data with a data key, then encrypting that data key with a more protected key.
  • AWS KMS: AWS Key Management Service, a managed service for creating and controlling keys.
  • KMS key: the protected key inside KMS that wraps data keys. Either an AWS managed key or a customer managed key.
  • AWS managed key (aws/s3): a KMS key AWS creates in your account for S3 the first time you use SSE-KMS without naming a key.
  • Customer managed key: a symmetric KMS key you create and control (policies, rotation, disabling).
  • Encryption context: unencrypted key-value pairs attached to an encryption operation; decryption must supply the same ones. Useful for tracking in audit logs.
  • Default encryption configuration: a bucket setting that says how objects are encrypted when the upload request doesn't say.
  • S3 Bucket Key: a short-lived bucket-level key that cuts the number of calls S3 makes to KMS.

How it works

0. Grounding: the baseline is already on

The docs state that S3 applies SSE-S3 as the base level of encryption for every bucket, and that since January 5, 2023 all new object uploads are automatically encrypted at no additional cost and with no impact on performance. SSE-S3 is the default configuration for every bucket. You change that in one of two ways:

  • Per request: put encryption information in the upload request (SSE-KMS, DSSE-KMS or SSE-C are allowed there).
  • Per bucket: change the bucket's default encryption configuration (SSE-KMS or DSSE-KMS are allowed there; SSE-C is not supported as a default).

If an upload request carries encryption info, S3 uses it. If it doesn't, S3 uses the bucket default. One object can only have one type of server-side encryption at a time.

1. SSE-S3: keys managed by S3

Each object is encrypted with a unique key, and that key is itself encrypted with a root key that S3 rotates regularly. The docs describe it as using 256-bit AES (the encryption-options page says AES-256, the SSE-S3 page says AES-GCM). There are no additional fees for SSE-S3, though requests to configure default encryption cost the usual request charges.

  • To ask for it explicitly, send the header x-amz-server-side-encryption: AES256. S3 echoes the header back in responses.
  • Don't send encryption headers on GET or HEAD for SSE-S3 objects (or SSE-KMS ones): the docs say you'll get an HTTP 400.
  • Encryption covers object data only, not object metadata.
  • A bucket policy can deny uploads that lack the header (the docs show a condition on s3:x-amz-server-side-encryption not equal to AES256), but the docs warn that such a deny can also block services that deliver objects without the header, such as some log deliveries.

2. SSE-KMS: keys in AWS KMS

With SSE-KMS you get more control: you can view separate keys, edit key policies, and follow key use in AWS CloudTrail. Two key types:

  • AWS managed key (aws/s3): used by default if you don't name a key. S3 creates it in your account the first time you add an SSE-KMS object. Objects encrypted this way can't be shared cross-account.
  • Customer managed key: you create it (it must be a symmetric encryption key), and you control policies, rotation and disabling. Needed if you want cross-account access. The docs recommend a fully qualified key ARN rather than an alias in cross-account cases, because an alias resolves in the requester's account.

Rules and limits from the docs: the KMS key must be in the same Region as the bucket; S3 supports only symmetric encryption KMS keys; and additional AWS KMS charges apply. Requests for KMS-encrypted objects must use TLS and be signed.

How envelope encryption works here (the docs' workflow, in my words):

  1. On write, S3 asks KMS for a data key. KMS returns the plaintext data key plus a copy encrypted under your KMS key.
  2. S3 encrypts the object with the data key, discards the plaintext key from memory as soon as it can, and stores the encrypted data key as metadata beside the object.
  3. On read, S3 sends the encrypted data key to KMS to be decrypted, uses the returned plaintext key to decrypt the object, and discards it again.

Permissions. For SSE-KMS, uploading needs kms:GenerateDataKey on the key, downloading needs kms:Decrypt, and a multipart upload needs both. Note what that means: having S3 permission to a bucket isn't enough to read SSE-KMS objects; you also need access on the key. The docs also advise restricting customer managed key policies to only the principals and services that need them.

Auditing. CloudTrail logs the KMS operations (for example GenerateDataKey and Decrypt), so you can see who used which key. The AWS console for KMS doesn't support the auditing, per the docs, but the KMS API does.

Encryption context. By default S3 uses the object ARN as the encryption context, or the bucket ARN if Bucket Keys are on. You can add one more pair with the x-amz-server-side-encryption-context header, but because the context isn't encrypted, don't put secrets in it.

Requiring KMS. A bucket policy can deny s3:PutObject unless the request names a KMS key (the docs show a Null condition on the KMS key ID header). If a request says aws:kms without a key ID, S3 assumes the AWS managed key.

Two gotchas in the docs. A server-access-log destination bucket must use SSE-S3, because with SSE-KMS default encryption S3 might deliver log objects encrypted with a key you can't access. And with default encryption set to SSE-KMS or DSSE-KMS, you're subject to KMS requests-per-second quotas.

3. DSSE-KMS: two layers

Dual-layer encryption applies two independent layers of AES-256. First, your data is encrypted with a KMS-generated data key; then the already-encrypted data is encrypted again with a separate S3-managed key. The docs position it for compliance regimes that require multilayer encryption, and note that it costs more and adds slightly higher latency. The KMS key must be in the same Region as the bucket, and S3 Bucket Keys aren't supported with DSSE-KMS. A bucket policy can require it with a condition value of aws:kms:dsse.

4. SSE-C: you bring the key

With SSE-C, you supply your own key in each request and S3 does the encryption work, but never stores your key. The consequences, straight from the docs' considerations list:

  • You must supply the key every time anyone downloads the object, and you track which key goes with which object. Lose the key and you lose the object.
  • You must use HTTPS. S3 rejects HTTP requests with SSE-C, and the docs say to treat a key sent over HTTP as compromised.
  • In a versioned bucket, each version can have its own key, so you track keys per version.
  • It isn't supported in the S3 console, and objects encrypted with SSE-C can't be natively decrypted by AWS managed services.
  • It can't be the bucket default.

Recent change worth knowing: the docs say that starting April 2026, SSE-C is disabled by default for all new general purpose buckets, and for existing buckets in accounts with no SSE-C encrypted objects. While blocked, upload requests that specify SSE-C are rejected with a 403 AccessDenied. To use it, you must set BlockedEncryptionTypes to NONE in the bucket's encryption configuration with PutBucketEncryption. The docs themselves say most modern workloads use SSE-S3 or SSE-KMS instead.

5. S3 Bucket Keys: making SSE-KMS cheaper

Without a Bucket Key, S3 uses an individual KMS data key per object and calls KMS every time a request touches a KMS-encrypted object. For workloads touching millions or billions of objects, that is a lot of KMS requests. With a Bucket Key, KMS generates a short-lived bucket-level key that S3 keeps temporarily and uses to create data keys for new objects, which the docs say can reduce KMS request costs by up to 99 percent. (Treat "up to 99 percent" as a ceiling: the docs say savings depend on the number of requesters, request patterns and object age.)

  • New objects only. Objects already in the bucket don't use the Bucket Key; the docs say to use CopyObject to apply it to existing ones.
  • How to turn on: in the default encryption rule (BucketKeyEnabled), or per request with the header x-amz-server-side-encryption-bucket-key-enabled: true (or false) to override the bucket setting.
  • Policy side effect: Bucket Keys use the bucket ARN as the encryption context instead of the object ARN, so any IAM or KMS key policy that matches on the object ARN will stop working and needs updating. CloudTrail will also show the bucket ARN and fewer KMS events.
  • Shared only per KMS key: a Bucket Key is shared only among objects encrypted by the same KMS key. Not supported for DSSE-KMS.
  • Different callers still count: bucket-level keys are fetched at least once per requester so access is captured in CloudTrail.

6. Default encryption and changing existing objects

  • Changing a bucket's default (for example to SSE-KMS) does not change objects already stored. The docs point to S3 Batch Operations (with a Copy action) to rewrite existing objects with a new encryption type, optionally driven by an S3 Inventory list.
  • Changing an object's encryption means creating a new object. In a versioned bucket, that creates a new version, and the role that did it becomes the owner of the new object. In the console, objects over 5 GB need the CLI or SDK for this.
  • S3 doesn't validate the KMS key ID you pass to PutBucketEncryption, so double-check it.
  • Default encryption itself has no additional charge; KMS charges apply for SSE-KMS and DSSE-KMS.

CLI shapes from the docs (placeholders in braces):

aws s3api put-bucket-encryption --bucket {bucket} \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyID": "{KMS-Key-ARN}"
      },
      "BucketKeyEnabled": true
    }]
  }'

aws s3api put-object --bucket {bucket} --key {key} \
  --server-side-encryption AES256 --body {file}

Why it matters

Encryption choices are about access control and accountability as much as secrecy. SSE-S3 asks nothing of you. SSE-KMS adds a second permission check (the key policy) and an audit trail, which is why it's common where you need to say who touched what, and why cross-account sharing needs a customer managed key. Bucket Keys are what keeps SSE-KMS from turning into a KMS bill at scale. And understanding SSE-C's trade-offs explains why AWS now blocks it by default. This leads straight into the next concept, access control, where the key policy and the bucket policy both have a say.

Remember this

  • New objects are encrypted at rest by default with SSE-S3, no extra fee. Your real choice is who manages the key.
  • SSE-KMS adds key policies and CloudTrail auditing; you need both S3 and KMS permissions. Cross-account sharing needs a customer managed key.
  • DSSE-KMS applies two layers and doesn't support Bucket Keys. SSE-C means you hold every key, and it's now blocked by default on new buckets.
  • Bucket Keys cut KMS request traffic for new SSE-KMS objects, and change the encryption context from object ARN to bucket ARN.
  • Changing the default doesn't touch existing objects; rewrite them (Batch Operations copy) if you need to.

Try it yourself

Projects 1 and 2 are offline. Projects 3 to 5 use the AWS CLI on a scratch bucket; the KMS ones create a KMS key, which has costs and a deletion waiting period, so use a throwaway key and schedule it for deletion afterwards. I checked the commands against the docs' syntax but haven't run them against a live account.

  1. Envelope encryption toy (offline, ~1.5 hours). In any language with a crypto library, write a "KMS" class that holds a master key and offers generate_data_key (returns plaintext plus wrapped copy) and decrypt. Write an "S3" that encrypts a file with the data key, stores the wrapped key beside it, and drops the plaintext key. Done when you can round-trip a file and explain why leaking the stored files alone doesn't reveal the content.
  2. Decision table (offline, 30 min). Make a table of the four options with columns: who holds keys, layers, extra fees mentioned in the docs, audit trail, console support, can be bucket default. Fill it from the docs, not memory. Done when every cell cites a docs page.
  3. Check the default. Create a scratch bucket, upload a file with a plain aws s3api put-object, then run aws s3api head-object and look for the ServerSideEncryption field. Done when you've seen AES256 without having asked for it.
  4. Switch to SSE-KMS with a Bucket Key. Create a symmetric KMS key, apply the docs' second put-bucket-encryption example, upload a new object, and check head-object for SSEKMSKeyId and BucketKeyEnabled. Then confirm the earlier object is unchanged. Done when the old and new objects show different encryption types.
  5. Break it on purpose. Using a second IAM identity with S3 access but no KMS permissions (or a policy you tweak to remove kms:Decrypt), try to download the SSE-KMS object. Done when you've seen the access-denied error and can say which permission was missing.
