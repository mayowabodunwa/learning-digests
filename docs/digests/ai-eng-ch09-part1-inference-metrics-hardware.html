Inference Optimization: Bottlenecks, Metrics and AI Hardware

Everything so far was about making a model better. Chapter 9 is about making it faster and cheaper, which is what decides whether anyone can afford to use it. Before any tricks, the chapter builds a vocabulary: what inference actually is, what a "bottleneck" means for a model, which numbers to measure (TTFT, TPOT, throughput, goodput, MFU, MBU), and what AI chips are made of. This part covers all of that groundwork. Part 2 covers the optimization techniques themselves.

In one line

You can't speed up what you haven't measured, so this part teaches you to identify whether inference is limited by computation or by moving data around, to read the standard latency, throughput and utilization numbers, and to understand the hardware those numbers come from.

The big idea

A great model that's too slow or too expensive is not useful. Inference optimization happens at three levels: the model (make it smaller or more efficient), the hardware (better chips) and the service (smarter scheduling and resource use). All of them begin with the same step as any optimization: find the bottleneck. For modern language models, the interesting twist is that generating text has two phases with different bottlenecks. Reading your prompt is limited by raw arithmetic; writing the answer, one token at a time, is usually limited by how fast the chip can fetch the model's weights from memory. Once you see that, most of the later techniques will make sense.

Key terms

  • Inference: using a trained model to compute an output for an input (the forward pass only).
  • Inference server / inference service: the server hosts the models and runs them on hardware; the service also receives, routes and may preprocess requests.
  • Compute-bound: a task whose speed is limited by how many calculations the chip can do.
  • Memory bandwidth-bound: a task limited by how fast data can move between memory and the processor.
  • Memory capacity-bound: a task that doesn't fit in memory at all (the familiar out-of-memory error). Not the same thing as bandwidth-bound.
  • Arithmetic intensity: the number of arithmetic operations per byte of memory accessed. It decides which kind of bound an operation is.
  • Prefill / decode: the two phases of language model inference. Prefill processes the input tokens in parallel; decode generates output tokens one at a time.
  • Online API / batch API: one optimized for latency, the other for cost.
  • Streaming mode: returning tokens as they're generated.
  • Latency, TTFT, TPOT: total response time; time to first token; time per output token.
  • Percentile (p50, p90, p99): the value below which that percentage of requests fall.
  • Throughput: output tokens per second across all users (or completed requests per unit time).
  • SLO: the target your service must hit (here "software-level objective", as the chapter defines it).
  • Goodput: requests per second that meet the SLO.
  • Utilization, MFU, MBU: how much of a resource's capacity you really use; model FLOP/s utilization; model bandwidth utilization.
  • FLOP/s: floating-point operations per second.
  • Accelerator, GPU, TPU: a chip built for a particular kind of work; graphics processing unit; Google's tensor processing unit.
  • HBM, SRAM, DRAM: kinds of memory in the hierarchy, from large and slow to small and fast.
  • TDP: thermal design power, a chip's expected heat output under typical load.

How it works

Grounding: what an inference service is

A model has two life stages: training builds it, inference uses it. Unless you train or finetune, inference is the part you care about. In production, an inference server hosts the models on hardware and, when a request comes in (say a user prompt), allocates resources, runs the model and returns the answer. It sits inside a broader inference service that receives, routes and possibly preprocesses requests first. If you call a model API from a provider, you're using someone else's inference service and they handle most of this chapter's techniques for you. If you host a model yourself, you build and maintain it. Even if you never implement these techniques, the chapter argues, understanding them helps you judge services and frameworks and diagnose your own latency and cost.

A cost angle worth noting: the chapter's footnote points out that a model developer only profits if revenue from inference exceeds training cost, which is one reason heavily used models can afford to cut inference prices. It adds that this logic doesn't apply to third-party providers selling inference on open source models.

Two kinds of bottleneck

Optimization is about finding the bottleneck, the way a city planner looks for congestion points. The chapter gives two main computational ones:

  • Compute-bound. The time is set by how much calculation there is. Password cracking is the chapter's example.
  • Memory bandwidth-bound. The time is set by how fast data moves between memory and the processor. For example, if your data lives in CPU memory but the work happens on a GPU, shuttling it across can dominate. Many people shorten this to "memory-bound".

Watch the terminology. The chapter flags that "memory-bound" is used two ways: bandwidth-bound (common among systems and GPU engineers) and capacity-bound (the out-of-memory error, common among ML engineers). Capacity problems can often be worked around by splitting the task, at the cost of transfer time, so they're really bandwidth problems in disguise. When someone says "memory-bound", ask which they mean.

Mathematically (from the "Roofline" paper), an operation's arithmetic intensity, the number of arithmetic operations per byte of memory read or written, decides which regime it's in. Profiling tools such as NVIDIA Nsight can draw a "roofline chart" showing where your workload sits. The fix depends on the bound: compute-bound work benefits from more chips or chips with higher FLOP/s; bandwidth-bound work benefits from chips with higher bandwidth.

Different models land differently. The chapter says Stable Diffusion-style image generation is typically compute-bound, while autoregressive language model inference is typically memory bandwidth-bound. As of the chapter's writing, many AI and data workloads are bandwidth-bound, though it expects future advances could make them compute-bound. That is a statement about the present, not a law.

Prefill versus decode

Language model inference has two steps. Prefill: the model processes all your input tokens in parallel. How many it can chew through at once is limited by the chip's operations per second, so prefill is typically compute-bound. Decode: the model generates one output token at a time, and each step involves loading large matrices (the weights) into the GPU, so it is typically memory bandwidth-bound. Because they behave so differently, production systems often run them on separate machines (Part 2 covers that). Context length, output length and how requests are batched together all change how much prefill and decode work there is, and therefore the bottleneck. The chapter notes that long context usually makes a workload bandwidth-bound, but clever techniques can remove that bottleneck.

Online and batch APIs

Many providers offer two kinds of inference API. Online APIs process requests as they arrive and optimize latency. Batch APIs optimize cost: with relaxed latency the provider can batch requests and use cheaper hardware. The chapter says that, at its time of writing, both Google Gemini and OpenAI offered batch APIs at a 50% cost reduction with turnaround in the order of hours instead of seconds or minutes (these are vendor terms that change; check current docs). Customer-facing chatbots and code completion want online; good fits for batch include synthetic data generation, periodic reports, onboarding a new customer's documents, reprocessing after migrating to a new model, personalized newsletters and knowledge base reindexing. Online APIs may still batch internally if it doesn't hurt latency.

Streaming. Generation can take a long time, so many online APIs stream tokens as they're produced, shortening the wait for the first one. The downside: you can't score the full response before the user sees it, though you can retract it afterward if you detect a problem.

A vocabulary trap: "batch inference" in traditional ML means precomputing predictions before requests arrive (feasible for finite inputs like recommendations). A foundation-model batch API is different: the prompts are open-ended and arrive from you, it just processes them with relaxed timing.

Latency metrics: TTFT, TPOT and percentiles

From the user's perspective the central axis is latency (answer quality belongs to the model, not the service). For autoregressive generation, especially streamed, the chapter splits it up:

  • Time to first token (TTFT): how long until the first token appears. It corresponds to the prefill step and depends on input length. A chatbot wants it near-instant; users may tolerate longer for summarizing a long document.
  • Time per output token (TPOT): how fast each subsequent token arrives. At 100 ms per token, 1,000 tokens take 100 s. Because people read at limited speed, the chapter suggests a TPOT of around 120 ms (6 to 8 tokens per second) is sufficient for most streaming use cases. Variants are called time between tokens or inter-token latency.
  • Total latency = TTFT + TPOT x (number of output tokens). The chapter's own formula.

Two apps can have the same total latency but feel different. Would your users prefer an instant start and slower tokens, or a slightly longer wait followed by fast output? The chapter says that needs user studies. You can also trade TTFT against TPOT by shifting compute between prefill and decode.

What the user sees isn't what the model sees. With chain-of-thought or agentic flows, the model may generate a hidden plan and tool outputs before the visible answer. From the model's side the first token appears at step 1; from the user's side it's much later. Some teams call the user-side measure time to publish.

Use percentiles, not averages. The chapter's example: ten TTFT values of 100, 102, 100, 100, 99, 104, 110, 90, 3,000 and 95 ms average to 390 ms, which makes the service look slow when nine of ten requests were fast. Percentiles tell you about specific fractions of requests: p50 (the median) is the typical case; p90, p95 and p99 reveal the tail, which may point to a network error or an unusually long prompt. Plotting TTFT against input length is also useful. I checked that arithmetic in code: mean 390, median 100.

Throughput, cost and goodput

Throughput is the number of output tokens per second an inference service can produce across all users and requests. Count input and output tokens separately, since prefill and decode have different bottlenecks; unqualified "throughput" usually means output tokens. It's often written tokens per second (TPS), or per user. You can also count completed requests per second (RPS) or per minute (RPM), which helps you see how the service copes with concurrent requests (some providers throttle heavy concurrency).

Throughput ties directly to compute cost. The chapter's worked example: a system costing $2 per hour at 100 tokens/s costs around $5.556 per million output tokens; with 200 output tokens per request, decoding 1,000 requests costs about $1.11. If the same hardware can prefill 100 requests per minute, prefilling 1,000 requests costs about $0.33. Total about $1.44 per 1,000 requests. I reproduced all of these in code. Caveat: these are the chapter's toy prices to teach the arithmetic, not real quotes. Direct throughput comparisons between systems can also mislead, since different tokenizers split text into different numbers of tokens; cost per request is a fairer yardstick.

The classic tension: batching and similar techniques can raise throughput but hurt latency. The chapter quotes a LinkedIn team's reflection that it's not uncommon to double or triple throughput if you accept worse TTFT and TPOT. So optimizing only for cost can ruin the user experience. That's why some teams track goodput, the number of requests per second that meet the SLO. If your SLO is TTFT at most 200 ms and TPOT at most 100 ms and the service completes 100 requests a minute but only 30 meet both, goodput is 30 per minute.

Utilization: GPU utilization, MFU and MBU

Beware "GPU utilization". The number reported by NVIDIA's nvidia-smi tool is the percentage of time the GPU is actively processing, not how much of its capacity is used. A GPU able to do 100 operations a second that does one operation per second can still show 100% utilization. If you pay for 100 and use 1, you're wasting money, but this metric won't tell you.

MFU (Model FLOP/s Utilization) is the observed throughput (tokens/s) as a fraction of the theoretical maximum at the chip's peak FLOP/s. If the chip could in theory generate 100 tokens/s but your service gets 20, MFU is 20%.

MBU (Model Bandwidth Utilization) is the fraction of achievable memory bandwidth you use. The bandwidth an LLM uses is parameter count x bytes per parameter x tokens/s; divide by the chip's theoretical bandwidth to get MBU. The chapter's example is a 7B model in FP16 (2 bytes per parameter) doing 100 tokens/s on an A100-80GB with 2 TB/s bandwidth. A discrepancy to flag: the chapter prints the bandwidth used as 700 GB/s, but 7 billion x 2 bytes x 100 = 1,400 GB/s, and only 1,400 GB/s divided by 2,000 GB/s gives the 70% MBU the chapter states. (700 GB/s would give 35%.) I recomputed it in code, so treat 1,400 GB/s and 70% as the consistent pair. The takeaway holds either way: fewer bytes per parameter (quantization) means less bandwidth consumed.

What counts as good depends on model, hardware and workload. Compute-bound workloads tend to show higher MFU and lower MBU; bandwidth-bound ones the opposite. Training usually achieves higher MFU than inference because its workloads are more predictable, and during inference prefill typically has higher MFU than decode. For training, the chapter says an MFU above 50% is generally considered good, though hard to hit on some hardware, and shows reported MFUs for large models from the PaLM paper between about 21% and 46%. It also notes MBU tends to fall as concurrent users increase, likely because the workload shifts from bandwidth-bound to compute-bound. And one more caveat from the chapter: chasing the highest utilization isn't the goal; a higher utilization means nothing if cost and latency both go up.

AI accelerators: what the chips are

The history of AI and hardware are intertwined. The chapter points out that insufficient computing power contributed to the first AI winter in the 1970s, and that AlexNet (2012) was widely credited as the first big result to train neural networks on GPUs, instead of thousands of CPUs, setting off the deep learning boom.

An accelerator is a chip designed for a particular type of work; an AI accelerator targets AI workloads. GPUs dominate. The chapter contrasts them: CPUs have a few powerful cores (up to about 64 on high-end consumer machines), good at sequential, general work like running an operating system; GPUs have thousands of smaller cores for many small independent calculations. Most ML work is matrix multiplication, which parallelizes well (the chapter cites estimates that matrix multiplication accounts for more than 90% of floating-point operations in a neural network). Parallelism, though, pushes on memory design and power.

Others in the field: AMD GPUs, Google's TPUs, Intel's Habana Gaudi, Graphcore's IPU, Groq's LPU, Cerebras' chips and more. A theme: specialized inference chips. The chapter cites a survey that says inference can exceed training cost in commonly used systems and may account for up to 90% of ML costs for deployed AI systems. Training needs more memory (backpropagation) and is harder in low precision; inference chips often favor lower precision and fast memory access over large memory capacity. Examples named: Apple Neural Engine, AWS Inferentia, Meta's MTIA, and edge chips like Google's Edge TPU and NVIDIA Jetson Xavier.

Different chips also have different compute primitives (scalar, vector, tensor). GPUs traditionally did vector operations and now often include tensor cores; TPUs are built around tensor operations. To run a model well, you must account for the chip's memory layout and compute units.

Three headline characteristics matter across use cases:

  1. Computational capability, usually peak FLOP/s. In practice you rarely reach the peak (the ratio is the utilization above). The higher the numerical precision, the fewer operations per second: the chapter's table for the NVIDIA H100 SXM lists roughly 989 teraFLOP/s for TF32, 1,979 for BF16 and FP16, and 3,958 for FP8 (with sparsity), so halving the bits roughly doubles the peak. Those are vendor-reported peak figures from the chapter; check current datasheets.
  2. Memory size and bandwidth. A GPU interacts with three memory levels: CPU memory (DRAM; the lowest bandwidth, around 25 to 50 GB/s in the chapter; laptops 16 to 64 GB); GPU high-bandwidth memory (HBM; roughly 256 GB/s to over 1.5 TB/s and around 24 to 80 GB for the chip the chapter describes); and on-chip SRAM (caches; very fast, often over 10 TB/s, but small, typically 40 MB or under). Much of GPU optimization is using this hierarchy well, and since PyTorch and TensorFlow don't give fine control over memory access, interest has grown in GPU languages such as CUDA, Triton and ROCm. The figures are reference numbers the chapter says vary by chip.
  3. Power consumption. Billions of transistors switching generate heat, which needs cooling that uses more electricity. The chapter's figures: an H100 running at peak for a year consumes about 7,000 kWh, versus about 10,000 kWh for an average US household's annual electricity use. Specs list maximum power draw or TDP; maximum draw can be roughly 1.1 to 1.5 times TDP. If you use a cloud provider you don't handle cooling or electricity directly.

Choosing an accelerator

The chapter's selection test is three questions: can the hardware run your workload at all, how long will it take, and how much does it cost? FLOP/s, memory size and memory bandwidth answer the first two. For compute-bound workloads, look for more FLOP/s; for bandwidth-bound ones, spend on bandwidth and memory. Cloud pricing is usage-based and, per the chapter, fairly similar across providers; for hardware you buy, add the initial price and ongoing power.

Why it matters

When an AI feature feels slow or the bill climbs, these are the questions you'll ask: is the first token slow (prefill, long prompts), or are tokens trickling out (decode)? Are averages hiding a bad tail? Are we using what we pay for? And when you compare a provider's claims, you now know to look at percentiles, goodput and cost per request rather than a single throughput number.

Remember this

  • Optimization starts by finding the bottleneck: compute-bound (arithmetic) or memory bandwidth-bound (data movement). For LLMs, prefill is typically compute-bound and decode typically bandwidth-bound.
  • Latency = TTFT + TPOT x output tokens. Judge latency with percentiles, since averages hide outliers.
  • Throughput links to cost, but chasing it alone can hurt latency; goodput counts only requests that meet your SLO.
  • nvidia-smi "GPU utilization" measures busy time, not efficiency; MFU and MBU measure how much of the chip's compute or bandwidth you actually use.
  • Chips differ in FLOP/s, memory size and bandwidth, and power; pick based on which your workload is limited by.

Try it yourself

Done when you can explain which number you'd put on a dashboard and why. Reproduce the chapter's ten-value example (mean 390 ms, median 100 ms) as a test. (I ran this and got those numbers.)
  2. Cost calculator. Given hourly hardware cost, decode tokens per second, average output tokens per request and prefill requests per minute, compute cost per 1,000 requests. Done when the chapter's inputs ($2/h, 100 tokens/s, 200 output tokens, 100 prefills/minute) give about $1.44 per 1,000 requests (it did when I ran it). Then vary throughput and see how cost moves.
  3. MBU calculator. Write mbu(params, bytes_per_param, tokens_per_s, peak_bandwidth). Done when 7B, 2 bytes, 100 tokens/s and 2 TB/s gives 0.70, and halving the bytes per parameter (as with 8-bit weights) halves the bandwidth used. Note the page's 700 vs. 1,400 GB/s discrepancy in your own comments. 
    def mbu(params, bytes_per_param, tokens_per_s, peak_bw_bytes_per_s):
    used = params * bytes_per_param * tokens_per_s
    return used / peak_bw_bytes_per_s

print(mbu(7e9, 2, 100, 2e12))   # 0.7
  4. Goodput counter. Create 50 fake requests with random TTFT and TPOT values and compute throughput versus goodput for an SLO of your choosing (the chapter's is TTFT at most 200 ms, TPOT at most 100 ms). Done when you can show a case where throughput looks fine but goodput is low, and adjust one threshold to see how sensitive it is. Synthetic data only.
  5. Streaming timer. If you have access to any model API with streaming, time how long the first chunk takes and how long each later chunk takes for a short and a long prompt. Done when you've estimated TTFT and TPOT for each and checked total latency against TTFT + TPOT x tokens. (If you have no API access, simulate a stream with time.sleep and the same timing code. That tests your timer, not a real model.)
  6. Spec-sheet reading. Pick two published accelerator spec pages and write down peak FLOP/s at two precisions, memory size, memory bandwidth and power. Compute each chip's FLOP-per-byte ratio and say which kind of workload it's better suited to. Done when you've marked which numbers are vendor peaks that you'd never reach in practice.
