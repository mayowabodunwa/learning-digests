S3 Replication: CRR, SRR, Replication Time Control and Batch Replication

Replication is S3 copying your objects to another bucket for you, automatically and after the fact. It sounds simple, but the details (what gets copied, what doesn't, why deletes behave strangely, and what "existing objects" means) are where people get caught. This digest builds the model one piece at a time.

In one line

S3 Replication automatically and asynchronously copies new and updated objects from a source bucket to one or more destination buckets (in the same Region with SRR, or another Region with CRR), Replication Time Control adds a time-bound target and monitoring, and Batch Replication handles objects that live replication skips.

The big idea

S3 already stores each object across multiple Availability Zones inside a Region, so replication isn't about basic durability. The docs give other reasons: keep copies in a distant Region for compliance, put data nearer to users, aggregate logs into one bucket, keep production and test accounts in sync, keep copies under a different owner, or put replicas into a colder storage class.

Two ideas drive everything below. First, live replication is a rule engine attached to the source bucket: it only looks forward, copying objects written after the rule exists. Second, replication has many "by default" behaviours that surprise people (delete handling, replicas of replicas, archived objects). Each one has a switch or a workaround, which I'll point to.

Simplification label: I describe the S3 side. Replication also has an IAM permissions setup (a role S3 assumes), plus extras like replica modification sync, multi-destination rules and multi-Region access points that I only mention. No prices are quoted; the docs say inter-Region transfer charges vary by Region pair.

Key terms

  • Replication: automatic, asynchronous copying of objects between S3 buckets, which can belong to the same or different accounts.
  • Live replication: replication of new and updated objects as they are written. Doesn't replicate objects that existed before the rule.
  • CRR (Cross-Region Replication): live replication to a bucket in a different AWS Region.
  • SRR (Same-Region Replication): live replication to a bucket in the same Region.
  • On-demand replication / Batch Replication: a job you run to replicate existing objects, failed objects, or replicas.
  • Replication configuration: the bucket-level document containing an IAM role and up to 1,000 rules.
  • Replication rule: status, priority, optional filter, delete-marker setting, destination.
  • Replica: the copy in the destination bucket.
  • Replication status: a per-object label (for example FAILED, COMPLETED, REPLICA) used in tracking and Batch Replication filters.
  • S3 RTC (Replication Time Control): an add-on to a rule giving a 15-minute replication target backed by an SLA, plus metrics and events.
  • Owner override: an option to make the destination bucket owner the owner of replicas.
  • Manifest: the list of objects a Batch Replication job acts on.

How it works

0. Grounding: the shape of a replication setup

Requirements from the docs, in plain words:

  • Both source and destination buckets must have versioning enabled (this is why last week's versioning digest comes first).
  • S3 needs permission to copy for you, via an IAM role named in the replication configuration. S3 can't replicate without it.
  • The relevant Regions must be enabled for the account(s) involved.
  • If the source bucket has Object Lock enabled, destination buckets must too.
  • Cross-account: the destination bucket owner must grant the source owner permission to replicate via a bucket policy, and the destination can't be a Requester Pays bucket.

Side effects of that versioning requirement: you can't disable versioning on the source bucket until you remove the replication configuration, and if you disable versioning on the destination, replication fails and objects get status FAILED.

1. Live replication: rules and filters

A replication configuration names an IAM role and one or more rules (up to 1,000 per source bucket, and the docs say that limit isn't adjustable). Each rule in the current (V2) format has:

  • Status: Enabled or Disabled.
  • Priority: which rule wins if two rules with the same destination bucket overlap; higher number wins.
  • Filter: optional; by key prefix, by tags, or both (combined with AND). An empty filter means all objects. Using a Filter means the rule also needs Priority and DeleteMarkerReplication.
  • DeleteMarkerReplication: whether to copy delete markers.
  • Destination: the destination bucket, and options such as storage class, owner override, RTC, KMS key.

You can send objects to several destination buckets, in different Regions if you like, and by default replicas use the source object's storage class unless you specify one (so you can land directly in a Glacier class, or replicate as-is and let a lifecycle rule on the destination move them later).

A minimal CLI-style configuration, shaped from the docs' RTC example (placeholders in braces, RTC pieces trimmed):

{
  "Role": "{IAM-role-ARN}",
  "Rules": [{
    "Status": "Enabled",
    "Priority": 1,
    "Filter": {"Prefix": "tax/"},
    "DeleteMarkerReplication": {"Status": "Disabled"},
    "Destination": {"Bucket": "arn:aws:s3:::{destination-bucket}"}
  }]
}

Note the docs' caveat on tag filters: with live replication, an object is replicated under a tag-based rule only if it carries the matching tag in the PutObject request itself. Tagging it afterwards doesn't trigger replication (Batch Replication can pick those up).

2. What is and isn't copied (the surprises)

Replicated by default (per the docs): objects created after the configuration was added; unencrypted objects and objects encrypted with SSE-S3 or SSE-C; metadata; tags; Object Lock retention information; and object ACL updates (unless ownership is changed). Objects encrypted with SSE-KMS aren't replicated unless you opt in with SourceSelectionCriteria and give a KMS key for the destination Region.

Not replicated by default:

  • Replicas of replicas. If A replicates to B and B replicates to C, objects in B that came from A don't flow on to C (Batch Replication can do it).
  • Previously replicated objects. Changing the destination in a rule doesn't re-copy old objects.
  • Objects in Glacier Flexible Retrieval, Glacier Deep Archive, and the Intelligent-Tiering Archive tiers. Restore them and copy first.
  • Bucket-level configuration changes such as lifecycle or notification settings.
  • Lifecycle actions. If lifecycle expires an object on the source, the resulting delete marker isn't replicated; configure the same lifecycle on both buckets if you want parity.
  • Objects the bucket owner can't read (permission gaps with cross-account object owners).

3. Deletes: a deliberate asymmetry

This is the part to read twice. With the current rule format (one with a Filter):

  • A simple delete (no version ID) creates a delete marker on the source. By default that marker is not replicated. You can enable delete marker replication on non-tag-based rules.
  • A delete with a version ID permanently deletes that version on the source, but isn't replicated. The docs say this protects data from malicious deletions.

The older (V1) format, which has no Filter, does replicate delete markers resulting from user actions (but not those created by lifecycle expiry). Also, by default, delete markers from a different source account aren't replicated.

4. Ownership and encryption on the way across

  • Ownership. Replicas stay owned by the source object's owner unless you add owner override (AccessControlTranslation with owner Destination), which hands ownership to the destination bucket's account. The docs also note that with ACLs disabled (Bucket owner enforced) on the destination, replicas end up owned by the destination bucket owner.
  • Encryption. SSE-KMS objects need an explicit opt-in plus a KMS key for the destination Region, and KMS request-rate quotas then apply to replication traffic too.

5. Replication Time Control (RTC)

Plain live replication has no time guarantee. The docs' workload table says same-Region or cross-Region replication without RTC is not SLA-backed and gives "24-48 hours (not SLA backed)" as the contrast case, while RTC gives a predictable time. RTC is an option on a rule:

  • The target: the docs say RTC replicates most objects in seconds and a high percentage within 15 minutes, backed by a service-level agreement. Flag: different docs pages state that percentage as 99.9 percent and as 99.99 percent. Check the live RTC page before relying on a number.
  • Enabling it turns on replication metrics (pending operations, pending bytes, maximum replication time, failed operations) published to CloudWatch, billed like CloudWatch custom metrics.
  • Event notifications OperationMissedThreshold and OperationReplicatedAfterThreshold tell you when an object misses the 15-minute threshold or replicates after it.
  • The only accepted value for the time and event threshold is 15 minutes.
  • The SLA doesn't apply when you exceed S3's request-rate guidelines or the default 1 Gbps replication transfer-rate quota (which you can ask to raise).
  • Batch Replication isn't covered by RTC.

The CLI-shaped rule fragment from the docs:

"Destination": {
  "Bucket": "arn:aws:s3:::{destination-bucket}",
  "Metrics": {"Status": "Enabled", "EventThreshold": {"Minutes": 15}},
  "ReplicationTime": {"Status": "Enabled", "Time": {"Minutes": 15}}
}

6. Batch Replication: everything live replication skips

Batch Replication is an on-demand job built on S3 Batch Operations. The docs list four uses:

  • Replicate objects that existed before the rule.
  • Retry objects whose status is FAILED.
  • Replicate objects already replicated elsewhere to a newly added destination.
  • Replicate replicas (the A to B to C case).

How it works: your source bucket must already have a replication configuration; the job needs a manifest (S3 can generate one from your rule's bucket, prefix and tags, stored in the source's Region, or you supply an S3 Inventory report or CSV, with version IDs for versioned buckets); and an IAM role. You can filter by ObjectReplicationStatuses (NONE, FAILED, COMPLETED, REPLICA) and by creation date. A completion report is available. Caveats from the docs: not supported for Glacier Flexible Retrieval or Deep Archive objects; a single job's manifest can hold up to 20 billion objects; it doesn't re-replicate objects deleted at the destination by version ID (use a Batch Copy in place instead); and the docs recommend disabling lifecycle rules while a job runs, because a delete marker may replicate before the versions it hides.

7. Other behaviour worth knowing

  • Replication takes as long as creating the original did; large objects can take hours. Lifecycle on the destination honours the object's original creation time, not when the replica landed.
  • Multipart uploads replicate as multipart; unfinished uploads can linger on the destination, so the docs recommend an AbortIncompleteMultipartUpload lifecycle rule there.
  • Replicating or copying Intelligent-Tiering objects with Batch Replication counts as access (it tiers them up).
  • Data-transfer charges apply to CRR depending on Region pair; the docs say there are none for SRR. I don't quote rates.
  • Two-way replication (with replica modification sync) is the docs' pattern for keeping buckets in sync across Regions, for example before Multi-Region Access Point failover; I only mention it here.

Why it matters

Teams often treat replication as "a backup" and then get surprised: a bad overwrite replicates, an old object never arrived, a lifecycle delete didn't propagate. Knowing it's an asynchronous, forward-looking copy with specific rules lets you use it for what it does well (compliance copies, latency, log aggregation, cross-account separation) and pair it with versioning and Object Lock where you need real protection. The next concepts, event notifications and multipart uploads, also interact with replication through failure events and incomplete uploads.

Remember this

  • Live replication (CRR or SRR) is asynchronous and forward-looking; it needs versioning on both buckets and an IAM role S3 can assume.
  • By default it doesn't copy pre-existing objects, replicas of replicas, archived-class objects, lifecycle-driven deletes, or version-ID deletes.
  • Delete markers aren't replicated by default under the current rule format; permanent version deletes never are.
  • RTC adds a 15-minute SLA-backed target plus metrics and missed-threshold events; confirm the exact percentage on the live page.
  • Batch Replication is the on-demand tool for existing, failed, re-destination and replica objects, driven by a manifest.

  2. What-wasn't-copied checklist (offline, 30 min). From the docs' "isn't replicated" list, write a test case for each item and the workaround. Done when each row cites the docs section.
  3. Set up SRR. Create two versioned buckets in one Region, follow the docs' same-account walkthrough to create the role and a rule, upload a file, and check it with aws s3api head-object on both sides. Done when the source shows ReplicationStatus and the destination shows REPLICA.
  4. Prove the delete asymmetry. Using the setup from project 3 with delete marker replication disabled, run a simple delete on the source and compare the two buckets with aws s3api list-object-versions. Done when you see a marker on the source only.
  5. Backfill with Batch Replication. Upload a file before creating a second rule's replication, confirm it doesn't appear on the destination, then create a Batch Replication job (console is easiest) with ObjectReplicationStatuses = NONE.
