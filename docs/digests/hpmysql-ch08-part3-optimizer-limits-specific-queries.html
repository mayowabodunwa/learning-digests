SQL · CH.8 DIGEST (PART 3, FINAL)

Where the Optimizer Struggles, and How to Rewrite COUNT, Pagination and UNION Queries

Parts 1 and 2 explained how MySQL runs a query. This last part is the practical payoff: the handful of places the optimizer does a poor job, and a toolkit of rewrites for the query shapes that cause the most trouble in real applications (counting, joining, grouping, paginating and combining results). It ends with the chapter's own three-move summary.

In one line

When MySQL's optimizer won't do something for you, you do it yourself by rewriting the query (pushing a limit inside a UNION, counting the right way, paginating from a position instead of an offset), and for most of these tricks the cost you remove is rows generated only to be thrown away.

The big idea

The source says the optimizer fails on only a limited number of query shapes, and those can usually be rewritten. The pattern behind most rewrites in this part is the same one from Part 1: stop making the server produce rows nobody needs. Counting every row to show a page number, skipping ten thousand rows to reach page 501, and building a giant union only to keep twenty rows are all examples.

One honest warning comes from the source itself: most of the advice in "Optimizing Specific Types of Queries" depends on the MySQL version and may not hold in future ones, since the server could learn to do some of these things on its own. I tested several of these on MySQL 8.0.46 and, where the behaviour differs from the book's description, I say so below.

This part covers printed pages 219 to 226: "Limitations of the MySQL Query Optimizer" (UNION limits, equality propagation, parallel execution, SELECT and UPDATE on the same table), "Optimizing Specific Types of Queries" (COUNT, JOIN, GROUP BY with ROLLUP, LIMIT and OFFSET, SQL_CALC_FOUND_ROWS, UNION), and the chapter "Summary."

Key terms

  • Push down: copying a condition (a LIMIT, WHERE or ORDER BY) from an outer query into the inner parts so they can use it early.
  • UNION / UNION ALL: combine the results of several SELECTs. UNION removes duplicate rows; UNION ALL keeps everything.
  • Temporary table: a scratch table the server builds mid-query to hold intermediate results.
  • Derived table: a subquery in the FROM clause, treated as a table. Example: FROM (SELECT ...) AS x.
  • Materialize: fill a temporary table with a subquery's result.
  • NULL: SQL's marker for "no value." It is not the same as zero or empty text.
  • Aggregate function: a function summarizing many rows (COUNT, SUM, MIN, MAX).
  • WITH ROLLUP: a GROUP BY option that adds extra "super-aggregate" rows (subtotals and a grand total).
  • Pagination: splitting a long list into pages. OFFSET says how many rows to skip first.
  • Deferred join: do the offset/limit on a small covering index first, then join back to the table to fetch the wide columns for just those rows.
  • Keyset ("cursor") pagination: remember the last key you showed and continue from it, rather than skipping rows. The source describes this as a cursor-like position.

How it works

Grounding: the optimizer's job is hard, and it takes shortcuts. Each shortcut that leaves a gap in what it can do gives you a recognizable "bad shape" of query. This part names those shapes, then gives remedies for the query types where beginners most often hurt themselves. You won't memorize all of it; the goal is to recognize the smell ("this generates a lot and throws most away") and know the family of fixes.

1. Limitations of the optimizer

UNION: conditions don't get pushed in

The source says MySQL sometimes can't push a condition from outside a UNION into the individual queries inside it. Its example: union two tables, each with an ORDER BY, and apply LIMIT 20 to the whole thing. MySQL stores both whole tables into a temporary table and then picks 20 rows. The fix: repeat the LIMIT 20 inside each part, so the temporary table holds at most 40 rows. Then, because the order in which rows come out of the temporary table is undefined, add a final outer ORDER BY before the last LIMIT if the result order matters.

I tried this on my small tables (customer with 2,000 rows, product with 300). Without inner limits, EXPLAIN estimated reading all 2,000 customer rows and all 300 product rows. With LIMIT 20 inside each part, the product part dropped to an estimated 20 rows. The customer part still showed 2,000 estimated rows with Using filesort because I had no index on name there; with an index it would not have to sort and read everything. One more version note: in 8.0 the inner ORDER BY without an inner LIMIT didn't show a filesort at all, which looks like the server discarding a pointless inner sort. I'm inferring that from the plan, not from documentation.

Equality propagation can cost you

Back in Part 2, equality propagation was a good thing. The source points out an edge case: a huge IN() list on a column that the optimizer knows equals columns in other tables gets copied to each of those columns. Normally helpful, but with a very large list it can slow both optimization and execution, and the source says there is no built-in workaround at the time of writing (you would have to change the source code) and that it isn't a problem for most people. I did not test this.

No parallel execution of a single query

Per the source, MySQL can't run one query in parallel across many CPUs, unlike some other databases, so don't waste time trying to configure it. (Many connections still run in parallel; the limit is about splitting a single statement. I haven't verified this against newer manuals, so check yours if it matters; the book says it as of its writing.)

SELECT and UPDATE on the same table

This one is a classic. You can't, in one statement, read from a table in a subquery while also updating that table. The source's example updates each row with the count of "similar" rows from the same table. MySQL raises error 1093. I reproduced it: with a table t(id, type, c), an UPDATE t AS o SET c = (SELECT COUNT(*) FROM t AS i WHERE i.type = o.type) failed with "You can't specify target table 'o' for update in FROM clause."

The workaround uses a derived table, which MySQL materializes into a temporary table first, so the table is opened and closed by the subquery before the outer update opens it. In effect it runs two statements: one grouped SELECT, then a multi-table UPDATE that joins the table with that result. I ran the rewritten form and it worked: rows with type 1 got count 2 and the row with type 2 got count 1. (The source calls this not strictly an optimizer limitation, but knowing how execution works helps you see the way around it.)

2. Optimizing specific kinds of queries

COUNT(): what it really counts

The source calls COUNT() one of the most misunderstood topics in MySQL. It works in two modes:

  • COUNT(expression) counts how many times the expression has a value, meaning is not NULL.
  • COUNT(*) counts rows. The star isn't expanded into the columns; it just means "count rows." MySQL also does this when it knows the expression can never be NULL.

The common mistake: writing a column name when you want a row count. The source says use COUNT(*) when you want rows, since it states your intent and avoids poor performance. To make the NULL point concrete, I made a 4-row table with a nullable column holding blue, red, NULL, blue:

  • COUNT(*) gave 4 (rows); COUNT(color) gave 3 (non-NULL values); COUNT(DISTINCT color) gave 2.

Counting several categories in one pass

A common question: how do I get "how many blue" and "how many red" in one query? An OR in COUNT won't separate them, and a WHERE with both colors returns nothing because no row is two colors at once. The source gives two equivalent patterns: SUM(IF(color = 'blue', 1, 0)), and COUNT(color = 'blue' OR NULL), which works because a false condition turns into NULL and is not counted. Another form is SUM(color = 'blue') (the source's footnote). On my four-row table the COUNT(... OR NULL) pattern gave blue = 2 and red = 1, and SUM(color='blue') gave 2. I also tried the tempting wrong one, COUNT(color = 'blue') without the OR NULL: it returned 3, because the comparison yields a value (0 or 1) for every non-NULL row and each counts. That's a handy trap to know about.

Approximate when you can

If you don't need an exact number, you have cheaper options. The optimizer's estimated rows in EXPLAIN often work: run EXPLAIN instead of the real query. On my 60,000-row table, EXPLAIN estimated about 60,345 rows for a full count (the true number was 60,000). The source also tells a story of a site counting active users, cached for 30 minutes and thus approximate by nature; dropping some extra WHERE conditions and an unnecessary DISTINCT (which removed a filesort) changed the count slightly but made the query far faster. And when exact counts are unavoidable, the source's options are a covering index, or changing the architecture, for example an external cache such as memcached, and it summarizes the dilemma as "fast, accurate, simple: pick any two."

One related observation of mine: a plain SELECT COUNT(*) FROM orders showed type: index, key: idx_cust, Using index, so MySQL counted using the smaller secondary index instead of the whole table. That's an observation on my build, not a promise.

JOIN queries: a few highlights

  • Index the join columns, in light of the join order. The source says that if the optimizer will join B before A, you don't need an index on B's join column; usually you only need indexes on the second table in the join order, unless they're needed for another reason. Unused indexes are overhead.
  • Make GROUP BY and ORDER BY refer to columns from one table, so MySQL can try to use an index for it (this ties directly to the filesort rule from Part 2).
  • Be careful upgrading MySQL. Join syntax, operator precedence and other behaviours have changed over time, so something that used to be an ordinary join can turn into a cross product, return different results, or become invalid syntax.

GROUP BY with ROLLUP

WITH ROLLUP adds super-aggregate rows (subtotals and a grand total) to a grouped result. The source warns it may not be well optimized: check the plan, watch whether grouping happens via filesort or a temporary table, and try removing WITH ROLLUP to see if the grouping method changes. Sometimes it is more efficient to do the super-aggregation in your application, even if that means fetching more rows, or use a derived table or temporary table with a UNION. The source's bottom line is that moving the rollup into your application code might be best.

I saw exactly the "method changes" effect. For SELECT status, COUNT(*) FROM orders GROUP BY status, the plan said Using temporary; adding WITH ROLLUP changed it to Using filesort. Both scanned the full table (estimated 60,345 rows). That's one version, one table, one dataset.

LIMIT and OFFSET: the cost hides in the offset

Pagination is almost always ORDER BY plus LIMIT/OFFSET. Without an index supporting the order, you pay for filesorts. The bigger issue is a large offset: LIMIT 10000, 20 generates 10,020 rows and discards the first 10,000. The source adds that if pages are viewed equally often, such queries scan half the table on average. Options: limit how deep users can page, or make deep pages cheaper.

Technique 1: the deferred join. Do the offset on a covering index, then join the few resulting ids back to the table for the wide columns. In my test on 60,000 orders: with a plain SELECT id, total FROM orders ORDER BY placed LIMIT 50000, 5 the plan was a full table scan type: ALL with Using filesort (the optimizer decided not to walk the placed index and then fetch rows). Written as a join against (SELECT id FROM orders ORDER BY placed LIMIT 50000, 5), the inner part used the placed index with Using index, and each of the five ids was then fetched by primary key (eq_ref). I did not time these; at 60,000 rows the difference would be too small to measure meaningfully, so I only compared the plans. The source says this works because the server examines as little data as possible in the index before fetching full rows.

Technique 2: positions. Precompute and index a position column, then use a range scan (WHERE position BETWEEN 50 AND 54). For ranked data, expect to precompute and store the ranks.

Technique 3: remember where you were (keyset pagination). The source's insight is that the problem is really the offset. If primary keys increase, fetch the first page with ORDER BY rental_id DESC LIMIT 20, then continue with WHERE rental_id < (last id you saw). It is efficient no matter how deep you go. I tried the same shape on my table: WHERE id < 40000 ORDER BY id DESC LIMIT 20 used a range scan on the primary key with Backward index scan. The estimated row count displayed (30,172) is just the optimizer's range estimate; with the LIMIT the server can stop after 20. Caveat: this approach fits "next/previous" navigation and an ordering with a unique, increasing key. It doesn't support jumping straight to "page 37" unless you also keep other state.

The source also mentions alternatives: precomputed summaries, or joining against redundant tables that hold only the primary key and the ORDER BY columns.

SQL_CALC_FOUND_ROWS: no magic

Many pagers add SQL_CALC_FOUND_ROWS to a LIMIT query to learn how many rows there would have been. There is no prediction involved: the server just keeps generating and discarding the rest of the result instead of stopping, which is very expensive. Better designs, per the source:

  • Switch the pager to a "Next" link: with 20 per page, ask for 21 rows (LIMIT 21), show 20, and if the 21st exists, render "Next."
  • Fetch and cache a larger batch (say 1,000 rows) and serve pages from the cache; you then know whether there are fewer than 1,000 results or "more than 1,000."
  • Estimate the total with EXPLAIN rows.
  • Use a separate COUNT(*) query, which can be much faster than SQL_CALC_FOUND_ROWS if it can use a covering index.

A version note I found: on 8.0.46, using SQL_CALC_FOUND_ROWS produced a warning (code 1287) that it is deprecated and will be removed in a future release, suggesting two separate queries instead. FOUND_ROWS() still returned the right total (60,000) in my test. The book doesn't mention the deprecation, so if you're on a recent 8.x version, prefer the separate-query approach.

UNION: help it, and use ALL

The source says MySQL always runs UNION by building a temporary table and filling it, so you may need to push WHERE, LIMIT and ORDER BY into each part by hand (as in the earlier example). It also says to always use UNION ALL unless you need duplicates removed: without ALL, the temporary table gets a distinct option that uses the whole row to decide uniqueness, which is expensive. And ALL doesn't remove the temporary table; the source says MySQL still places results in one and reads them out, even when it could return rows directly.

My EXPLAIN comparison: plain UNION had an extra row of type UNION RESULT with Using temporary; the UNION ALL plans I ran had no such row. I can't tell from EXPLAIN alone whether 8.0 avoids the temporary table for UNION ALL internally, so I'm not contradicting the book, only noting that the plan output looks different from what its text would suggest. The cost advice (UNION ALL unless you need to dedupe) stands on its own because dedupe is extra work.

3. The chapter's summary: three moves

The source closes with its core claim: query optimization is the last piece of an interlocking puzzle with schema design and indexing, you need to understand each to do the others well, and in the end it is still about response time. Its final line sums up the whole chapter: stop doing things, do them fewer times, and do them more quickly. Notice that every rewrite in this part is one of those three: drop the unneeded SQL_CALC_FOUND_ROWS (stop), push the limit into the union (fewer rows), use a covering index in a deferred join (faster).

Why it matters

Pagination, counts and unions are in nearly every application, and they're where "it was fast in testing" turns into "the site is crawling" once the table grows. Deep offsets and exact counts both get slower as data grows, because the work is proportional to rows skipped or counted. Knowing the rewrites, and why they work, means you can fix those paths without guessing. The deeper habit is the same through all three parts of this chapter: look at what the server is generating, compare it to what you need, and shrink the gap.

It also closes the loop on the three chapters in this track: schema (Ch.6) decides what's possible, indexes (Ch.7) decide what's cheap, and query shape (Ch.8) decides whether MySQL gets to use either.

Remember this

  • The optimizer fails in a limited number of known shapes; the usual fix is a rewrite that stops it generating throwaway rows.
  • Push LIMIT (and ORDER BY) into each part of a UNION, and use UNION ALL unless you need dedupe.
  • COUNT(*) counts rows; COUNT(column) counts non-NULL values.
  • The cost of deep pagination is the offset; defer the join, store positions, or continue from the last key.
  • SQL_CALC_FOUND_ROWS isn't magic and is deprecated in recent 8.x; use "Next" links, a cache, an estimate, or a separate count.
  • Advice in this section is version dependent; test on your version.

Try it yourself

  1. Count autopsy. Make a table with a nullable column and a few NULLs. Write the queries for COUNT(*), COUNT(col), COUNT(DISTINCT col), and a one-pass "how many of each category" query using both the SUM(IF(...)) and COUNT(... OR NULL) patterns. Done when you can predict each result before running it, including the wrong COUNT(col = 'x') trap.
  2. Pagination showdown. Load 500,000 rows. Time page 1, page 500 and page 20,000 using plain OFFSET, a deferred join, and keyset pagination (run each at least three times). Chart the timings. Done when you can explain the curves, and say what keyset can't do that offset can.
  3. Next-link pager. Build a tiny paging function that requests LIMIT page_size + 1 and returns the rows plus a "has next page" flag. Done when it works on exactly-full, partially-full and empty pages.
  4. Union pushdown. Union two tables with ORDER BY ... LIMIT 20 on the outside only, then with the limit repeated inside each part plus an outer ORDER BY. Compare EXPLAIN rows and the real timing, and check both give the same final 20 rows. Done when you can say why the outer ORDER BY is still needed.
  5. The self-update puzzle. Reproduce error 1093 on a table of your own, then fix it with the derived-table join. Done when the update works and you can say in your own words why the derived table helps.
  6. Rollup in the app. Run a GROUP BY ... WITH ROLLUP query and look at its plan; then write the same totals by running the plain grouped query and summing in code (any language). Done when the two outputs match and you've compared plans and timing.

Go deeper (optional)

Take one real list screen in an application you know and trace its three costs: the page query, the count, and any join behind it. Decide for each whether the source's three moves (stop, fewer, faster) applies. This is the last chapter in this track's focused scope.
