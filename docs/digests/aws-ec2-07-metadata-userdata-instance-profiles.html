Instance Metadata (IMDSv2), User Data, Instance Profiles and IAM Roles

How does a freshly launched server know its own instance ID, run your setup script, and call AWS APIs without anyone pasting access keys onto it? Three linked features: the instance metadata service, user data, and IAM roles delivered through instance profiles. They also form one of the best-known security boundaries on EC2.

In one line

Every instance can ask a local, link-local address (169.254.169.254) about itself; it can be handed a launch-time script (user data); and it can receive temporary AWS credentials for an IAM role via an instance profile, with IMDSv2 as the safer, token-based way to read all of it.

The big idea

A virtual server needs three things at birth: knowledge about itself ("who am I, where am I?"), instructions ("what should I set up?"), and an identity AWS trusts ("what am I allowed to do?"). EC2 answers each with a mechanism that lives on the instance's own network interface, so no secrets need to travel through your code or your AMI.

They connect: user data scripts run on the instance, call the metadata service to learn their instance ID, and use role credentials from the same service to call other AWS services. That makes the metadata service a juicy target if something on the instance can be tricked into making web requests, which is why IMDSv2 exists.

This builds on earlier EC2 digests (AMIs, Auto Scaling launch templates, Systems Manager). I quote no prices; everything here is configuration.

Key terms

  • Instance metadata: data about a running instance (instance ID, AMI ID, type, network, placement, IAM info, and more), readable only from within the instance.
  • IMDS: the Instance Metadata Service, the local endpoint that serves it.
  • IMDSv1 / IMDSv2: the older request/response method, and the newer session-token method.
  • Session token: a short-lived, instance-specific key that IMDSv2 requires on requests.
  • User data: a blob of text you provide at launch (often a script) that the instance can read and act on.
  • cloud-init: the package on many Linux images that reads user data and does first-boot setup.
  • IAM role: a set of permissions that a trusted entity (here, an EC2 instance) can assume.
  • Instance profile: the container that passes a single IAM role to an EC2 instance.
  • Temporary credentials: an access key, secret key and session token that expire and are rotated automatically.
  • SSRF: server-side request forgery, tricking a server into making a request on an attacker's behalf. (A concept the docs reference via IMDSv2's design; defined here in my words.)
  • Hop limit: how many network hops the token response may travel (IP time-to-live).
  • Base64: a text encoding for binary-safe transfer; user data must be base64-encoded in transit.

How it works

0. Grounding: a phone line that only the instance can dial

The IMDS runs locally on every instance, at 169.254.169.254 (IPv4), plus an IPv6 endpoint [fd00:ec2::254] that is only supported on Nitro-based instances in IPv6-supported subnets, and which you must enable explicitly. The docs say you can access metadata and user data only from within the instance itself.

But the important caveat: the data is "not protected by authentication or cryptographic methods". Anyone with direct access to the instance, and potentially any software running on it, can read it. So the docs say not to store passwords or long-lived encryption keys in user data.

1. What's in instance metadata

The docs group metadata into categories. A sample from their table: ami-id, instance-id, instance-type, hostname, local-ipv4, public-ipv4, placement/availability-zone, placement/region, security-groups, mac, network details under network/interfaces/macs/..., iam/info and iam/security-credentials/<role-name> (only present if a role is attached), spot/instance-action (present only when a Spot Instance has been marked for interruption), and events/maintenance/.... Instance tags are available only if you explicitly allow access to tags in instance metadata. Dynamic data such as the instance identity document is generated at launch.

Use latest in the path instead of a dated version so code doesn't need updating when AWS releases new categories. On Nitro-based instances, you can only retrieve metadata categories that were available at launch; Xen instances can refresh them by stopping and starting.

2. IMDSv1 vs. IMDSv2

IMDSv1 is a plain request/response: a simple GET returns the answer. IMDSv2 is session-oriented:

  1. Send a PUT to /latest/api/token with a header X-aws-ec2-metadata-token-ttl-seconds (the docs' example uses 21600, i.e. six hours; the valid range is one second to six hours). The response is a token.
  2. Include that token in a header X-aws-ec2-metadata-token on every GET (or HEAD).

The token is instance-specific and is rejected on other instances. By default both versions are allowed; you can configure an instance to require IMDSv2, in which case requests without a valid token get 401 Unauthorized. If those headers are present the request is treated as IMDSv2, otherwise as IMDSv1.

Why the extra step helps (docs details plus my plain-language reading, not an official explanation): the PUT response by default has an IP hop limit of 1, and PUT requests carrying an X-Forwarded-For header are rejected. Together with the need to craft a PUT with a custom header, that makes it harder for a simple "fetch this URL for me" bug or a misconfigured proxy to hit the service. The docs link a security blog post about defence in depth against open firewalls, reverse proxies and SSRF for the full argument.

Caveats. A hop limit of 1 can cause trouble for containers on the instance (the docs advise raising it, up to 64, when needed). SDKs must be recent enough: the docs list minimum versions (for example AWS CLI 1.16.289, Boto3 1.12.6). And requiring IMDSv2 breaks anything still using IMDSv1.

3. Configuring the IMDS: where, and who wins

The options per instance (docs): IMDS enabled or disabled; IPv6 endpoint; metadata version (httpTokens optional or required); response hop limit (1 to 64); and access to tags in metadata. They can be set at three levels, with this precedence for a new instance: (1) the launch request or launch template, (2) account-level defaults per Region, (3) the AMI (imds-support: v2.0 sets IMDSv2 and a hop limit of 2). Each option is evaluated separately. You can change options after launch on a running or stopped instance, unless an IAM policy or SCP forbids it. There is also an account-level enforcement setting; when it's on, launches that don't resolve to required fail.

CLI form checked on the reference page: aws ec2 modify-instance-metadata-options --instance-id i-... --http-tokens required --http-endpoint enabled. Docs warning: turning the endpoint off breaks anything that relies on it, so test first. Note this connects to the Systems Manager digest: its Default Host Management Configuration requires instances to use IMDSv2.

4. User data: first-boot instructions

  • Opaque to EC2: what you give is what you get back; the instance interprets it. On Linux, two types: shell scripts (starting with #!) and cloud-init directives (starting with #cloud-config). On Windows, the launch agents handle it, using tags like <script> or <powershell>.
  • Must be base64-encoded in transit; the console and the run-instances CLI do it for you. Limit: 16 KB raw (before encoding). I computed that 16 KB becomes 21,848 characters after base64 using the docs' formula ceil(n/3)*4.
  • By default it runs only on the first boot of a launch; you can configure it to run on every restart (on Windows, <persist>true</persist>).
  • Linux scripts run as root, so don't use sudo; they aren't interactive (e.g. use -y flags). Output goes to /var/log/cloud-init-output.log for debugging, and the script is stored under /var/lib/cloud/instances/<instance-id>/, so delete it before making an AMI from the instance or it will be baked in.
  • User data is an instance attribute and is not included in an AMI made from the instance. You can edit it only while the instance is stopped (and root must be EBS); a changed script does not rerun by default.
  • Boot time grows with what you run: allow a few minutes. For heavy setup, the idea of baking an AMI (digest 1) is the common alternative.
  • If a user data script calls AWS APIs, the instance needs an instance profile.

5. IAM roles and instance profiles: credentials without secrets

Applications must sign API requests with AWS credentials. Shipping long-term keys to instances (especially ones AWS creates for you like Spot or Auto Scaling) is hard and risky. The docs' answer: create an IAM role, define who can assume it and what it can do, attach it to the instance, and let the app fetch temporary credentials.

  • An instance profile is the container that passes a role to the instance. If you create the role in the IAM console, a profile with the same name is made automatically; with the CLI/API they are separate actions and can have different names. A profile holds one role; a role can be in many profiles. You attach at most one instance profile to an instance.
  • Credentials are retrieved from iam/security-credentials/<role-name> and look like AccessKeyId, SecretAccessKey, Token, Expiration. They're rotated automatically, with new ones available at least five minutes before the old ones expire. The AWS SDKs, CLI and PowerShell tools fetch and refresh them for you, so application code rarely touches this path.
  • To change permissions, replace the instance profile; the docs advise against removing a role from a profile because the change can take up to an hour. Edits to the role's policy propagate to all instances using it.
  • Attach with the console (Actions, Security, Modify IAM role) or CLI. The reference page shows: aws ec2 associate-iam-instance-profile --instance-id i-... --iam-instance-profile Name=admin-role, usable on running or stopped instances.
  • Use least-privilege policies; the docs suggest IAM Access Analyzer can generate a policy template from CloudTrail activity.

Warning from the docs: services that make HTTP calls on your behalf (HTTP proxies, HTML/CSS validators, XML processors with inclusion) can expose these credentials if they can be pointed at the metadata address.

Instance identity role (a different thing). Every instance also gets an automatic instance identity role used by a few integrated AWS features (such as EC2 Instance Connect and Systems Manager Default Host Management Configuration) to identify the instance. The docs say its credentials have no policies attached, so they give no extra API permissions beyond identification.

Why it matters

This trio explains a lot of real-world EC2 security. It is why you never need to paste keys on an instance, why a bug that lets an attacker make your server fetch an arbitrary URL can become a credential leak, and why "require IMDSv2" is a common hardening step. It also underlies Systems Manager and Auto Scaling bootstrapping (user data plus lifecycle hooks).

Remember this

  • The IMDS is a local, unauthenticated endpoint at 169.254.169.254: don't put secrets in user data or metadata.
  • IMDSv2 = PUT for a token (up to six hours), then send the token on every GET; by default both v1 and v2 are allowed until you require v2.
  • User data is base64, max 16 KB raw, runs as root on first boot only by default, and isn't copied into AMIs.
  • An instance profile carries one IAM role; the instance gets auto-rotated temporary credentials via the IMDS; SDKs fetch them for you.
  • Setting precedence for IMDS options: launch request, then account default, then AMI; each option separately.

Try it yourself

Projects 1 and 2 run locally with no AWS account. Projects 3 to 5 use a small EC2 instance you should terminate afterwards (it may cost money). The metadata curl commands and the two CLI commands are as shown on the docs pages I fetched; I did not run any of them against a live account.

  1. Fake IMDS (no AWS). Write a tiny HTTP server that accepts PUT /latest/api/token with a TTL header, returns a random token, and only answers GET /latest/meta-data/instance-id when the token header is valid and unexpired (otherwise 401). Done when: a request with no token fails, a valid one succeeds, and an expired one fails.
  2. Precedence resolver (no AWS). Implement the three-level precedence (launch value, account default, AMI) for HttpTokens and the hop limit. Done when: it reproduces the docs' Example 1 (tokens required from the AMI, hop limit 1 from the account).
  3. Read your own metadata. SSH or Session Manager into a small instance and run the docs' IMDSv2 two-step with curl to read instance-id and placement/region. Done when: you get both values, and a bare GET behaves as expected for your instance's setting.
  4. Require IMDSv2. Run aws ec2 modify-instance-metadata-options --instance-id <id> --http-tokens required, then retry the bare GET. Done when: the bare request returns 401 and the token-based one works.
  5. User data with a role. Launch an instance with an instance profile that allows only read access to one S3 bucket of yours and user data that writes the instance ID into a file. Check /var/log/cloud-init-output.log. Done when: the file exists, and you can explain why the script didn't need any stored keys. Then try an action the role doesn't allow and read the error.
