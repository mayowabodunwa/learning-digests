AWS S3 · CONCEPT 5 DIGEST

S3 Access Control: Bucket Policies, IAM, ACLs, Block Public Access and Access Points

An S3 bucket starts private. Everything after that is you deciding who gets in and how, and S3 gives you several overlapping tools to do it. This digest sorts them: which ones are the modern defaults, which one is a legacy you mostly switch off, and which one is a safety net that overrides the rest.

In one line

S3 decides every request by looking at identity-based policies (IAM), resource-based policies (bucket and access point policies, plus legacy ACLs), and guardrails like Block Public Access, with an explicit deny beating any allow and no allow meaning denied.

The big idea

The first thing to know is the starting position: by default all S3 resources are private. Only the account that created the resource (the resource owner) and IAM identities in that account with the right permissions can reach it. Every other way in is something someone granted.

The second thing is that "granting" can happen in several places, and they're checked together. A policy on the person or role (IAM), a policy on the bucket, a policy on an access point, an old-style ACL, and an account-wide Block Public Access switch can all weigh in on one request. Once you know what each tool is for, the pile stops feeling random.

Simplification label: this is the S3-side view. IAM itself (users, roles, policy evaluation across services, service control policies) is a big topic that I only touch where S3 docs do. I also don't cover S3 Access Grants, which the docs list as another option.

Key terms

  • Resource owner: the AWS account that creates the resource. For an object, the account that uploaded it (unless ACLs are disabled, see below).
  • Principal: who a statement is about: a user, role, account or service.
  • Identity-based policy: a policy attached to an IAM user, group or role saying what that identity may do.
  • Resource-based policy: a policy attached to the resource, such as a bucket policy or access point policy, saying who may do what to it.
  • Policy statement: one rule with an Effect (Allow or Deny), Principal, Action, Resource and optional Condition.
  • Implicit deny: if nothing allows a request, it's denied.
  • Explicit deny: a Deny statement. Used to guarantee blocking even if another policy allows.
  • ACL (access control list): the older per-bucket / per-object permission list, predating policies.
  • Object Ownership: a bucket setting that controls who owns uploaded objects and whether ACLs are active.
  • Block Public Access (BPA): override switches that stop public access from being granted by ACLs or policies.
  • Access point: a named network endpoint attached to a bucket, with its own policy and network controls.
  • Cross-account access: one AWS account accessing another account's resources.

How it works

0. Grounding: the pieces and who owns what

When S3 gets a request it evaluates all the relevant policies: the user's policy, the bucket policy, and bucket and object ACLs. If it finds no valid permission, it returns 403 Forbidden (Access Denied).

Ownership matters because policies are "owned" by accounts. By default, if another account uploads an object into your bucket, that account owns the object. The bucket owner still keeps some powers (the docs say they pay the bills, so they can deny access to or delete any object in the bucket regardless of who owns it). That ownership split is why cross-account S3 used to be messy, and why Object Ownership (section 3) exists.

1. Policies: the main tool

A policy statement has a few parts. From the docs:

  • Resource: the ARN of the bucket, object, access point or job. Bucket-level actions use arn:aws:s3:::bucket; object-level ones use arn:aws:s3:::bucket/* (all objects) or .../prefix/* (a prefix).
  • Action: what's allowed or denied, such as s3:GetObject. Note the docs' own example that s3:ListBucket is the permission behind the ListObjectsV2 operation, so names don't always match.
  • Effect: Allow or Deny. No allow means implicitly denied; an explicit Deny blocks even if another policy allows.
  • Principal: who the statement is for (in bucket policies).
  • Condition: when the statement applies, using AWS-wide and S3-specific condition keys.

A tiny example in the shape of the docs' own sample, allowing one user to read a bucket (this is my paraphrase of the structure, with placeholders):

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"AWS": "arn:aws:iam::{account-id}:user/{name}"},
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": ["arn:aws:s3:::{bucket}", "arn:aws:s3:::{bucket}/*"]
  }]
}

Notice both the bucket ARN and the /* object ARN: list actions apply to the bucket, get actions to objects.

Which kind of policy when? Per the docs: use a bucket policy for one bucket or a few, or when buckets share similar permissions (you manage one policy per bucket); and you can't grant to another AWS account with an identity-based policy alone, so cross-account needs a bucket policy (or another recommended tool like access points). Both bucket policies and identity-based policies have a 20 KB size limit, which complex setups can hit.

Two-sided checks. From the authorization docs: an IAM principal needs permission from the account it belongs to and from the account that owns the resource (for cross-account work). For objects the bucket owner doesn't own, S3 also checks the bucket policy for an explicit deny, because the bucket owner can deny access to any object in the bucket.

2. ACLs: the legacy tool (and why they're off)

ACLs are the oldest access mechanism: a list of grants on a bucket or object. The docs say the majority of modern use cases don't need them and recommend keeping them disabled except where you must control access per object individually. A couple of reasons it matters: S3 treats an ACL as public if it grants anything to the predefined AllUsers or AuthenticatedUsers groups.

3. Object Ownership: the ACL switch

This is a bucket-level setting with three values:

  • Bucket owner enforced (the default for new buckets): ACLs are disabled, the bucket owner owns every object, and access is controlled by policies only. Requests that set or update ACLs fail, but requests to read ACLs work.
  • Bucket owner preferred: ACLs on. New objects written with the bucket-owner-full-control canned ACL are owned by the bucket owner.
  • Object writer: ACLs on. The uploading account owns the object and can grant access via ACLs.

With ACLs disabled, uploads must either specify no ACL or the bucket-owner-full-control ACL; others fail with a 400 and error code AccessControlListNotSupported. You can disable ACLs on existing buckets too (review your ACL-based permissions and policies first), and you can switch back later: previously existing ACLs are restored, though objects written in the meantime remain owned by the bucket owner.

4. Block Public Access: the safety net

Block Public Access (BPA) settings override policies and ACLs that would otherwise make things public. By default, new buckets, access points and objects don't allow public access, but people can edit policies or ACLs to allow it. BPA exists to stop that. You can set it per access point, per bucket, per account, and at the organization level through AWS Organizations; when levels differ, S3 applies the most restrictive combination. There are four independent settings:

  • BlockPublicAcls: calls that try to set a public ACL fail (PutBucketAcl, PutObjectAcl, and PutObject with a public ACL). Existing ACLs aren't changed.
  • IgnorePublicAcls: S3 ignores all public ACLs on the bucket and its objects, while still accepting uploads that include them.
  • BlockPublicPolicy: S3 rejects PutBucketPolicy calls whose policy would allow public access (and same-account access point policies). The docs recommend applying it at the account level, since a user who can edit the bucket policy could otherwise turn the bucket setting off.
  • RestrictPublicBuckets: a bucket or access point with a public policy is limited to AWS service principals and authorized users in the owner's account, blocking cross-account access.

The docs recommend turning all four on for your account unless you need public access (for example, a static website without CloudFront, which requires turning off the relevant BPA settings). Two things to remember. BPA doesn't alter existing policies or ACLs, so removing a BPA setting makes a bucket with a public policy or ACL publicly reachable again. And BPA covers resource policies and ACLs on S3 resources, so the docs also tell you to check identity-based policies and other resource policies (like KMS key policies) yourself.

What counts as "public"? For policies, S3 starts by assuming public, then calls it non-public only if it grants access to fixed values (no wildcards) of things like a specific principal, a set of CIDR blocks via aws:SourceIp, aws:SourceVpc, aws:SourceVpce, aws:SourceArn, or aws:SourceAccount. A "Principal": "*" statement with no limiting condition is public. One statement can make the whole policy public, which then makes RestrictPublicBuckets cut off even the other statements' cross-account grants.

5. Access points: many doors, one bucket

An access point is a named network endpoint attached to a bucket. Each one has its own policy and network controls, which S3 enforces for requests made through it. Use them when many teams or apps share a dataset and one huge bucket policy is hard to manage.

  • Both must allow. If an access point is attached to a bucket, the access point policy works with the bucket policy, and the docs say both must permit the request. The recommended pattern is delegating: a bucket policy that allows access when s3:DataAccessPointAccount matches your account, so the access point policies do the real work.
  • VPC-only. You can set the network origin to a specific VPC so the access point only takes requests from that private network. The VPC config can't be changed after creation.
  • Own BPA. Each access point has its own Block Public Access settings (all on by default for new ones), fixed at creation.
  • Doesn't change the bucket. Restrictions in an access point policy apply only to requests through that access point; direct bucket requests work as before.
  • Limits from the docs: each access point attaches to exactly one bucket; by default up to 10,000 per account per Region (can request an increase); names are 3 to 50 characters, DNS-compliant, unique within account and Region; policies limited to 20 KB; HTTPS only; no anonymous access; objects only (you can't delete buckets or set up replication through one).
  • Cross-account: you can create an access point on another account's bucket, but it grants nothing until the bucket owner authorizes it in their bucket policy.

Create one from the CLI (syntax from the docs):

aws s3control create-access-point --name {name} \
  --account-id {account-id} --bucket {bucket}

6. Putting it together: a sensible default stack

Reading across the docs, the modern path they point to is: keep Block Public Access on, keep ACLs disabled (Bucket owner enforced), grant access with IAM policies for your own principals and bucket policies (or access points) for sharing, and use explicit denies for must-never-happen rules. That is a summary of the docs' recommendations, not the only valid design; some workloads (for example static websites, or per-object ACL needs) have good reasons to deviate.

Why it matters

Misconfigured S3 access is one of the most common ways data ends up exposed, and nearly always because one of these layers was loosened without the person realizing which others were still in play. Knowing the layers also makes the next concepts click: presigned URLs, CORS and website hosting all interact with Block Public Access and policies, and replication and event notifications need cross-account permissions.

Remember this

  • S3 resources are private by default; access is whatever you grant, and no allow means denied while an explicit deny beats allows.
  • Policies (IAM, bucket, access point) are the main tool; ACLs are legacy and disabled by default on new buckets via Object Ownership "bucket owner enforced".
  • Block Public Access has four settings and can override public policies and ACLs at access point, bucket, account and organization levels; the most restrictive combination wins.
  • Access points are named doors to one bucket with their own policy and network origin; both the access point and bucket must allow the request.
  • Removing a Block Public Access setting doesn't rewrite policies, so an old public policy can become live again.

Try it yourself

Projects 1 and 2 are offline. Projects 3 to 5 use the AWS CLI against a scratch bucket in your own account; I checked the syntax against the docs but haven't run it against a live account. Don't make anything genuinely public, and delete the scratch resources afterwards.

  1. Policy evaluator toy (offline, ~1.5 hours). Model statements as (effect, principal, action, resource-pattern). Implement "explicit deny wins, otherwise any allow, otherwise denied". Done when a test with an allow plus an overlapping deny returns denied, and an empty policy set returns denied.
  2. "Is it public?" classifier (offline, ~1 hour). Given a list of bucket-policy statements, flag the ones with Principal: "*" and no limiting condition, using the docs' fixed-value rule for the condition keys. Done when it flags the docs' two "public" examples and passes the aws:SourceVpc fixed-value example.
  3. Inspect your defaults. On a fresh bucket run aws s3api get-public-access-block --bucket NAME and aws s3api get-bucket-ownership-controls --bucket NAME. Done when you can say what each returned value means and how it matches the docs' stated defaults for new buckets.
  4. Trigger a BPA rejection. With BlockPublicPolicy on, try aws s3api put-bucket-policy with a deliberately public statement (Principal: "*", no conditions) on your scratch bucket. Done when S3 rejects it and you can explain which setting blocked it.
  5. Make an access point. Run aws s3control create-access-point --name NAME --account-id ID --bucket BUCKET, then attach a small read-only policy for one IAM user with aws s3control put-access-point-policy, and add the delegation bucket policy from the docs. Done when that user can read through the access point ARN but a different, unlisted prefix is denied.
