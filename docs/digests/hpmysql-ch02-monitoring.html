Monitoring in a Reliability Engineering World

Why "is the database up?" isn't a good enough question anymore, and the small vocabulary (SLI, SLO, SLA) that lets you actually answer "are our customers happy?" instead.

In one line

Good MySQL monitoring isn't about staring at a wall of graphs, it's about picking a handful of numbers tied to customer experience, agreeing on what "healthy" means for each one, and watching those in a way that warns you before customers notice, not after.

The big idea

For a long time, monitoring a database mostly meant reactive digging: a server got slow, and someone who deeply understood MySQL internals went and profiled it. Site reliability engineering (SRE), a set of practices popularized by Google, reframes this. Instead of asking "is the server healthy" from the inside, you start by asking "are customers happy" from the outside, then pick a small set of measurable signals that answer that question, agree on acceptable ranges for them, and let those numbers guide where engineering time goes. That vocabulary (SLI, SLO, and optionally SLA) is the backbone of this unit, and it changes monitoring from "watch everything" into "watch the few things that actually matter, on purpose."

Key terms

  • SRE (site reliability engineering) — a set of practices, popularized by Google, for running production systems that emphasizes measurable outcomes over gut-feel operations.
  • SLI (service level indicator) — the answer to "how do I measure whether my customers are happy?" A single measurable signal, like "response time for a customer-facing API."
  • SLO (service level objective) — the answer to "what's the minimum I can allow that SLI to be and still call customers happy?" Always defined over a time span (a month, say), never as a bare number in isolation.
  • SLA (service level agreement) — an SLO that's been written into a contract with paying customers, with financial or other penalties attached if it's missed. Optional, and more of a business decision than an engineering one.
  • MTTR (mean time to recovery) — roughly, how fast you can realistically get back to a working state after something breaks. Used to set expectations for disaster-recovery targets.
  • Synthetic transaction (or synthetic test) — a fake action you run on purpose (like a scripted SELECT 1, or a scripted write-then-read) purely to check that a system is actually available, instead of waiting for a real customer to hit a problem.
  • Threads_running — a MySQL status counter for how many queries are actively executing right now on a given host, as opposed to sitting idle.
  • threads_connected / max_connections — how many client connections currently exist versus the ceiling the server is configured to allow. A common failure mode is hitting the ceiling and being unable to open new connections at all.
  • Connection storm — a feedback loop where slower queries make application code open more connections to compensate, and that extra connection load makes the database even slower, which opens even more connections.
  • Replication lag — the delay between a write landing on the source server and that same write becoming visible on a replica. If your app reads from replicas, lag can make fresh data look temporarily missing.
  • Source / replica — in a common MySQL setup, one server (the source) accepts writes and streams changes out to one or more replicas, which mostly serve reads.
  • I/O wait / IOutil — how much time a server's threads spend queued up waiting on disk, and what percentage of the disk's overall access capacity is currently in use.
  • Leading indicator vs. lagging indicator — a leading indicator (like a rising disk-growth rate) warns you before customers are affected; a lagging one (like a spike in customer-facing errors) tells you after they already are.
  • Functional sharding — splitting specific tables that serve one business purpose off into their own dedicated database cluster, so that piece's uptime and performance can be managed on its own.
  • Horizontal sharding — splitting one large data set across multiple database clusters once it's grown past what a single cluster can reliably serve, using some lookup mechanism to find the right piece.
  • Percentile — the value below which a given percentage of your data points fall. The 95th percentile (p95) of response times is the value that 95% of requests were faster than.
  • Average (mean) — the sum of all values divided by how many there are. Useful for some things, but easy to get pulled around by a small number of extreme outliers without you noticing.

How it works

Here's the mental shift worth grounding yourself in before the specifics: monitoring used to be something a small, specialized DBA team did privately, mostly by reacting once something already felt slow. SRE thinking flips the order of operations. You start by deciding, out loud and as a team, what "healthy" means from a customer's point of view, write it down as a number with a time window attached, and only then decide what to watch and alert on. That single reordering (define "happy" first, instrument second) is what the rest of this unit builds on.

Defining SLIs, SLOs, and SLAs

These three terms form a small ladder, each one answering a slightly different question. An SLI is a measurement: "response time for the checkout API" or simply "is the service up." An SLO is a target range for that measurement, always tied to a time window, like "99.5% of pages load in under a few hundred milliseconds, measured across a month." An SLA is an SLO that's been turned into a promise with real consequences attached, usually financial, made to paying customers rather than internal teams. SLAs are optional; most of what you'll actually use day to day is the SLI/SLO pair.

The trap of aiming for 100%

Once you start picking targets, the instinct is to reach for perfection: "we will not have any downtime." It's worth resisting that on purpose. The point of an SLO isn't to be as strict as possible, it's to define the minimum that keeps customers happy, so that engineering time above that line can go toward new features instead of squeezing out one more nine of reliability nobody asked for. Concretely: if customers are content with a page loading in two seconds, chasing 750 milliseconds is spending real effort on something that isn't actually the bottleneck to anyone's happiness.

Three nines (99.9%) already means well under ten minutes of allowed downtime in an average week. Every extra nine gets meaningfully more expensive in engineering effort, which is exactly why the goal isn't "as many nines as possible" but "the fewest nines that still make customers happy."

What to measure: a worked online-store example

To make this concrete, imagine a fictional online store whose traffic is growing and whose infrastructure team needs to prove the database layer can keep up. A workable pair of SLIs and SLOs for that store might look like: pages load faster than a few hundred milliseconds at least 99.5% of the time, measured across a month, and checkout succeeds without an intermittent failure at least 99% of the time in a given calendar month. Notice what's not in either of those: a demand for 100%. Failure is treated as inevitable, and the time window is what lets a team balance new feature work against reliability work instead of chasing perfection on every single request.

A useful pattern in the source material is combining latency and correctness in one sentence: "I expect 99.5% of my database requests to be served quickly, with no errors." That single sentence isn't confirmed by any one metric; it's really shorthand for a bundle of signals working together across three themes worth designing for on purpose: availability, latency, and lack of critical errors. A synthetic test, like a scripted page load run continuously in production, is a good starting signal that "things are broadly OK," but it's only the beginning of the picture.

Monitoring solution options

Once you know what you want to measure, you need something to actually collect and display it. Broadly, you're picking between paying a vendor and assembling something from open pieces, and it's a genuine tradeoff rather than an obviously correct choice either way. Commercial tools whose whole job is profiling database performance (the source names SolarWinds Database Performance Management as an example) can make query-level insight accessible to a much wider slice of an engineering org than a small DBA team could reach alone, in exchange for cost. On the open source side, Percona Monitoring and Management (PMM) is a well-established client/server pair: you install a lightweight client on each database instance, it ships metrics to a central server, and that server hosts pre-built dashboards shaped by a lot of accumulated community experience running MySQL, which makes it a solid on-ramp for engineers who are new to the database.

A third path is shipping MySQL's own slow query logs and Performance Schema output somewhere central, then mining them with tools like pt-query-digest (part of the Percona Toolkit). This works, but it tends to be after the fact: you're often discovering a regression once it's already been happening for a while, rather than catching it as it starts. Performance Schema itself is genuinely useful for digging into "why is this specific thing slow," but on its own it isn't really built to answer "are we meeting our reliability promises to customers" (that job belongs to the SLI/SLO layer sitting on top of it).

Monitoring availability

Availability means being able to answer customer requests without an error, which in HTTP terms usually means a clean success like a 200, or an accepted-but-async 202. The cleanest way to verify it is from outside your own system, either passively (reading logs from whatever sits between your application and the database) or actively, by running a synthetic transaction: something as small as a scripted SELECT 1 just to confirm MySQL is alive and parsing queries, or something heavier like an actual write-then-read to confirm data really landed.

External checks confirm availability, but they don't warn you before a problem exists, they only tell you once it already does. That's where a leading indicator like the Threads_running status counter helps: it tracks how many queries are actively executing on a host right now. When that number climbs steadily and doesn't come back down, it usually means queries aren't finishing fast enough and are piling up, which can escalate into the operating system killing the MySQL process outright under CPU or memory pressure, a severe outage if it happens on a source node. A rough starting point is comparing Threads_running against how many CPU cores the host has; sustained numbers well above that core count are worth alerting on before things get dire, alongside watching how close you're getting to max_connections.

Monitoring query latency

MySQL has built-in ways to track how long queries take on the server side, and trending those over time as your application code changes is worthwhile. But server-side latency alone isn't the full customer picture, especially once your architecture has more than one hop between a user's click and a database row. Instrumenting the client side too (having application code itself report time-to-completion for a query) gets you meaningfully closer to what a real customer actually experienced, and pairing that with tracing tools that can follow one request across several services is how you catch the outliers a simple average would hide.

Monitoring for errors

Not every error is a fire. In a system with more than one moving part, some client-side errors are intermittent and resolve themselves on retry, so the raw existence of an error isn't automatically a signal something's broken. What matters more is the rate of an error accelerating across your fleet. Two worth knowing by name: a sharp rise in lock wait timeouts can signal escalating row-lock contention on your source node, and a sudden surge of aborted connections often points at trouble somewhere in the layer between clients and the database, both of which are worth watching as rates rather than one-off counts.

Some errors, on the other hand, matter the moment they appear even once. A MySQL instance unexpectedly reporting it's running in read-only mode can mean a replica just got promoted to source but hasn't been switched out of read-only yet (which is effectively write downtime for your whole cluster), or that something in your access layer is misrouting writes to a replica. Likewise, "too many connections" or an OS-level "cannot create new thread" error means your application layer has opened and held more connections than the server is configured to allow, and these tend to surface immediately to customers as failed requests.

Proactive monitoring: watching for trouble before it's customer-facing

SLO-style monitoring is great at telling you when customers are already unhappy. Proactive monitoring is the other half: watching signals that aren't directly tied to customer impact yet, so you get a heads-up before they become an incident. The balance to strike is that an alert always needs to be actionable: paging someone when a disk is already 100% full is too late (the service is already down), while paging at 80% full might still be too slow if the growth rate is fast, or too noisy if it isn't.

  • Disk growth — worth tracking as a rate if your tooling allows it, not just a static threshold, since a long-running transaction with a large undo log or a big schema change can burn through free disk far faster than a slow, steady creep would suggest. If rate-tracking isn't available, layered thresholds (a soft warning during business hours, a harder page for off-hours) are a reasonable fallback, and a single hard threshold is the bare minimum if that's all your tooling supports.
  • Connection growth — as an application layer scales out, it opens more and more database connections, and a server only has a finite max_connections pool. Watching threads_connected alongside threads_running tells two different stories: connections high but threads_running low usually means the app layer is opening connections it isn't really using; both high and climbing usually means real load that's genuinely risking overload. Tracking threads_connected / max_connections as a percentage tends to be more useful than watching the raw count, since it scales naturally as you add capacity. Watch out for a connection storm too: rising latency can make an application layer open even more connections to compensate, which adds load and makes latency worse, feeding the same loop.
  • Replication lag — the gap between a write landing on the source and showing up on a replica. If reads are served from replicas, a lagging replica can make fresh data look like it silently vanished to a user (think a social comment that seems to not have saved). Lag is both an acute signal that something's wrong right now and a slower-moving trend: even without a customer-facing incident, a rising lag trend can be an early sign that write volume is starting to outgrow what your replicas can keep up with at current capacity.
  • I/O utilization — even on solid-state storage, once your data outgrows memory, you'll eventually be waiting on disk I/O for some queries. Tools like iostat let you track IOutil, the percentage of a disk's overall access capacity currently in use, as a running trend over a day, a few days, or a week. Sustained values close to 100% on a host that isn't mid-backup is usually worth investigating as a sign of full table scans or inefficient queries.
  • Auto-increment space — by default, an auto-increment primary key is a signed integer, and it's possible to run out of key space simply by inserting enough rows over time. Watching remaining key space for any auto-increment primary key is a cheap, easy check that can save you a genuinely painful incident later, since the fix (widening a column) is far easier to do calmly ahead of time than as an emergency.
  • Backup restore time — a disaster-recovery plan is really a promise about how fast you can recover, and that promise only holds if you actually test and time the whole restore-and-catch-up process regularly, not just take a backup and assume it works. As a data set grows, restore time tends to creep up quietly, and it's the kind of metric that can quietly outgrow your recovery-time promise if nobody's watching its trend.

Learning your business's traffic cadence

Every business has a rhythm to its traffic, and that rhythm is exactly when your SLOs get tested hardest and watched most closely. Peak traffic for a given business can run orders of magnitude above an "average" day, and if your database infrastructure isn't ready for that specific shape of spike, that's precisely when customers notice. A few concrete examples of what "cadence" looks like in practice: an ecommerce store's busiest stretch tends to run from late November through the end of the year, with far more concurrent shopping carts and a lot more revenue riding on the same failure modes that are low-stakes the rest of the year. Human resources software often sees a traffic surge in November in the US, when a lot of employees are making annual benefits elections during open enrollment. An online fresh-flower vendor's busiest single day of the year is typically Valentine's Day. None of these cadences look alike, and knowing your own business's version of this is what tells you when to actually worry about capacity, not just react once you're already in the middle of it.

Why averages lie and percentiles tell the truth

This is the idea worth carrying out of the whole unit. A lot of metrics tooling aggregates long-term data down to averages by default, and over any time span longer than a few weeks, that quietly smooths away spikes. If you're checking whether your disk I/O usage could double over the next year, a graph built from averaged data points can give you a false sense of calm right up until it doesn't. An average also gets dragged around by a small number of extreme values without telling you it happened: one very slow query buried in ten thousand fast ones barely moves the average at all, even though that one query might represent a genuinely bad experience for whoever hit it.

Percentiles fix this by working differently: sort every data point in a time window, then report the value at a given rank. The 50th percentile (p50, the median) is the point where half your requests were faster and half were slower. The 95th percentile (p95) is the point where 95% were faster, meaning the slowest 5% were pushed past it. The higher the percentile, the closer you're looking at your worst-served customers rather than your typical one, which is usually exactly who you actually care about when you're deciding if the database layer is doing its job.

Long-term monitoring tools worth demanding

Since percentiles matter this much, it's worth checking your monitoring tooling can actually give you them, not just averages, especially at retention periods stretching back months. A few things worth confirming when you're picking or auditing a metrics tool: does it store and display percentiles (not just pre-aggregated averages) for long time ranges, does it stay fast and usable when you ask it for a long historical window rather than just the last hour, and does it live in the same place the rest of your engineering org already looks at metrics, so database health isn't siloed off as a separate, special-case dashboard nobody outside the database team checks.

Using SLOs to guide bigger architecture decisions

The same SLIs and SLOs that tell you how things are doing right now can also tell you when it's time to make a bigger structural change. As a business grows, holding onto the same availability or latency targets (let alone tightening them) gets more expensive, because the traffic and data volume behind those numbers is growing too. Watching SLOs trend the wrong way over time, alongside signals like replication lag creeping up or disk growth accelerating, is often the earliest honest signal that it's time to consider functional sharding (splitting off one business area's tables into their own cluster) or horizontal sharding (splitting one large data set across multiple clusters), well before a capacity-driven incident forces the decision under pressure.

Why it matters

This unit is the vocabulary that makes every later, more technical topic actually prioritizable. Without an agreed SLI and SLO, "is this replication lag bad?" or "is this query slow?" turns into an argument about feelings. With them, it becomes a number you can check a graph against. It's also the difference between a team that's constantly firefighting reactively and one that catches trouble (a filling disk, a creeping replication lag, an approaching auto-increment ceiling) while it's still cheap and calm to fix. And the averages-versus-percentiles idea specifically will keep showing up: any time you're deciding whether a system is "fast enough," the average is very often lying to you about your worst-served customers.

Remember this

  • An SLI measures, an SLO sets the acceptable range for that measurement over a time window, and an SLA (optional) turns an SLO into a contract with penalties.
  • Don't aim SLOs at 100%. The goal is the minimum that keeps customers happy, so engineering time above that line can go toward new features instead.
  • Good monitoring covers three themes at minimum: availability, latency, and errors, plus proactive signals (disk growth, connection growth, replication lag, I/O utilization, auto-increment space, backup restore time) that warn you before customers are affected.
  • Averages smooth away the outliers that actually hurt your worst-served customers. Percentiles (p50, p95, p99) show you the tail an average hides.
  • Know your business's traffic cadence ahead of time. Peak traffic can run orders of magnitude above average, and that's exactly when your SLOs get tested hardest.

Try it yourself

  • Write your own SLI/SLO sentence. Pick any project you run, even a small personal one, and write one sentence in the shape "I expect [some %] of [some request type] to [some behavior] within [some time window]." Done when you can defend, out loud, why that percentage isn't 100%.
  • Build a percentile meter. In any language, generate a list of a few thousand fake response times: mostly small random numbers, plus a small handful (1-2%) of much larger ones to simulate a slow tail. Compute and print the average, p50, p95, and p99. Done when you can see the average sitting much closer to p50 than to p99, even though the slow requests are real and included in every calculation.
  • Watch threads_connected diverge from threads_running. Spin up MySQL or MariaDB in a free Docker container. In one script, open and hold 20 idle connections; in another, run a handful of connections that are actually busy-looping a query. Run SHOW STATUS LIKE 'Threads%'; while both are active. Done when you can explain, from the two numbers alone, which script is the "idle connections" one and which is the "real load" one.
  • Check your auto-increment headroom. On any MySQL table with an integer auto-increment primary key, look up its current auto-increment value and its column's max possible value in information_schema, then calculate what percentage of the key space has been used. Done when you have a concrete percentage, even if it's a tiny fraction of one percent on a fresh table.
  • Build a tiny disk-growth alarm. Write a script that samples free disk space on a scratch directory every few seconds while you write a steadily growing dummy file, calculates the current rate of consumption, and prints an estimated time-to-full. Done when your script would have paged you with enough lead time to actually do something about it.
  • Map your own business cadence. For any product, real or hypothetical, write down its single busiest week of the year and estimate roughly how many times busier that week is than an average one, the same way the ecommerce/HR/flower-vendor examples do above. Done when you can name one specific database-layer consequence (more connections, more writes, more replication load) that peak week would cause.

Go deeper

Performance Schema comes up here mostly as a tool for digging into "why is this query slow" rather than as an SLO-tracking tool on its own, and it's worth exploring in more depth: a natural next question is how you'd pull an actual p95 or p99 latency number for a specific query pattern directly out of MySQL itself, instead of relying entirely on a client-side or external tool to compute it for you.
