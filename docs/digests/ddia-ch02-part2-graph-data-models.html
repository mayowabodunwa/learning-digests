Data Models and Query Languages, Part 2: Graph-Like Data Models

What happens once "many-to-many" stops being the exception and becomes most of your data: why graphs give you a third shape to reach for, how Cypher and SPARQL let you ask for a pattern instead of writing a chain of joins, and why a graph database is not just the 1970s network model wearing a new outfit.

In one line

When almost anything in your data can be related to almost anything else, a graph (things plus the relationships between them, both queryable) tends to fit more naturally than forcing everything into tables or documents, and modern graph query languages finally let you ask "find a pattern like this" declaratively instead of hand-walking pointers.

The big idea

Part 1 ended on many-to-many relationships: document databases handle one-to-many nicely and strain once references multiply, while the relational model copes better because joins are a built-in, optimized operation. Graphs are what you reach for once those connections stop being occasional and become the point of the data itself, think of a social network, a map, or a recommendation engine. This part covers two ways to model and query that kind of data (the property graph, queried with Cypher, and the triple-store, queried with SPARQL), a reminder that you can technically force graph data into SQL (awkwardly), and the reason graph databases, despite looking a bit like the old CODASYL network model, actually solve its core problem rather than repeating it.

Key terms

  • Graph — a structure made of two kinds of objects: vertices (things) and edges (the relationships between them). Social networks, road maps, and the web itself (pages linked by hyperlinks) are all naturally graphs.
  • Vertex (node) — one "thing" in a graph: a person, a web page, a road junction, whatever your data is about.
  • Edge (relationship) — a connection between two vertices. An edge always has a direction: it starts at a tail vertex and points to a head vertex.
  • Property graph — the graph model where both vertices and edges are more than just an ID: each one also carries a small bag of key-value properties. Implemented by databases like Neo4j.
  • Label — the name attached to an edge (or a vertex type) describing what kind of relationship or thing it is, e.g. DEPENDS_ON or MAINTAINED_BY. Different labels let one graph store many different kinds of facts at once.
  • Cypher — the declarative, pattern-matching query language created for Neo4j (named after a character in The Matrix, not related to cryptographic ciphers).
  • MATCH clause — Cypher's way of describing the shape you're looking for in the graph, using an arrow notation like (a)-[:REL]->(b).
  • Variable-length path (*0..) — a piece of Cypher path syntax meaning "follow this edge label zero or more times," used when you don't know in advance how many hops a relationship chain will take (similar in spirit to the * in a regex).
  • Recursive common table expression (WITH RECURSIVE) — a SQL feature, standardized in SQL:1999, that lets a query build up a result set by referring to its own in-progress output, which is how you fake a variable-length graph traversal in plain SQL.
  • Triple-store — a graph database that stores every fact as a tiny three-part statement, implemented by databases like Datomic and AllegroGraph.
  • Triple — one (subject, predicate, object) statement, e.g. (transit-lib, dependsOn, http-core). Equivalent to one edge, or, when the object is a plain value, one property, in a graph.
  • RDF (Resource Description Framework) — the W3C data model behind triple-stores, originally designed so different websites could publish machine-readable data in a shared format (the "semantic web").
  • Turtle — a compact, human-readable text format for writing RDF triples (there's also a much more verbose RDF/XML format that means the same thing).
  • SPARQL — the standard declarative query language for RDF triple-stores (SPARQL Protocol and RDF Query Language, pronounced "sparkle"). Its pattern-matching syntax predates and heavily influenced Cypher's.
  • Datalog — an older (1980s) rule-based query language, a subset of Prolog, that builds queries out of small, reusable, sometimes-recursive rules rather than one big statement. Used by Datomic and Cascalog.
  • CODASYL / network model — the 1970s data model from Part 1 where a record could have multiple parents, but the only way to reach a record was to walk a pre-declared chain of pointers (an "access path").

How it works

Why reach for a graph at all

Part 1's closing point was that many-to-one and many-to-many relationships are where document databases start to strain and the relational model earns its keep, because joins are a first-class, optimized operation there. Graphs are the next step along that same line: once the connections in your data aren't just common but are genuinely the point, the relational model can start to strain too. A social network (who knows whom), the web itself (which pages link to which), and a road network (which junctions connect to which) are all naturally graph-shaped, and well-known algorithms already exist for them, like a car navigation system finding the shortest path between two junctions, or PageRank ranking web pages by how they're linked to.

A graph is not necessarily made of one kind of thing, either. It's common for every vertex to represent the same kind of entity (all people, or all web pages), but a graph can just as easily mix several kinds of vertices and edges in one datastore. As one real illustration of that: Facebook's internal graph reportedly holds vertices for people, places, events, check-ins, and comments, with edges capturing who's friends with whom, which check-in happened where, who commented on what, and so on, all as one connected structure rather than separate stores per entity type. There are a couple of different, related ways to actually build and query a graph like this, and this digest covers two of them: the property graph model (queried with Cypher) and the triple-store model (queried with SPARQL). There are also imperative graph query languages, like Gremlin, and dedicated graph-processing frameworks for batch computation over huge graphs, like Pregel, but those are outside what this part covers in depth.

The property graph model

In the property graph model, a vertex is: a unique identifier, a set of outgoing edges, a set of incoming edges, and a collection of properties (plain key-value pairs). An edge is: a unique identifier, the vertex it starts at (the tail), the vertex it ends at (the head), a label describing what kind of relationship it is, and its own collection of properties. Notice edges get properties too, not just vertices, so you can attach detail to the relationship itself (like the year a dependency was added), not only to the things it connects.

Here's an original example to make this concrete: imagine tracking software packages and who maintains them. transit-lib is a Package vertex with properties {name: 'transit-lib', version: '2.3.0'}. It has a DEPENDS_ON edge (with a property {since: 2021}) pointing to another Package vertex, http-core. Both packages have a MAINTAINED_BY edge pointing to an Org vertex, Acme or Globex respectively.

Three things about this model matter a lot in practice. First, any vertex can have an edge to any other vertex, there's no schema declaring in advance which kinds of things are allowed to connect. Second, given any vertex you can efficiently find both its incoming and its outgoing edges (that's exactly why, if you represent this in plain relational tables, you'd index the edges table on both the tail and the head columns), which means you can traverse the graph forward or backward. Third, different labels let you store several genuinely different kinds of relationships in one graph while keeping the data model clean. Put together, this tends to make graphs unusually good for evolvability: as an application grows and needs a new kind of relationship (say, a FORKED_FROM edge between packages), you can typically just start creating edges with that label, without redesigning anything that already exists.

Cypher: asking for a pattern, not a procedure

Cypher is a declarative query language for property graphs, built for Neo4j. Its signature move is an arrow notation you use both to create data and to describe a pattern you want the database to find. Continuing the package example, here's an original Cypher statement that creates a small piece of that graph:

CREATE
  (transitLib:Package {name:'transit-lib', version:'2.3.0'}),
  (httpCore:Package    {name:'http-core',   version:'1.0.4'}),
  (acme:Org             {name:'Acme'}),
  (globex:Org           {name:'Globex'}),
  (transitLib) -[:DEPENDS_ON {since:2021}]-> (httpCore),
  (transitLib) -[:MAINTAINED_BY]-> (acme),
  (httpCore)   -[:MAINTAINED_BY]-> (globex)

Each vertex gets a short symbolic name (transitLib, httpCore...) so later parts of the same query can refer back to it. Now suppose you want to answer a real question: which packages maintained by Acme depend, directly or through some chain of other packages, on a package maintained by Globex? That's exactly the kind of "unknown number of hops" question a graph is built to answer, and Cypher's MATCH clause expresses it concisely:

MATCH
  (pkg:Package) -[:DEPENDS_ON*0..]-> (dep:Package) -[:MAINTAINED_BY]-> (:Org {name:'Globex'}),
  (pkg) -[:MAINTAINED_BY]-> (:Org {name:'Acme'})
RETURN pkg.name

Read the first line as: find a package pkg, then follow zero or more DEPENDS_ON edges (that's what *0.. means, "this edge label, zero or more times," much like the * in a regular expression) until you land on some package dep, which itself has a MAINTAINED_BY edge to the Org named Globex. The second line says that same pkg also has to be maintained by Acme. Nothing in the query says how to execute this: whether to start by scanning every package, or to start from the Globex vertex and work backward along incoming edges. As is typical for a declarative language, that's left entirely to the query optimizer, which is free to pick whatever strategy it predicts will be fastest.

Can you query a graph with plain SQL? Sort of.

You can absolutely store a property graph in ordinary relational tables: one table for vertices, one for edges, each with a JSON-ish properties column, and indexes on the edge table's tail and head columns so you can traverse in either direction. The catch shows up the moment you try to query it. In a typical relational query you know in advance exactly which joins you need. In a graph query like the one above, you don't: you might need to walk one DEPENDS_ON edge, or five, before you find what you're after, so the number of joins isn't fixed ahead of time.

SQL does have an answer to this, since SQL:1999: a recursive common table expression, written with WITH RECURSIVE, which lets a query refer to its own result set so it can keep growing it until no more rows match. It's supported in PostgreSQL, IBM DB2, Oracle, and SQL Server. Here's the same "who depends on Globex, and is also maintained by Acme" question, written against a generic nodes/edges schema:

WITH RECURSIVE
  -- packages maintained directly by Globex
  globex_direct(node_id) AS (
    SELECT edges.tail_id FROM edges
      JOIN nodes ON nodes.node_id = edges.head_id
      WHERE edges.label = 'maintained_by' AND nodes.props->>'name' = 'Globex'
  ),
  -- grow that set by following incoming depends_on edges, however many hops it takes
  depends_on_globex(node_id) AS (
      SELECT node_id FROM globex_direct
    UNION
      SELECT edges.tail_id FROM edges
        JOIN depends_on_globex ON edges.head_id = depends_on_globex.node_id
        WHERE edges.label = 'depends_on'
  )
SELECT nodes.props->>'name'
FROM nodes
JOIN depends_on_globex ON nodes.node_id = depends_on_globex.node_id
JOIN edges e2       ON e2.tail_id = nodes.node_id AND e2.label = 'maintained_by'
JOIN nodes org      ON org.node_id = e2.head_id AND org.props->>'name' = 'Acme';

That works, and it's a genuinely useful technique to know, but notice how much more of the traversal logic you have to spell out by hand compared to Cypher's single *0... This isn't a knock on SQL in general, it's a good illustration of a broader point: a technique being possible in a language doesn't mean that language was designed for it, and picking a data model that actually fits your problem tends to save you a lot of this kind of clumsiness later.

Triple-stores and SPARQL

The triple-store model is mostly the property graph model wearing different words. Instead of vertices and labeled edges, everything is stored as tiny three-part statements: (subject, predicate, object). In the triple (transit-lib, dependsOn, http-core), transit-lib is the subject, dependsOn is the predicate (a verb), and http-core is the object. The subject of a triple lines up with a vertex. The object is one of two things: a plain value like a string or number, in which case the predicate and object together work like a property ((transit-lib, name, "transit-lib") is just a vertex with a name property), or another vertex, in which case the predicate is an edge label, the subject is the tail, and the object is the head.

Here's the same small package graph written as triples, in a compact text format called Turtle:

@prefix : <urn:example:>.
_:translib a :Package; :name "transit-lib"; :dependsOn _:httpcore; :maintainedBy _:acme.
_:httpcore a :Package; :name "http-core";   :maintainedBy _:globex.
_:acme     a :Org;     :name "Acme".
_:globex   a :Org;     :name "Globex".

The _:translib-style names only mean something inside this one file, they exist purely so multiple triples can point at "the same vertex." The semicolons are a shorthand for saying several things about the same subject without repeating it. (A side note worth flagging: triple-stores are closely associated with the "semantic web," the idea that websites could publish machine-readable data the way they publish pages for humans, using RDF as a shared format. That vision was heavily hyped in the early 2000s and, at least as of this writing, hasn't really materialized at internet scale, so treat "semantic web" and "triple-store" as related but separable ideas: a triple-store can be a genuinely useful internal data model for an application with zero interest in publishing anything to the open web.)

SPARQL is the standard query language for triple-stores built on the RDF data model. It predates Cypher, and Cypher's pattern-matching syntax borrows from it, so the two read similarly. Here's the Acme/Globex dependency question again, this time in SPARQL:

PREFIX : <urn:example:>
SELECT ?pkgName WHERE {
  ?pkg :name ?pkgName .
  ?pkg :dependsOn* / :maintainedBy / :name "Globex" .
  ?pkg :maintainedBy / :name "Acme" .
}

Variables start with a question mark. The line ?pkg :dependsOn* / :maintainedBy / :name "Globex" chains three predicates together with /: follow dependsOn zero or more times (the *, same idea as Cypher's *0..), then one maintainedBy edge, then check the resulting vertex's name property equals "Globex", all in one line. Because RDF doesn't distinguish between an edge and a property, both work through the same predicate syntax.

Datalog: building queries out of small, reusable rules

Datalog is much older than Cypher or SPARQL, studied by academics since the 1980s, and it's the query language behind Datomic (Cascalog is a Datalog implementation for querying large Hadoop datasets). Its data model looks like the triple-store model generalized slightly: instead of writing (subject, predicate, object), you write predicate(subject, object). Where Cypher and SPARQL jump straight to a single query, Datalog builds a query out of small rules that can call each other, similar to how functions call other functions, including calling themselves recursively. Here's the package example as Datalog facts and rules:

name(acme, 'Acme').
name(globex, 'Globex').
maintained_by(translib, acme).
maintained_by(httpcore, globex).
depends_on(translib, httpcore).

depends_on_rec(Pkg, Dep) :- depends_on(Pkg, Dep).
depends_on_rec(Pkg, Dep) :- depends_on(Pkg, Via), depends_on_rec(Via, Dep).

needs_review(PkgName) :- name(Pkg, PkgName),
                          maintained_by(Pkg, AcmeOrg), name(AcmeOrg, 'Acme'),
                          depends_on_rec(Pkg, Dep),
                          maintained_by(Dep, GlobexOrg), name(GlobexOrg, 'Globex').

?- needs_review(Who).
/* Who = 'transit-lib'. */

Words starting with an uppercase letter (Pkg, Dep, Who) are variables. The two depends_on_rec rules define a new relationship that isn't stored directly: the first rule says a direct dependency counts, the second says "if A depends on B, and B recursively depends on C, then A recursively depends on C," and the database keeps reapplying that second rule until nothing new is produced. That's a genuinely different way to think about a query than one big declarative statement, and it's less handy for a one-off question, but rules can be combined and reused across many queries, which tends to pay off once your data and questions both get more complex.

Graphs vs. the old network model, for real this time

CODASYL's network model, from Part 1, let a record have multiple parents, which sounds a lot like a graph where a vertex can have multiple incoming edges. Given that, it's a fair question whether a graph database is just CODASYL rebranded. It isn't, and the differences are worth naming precisely, since they're exactly what makes graphs practical where the network model wasn't:

  • Schema. CODASYL required a schema declaring which record type could be nested inside which other record type. A graph database has no such restriction: any vertex can have an edge to any other vertex, which is what lets you add a brand-new relationship type without redesigning anything that already exists.
  • How you reach a record. In CODASYL, the only way to a particular record was to walk one of its pre-declared access paths. In a graph database, you can refer directly to any vertex by its unique ID, or look one up through an index, no access path required.
  • Ordering. CODASYL kept a record's children as an ordered set, which the database had to maintain (with real consequences for how data was physically laid out) and which applications had to think about when inserting. In a graph database, vertices and edges typically aren't ordered at all; you only sort when you ask a query to sort its results.
  • Query style. CODASYL queries were all imperative, and easy to break with a schema change. You can still write imperative traversal code against a graph database if you want to, but most graph databases also offer a high-level declarative language, Cypher or SPARQL, on top.

Worth bounding that first point a little: "any vertex can have an edge to any other vertex" describes the common, schema-flexible case for property graph and triple-store databases, not a universal law of every graph system everywhere; some graph tools do let you layer optional constraints on top. The core contrast still holds: CODASYL made you declare and hand-navigate your access paths up front, while a typical graph database lets the connections and the query optimizer do that work instead.

Why it matters

Data started out as one big tree (the hierarchical model), which struggled with many-to-many relationships, which is exactly the problem the relational model was invented to solve. Document databases and graph databases are the two directions modern NoSQL took that same fight in: document databases bet that relationships between records will stay rare, graph databases bet the opposite, that anything might eventually relate to everything. All three (relational, document, graph) are genuinely useful today, each in its own domain, and you can emulate one in terms of another (as the recursive-CTE example above shows), but the result tends to be awkward, which is exactly why different systems exist for different shapes of problem instead of one that tries to do everything. Recognizing when your data has quietly become "anything relates to everything" is a real, practical skill: it's the signal that tells you it might be worth reaching for a graph model instead of forcing more joins onto a relational schema, or more application-side lookups onto a document one.

Remember this

  • A graph is just vertices (things) plus edges (labeled, directional relationships between them), and a property graph lets both carry their own key-value properties.
  • Cypher and SPARQL let you describe a pattern ("this vertex, connected this way, to a vertex with this property") and leave the traversal strategy to the query optimizer, the same declarative bet SQL made decades earlier.
  • SQL can express a variable-length graph traversal with WITH RECURSIVE, but it's noticeably more code than Cypher's *0.., a good reminder that "possible" and "designed for this" aren't the same thing.
  • A triple-store's (subject, predicate, object) facts are the same underlying idea as a property graph's vertices and edges, just described with different vocabulary.
  • Graph databases aren't CODASYL again: no fixed schema restricting connections, direct ID/index access instead of hand-walked paths, and declarative query languages on top when you want them.

Try it yourself

  • Plain-dict graph and a manual traversal. Model a small dependency graph as a Python (or any language) dict of vertices and a list of edges (each edge a tail, head, and label), then write a function that checks whether package A depends on package B directly or through any chain of other packages. Done when: your function correctly answers "yes" for a chain of at least 3 hops and "no" for an unrelated pair.
  • Recursive SQL CTE for a 2-hop traversal. Using SQLite (or Postgres), create the generic nodes/edges tables from this digest, insert a handful of packages, orgs, and edges, then write a WITH RECURSIVE query that finds every package depending (directly or transitively) on a package maintained by a given org. Done when: the query's results match what you can verify by tracing the chain by hand.
  • Flat triples, queried in code. Represent the same small graph as a plain list of (subject, predicate, object) tuples, then write a function that answers "who maintains what" and "what does X depend on" purely by filtering that list, no graph library involved. Done when: both questions return correct answers using nothing but list filtering.
  • Toy Datalog rule engine. Reimplement the depends_on_rec idea from this digest as a small recursive function over your list of edges (not a real Datalog engine, just the same logic), then confirm it finds transitive dependencies your direct-only lookup misses. Done when: it correctly finds a dependency that's 3+ hops away.
  • Schema-change stress test. Add a brand-new relationship type (like FORKED_FROM) to both your dict-graph from the first project and to a small fixed relational schema (a proper table with foreign key columns) representing the same data. Done when: you can point to the exact extra step (a new column, table, or migration) the relational version needed that the graph version didn't.
  • Try a real graph database. Spin up Neo4j (the free desktop app or an online sandbox), load a tiny dataset with a Cypher CREATE statement like the one in this digest, and run one MATCH ... RETURN query with a variable-length path. Done when: the query returns the result you expected, and you can explain in your own words what *0.. is doing.

Go deeper

The most re-readable idea here is the CODASYL comparison: it's tempting to assume "graph database" and "1970s network model" are the same thing wearing different clothes, and the four concrete differences above (schema, access, ordering, query style) are the fastest way to see why that assumption is wrong. A natural next question: for a project you're building, is there a relationship you're currently faking with extra lookup tables or application-side joins that would just be a single labeled edge in a graph?
