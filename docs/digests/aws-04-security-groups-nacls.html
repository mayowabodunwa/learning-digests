Security Groups and Network ACLs in Depth

Two firewalls guard every EC2 instance in a VPC, and they behave nothing alike: one remembers your conversation, the other has amnesia after every single packet.

In one line

A security group is a stateful, instance-level firewall that only ever allows traffic, while a network ACL is a stateless, subnet-level firewall that can allow or deny, and understanding "stateful vs stateless" is what makes both of them make sense.

The big idea

Topic 1 covered how a route table decides whether traffic can even reach a subnet in the first place (public vs. private). Security groups and network ACLs (often shortened to "NACLs") are the next layer down: once traffic is routed to the right place, these two controls decide whether any specific packet is actually allowed through. A security group sits at the instance level and only knows how to say "yes" (allow); it also remembers an open connection, so it automatically lets the reply traffic back in without you writing a matching rule for it. A network ACL sits at the subnet level, can say "yes" or "no" (allow or deny), and has no memory at all: it checks every single packet, in both directions, against its rule table from scratch, every time.

Key terms

  • Security group — a virtual firewall that controls the traffic allowed to reach and leave the resources it's associated with (most commonly an EC2 instance). Allow rules only.
  • Network ACL (NACL) — a virtual firewall that allows or denies traffic at the subnet level, applying to every resource in the subnets it's associated with.
  • ENI (Elastic Network Interface) — the virtual network card AWS attaches to an instance. A security group technically attaches to the ENI, not the instance itself, which matters if an instance has more than one network interface.
  • Stateful — remembers a connection. If a security group lets a request out, it automatically lets the matching response back in, regardless of what the inbound rules say.
  • Stateless — has no memory of past traffic. A network ACL evaluates every packet independently, so an allowed outbound request does not get its response automatically let back in; you need a separate rule for that.
  • Ephemeral port — the temporary, high-numbered port a client picks for the return leg of a connection it starts. The exact range depends on the client's operating system or service (more on this below), which is exactly why it trips people up when writing NACL rules.
  • Ingress / egress — AWS's terms for inbound and outbound traffic. You'll see them in the console and CLI (e.g. AuthorizeSecurityGroupIngress).
  • Rule evaluation order — how a firewall decides which rule applies. A security group looks at all of its rules together and allows traffic if any rule matches. A network ACL checks its numbered rules starting from the lowest number and stops at the first match.
  • Default security group — the security group named "default" that AWS automatically creates with every VPC. It has a specific starting shape, covered below; it is not the same thing as "a security group you just created."
  • Custom security group — any security group you create yourself. It starts with a different (and stricter) shape than the default one.
  • Default network ACL — the network ACL that comes automatically with every VPC and is attached to any subnet you don't explicitly assign to a different one.
  • Custom network ACL — a network ACL you create yourself, which starts in a very different state than the default one (more below).
  • Asterisk (*) rule — the un-removable, un-modifiable catch-all rule at the bottom of every network ACL's rule table (both inbound and outbound). It denies anything that didn't match an earlier numbered rule.
  • Defense in depth — the security idea of stacking independent layers of protection so a mistake in one layer doesn't equal total exposure. It's the reason both of these controls exist side by side instead of AWS just picking one.

How it works

Here's where this fits relative to Topic 1's core networking material: a route table decides whether traffic bound for a subnet is even routed there at all (recall the whole public-vs-private-subnet distinction was just about whether a route table sends 0.0.0.0/0 to an internet gateway). Security groups and network ACLs sit downstream of that decision. Once traffic has a legitimate route to a subnet, the network ACL attached to that subnet gets first look at it, and then, if it's headed to a specific instance, that instance's security group gets a second look. Both have to agree the traffic is allowed. Get either layer wrong and the resource is either unreachable when it shouldn't be, or reachable when it really shouldn't be.

1. Security groups in depth

A security group is associated with resources (usually the ENI of an EC2 instance), and it controls both the inbound traffic allowed to reach that resource and the outbound traffic allowed to leave it. You can attach more than one security group to a resource; when you do, AWS aggregates all of their rules into a single effective rule set, so if any attached security group's rule allows a piece of traffic, it's allowed.

The single most important characteristic: security groups only support allow rules, never deny rules. There's no "block this IP" option inside a security group. If you want to actively deny something (rather than simply not allow it), you need a network ACL, which is one of the reasons the two exist together.

Security groups are also stateful. If an instance sends a request out (say, an EC2 instance opening a connection to an external API), the response traffic is automatically allowed back in, regardless of what the inbound rules say. The same is true in reverse: if inbound traffic is allowed in, the response is automatically allowed back out, regardless of the outbound rules. You never write a security group rule for "the reply to a request I already allowed."

Two different starting points are worth telling apart, because they're easy to mix up:

  • The default security group that comes with every VPC (literally named "default") starts with one inbound rule that allows all traffic, all protocols, all ports, from itself (its source is its own security group ID), and an outbound rule that allows all outbound IPv4 traffic (plus all outbound IPv6 traffic if the VPC has an IPv6 CIDR block). In practice this means two instances both left on the default security group can talk to each other over anything, but neither can be reached from outside that security group, including from an internet gateway or NAT gateway.
  • A custom security group you create yourself starts with no inbound rules at all (nothing is allowed in until you add a rule) and one default outbound rule that allows all outbound traffic (which you're free to remove and replace with something narrower).

A rule itself is built from a protocol, a port range (or ICMP type/code), and a source (inbound) or destination (outbound). That source or destination can be a CIDR block, a single IP address, a managed prefix list, or the ID of another security group. That last option, referencing another security group as the source, is genuinely useful: it lets you write a rule like "allow traffic from any instance in the web-tier security group" instead of hardcoding IP ranges, and it keeps working automatically as instances in that group scale up or down.

2. Network ACLs in depth

A network ACL is attached to a subnet (every subnet must have exactly one network ACL, and one network ACL can be attached to multiple subnets, but a subnet only ever has one at a time). Unlike a security group, its rules are numbered, from 1 to 32766, and each rule can be either allow or deny. AWS evaluates a network ACL's rules starting from the lowest number; the moment a piece of traffic matches a rule, that rule's allow/deny decision is applied and no further, higher-numbered rules are checked, even if one of them would have said something different. That's why the common advice is to number rules in gaps of 10 or 100 (100, 110, 120...), so you can slot a new rule in between two existing ones later without renumbering everything.

Every network ACL, default or custom, ends with an asterisk (*) rule in both its inbound and outbound tables. This rule can't be deleted or modified, and it denies anything that didn't match an earlier numbered rule; it's the network ACL's built-in "if nothing else matched, block it" backstop.

The default and custom starting points differ sharply here too:

  • The default network ACL that comes with a VPC starts with rule 100 allowing all IPv4 traffic (and rule 101 allowing all IPv6 traffic, if the VPC has an IPv6 CIDR block), in both the inbound and outbound tables, followed by the un-removable asterisk deny-all rule. In other words, it starts wide open, and traffic only gets blocked if it somehow fails to match that "allow everything" rule 100.
  • A custom network ACL you create starts with nothing but the asterisk deny-all rules in both directions; there's no rule 100. That means a brand-new custom network ACL denies everything, in both directions, until you add allow rules to it yourself.

Network ACL rules are evaluated as traffic enters or leaves the subnet, not as it's routed between instances within the same subnet, and IPv4 and IPv6 rules are evaluated completely separately from each other.

3. Stateful vs. stateless, and why ephemeral ports matter

This is the distinction that makes everything above click. A security group is stateful: it tracks the connection, so once it lets a request out (or in), the reply is automatically let back in (or out) without a matching rule. A network ACL is stateless: it has no concept of "this is a reply to something I already allowed." Every packet, in every direction, gets checked against the rule table fresh.

That difference has a very concrete consequence. Say an instance in your subnet opens an outbound HTTPS connection to some server on the internet. The response traffic doesn't come back on port 443; it comes back to whatever ephemeral port your instance's operating system picked when it opened the connection, a temporary, high-numbered port used just for that one conversation. A security group doesn't care what that port number is, because it already knows this is the automatically-allowed reply to a connection it approved. A network ACL has no such memory: for that reply to get back into the subnet, you need a separate inbound allow rule that covers the ephemeral port range your instances might be using, or the reply gets silently dropped at the subnet boundary and the connection just times out.

The tricky part is that the ephemeral port range isn't one fixed number: it's chosen by whichever operating system or service initiated the connection. A few examples: many Linux kernels (including Amazon Linux) use ports 32768–61000; Elastic Load Balancing uses 1024–65535; Windows Server 2008 and later uses 49152–65535; older Windows versions through Server 2003 used 1025–5000; a NAT gateway uses 1024–65535; and AWS Lambda uses 1024–65535. Since you often don't control (or can't predict) what's connecting to a public-facing resource, a common practical approach is to open the broad 1024–65535 range inbound for return traffic, and if you need to block something narrower within that range, add a deny rule at a lower rule number than the wide allow rule (remember, lowest number wins).

4. Layering the two together for defense in depth

AWS's own guidance frames these as complementary, not redundant: use security groups as your primary, day-to-day access control (because they're more flexible: stateful, and they can reference other security groups by ID), and bring in network ACLs when you want a coarser, stateless backstop at the subnet boundary. Because a network ACL applies to an entire subnet regardless of which instances are in it, it protects you even in a scenario a security group alone can't: someone launches a new instance into that subnet and forgets to attach the right security group. The instance would fall back to the VPC's default security group (self-reference-only inbound, as covered above), and the subnet's network ACL is still standing guard on top of that regardless.

In practice, that means the two rarely need to enforce identical rules. A reasonable pattern is a permissive-but-sane network ACL (or even close to the wide-open default) that mostly exists to allow you to explicitly deny known-bad ranges or provide a subnet-wide guard rail, combined with tightly scoped security groups doing the real per-instance access control day to day. If you ever do need the stateless, subnet-wide deny (blocking a specific malicious IP range from an entire subnet in one place, for example), that's a job security groups genuinely can't do, and network ACLs can.

Why it matters

Getting either layer wrong is one of the most common ways to either lock yourself out or expose something you didn't mean to. AWS's own best-practice guidance calls this out directly for the classic case: if you open port 22 (SSH) or 3389 (RDP) in a security group with a source of 0.0.0.0/0, you've just allowed literally any IP address on the internet to attempt that connection, not just your own network. That's a security group mistake, not a network ACL one, and it's exactly the kind of thing a stricter, well-scoped network ACL on the subnet can catch as a second line of defense even if a security group rule slips through too broad. On the other side, the stateless nature of network ACLs is the far more common source of "why can't anything reach my instance" debugging sessions: an inbound rule that looks perfectly correct but has no matching outbound rule for the ephemeral return ports (or vice versa) will make a connection hang and time out, even though every individual rule looks fine in isolation. Once you can read a security group as "one-directional intent, reply is free" and a network ACL as "every packet pays its own way, in numbered-rule order," both kinds of debugging get a lot faster.

Remember this

  • Security groups operate at the instance/ENI level, are stateful (return traffic is automatically allowed), and only support allow rules, never deny.
  • Network ACLs operate at the subnet level, are stateless (you must explicitly allow both directions, including ephemeral return ports), and support both allow and deny rules.
  • A network ACL evaluates its numbered rules starting from the lowest number and stops at the first match; a security group evaluates all of its rules together and allows traffic if any rule matches.
  • The default security group starts self-referencing-only inbound and allow-all outbound; a security group you create starts with zero inbound rules and one allow-all outbound rule. The default network ACL starts allow-all; a custom network ACL you create starts deny-all.
  • Ephemeral ports are the reason stateless firewalls need a return-traffic rule at all, and the exact range depends on the client's OS or service, not one universal number.

Try it yourself

  1. Lock an EC2 instance down to a minimal security group. Launch a small Free Tier instance, remove it from the default security group, and attach a custom security group with exactly one inbound rule (SSH or HTTP, from your own IP only). Done when: you can connect from your machine, and you can explain out loud why nobody else on the internet can.
  2. Deliberately break return traffic with a NACL, then fix it. On that instance's subnet, create a custom network ACL, add an outbound allow rule for your traffic (e.g. HTTPS out), but skip the inbound ephemeral-port allow rule. Done when: your outbound request hangs and times out; then add an inbound allow rule for ports 1024–65535 and confirm the same request now works.
  3. Try to write a "deny" security group rule. Open the console's security group rule editor and look for any way to explicitly block a source. Done when: you've confirmed for yourself (not just read here) that the option doesn't exist, and you understand why you'd reach for a network ACL instead.
  4. Read your own account's actual defaults. Using the console or aws ec2 describe-security-groups / describe-network-acls, pull up the default security group and default network ACL in one of your VPCs. Done when: you can point to the self-referencing inbound rule on the default security group and the rule-100-allow-all plus asterisk-deny-all pair on the default network ACL, in your own account's real output.
  5. Prove rule order matters on a NACL. On a custom network ACL, add a low-numbered rule denying one specific IP on port 443, and a higher-numbered rule allowing all traffic on port 443. Test access from the denied IP, then swap the rule numbers so the allow rule has the lower number. Done when: you've watched the same two rules produce opposite outcomes purely from renumbering them.
  6. Layer both and remove one at a time. Put an instance behind a tight security group and a tight custom network ACL simultaneously. Loosen the network ACL back toward the default (allow-all) while keeping the security group tight, then reverse it. Done when: you can explain, from what you observed, why relying on only one of the two layers is riskier than using both.

Go deeper

AWS VPC also has a Reachability Analyzer tool, a static configuration analyzer that traces the hop-by-hop path between two resources and tells you exactly which security group rule or network ACL rule is blocking a connection, instead of you having to reason through the rule tables by hand. Once the mental model in this digest feels solid, that tool is worth trying on a real "why can't A reach B" scenario in your own VPC.
