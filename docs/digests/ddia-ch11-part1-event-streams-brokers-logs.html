SYSTEMS · CH.11 DIGEST (PART 1)

Event Streams, Message Brokers, and Partitioned Logs

Batch processing assumed the input was a finite pile of files. Real data keeps arriving, so this chapter asks what happens if you stop waiting for "the end of the day" and process each event as it happens. This first part covers the plumbing: what an event stream is, why polling a database is a poor way to move events, how traditional message brokers deliver them, and why a different design, the partitioned log, ends up feeling a lot like the batch world's files. It stops right before "Databases and Streams".

In one line

A stream is an unbounded sequence of events, and the main design choice in moving them around is whether messages are transient and deleted once delivered (traditional brokers) or durably kept in an append-only log that consumers read at their own pace (log-based brokers).

The big idea

Chapter 10's batch jobs needed bounded input: a sort can't emit its first output until it has seen the last input. But most real data is unbounded (your users made data yesterday and will tomorrow), so batch systems chop it into artificial chunks like "a day's worth". The cost is delay: a change shows up in the output a day later. Shrink the chunks to a second, or to nothing at all, and you have stream processing. To do that you need a way to hand events from the things that produce them to the things that react to them, with low delay, without losing them, and without one slow reader breaking everyone else. Messaging systems solve this in several ways, and the differences matter.

Key terms

  • Bounded / unbounded data: finite and known size versus never-ending and arriving over time.
  • Stream: data made available incrementally over time. (The source notes the idea appears in Unix stdin/stdout, lazy lists, file APIs, TCP connections, and audio/video delivery.)
  • Event: a small, self-contained, immutable record of something that happened at some time, usually with a timestamp. The streaming word for a "record".
  • Producer (publisher, sender) / consumer (subscriber, recipient): who writes events, who reads them.
  • Topic (stream): a named group of related events.
  • Messaging system / publish-subscribe: producers send messages that are delivered to interested consumers.
  • Backpressure (flow control): blocking a producer from sending more when the consumer can't keep up.
  • Webhook: registering a callback URL so another service calls you when something happens.
  • Message broker (message queue): a server, essentially a database optimized for message streams, that producers write to and consumers read from.
  • Load balancing / fan-out: each message goes to one consumer in a group, or to all of them.
  • Acknowledgment (ack) / redelivery: a consumer tells the broker it finished a message; without an ack, the broker delivers it again.
  • Log-based message broker: a broker that stores messages in an append-only, partitioned log (Kafka, Kinesis, DistributedLog are the source's examples).
  • Offset: the increasing sequence number of a message within a partition.
  • Consumer group: consumers sharing the work of a topic, usually by being assigned whole partitions.
  • Head-of-line blocking: one slow item holds up the ones behind it.
  • Segment: a chunk of the log file; old segments are deleted or archived to free disk space.

How it works

Grounding first. In Chapter 10 the interface between jobs was a file. In a stream the equivalent is a sequence of events. An event is generated once by a producer and may be processed by many consumers, just as a file is written once and read by many jobs. Events are encoded as text, JSON or binary (Chapter 4), so they can be stored or sent over the network. Examples from the source: a user viewing a page or buying something, a temperature sensor reading, a CPU metric, or one line of a web server log.

Why not just have the producer write to a database and have consumers poll it? In principle that works; it is what a daily batch job does. But as you move toward continual, low-delay processing, polling gets expensive: the more often you poll, the smaller the share of requests that find anything new. Consumers should be notified when events arrive. Databases have traditionally been weak at this: triggers exist, but the source calls them limited and "somewhat of an afterthought". So specialized tools for event delivery appeared.

Messaging systems: two questions to ask

A direct channel like a Unix pipe or TCP connection links one sender to one receiver. Messaging systems generalize this so that many producers can write to a topic and many consumers can read from it (publish/subscribe). There's no single right design; the source suggests asking two questions of any system:

  1. What if producers send faster than consumers can process? Three options: drop messages, buffer them in a queue, or apply backpressure. Unix pipes and TCP use backpressure (a small fixed buffer; when it fills, the sender blocks). If you buffer, ask what happens as the queue grows: does the system crash when it no longer fits in memory, or spill to disk, and how does that affect performance?
  2. What if nodes crash or go offline: are messages lost? Durability costs something (writing to disk and/or replication). If you can sometimes lose messages you can get higher throughput and lower latency. Whether that is acceptable depends on the use: an occasional missing sensor reading is probably fine (another is coming soon, though if many are dropped it may not be obvious the metrics are wrong); counting events needs reliable delivery since each lost message makes the counter wrong.

A reminder from batch processing: failed tasks are retried and partial output discarded, so the output is as if no failure occurred. Later parts show how to get a similar guarantee for streams.

Direct messaging from producers to consumers

Some systems skip intermediaries. The source lists: UDP multicast (used in finance for stock feeds where low latency matters; UDP is unreliable, but application-level protocols can recover lost packets if the producer remembers what it sent); brokerless libraries such as ZeroMQ and nanomsg (publish/subscribe over TCP or IP multicast); StatsD and Brubeck (metrics collection over unreliable UDP, so counter metrics are at best approximate); and direct HTTP or RPC calls, as in webhooks. These work well for the situations they were designed for, but application code must be aware of possible message loss, and they generally assume producers and consumers are always online: a consumer that is offline may miss messages, and a retrying producer that crashes loses its buffer.

Message brokers

A widely used alternative is a message broker, which runs as a server that producers and consumers connect to as clients. Because data is centralized in the broker, clients can come, go and crash more easily, and durability becomes the broker's problem. Some brokers keep messages only in memory; others, depending on configuration, write them to disk. With slow consumers they generally allow unbounded queueing (again, configuration-dependent). Consequently consumers are usually asynchronous: the producer waits only for the broker to confirm it buffered the message, not for it to be processed, and delivery happens at some undetermined future moment (often within a fraction of a second, longer if there is a backlog).

Brokers versus databases. Some brokers can even take part in two-phase commit (XA/JTA), which makes them database-like, but the source lists practical differences. Databases keep data until it is explicitly deleted; most brokers delete a message once delivered, so they are not for long-term storage. Brokers assume a small working set (short queues); a large backlog slows each message and may degrade throughput. Databases offer secondary indexes and search; brokers usually offer subscription to topics matching a pattern. And a database query returns a point-in-time result and doesn't tell you when it becomes outdated, whereas brokers don't support arbitrary queries but do notify you when new messages arrive. This is the "traditional view" captured by the JMS and AMQP standards and software such as RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO EMS, IBM MQ, Azure Service Bus and Google Cloud Pub/Sub (the source's list).

Multiple consumers: load balancing and fan-out

When several consumers read a topic, two patterns apply (and can be combined):

  • Load balancing: each message goes to one of the consumers, so they share the work. Useful when messages are expensive to process and you want to add consumers to parallelize. (AMQP: several clients on the same queue; JMS: shared subscription.)
  • Fan-out: each message goes to all consumers, letting several independent consumers tune in to the same broadcast, like several batch jobs reading the same file. (JMS: topic subscriptions; AMQP: exchange bindings.)

Combined example: two groups each subscribe to the topic so each group as a whole gets every message, but within a group only one node gets any given message.

Acknowledgments and redelivery, and why order breaks

A consumer can crash after receiving a message but before finishing it. So brokers use acknowledgments: the consumer explicitly tells the broker when it has finished, and only then is the message removed. If the connection closes or times out with no ack, the broker assumes it wasn't processed and redelivers to another consumer. (It's possible the message was fully processed and only the ack was lost; handling that properly needs an atomic commit protocol, per the source.) Combined with load balancing, redelivery changes ordering: if consumer 2 crashes on message m3 while consumer 1 is busy with m4, the unacknowledged m3 is later redelivered to consumer 1, which sees m4, m3, m5. The source says the combination of load balancing with redelivery inevitably leads to reordering, even if the broker tries to preserve order as the JMS and AMQP standards require. Avoid it by using a separate queue per consumer (no load balancing). Reordering is harmless when messages are independent, but matters when there are causal dependencies.

Partitioned logs

Ordinary network sends leave no trace, and even durable brokers delete messages once delivered. Databases and filesystems take the opposite stance: whatever is written is kept until someone deletes it. This difference matters for derived data. A batch job can be rerun any number of times without harming its read-only input; with AMQP/JMS-style messaging, receiving a message is destructive, so you can't rerun a consumer and get the same result. A newly added consumer sees only messages sent after it registered. The question: can we have the durable storage of a database with the low-latency notification of messaging? That's the log-based message broker.

A log is just an append-only sequence of records on disk (as in storage engines and replication). A producer appends to the end; a consumer reads sequentially and, at the end, waits to be notified of new appends (like tail -f). To exceed one disk's throughput, partition the log (Chapter 6): each partition is a separate log, possibly on a different machine, and a topic is a group of partitions carrying the same type of message. Within a partition, the broker gives each message a monotonically increasing offset; messages in a partition are totally ordered, but there is no ordering guarantee across partitions.

The source names Apache Kafka, Amazon Kinesis Streams and Twitter's DistributedLog as log-based brokers (Google Cloud Pub/Sub is architecturally similar but exposes a JMS-style API). Although they write everything to disk they reach millions of messages per second by partitioning, and get fault tolerance by replicating messages.

Logs compared to traditional messaging

Fan-out is trivial: readers don't affect each other because reading doesn't delete. For load balancing, instead of assigning individual messages the broker assigns whole partitions to nodes in a consumer group; each consumer reads its partitions sequentially, usually single-threaded. Downsides: the number of consumers sharing a topic is at most the number of partitions (a partition's messages go to one node); and one slow message holds up the ones behind it in its partition (head-of-line blocking). So, per the source: if messages are expensive to process, you want per-message parallelism, and order isn't important, the JMS/AMQP style fits better; if throughput is high, each message is quick, and order matters, the log-based approach works very well. (Parallelism can be raised with more partitions.)

Consumer offsets. Because a consumer reads a partition sequentially, "everything below my offset is done, everything above isn't" is enough bookkeeping; the broker needn't track acks per message, just record offsets periodically. That lowers overhead and allows batching and pipelining, which raises throughput. It's the same idea as the log sequence number in database replication (Chapter 5): the broker acts like the leader and the consumer like a follower. If a consumer fails, another node takes its partitions and resumes at the last recorded offset; messages processed after that offset was recorded will be processed again (the chapter returns to this issue later).

Disk space. The log is split into segments, and old ones are deleted or archived, so effectively it's a bounded circular buffer on disk. A consumer that falls so far behind that its offset points to a deleted segment misses messages. The source's back-of-the-envelope calculation: a typical large hard drive (at the time of writing) holds 6 TB and writes 150 MB/s, so writing at full speed fills it in about 11 hours (my own check: 6 TB / 150 MB/s is roughly 40,000 seconds, about 11 hours). Real deployments rarely write at full bandwidth, so logs typically hold several days or weeks. Throughput stays roughly constant regardless of retention since everything is written to disk anyway, unlike brokers that keep messages in memory by default and slow down once they spill to disk.

When consumers can't keep up. In the earlier taxonomy (drop, buffer, backpressure), the log is buffering with a large but fixed-size buffer. You can monitor how far a consumer is behind the head and alert a human, who has a long time to fix it. A lagging consumer affects only itself, so you can experimentally consume a production log for testing or debugging without disrupting others. When a consumer shuts down it consumes no resources; only its offset remains, unlike traditional brokers where queues of dead consumers keep accumulating messages unless deleted.

Replaying old messages. Consuming from a log is read-only; the only side effect is the offset moving, and the offset is under the consumer's control. You can start a copy of a consumer from yesterday's offsets, write to a different place, and reprocess the last day, as many times as you like with different code. That makes log-based messaging more like the batch processing of Chapter 10, with derived data cleanly separated from input and easier recovery from bugs: "a good tool for integrating dataflows within an organization".

Why it matters

Almost any system that reacts to events, from metrics pipelines to order processing to change feeds, sits on one of these two designs. Knowing the trade-off tells you why Kafka-style systems let you replay history, why a work queue is a better fit for slow, independent jobs, and why "just poll the database" stops working as latency targets shrink. It also sets up the next part, where the log idea connects streams and databases.

Remember this

  • A stream is unbounded; an event is a small immutable record; producers write, consumers read. Notification beats polling when delay matters.
  • Ask two questions of any messaging system: what happens when consumers are slower (drop, buffer, backpressure), and what happens on crashes (are messages lost).
  • Traditional brokers delete after ack, load-balance per message, and can reorder after redelivery.
  • Log-based brokers append to partitioned logs: ordered within a partition, offsets as consumer position, durable for a retention window, replayable.
  • Max consumers in a group equals the number of partitions, and a slow message blocks its partition.

Try it yourself

  1. Tiny log broker. Implement a topic as N append-only lists with a hash of the key picking the partition, and a consumer that tracks an offset per partition. Done when per-key order is preserved and a consumer restarted at offset 0 sees everything again.
  2. Replay. Run two consumers over the same log with different code (one counts events, one sums a field), then reset one to an older offset. Done when you can reproduce a result exactly by rerunning from the same offset.
  3. Load balancing with redelivery. Build a simple queue with acks, two workers, and a worker that randomly "crashes" before acking. Done when you can show an out-of-order processing sequence and a duplicate, and explain each.
  4. Backpressure vs buffer vs drop. Connect a fast producer to a slow consumer three ways: bounded blocking queue, unbounded queue, and drop-oldest ring buffer. Done when you can report memory use, loss, and producer delay for each.
  5. Lag alarm. Add a function that computes how far each consumer's offset is behind the log head and prints a warning past a threshold you choose. Done when slowing one consumer triggers only its own warning.
