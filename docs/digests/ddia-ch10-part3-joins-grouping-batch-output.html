SYSTEMS · CH.10 DIGEST (PART 3)

Joins, Grouping, and What Batch Jobs Produce

Part 2 gave us a cluster that can run a mapper and a reducer over files. This part asks the practical questions: how do you join two datasets when there are no indexes, how do you cope when one key is wildly more popular than the rest, what do you do with the output of a batch job, and how does all this compare with the parallel databases that existed long before Hadoop? It stops right before the section called "Beyond MapReduce", which is the next part.

In one line

Joins and groupings in a batch job are all about getting every record that shares a key into the same place, either by sorting and sending them to a reducer, or by making smart assumptions about the data so a mapper can do the join alone; and the best place to put the result is a fresh set of immutable files, not a live database.

The big idea

A database answers "give me the user with ID 4821" with an index lookup. A batch job has no such luxury: it reads whole files from start to end. So when a batch job needs to combine two datasets, it doesn't ask questions one record at a time. It reorganizes the data so that everything about the same key ends up side by side, then does the combining in a simple loop with no network calls. That one move explains reduce-side joins, grouping, and even the fix for hot keys. The second half of this part is about the other end of the pipeline: what a job produces (search indexes, read-only database files) and why "write new files, never poke a live database" keeps things safe and easy to redo. The part closes by comparing Hadoop's approach with massively parallel processing (MPP) databases, which solved a lot of these same problems years earlier.

Key terms

  • Join: combining records from two datasets that refer to each other, such as an event that holds a user ID with the user record that has that ID. The source focuses on equi-joins, where the match is "these two fields are equal" (databases can do other kinds of joins too).
  • Full table scan: reading every record rather than looking up a few through an index. Terrible for finding one record, perfectly reasonable when you want an aggregate over most of the data.
  • Activity events / clickstream: a log of what logged-in users did on a site. The source treats it as the big "fact table" side of the join; the user database is a "dimension".
  • Sort-merge join: a reduce-side join where mappers tag records with the join key, the framework sorts them, and the reducer merges the sorted records from both sides.
  • Secondary sort: arranging the reducer's input so that, within one key, records arrive in a chosen order (for example the user record first, then the events by timestamp).
  • Sessionization: grouping all the events of one user (or session) together to see the sequence of what they did.
  • Hot key / linchpin object: a key with vastly more related records than average (a celebrity account with millions of followers).
  • Skew / hot spot: one reducer getting far more records than the others, so the whole job waits on it.
  • Reduce-side join: the join logic runs in the reducers; mappers only prepare the data.
  • Map-side join: a cut-down job with no reducers and no sorting; each mapper reads input and writes output, doing the join itself, which requires assumptions about the inputs.
  • Broadcast hash join: a map-side join where a small dataset is loaded entirely into an in-memory hash table in every mapper of the big dataset.
  • Partitioned hash join: a map-side join where both inputs are already split the same way by the same key and hash function, so each mapper loads only one slice of the small side (Hive calls it a bucketed map join).
  • Map-side merge join: a map-side join where both inputs are partitioned the same way and sorted by the key, so a mapper can merge them like a reducer would.
  • Search index (term dictionary and postings list): a lookup structure from a keyword to the list of document IDs containing it.
  • Human fault tolerance: the ability to recover from mistakes in code by rolling back and rerunning, because inputs weren't damaged.
  • MPP database (massively parallel processing): a database that runs analytic SQL queries in parallel across a cluster of machines (the source names Teradata, Gamma and Tandem NonStop SQL as early examples).
  • Schema-on-read: storing data raw and leaving its interpretation to whoever reads it, the opposite of fixing a schema before loading.
  • Preemption: a scheduler terminating a lower-priority task to free resources for a higher-priority one.

How it works

Grounding first. In an ordinary database, relationships between records (a foreign key, a document reference, an edge in a graph) are followed by index lookups: find the one user row, then the next. MapReduce has no concept of indexes in the usual sense. When you give a job some files it reads all of them, which a database would call a full table scan. For fetching one record that would be outrageously wasteful, but for analytics, where you want a number computed over a huge share of the records, scanning everything (in parallel across machines) is quite reasonable. So when this part says "join" in a batch setting, it means resolve every occurrence of an association in the dataset at once, for all users together, not look up one user. Keep that picture in mind: it's the whole dataset or nothing.

The running example: events and users

The source uses a join between a log of user activity events (huge, each row holds a user ID and what they did) and a database of user profiles (smaller, includes things like date of birth). The goal: figure out which pages are popular with which age groups. The events only carry the user ID, and copying the full profile into every event would be wasteful, so you must join.

The naive way is to loop through the events and, for each, ask the user database over the network. The source gives three reasons this is bad: throughput gets capped by network round trips, a local cache only helps depending on how the data is distributed, and running many such queries in parallel can overwhelm the database. It also makes the job nondeterministic, since the remote data may change while you're reading it. The principle the source states: for good batch throughput, computation should be as local as possible to one machine, and random-access network requests per record are too slow.

The better way: take a copy of the user database (for example pulled from a backup through an ETL process) and drop it into the same distributed filesystem as the event log. Now both are just files, and MapReduce can bring matching records together.

Reduce-side sort-merge join

Remember the mapper's job: pull a key and value out of each record. Here you run two kinds of mappers. One set reads activity events and emits (user ID, event). Another set reads the user file and emits (user ID, date of birth). The framework partitions all that output by key and sorts it. The effect: for each user ID, the user's record and all of their events end up adjacent in one reducer's input. With a secondary sort, you can arrange for the user record to come first, then the events in timestamp order.

The reducer then runs once per user ID. The first value is the date of birth, which it holds in a local variable, and then it loops over the remaining events, emitting pairs of (URL viewed, viewer's age in years). A follow-up job can then compute the age distribution per URL. Because the reducer sees one user at a time it only holds one user record in memory and never touches the network. This is a sort-merge join: mapper output is sorted by key, then reducers merge the sorted lists from both sides.

Bringing related data together: keys as addresses

A mental model the source offers: think of mappers as sending messages to reducers. The key works like a destination address. It's not an IP address, just an arbitrary string, but everything with the same key is delivered to the same place, namely a single call to the reducer. (That's a mental model, not a literal description of the network protocol.)

What you gain is a clean split. The messy physical part (getting the data to the right machine) belongs to the framework, and your reducer is ordinary, single-threaded logic that can run at high throughput with low memory. The source contrasts this with typical database use, where a data fetch sits deep inside application code. A bonus: because MapReduce handles all the communication, it also shields your code from partial failures like another node crashing, by transparently retrying failed tasks.

GROUP BY and sessionization

Grouping uses the very same pattern. Set up the mappers so the key they emit is the thing you group by; the partition and sort brings all records with that key to one reducer; the reducer aggregates. The source lists typical aggregations: counting records per group (COUNT(*)), summing a field (SUM), or picking the top k records by some ranking. So joining and grouping look quite similar on MapReduce.

Sessionization is a grouping where the key is a session cookie or user ID. If you have several web servers, one user's events are scattered across different servers' log files; grouping on the user identifier collects them in one place (while different users spread across different partitions) so you can see the order of actions. The source says this can be used for A/B testing (did users shown the new site version buy more?) or judging whether a marketing activity is worthwhile.

Handling skew

"Bring all records with the same key to the same place" breaks down when one key has an enormous share of the records. In a social network most users have a few hundred connections while a few celebrities have millions of followers. Those are hot keys. If one reducer gets all of a celebrity's records it does far more work than the rest. And since a job only finishes when all its reducers finish, everything downstream waits for the slowest reducer.

The source describes three compensations (they are tool-specific techniques, not universal defaults):

  • Pig's skewed join: first run a sampling job to discover the hot keys. In the real join, mappers send records for a hot key to one of several reducers chosen at random (instead of the usual deterministic hash of the key). The other join input's records for that key are replicated to all reducers handling it. Cost: copying the other side several times.
  • Crunch's sharded join: similar, but you name the hot keys explicitly instead of sampling.
  • Hive's skewed join: hot keys are declared in table metadata and stored in separate files, and joins on them use a map-side join (next section).

For grouping a hot key you can use two stages: stage one sends records to a random reducer, so each reducer aggregates a subset of the hot key's records into a compact value; stage two combines those partial values into one per key. This works for aggregations where combining partial answers is possible (counts and sums are natural; the source mentions it generally for aggregating).

Map-side joins

The joins so far are reduce-side: the mappers merely prepare data and the reducers join. The upside is that you don't need to assume anything about the inputs. The downside is cost: sorting, copying to reducers and merging can be expensive, and depending on memory buffers, data may be written to disk several times along the way.

If you can make assumptions about your data, you can use a map-side join: a cut-down job with no reducers and no sorting, where each mapper reads one input block and writes one output file. Three variants, in order of how strong the assumption is:

  1. Broadcast hash join: one input is small enough to fit in memory. Each mapper (there is one per block of the large input) first loads the whole small dataset into a hash table, then scans its piece of the large input and looks each key up. The "broadcast" is each mapper reading the entire small input; "hash" is the table. The source says Pig calls this a replicated join, Hive a MapJoin, and it's also used in query engines like Impala. Variant: store the small side as a read-only index on local disk; the hot parts stay in the OS page cache, giving near in-memory lookup speed without the data needing to fit in memory.
  2. Partitioned hash join: both inputs are partitioned the same way (same key, same hash function, same number of partitions). The source's example splits by the last decimal digit of the user ID, so mapper 3 loads only users ending in 3 and scans only events for users ending in 3. Each hash table is smaller. This works well when the inputs came from earlier jobs that already grouped them that way.
  3. Map-side merge join: inputs are partitioned the same way and sorted by the same key. Then size doesn't matter; the mapper reads both files in ascending key order and matches records like a reducer would. If this is possible, earlier jobs probably produced that layout; it could have been done in their reduce stage, but a separate map-only job makes sense if the sorted, partitioned data is useful for other things too.

Why the join choice affects the next job

The output layout differs: a reduce-side join's output is partitioned and sorted by the join key; a map-side join's output is partitioned and sorted the same way as the large input (one map task per block of the large input, whichever map-side variant). Because map-side joins assume things about size, sorting and partitioning, you need to know the physical layout of datasets, not just their encoding and directory name: how many partitions, and by which keys they're split and sorted. In the Hadoop world, the source says this metadata is often kept in HCatalog and the Hive metastore.

The output of batch workflows

Why run all these jobs? The source separates two kinds of database work. Transaction processing (OLTP) looks up a few records by key through indexes. Analytics scans many records and produces reports. Batch processing is neither: it is closer to analytics because it scans large inputs, but the output often isn't a report, it's some other structure.

Search indexes. Google's original use of MapReduce was building its search index, as a workflow of 5 to 10 jobs (the source notes Google later moved away from MapReduce for that). A full-text index is, at heart, a term dictionary (look up a keyword) plus postings lists (the document IDs containing it); real indexes carry more data for ranking, spelling and synonyms. In a batch build, mappers split the documents up, each reducer builds the index for its partition, and index files are written to the distributed filesystem. Since querying an index is read-only, these files are immutable once built. When documents change you can rebuild everything and swap wholesale (costly if little changed, but easy to reason about: documents in, indexes out), or build incrementally the way Lucene writes new segments and merges them in the background (more on that in Chapter 11).

Key-value stores and ML outputs. Batch jobs also build classifiers (spam filters, anomaly detection) and recommendation systems (people you may know, related products). The output is often a database the web app queries by key, such as user ID to suggested friends. Getting it there is the question.

The obvious route is to write to the production database from inside a mapper or reducer, one record at a time. It works if the network allows it, but the source gives three reasons it's a bad idea:

  1. A network request per record is orders of magnitude slower than batch throughput, even with client-side batching.
  2. Many parallel tasks writing at once can overwhelm the database and hurt its query performance, spreading trouble to other systems.
  3. MapReduce normally gives an all-or-nothing result: if the job succeeds, the output is as if every task ran exactly once (even if some were retried); if it fails, there is no output. Writes to an external system are visible side effects you can't hide that way, so partial results can leak, and task retries and speculative execution complicate it.

The better pattern: build a brand-new database inside the job and write it as files to the output directory, like the search index. Those files are immutable and can be bulk-loaded into read-only servers. Examples named in the source: Voldemort, Terrapin, ElephantDB, and HBase bulk loading. Because the stores are read-only, the data structures are simple (no write-ahead log needed). The source's Voldemort description: the server keeps answering from the old files while the new ones are copied over; when the copy completes, it atomically switches to the new files; if something is wrong, it can switch back, since the old files are still there.

The philosophy of batch output

This is the Unix philosophy again: a program reads input, writes output, leaves the input untouched, replaces any previous output, and has no other side effects. You can rerun it as often as you like. Treating inputs as immutable and avoiding external side effects gives performance and, per the source, several maintainability wins:

  • Roll back and rerun. If a bug produced bad output, deploy the old code and rerun, or keep old output in another directory and point back at it. A database with read-write transactions doesn't work this way: rolling back buggy code does nothing to the bad data already written. The source calls recovering from buggy code human fault tolerance.
  • Faster feature development, since mistakes aren't irreversible.
  • Safe automatic retries. A failed task is rerun on the same input; a bug will keep crashing until the job fails after a few attempts, while a transient fault is tolerated. This is safe because inputs are immutable and failed tasks' output is discarded.
  • Reuse of the same files by several jobs, including monitoring jobs that check whether output looks sane (for instance by comparing with the previous run).
  • Logic separated from wiring (input and output directories), so one team writes a job and another decides where and when to run it.

One difference from Unix: Unix tools assume untyped text and spend effort parsing it (remember {print $7}). On Hadoop, structured formats such as Avro and Parquet remove much of that parsing and support schema evolution (recall Chapter 4).

Comparing Hadoop to distributed databases

The source's summary line: Hadoop is somewhat like a distributed Unix, with HDFS as the filesystem and MapReduce as a quirky Unix process that always runs a sort between its map and reduce phases. And it was not new in algorithms: MPP databases had implemented parallel joins and processing a decade earlier. The headline difference: MPP databases focus on running analytic SQL in parallel, whereas MapReduce plus a distributed filesystem is closer to a general-purpose operating system that runs arbitrary programs.

Diversity of storage

Databases make you fit data into a model (relational, documents). Files are just bytes, in any encoding: text, images, video, sensor readings, genome sequences. So Hadoop made it possible to dump data in first and decide how to process it later; MPP databases usually require careful up-front modeling of data and queries. The source argues that making data available quickly, even in a raw, awkward form, is often more valuable than agonizing over the ideal model, similar to a data warehouse's value in bringing data from many parts of an organization together (an idea sometimes called a data lake). The catch is that interpretation becomes the consumer's problem (schema-on-read). That can be an advantage when producers and consumers are different teams; the source's slogan for it is the "sushi principle": raw data is better. A common use: dump raw data into the filesystem, clean and transform it with jobs, then load it into an MPP warehouse. Modeling still happens, just as a separate, decoupled step.

Diversity of processing models

MPP databases are tightly integrated, so they can be well tuned for the queries they were designed for, and SQL is expressive and friendly to analyst tools. But not all processing fits SQL: recommendation systems, relevance ranking in search, image analysis and other application-specific work (feature engineering, language models, fraud-risk functions) need code. MapReduce let engineers run their own code at scale; Hive built SQL on top of it, but you can also write jobs that don't look like SQL at all. People later found MapReduce too limiting or slow for some work, and other processing models appeared on Hadoop (next part). All of them can share one cluster and the same files, so you don't copy data into a different specialized system for each kind of work. The ecosystem includes HBase (random-access OLTP style) and Impala (MPP-style analytics), which use HDFS but not MapReduce.

Designing for frequent faults

Batch jobs are less sensitive to faults than online systems because users aren't waiting and the job can be rerun. Most MPP databases abort a whole query if a node dies, and rerun it; queries are short, so that's cheap, and they like to keep data in memory (hash joins). MapReduce retries at the granularity of a single task and writes eagerly to disk, partly for fault tolerance and partly assuming the data won't fit in memory anyway. Task-level recovery makes fault-free runs slower but pays off for big, long jobs likely to hit at least one failure.

Is that really worth it, if machine failures are rare in most clusters? The source's answer is historical. At Google, batch jobs shared machines with production services, each task had a priority and resource limits, and low-priority tasks could be preempted. The source reports that a MapReduce task running for an hour had roughly a 5% chance of being terminated to make room (more than an order of magnitude higher than hardware or reboot failures), and with 100 tasks of 10 minutes each there's a better than 50% chance that at least one gets killed. So MapReduce tolerates frequent task loss not because hardware is flaky but because arbitrary termination lets the cluster be used more fully. Bound it: those are Google figures from the source, at the time. The source adds that general priority preemption isn't supported in YARN, Mesos or Kubernetes at the time of writing, so where tasks aren't killed so often, MapReduce's design choices make less sense.

Why it matters

"Move related data together, then do simple local work" is the idea behind distributed joins everywhere, not just Hadoop. Knowing the reduce-side versus map-side trade-off helps you reason about why a join is slow or fast, and the skew discussion is the same hot-key problem you'll meet again with partitioned databases. And the output pattern (build new, immutable, then switch) is a practical lesson for any system where a pipeline feeds a serving store. It sets up the next part, where the MapReduce execution model itself comes under scrutiny.

Remember this

  • Batch jobs have no indexes, so they join by rearranging data: in a reduce-side sort-merge join, mappers key both inputs by the join key, sorting lines them up, and the reducer joins them locally.
  • Grouping, counting, and sessionization use the same pattern: make the group key the mapper's key.
  • Hot keys cause skew; the job waits for the slowest reducer. Fixes include random spreading of the hot key (Pig, Crunch), separate handling (Hive), and two-stage aggregation.
  • Map-side joins skip sorting and reducers but need assumptions: small side (broadcast), same partitioning (partitioned hash), or same partitioning plus sorting (merge).
  • Write batch output as new immutable files and switch over, instead of writing live to a database; it makes rollback, retry and reruns safe.
  • MapReduce tolerates task loss because of how Google shared machines, not because tasks fail constantly everywhere.

Try it yourself

  1. Hand-rolled sort-merge join. In any language, write two mappers (users and events) that emit (user_id, (tag, value)) with tag 0 for users and 1 for events. Sort, group by key, and write a reducer that remembers the profile and emits (url, birth year). Done when the output equals a naive dictionary lookup on the same data, including users that never appear in events and events with unknown users (decide, and write down, whether those are dropped).
  2. Broadcast hash join. Rewrite project 1 with no sorting: load the small file into a dictionary and stream the big file. Time both versions on 1 million generated events. Done when you can say which is faster on your machine and why, with the caveat that your machine is one machine, not a cluster.
  3. Hot key lab. Generate counts where one key has 100,000 records and 50 keys have 10. Hash-partition into 4 "reducers" and print the load per reducer. Then add a random salt for the hot key, aggregate per (key, salt), and combine in a second pass. Done when the final counts match and the maximum load drops.
  4. Partitioned vs merge join. Split both inputs into 10 files by user ID mod 10 (and sort each). Join file N with file N only, once with a hash table and once with a two-pointer merge. Done when both match project 1 and the merge version never holds more than one user in memory.
  5. Atomic publish. Have a script build a small key-value file as data.v2 in a new directory, then flip a symlink named current to it, with a reader that always opens current. Done when you can roll back by flipping the link, and the reader never sees a half-written file.
