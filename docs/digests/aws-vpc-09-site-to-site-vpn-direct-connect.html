Site-to-Site VPN, Direct Connect, and Hybrid Routing

How a VPC gets a private path to your office or data center: an encrypted tunnel over the internet, a dedicated physical link, or both, and how routes decide which path traffic takes.

In one line

Site-to-Site VPN builds IPsec tunnels (in the usual setup, over the internet) between AWS and your on-premises device; Direct Connect gives you a private physical connection into AWS; and in both cases the real work is routing, meaning which prefixes each side knows about and which path wins when there are several.

The big idea

So far every network in this series has lived inside AWS. "Hybrid" means one side is somewhere else: an office, a data center, a colocation cage. By default, per the VPN docs, an instance in a VPC can't talk to a remote device on your network, so you have to build the bridge on purpose. AWS gives you two main bridges. The VPN one is quick to set up and rides your normal internet connection, wrapped in encryption. The Direct Connect one is a dedicated link, which takes longer to arrange but bypasses internet service providers on the path. You can run them together. After the bridge exists, the question that fills real-world troubleshooting is routing: both sides need routes pointing across, and when multiple routes could match, AWS has a specific order for choosing.

Key terms

  • Site-to-Site VPN connection: a secure connection between your on-premises equipment and your VPCs.
  • IPsec: the protocol suite the VPN uses to encrypt traffic. The docs say the service supports IPsec VPN connections.
  • VPN tunnel: an encrypted link between AWS and your network. Each VPN connection includes two tunnels you can use at the same time for high availability.
  • Virtual private gateway (VGW): the AWS-side VPN endpoint that attaches to a single VPC.
  • Transit gateway: the hub from Concept 2, which can also be the AWS-side VPN endpoint.
  • Customer gateway (CGW): an AWS resource that tells AWS about your device. The customer gateway device is the real router, firewall or software on your side.
  • BGP: Border Gateway Protocol, a routing protocol where each side advertises the networks it can reach. Called "dynamic" routing in the VPN docs.
  • Static routing: you type in the on-premises prefixes yourself.
  • ASN: autonomous system number, the identifier BGP uses for a network.
  • Direct Connect (DX): a service that links your network to a Direct Connect location over a standard Ethernet fiber-optic cable.
  • Virtual interface (VIF): a logical interface on a DX connection. Types: private, public, transit.
  • Direct Connect gateway: a globally available resource that lets one DX connection reach VPCs across Regions.
  • Route propagation: letting a gateway automatically add learned routes into a VPC route table.

How it works

Grounding: the shape of a hybrid connection

Picture your office network on the left and your VPC on the right. Something has to sit at the edge of each. On the AWS side that is a gateway (a virtual private gateway attached to one VPC, or a transit gateway shared by many). On your side it is a device that speaks the same language. Between them is a path: encrypted tunnels over the public internet (VPN), a dedicated circuit (Direct Connect), or a VPN running on top of a dedicated circuit.

1. Site-to-Site VPN: the pieces

The components. A VPN connection needs a target gateway on the AWS side (virtual private gateway or transit gateway), a customer gateway resource describing your device, and the physical or software device itself. The connection offers two tunnels between the AWS-side gateway and your customer gateway. The docs say you can use both simultaneously for high availability, and that you should configure both.

Who starts the tunnel. By default your device brings up the tunnels by generating traffic and initiating the IKE negotiation (IKE is the key-exchange step). You can configure the connection so AWS initiates instead.

Virtual private gateway versus transit gateway. A virtual private gateway attaches to a single VPC. A transit gateway can serve many VPCs plus on-premises. A few feature differences from the docs: IPv6 traffic isn't supported on virtual private gateway VPN connections (use a transit gateway or Cloud WAN), and a single VPN connection can't carry both IPv4 and IPv6 at the same time. The docs also describe a "Large Bandwidth Tunnel" supporting up to 5 Gbps per tunnel versus the standard 1.25 Gbps, available for connections attached to a transit gateway or Cloud WAN. You can change the target gateway of an existing connection from a virtual private gateway to a transit gateway.

Cost shape. You pay per VPN connection hour while it's provisioned and available, plus data transfer out from EC2 to the internet. I'm not quoting rates.

Other limitations noted by the docs. No Path MTU Discovery; you can't modify an existing IPv4 VPN connection to use IPv6 (delete and recreate); and when joining multiple VPCs to a common on-premises network, use non-overlapping CIDRs (same lesson as peering).

Representative CLI from the reference page (IDs are placeholders):

aws ec2 create-vpn-connection --type ipsec.1 --customer-gateway-id cgw-001122334455aabbc --vpn-gateway-id vgw-1a1a1a1a1a1a2b2b2
add --options "{\"StaticRoutesOnly\":true}" if your device doesn't support BGP; --type only accepts ipsec.1; pass either a VGW or a transit gateway ID, not both

2. Static vs. dynamic routing on the VPN

You choose when creating the connection. If your device supports BGP, pick dynamic: the device advertises its routes to AWS and you don't enter static routes (the docs say that if you use BGP you cannot also specify static routes). If it doesn't, pick static and enter the prefixes yourself. The docs recommend BGP-capable devices because BGP's liveness checks help traffic fail over to the second tunnel when the first goes down.

On the VPC side you must also update the route table so traffic for your remote network targets the virtual private gateway; the docs note you can enable route propagation so the routes are added automatically. And one more constraint from the docs: only prefixes known to the virtual private gateway, through BGP or static entries, can receive traffic from your VPC; the gateway doesn't route anything else outside its attached VPC's CIDR.

3. Direct Connect: the dedicated link

What it is. You connect your router to an AWS Direct Connect router at a Direct Connect location using a fiber cable. On top of that physical connection you create virtual interfaces that reach either AWS public services (like S3) or your VPCs, "bypassing internet service providers in your network path". Requirements include being colocated at a DX location or working with a partner or service provider, supporting 802.1Q VLANs and BGP with MD5 authentication, and using single-mode fiber with specific optics for 1, 10, 100 or 400 Gigabit Ethernet.

Three VIF types.

  • Private VIF: reach a VPC with private IPs. Connect to one VPC directly, or to a Direct Connect gateway to reach multiple virtual private gateways across accounts and Regions (not the China Regions).
  • Public VIF: reach AWS public services using public IP addresses.
  • Transit VIF: reach one or more transit gateways associated with a Direct Connect gateway.

Direct Connect gateway. A globally available resource that acts as a distributed set of BGP route reflectors and sits outside the data path, so it is not a single point of failure. You associate it with a transit gateway, a virtual private gateway, or a Cloud WAN core network. Important limit: gateway associations on the same Direct Connect gateway can't send traffic to each other by default (VPC to VPC through it), with a documented exception when a supernet that overlaps the VPCs is advertised on the same virtual interface. That exception is a real source of surprise; the docs list ways to block it.

Encryption. The docs are explicit: Direct Connect does not encrypt traffic in transit by default. Options: run an IPsec VPN over it (the docs describe combining DX dedicated connections with the VPC VPN for an IPsec-encrypted private connection) or use MACsec on supporting connections, which encrypts between your data center and the Direct Connect location.

Cost shape. Two billing elements: port hours (depending on capacity and dedicated vs hosted connection) and outbound data transfer.

Simplification: I describe DX as "a private link". It is private in the sense of bypassing the public internet path, but, as above, private is not the same as encrypted.

4. Hybrid routing: which route wins?

This is the part most worth memorising, straight from the VPN route-priority page.

In the VPC route table. The most specific matching route wins (longest prefix match), with two special cases. If propagated routes from a VPN or Direct Connect overlap with the VPC's local route, the local route is preferred even if the propagated routes are more specific. And if a propagated route has exactly the same destination as a static route (so longest prefix can't decide), the static route is prioritised when its target is an internet gateway, virtual private gateway, network interface, instance, peering connection, NAT gateway, transit gateway or gateway endpoint. The docs' example: a static route to an internet gateway beats a propagated virtual private gateway route for the same 172.31.0.0/24.

Inside the virtual private gateway. Longest prefix match applies when all endpoints are healthy, and tunnel health takes precedence over other attributes. For equal prefixes, from most to least preferred:

  1. BGP-propagated routes from a Direct Connect connection
  2. Manually added static routes for a VPN connection
  3. BGP-propagated routes from a VPN connection
  4. Among BGP VPN routes, the shortest AS PATH; then, if equal, the lowest MED.

The practical reading: Direct Connect is preferred over VPN for the same prefix, which is why people use VPN as the backup for DX. Other points from that page: AWS picks one of the two tunnels as the primary egress path and that choice may change, so configure both and allow asymmetric routing; a virtual private gateway uses one tunnel across all connections on it; ECMP (using multiple tunnels at once) is supported for VPN on a transit gateway but not on a virtual private gateway. The docs recommend advertising more specific BGP routes to influence path choice.

Choosing, at a glance

  • Path: VPN = encrypted tunnels over your internet connection. DX = dedicated link bypassing ISPs on the path.
  • Encryption: VPN = IPsec. DX = not encrypted by default; add VPN or MACsec.
  • Setup: VPN = create resources and configure your device. DX = needs presence at a DX location or a partner.
  • Redundancy built in: VPN = two tunnels per connection. For DX, the docs have separate resiliency guidance that I haven't read, so I'm not making claims here.
  • Together: DX as primary with VPN as a backup is a common pattern; the route order above is why it works. "Common pattern" is my wording, not a docs guarantee.

Why it matters

Almost every company that isn't cloud-only needs this: databases that stay on-prem, offices that need access to private subnets, migrations that run for months. It also ties the whole series together: the VPC route tables (Concept 1), transit gateways (Concept 2), hybrid DNS over these links (Concept 5), and the lesson that peered VPCs can't borrow a neighbour's VPN or Direct Connect (Concept 8).

Remember this

  • A VPN connection = two IPsec tunnels between a VGW or transit gateway and your customer gateway; configure both.
  • Pick BGP (dynamic) if your device supports it, static otherwise; you can't mix static routes with BGP on one connection.
  • Direct Connect bypasses ISPs on the path but is not encrypted by default.
  • VIF types: private (VPC), public (AWS public services), transit (transit gateways via a DX gateway).
  • For identical prefixes, a virtual private gateway prefers DX-learned BGP, then VPN static, then VPN BGP.

Try it yourself

  1. Paper design first. Draw your office (192.168.0.0/16 is a fine example), a VPC, a virtual private gateway, a customer gateway and the two tunnels. Done when: you can label every route table entry on both sides.
  2. Create the AWS-side resources. Create a virtual private gateway, attach it to a scratch VPC, and create a customer gateway using a documentation IP such as 203.0.113.12 and a private ASN. Then create a VPN connection with create-vpn-connection. Done when: describe-vpn-connections lists it with two tunnels. The tunnels will show down since no real device exists; a VPN connection is billed per hour, so delete it right after. I haven't run this for you.
  3. Download the sample configuration. In the console choose the connection's download-configuration action for a vendor of your choice. Done when: you can find the tunnel outside IPs, inside CIDRs and pre-shared keys in it and explain what each is for. Treat the file as sensitive (the CLI reference warns the response contains sensitive cryptographic information).
  4. Enable route propagation. Turn on propagation on a scratch route table and add a static VPN route. Done when: you can show which routes are marked propagated and which are static.
  5. Route preference quiz. Write a small function that takes a list of candidate routes (prefix, source: DX-BGP, VPN-static, VPN-BGP, AS PATH length, MED) and returns the winner using the order in this digest. Done when: it passes tests for longer-prefix wins, DX beats VPN on equal prefixes, and shortest AS PATH breaks a VPN-BGP tie.
  6. Read, don't buy. Open the Direct Connect docs and the locations list, and write a one-page note on what you'd need to arrange (location or partner, port, cross-connect, VIF) to get a private VIF. Done when: you've listed the prerequisites without ordering anything.
