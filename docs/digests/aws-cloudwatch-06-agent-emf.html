AWS CLOUDWATCH · CONCEPT 6 DIGEST

The CloudWatch Agent and Embedded Metric Format

CloudWatch can see an EC2 instance's CPU out of the box, but it can't see inside the machine: how much memory is used, how full the disk is, what the application wrote to its log file. The CloudWatch agent is the little program you install to fix that. And for code that produces its own numbers (a Lambda function, a container), the Embedded Metric Format lets you publish metrics by simply writing a specially shaped log line. This digest covers both.

In one line

The CloudWatch agent collects metrics, logs and traces from inside servers and ships them to CloudWatch, while the Embedded Metric Format (EMF) turns a structured JSON log event into both a log entry and one or more custom metrics.

The big idea

In the metrics digest we published numbers with PutMetricData, and in the logs digest we sent text with PutLogEvents. Both are API calls you'd have to write code for. These two features reduce that work in different places:

  • The agent runs on the machine, reads things you configure (system metrics, log files), and sends them for you. You write a JSON configuration file instead of code.
  • EMF is a format, not a program. If your application prints a JSON line that includes a small _aws block describing which fields are metrics, CloudWatch Logs automatically extracts those fields as metrics. One line gives you the detailed event (searchable in Logs Insights) and the metric (graphable and alarmable).

Key terms

  • CloudWatch agent: software, open source under the MIT license, that collects metrics, logs and traces from EC2 instances, on-premises servers and containerised apps.
  • In-guest metric: a metric measured from inside the operating system (such as memory used), as opposed to what AWS can observe from outside the instance.
  • Agent configuration file: a JSON file telling the agent what to collect and where to send it. Top-level sections: agent, metrics, logs, traces, opentelemetry.
  • CWAgent: the default namespace for metrics the agent publishes (you can choose another).
  • StatsD / collectd: two protocols that applications and tools use to emit metrics. The agent can receive them.
  • Instance profile / IAM role: how an EC2 instance gets permissions. The agent uses it to call CloudWatch.
  • Embedded Metric Format (EMF): a JSON specification where a log event carries instructions for extracting metrics from itself.
  • Metric directive: an entry in the CloudWatchMetrics array saying which namespace, dimensions and metrics to extract.
  • Target member: a top-level field in the JSON that a directive points at, such as the field holding the latency number.

How it works

Grounding: what CloudWatch can and can't see by default

Out of the box, a service like EC2 publishes metrics that AWS can observe from outside, such as CPU utilisation. Things that only the operating system knows, like memory use or disk used percentage, aren't in that set. The agent is how you get them. It also collects logs from files on the machine, which is the usual way application logs reach CloudWatch Logs.

Simplification: I'm saying "memory and disk aren't in the default set" as the mental model. The docs' wording is that the agent collects "internal system-level metrics" in addition to the metrics for EC2 instances, and it lists the full set on its own page, which I didn't walk through.

1. What the agent can collect

From the docs, the agent can:

  • Collect system-level metrics from EC2 instances across operating systems and from on-premises servers (including hybrid setups and servers not managed by AWS).
  • Receive custom application metrics over StatsD (Linux and Windows Server) or collectd (Linux only).
  • Collect logs from EC2 instances and on-premises servers running Linux or Windows Server (the docs note it doesn't collect from FIFO pipes).
  • Send metrics to CloudWatch, to Amazon Managed Service for Prometheus, or to both.
  • Collect traces from OpenTelemetry or X-Ray client SDKs (from version 1.300025.0) and send them to X-Ray, which saves running a separate trace daemon.

Logs collected by the agent are stored in CloudWatch Logs exactly like other logs. Metrics it collects are billed as custom metrics, so more measurements means a bigger bill; I'm not quoting any prices.

2. Getting the agent running: the four-step flow

The docs give the general flow:

  1. Create IAM roles or users that let the agent collect and send. For EC2, the prerequisites page walks through creating a role with the AWS managed policy CloudWatchAgentServerPolicy, then attaching it to the instance. For on-premises servers it uses an IAM user with long-term credentials, which the docs flag as a security risk (grant only what's needed and remove the user when finished). If you want the agent to set log retention, the role also needs the logs:PutRetentionPolicy permission.
  2. Download the agent package. (The docs describe command-line, console and Systems Manager installs; supported systems include Linux, Windows and macOS.)
  3. Write the configuration file. You can create it by hand or with a wizard.
  4. Install and start the agent. On an EC2 Linux instance, the docs' start command is sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s -c file:<configuration-file-path>. In their words, -a fetch-config makes the agent load the latest configuration file and -s starts it. They also show -c ssm:<parameter-store-name> to read the config from Systems Manager Parameter Store (shown on the on-premises example).

Network requirement. The server needs to reach the CloudWatch and CloudWatch Logs endpoints. The docs say instances need outbound internet access; in a private subnet that means going through a NAT gateway or VPC endpoints. This ties straight back to the VPC track: a private instance with no NAT and no endpoint won't deliver any data.

3. The configuration file

The file is JSON. Per the docs, the recommended Linux path is /opt/aws/amazon-cloudwatch-agent/etc/cloudwatch-agent.json. The parts you'll touch first:

  • agent: global behaviour. metrics_collection_interval defaults to 60 seconds; the docs say values below 60 produce high-resolution metrics. omit_hostname stops the hostname being published as a dimension.
  • metrics: namespace (default CWAgent), append_dimensions (adds EC2 dimensions such as InstanceId or AutoScalingGroupName), aggregation_dimensions (roll-ups across instances), and the required metrics_collected where you name sections like cpu, disk, mem, statsd.
  • logs: inside logs_collected, a files.collect_list where each entry has a required file_path (globs allowed) and optional log_group_name, log_stream_name, retention_in_days, log_group_class, and filters.
  • traces: which trace receivers to listen on (X-Ray, OTLP).

A few specifics worth remembering, all from the docs. The default log stream name is {instance_id}. If you omit log_group_name it's derived from the file path. For retention, omitting it means never expire for new groups. log_group_class can be STANDARD (default) or INFREQUENT_ACCESS and can't be changed after creation (this is the same rule from the logs digest). Filters can include or exclude lines by RE2 regular expression.

A tiny config in the docs' shape (illustrative, assembled from the documented fields):

{ "agent": { "metrics_collection_interval": 60 }, "metrics": { "namespace": "MyServers", "metrics_collected": { "mem": { "measurement": ["mem_used_percent"] }, "disk": { "measurement": ["used_percent"], "resources": ["*"] } } }, "logs": { "logs_collected": { "files": { "collect_list": [ { "file_path": "/var/log/myapp/app.log", "log_group_name": "/myapp/app", "retention_in_days": 14 } ] } } } }

I wrote this example myself from the field descriptions; the metric names mem_used_percent and used_percent follow the docs' naming style (the docs example uses used_percent for disk) but check the "Metrics collected by the CloudWatch agent" page for the exact name list before using it.

4. Embedded Metric Format: a log line that is also a metric

Now the second tool. The docs describe EMF as a way to generate custom metrics asynchronously by writing logs to CloudWatch Logs. CloudWatch extracts the metrics for you, so you can graph and alarm on them, while the full detailed event stays available to Logs Insights queries. It is aimed at short-lived things like Lambda functions and containers, where you don't want separate metric-publishing code or a daemon to maintain.

Two practical consequences from the docs. You don't need cloudwatch:PutMetricData permission, only logs:PutLogEvents. And you are charged for log ingestion and storage plus the custom metrics generated.

5. Anatomy of an EMF document

The log event message must be a valid JSON object with nothing before or after it. It needs an _aws object containing CloudWatchMetrics, an array of metric directives. The docs' example is a good one to study:

{ "_aws": { "Timestamp": 1574109732004, "CloudWatchMetrics": [ { "Namespace": "lambda-function-metrics", "Dimensions": [["functionVersion"]], "Metrics": [ { "Name": "time", "Unit": "Milliseconds", "StorageResolution": 60 } ] } ] }, "functionVersion": "$LATEST", "time": 100, "requestId": "989ffbf8-9ace-4817-a57c-e4dd734019ee" }

Read it in layers:

  • Timestamp (milliseconds since 1970 UTC): the docs say it must be no more than 14 days in the past or 2 hours in the future, otherwise the metrics aren't published.
  • Namespace: where the metric lands.
  • Dimensions: an array of dimension sets (each an array of key names). The named keys must also be top-level fields in the JSON, with string values. A set can have up to 30 keys, and every dimension set creates a separate metric in CloudWatch.
  • Metrics: for each, a Name pointing at a top-level numeric field (or an array of numbers, up to 100 values), an optional Unit (defaults to None), and an optional StorageResolution (1 for high resolution, 60 for standard, with 60 the default).
  • Everything else, like requestId above, is just ordinary log data. It's not a dimension unless the directive says so.

Limits and rules to remember (docs): a single log event is limited to 1 MB; a log event must not contain more than 100 metric definitions in total, or CloudWatch extracts no metrics from it; a numeric array target can't have more than 100 members, or no metrics are extracted from that event; targets must be top-level fields and cannot be nested objects; invalid names, namespaces or dimension sets cause those particular metrics to be skipped rather than the whole event failing (for dimension sets, others in the same directive are unaffected). Failures can be tracked via metrics in the AWS/Logs namespace. Delivery is at least once, so duplicates may occasionally occur.

The cost trap. The docs are blunt: if you put a high-cardinality field such as requestId into Dimensions, EMF will by design create a custom metric for each unique combination. That is the same cardinality warning as in the metric filter digest. Keep identifiers as plain fields, and use only low-cardinality fields (function version, operation name, environment) as dimensions.

Caveat: the docs list Embedded metric format as a Standard log class feature only (not supported on Infrequent Access).

6. Getting EMF into CloudWatch

  • Client libraries. AWS publishes open-source libraries that build and send EMF for you. I didn't read the per-language pages.
  • PutLogEvents. Generate the JSON yourself, following the specification, and send it with the API.
  • Via the CloudWatch agent. Add "logs": { "metrics_collected": { "emf": { } } } to the agent config so it listens on a socket (the docs say the default is tcp:25888, and their manual example writes to a UDP socket on the same port). Requirements from the docs: the agent must be version 1.230621.0 or later, each event must include a LogGroupName key (inside _aws in their example) so the agent knows the log group, and each event must be on a single line with no newline characters.
  • Lambda. The docs say you don't need to install the agent to send EMF logs from Lambda functions. They add a caveat: Lambda timeouts aren't handled automatically, so if the function times out before metrics are flushed, that invocation's metrics are not captured.

7. Agent or EMF or PutMetricData: which when?

Agent: you own a server (EC2 or on-premises) and want OS-level metrics and log files collected without changing application code.

EMF: your code already logs, or runs somewhere short-lived like Lambda or containers, and you want metrics plus rich searchable context from the same line.

PutMetricData: you want direct control of one metric without logs involved.

Simplification: these overlap. The agent itself can also receive EMF and StatsD, and EMF libraries can send through the agent. Treat this as a first-pass guide, not a rule.

Why it matters

Most real alarms in the alarms digest need data that CloudWatch doesn't collect by default: memory pressure, disk filling up, application-level counters. The agent and EMF are the two most common ways that data arrives. They are also where bills surprise people, because each extra measurement or dimension combination can be another billed custom metric.

Remember this

  • The agent runs on the server, reads a JSON config, and ships metrics and logs; it needs an IAM role (CloudWatchAgentServerPolicy on EC2) and network access to CloudWatch.
  • Agent metrics land in the CWAgent namespace by default and are billed as custom metrics.
  • EMF is a JSON log line with an _aws block that tells CloudWatch which fields to turn into metrics.
  • Only put low-cardinality fields in Dimensions; every dimension set makes its own metric.
  • EMF needs logs:PutLogEvents, not cloudwatch:PutMetricData; Lambda needs no agent.

Try it yourself

  1. Write a valid EMF line by hand. Start from the docs' example document, change the namespace, metric name and unit, and add one extra non-dimension field. Check it against the rules list above. Done when: you can explain, field by field, whether each ends up as a metric, a dimension, or just log data.
  2. Send it with PutLogEvents. Put your EMF line into a lab log group using aws logs put-log-events (timestamps in milliseconds; see the logs digest). Note that the EMF spec has its own Timestamp inside _aws. Done when: the metric appears under your namespace in the console (allow a little time) and you can find the same event in Logs Insights.
  3. Break it on purpose. Reference a metric name that has no matching top-level field, or nest the value one level down. Done when: you've observed that the metric doesn't appear, and you can point to the spec rule that explains why.
  4. Count the cost of a dimension. On paper, take an EMF directive with one dimension set of Operation (5 values) and Environment (2 values). Work out how many distinct metrics that creates for one metric name, then what happens if you add requestId. Done when: your answer matches the docs' rule that each dimension set combination is a separate metric.
  5. Install the agent on a lab instance. Create the IAM role with CloudWatchAgentServerPolicy, attach it, install the package, write a small config with one metric section and one log file, and start it with the docs' fetch-config command. Done when: a CWAgent (or your chosen) namespace shows up in the console and your log file's lines appear in a log group. Delete the instance and log group afterwards.
  6. Agent-fed EMF (stretch). Add "emf": { } to the agent's logs section and send one line to port 25888 as in the docs' bash example. Done when: the event lands in the log group named in LogGroupName and the metric appears.
