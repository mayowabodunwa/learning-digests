Auto Scaling Groups & Elastic Load Balancing

You already know how to launch one server from one AMI. This is about what happens once you need several of them, kept healthy, and reachable through a single front door: an Auto Scaling group holds the servers to a size, an Elastic Load Balancer hands out the traffic, and the two talk to each other automatically.

In one line

An Auto Scaling group is a rule for how many EC2 instances should exist right now (never fewer than a minimum, never more than a maximum), and an Elastic Load Balancer is the front door that only sends traffic to the instances currently passing their health checks, and when you use them together, the group automatically registers new instances with the load balancer and deregisters the ones it removes.

The big idea

Part 1 covered a single instance: pick an AMI, pick an instance type, launch it. In real production use, you rarely run just one. Amazon EC2 Auto Scaling lets you define a group of instances and a target size for that group, then it keeps the group at that size on its own, replacing instances that die and adding or removing instances as demand changes. Elastic Load Balancing sits in front of a group like that (or any set of instances) and spreads incoming requests across whichever of them are currently healthy, so one slow or broken server doesn't take your whole application down with it. Used together, an Auto Scaling group and a load balancer form a loop: the group keeps the right number of servers running, the load balancer keeps sending traffic only to the ones that are actually working, and each one tells the other when membership changes.

Key terms

  • Auto Scaling group (ASG) — a collection of EC2 instances "treated as a logical grouping for the purposes of automatic scaling and management," per AWS's own definition.
  • Launch template — the configuration an Auto Scaling group uses to launch each instance: which AMI, which instance type, which key pair, which security groups. This is the same AMI-plus-instance-type pairing from Part 1, just handed to the group instead of to a one-off launch.
  • Minimum size — the fewest instances the group is ever allowed to have. Amazon EC2 Auto Scaling ensures the group never goes below this.
  • Maximum size — the most instances the group is ever allowed to have. Amazon EC2 Auto Scaling ensures the group never goes above this.
  • Desired capacity — the number of instances Amazon EC2 Auto Scaling actually tries to keep running right now, somewhere between the minimum and the maximum.
  • Health check — a periodic check Amazon EC2 Auto Scaling uses to decide whether an instance in the group is still good. It can come from Amazon EC2 itself, Elastic Load Balancing, VPC Lattice, Amazon EBS, or a custom check you define.
  • Health check grace period — a window right after an instance launches during which Amazon EC2 Auto Scaling holds off treating a health check failure as a reason to replace it, giving the instance time to boot and start responding normally before it's judged.
  • Scaling policy — a rule you attach to a group that adjusts desired capacity up or down, between the minimum and maximum, in response to demand (or on a schedule). Covered here only at the concept level; the mechanics come later.
  • Load balancer — a single point of contact for clients that spreads incoming traffic across multiple targets (such as EC2 instances) in one or more Availability Zones.
  • Listener — a process on the load balancer that checks for connection requests using a protocol and port you configure, and applies rules to decide where each request goes.
  • Rule — a condition-plus-action attached to a listener. Every listener needs a default rule; you can add more to route different requests differently.
  • Target group — a named group of registered targets (like EC2 instances) that a listener rule can route requests to. Health checks are configured per target group.
  • Target — one thing registered with a target group and eligible to receive traffic, most commonly an EC2 instance.
  • Application Load Balancer / Network Load Balancer / Gateway Load Balancer — the current-generation load balancer types Elastic Load Balancing offers; you pick the one suited to your traffic. A fourth type, Classic Load Balancer, is the previous generation AWS recommends migrating away from. This digest stays at overview depth; the differences between them are their own future topic.

How it works

Here's the grounding picture: an Auto Scaling group and a load balancer solve two different problems that happen to sit right next to each other. The group's job is "how many servers should exist and are they healthy." The load balancer's job is "which of the existing servers should this particular request go to." Neither one needs the other to function on its own, but AWS wires them together so that when the group's membership changes, the load balancer's list of usable targets changes with it, automatically.

1. What an Auto Scaling group actually is

An Auto Scaling group is defined by three numbers and a launch template. The launch template is the same AMI-plus-instance-type combination from Part 1, just reused every time the group needs to launch a new instance. The three numbers are the minimum size, the maximum size, and the desired capacity, and AWS is direct about what each one guarantees: "You can specify the minimum number of instances in each Auto Scaling group, and Amazon EC2 Auto Scaling ensures that your group never goes below this size," the same wording applies in reverse for the maximum, and "if you specify the desired capacity... Amazon EC2 Auto Scaling ensures that your group has this many instances." Desired capacity is the number the group is actively trying to maintain; minimum and maximum are just the floor and ceiling it's allowed to move between. AWS's own example group has "a minimum size of four instances, a desired capacity of six instances, and a maximum size of twelve instances," which is a useful way to picture it: desired capacity can drift anywhere from 4 to 12, but never outside that range.

2. How the group keeps the right instances running

An Auto Scaling group's core job, alongside scaling, is maintaining its size no matter what. AWS states this plainly: "The Auto Scaling group continues to maintain a fixed number of instances even if an instance becomes unhealthy. If an instance becomes unhealthy, the group terminates the unhealthy instance and launches another instance to replace it." All instances in a group start out with a Healthy status and are assumed healthy unless the group is told otherwise, and it can be told by several sources: Amazon EC2 itself, Elastic Load Balancing, VPC Lattice, Amazon EBS, or a custom health check you define. When a launch happens, the group performs the built-in EC2 status checks first, and, after the health check grace period passes, any of the optional health checks you've turned on for the group; these checks then continue periodically for the life of the instance. An instance can also become unhealthy just by disappearing unexpectedly (a Spot Instance interruption, someone terminating it by hand), and the group responds the same way either way: launch a replacement using the group's current launch template settings.

Multi-Availability Zone groups get an extra layer of resilience for free: if you specify multiple Availability Zones for a group, "Amazon EC2 Auto Scaling automatically tries to maintain equivalent numbers of instances in each enabled Availability Zone," and if a zone becomes unhealthy or unavailable and later recovers, the group rebalances on its own by launching in the zones with the fewest instances and terminating elsewhere. This is a simplification worth flagging: the exact rebalancing behavior (and the temporary margin it's allowed to exceed maximum capacity by while doing so) has more nuance than fits here.

3. Scaling policies, at a glance

A scaling policy is what moves desired capacity around on its own instead of you doing it by hand. AWS's own description: "You can use scaling policies to increase or decrease the number of instances in your group dynamically to meet changing conditions. When the scaling policy is in effect, the Auto Scaling group adjusts the desired capacity of the group, between the minimum and maximum capacity values that you specify, and launches or terminates the instances as needed." You can also scale on a schedule instead of (or alongside) a dynamic policy. This digest deliberately stops at "a policy is a rule that moves desired capacity between min and max"; the actual policy types and how you'd tune one are their own concept later in this rotation.

4. What an Elastic Load Balancer actually does

Elastic Load Balancing's own summary is worth quoting in full because it's the whole idea in two sentences: "Elastic Load Balancing automatically distributes your incoming traffic across multiple targets, such as EC2 instances, containers, and IP addresses, in one or more Availability Zones. It monitors the health of its registered targets, and routes traffic only to the healthy targets." A load balancer is a single point of contact for clients. You attach one or more listeners to it, each watching a protocol and port for incoming connections. Each listener has rules (a required default rule, plus optional extras) that decide, for a given request, which target group it goes to. A target group is where the actual EC2 instances (or other targets) are registered, and health checks are configured per target group, so the load balancer knows which of that group's targets are currently safe to send traffic to. Elastic Load Balancing offers a few load balancer types (Application, Network, and Gateway Load Balancers as the current generation, plus the older Classic Load Balancer AWS recommends migrating away from); which one you'd pick, and why, is deep enough to be its own concept later in this rotation, so this digest treats "a load balancer, a listener, and a target group" as the shape that's common across all of them.

5. How an Auto Scaling group and a load balancer work together

This is the pairing the whole digest is building toward, and AWS states the mechanism directly: "If you enable Auto Scaling with Elastic Load Balancing, instances that are launched by Auto Scaling are automatically registered with the target group. Likewise, instances that are terminated by Auto Scaling are automatically de-registered from the target group." In other words, you don't maintain two separate lists by hand. When the group launches a new instance (because one died, because a scaling policy raised desired capacity, or because you changed it manually), that instance shows up as a new target automatically. When the group terminates an instance, it disappears from the target group automatically too, so the load balancer stops sending it traffic before it's even gone. The load balancer's own health checks also feed back into this loop, since Elastic Load Balancing is explicitly listed as one of the sources an Auto Scaling group can use to decide an instance is unhealthy and needs replacing.

Why it matters

This is what actually makes the Part 1 material useful in production. A custom AMI with your application pre-installed is what lets a scaling event bring up a working server in minutes instead of running setup from scratch every time, and the load balancer is what makes adding or removing servers invisible to whoever's using your application, since traffic just keeps flowing to whichever instances are healthy. It also matters when things go wrong upstream of your own account. During a documented AWS us-east-1 event on December 7, 2021, AWS's own post-event summary noted that "the EC2 APIs that customers use to launch new instances... experienced increased error rates and latencies," and separately that "existing Elastic Load Balancers remained healthy during the event, but the elevated API error rates and latencies for the ELB APIs resulted in increased provisioning times for new load balancers and delayed instance registration times." That's a real-world version of exactly the mechanism covered here: an Auto Scaling group can only replace an unhealthy instance if the EC2 launch API underneath it is working, and a load balancer can only register a new target if the ELB API underneath it is working too. Already-running load balancers kept serving traffic fine; it was the "launch something new and wire it in" step that slowed down.

Remember this

  • An Auto Scaling group is a launch template plus three numbers: minimum size, maximum size, and desired capacity, the number it's actively trying to maintain between the other two.
  • The group replaces unhealthy instances on its own, using health checks that can come from EC2, Elastic Load Balancing, VPC Lattice, EBS, or a custom check you define, after a grace period on launch.
  • A load balancer is a single point of contact: a listener's rules send each request to a target group, and health checks configured on that target group decide which of its targets get traffic right now.
  • Attach a target group to an Auto Scaling group and the two stay in sync automatically: launch registers a new target, terminate deregisters it, no manual bookkeeping.
  • Which load balancer type to pick, and how to tune scaling policies and health checks, are their own deeper concepts still to come in this rotation.

Try it yourself

  1. Create your first Auto Scaling group. Build a launch template (Free Tier-eligible AMI and instance type), then create a single-instance Auto Scaling group from it, and confirm the instance reaches the InService lifecycle state with a Healthy status. Done when: you can point to where the launch template supplied the AMI and instance type, and where the Auto Scaling group's desired capacity is set. Cost caution: stay within Free Tier-eligible options and delete the group (which terminates its instance) when you're done for the day.
  2. Terminate the instance and watch it get replaced. From the EC2 console, terminate the running instance that belongs to your Auto Scaling group (not by deleting the group itself). Done when: the group's Activity history shows a termination entry followed by a new launch entry, and the Instances tab shows only the new instance, without you doing anything to trigger the replacement.
  3. Manually change desired capacity and watch it distribute. Edit your group's desired capacity from 1 up to 2 or 3 (keep max above that), across multiple Availability Zones if you set the group up that way. Done when: you can see the new instances appear in the Activity history and, if you used more than one Availability Zone, that Amazon EC2 Auto Scaling spread them across the zones rather than piling them into one.
  4. Put a load balancer in front of two instances and watch health checks work. Register two running instances with a new target group, create a load balancer with a listener pointed at that target group, then stop one instance (or block its health check port with a security group rule) and watch the target group mark it unhealthy. Done when: the target group's console view shows one target healthy and one unhealthy, and requests to the load balancer's DNS name only reach the healthy one. Cost caution: a load balancer is a separate billed resource that isn't guaranteed to fall under current Free Tier terms, so check the current terms before you start and delete the load balancer and target group promptly once you're done.
  5. Attach your Auto Scaling group to a target group and watch registration happen on its own. Point your Auto Scaling group at the target group from the previous project, then raise desired capacity by one and, separately, terminate an instance in the group. Done when: you've watched a newly launched instance appear in the target group's registered targets without you registering it by hand, and watched a terminated instance disappear from it the same way.
