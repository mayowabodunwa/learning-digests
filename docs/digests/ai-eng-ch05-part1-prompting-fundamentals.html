AI ENGINEERING · CH.5 DIGEST (PART 1)

Prompt Engineering: Prompts, In-Context Learning & Best Practices

A prompt is the whole instruction you hand a model, and prompt engineering is just getting good at writing that instruction. This part covers what a prompt is actually made of, why models can "learn" from examples without being retrained, and the handful of techniques (clear instructions, examples, breaking tasks down, asking the model to think step by step) that keep showing up across every model provider's own guides.

In one line

Prompt engineering is the cheapest way to change what a model does: no retraining, just better instructions, and a small set of techniques (clarity, examples, decomposition, "think step by step") consistently move the needle across a wide range of models.

The big idea

Before a model can help you, you have to tell it what you want, and it turns out that how you tell it matters a lot. Models can pick up new behavior just from what you put in the prompt itself, no weight updates required, which is called in-context learning. On top of that, a handful of prompting habits (being explicit, giving examples, breaking big tasks into small ones, asking the model to reason before answering) show up again and again in guidance from OpenAI, Anthropic, Meta, and Google, because they tend to help across a wide range of models, not just one.

Key terms

  • Prompt engineering — crafting an instruction that gets a model to produce the outcome you want, without changing the model's own weights. It's usually the first, cheapest thing to try before more resource-intensive techniques like finetuning.
  • Prompt — the whole input you send to a model. This digest uses the word this way (some teams use "prompt" and "context" interchangeably, more on that below).
  • Context — the information you give a model so it can actually do the task (a paper to answer questions about, a disclosure document, prior conversation). Think of it as the supporting material inside the prompt, separate from the instruction itself.
  • In-context learning — a model changing its behavior based on what's in the prompt, with no retraining involved. Introduced by the GPT-3 paper (Brown et al., 2020).
  • Shot — one worked example included in a prompt.
  • Zero-shot — a prompt with no examples, just an instruction (and maybe context).
  • Few-shot (n-shot) — a prompt that includes n worked examples before the real task. "5-shot" means 5 examples.
  • System prompt — in APIs that split a prompt into parts, the slot usually used for the task description, persona, and rules set by the application developer.
  • User prompt — the slot usually used for the actual question or task, often filled in by (or on behalf of) the end user.
  • Chat template — the exact, model-specific format used to stitch a system prompt and user prompt into one final string of tokens. It's defined by whoever built the model, not by you.
  • Prompt template — different from a chat template: a reusable structure an application developer writes to fill in ("hydrate") with real data for each query.
  • Chain-of-thought (CoT) prompting — explicitly asking a model to work through steps before giving a final answer, instead of jumping straight to one.
  • Self-critique (self-eval) — asking a model to check or critique its own generated output.
  • Prompt decomposition — breaking one large, complicated task prompt into a chain of smaller prompts, each handling one subtask.
  • Prompt catalog — a shared, versioned store of prompts (with metadata like model, creator, date) kept separate from application code, so multiple apps can reuse and track prompt versions independently.

How it works

Here's the grounding picture before the details: a prompt is nothing exotic, it's just the text you feed a model, and the model responds by predicting what should come next given that text. That's it. What makes prompt engineering worth a whole chapter is that the model has to actually follow what you wrote, and small differences in wording, structure, or ordering can change the output a surprising amount, especially for weaker models. Prompt engineering is the cheapest model-adaptation technique there is: you're not touching the model's weights at all, just getting better at asking. Everything below unpacks how prompts are put together, why models can "learn" from a prompt alone, and the practices that consistently help.

1. The three ingredients of a prompt

A prompt is generally made of up to three parts: a task description (what you want done, including any role you want the model to play and the format you want back), one or more examples of how to do the task, and the task itself (the concrete question or input to act on). Not every prompt uses all three. A one-off question like "What's the boiling point of water at sea level?" is really just the task, no description or examples needed. A more involved prompt might read: "You're a strict copyeditor. Flag any sentence over 25 words. Text: [paste article]" — that's a task description (the persona and the rule) plus the task (the article). Later sections add the third ingredient, examples, back in.

2. In-context learning: zero-shot vs. few-shot

Traditionally, a model only does what it was trained to do, and changing its behavior means retraining or finetuning it (updating its weights). The GPT-3 paper showed something different: a model can pick up a new desired behavior just from examples placed in the prompt, with no weight updates at all. This is called in-context learning, and it's a form of continual learning, since it lets a model act on information it never saw during training. For example, a model trained before some new library's documentation existed still won't know that library's newest functions from memory, but you can paste relevant docs into its context and it can often work with them anyway.

Each example you put in the prompt is a shot. A prompt with no examples is zero-shot. A prompt with, say, three worked examples is 3-shot (the general term is few-shot). In general, more examples tend to help a model understand what you want, but two things push back against piling on examples: a longer prompt costs more (most APIs charge per token) and, per one 2023 analysis from Microsoft, stronger models like GPT-4 sometimes showed only limited extra improvement from few-shot examples compared to zero-shot, likely because a more capable model is already better at following plain instructions. That result probably doesn't hold evenly everywhere, though: if a model rarely saw examples of some narrow, specific format in its training data, a few well-chosen examples in the prompt can still make a big difference for that specific case.

3. System prompts vs. user prompts, and the chat template underneath

Many model APIs let you split a prompt into a system prompt and a user prompt. In a common setup, the system prompt carries the task description or persona (set by whoever built the application), and the user prompt carries the actual question or task (often coming from the end user). Picture a chatbot that helps someone read a home inspection report: the system prompt might say "you're an experienced home inspector, answer succinctly," while the user prompt carries the uploaded report and the question "is the roof in good shape?" Almost every generative AI product you've used, including consumer chatbots, has a system prompt working behind the scenes, even if you never see it.

Here's the part that surprises people: under the hood, the system prompt and user prompt don't stay separate. They get combined into one single string of text (and special marker tokens) using a chat template that's specific to that model, not something an application developer invents. Different models use different templates, and the same provider can change the template between versions of their own model. Get the template wrong (an extra line break, the wrong marker tokens) and a model's behavior can degrade in ways that are genuinely hard to notice, because the model usually still produces a plausible-looking answer even with a mismatched template; it just performs worse than it should. A practical habit worth borrowing: before sending a request in production, print the exact final prompt your code assembled and check it matches what the model actually expects.

Why does a system prompt often seem to boost performance? The chapter points to two likely, non-exclusive reasons rather than one guaranteed cause: the system prompt comes first in the final combined prompt, and a model might simply be better at processing instructions that come first; and some models are specifically post-trained to pay more attention to system-level instructions (this is also part of how model developers try to make prompt attacks harder, more on that in a later part). Neither reason is a hard guarantee for every model, so it's worth testing on whichever model you're actually using.

4. Writing instructions the model can't misread

Communicating with a model is a lot like communicating with a person: vague instructions get vague results. A few habits help. First, remove ambiguity about exactly what you want: if you're asking a model to score something, say the scale (1 to 5? 1 to 100?) and say what to do about edge cases (should it guess, or say "I don't know"?). If you notice an undesired pattern, like the model returning "4.5" when you wanted whole numbers, that's a sign to update the instruction, not just hope it stops.

Second, giving the model a persona can shift its perspective in a useful way. Asking a model to act as, say, a supportive kindergarten teacher rather than a harsh critic when reviewing a young child's writing sample can noticeably change the tone and generosity of its feedback, even though nothing about the actual writing changed. Third, examples (the few-shot idea from above) work as a best practice too, not just a learning trick: showing the model one or two examples of the tone or stance you want can steer it away from a generic, hedge-everything answer and toward the kind of response you're actually looking for.

Finally, be explicit about output format. If you want a concise answer, say so (long answers cost more per token and take longer to generate). If you don't want a throat-clearing preamble like "Based on this text, I'd say...", say that too. If you want structured output like JSON, name the exact keys you expect, and give an example if the shape is at all ambiguous. For tasks like classification where you expect the model to emit something short right after your input, add a clear end-of-input marker. Without one, a model can sometimes drift into continuing your input instead of answering it, since a language model, left alone, doesn't strictly separate "what you gave it" from "what it's generating."

5. Giving the model what it needs: context and breaking big tasks down

Just like a student does better on an exam with the right reference material, a model does better with the right context. If you want good answers about a specific paper, put that paper in the prompt. Context also cuts down on made-up answers: when a model doesn't have the facts it needs, it falls back on its own internal (and possibly outdated or wrong) knowledge, which is one common source of hallucination. You can supply context directly, or give the model tools to go fetch it itself (retrieval, web search), though that's a bigger topic for another day.

One tricky variant: restricting a model to only use the context you gave it, and nothing from its general training. This shows up a lot in roleplay-style products, like a chatbot playing a fictional character who shouldn't know anything outside that fictional world. Clear instructions ("answer using only the information below") plus a couple of examples of questions it should refuse can nudge a model in that direction, but there's no guarantee it always sticks to the boundary. Prompting alone can't promise a hard wall here; that's a limitation worth remembering rather than a solved problem.

For genuinely complex tasks, it often helps to break one big prompt into a chain of smaller ones, called prompt decomposition. Picture an email-triage assistant: instead of one giant prompt trying to read an email, decide what it's about, and draft a reply all at once, you could split it into two prompts, one that classifies the email's category, and a second, category-specific prompt that drafts the reply. Decomposition brings a few real benefits: you can monitor each intermediate step, debug a broken step without touching the others, run independent steps in parallel to save time, and each individual prompt is simply easier to write than one sprawling one. GoDaddy reported in 2024 that their customer support chatbot's prompt had grown to more than 1,500 tokens after iterating on it, and that decomposing it into smaller, targeted prompts improved performance while cutting token costs. The trade-off is real too: more steps usually means more model calls (more latency, and users waiting longer before seeing a first output token if they don't see intermediate steps), though decomposed prompts aren't necessarily twice the cost of one big prompt, since smaller prompts often use fewer tokens each and you can route simpler subtasks to a cheaper model.

6. Giving the model time to think: chain-of-thought and self-critique

You can also nudge a model to spend more effort working through a problem instead of answering instantly. Chain-of-thought (CoT) prompting means explicitly asking the model to reason step by step before it commits to a final answer. It's one of the older prompting tricks that's held up well across many different models; it was described in a 2022 research paper (well before ChatGPT existed) and shown to noticeably improve performance on math and reasoning benchmarks, especially for larger models. The simplest version is just adding a phrase like "think step by step" or "explain your reasoning before answering" to a prompt; a more guided version spells out the exact steps you want followed, or shows one worked example of stepped reasoning. One team (LinkedIn, per the chapter) also reported that CoT reduced how often their model hallucinated, though how much this generalizes likely depends on the task and model.

Self-critique (also called self-eval) is a related idea: asking the model to check its own output before finalizing it. Both techniques share a real cost, though: extra reasoning steps mean the user waits longer before seeing any output at all, which matters more for tasks where people don't see those intermediate steps and are just watching a loading spinner.

7. Iterating, evaluating tools, and treating prompts like versioned code

Prompt engineering is rarely a one-shot activity. As you learn how a model actually behaves, you revise. If you ask a model to recommend "the best" programming language and it hedges with "it depends on your use case," and that's not what you wanted, you can revise the prompt to force a pick anyway. Each model also has its own quirks: one might prefer the instructions up front, another at the end; one might be stronger with numbers, another with roleplay. Reading a model's own prompting guide (when one exists) and testing the same prompt across a couple of different models is a fast way to build intuition for a specific model's quirks. When you do iterate, do it systematically: version your prompts, use a consistent evaluation set and metric so you can actually compare one version to the next, and judge a change by its effect on the whole system's output, not just one subtask, since a prompt tweak that improves one step can quietly hurt another.

Because the space of possible prompts for any task is enormous, tools exist to help automate parts of this process, from libraries that try to search for a strong prompt automatically, to simply asking a model to draft or critique a prompt for you. These tools can genuinely help, but they come with real risks worth knowing about: many make several hidden API calls per prompt you're testing (one to generate a candidate, another to validate its output, another to score it), so costs can climb faster than expected; and tool developers make mistakes too, from using the wrong chat template for a given model to typos baked into a default prompt template. A sensible default is to write your own prompts by hand first to build a real feel for the model and your requirements, and if you do use a tool, actually read what it produces rather than trusting it blindly.

Finally, it's worth treating prompts less like scratch text and more like code you maintain. A simple version of this: keep prompts in their own file or module, separate from application logic, so they're independently readable, testable, and reusable across projects. A more mature version, useful once you have prompts scattered across several applications: a shared prompt catalog that tracks each prompt's metadata (which model it targets, who owns it, when it was last changed) and lets different applications intentionally use different, pinned versions of a prompt instead of being forced onto whatever the latest edit happens to be.

Why it matters

Prompt engineering is the technique you'll use before every other one, because it costs nothing but time and doesn't require any special infrastructure. It's also everywhere already: the system-versus-user prompt split underlies essentially every consumer AI chatbot, and decomposition plus "think step by step" show up constantly inside production systems that chain multiple model calls together (an area often called agents, which builds directly on the ideas here). Getting comfortable with these fundamentals is also what makes the next layer worth learning: how far you can actually push a prompt before length becomes a real constraint, and how attackers try to break a well-crafted system prompt from the outside, both of which build directly on what a "prompt," "context," and "system prompt" actually mean.

Remember this

  • A prompt = task description + examples + the task itself. In-context learning lets a model change its behavior from what's in the prompt alone, no retraining needed.
  • Zero-shot means no examples; few-shot (n-shot) means n worked examples included. More examples generally help, but cost more tokens, and stronger models often need fewer.
  • System and user prompts feel separate in your code, but get concatenated into one string by a model-specific chat template before the model ever processes them. A wrong template causes quiet, hard-to-spot performance drops.
  • Clear instructions, personas, examples, sufficient context, breaking work into smaller chained subtasks, and asking the model to "think step by step" are the highest-leverage, broadly-applicable techniques across models.
  • Treat prompts like code: version them, test changes against a consistent eval set, and evaluate at the whole-system level, not just one subtask.

Try it yourself

  1. Zero-shot vs. few-shot showdown. Pick a small classification or formatting task (like labeling short reviews as positive/negative). Write a zero-shot prompt and a 3-shot version of the same task, then run both on 5 identical inputs. Done when: you can point to at least one input where the examples visibly changed the model's answer or its format.
  2. Build a two-part persona bot. Using any API (or playground) that separates system and user prompts, write a system prompt giving the model a persona and a rule, then ask the same question with and without that system prompt active. Done when: you can describe in your own words how the persona changed the tone or content of the answer.
  3. Print the assembled prompt. Before sending a request, print out the exact final text (or as close as your API exposes) your system and user prompts get combined into. Done when: you've confirmed it matches what you expected, or found a surprise (an odd line break, an unexpected order) that would've been invisible otherwise.
  4. Test "think step by step" head to head. Pick 5 questions that require a bit of reasoning (simple word problems, comparisons). Ask each one plain, then again with "think step by step" appended. Done when: you've logged whether the answer, correctness, or quality changed for each of the 5, including any cases where it made no difference.
  5. Decompose one task into a chain. Take a task with two logical stages (classify, then respond) and build it two ways: as one big prompt, and as two chained prompts. Done when: you can compare both on the same 5 inputs and note any difference in quality, latency, or how easy each was to debug.
  6. Version a prompt like code. Put a prompt in its own file with a short header noting the model it targets and the date, make one deliberate change, and diff the two versions with git diff. Done when: you have a clean, readable diff of exactly what changed and why.
