Prompt Engineering: Prompts, In-Context Learning & Best Practices

A prompt is built from a few interchangeable parts, and whether or not you show the model examples is the single biggest lever you have before you ever touch a model's weights. Once that clicks, the rest of prompt engineering is really just a checklist of ways to remove ambiguity.

In one line

A prompt is the whole input you hand a model, it's usually made of a task description, optional examples, and the actual task, and most of what people call "prompt engineering" is a set of concrete techniques for making that input as unambiguous as possible.

The big idea

Prompt engineering means writing an instruction that gets a model to produce the outcome you want, without changing anything inside the model itself (no retraining, no weight updates). That last part is what makes it different from finetuning, and it's also why it's usually the first thing worth trying: it's cheap, fast to iterate on, and foundation models already have enough general capability that a well-written prompt can get surprisingly far on its own. The trick is that "just write good instructions" turns out to hide a lot of structure: how many examples to show, where to put which instruction, how long your prompt can even be, and how to keep a growing pile of prompts organized once you have more than one.

Key terms

  • Prompt — the whole input you give a model to get a task done. It can include a task description, examples, and the concrete task itself, though it doesn't have to include all three.
  • Prompt engineering — crafting a prompt that reliably gets a model to produce the outcome you want, without updating the model's weights.
  • In-context learning — a model picking up a new behavior from information given inside the prompt itself, rather than from further training. It's what lets a model do a task it wasn't specifically trained to do, just by showing it what you want in the prompt.
  • Shot — one example of the task included in the prompt. Five examples is "5-shot."
  • Zero-shot / few-shot — zero-shot means no examples are given in the prompt; few-shot means one or more examples are given before you ask the model to do the actual task.
  • Context — as used in this digest, the information the model needs in order to carry out what the prompt is asking (a document to reference, prior conversation, retrieved facts). Different sources use "prompt" and "context" to mean slightly different things; more on that below.
  • System prompt / user prompt — two slots some model APIs let you split a prompt into. The system prompt usually carries the app developer's instructions or persona; the user prompt usually carries what the end user typed.
  • Chat template — the exact text format (special tokens, ordering) that a specific model expects a system prompt and user prompt to be assembled into before it's fed to the model. Different models, and even different versions of the same model family, can use different templates.
  • Context length — the maximum amount of text (measured in tokens, roughly word-pieces) a model can accept as input at once.
  • Needle in a haystack (NIAH) — a test that plants one specific piece of information somewhere inside a long prompt and checks whether the model can find it, used to see how well a model actually uses a long context rather than just accepting one.
  • Chain-of-thought (CoT) prompting — asking a model to work through a problem in steps instead of jumping straight to a final answer.
  • Self-critique — asking a model to check or evaluate its own output as a separate step.
  • Prompt decomposition — breaking one big, complex prompt into a chain of smaller, simpler prompts that each handle one subtask.
  • Prompt catalog — a shared, versioned store of an organization's prompts kept separate from application code, so different applications can track, search, and choose which version of a prompt they depend on.

How it works

Here's the grounding picture before the details: a prompt isn't one solid block of text you either get right or wrong on the first try. It's assembled from a small number of parts (an instruction, maybe some examples, the actual task) that you can mix, reorder, and iterate on independently, the same way you'd revise an email before hitting send. What follows walks through what those parts are, why showing a model examples works at all, how a prompt gets physically packaged before it reaches a model, how much room you have to work with, and then a working set of best practices for using that room well.

1. What a prompt actually is

A prompt is an instruction given to a model to perform a task. That task can be as small as answering a one-line question or as open-ended as asking a model to draft a whole document. A prompt generally consists of one or more of three parts: a task description (what you want the model to do, including any role you want it to play and the format you want back), example(s) of how to do the task, and the task itself, meaning the concrete thing you actually want done right now (the question to answer, the text to summarize).

Not every prompt needs all three. A one-line question to a general-purpose assistant might just be the task, with no explicit description or examples at all. But once you're building an application rather than chatting casually, being deliberate about which of these three parts you're including, and where, is most of what "writing a good prompt" means in practice. One useful thing to know up front: which prompt structure works best isn't fixed across models. Most models tend to perform better when the task description comes first in the prompt, but that's not universal, some models seem to do better with it at the end instead, so it's worth testing structure on whichever model you're actually using rather than assuming one layout is always correct.

2. In-context learning: zero-shot vs. few-shot

Teaching a model what to do through the prompt, instead of through training, is called in-context learning. The term comes from the 2020 GPT-3 paper "Language Models Are Few-Shot Learners," which showed something that wasn't obvious beforehand: a model trained only to predict the next token could still pick up tasks like translation, reading comprehension, and simple math just from examples placed in its prompt, with no weight updates at all. Before that, a model could really only do what it was explicitly trained to do; changing its behavior meant retraining or finetuning it.

Each example you put in the prompt is called a shot. A prompt with no examples is zero-shot; a prompt with examples is few-shot (five examples would be "5-shot"). In general, showing a model more examples tends to help it perform better, but that comes at a real cost: more examples means a longer prompt, and a longer prompt means higher inference cost, plus you're bounded by the model's maximum context length. How many examples are actually worth including depends on the model and the task, and it's something you have to test rather than assume.

It's also worth knowing this isn't a fixed law: with the original GPT-3, few-shot prompting showed a big improvement over zero-shot. But in one 2023 analysis from Microsoft looking at GPT-4 and a few other newer models, few-shot only produced a limited improvement over zero-shot for the use cases studied there, suggesting that as models get better at just following plain instructions, the extra boost from examples can shrink. That said, this doesn't mean examples stop mattering everywhere: for something narrow and unusual that a model hasn't seen much of in its training data (a niche internal API, for instance), including examples in the prompt can still make a large difference. Treat "do I need few-shot here" as an empirical question for your specific model and task, not a settled rule.

3. Prompt vs. context: sorting out the terminology

You'll see "prompt" and "context" used inconsistently across the field, and it's worth naming that up front so it doesn't trip you up later. The original GPT-3 paper used "context" to mean the entire input into the model, the same thing as "prompt." Other practitioners use context to mean just the contextual information inside the prompt (the part the model needs in order to do the task), separate from the instruction itself. Some vendor documentation uses "context" to mean something closer to the task description (specifying what topics to focus on or what tone to use). None of these are wrong, they're just different conventions. For the rest of this digest, "prompt" means the whole input into the model, and "context" means the information provided so the model can perform the task, which matches how the source material for this digest defines the two terms.

4. System prompts, user prompts, and chat templates

Many model APIs let you split a prompt into a system prompt and a user prompt. A common pattern: the system prompt carries the role the model should play and the app developer's instructions, while the user prompt carries the specific question or request, often supplied at runtime. For example, a chatbot that helps people read property disclosures might get a system prompt telling it to act like an experienced real estate agent and answer succinctly, while the user prompt carries the actual uploaded document and question. Almost all generative AI applications, ChatGPT included, use a system prompt in some form, though you're not required to split things this way, you can put everything in one or the other if that works better for your case.

Under the hood, the system prompt and user prompt don't stay separate. They get combined into one final prompt following a chat template defined by whoever built the model, and that template can literally just be plain text with placeholders for the system prompt and the user's message, wrapped in special marker tokens the model was trained to recognize. Two things worth knowing: different models use different templates (and the same provider can change the template between versions of the same model family), and getting the template wrong tends to cause a silent, hard-to-spot failure rather than an obvious error, the model just performs worse without telling you why. A few concrete habits help here: make sure whatever you send follows the model's documented template exactly, double-check that any third-party tool you use is applying the right template for the model you're using, and print out the final assembled prompt before sending it so you can eyeball it.

Why would a system prompt boost performance at all, if it just gets concatenated into one prompt anyway? Two candidate reasons are described in the source material: the system prompt usually comes first in the final assembled prompt, and models may simply be better at following instructions that appear early, and some models have been deliberately trained (through post-training) to pay extra attention to whatever is in the system prompt specifically, partly because that also helps the model resist certain kinds of prompt attacks.

5. Context length and context efficiency

How much you can fit into a prompt is capped by the model's context length, the maximum number of tokens it accepts as input. This limit has grown a lot: early GPT models were capped around 1K to 4K tokens, barely enough for a college essay, while by mid-2024 some models documented context lengths in the millions of tokens, enough to fit a large codebase or thousands of Wikipedia pages. Worth flagging: these exact figures reflect where things stood as of when the source material was written, and context limits keep moving, so treat any specific number here as illustrative rather than current, and check a model's own documentation for its real limit today.

A longer context window doesn't mean every part of it gets used equally well. Research (Liu et al., 2023) found that the models tested were noticeably better at using information placed near the beginning or end of a prompt than information buried in the middle. One way people test this is a needle in a haystack (NIAH) test: plant one specific fact (the "needle") somewhere inside a long passage (the "haystack") and ask the model to retrieve it, then repeat at different positions to see where retrieval accuracy drops. A related benchmark, RULER, tests long-context handling more broadly. The practical upshot: if a model's performance clearly degrades on your own longer prompts, that's a signal to shorten them or restructure what's near the middle, not just to assume a bigger context window will always help.

6. Prompt engineering best practices

Early prompt engineering leaned on hacky tricks (specific phrasing quirks, oddly specific bribes for a "right answer") that could work on weaker, older models but tend to age poorly as models get better at just following plain instructions. The practices below are described as more durable, general techniques distilled from guidance published by multiple model providers and from teams that have shipped real generative AI applications. Even so, expect each specific model to have its own quirks on top of these general practices, so it's worth checking a model-specific prompting guide when one exists.

Write clear, explicit instructions. State exactly what you want without ambiguity: if you want a 1-to-5 score, say so; if you want the model to say "I don't know" instead of guessing, say that too. When you notice an undesirable pattern (say, the model returning fractional scores when you wanted whole numbers), that's a signal to make the instruction more explicit, not a dead end. Three techniques help here specifically: asking the model to adopt a persona (a source example found that grading the same short essay changed noticeably depending on whether the model was told to act like a strict grader versus a first-grade teacher), providing one or two examples of the response style you want (useful anytime the "right" tone or framing isn't obvious from the instruction alone), and specifying the output format explicitly, including telling the model not to add a preamble if you don't want one, and using a clear marker to signal where the model's structured output should begin so it doesn't just keep extending your input instead of answering.

Provide sufficient context. Just like a student does better on an exam with reference material at hand, a model tends to do better, and hallucinate less, when the prompt includes what it actually needs to answer accurately, rather than being left to rely only on what it happened to learn during training. Gathering that material for a given query is called context construction, and tools like retrieval pipelines and web search exist specifically for this (covered in more depth elsewhere). A related, trickier goal is restricting a model to use only the provided context, common in roleplay or simulation use cases where you don't want the model reaching outside a fictional world for its answers. Clear instructions plus examples of questions it shouldn't answer can nudge this, but since a model isn't guaranteed to follow every instruction, prompting alone isn't a reliable hard guarantee here.

Break complex tasks into simpler subtasks. Rather than one giant prompt trying to do everything, split a multi-step task into a chain of smaller prompts, each handling one subtask, and feed the outputs from earlier steps into later ones. A customer support example: one prompt classifies the intent of a request, then a second prompt (chosen based on that classification) generates the actual response. This kind of prompt decomposition tends to help performance since models are generally better at simpler instructions, and it comes with side benefits: you can monitor each intermediate output, debug one step without touching the others, run independent steps in parallel to cut latency, and each individual prompt is just easier to write. The tradeoffs: more steps usually means more model calls (though not necessarily proportionally more cost, since smaller prompts often use fewer tokens and cheaper models can sometimes handle the simpler steps), and if users don't see intermediate outputs, more steps can mean a longer wait before they see anything at all.

Give the model time to think. Chain-of-thought (CoT) prompting means explicitly asking a model to work through a problem step by step rather than jumping straight to a final answer, and it's described as one of the earliest prompting techniques shown to work broadly across different models. The simplest version just adds a phrase like "think step by step" to the prompt; a more guided version spells out the actual steps you want followed, or shows one worked example of the reasoning before asking the real question. A related technique, self-critique, asks the model to check its own output as a separate step. Both tend to improve results on reasoning-heavy tasks, but both also add latency, since the model produces more intermediate output before you see a final answer, and that can matter if your application is latency-sensitive.

Iterate on your prompts. Prompt engineering is inherently back-and-forth: as you learn how a specific model actually behaves, you revise the prompt in response. Different models have different quirks, one might be stronger with numbers, another with roleplay, one might prefer instructions up front, another at the end, so testing the same prompt across models (and reading a model-specific prompting guide, when one exists) builds a much better feel for what you're working with than guessing. As you iterate, do it systematically: version your prompts, track experiments, and evaluate any change against a fixed, standardized set of test cases so you can tell whether a prompt tweak actually helped, rather than trusting a gut feeling on one example. It's also worth evaluating a prompt change in the context of the whole system, a change that helps one subtask can still hurt overall performance.

Understand what prompt engineering tools actually do before relying on them. Tools exist that try to automate prompt optimization end to end (you specify inputs, outputs, and an evaluation metric, and the tool searches for a prompt or chain of prompts that maximizes it), and other tools use an AI model itself to write, critique, or mutate prompts. These can genuinely help, but they carry real risks worth knowing about: they often make hidden model API calls that can run up your bill fast (multiple evaluation examples times multiple prompt variations times multiple calls per prompt adds up quickly), tool developers can make mistakes (using the wrong chat template for a model, or shipping prompts with plain typos), and a tool's default prompts or templates can change without warning, adding complexity and new failure modes the more of them you stack together. A reasonable default: start by writing your own prompts by hand so you understand your model and requirements directly, and if you do use a tool, always inspect the actual prompts it produces and keep an eye on how many API calls it's generating.

7. Organizing and versioning prompts

Once you have more than a couple of prompts, it's worth deliberately separating them from your application code rather than leaving them inline, for a few concrete reasons: multiple applications can reuse the same prompt, prompts and code can be tested independently of each other, separating the two makes both easier to read, and it lets non-engineers (subject matter experts) help write and refine prompts without needing to touch code at all. A simple version of this is just keeping prompts in their own file and importing them where needed. A more structured version wraps each prompt with metadata (which model it targets, who created it, which application uses it, when) so a growing prompt library stays searchable, and some teams go further with a dedicated .prompt file format that bundles a prompt's text together with its expected input and output shape.

If prompts live in the same git repository as your application code, they get versioned automatically, but that has a real downside: if several applications share one prompt and it gets updated, every dependent application is forced onto the new version at once, since there's no way for one app to opt into staying on an older version. That's the problem a prompt catalog is meant to solve: a separate, explicitly versioned store of prompts where different applications can deliberately choose which version they depend on, complete with metadata and search, and ideally something that can tell you which applications depend on a given prompt so you know who to notify before changing it.

Why it matters

This is the foundation everything else in applied prompting sits on. Before you reach for finetuning, or build out retrieval and agent pipelines, the source material frames prompt engineering as the thing worth maxing out first, it's cheap and fast to iterate on, and a lot of production behavior (accuracy, format compliance, cost, latency) is decided by choices covered here: how many examples you show, where you put your instructions, how you split up a big task, and whether your prompts are organized well enough that a whole team can build on them without stepping on each other. It's also the ground floor for two things picked up later: this same chapter continues into defending a deployed application against people trying to manipulate its prompts, and the next chapter builds on "provide sufficient context" by covering how to actually construct that context automatically, through retrieval and tool use.

Remember this

  • A prompt is built from up to three parts: a task description, optional examples, and the task itself. Few-shot means adding examples; zero-shot means skipping them, and more examples generally help but cost more tokens.
  • In-context learning lets a model pick up a new behavior from what's in the prompt, with no retraining, but it's bounded by the model's context length and by what you're willing to pay per token.
  • Models tend to use information near the start and end of a prompt better than information buried in the middle (the needle-in-a-haystack finding), so put your most important instructions at those ends.
  • Breaking one big prompt into a chain of smaller subtask prompts usually costs more calls, but tends to be easier to debug, monitor, and sometimes even cheaper overall since smaller prompts use fewer tokens.
  • Keep prompts out of your application code, in their own file or a proper prompt catalog, so you can version, test, and share them independently of everything else.

Try it yourself

  1. Run a zero-shot vs. few-shot showdown. Pick a small task (classify sentiment, extract a structured field from messy text) and write two prompts against a real LLM API or a free playground: one zero-shot, one with two or three labelled examples. Done when: you've compared the outputs side by side and can point to at least one case where the few-shot version behaved differently.
  2. Build a tiny reusable prompt template. Write a task description with placeholders (like {{topic}} and {{tone}}) stored separately from the code that calls it, and fill those placeholders programmatically before sending the request. Done when: you can swap in a new topic or tone without editing the prompt text itself.
  3. Test system-prompt vs. user-prompt placement. Using an API with separate system and user roles, put an instruction in the system prompt and run it, then move that exact same instruction into the user prompt and run it again. Done when: you've written down whether, and how, the response changed.
  4. Run your own needle-in-a-haystack test. Assemble a few paragraphs of text, plant one made-up fact near the start in one run, in the middle in another, and near the end in a third, then ask the model to retrieve that fact each time. Done when: you have a small table showing which position(s) the model got right and which it missed.
  5. Decompose one task into a two-step chain. Take a task you'd normally solve with a single large prompt (say, "classify this message and draft a reply") and split it into two prompts run in sequence, feeding the first prompt's output into the second. Done when: you can compare the two-step version's output quality against the single-prompt version on the same input.
  6. Run a chain-of-thought A/B test. Ask a model the same multi-step reasoning or arithmetic question twice, once plain, once with "think step by step" added. Done when: you've recorded whether the step-by-step version reached a different final answer, and which one was actually correct.
