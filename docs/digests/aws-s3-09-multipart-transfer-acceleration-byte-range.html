S3 Multipart Upload, Transfer Acceleration and Byte-Range Fetches: Moving Big Objects Faster

Moving a big file to or from S3 as one long request is fragile and slow. S3 gives you three tools for that: split the upload into parts (multipart upload), shorten the network path to the bucket (Transfer Acceleration), and download just the bytes you want, in parallel (byte-range fetches). This digest explains each, what they cost you in complexity, and the cleanup you must not forget.

In one line

Multipart upload sends one object as independently retryable parts that S3 stitches together, Transfer Acceleration routes uploads through nearby CloudFront edge locations to the bucket, and byte-range fetches use the HTTP Range header to download pieces of an object, possibly many at once.

The big idea

Imagine moving house with one giant truck trip. If the truck breaks down at 90 percent, you start over. Splitting into many car trips (parts) means a breakdown only costs you one trip, and you can run several cars at once. That's multipart upload. If the road is long and bumpy, a faster route to a nearby depot helps; that's Transfer Acceleration. And when you only need the kitchen boxes, you fetch just those; that's a byte-range fetch.

These tools solve different problems: reliability and parallelism (multipart and ranges) and distance (acceleration). They also come with traps: unfinished multipart uploads quietly cost money until cleaned up, acceleration has extra charges and bucket-name restrictions, and ranges have a limit of one range per request.

Simplification label: I don't quote prices. The docs mention that extra charges can apply for Transfer Acceleration and that incomplete multipart parts are billed; I point to the pricing page instead. I also note a few places where the docs disagree on size limits.

Key terms

  • Multipart upload: uploading one object as a set of parts that S3 assembles afterwards.
  • Part: a contiguous chunk of the object's data, identified by a part number.
  • Upload ID: the identifier S3 returns when you initiate a multipart upload; required for every later step.
  • ETag: an identifier S3 returns for each uploaded part; you must send the list back to complete the upload.
  • Complete / abort: the two ways a multipart upload ends: assemble the object, or throw the parts away.
  • Checksum: a fingerprint of data used to detect corruption in transit.
  • Transfer Acceleration: a bucket-level feature that speeds long-distance transfers via CloudFront edge locations.
  • Edge location: a CloudFront point of presence close to users.
  • Accelerate endpoint: the special hostname (bucket.s3-accelerate.amazonaws.com) you use for accelerated transfers.
  • Byte-range fetch: a GET with a Range header requesting only certain bytes of an object.
  • Prefix (performance): the leading part of a key; the docs state request-rate guidelines per prefix.

How it works

0. Grounding: why single requests struggle

A single PUT or GET is one HTTP request on one connection. For small objects that's fine. For big ones, a network blip forces a restart, and one connection often can't fill the available bandwidth. The docs frame S3 as a very large distributed system, not a single network endpoint, and say the best performance comes from issuing multiple concurrent requests across separate connections (S3 has no limit on the number of connections to a bucket). Everything below is a way to do that safely.

1. Multipart upload

The docs recommend multipart upload as a best practice for objects of 100 MB or larger. Advantages they list: higher throughput by uploading parts in parallel; quick recovery (retry only the failed part); pause and resume (there is no expiry on an initiated upload, so you must explicitly finish or stop it); and starting an upload before you know the final size.

The three steps:

  1. Initiate (CreateMultipartUpload): you specify a checksum type, and any metadata you want on the object must be given here. S3 returns an upload ID. Anonymous users can't initiate multipart uploads.
  2. Upload parts (UploadPart): each with the upload ID and a part number from 1 to 10,000. Parts can go in any order and in parallel, and part numbers needn't be consecutive. Re-uploading the same part number overwrites the earlier part. Record each part's number and ETag.
  3. Complete (CompleteMultipartUpload): send the upload ID and the list of part numbers with their ETags. S3 concatenates the parts in ascending part-number order into the object, and the parts then no longer exist. The final ETag isn't necessarily an MD5 of the data.

Don't build the completion list from a listing call. The docs say to maintain your own list of part numbers and ETags rather than using the list-parts output.

The limits table (from the docs' multipart limits page): maximum object size 48.8 TiB; up to 10,000 parts; part size 5 MiB to 5 GiB (no minimum for the last part); list-parts and list-uploads each return at most 1,000 results per request. Flag: other pages say different things about maximum sizes (the console and single-GET pages mention 5 TB and 50 TB figures, and one SDK sample mentions 5 TB for multipart), so treat the limits page as the authoritative one and re-check it live.

Checksums. The docs say the SDK and console use a checksum algorithm by default, and S3 can validate integrity server-side, failing the request with BadDigest on mismatch. If you use checksums on a multipart upload, part numbers must be consecutive starting at 1, otherwise completing returns a 500 error.

Cost trap and the cleanup rule. After you initiate and upload even one part, you're billed for the stored parts until you complete or stop the upload. The docs' recommended cleanup is a lifecycle rule with the AbortIncompleteMultipartUpload action (this is the same lifecycle engine from the storage classes digest). Their JSON example:

{
  "Rules": [{
    "ID": "abort-stale-uploads",
    "Status": "Enabled",
    "Filter": {"Prefix": ""},
    "AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 7}
  }]
}

Applied with aws s3api put-bucket-lifecycle-configuration --bucket NAME --lifecycle-configuration file://lifecycle.json. The docs say this applies to existing and future uploads, doesn't affect completed uploads or delete any objects, and incurs no early-delete charge. Other cleanup facts: after stopping an upload you can't upload more parts with that ID, and in-flight part uploads can still succeed afterwards, so stop only after they finish.

Concurrency and overwrites. Several multipart uploads can target the same key. In a versioned bucket, completing one always creates a new version, and the current version is whichever upload started most recently, not whichever finished last. In an unversioned bucket other requests in between can win. To prevent overwriting an existing key, the docs point to conditional writes on CompleteMultipartUpload.

Permissions. Uploading parts needs s3:PutObject; aborting needs s3:AbortMultipartUpload; listing parts and uploads have their own actions. With SSE-KMS the caller needs kms:GenerateDataKey and kms:Decrypt on the key, as in the encryption digest.

In practice, you rarely call these by hand. The docs say the high-level SDK transfer tools and the CLI's aws s3 cp handle the splitting automatically (the docs mention it kicks in around 8 MB for copies), and the low-level API is for pausing/resuming, varying part sizes, or unknown sizes. The console upload is capped at 160 GB; larger files need the CLI or SDK.

2. Transfer Acceleration

Transfer Acceleration is a bucket-level feature to speed transfers over long distances between a client and a general purpose bucket. Data enters at a nearby CloudFront edge location and is routed to S3 over an optimized network path. The docs say it fits cases like customers uploading from around the world to one central bucket, regularly moving gigabytes to terabytes across continents, or being unable to use available bandwidth over the public internet. Extra data transfer charges might apply.

Requirements:

  • Virtual-hosted-style requests only.
  • The bucket name must be DNS-compliant and contain no periods.
  • You enable it on the bucket; the docs say it can take up to 20 minutes before speed improves. Only the bucket owner can set the state (or someone granted s3:PutAccelerateConfiguration).
  • You must use the accelerate endpoint bucket-name.s3-accelerate.amazonaws.com (or the dual-stack form for IPv6); the regular endpoint still works for ordinary transfers.
  • It's supported only in a listed set of Regions (the docs list fifteen, such as us-east-1, eu-west-1, ap-southeast-2), so check the live list.
  • The accelerate endpoint doesn't support ListBuckets, CreateBucket or DeleteBucket.

Docs' CLI shapes:

aws s3api put-bucket-accelerate-configuration \
  --bucket {bucket} --accelerate-configuration Status=Enabled

aws configure set default.s3.use_accelerate_endpoint true

The second line makes the CLI's s3 and s3api commands use the accelerate endpoint for the default profile. You can suspend with Status=Suspended, after which the accelerated endpoint stops working. The docs also offer a Speed Comparison tool that uploads to various Regions with and without acceleration; use it to check whether acceleration helps for your location, since it's not guaranteed to be faster everywhere.

3. Byte-range fetches

With the HTTP Range header on GetObject, you download only part of an object. Why bother? The docs give two reasons: multiple concurrent connections can each fetch a different range of the same object, giving higher aggregate throughput than one whole-object request; and small ranges retry faster if interrupted. The docs' CLI example:

aws s3api get-object --bucket {bucket} --key {key} \
  --range bytes=0-500 {outfile}

The range must be prefixed with bytes=. A key limit from the docs: S3 doesn't support retrieving multiple ranges in a single GET, so you issue one request per range. There's also a partNumber parameter on GET to address a single part directly. The docs' alignment tip: if you uploaded with multipart, it's best to GET in the same part sizes (or aligned to part boundaries).

The same page notes that single GETs are limited to 5 TB, so larger objects must be read with concurrent range or part-number requests. For big downloads, the docs recommend the SDK/CLI transfer managers, which can split downloads for you.

4. Related performance guidance

The performance guidelines page pulls this together: measure first; scale connections horizontally; use byte-range fetches; retry slow requests (aggressive timeouts and retries help latency consistency, since a retry is likely to take a different path); keep compute and storage in the same Region; use Transfer Acceleration for distance; and use current SDKs. The docs also state request-rate guidance of at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per prefix in a bucket, with no limit on the number of prefixes. S3 may return HTTP 503 (Slow Down) while it scales to a new sustained rate, which you can monitor with CloudWatch request metrics.

Why it matters

Backups, video, datasets and ML artifacts are all big-object workloads, and these tools are what keep them from being slow or flaky. The multipart cleanup rule is an easy cost control to forget, and the docs recommend it; consider it for any bucket that takes large uploads. Ranges also let a reader fetch only the slice of a large object it needs, rather than the whole thing.

Remember this

  • Multipart upload = initiate, upload numbered parts (in parallel), complete with a list of part numbers and ETags. Parts are 5 MiB to 5 GiB, up to 10,000 of them.
  • Uploaded parts are billed until you complete or abort; add an AbortIncompleteMultipartUpload lifecycle rule.
  • Transfer Acceleration uses a separate endpoint, needs a period-free DNS-compliant bucket name and a supported Region, and can add charges; test whether it helps you.
  • Byte-range fetches use Range, one range per request, and pair well with parallel connections and part-aligned reads.
  • The docs disagree on some size figures across pages, so check the live limits page for numbers you rely on.

Try it yourself

Projects 1 and 2 are offline. Projects 3 to 5 use the AWS CLI on a scratch bucket. The get-object --range, accelerate and lifecycle commands are copied in shape from the docs. The low-level multipart CLI commands (create-multipart-upload, upload-part, complete-multipart-upload, list-multipart-uploads, abort-multipart-upload) are listed by name in the docs but I did not read their flag details, so check the CLI reference. Multipart storage and acceleration can cost money; abort uploads and delete the bucket afterwards.

  1. Part planner (offline, ~30 min). Given an object size, choose a part size so you stay within 10,000 parts and the 5 MiB to 5 GiB limits; output the part count and last-part size. Done when it rejects sizes that can't fit and handles an exact multiple correctly.
  2. Mini multipart simulator (offline, ~1.5 hours). Split a local file into parts, "upload" them to a folder in random order with random failures and retries, record (part number, checksum), then assemble in part-number order. Done when the reassembled file's hash equals the original even with out-of-order, retried and overwritten parts.
  3. Range fetch. Upload a 1 MB file, then fetch --range bytes=0-99 with aws s3api get-object and check the output file's size. Try two ranges in one command to see that you can't. Done when you get exactly 100 bytes and understand why the docs say one range per request.
  4. Parallel download. Write a small script that fetches a larger object as 4 ranges concurrently and stitches them together. Done when the result's hash matches a normal download.
  5. Leave a mess, then clean it. Initiate a multipart upload with the low-level CLI and upload one part, list in-progress uploads, then apply the docs' AbortIncompleteMultipartUpload lifecycle JSON and also abort the upload manually. Done when the upload no longer appears in the list and you can say what would have kept billing otherwise.
