Container Insights, Lambda Insights, ServiceLens and X-Ray Tracing

Metrics tell you a number moved. Logs tell you what a component said. But in a modern application one user click can pass through a load balancer, a container, a Lambda function and a database, and the question "which hop is slow?" needs a different tool. This last concept in the track covers the opinionated "Insights" dashboards for containers and Lambda, and distributed tracing with X-Ray, including what happened to the feature called ServiceLens.

In one line

Container Insights and Lambda Insights give you ready-made metrics and logs for containers and Lambda functions, while X-Ray tracing follows a single request across all the services it touches and draws the result as a trace map.

The big idea

There are three kinds of telemetry people usually talk about: metrics (numbers over time), logs (records of events), and traces (the path of one request through many components). You've already met the first two in this track. This digest adds the third, plus two shortcuts for the first two on specific kinds of compute.

  • Container Insights collects, aggregates and summarises metrics and logs from containerised applications (on ECS, EKS, and other Kubernetes platforms) so you get cluster, node, pod, task and service views without hand-building them.
  • Lambda Insights does the same for Lambda functions, adding diagnostics like cold starts.
  • X-Ray traces requests end to end. ServiceLens was the CloudWatch feature that put traces, metrics and logs on one map; per the docs it has now been combined with the X-Ray service map into the trace map in the CloudWatch console, and CloudWatch has also added Application Signals for service-level views.

A nice thread to notice: both Insights products work by writing structured performance log events and extracting metrics from them with the Embedded Metric Format from two digests ago. This concept leans on a lot of what you've learned.

Key terms

  • Container Insights: CloudWatch's collection of metrics and logs for containerised workloads on ECS, EKS, RedHat OpenShift on AWS, and Kubernetes on EC2, including clusters on Fargate for ECS and EKS.
  • Performance log event: a structured JSON log entry, in embedded metric format, from which CloudWatch derives metrics.
  • Enhanced observability: a newer Container Insights mode that adds more dimensions and metrics (down to container level); the docs recommend it over the original.
  • Lambda Insights: a monitoring solution for Lambda that uses a Lambda extension (delivered as a layer) to collect system-level metrics and diagnostics.
  • Lambda layer / extension: a packaged add-on that runs alongside your function code.
  • Trace: all the data about one request as it moves through your application, tied together by a trace ID.
  • Segment: the data one compute resource records about its part of the work on a request.
  • Subsegment: a finer-grained piece inside a segment, such as one downstream call or one function.
  • Trace map / service graph: the picture X-Ray builds of services (nodes) and their connections (edges).
  • Sampling: tracing only a fraction of requests to control cost.
  • Annotation / metadata: extra key-value data you attach to a trace; annotations are indexed for searching, metadata is not.
  • Application Signals: a CloudWatch feature that auto-collects metrics and traces from your applications and shows services, dependencies and service level objectives (SLOs).

How it works

Grounding: why "the three pillars" need each other

Picture an online shop. An alarm says checkout latency is high (a metric). Your logs show timeouts, but from which service? You'd have to hop between log groups and guess. A trace answers it directly: it shows the single request as a timeline, with the load balancer, the checkout service, the payment call and the database call laid out and timed. The Insights products take care of the other side: making sure the basic CPU, memory and restart metrics for your containers and functions exist at all, without you writing the collection code.

1. Container Insights

From the docs: Container Insights collects, aggregates and summarises metrics and logs from containerised applications and microservices, and supports ECS, EKS, RedHat OpenShift on AWS, and Kubernetes platforms on EC2. It includes clusters on Fargate for both ECS and EKS. Besides the usual CPU, memory, disk and network, it gives diagnostic information such as container restart failures. You can set CloudWatch alarms on its metrics.

  • How it collects: data arrives as performance log events in embedded metric format. CloudWatch creates aggregated metrics at the cluster, node, pod, task and service level from them. On EKS, ROSA and Kubernetes, a containerised version of the CloudWatch agent discovers running containers in the cluster.
  • Where metrics live: for ECS, the namespace is ECS/ContainerInsights. Examples from the docs' table: CpuUtilized, CpuReserved, MemoryUtilized, MemoryReserved, NetworkRxBytes, NetworkTxBytes, RunningTaskCount, DesiredTaskCount, PendingTaskCount, RestartCount, with dimensions like ClusterName, ServiceName and TaskDefinitionFamily.
  • A log group is created for you for the performance events (the ECS setup page mentions a path of the form /aws/ecs/containerinsights/<ClusterName>/performance).
  • Cost control built in: the docs say CloudWatch does not automatically create all possible metrics from the log data; you can query the raw performance log events with Logs Insights for extra detail. Original Container Insights is charged as custom metrics and log ingestion; the enhanced observability version for EKS is charged per observation. No prices quoted here.
  • Metrics appear late: the docs note they are not visible until container tasks have been running for some time, and not before setup is complete.
  • Encryption: to encrypt this data with your own KMS key you manually enable KMS encryption on the log group; the docs say only symmetric keys are supported.

Turning it on for ECS (docs' CLI): aws ecs put-account-setting --name containerInsights --value enabled makes new clusters have it on by default, and aws ecs update-cluster-settings --cluster <cluster-name> --settings name=containerInsights,value=enabled adds it to an existing cluster. For the enhanced version, use enhanced instead of enabled. The docs add a subtle point: by default the account setting applies only to the currently authenticated user; to apply account-wide you specify the root user with --principal-arn. They also say to use an AMI with ECS agent version 1.29 or later for ECS on EC2.

2. Lambda Insights

Per the docs, Lambda Insights collects, aggregates and summarises system-level metrics (CPU time, memory, disk, network) and diagnostic information such as cold starts and Lambda worker shutdowns. It uses a CloudWatch Lambda extension supplied as a Lambda layer. When installed, the extension collects system-level metrics and emits one performance log event per invocation, and CloudWatch uses embedded metric format to extract the metrics from those events. (Two digests ago, EMF; here it is in action.)

  • Runtimes: it works with Lambda runtimes that support extensions; the docs also say the Lambda Insights agent is supported only on runtimes that use Amazon Linux 2 and Amazon Linux 2023.
  • Enabling: a one-click toggle in the Lambda console, or the CLI, CloudFormation, SAM, CDK or Serverless Framework. The CLI route in the docs has three steps: attach the managed policy CloudWatchLambdaInsightsExecutionRolePolicy to the function's execution role (aws iam attach-role-policy ...); add the extension layer with aws lambda update-function-configuration --function-name <name> --layers "<extension layer ARN>", where the ARN depends on your Region and the extension version; and, only for functions in a private subnet with no internet access, create a CloudWatch Logs interface VPC endpoint.
  • Cost: you pay for metrics and logs, plus the Lambda execution time the extension consumes, billed in 1 ms increments. No prices quoted here.

Caveat I'm adding from general knowledge, not from the page: the --layers option sets the function's whole layer list, so if your function already uses layers, include them in the same command. Check the Lambda CLI reference before running it on a function you care about.

3. X-Ray: how tracing works

The docs define X-Ray as a service that collects data about requests your application serves, with tools to view, filter and gain insights into it. For any traced request you see not only the request and response, but the calls your application makes to downstream AWS resources, microservices, databases and web APIs.

  • Segments and subsegments. Each compute resource sends a segment describing its work: host, request, response, start and end times, and issues. A segment can be broken into subsegments for downstream calls (an AWS service, an HTTP API, a SQL database) or for specific functions in your code. For services that don't send their own segments, like DynamoDB, X-Ray uses subsegments to create inferred segments, so those dependencies still appear on the map.
  • Trace ID and the tracing header. A trace ID tracks a request through your application. The first supported service the request hits adds a header named X-Amzn-Trace-Id carrying the trace ID and the sampling decision, which gets passed downstream. The docs show it looks like Root=1-5759e988-bd862e3fe1be46a994272793;Parent=53995c3f42cd8ad8;Sampled=1. They also note that clients can add this header themselves, so your app may remove it from incoming requests.
  • Sending the data. Your SDK sends JSON segment documents to the X-Ray daemon (listening for UDP traffic), which batches and uploads them; the daemon is included on Elastic Beanstalk and Lambda platforms. The CloudWatch agent (version 1.300025.0 or later) can also collect traces from OpenTelemetry or X-Ray SDKs.
  • Sampling. To control cost, the X-Ray SDK by default records the first request each second and five percent of additional requests. You can change the default rule or add rules by service or request properties, for example tracing every request that changes state while sampling low on health checks.
  • Annotations vs metadata. Annotations are simple key-value pairs that are indexed for filter expressions (up to 50 indexed per trace); metadata can be any type and is not indexed.
  • Error classes. Error is a client error (4xx), Fault is a server fault (5xx), and Throttle is a 429.
  • Retention. The docs state trace data and service graph data are retained for 30 days.

4. The trace map, ServiceLens and Application Signals

X-Ray combines nodes from every service that processed requests with the same trace ID into one service graph, shown as a trace map. In the CloudWatch console it's under X-Ray traces, Trace Map. Per the docs, nodes are outlined by colour: red for server faults (5xx), yellow for client errors (4xx), purple for throttling (429). Selecting a node or edge shows metrics, response-time distribution, traces and, for supported nodes, related logs. The docs also say the map can display up to 10,000 nodes, supports cross-account tracing, and connects traces across event-driven apps that use SQS and Lambda.

What happened to ServiceLens? The tracker lists ServiceLens as part of this concept. The docs page I fetched at the ServiceLens address returned the X-Ray trace map page, which states that "the X-Ray service map and CloudWatch ServiceLens map are combined into the X-Ray trace map within the Amazon CloudWatch console." So, as of these docs, ServiceLens as a separate feature has been merged into the trace map. Treat older tutorials that say "open ServiceLens" as pointing at this combined experience.

Application Signals is the newer layer. The docs say it automatically collects metrics and traces from applications on EC2, ECS and Lambda (and EKS), shows call volume, availability, latency, faults and errors, discovers an application topology map, and lets you define and track service level objectives (SLOs). It supports Java, Python, Node.js and .NET applications. Using it incurs charges, and it works together with RUM and Synthetics canaries from the previous digest. This digest only introduces it.

Simplification: I'm treating "metrics, logs, traces" as three separate signals. The docs show them linked: select a point on a graph in Application Signals to see correlated traces, and use "View logs" from a trace map node.

5. Picking the right tool

"Is my ECS or EKS cluster healthy, and how are tasks and pods using resources?" Container Insights.

"Why is this function slow, how much memory does it really use, how often are cold starts?" Lambda Insights.

"Where in the request path is the time or the error?" X-Ray traces and the trace map.

"Are my services meeting their targets?" Application Signals with SLOs.

Simplification: they overlap, and you can enable several at once. The docs also note Application Signals isn't required to use Synthetics or RUM.

Why it matters

As soon as an application has more than one moving part, "check the CPU graph" stops being enough. These tools provide the structure for diagnosing distributed systems: the cluster-level view, the function-level view, and the request-level view. They also close the loop on the whole track: metrics from namespaces and dimensions, alarms on them, logs and queries over events, dashboards, agents and EMF to produce the data, EventBridge to react, canaries and RUM to test from outside, and now traces to follow one request inside.

Remember this

  • Container Insights and Lambda Insights both work by emitting performance log events in embedded metric format, from which CloudWatch extracts metrics.
  • Container Insights covers ECS, EKS, ROSA and Kubernetes on EC2 (incl. Fargate); Lambda Insights uses an extension layer on the function.
  • A trace follows one request via a trace ID in the X-Amzn-Trace-Id header; it is made of segments and subsegments.
  • X-Ray's default sampling is the first request each second plus five percent of the rest; data is kept 30 days.
  • ServiceLens's map is now merged into the X-Ray trace map in the CloudWatch console; Application Signals adds service-level views and SLOs.

Try it yourself

  1. Lambda Insights on a hello-world function. Create a tiny function, attach the managed policy to its role, add the extension layer for your Region (look up the ARN in the docs' version list), invoke it a few times. Done when: you find metrics in the Lambda Insights namespace and a performance log event in the matching log group, and can explain how the first became the second.
  2. Read a performance event. Open one of those events in Logs Insights. Done when: you've spotted the _aws block from the EMF digest and can name the namespace, dimensions and at least two metric fields.
  3. Container Insights on a small ECS cluster. Run aws ecs put-account-setting --name containerInsights --value enabled (mind the principal-arn caveat), launch one tiny service, wait several minutes. Done when: RunningTaskCount shows under ECS/ContainerInsights for your cluster and you've put an alarm on RunningTaskCount dropping to zero. Delete the cluster afterwards.
  4. Turn on active tracing. Enable X-Ray active tracing on your Lambda function (console toggle), invoke it, and open the trace map under X-Ray traces in CloudWatch. Done when: you can see your function as a node and open one trace's timeline.
  5. Break something and find it. Make the function call a non-existent endpoint or throw an error on purpose. Done when: the node outline changes colour and you've used "View logs" or the trace timeline to find the cause.
  6. Sampling arithmetic. On paper: with the default rule (first request each second plus five percent of additional requests), roughly how many traces per minute would a service handling 10 requests per second produce? Show your reasoning, state it is an estimate, and compare with a rule that traces everything. Done when: you can explain why the default is called conservative in the docs.
