AI · CH.6 DIGEST (PART 2, FINAL)

Agents: Tools, Planning, Failure Modes and Memory

Part 1 ended on a hint: a retriever and a SQL runner are both things a model can call to go get information it doesn't have. This part follows that thread all the way. We'll look at what makes something an agent, what tools it can use, how it plans and checks its own work, the new ways agents fail (and how to measure them), and the memory system that holds it all together. We finish with the chapter's own wrap-up. The author is upfront that the agents section is a best-effort framework for a young field, so I've flagged where things are opinion or still open.

In one line

An agent is a model that can look at an environment and take actions in it through tools, with the model itself acting as the planner that decides what to do next, checks the results, and keeps track of what it has seen.

The big idea

A plain model can do one thing: turn input into output (text in, text out). Give it tools and a loop and it can do much more: look something up, run code, query a database, send an email, then look at what happened and decide the next move. That's the agent pattern. The catch is that every extra capability is also an extra way to fail. Agents make multi-step decisions, so small errors can pile up, and tools that change things (write actions) can cause real damage. So most of the engineering here is about three questions: which tools to hand over, how to get a reliable plan out of the model, and how to measure the new kinds of failure. Memory is the supporting piece, because all of this generates far more information than fits in one prompt.

Key terms

  • Agent: anything that can perceive an environment and act on it. Here, a model plus the environment it works in plus the actions (tools) it can take.
  • Environment: the world the agent operates in, set by the use case (a game, the internet, a computer's terminal and files, a database).
  • Tool: a capability the agent can invoke, usually a function (search, calculator, SQL runner, email API).
  • Tool inventory: the full set of tools an agent is allowed to use.
  • Read-only action: an action that lets the agent perceive without changing anything (look up a record, read an email).
  • Write action: an action that changes the environment (delete a row, send an email, start a bank transfer).
  • Planner: the part that decides which steps to take. In a foundation-model agent, the model itself.
  • Task, goal, constraint: a task is defined by what you want (the goal) and the limits it must respect (constraints, such as a budget or a deadline).
  • Plan / task decomposition: a roadmap of manageable steps for a task. Producing one is also called decomposing the task.
  • Reflection: the agent (or a second component) evaluating a plan, a step's result, or the final outcome, to spot mistakes.
  • Error correction: acting on what reflection found, usually by generating a new plan.
  • Function calling: the common name for a model API feature where the model can ask to invoke one of your declared tools, naming the function and its arguments.
  • Control flow: the order in which a plan's steps run. Sequential, parallel, if-statement, and for-loop are the four kinds covered.
  • Intent classifier: a prompt or small model that works out what the user is actually trying to do, which helps pick tools and reject out-of-scope requests.
  • ReAct: a pattern that interleaves reasoning and acting: think, act, observe, repeat until done.
  • Reflexion: a framework that splits reflection into an evaluator (judges the outcome) and a self-reflection step (works out what went wrong), then tries a new plan.
  • Ablation study: removing one component (here, a tool) and measuring how much performance drops, to learn whether it earns its place.
  • Planning failure / tool failure / efficiency failure: the three families of agent-specific problems: a bad plan, a right tool giving a wrong result, and a correct but wasteful run.
  • Internal knowledge: what the model absorbed in training. Doesn't change unless the model is updated.
  • Short-term memory: the model's context window for the current task. Fast, but limited in size.
  • Long-term memory: external storage the model reaches by retrieval, which persists across tasks.
  • Memory management / memory retrieval: deciding what to store or drop, versus fetching what's relevant from long-term storage.
  • FIFO (first in, first out): a simple eviction rule where the oldest items are the first to be removed.
  • Prompt-based method: anything that improves results purely through the model's inputs (prompts, context, tools) without changing the model's weights. RAG and agents both qualify.

How it works

Grounding first. Think about how you'd get a very smart new colleague to help with something messy, like "figure out why last month's signups dropped." You wouldn't hand them one sheet of paper and demand a single answer. You'd give them access (the dashboard, the database, the team chat), they'd form a rough plan, poke at the data, notice something odd, change direction, and keep notes so they don't redo work. An AI agent is that same shape: access (tools), a way of deciding what to do (planning, checking), and notes (memory). Everything in this part is one of those three, plus the question "how do I know it's doing well?" (evaluation). I'll take them in that order, starting with what an agent actually is.

1. What an agent is, and why it needs a stronger model

The definition is deliberately broad: an agent is anything that can perceive its environment and act upon it. Two things characterize it: the environment it lives in, and the set of actions it can take. The environment comes from the use case. For a game-playing agent it's the game. For a web-scraping agent it's the internet. For a coding agent it might be a computer's terminal and file system, with actions like "search files," "open a file," and "edit lines."

Actions come from tools, and the two constrain each other. The environment decides which tools even make sense (in a chess game the only sensible actions are legal chess moves), while the tool inventory limits where the agent can operate (an agent whose only skill is swimming is stuck in water). Many apps you already use are agents with a small toolbox: a chat assistant that can search the web, run code, and generate images qualifies. The chapter also points out that a RAG system is itself a simple agent, with the retrievers and SQL runner as its tools.

In an AI agent, the model is the brain: it takes in the task plus feedback from the environment, plans a sequence of actions, and judges whether the job is done. Here's a made-up example in my own words. A bookshop owner asks, "Will I sell out of the new cookbook before the next shipment?" A tool-using agent could work like this:

  1. Reason: "I need current stock and recent sales rate."
  2. Call a stock-lookup tool. Observe: 42 copies left.
  3. Call a sales-history tool. Observe: sales numbers for the last four weeks.
  4. Reason: "The last four weeks include a holiday spike, so that rate is misleading. I need an ordinary-week figure too."
  5. Call the sales-history tool again for a normal period, then write an answer.

Notice the agent decided to fetch more data after looking at the first result. That "look, think, act again" loop is the heart of it.

Why agents usually need a more capable model than a one-shot task. Two reasons are given. First, compound mistakes: a task with many steps multiplies the chance of an error. If each step is right 95% of the time, ten steps in a row come out right about 60% of the time, and a hundred steps about 0.6%. That's a simplification: it assumes each step succeeds or fails independently and that any single miss ruins the run. Real agents can catch and repair some of their own slips (that's what reflection is for), so treat 60% as an illustration of the pressure, not a prediction. Second, higher stakes: with tools that act, any failure can have bigger consequences. Long tasks also cost time and money, which the autonomy is meant to pay back by saving human time.

2. Tools: what to hand the agent

An agent doesn't strictly need tools, but without them it's limited to whatever one thing the bare model can do (text models make text, image models make images). Tools let it both perceive and act. Actions that only observe are read-only; actions that alter the environment are write actions. That split matters a lot for safety, as you'll see. The chapter groups tools into three categories.

Knowledge augmentation. Tools that fetch context, the same job as RAG. Text and image retrievers and SQL runners from Part 1 count, and so do things like an internal people search, an inventory API, a Slack or email reader. Web browsing is a big one here (the chapter uses it as an umbrella for any internet-reaching tool: search APIs, news APIs, GitHub APIs, social media APIs). It keeps a model from going stale, meaning its training data is out of date, so it can't answer about this week's weather, news, or flight status without help. The trade-off the author flags: the internet is messy, so choose which internet APIs you connect with care.

Capability extension. Tools that patch a model's known weak spots. Models are unreliable at exact arithmetic, so a calculator beats trying to train the skill in. Other cheap helpers include a calendar, time zone converter, unit converter, and a translator for languages the model handles poorly. A code interpreter is the heavyweight version: the model writes code, runs it, and reads the results or the error, which lets an agent act as a coding assistant, data analyst, or research assistant. The chapter warns that automatic code execution brings the risk of code injection (covered in Chapter 5's defensive prompting material), so sandboxing and proper security matter. Tools can also make a single-modality model effectively multimodal: a text-only model can call an image generator, an image captioner, a transcription tool, or OCR for PDFs. As a data point, the chapter cites the Chameleon paper, where an agent with 13 tools beat the same base model alone on several benchmarks (the chapter reports an 11.37% improvement over the best published few-shot result on ScienceQA, and a 17% accuracy improvement on TabMWP). Treat those as one paper's results on those benchmarks, not a general guarantee.

Write actions. Tools that change things: a SQL runner can drop a table, an email API can send a reply, a banking API can start a transfer. They unlock whole workflows (research a lead, draft and send a first email, read the reply, update the records). They also raise the stakes. The chapter's analogy is good: you wouldn't give a new intern the power to delete the production database, and you shouldn't give an unreliable AI the power to move money. Trust in both capability and security has to be earned, and the system has to be protected from people trying to manipulate it into harmful actions. The author's stance isn't "never let agents act," it's that rigorous safeguards need to come with the autonomy. A practical consequence the chapter returns to later: define, per action, how much automation is allowed.

A quick sorting exercise (my own example). Imagine an agent for a small online shop. Sort these into read-only or write: get_order_status (read), search_help_articles (read), issue_refund (write), update_shipping_address (write), send_apology_email (write). Three out of five can change the real world. That's a hint for where to put approval gates.

3. Function calling: how a model "uses" a tool

A model only produces text. So how does it use a tool? Through function calling, the name many model providers use for their tool-use feature. Details differ by provider, so the chapter describes the general shape (and says to consult your provider's docs for specifics):

  1. Create a tool inventory. Declare each tool you might want used: its entry point (the function name), its parameters, and documentation saying what it does and what the parameters mean.
  2. Say which tools are allowed for this query. Many APIs let you choose per request, and some add a mode setting: required (the model must use at least one tool), none (no tools), or auto (the model decides).

Then, given a user question, the model's reply isn't prose. It's a structured request along the lines of "call function X with arguments Y." Your code then runs that function and feeds the result back so the model can write the final answer. The model proposes; your program executes. The chapter notes that some function-calling APIs make sure only declared functions get generated, but that doesn't guarantee the argument values are right. Its practical tip is worth underlining: always have the system report the parameter values it used for each call, and inspect them.

4. Planning: from a task to a roadmap

A task has a goal and constraints. "Organize a team offsite" is the goal; "under a fixed budget, in one city, on specific dates" are constraints. Complex tasks need a plan, a roadmap of steps, and good planning means understanding the task, weighing options, and picking the most promising one. The chapter admits planning is a huge field and only skims the surface.

Order and choice of steps matter for efficiency, not just correctness. Take "how many startups with no revenue have raised a large round?" You could find all no-revenue companies and then filter by funding, or find the heavily funded ones and then filter by revenue. Both are correct, but one starts from a much smaller pile, so it's far cheaper. A good planner picks the cheaper path.

Decouple planning from execution. You could prompt a model to think step by step and then immediately run every step in one go. The danger: if it invents a thousand-step plan that doesn't reach the goal, it may burn hours of time and API spend before anyone notices. So the chapter recommends generating a plan first, validating it, and only then executing. Validation can be cheap heuristics (reject plans that use a tool the agent doesn't have; reject plans longer than some step cap you choose) or an AI judge that critiques the plan. A bad plan goes back to the planner for another try; a good one gets executed, and the outputs are evaluated again. Plans don't have to cover the whole task; they can cover one subtask at a time. To save time you can generate several candidate plans in parallel and have an evaluator pick one, which trades extra cost for lower latency.

This gives you three components (generate, validate, execute). If you think of each as its own agent, that's a multi-agent system, and the chapter notes that most real agentic workflows end up that way.

Intent matters. Planning needs to understand what the user is really after, so agents often use an intent classifier (another prompt or a small trained classifier). Knowing the intent helps choose tools: a billing question probably needs a payments lookup, while "how do I reset my password" needs documentation retrieval. A useful extra class is IRRELEVANT, so the agent can politely decline out-of-scope requests instead of wasting compute searching for impossible solutions.

Humans in the loop. Humans can supply a high-level plan for tasks the agent struggles to plan, approve a plan, or personally execute risky steps (updating a database, merging a code change). That only works if you clearly define the automation level allowed for each action.

Putting it together, solving a task typically looks like: (1) generate a plan, (2) reflect on the plan and replace it if bad, (3) execute, (4) reflect on the outcomes, correct mistakes, and replan if the goal isn't met. You've met the ingredients before: "think step by step" asks a model to decompose, "check whether your answer is correct" asks it to reflect.

5. Can foundation models actually plan?

This is flagged as an open question, so I'll present both sides without picking one. Some prominent researchers argue that autoregressive language models (the kind that produce one token at a time, left to right) can't truly plan. One critique is that what looks like a plan is general planning knowledge pulled out of the model, which can look reasonable and still fail once you try executing it. The chapter's own take is that the evidence is mostly anecdotal, and it's unclear whether models are fundamentally unable or we simply haven't learned to use them well.

The reframing that helped me: planning is a search problem. You explore paths toward a goal, predict how each will turn out, and pick the most promising, sometimes concluding no path exists. Search often needs backtracking: try action A, find yourself somewhere unpromising, return and try B. The argument "left-to-right models can't backtrack" is countered in the chapter: a model can notice a path isn't working and revise it, or just start over. A second point: to plan well you need to know not only the available actions but what state each action leads to (if turning right means falling off a cliff, you skip it). That suggests prompting only for a list of actions, as plain chain-of-thought does, may not be enough, and the chapter mentions a paper arguing a model can predict outcomes well enough to plan with its own internal "world model." Even if a model can't plan alone, it can be one part of a planner, for example paired with a search tool and a way to track state.

Side note on reinforcement learning (RL). RL has long used the word agent too. The practical difference is where the planner comes from: an RL agent's planner is trained by an RL algorithm (often time-consuming and resource-heavy), while a foundation-model agent uses the model itself, which you prompt or finetune. Nothing stops you combining them, and the author suspects the two will merge over time. That last part is a prediction, not a fact.

6. Generating plans in practice

The simplest plan generator is a prompt. You list the available actions, state that the plan must be a sequence of valid actions, show a couple of examples, and put the task at the end. The chapter stresses its sample prompt is for illustration; real ones are more elaborate, and the plan format (a list of function names whose parameters get filled in as you go) is just one of many ways to structure control.

Parameters are the slippery part. Exact argument values are often unknowable in advance because they come from earlier tool outputs (a date tool returns today's date, and the next step's date range is computed from it). Sometimes a request is simply under-specified ("average price of the best sellers": how many? this week or all time?), so the model has to guess, and guesses can be wrong. Since both the sequence and the parameters are model-generated, both can be hallucinated: calling a function that doesn't exist, or a real one with wrong arguments. The listed ways to improve planning are all familiar: better system prompt with more examples, clearer tool and parameter descriptions, simpler tool functions (split a complex one in two), a stronger model, or finetuning for plan generation.

Planning granularity. A plan can be zoomed out (quarter by quarter) or zoomed in (week by week). The trade-off: detailed plans are harder to produce but easier to run, while high-level plans are easy to produce but hard to execute. Hierarchical planning sidesteps it: plan coarsely first, then expand each part. A second granularity question is naming. If your plan uses exact function names and a tool gets renamed, you have to update prompts and examples (and re-finetune if you trained on old names). Plans written in plain language ("get the current date," "look up the top seller") survive tool changes and are closer to what the model is best at, so hallucination is likely lower. The cost is that you then need a translator to turn each plain-language step into an executable call. Translating is an easier job than planning, so a weaker model can often do it.

Control flows beyond a straight line. The order in which steps run is the plan's control flow. Four kinds are described:

  • Sequential: B after A, usually because B needs A's output.
  • Parallel: A and B at the same time. Example: after getting a list of items, look up each item's price simultaneously.
  • If statement: pick B or C based on what the previous step returned.
  • For loop: repeat a step until a condition is met.

In ordinary software those conditions are exact. In an agent, the model decides them, so non-sequential plans are harder to generate and to translate into commands. Practical tip: when comparing agent frameworks, check which control flows they support. Parallel execution can cut the latency users feel, such as when visiting ten websites.

7. Reflection and error correction

Reflection can happen at several points: when the request first arrives (is this even feasible?), after a plan is made (does it make sense?), after each step (am I on track?), and after the whole plan (did I finish the job?). The chapter's phrasing: reflection isn't strictly required for an agent to run, but it's close to required for an agent to succeed. Reflection produces insights that uncover errors, and error correction fixes them, so they go hand in hand. It can come from the same agent via a self-critique prompt, or from a separate component such as a scorer (a model that outputs a score for each outcome), or from a second agent that evaluates the first.

ReAct (from a 2022 paper) popularized interleaving reasoning and acting. At each step the agent writes a thought (planning), takes an action, reads the observation (reflection), and loops until it decides it's finished. The prompt usually shows examples of the format: Thought 1, Act 1, Observation 1, and so on, ending in a Finish action with the answer. Reflexion (2023) separates reflection into two modules, an evaluator and a self-reflection step that writes down what went wrong, then proposes a new attempt (the paper calls a plan a "trajectory"). Picture a coding task where the evaluator finds the code fails a third of the tests, and the self-reflection step realizes the code never considered inputs where every number is negative. The next attempt accounts for that. This is how agents can "learn from mistakes" within a task.

Reflection is relatively easy to add and can produce surprisingly large gains compared with the effort. The cost is latency and money: thoughts and observations are extra tokens, and both ReAct and Reflexion lean on plenty of examples in the prompt, which raises input cost and uses up context space that could hold other information.

8. Choosing tools

There's no foolproof recipe. Published agents range from a handful of tools (one finetuned model learned five; Chameleon used 13) to attempts at choosing among 1,645 APIs. More tools means more capability but also more to learn and use well, and longer tool descriptions that may not fit in context. The chapter's advice is to experiment:

  • Compare the agent's performance with different tool sets.
  • Run an ablation: remove a tool and see if performance drops. If it doesn't, drop the tool.
  • Find tools the agent keeps getting wrong. If prompting and even finetuning can't make a tool usable, replace it.
  • Plot how often each tool gets called to see which are popular and which are ignored.

One study the chapter cites found two patterns: different tasks lean on different tools (a science question set used knowledge retrieval a lot more than a table-math set), and different models show different tool preferences (two models picked different mixes). So tool choice depends on the model and the task, not just the environment. When evaluating agent frameworks, check which planners and tools they support, and how easy it is to add new tools later, since your needs will change.

Two research ideas on agents building tools: tool transition analysis asks, after tool X, how likely is tool Y? Pairs that always appear together could be merged into one bigger tool. And a system called Voyager keeps a skill library: when a newly written skill (a small program) proves useful, it's saved and can be retrieved for later tasks, conceptually like adding to the tool inventory. These are research directions, not settled practice.

9. How agents fail, and how to measure it

Evaluation is about catching failures, and the more an agent does, the more places it can go wrong. On top of the general failures from earlier chapters, agents have their own, in three families: planning, tools, and efficiency. The method is the same throughout: list the failure modes, then measure how often each happens. (The author also mentions public agent benchmarks and leaderboards for function calling, agent evaluation harnesses, and travel planning; names and availability change, so check what exists when you need one.)

Planning failures. The most common kind is a tool-use mistake. There are three flavors:

  • Invalid tool: the plan names a tool that isn't in the inventory.
  • Valid tool, invalid parameters: right tool, wrong argument list (too many, too few, wrong names).
  • Valid tool, incorrect parameter values: right tool, right shape, wrong number or string (for instance converting 100 when the user said 120).

Then there's goal failure: the plan doesn't solve the task, or solves it while breaking a constraint (a trip to the wrong city, or the right city way over budget). Time is a constraint people forget: a grant proposal finished after the deadline is useless. And there's a sneaky one caused by faulty reflection: the agent is convinced it's done when it isn't (asked to seat 50 guests in 30 rooms, it places 40 and declares success).

To measure planning, build a dataset where each example is a (task, tool inventory) pair, have the agent generate several plans per task, and compute things like: what share of plans are valid; how many tries it takes on average to get a valid plan; what share of tool calls are valid; how often invalid tools are called; how often valid tools get invalid parameters; how often they get wrong values. Then read the failures for patterns: which task types, which tools. If one tool keeps tripping the agent, try better prompting, more examples, or finetuning, and if all else fails, swap it for an easier tool.

Tool failures. The agent picked the right tool, but the output is wrong: a captioner describes the image incorrectly, a SQL generator writes bad SQL, or the translator that converts plain-language steps into commands slips. Another cause is a missing tool, such as needing live prices with no internet access. Each tool should be tested independently, and the advice is to print every tool call and its output so you can inspect them. For missing tools, watch which domains the agent fails in and ask human experts which tools they'd reach for.

Efficiency. A correct run can still be wasteful. Track average steps per task, average cost per task, and how long each action takes (spotting slow or pricey ones). Compare against a baseline, which may be another agent or a human. One caution from the chapter: human efficiency and AI efficiency aren't the same thing. Visiting a hundred web pages is slow for a person who opens one at a time but may be trivial for a program that fetches them all at once.

10. Memory: how an AI app holds on to information

RAG and agents both handle more information than a prompt can hold. A RAG system's retrieved context grows across turns, and an agent has to keep instructions, examples, tool lists, plans, tool outputs, and reflections. Memory means the mechanisms that let a model retain and use information. The chapter describes three:

  • Internal knowledge. What the model learned in training. It's available on every query and only changes if the model itself is updated.
  • Short-term memory. The context window. Previous messages can be added to it, which is how a conversation stays coherent. It's fast but small, and it doesn't persist across tasks, so it should hold what matters for the task at hand.
  • Long-term memory. External data reached by retrieval, as in RAG. It persists across tasks, and unlike internal knowledge you can delete things from it without touching the model.

A human parallel: knowing how to breathe is internal knowledge, the name of the person you just met is short-term, and books, notes, and computers extend long-term memory. The rule of thumb for where to put information is by how often it's needed: what's essential for all tasks belongs in the model itself (via training or finetuning), rarely needed material belongs in long-term memory, and short-term memory is for immediate, task-specific stuff.

What a memory system buys you. The chapter lists four benefits. (1) Handling overflow inside a session: a long task piles up more than the context holds, so the excess goes to long-term storage. (2) Persisting across sessions: a coaching assistant that makes you re-explain yourself every time is annoying, and one that remembers your preferences can personalize its suggestions. (3) Consistency: if you ask a person to rate something twice, they're more consistent if they remember their first answer, and a model that can see its past answers can calibrate. (4) Structural integrity: pasting a table into a prompt doesn't guarantee the model treats it as a table, whereas a memory system that stores structured data (a spreadsheet of leads, a queue of pending actions) keeps the structure.

Two jobs: management and retrieval. Retrieval from long-term memory works like the RAG retrieval from Part 1, so the chapter focuses on management, which is basically two operations: add and delete. Long-term storage is cheap and expandable, so deleting from it may be unnecessary. Short-term memory is capped by the context length, so it needs a policy. One way to think about it: reserve a share of the context for retrieved long-term items (say 30%, purely as an example), and the rest is the short-term budget. When short-term fills up, the overflow moves to long-term storage.

Eviction strategies borrow from data systems in general. The simplest is FIFO: the oldest content is removed first. Some API providers and frameworks effectively do this by dropping the start of long conversations or keeping only the last N messages or tokens. It's easy but it bakes in an assumption that early content matters least, and that can be badly wrong. Often the first message states the whole purpose of the conversation. (The chapter notes small talk can be the exception.) Smarter approaches cut redundancy: summarize the conversation (with the same model or another), track named entities, or go further, as one research team did with a classifier that decides, sentence by sentence, whether the memory, the summary, or both should contribute to the new memory. Another team had the agent reflect after each action and decide whether the new information should be inserted, merged with existing memory, or should replace outdated, contradicting memory. What to do with contradictions depends on the use case: some keep the newest, some ask a model to judge, and some keep both because different perspectives can help even though they can confuse the agent.

11. The chapter's wrap-up

The summary stitches the whole chapter together, and it's a nice recap of both parts. RAG came first: many tasks need more background knowledge than a context window holds, and RAG is a two-step process (retrieve, then generate) whose success depends on retriever quality. Term-based retrievers like BM25 and Elasticsearch are light and make strong baselines; embedding-based retrievers cost more compute but can do better, and they're powered by vector search, the same technology behind search and recommendation systems.

Then the link: RAG is a special case of the agent pattern, where the retriever is one tool. Both let a model get around its context limit and stay current, but agents go further. An agent is defined by its environment and tools; the model is the planner, and complex tasks need a strong one, helped along by reflection and memory. More tools means more capability, but also potentially more catastrophic failures as automation grows, so tool use exposes agents to the security risks from the prompting chapter and needs rigorous defenses. Finally, both patterns are prompt-based: they improve results purely through what goes into the model, without changing it. The next chapter turns to changing the model itself (finetuning).

Why it matters

Almost every "AI assistant that does things" product is some arrangement of the parts above, so the vocabulary here lets you read a new agent framework or product announcement and ask good questions: what's the tool inventory, which tools write, who validates plans, what control flows are supported, what gets remembered, and how is it measured? It also reframes debugging. When an agent misbehaves, "the model is bad" is rarely the whole story. It might be a missing tool, a vague tool description, a wrong parameter value, a plan that was never validated, or a memory policy that quietly evicted the user's original goal. Each of those is something you can measure and fix, which is far more encouraging than hoping a bigger model will cure everything.

Cloud builders will recognize the pattern too: function calling plus approval gates for risky actions is the same instinct as least-privilege permissions. Give the agent the narrowest set of write abilities it needs, and put a human in the path of the dangerous ones.

Remember this

  • An agent is a model plus an environment plus tools, with the model acting as planner. A RAG system is the simple case where retrieval is the tool.
  • Read-only tools let an agent look; write tools let it change things. Most of the safety thinking is about the second kind, including per-action approval levels.
  • Plan first, validate the plan, then execute, and reflect on results. Reflection is cheap to add and often pays off, but costs extra tokens and latency.
  • Agents fail in three families (planning, tools, efficiency). Define each failure mode, log every tool call with its arguments, and measure how often each happens.
  • Memory has three layers (the model, the context, external storage). Eviction policy matters: naive oldest-first can throw away the one message that stated the goal.

    print(f"per-step {p:.0%} ->", " | ".join(row))
    Done when: you can explain, using your own table, why raising per-step accuracy from 95% to 99% matters more over 50 steps than over 3, and you've stated the independence assumption your numbers rely on.
  2. Tool-call checker. Start from this validator, then add a third check for wrong parameter values by giving each test case an expected answer. 
    # Classify each planned tool call the way the failure-mode list does.
TOOLS = {
    "get_date": [],
    "c_to_f": ["celsius"],
    "top_sellers": ["start", "end", "count"],
}

def check_call(name, args):
    if name not in TOOLS:
        return "invalid tool"
    if sorted(args) != sorted(TOOLS[name]):
        return "valid tool, invalid parameters"
    return "ok so far (values still unchecked)"

plan = [
    ("get_date", {}),
    ("web_search", {"q": "weather"}),
    ("c_to_f", {"celsius": 30, "unit": "F"}),
    ("c_to_f", {"celsius": 30}),
]
for name, args in plan:
    print(f"{name}{args} -> {check_call(name, args)}")
    Done when: a list of at least 12 hand-written planned calls is sorted into the three failure types plus "ok", and you report the share in each bucket.
  3. A tiny think-act-observe loop. The script below fakes the model with a scripted list so you can see the plumbing. Replace the fake with a real model call if you have access, and add a second tool. 
    # A scripted "model" drives a ReAct-style loop, so you can see the plumbing
# without any API. Swap fake_model for a real model call later.
def c_to_f(celsius):
    return celsius * 9 / 5 + 32

TOOL_FUNCS = {"c_to_f": c_to_f}

script = iter([
    {"thought": "I need Fahrenheit for 30 C.", "act": ("c_to_f", {"celsius": 30})},
    {"thought": "The tool gave 86.0, which answers it.", "act": ("finish", {"answer": "30 C is 86 F"})},
])

def fake_model(history):
    return next(script)

def run_agent(task, max_steps=5):
    history = [("task", task)]
    for step in range(1, max_steps + 1):
        out = fake_model(history)
        name, args = out["act"]
        print(f"Thought {step}: {out['thought']}")
        print(f"Act {step}: {name}({args})")      # always log the arguments
        if name == "finish":
            return args["answer"]
        if name not in TOOL_FUNCS:
            history.append(("observation", f"error: no tool named {name}"))
            continue
        result = TOOL_FUNCS[name](**args)
        print(f"Observation {step}: {result}")
        history.append(("observation", result))
    return "stopped: hit the step limit"

print(run_agent("What is 30 C in Fahrenheit?"))
    Done when: your loop logs every action with its arguments, stops at a step limit you chose, and handles a call to a tool that doesn't exist without crashing.
  4. Approval gate for write actions. Tag each tool read or write and block writes until a human approves. Extend it to a log of every request and its decision. 
    # Tag each tool as read or write, and require approval before any write runs.
TOOLS = {
    "get_order_status": {"writes": False, "fn": lambda order_id: f"order {order_id}: shipped"},
    "issue_refund":     {"writes": True,  "fn": lambda order_id: f"refunded order {order_id}"},
}

def run_tool(name, args, approve):
    tool = TOOLS[name]
    if tool["writes"] and not approve(name, args):
        return "blocked: a human said no"
    return tool["fn"](**args)

def always_no(name, args):
    print(f"  approval requested for {name}{args}")
    return False

print(run_tool("get_order_status", {"order_id": 7}, always_no))
print(run_tool("issue_refund", {"order_id": 7}, always_no))
print(run_tool("issue_refund", {"order_id": 7}, lambda n, a: True))
    Done when: you have five tools (at least two writes), a printed audit log, and one test showing a write was blocked and another showing it ran after approval.
  5. Memory eviction showdown. Compare plain oldest-first eviction with a version that pins the opening goal. Then add a third strategy that replaces old messages with a one-line summary (hand-written is fine). 
    # Compare two ways of shrinking a chat history to fit a word budget.
history = [
    "GOAL: quiz me on VPC routing, one question at a time, wait for my answer",
    "ok",
    "route tables decide where traffic goes",
    "next one please",
    "what does a NAT gateway do",
    "next one please",
]

def words(msgs):
    return sum(len(m.split()) for m in msgs)

def fifo(msgs, budget):
    kept = list(msgs)
    while words(kept) > budget:
        kept.pop(0)                  # the oldest message goes first
    return kept

def fifo_keep_first(msgs, budget):
    first, rest = msgs[0], list(msgs[1:])
    while words([first] + rest) > budget and rest:
        rest.pop(0)                  # evict the oldest AFTER the pinned goal
    return [first] + rest

print("plain FIFO     :", fifo(history, 20))
print("pin the goal   :", fifo_keep_first(history, 20))
    Done when: you've built a 10-message chat where plain oldest-first loses something important, and you can point to which strategy kept it and what it cost you in space.

Pretend to remove each tool in turn and count tasks that break. Done when: you've identified at least one tool that no task needs (a candidate to drop) and one tool whose removal breaks the most tasks, and you can say what real data you would log to confirm it.
