Performance Schema: Instruments, Consumers, and Getting It Configured

Ch.2 taught you to watch the outside of MySQL, the SLIs and SLOs customers feel. This chapter goes inside the server itself, and Part 1 covers the two ideas everything else is built on, plus how you actually turn the thing on.

The big idea

Ch.2 was about watching MySQL from the outside: is checkout succeeding, are pages loading fast, is a replica falling behind. Performance Schema is a different, complementary tool. It's a database inside your database that records what's happening at the level of individual pieces of server code, things like "how long did this exact query take" or "how much memory did this background thread allocate." It's not a replacement for the older SHOW STATUS-style counters you met in Ch.2 (things like Threads_running), it's a much finer-grained lens you point at specific problems once you already suspect something is wrong, or want to watch continuously for patterns those simpler counters can't show you.

This first part covers the foundation: the two core building blocks (instruments and consumers), how the resulting tables are organized, what it costs you to turn instrumentation on, its real limitations, a friendlier companion schema called sys, how MySQL's threads are identified, and every method the source describes for switching Performance Schema on, off, and everywhere in between. Part 2 (next batch) will go through the specific things you can actually investigate with it: slow statements, locks, memory hogs, and more.

Key terms

  • Performance Schema (performance_schema) — a database built into MySQL that stores low-level metrics about what's happening inside the server itself, as opposed to just the customer-facing signals Ch.2 covered.
  • Instrument — a specific portion of MySQL's own code that has been wired up so it can report what it's doing. Example from the source: wait/lock/metadata/sql/mdl is the instrument you'd enable to capture information about metadata locks.
  • Consumer — a table that stores the information an instrument produces. If you instrument queries, the consumer records things like total executions, how many times no index was used, and time spent.
  • setup_instruments — the table in performance_schema listing every supported instrument and whether it's currently enabled.
  • Digest — a normalized version of a query, with the specific literal values stripped out, so many similar queries can be tracked as one thing. SELECT user,birthdate FROM users WHERE user_id=19 and the same query with user_id=13 or 27 all collapse into one digest: SELECT user,birthdate FROM users WHERE user_id=?.
  • sys schema — a companion schema (included since MySQL 5.7) made entirely of views and stored routines that sit on top of performance_schema, to make common questions easier to ask. It stores no data of its own.
  • Foreground thread / background thread — a foreground thread is created for a user connection; a background thread is created internally, say by the main server process or a storage engine.
  • THREAD_ID — MySQL's own internal identifier for a thread, used throughout performance_schema tables. It is not the same value as PROCESSLIST_ID, and the source flags this explicitly as a common point of confusion.
  • PROCESSLIST_ID — the connection identifier you see in SHOW PROCESSLIST output, or in the "Your MySQL connection id is" message when you connect via the command-line client. Only foreground (user connection) threads have one.
  • setup_objects, setup_threads, setup_actors — tables that let you scope instrumentation down to specific database objects, specific background threads, or specific user accounts, instead of everything at once.
  • Autosizing / autoscaling — some performance_schema tables allocate a small amount of memory at startup and grow as needed, rather than reserving a fixed size upfront.

How it works

Performance Schema exists because tuning a database is an iterative loop: you make a change, and then you need real evidence of whether it helped. Did queries get faster? Are locks gone or still piling up? Did memory usage change? The source frames the whole chapter around answering exactly those kinds of questions, and Performance Schema is the mechanism MySQL gives you for doing it from inside the server, at a level of detail that customer-facing monitoring alone can't reach.

Two ideas everything else builds on: instruments and consumers

The source introduces two concepts right at the start, and almost everything else in the chapter is really just detail layered on top of these two.

An instrument is a piece of MySQL's own code that has been marked so it can report on itself. If you want to know about metadata locks (a kind of lock that protects a table or other object's definition from being changed while something else is using it, which Part 2 covers in depth), you'd enable the instrument named wait/lock/metadata/sql/mdl. A consumer is simply the table that stores what that instrument reports. Instrument queries, and the consumer records things like the total number of executions, how many times no index was used, and how much time was spent.

Picture a small online bookstore's checkout query running thousands of times a day. The instrument is the piece of server code responsible for noticing "a SELECT just ran." The consumer is the table where that gets tallied up: how many times, how long each one took, whether it needed a temporary table. You never touch the instrument directly, you just enable it and then query the consumer table with ordinary SQL.

Every instrument's name is built from parts separated by a slash, read left to right from general to specific. The source gives two examples: statement/sql/select and wait/synch/mutex/innodb/autoinc_mutex. In the first, statement says this is a statement-type instrument, and select narrows it down to SELECT queries specifically. In the second, wait says it's a wait-type instrument, synch narrows to synchronization waits, mutex narrows further to mutex waits (a mutex is a lock a piece of code takes on itself to avoid two threads touching the same internal data at once), and innodb/autoinc_mutex says specifically it's the mutex InnoDB (MySQL's default storage engine) sets when handling an auto-increment column.

From instrument to a row you can query

When an application connects to MySQL and runs something that touches an enabled instrument, the server wraps that call so the result gets recorded into the matching consumer table. The source is upfront that this isn't free: enabling an instrument means extra code runs on every single call it touches, and that costs CPU. Keep that trade-off in mind through this whole chapter: instrumentation is a lens you point deliberately, not something you leave maximally on by default.

How the consumer tables are organized

Performance Schema stores results across a large number of tables (the source notes that MySQL Community 8.0.25 specifically ships 110 of them, though this count is version-specific and worth re-checking against whatever version you're actually running). Rather than memorizing all of them, it helps to know the families they fall into.

Current and historical data. For a handful of event categories, three related tables exist per category, distinguished by a suffix: a *_current table (events happening right now), a *_history table (the last 10 completed events, per thread), and a *_history_long table (the last 10,000 completed events per thread, globally). Both history sizes are configurable. This three-table pattern exists for four categories: events_waits (low-level waits, like acquiring a mutex), events_statements (SQL statements), events_stages (profiling detail, like time spent creating a temporary table), and events_transactions (transactions).

Summary tables and digests. A summary table holds pre-aggregated information, for example memory_summary_by_thread_by_event_name rolls up memory usage per thread. Digests, introduced above as a key term, let Performance Schema track metrics like latency for a normalized query shape without keeping every literal variation separately.

Instances. These tables describe specific object instances that exist on this MySQL installation. The source's example is file_instances, which holds filenames and how many threads access each one.

Setup tables. These are used to configure Performance Schema at runtime, and you'll meet several of them below: setup_instruments, setup_consumers, setup_objects, setup_threads, and setup_actors.

Other tables. Some tables don't fit a strict naming pattern, like metadata_locks, which holds data about metadata locks (Part 2 covers this table in more depth).

What watching costs you

Performance Schema's data lives entirely in memory. Some tables autosize: they start small and grow only as needed, rather than reserving a fixed amount upfront. Here's the catch worth remembering: once that memory is allocated, it is not released, even if you later disable the instrumentation and empty (truncate) the table. The only way to actually reclaim it is a server restart.

CPU cost is the other side of this. Every instrumented call adds two extra internal calls (the source calls these "macros") to record the result. How much that actually costs depends heavily on which instrument you're talking about. A statement-type instrument like statement/sql/select fires once per query, so enabling statement instrumentation is barely noticeable. A wait-type instrument tied to row locks is a completely different story: scanning an InnoDB table with a million rows means setting and releasing roughly a million row locks, so instrumenting locks at that scale can raise CPU usage significantly. The same caution applies to memory and metadata lock instrumentation. The practical takeaway: enable what you actually need, and expect the cost to vary wildly depending on how often the underlying code path runs.

Three limitations worth knowing before you rely on this

The source is direct about three real constraints, and it's worth internalizing them now rather than getting surprised by them later.

  • It needs support from the specific MySQL component involved. If you're trying to find which component is using the most memory and the answer turns out to be a storage engine that doesn't support memory instrumentation, Performance Schema simply won't be able to show you where that memory went.
  • It only sees data from the moment an instrument and its consumer are both enabled. If you start a server with everything disabled and only enable memory instrumentation later, you won't be able to recover the exact amount already allocated by something like the InnoDB buffer pool (a cache InnoDB keeps in memory), because that allocation already happened before you turned the lens on.
  • Freeing memory is genuinely hard. As covered above, autosized consumers only grow when data starts flowing, but disabling an instrument or consumer afterward does not give that memory back. A restart is the only real fix.

The sys schema: a friendlier front end

Since MySQL 5.7, a standard installation also ships a companion schema called sys. It is made up entirely of views and stored routines that sit on top of performance_schema, meant to make common questions easier to ask without writing raw joins across several tables yourself. It's worth remembering, though, that sys stores nothing of its own: everything it shows you is ultimately pulled from the underlying performance_schema tables. If you need a piece of data sys doesn't expose, the fix is to go check whether it exists in the raw performance_schema table underneath.

Understanding threads: two different IDs that are easy to mix up

MySQL server itself is multithreaded. Every component, whether it's a background piece like a storage engine's internal housekeeping or a foreground connection a user opened, runs as its own thread. Each thread carries at least two different identifiers, and the source calls out explicitly that they are not interchangeable: an operating-system-level thread ID (visible to tools like the Linux ps -eLf command) and MySQL's own internal THREAD_ID, which is what you'll see used throughout performance_schema tables. On top of that, every foreground thread (a user connection) also gets a PROCESSLIST_ID, the same connection ID you'd see in SHOW PROCESSLIST output, or in the "Your MySQL connection id is" message the command-line client prints when you connect.

The threads table in performance_schema lists every thread on the server, with columns including NAME, THREAD_ID, PROCESSLIST_ID, and THREAD_OS_ID. Background threads generally show NULL for PROCESSLIST_ID, since that identifier only applies to user connections. Beyond the identifiers, the threads table carries roughly the same information as SHOW PROCESSLIST, plus a few extra columns like RESOURCE_GROUP or PARENT_THREAD_ID.

Here's why the distinction matters in practice: performance_schema tables use THREAD_ID everywhere, but PROCESSLIST_ID only shows up in the threads table itself. If you're troubleshooting something like a stuck lock and need the connection ID so you can actually kill it, you have to look it up through the threads table first. And because threads can be joined against most of the other performance_schema tables, it becomes the hub you connect through to pull in query details, locks, mutexes, or open table instances for a given connection.

Turning it on: configuration

A small number of settings can only be changed when the MySQL server starts: whether Performance Schema is enabled at all, and the variables controlling memory usage and limits for what gets collected. Everything else, meaning individual instruments and consumers, can be flipped on or off while the server is running. The source's own advice here is worth repeating: you can run with Performance Schema itself on but almost everything inside it disabled, then dynamically enable just the specific instruments and consumers you need right before you expect to investigate an issue. That way you're not spending resources on data you don't need, and you don't risk starving the server through over-instrumentation.

Enabling Performance Schema itself. This is controlled by the performance_schema variable, set to ON or OFF. It's a read-only variable at runtime: the only way to change it is in the configuration file or as a command-line parameter when the server starts.

Enabling and disabling individual instruments. You can check any instrument's current state by querying setup_instruments, for example filtering WHERE NAME='statement/sql/select' and looking at its ENABLED column. The source describes three ways to change it:

  • An ordinary UPDATE against setup_instruments, e.g. SET ENABLED='YES' WHERE NAME='statement/sql/select'. Because this is standard SQL, wildcards work too, so you could enable every SQL statement instrument at once with WHERE NAME LIKE 'statement/sql/%'. This change does not persist across a restart.
  • The sys schema's ps_setup_enable_instrument (and its counterpart, ps_setup_disable_instrument) stored procedures, which also support wildcards (use '%' to affect every instrument). Functionally, this is the same as the direct UPDATE, including that it also doesn't survive a restart.
  • The startup option performance-schema-instrument='instrument_name=value', where value is one of ON/TRUE/1 to enable, OFF/FALSE/0 to disable, or COUNTED to count occurrences without timing them. This can be repeated for multiple instruments, supports wildcards, and (unlike the other two methods) does persist, since it's set at startup. One quirk worth knowing: if two of your specified patterns could both match the same instrument, the longer, more specific string wins regardless of the order you wrote them in.

Enabling and disabling consumers. The same three-method pattern applies: update the setup_consumers table, call the sys schema's ps_setup_enable_consumer / ps_setup_disable_consumer procedures, or set the performance-schema-consumer configuration parameter at startup. There are 15 possible consumers in total. Most are self-explanatory, but a few deserve a plain-English description: the events_stages_[current|history|history_long] family holds profiling detail like "Creating tmp table" or "statistics"; events_statements_[...] holds statement statistics; events_transactions_[...] holds transaction data; events_waits_[...] holds wait data. Two consumers control instrumentation at a broader level: global_instrumentation, which, if disabled, means no individual settings are even checked and no data (global or per-thread) is collected at all; and thread_instrumentation, which is only checked if global instrumentation is on, and which governs whether per-thread and individual event data gets collected. Finally, statements_digest controls whether statement digests (the normalized query shapes from the key terms above) get collected.

Scoping what actually gets watched

Beyond turning categories of instrumentation on or off, Performance Schema lets you narrow monitoring down to specific objects, specific background threads, and specific user accounts.

The setup_objects table controls instrumentation by object. Its OBJECT_TYPE column takes one of five values: EVENT, FUNCTION, PROCEDURE, TABLE, or TRIGGER, and you can further narrow things with OBJECT_SCHEMA and OBJECT_NAME, both of which support wildcards. The source's example disables instrumentation for every trigger in a schema called test, via INSERT INTO setup_objects (OBJECT_TYPE, OBJECT_SCHEMA, OBJECT_NAME, ENABLED) VALUES ('TRIGGER', 'test', '%', 'NO'), then carves out one exception for a specific trigger with a second, more specific row. When Performance Schema decides whether to instrument something, it looks for the most specific matching rule first and only falls back to a broader one if nothing more specific matches. There's no configuration-file option for this table; to persist your rules across a restart, the source points you to writing the same INSERT statements into a SQL file and loading it at startup via the init_file option.

The setup_threads table lists background threads that can be individually monitored, with an ENABLED column and a HISTORY column (whether that thread's events also get stored in the _history and _history_long tables). The example given disables history logging just for the event scheduler thread: UPDATE setup_threads SET HISTORY='NO' WHERE NAME='thread/sql/event_scheduler'. Because setup_threads doesn't cover user (foreground) threads, a separate table, setup_actors, exists for that: it has HOST, USER, an unused ROLE column, ENABLED, and HISTORY, letting you set rules per account or per host, with wildcards supported. Like setup_objects, neither of these has a config-file option, so persisting changes again means an init_file-loaded SQL script.

Sizing the memory it's allowed to use

Performance Schema's tables use the PERFORMANCE_SCHEMA storage engine, which keeps everything in memory. Some of these tables are autosized by default, others have a fixed row count, and you control both cases with startup variables following the pattern performance_schema_object_[size|instances|classes|length|handles], where "object" refers to whichever consumer, setup table, or instrumented instance you're sizing. The source's own examples: performance_schema_events_stages_history_size sets how many stage events per thread the events_stages_history table stores, and performance_schema_max_memory_classes caps how many distinct memory instruments can exist.

Sensible defaults (and why they're worth naming a version for)

The source is careful to point out that MySQL's defaults shift from version to version, so anything here is worth double-checking against the current MySQL Reference Manual before you rely on it operationally. With that boundary named, here's what it describes: since version 5.7, Performance Schema is enabled by default, but with most instruments turned off. Only global, thread, statement, and transaction instrumentation is on out of the box. Since version 8.0, metadata lock and memory instrumentation are additionally enabled by default. The mysql, information_schema, and performance_schema databases themselves are not instrumented by default; everything else (other objects, threads, and actors) is. Most instance, handle, and setup tables are autosized. The _history tables keep the last 10 events per thread, and _history_long tables keep the latest 10,000 events per thread, by default. Stored SQL text and stored SQL digests are both capped at 1,024 bytes by default; anything longer gets right-trimmed.

Why it matters

This foundation is what makes Part 2 legible. Once you actually understand that an instrument is a watch point, a consumer is where its results land, and that you can dial the scope up or down through setup_objects, setup_threads, and setup_actors, the specific investigations (why is this query slow, who's holding this lock, what's eating memory) stop feeling like a list of unrelated tricks and start feeling like the same small toolkit applied to different questions. It also sets you up to make an informed cost decision every time: you now know that flipping on instrumentation isn't free, so you can be deliberate about what you turn on and when, rather than either avoiding Performance Schema out of fear or leaving everything on and wondering why CPU crept up.

Remember this

  • An instrument is a watch point in MySQL's own code; a consumer is the table that stores what it reports. Nearly everything else in this chapter is detail on top of that pair.
  • Instrument names read general to specific, separated by slashes (statement/sql/select). Consumer tables cluster into families: current/history/history_long, summary/digest, instances, setup, and a few others.
  • Instrumentation costs CPU, and the cost varies enormously by instrument (a once-per-query statement instrument versus a per-row-lock wait instrument are very different bets). Its memory is also never freed without a restart.
  • THREAD_ID is Performance Schema's internal identifier and shows up everywhere; PROCESSLIST_ID is the connection ID from SHOW PROCESSLIST and only lives in the threads table. They are not interchangeable.
  • Two dynamic methods (a direct UPDATE, or the sys schema's stored procedures) enable instruments and consumers the same way but don't survive a restart; only the performance-schema-instrument/consumer startup options do.

Try it yourself

  • Flip an instrument on and confirm it. On a local MySQL 8.0 instance, run SELECT * FROM performance_schema.setup_instruments WHERE NAME='statement/sql/select'\G and note the ENABLED value. Then run the UPDATE the source describes to set it to 'YES', and query it again. Done when: you can show the ENABLED column changing from one value to the other in your own terminal output.
  • Compare Ch.2's lens with this one. On the same instance, run SHOW GLOBAL STATUS LIKE 'Threads_running'; (the Ch.2-style counter), then separately query SELECT NAME, THREAD_ID, PROCESSLIST_ID, THREAD_OS_ID FROM performance_schema.threads;. Done when: you can explain in your own words one thing the threads table shows you that the single Threads_running number doesn't (for example, which specific connection is which).
  • Read five instrument descriptions. Query SELECT NAME, DOCUMENTATION FROM performance_schema.setup_instruments WHERE DOCUMENTATION IS NOT NULL LIMIT 5; and read what each one actually does. Done when: you can restate two of the five descriptions in your own plain-English words without looking at the screen.
  • Find your own connection twice. Open two separate MySQL command-line sessions. In each, note the "Your MySQL connection id is" number MySQL prints, then run the threads-table query from the exercise above and find the row matching each session by its PROCESSLIST_ID. Done when: you've correctly matched both sessions to their own row in the threads table.
  • Test which enable-method survives a restart. Enable an instrument via a direct UPDATE to setup_instruments, then restart your local MySQL instance and check its ENABLED value again. Then (separately) add the same instrument via the performance-schema-instrument startup option in your config file, restart, and check again. Done when: you can show the UPDATE-based change reverting after restart while the startup-option change persists.
  • Scope monitoring down with setup_objects. On a scratch schema, insert a row into setup_objects disabling TRIGGER instrumentation for that schema with the wildcard object name, following the pattern the source describes, then insert a second, more specific row re-enabling it for one named trigger. Done when: you can explain, using your own two rows, why Performance Schema picks the specific rule over the wildcard one.
