SYSTEMS · CH.7 DIGEST (PART 2)

Weak Isolation: Read Committed, Snapshots, Lost Updates, and Write Skew

Part 1 defined isolation as "concurrent transactions don't step on each other" and then admitted that real databases mostly offer weaker versions of it. This part walks through those weaker levels and the specific bugs each one still allows. It is the most practically useful stretch of the chapter, because it explains why code that "uses transactions" can still go wrong. It stops right before the section on serializability.

In one line

Read committed stops dirty reads and dirty writes, snapshot isolation also gives you a stable view of the data, but lost updates and write skew can still slip through, and each needs its own fix or a truly serializable level.

The big idea

Concurrency bugs only occur when you get unlucky with timing, so they are hard to test for and hard to reason about. Databases try to hide them with isolation, but full serializable isolation costs performance, so many databases default to weaker levels that prevent some problems. The skill this part teaches is naming the problems: dirty reads, dirty writes, read skew, lost updates, write skew, phantoms. If you can name the anomaly, you can ask whether your database's isolation level stops it. The source also warns against the lazy answer "just use an ACID database for financial data", because many popular "ACID" relational databases use weak isolation by default.

Key terms

  • Read committed: the most basic level; no dirty reads, no dirty writes.
  • Dirty read: reading another transaction's uncommitted write.
  • Dirty write: overwriting another transaction's uncommitted write.
  • Row-level lock: a lock on one row or document, held until the transaction commits or aborts, used to prevent dirty writes.
  • Read skew (nonrepeatable read): seeing different parts of the database at different points in time within one transaction.
  • Snapshot isolation: each transaction reads from a consistent snapshot of the database as of its start.
  • MVCC (multi-version concurrency control): keeping several committed versions of an object side by side so different transactions can see different points in time.
  • Transaction ID (txid): a unique, always-increasing number given to each transaction.
  • Repeatable read: the SQL standard's name for a level; many databases use it as a name for snapshot isolation, with big differences between them.
  • Lost update: two read-modify-write cycles overlap and one write overwrites the other without including its change.
  • Atomic write operation: a database-provided operation like value = value + 1 that does the read-modify-write safely.
  • Explicit locking (FOR UPDATE): the application asks the database to lock the rows it just read.
  • Compare-and-set: update only if the value is still what you last read.
  • Write skew: two transactions read the same data, then each write different objects, together breaking a rule neither alone would.
  • Phantom: a write in one transaction changes the result of another transaction's search query.
  • Materializing conflicts: adding rows purely so there is something to lock.
  • Commutative operation: one that gives the same result applied in any order (increments, adding to a set).

How it works

Grounding first. If two transactions touch different data, they can run in parallel safely. Trouble starts when one reads something another is changing, or both change the same thing. The source's framing is that serializable isolation would let you pretend no concurrency exists, but it has a cost, so many databases give you less, and the less you get, the more subtle the bugs. Real losses have come from this: the source notes concurrency bugs from weak isolation have caused substantial financial losses, led to investigations by financial auditors, and corrupted customer data. Our job is to understand which anomalies exist and which levels block them. The discussion is informal and example-driven (rigorous definitions are in the academic literature).

Read committed

Two promises. No dirty reads: you only see data that has been committed. A transaction's writes become visible to others when it commits, all at once. This avoids seeing a partial update (a new email without its counter) and avoids seeing data that is later rolled back. No dirty writes: you only overwrite data that has been committed, usually by delaying the second write until the first transaction commits or aborts. Why it matters: in the source's used-car example, Alice and Bob both try to buy the same car, which takes two writes (the listing's buyer and the invoice's recipient). With dirty writes, Bob could win the listing while Alice wins the invoice. (Read committed does not fix the double-counter-increment race from Part 1: the second write comes after the first committed, so it's not a dirty write, though it's still wrong.)

How it's implemented. Read committed is very popular; the source lists it as the default in Oracle 11g, PostgreSQL, SQL Server 2012, MemSQL and others. Dirty writes are usually prevented with row-level locks held until commit or abort. Dirty reads could use the same lock (readers briefly take it), but a long write transaction would then block many readers, hurting response times and spreading slowness across an application. So most databases remember both the old committed value and the new uncommitted one: readers get the old value until the writer commits. (The source notes IBM DB2 and SQL Server in the read_committed_snapshot=off configuration use locks for this.)

Read skew, and why snapshots help

Read committed still allows anomalies. Suppose Alice has $1,000 split into two $500 accounts, and a transfer of $100 happens while she is viewing them. She might read account 1 before the transfer arrives ($500) and account 2 after it left ($400): total $900, as if $100 vanished. Each value was committed when read, so read committed is satisfied. This is read skew (also called a nonrepeatable read: re-read account 1 later and you'd see $600). (Note "skew" here means a timing anomaly, unlike its earlier meaning of unbalanced load.) Alice would see consistent numbers on reload, but some cases can't tolerate temporary inconsistency:

  • Backups: a backup of a large database takes hours; if parts reflect older data and parts newer, restoring it makes the inconsistency permanent.
  • Analytic queries and integrity checks: scanning large parts of the database at different points in time gives nonsense results.

The usual fix is snapshot isolation: each transaction sees all data that was committed when the transaction started, and nothing later, even if other transactions change it afterward. It is supported by PostgreSQL, MySQL with InnoDB, Oracle, SQL Server and others (per the book). Great for long-running read-only queries.

How snapshot isolation is implemented: MVCC

Writers still use write locks (to prevent dirty writes), but reads need no locks. The key principle: readers never block writers, and writers never block readers. To allow this the database keeps several committed versions of each object: multi-version concurrency control. Read committed, in such engines, typically uses a fresh snapshot per query, while snapshot isolation uses one snapshot for the whole transaction.

In the PostgreSQL-style design the source describes, every transaction gets a unique, increasing transaction ID. Each row has created_by (the writer's txid) and deleted_by (empty initially). A delete only marks the row; later, garbage collection removes rows no transaction can still see. An update is a delete plus a create. (In the $500 to $400 example, the table briefly holds both the $500 row marked deleted and the new $400 row.)

Visibility rules, from the source. When a transaction starts, the database lists the transactions still in progress. Then:

  1. Writes by those in-progress transactions are ignored, even if they later commit.
  2. Writes by aborted transactions are ignored.
  3. Writes by transactions with a later transaction ID are ignored, committed or not.
  4. All other writes are visible.

Put another way, an object is visible if its creator had committed before your transaction started, and it is either not marked deleted or its deleter had not yet committed at that time. Because values are never updated in place, a long-running transaction can keep reading old values at small overhead.

Indexes. One option: the index points to all versions and the query filters out invisible ones; when garbage collection removes old versions, so do the index entries. PostgreSQL has optimizations such as avoiding index updates when versions fit on the same page. A different approach, used by CouchDB, Datomic and LMDB, is an append-only/copy-on-write B-tree: each write creates new copies of the modified pages up to a new root, and a root is a consistent snapshot. No transaction ID filtering is needed, but a background process must compact and garbage collect.

Naming confusion. Snapshot isolation is called serializable in Oracle and repeatable read in PostgreSQL and MySQL. The SQL standard defined repeatable read before snapshot isolation existed (it is based on System R's 1975 definitions), and the standard's definitions are ambiguous. Databases that implement repeatable read differ widely, IBM DB2 uses "repeatable read" to mean serializability, and the source concludes: "nobody really knows what repeatable read means".

Preventing lost updates

So far we considered what reads see. Now two transactions writing. A lost update happens in a read-modify-write cycle: both read, both change, and the later write doesn't include the earlier change (it "clobbers" it). Examples: incrementing a counter or balance; adding an element to a list inside a JSON document; two users saving a wiki page by sending the whole page. Remedies:

  • Atomic write operations. UPDATE counters SET value = value + 1 WHERE key = 'foo' is concurrency-safe in most relational databases (the source's wording; check yours). MongoDB offers atomic local edits to part of a document; Redis offers atomic data-structure operations. Usually the best solution if your logic fits, though not everything does (arbitrary text editing). Often implemented by taking an exclusive lock when reading (sometimes called cursor stability) or by running all atomic operations on a single thread. A warning: ORMs make it easy to accidentally write unsafe read-modify-write code instead of using atomic operations.
  • Explicit locking. When atomic operations aren't enough (the source's example: a game where a move must also follow game rules), SELECT ... FOR UPDATE locks the rows returned, so others wait until your cycle finishes. It works but is easy to get wrong: forget a lock somewhere and you have a race.
  • Automatic detection. Let cycles run in parallel and abort one if the database detects a lost update; the aborted transaction retries. Efficient with snapshot isolation. The source says PostgreSQL's repeatable read, Oracle's serializable and SQL Server's snapshot isolation detect lost updates, but MySQL/InnoDB's repeatable read does not (so by the stricter definition MySQL does not provide snapshot isolation). Advantage: no special application code to forget.
  • Compare-and-set. Update only if the value is unchanged since your read: UPDATE ... WHERE id = 1234 AND content = 'old content'. Check whether any row was affected and retry otherwise. But if the database lets the WHERE clause read from an old snapshot it may not be safe; the source says to check your database's behavior before relying on it.
  • In replicated databases (multi-leader or leaderless), locks and compare-and-set assume a single up-to-date copy, which doesn't exist. Instead, allow conflicting versions (siblings) and merge. Commutative operations (counter increments, adding to a set) work well; Riak 2.0 datatypes use this. Last write wins loses updates, and unfortunately is the default in many replicated databases.

Write skew

The source's example: a hospital requires at least one doctor on call per shift. Alice and Bob are the two on call and both request leave at the same moment. Each transaction first checks that two or more doctors are on call; under snapshot isolation both checks see 2, so both proceed. Alice updates her record, Bob updates his, both commit, and nobody is on call. This is write skew. It's neither a dirty write nor a lost update, because they updated different objects, but it's a race: run one after the other and the second would have been refused. You can see write skew as a generalization of lost update: two transactions read the same objects, then update some of them; if they update the same object you get a dirty write or lost update, depending on timing.

Options are narrower:

  • Single-object atomic operations don't help (several objects involved).
  • Automatic lost-update detection doesn't help; the source says write skew isn't detected in PostgreSQL's repeatable read, MySQL/InnoDB's repeatable read, Oracle's serializable or SQL Server's snapshot isolation. Preventing it automatically requires true serializable isolation.
  • Constraints help only for simple rules (uniqueness, foreign keys). A rule over multiple objects usually isn't supported natively, though triggers or materialized views may emulate it.
  • If you can't be serializable, the second-best is to explicitly lock the rows the transaction depends on: SELECT ... WHERE on_call = true AND shift_id = 1234 FOR UPDATE.

More examples of the same shape: double-booking a meeting room (check for overlapping bookings, then insert); two players moving different pieces to the same square; two users claiming the same username (a unique constraint is a simple fix here); and double-spending (two spending items inserted concurrently drive a balance negative).

Phantoms and materializing conflicts

The pattern in all those examples: (1) a SELECT checks a requirement by searching for rows matching a condition; (2) application code decides what to do; (3) it writes, and the write changes the answer to step 1's search. In the doctor example you can lock the rows from step 1 with FOR UPDATE. In the other examples, the check is for the absence of rows, so there is nothing to lock. A write in one transaction changing the results of another's search is called a phantom. Snapshot isolation avoids phantoms for read-only queries but not in read-write transactions.

If the issue is that there's no object to lock, you can create one: for the booking system, pre-create a table of room-and-time-slot rows (say 15-minute slots for six months) purely as locks. A booking transaction does SELECT ... FOR UPDATE on the slots it wants, then checks for overlaps and inserts. That is materializing conflicts. The source calls it hard, error-prone, and ugly (it leaks concurrency control into the data model), a last resort; a serializable isolation level is much preferable in most cases.

Why it matters

This is the part to remember when someone says "we use transactions, so we're safe." A check-then-write pattern (book if free, spend if funded, claim if unclaimed) is exactly where write skew hides. It also tells you what to look at in your own database: its default isolation level, and whether its "repeatable read" or "serializable" is really snapshot isolation.

Remember this

  • Read committed: no dirty reads or writes, but you can still see read skew and lose updates.
  • Snapshot isolation (MVCC): each transaction reads a consistent snapshot; readers and writers don't block each other. Names differ per database.
  • Lost updates: use atomic operations, explicit locks, automatic detection, or compare-and-set, and check what your database really does.
  • Write skew and phantoms come from a check followed by a write that invalidates the check on other objects; only serializability reliably prevents them, with locks and constraints as partial fixes.
  • Weak-isolation bugs are timing-dependent and hard to test; learn the names so you can look for them.

Try it yourself

  1. Mini MVCC. Store rows with created_by and deleted_by and write the four visibility rules as a function. Done when a reader that started before a transfer commits sees old balances after the transfer commits, and a later reader sees new ones.
  2. Read skew demo. In a database with read committed (such as PostgreSQL's default), open two sessions: one sums two accounts across two separate queries while the other transfers money between them. Done when you can make the total briefly look wrong, then repeat with a snapshot-based level and see it stable.
  3. Lost update lab. Run read-modify-write counter increments from two sessions at once, then fix with value = value + 1, then with SELECT ... FOR UPDATE. Done when you can explain why each fix works and which one you would forget to apply.
  4. Write skew reproduction. Build the on-call table and run both leave requests concurrently under a snapshot-based level. Done when you reproduce zero doctors on call, then prevent it with FOR UPDATE on the dependent rows or a stronger level (check your database's docs for its serializable mode).
  5. Phantom-proofing. For a booking table, try the check-then-insert pattern concurrently, then add a pre-created slot table and lock the slots (materializing conflicts). Done when double-booking stops, and you've written down why you would prefer serializable isolation instead.
