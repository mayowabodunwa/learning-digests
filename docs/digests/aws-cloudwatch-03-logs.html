CloudWatch Logs: Log Groups, Streams, Retention, Metric Filters and Subscription Filters

Metrics tell you that something is wrong. Logs tell you what actually happened. This digest covers how CloudWatch Logs organises text records (log events, log streams, log groups), how long it keeps them (retention), and the two filters that turn a log group into something active: metric filters that make numbers out of text, and subscription filters that stream matching lines to another service.

In one line

CloudWatch Logs stores timestamped text records in log groups, deletes them on a schedule you choose, and can watch the incoming flow to count patterns into metrics or forward matches somewhere else.

The big idea

Your application, your servers and many AWS services write lines of text describing what they are doing. Those lines are useless if they only live on a disk that might disappear. CloudWatch Logs gives them a central home. You organise them into log groups (one per application or purpose), and inside each group every source gets its own log stream. The group is where you set the rules that apply to everything inside it: how long to keep data, who can read it, and which filters watch it.

Then come the two filters. A metric filter looks at each incoming line, and if it matches your pattern, adds a data point to a normal CloudWatch metric. That is the bridge back to the previous two digests: once a log pattern is a metric, you can graph it and put an alarm on it. A subscription filter is different. It does not make a metric, it sends the matching log events on to another service (a Kinesis data stream, an Amazon Data Firehose stream, or a Lambda function) so something else can process them in near real time.

Key terms

  • Log event: one record of something that happened. CloudWatch Logs understands exactly two properties: a timestamp and the raw message. The message must be UTF-8 text.
  • Log stream: a sequence of log events that share the same source. Typically that means one application instance or resource, for example the access log of one particular web host.
  • Log group: a collection of log streams that share the same retention, monitoring and access control settings. Every log stream belongs to exactly one log group. The docs say there is no limit on how many streams one group can hold.
  • Retention setting: how long log events are kept before they are expired and deleted. Set per log group.
  • Log class: a log group is either Standard (full featured) or Infrequent Access (cheaper ingestion, fewer features). It is chosen when the group is created and can't be changed afterwards.
  • Filter pattern: a small piece of syntax that says which log events you care about. The same syntax is used by metric filters, subscription filters, searching log events, and Live Tail.
  • Metric filter: a rule on a log group that extracts numbers from matching events and publishes them to a CloudWatch metric.
  • Subscription filter: a rule on a log group (or the account) that delivers matching events to a destination service as they arrive.
  • Default value (metric filter): the number reported for a period in which logs arrived but nothing matched.
  • Deletion protection: an optional switch on a log group that blocks delete operations until you turn it off. It is off by default.

How it works

Grounding: why logs are a separate thing from metrics

A metric is a number over time: "CPU was 63 percent at 14:02". It is compact and easy to alarm on, but it throws away the story. A log event keeps the story: "14:02:11 order 8841 failed: payment provider timed out". If a metric alarm says the error rate jumped, the logs are where you go to find out which errors, for which customers, in which order.

The two are meant to work together, and that is the thread running through this digest. Logs are the detailed record. Metric filters compress that record back into numbers when you want to graph or alarm on it. Subscription filters ship that record onward when you want another system to work with it.

Simplification: I describe "logs" as plain text lines. CloudWatch Logs accepts any UTF-8 message, and many people write each line as structured JSON so it can be filtered by field later. Both are the same thing to the service: a timestamp plus a message.

1. The hierarchy: events, streams and groups

Think of three nested containers.

  • A log event is one line (or one multi-line record) with a timestamp.
  • A log stream holds the events that came from one source, in order. If you have three web servers, a common layout is one stream per server.
  • A log group holds the streams that belong together. The docs give the example of a group named MyWebsite.com/Apache/access_log that holds one stream per host.

Why group-level settings matter. According to the docs, retention settings and metric filters are assigned to a log group and then apply to every stream in it. So a sensible habit is to split groups by how you want to treat the data. Debug chatter from a test app and audit records need very different retention, so they belong in different groups.

How logs get in. CloudWatch Logs receives events automatically from several AWS services. For your own sources you can use the CloudWatch agent (which can ship metrics and logs), the aws logs put-log-events CLI command, or the PutLogEvents API, which uploads batches of events. We cover the agent properly in a later concept of this track.

Housekeeping features the docs list for log groups: tags (key-value labels, up to 50 per log group, useful for cost tracking by owner or environment) and deletion protection, which blocks all deletion operations on the group until you explicitly disable it.

2. Log classes: Standard vs Infrequent Access

When you create a log group you pick a class. Standard is the full-featured option for logs you monitor in real time or read often. Infrequent Access is a lower-cost option for logs you rarely read, such as ad-hoc querying and after-the-fact investigation. The docs say the two classes differ in ingestion cost only (storage and Logs Insights query charges are the same). I'm deliberately not quoting any prices, since I'd need the live pricing page for that.

The part that matters for this digest is the feature table. Per the docs, metric filters and subscription filters are both supported on Standard log groups and not on Infrequent Access log groups. Live Tail and the embedded metric format are also Standard only. And, important: after a log group is created, its class can't be changed. Pick on purpose.

Caveat: the docs also mention a third class, Delivery, meant only for delivering AWS Lambda logs to S3 or Firehose, with a fixed two-day retention. I'm not covering it further.

3. Retention: how long events stay

By default, per the docs, log data is stored indefinitely (the console shows Never Expire). You can set a retention period on each log group, and you can change it at any time. Events older than the setting are expired and deleted automatically.

Why you care: stored logs cost money, and logs can contain things you shouldn't keep forever. Setting retention on every group is a cheap habit that stops silent growth. The CLI reference says valid values for --retention-in-days are a fixed list: 1, 3, 5, 7, 14, 30, 60, 90, 120, 150, 180, 365, 400, 545, 731, 1096, 1827, 2192, 2557, 2922, 3288 and 3653. You can't type an arbitrary number like 45. To go back to never expiring you use a different command (delete-retention-policy), not put-retention-policy.

The catch. The docs note that CloudWatch Logs doesn't delete events the instant they reach the retention setting. It typically takes up to 72 hours afterwards, and in rare situations longer. Events that have reached their retention are marked for deletion and, per the docs, stop adding to archival storage cost even before they're physically gone. The same note warns about a subtle trap: if you lengthen retention while expired-but-not-yet-deleted events still exist, those events can survive until the new, longer date. If you need data gone for a compliance reason, don't assume the deadline is exact.

4. Filter patterns: the shared mini-language

Both kinds of filter, plus searching and Live Tail, use one pattern syntax. Learning it once pays off three times. The docs describe four styles:

  • Plain terms in unstructured text. ERROR matches events containing that word. ERROR ARGUMENTS matches events that contain both. ?ERROR ?ARGUMENTS matches events with either. ERROR -ARGUMENTS includes ERROR but excludes ARGUMENTS. Put an exact phrase in double quotes: "INTERNAL SERVER ERROR". Patterns are case sensitive.
  • JSON patterns in curly braces, using $. to pick a field: { $.eventType = "UpdateTrail" } or { $.latency < 50 }. Compound conditions use && and ||.
  • Space-delimited patterns in square brackets, where you name each field: [ip, user, username, timestamp, request, status_code, bytes], optionally with conditions such as status_code = 404 || status_code = 410.
  • Regular expressions wrapped in percent signs, for example %AUTHORIZED%. The docs list the supported operators and say parentheses aren't supported.

Simplification: I skipped many details such as numeric operators in space-delimited patterns, wildcard selectors, and quota limits on regex use in a pattern. The docs page has them all and is worth skimming once.

5. Metric filters: text in, numbers out

A metric filter takes a log group, a filter pattern, and a recipe for a metric. As events come in, any event matching the pattern adds to the metric. The docs list its parts:

  • Filter pattern: what to look for.
  • Metric name and namespace: where the result goes (you met both in the Metrics digest).
  • Metric value: the number to publish per match. For counting occurrences it's 1. It can also be a number pulled out of the event, for example the docs show { $.latency = * } metricValue: $.latency, which publishes the latency value found in a JSON event.
  • Default value: the number reported for a period when logs arrived but nothing matched. The docs recommend setting it (even to 0) so the metric isn't "spotty". Note the caveat in the docs: if no logs are ingested at all during a minute, no value is reported. You also can't set a default value if you assign dimensions.
  • Dimensions: optional, only for JSON and space-delimited patterns, up to three. Each unique name/value pair creates a new variant of the metric.
  • Unit: optional. Pick the right one up front, since the docs say changing it later has no effect.

Important behaviours to know.

  • Not retroactive. Per the docs, a metric filter only publishes data points for events that happen after the filter was created. It does not go back through old logs.
  • Standard class only. Metric filters aren't supported on Infrequent Access groups.
  • At least once. The docs say delivery to the metric is at least once, so occasional duplicates can happen. A count from a metric filter is a good signal, but not an accounting-grade total.
  • Watch dimension cardinality. The docs warn that dimension values are charged like custom metrics and that you shouldn't use high-cardinality fields such as an IP address or request ID as dimensions. They also say AWS might disable a metric filter that generates 1000 different name/value pairs for its dimensions over a certain amount of time.

For a Lambda function or EC2 app, this is the classic pattern: log ERROR lines, a metric filter counts them per minute, and an alarm (last digest) emails you when the count passes a threshold.

6. Subscription filters: a live feed to another service

A subscription filter gives you "a real-time feed of log events" delivered to another service, per the docs: an Amazon Kinesis Data Streams stream, an Amazon Data Firehose stream, or an AWS Lambda function (and the docs also describe streaming to Amazon OpenSearch Service). You create the destination first, then the subscription filter, which holds a filter pattern and the destination's address.

Details the docs give.

  • Events are sent base64 encoded and compressed with gzip, so a receiver must decode and decompress.
  • Delivery usually happens in less than three minutes after ingestion ("soon after being ingested"), so it is near real time, not instant.
  • Delivery is at least once, so duplicates may occasionally occur. Events may also be batched when possible, though batching is not guaranteed.
  • If the destination returns a retryable error (throttling, HTTP 5xx), CloudWatch Logs keeps retrying for up to 24 hours. For a non-retryable error such as AccessDeniedException, the filter is disabled for up to 10 minutes and the logs in that window are skipped.
  • Standard-class log groups only.
  • The CLI command put-subscription-filter takes a role ARN that gives CloudWatch Logs permission to deliver, unless the destination is a cross-account logical destination. For a Lambda destination, the CLI reference notes that iam:PassRole is not required.

A limit I can't pin down. The Subscriptions overview page says each log group can have up to five subscription filters and each account can have one account-level subscription filter per Region. The CLI reference page for put-subscription-filter says up to two per log group. The two pages disagree, so check the current quotas page before designing around the number.

7. Metric filter vs subscription filter at a glance

Metric filter: output is a CloudWatch metric (a number per minute). Use it when you want to graph or alarm on how often something appears in logs. Keeps working inside CloudWatch.

Subscription filter: output is the matching log events themselves, pushed to Kinesis, Firehose or Lambda. Use it when another system needs the actual text, for example to archive, enrich or analyse it.

Neither is how you ask ad-hoc questions about old data. That is what the next concept (Logs Insights) is for.

Why it matters

Almost every "what went wrong?" investigation on AWS ends in a log group, and almost every "tell me when X happens" requirement that isn't a built-in metric ends in a metric filter. Retention is also where surprise bills and compliance questions come from, because the default is to keep everything forever. Knowing what lives on the group (retention, filters, class) lets you look at one log group and predict its behaviour.

Remember this

  • Events live in streams, streams live in a group. Rules like retention and filters are set on the group.
  • Default retention is keep forever. You pick from a fixed list of day values, and deletion can lag by up to about 72 hours.
  • A metric filter turns matching log lines into a metric. It is not retroactive and works on Standard class groups.
  • A subscription filter streams matching events to Kinesis, Firehose or Lambda, base64 and gzip encoded.
  • Log class can't be changed after creation, so choose it up front.

Try it yourself

  1. Build the hierarchy by hand. Run aws logs create-log-group --log-group-name /lab/shop, then aws logs create-log-stream --log-group-name /lab/shop --log-stream-name web-1, then push a few events with aws logs put-log-events using --log-events timestamp=<ms since epoch>,message="..." (on GNU/Linux, date +%s%3N gives the current time in milliseconds; the reference warns the timestamp is milliseconds, not seconds, and events older than 14 days are rejected). Done when: you can see the events in the console under that stream and can explain which setting would live on the group vs the stream.
  2. Set and read retention. Use aws logs put-retention-policy --log-group-name /lab/shop --retention-in-days 3 and confirm with aws logs describe-log-groups --log-group-name-prefix /lab. Then try an invalid value such as 45. Done when: you've seen the accepted value in the output and recorded what the invalid one does.
  3. Test patterns before using them. In the console, use the filter pattern test box with sample lines (or aws logs test-metric-filter --filter-pattern ERROR --log-event-messages "line one" "line two", which takes up to 50 messages and returns a matches list) to try ERROR, ERROR -TIMEOUT, and "INTERNAL SERVER ERROR" against six lines you invent. Done when: you have a small table of which lines matched each pattern and you can explain every result, including a case-sensitivity miss.
  4. Make a metric from logs. Create a metric filter on /lab/shop with aws logs put-metric-filter (pattern ERROR, metricValue=1, defaultValue=0, a namespace of your choice). Then send new events, some with ERROR. Done when: the metric shows counts in the console and you've confirmed that events sent before the filter existed were not counted.
  5. Extract a number. Write JSON log events like {"latency": 50, "requestType": "GET"} and create a metric filter using pattern { $.latency = * } with metric value $.latency. Done when: you can graph the Average of that metric and read your latency values off it.
  6. Subscription to Lambda (stretch). Create a small Lambda that decodes base64, gunzips and prints the payload, then attach it with aws logs put-subscription-filter (the function needs permission to be invoked by CloudWatch Logs). Done when: the function's own logs show the decoded events from your test log group.
