Elastic Load Balancing in Depth: ALB vs. NLB vs. GWLB, Target Groups and Health Checks

Once you run more than one server, something has to decide which one gets each request, and stop sending traffic to the one that just fell over. That's the load balancer. AWS has three current types that work at different network layers, and they share the same skeleton: listeners, target groups, health checks.

In one line

Elastic Load Balancing spreads incoming traffic across healthy targets in one or more Availability Zones; you choose an Application (layer 7), Network (layer 4) or Gateway (layer 3) Load Balancer depending on what you need to do with the traffic.

The big idea

A load balancer is a single front door with a receptionist who knows which back-office servers are awake. The clients only know the front door's address. You can add or remove servers behind it without clients noticing, and servers that fail their checks stop getting visitors.

The three types differ in how much they look at. ALB reads the request (URL, host, headers) so it can make smart routing decisions. NLB looks only at connections (TCP/UDP/TLS/QUIC), which is why it fits raw speed and static IPs. GWLB isn't for your own app servers at all: it's a doorway for traffic to pass through security appliances like firewalls.

This builds on the earlier EC2 digest, which introduced load balancing and Auto Scaling at a pairing level. This one goes deeper on the load balancer half. I quote no prices; the docs just say you pay for what you use and point to the pricing page.

Key terms

  • Load balancer: the single point of contact for clients that distributes incoming traffic across targets.
  • Target: a destination that receives traffic, such as an EC2 instance, a container, an IP address or (for ALB) a Lambda function.
  • Listener: a process that checks for connection requests using a protocol and port you configure.
  • Rule (ALB): a priority, one or more conditions and one or more actions on a listener.
  • Target group: a set of registered targets that a listener forwards to, with its own health check settings.
  • Health check: a periodic test request the load balancer sends to each target.
  • Load balancer node: the piece of the load balancer that ELB creates in each Availability Zone you enable.
  • Cross-zone load balancing: letting each node send traffic to targets in all enabled AZs rather than only its own.
  • OSI layers 3, 4, 7: network layer (IP packets), transport layer (TCP/UDP connections), application layer (e.g. HTTP).
  • Internet-facing / internal: whether the nodes have public IPs or only private ones.
  • Fail open: when every target looks unhealthy, the balancer sends traffic to all of them anyway.
  • GENEVE: the tunnelling protocol (port 6081) GWLB uses to talk to appliances.

How it works

0. Grounding: why not just give clients a server's address?

If clients connect straight to one instance, that instance is a single point of failure and a ceiling on capacity. With ELB, clients resolve the load balancer's DNS name and get the IP addresses of its nodes; a node picks a healthy target and forwards to it using the target's private IP. The docs note the DNS entry has a time-to-live of 60 seconds so addresses can change quickly as ELB scales the balancer. Targets don't need public IPs, even behind an internet-facing balancer.

1. Three types, three layers

  • Application Load Balancer (ALB): works at the application layer (OSI layer 7). It evaluates listener rules in priority order and can route by the content of the request: path conditions, host conditions, HTTP headers and methods, query parameters, source IP. It can also redirect, return a custom HTTP response, authenticate users, and register Lambda functions as targets. Target groups speak HTTP or HTTPS (HTTP/1.1 by default, HTTP/2 or gRPC optionally).
  • Network Load Balancer (NLB): works at layer 4. The docs say it can handle millions of requests per second. Target group protocols include TCP, UDP, TCP_UDP, TLS, QUIC and TCP_QUIC. It gets a static IP per enabled AZ and you can optionally attach one Elastic IP per subnet on an internet-facing one. It supports registering targets by IP, including outside the VPC.
  • Gateway Load Balancer (GWLB): works at layer 3. It exists to deploy, scale and manage virtual appliances like firewalls, intrusion detection/prevention and deep packet inspection systems. It acts as a transparent gateway (one entry and exit point), listens for all IP packets on all ports, and exchanges traffic with appliances via GENEVE on port 6081.
  • Classic Load Balancer: previous generation; the docs recommend migrating. Not covered further.

Which do I pick? (my reading of the docs, not an official decision tree.) Need to route by URL path or host header, or use Lambda targets: ALB. Need static IPs, UDP/TCP/TLS/QUIC, or very high connection volume: NLB. Need to push traffic through third-party or in-house inspection appliances: GWLB. Simplification flag: this is a rule of thumb; the full feature comparison lives on the ELB product comparison page, which I did not fetch. One docs-stated twist: an NLB target group can even register an Application Load Balancer as a target type.

2. Listeners, rules and target groups

A listener waits for connections on a protocol and port. On an ALB, each listener has a mandatory default rule and optional extra rules; each rule has a priority, conditions and actions, and when its conditions match, the actions run (typically "forward to target group X"). On an NLB, the listener forwards to a target group.

A target group has a target type chosen at creation, which you can't change afterwards:

  • instance: register by instance ID; traffic goes to the instance's primary private IP on its primary network interface.
  • ip: register IP addresses. For an ALB these must come from the VPC subnets or the RFC 1918 and RFC 6598 private ranges the docs list; publicly routable IPs are not allowed. This is how you reach peered VPCs, on-premises servers over Direct Connect or VPN, or multiple apps sharing a port on one instance.
  • lambda: a single Lambda function (ALB).

A target can be registered in several target groups, and the docs say each target group can be used with only one load balancer. Registering a new target: traffic starts once registration completes and the first health check passes. Deregistering: the balancer stops routing new requests immediately and the target goes into draining while in-flight requests finish; the ALB attribute deregistration_delay.timeout_seconds defaults to 300 (range 0 to 3600).

Routing algorithm per ALB target group: round_robin (default), least_outstanding_requests, or weighted_random. NLB picks a target by a flow hash (protocol, source and destination IP and port, and for TCP the sequence number), so a single TCP connection stays on one target for its life. GWLB uses a 5-tuple flow hash by default so a flow always hits the same appliance.

3. Health checks: how a balancer notices a dead server

The ALB docs give these settings (API names) and defaults for instance/ip target groups:

  • HealthCheckProtocol: HTTP (default) or HTTPS, using GET. HealthCheckPath default /. HealthCheckPort default is the port the target takes traffic on.
  • HealthCheckIntervalSeconds: default 30 (range 5 to 300).
  • HealthCheckTimeoutSeconds: default 5 (range 2 to 120).
  • HealthyThresholdCount: default 5 (range 2 to 10). UnhealthyThresholdCount: default 2 (range 2 to 10).
  • Matcher (success codes): default 200; HTTP values can be 200 to 499, as a list or range.

Worked timing (my arithmetic on the defaults). With the default 30-second interval and an unhealthy threshold of 2, a target that stops responding needs two consecutive failures, so roughly 60 seconds of failed checks before it's taken out of service. To come back, five consecutive successes at 30 seconds is roughly 150 seconds. The docs call the interval "approximate", so treat these as ballpark. A newly registered target is the exception: it needs to pass just one initial health check.

Health states: initial, healthy, unhealthy, unused (not registered, group not used in a listener rule, AZ not enabled, or instance stopped/terminated), draining, and unavailable (health checks disabled). Reason codes starting with Elb. are balancer-side, Target. are target-side; for example Target.ResponseCodeMismatch and Target.Timeout.

Fail open. If a target group contains only unhealthy targets, the ALB routes to all of them anyway. The reasoning I took from the docs: if everything looks dead, sending to something beats sending to nothing. The docs also let you set target group health thresholds (minimum healthy count or percent) that trigger DNS failover (the zone's IPs are removed from DNS) and routing failover (send to all targets, healthy or not, in that zone). Docs example: two AZs of 10 targets, 6 fail in AZ B, threshold 50%: with cross-zone off, AZ B is at 40% and fails over; with cross-zone on, the pooled 14 of 20 is 70% and nothing fails over.

4. Availability Zones, nodes and cross-zone balancing

Enabling an AZ makes ELB create a node there. Registered targets in an AZ you haven't enabled get no traffic. An ALB requires at least two AZs. By default (when cross-zone is off) each node only sends to targets in its own AZ, which can produce uneven load. The docs' example: 2 targets in AZ A, 8 in AZ B, and DNS splits clients 50/50 between nodes. Cross-zone off: each A target gets 25%, each B target 6.25%. Cross-zone on: every one of the 10 gets 10%.

Defaults differ by type (docs): ALB has it always on at the load balancer level, though it can be disabled per target group; NLB and GWLB have it off by default and you can toggle it.

5. Internet-facing vs. internal, and how it ties to Auto Scaling

An internet-facing balancer's nodes have public IPs; an internal one has only private IPs and serves clients that can reach the VPC. Both talk to targets over private IPs. A classic two-tier pattern from the docs: internet-facing balancer in front of web servers, internal balancer in front of app servers.

With instance targets you can attach a target group to an Auto Scaling group; the group registers launched instances and deregisters terminated ones for you. That is the link to the next concept (Auto Scaling in depth).

Gateway Load Balancer plumbing. Consumers reach GWLB through a Gateway Load Balancer endpoint (a kind of VPC endpoint). You put the endpoint and the application servers in different subnets, so the endpoint can be the next hop in the application subnet's route table. Traffic goes consumer VPC, endpoint, GWLB in the provider VPC, appliance, and back. The docs stress you are responsible for choosing and trusting the appliance software; AWS doesn't guarantee its security or reliability.

Why it matters

Load balancers are how "one server" turns into "a service". Health checks and AZ choices decide whether a failure is invisible or an outage, and the cross-zone default is a classic source of uneven load. Picking the wrong type is expensive to undo, so knowing the layer distinction up front helps.

Remember this

  • All three current types share listener, target group and health check concepts; they differ by layer: ALB (7, request-aware), NLB (4, connection-level), GWLB (3, appliances via GENEVE on 6081).
  • Health is per target group. Defaults for an ALB: 30 s interval, 5 s timeout, 5 passes to heal, 2 fails to eject.
  • If every target looks unhealthy, an ALB fails open and sends to all of them.
  • Cross-zone balancing is on for ALB by default but off by default for NLB and GWLB, which changes how evenly targets are loaded.
  • Target type (instance, ip, lambda) is fixed at target group creation; ip targets must be private addresses.

Try it yourself

Projects 1 to 3 run locally with no AWS account. Projects 4 and 5 touch AWS and may incur charges (load balancers are billed while they exist); delete everything afterwards. I did not run any AWS commands for this digest. I checked the arithmetic in 1 and 2 by hand against the docs' examples.

  1. Round-robin vs. cross-zone simulator. Model 2 AZs, with node A getting 50% of requests and node B 50%, and target counts you choose. Compute per-target share with cross-zone on and off. Done when: 2 and 8 targets reproduce 25% / 6.25% (off) and 10% each (on), and you can explain why.
  2. Health-check state machine. Implement a target that flips between up and down on a schedule and a checker with interval, unhealthy threshold and healthy threshold parameters. Done when: with 30 s, 2 and 5 your log shows the target ejected after about 60 s of failures and restored after about 150 s of successes.
  3. Mini load balancer. In any language, start three tiny HTTP servers and a proxy that round-robins across the healthy ones, polling a /health path. Kill one server. Done when: requests keep succeeding and the dead server stops receiving traffic. Then kill all three and decide what your proxy should do; compare with ALB's fail-open behaviour.
  4. Path-based routing on ALB (small cost). Create an ALB with two target groups and a rule that forwards /api/* to one and everything else to the default. Done when: two different test pages come back from the same DNS name by path, and you can point at the rule priority and default rule in the console. Delete the load balancer after.
  5. Read a target's health. With any target group, run aws elbv2 describe-target-health --target-group-arn <arn> (I'm writing this from memory of the CLI; check it against the CLI reference). Done when: you can explain each state and reason code it returns using the docs' tables.
