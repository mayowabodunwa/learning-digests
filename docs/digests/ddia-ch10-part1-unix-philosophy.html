SYSTEMS · CH.10 DIGEST (PART 1)

Batch Processing with Unix Tools

This chapter is a turn: the first nine chapters were mostly about systems that answer requests right away (a database query, an API call). This one is about systems that chew through a big pile of data on their own schedule and hand you an answer later. Before getting anywhere near MapReduce or Hadoop, the chapter starts somewhere much smaller and older: five ordinary Unix commands chained together. That small example carries almost every idea the rest of the chapter builds on, so Part 1 slows down and sits with it.

In one line

Batch processing means running a job over a big, fixed pile of data and getting an answer later rather than instantly, and a plain Unix pipeline (small programs, each doing one thing, connected by a shared "just bytes" interface) already shows you why that style of processing scales so well.

The big idea

Most of the systems this book has covered so far are built around a request and a response: you ask, you wait a little, you get an answer, and how long that wait is (the response time) is the thing you obsess over. Batch processing flips that. You hand a job a large, fixed input, it runs for a while (minutes, hours, sometimes days) with nobody watching a spinner, and what you care about is throughput: how much data it can get through in a given amount of time, not how fast any single piece of it comes back. Before the chapter gets to distributed tools like MapReduce, it deliberately starts with a single machine and five small Unix commands piped together, because that tiny example already contains the core ideas: programs that each do one small thing well, a shared interface simple enough that any of them can feed any other, and a design that makes it easy to inspect, restart, and trust what happened. Those ideas don't go away once you scale up to thousands of machines, they just get bigger clothes.

Key terms

  • Service (online system) — waits for a request and tries to answer it as fast as it can. Response time and availability (can a client even reach it) are what you measure.
  • Batch processing system (offline system) — takes a large, fixed amount of input, runs a job over all of it, and produces output. Nobody is usually sitting there waiting on it, so it's normally scheduled to run on its own (say, once a night).
  • Stream processing system (near-real-time / nearline) — sits between the two: like a batch job it produces output without being asked, but it reacts to events shortly after they happen instead of waiting for a whole fixed dataset. Covered properly in the next chapter, mentioned here only to place batch processing on the map.
  • Throughput — how much data a job gets through per unit of time. The main thing you optimize for in batch processing, the way response time is the main thing you optimize for in a service.
  • Unix pipe — a way of connecting the output of one program directly to the input of another (the | symbol in a shell), with a small in-memory buffer, so data can flow between programs without ever being written to disk in between.
  • stdin / stdout ("standard in" / "standard out") — the default input and output channels a program reads from and writes to. If you don't redirect them, stdin is your keyboard and stdout is your screen; pipes and files let you redirect either one.
  • Working set — the amount of data a job needs to keep in memory with fast, random access while it runs. Whether a job fits comfortably on one machine often comes down to the size of its working set, not the size of its whole input.
  • External sort / mergesort — a way of sorting data that's too big to fit in memory: sort what fits into memory-sized chunks, write each sorted chunk to disk, then merge the sorted chunks together. It leans on sequential disk reads, which are far cheaper than random ones.
  • Uniform interface — an interface simple enough that wildly different things (a file, a network socket, a keyboard, a printer) can all be used the same way. In Unix, that shared interface is "a sequence of bytes, read or written through a file descriptor."
  • Loose coupling / inversion of control — a program that doesn't hardcode where its input comes from or where its output goes, so whoever runs it (a shell user, in this case) gets to decide how to wire it up.

How it works

Start with the grounding idea: not every system is built to answer a question the instant it's asked. Kleppmann's chapter opens by splitting data systems into three rough families. A service sits and waits for requests, one at a time, and tries to answer each one quickly (a web server, a database, a search index all behave this way, and you'd notice immediately if one suddenly got slow). A batch processing system is the opposite in shape: you hand it a large, already-complete pile of input, it works through the whole thing without anyone waiting on an individual answer, and it's usually kicked off on a schedule (nightly, hourly) rather than by a person clicking a button. A stream processing system sits in between: like a batch job it isn't answering a single request, but instead of chewing through a fixed pile of data it reacts to events as they arrive, so its results show up much sooner. This digest, and the rest of Chapter 10, is about the middle one: batch processing. Streaming gets its own chapter next.

1. A tiny batch job: finding your busiest pages with five commands

Picture a web server that appends one line to a log file for every request it serves, something like a timestamp, the visitor's IP, the page requested, and the response status. Say you want to know your five most-requested pages. You don't need to write a program for that. In a Unix shell, a chain like this does the whole job:

cat access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -n 5

Reading it left to right: cat streams the log file out as bytes. awk '{print $7}' splits every line on whitespace and keeps only the 7th field, which (given a typical log line layout) happens to be the requested URL. sort puts every URL alphabetically next to its other occurrences, so if a URL was requested 40 times, you now have 40 identical lines in a row. uniq -c collapses each run of identical adjacent lines into one line with a count in front. The second sort -rn sorts by that count, numerically, largest first. head -n 5 keeps only the top five lines and throws the rest away. Run this over gigabytes of log data and it typically finishes in seconds, and if you decide you'd rather see the top IP addresses instead of top pages, you just swap which field awk prints; nothing else in the chain has to change.

You could write the same analysis as a small program instead: open the file, keep a hash table mapping URL to count, increment it for each line, then sort the hash table's entries at the end and print the top five. That's a perfectly reasonable program, and which style you reach for is partly taste. But the two approaches don't just look different, they actually do the work differently, and that difference is worth pulling apart on purpose because it's the same trade-off you'll meet again once jobs get too big for one machine.

2. Sorting on disk vs. a hash table in memory

The hash-table version keeps every distinct URL and its running count sitting in memory, so it can look up and update a counter in roughly constant time. Whether that's a fine strategy depends entirely on the job's working set: the amount of data it needs fast, random access to at once. Here, the working set is just "one entry per distinct URL", not one entry per log line, so even a log with tens of millions of requests can have a modest working set if there are only a few thousand distinct pages. In a common case like that (a small to mid-sized site), the whole working set comfortably fits in memory (say, well under a gigabyte), and a hash table works fine, even on a laptop.

The pipeline version never builds a hash table at all. Instead it leans entirely on sort, and the trick is that once identical lines are sorted next to each other, counting duplicates is a cheap, purely sequential scan (that's exactly what uniq -c does). The advantage shows up once the working set is bigger than available memory: a good external sort doesn't need to hold everything in RAM, it can sort chunks that do fit in memory, write each sorted chunk out to disk, and then merge the sorted chunks back together, an approach usually called external mergesort. Merging sorted chunks only ever needs to read each one sequentially, and sequential disk access is a lot cheaper than jumping around randomly, so this scales gracefully even when the data is much bigger than memory. Worth naming the specific tool here rather than a universal claim: GNU coreutils' sort (the version you get on most Linux systems) automatically spills to disk once the input is larger than it can comfortably hold in memory, and it also automatically spreads the sorting work across multiple CPU cores. That's a property of that particular implementation, not a law of sorting in general, but it's exactly why the five-command pipeline above scales to large logs without you doing anything special: the likely bottleneck becomes how fast you can read the log file off disk in the first place, not memory.

3. The Unix philosophy: small tools, one shared interface

None of the above works by accident. It's the direct result of a design philosophy Unix was built around from early on. Doug McIlroy, who invented the Unix pipe, described the idea in 1964 with a plumbing metaphor: programs should connect "like a garden hose, screw in another segment when it becomes necessary to massage data in another way." That idea got written up more formally in 1978 as a short set of principles, boiled down here to the two that matter most for batch processing: make each program do one thing well, and expect the output of every program to become the input of some other program you haven't written yet, so don't clutter that output with anything extraneous. sort is a good example of the first rule taken seriously: it's a solid, well-optimized sorting implementation, and on its own that's basically it, that's all it does. It only becomes genuinely powerful once it's combined with something like uniq, which is exactly the second rule in action.

For that combining to actually work, every one of these small programs has to agree on the same input/output interface, otherwise "chain them together" is just wishful thinking. Unix's answer is about as simple as an interface can get: a file, or more precisely a file descriptor, which is just an ordered sequence of bytes. That single, boring interface is powerful precisely because it's shared by so many different things: an actual file on disk, a pipe connecting two processes, a keyboard, a terminal screen, even a network socket. By convention (not by hard requirement), most Unix text tools go one step further and treat that byte sequence as lines of ASCII text separated by the newline character, which is exactly what let awk, sort, uniq, and head all agree on what a "record" is in the pipeline above, without any of them having been written by the same team or even in the same decade.

4. Separating "what a program does" from "where its data comes from"

The other half of what makes Unix pipelines composable is that most Unix programs don't hardcode where their input comes from or where their output goes. Left alone, a program's stdin defaults to your keyboard and its stdout defaults to your screen, but a shell lets you redirect either one to a file, or connect one program's stdout straight to another program's stdin with a pipe. The program itself never needs to know or care which of those is happening. That separation of "the logic of what this program does" from "the wiring of where its bytes come from and go" is sometimes called loose coupling, or inversion of control: the program doesn't decide how it's wired up, whoever runs it does. In the log pipeline, you could drop in your own small program between two of the existing steps (say, one that turns raw IP addresses into country codes) as long as it reads stdin and writes stdout, and the rest of the chain wouldn't need to change or even notice.

This isn't unlimited, though. It works best for a program with a single input and a single output. A program that genuinely needs several distinct inputs, or needs to talk to a network connection directly rather than through stdin/stdout, has to wire that up itself, and loses some of the "just plug it into a shell pipeline" flexibility as a result.

5. Why these pipelines are easy to trust: transparency

The last piece is less about performance and more about confidence: Unix pipelines are unusually easy to inspect and safely retry. Unix commands normally treat their input files as read-only; running the five-command pipeline above a hundred times with different options never touches access.log itself, so there's no fear of damaging your source data by experimenting. You can also cut a long pipeline short at any stage, pipe just that much into a pager like less, and eyeball whether the output looks the way you expect before wiring up the rest, which turns "did that step even work" from a guess into something you can check directly. And because each stage just reads bytes and writes bytes, you can save any intermediate stage's output to a file and use that file as the starting point for the next stage, which means a failure three steps in doesn't force you to rerun the whole pipeline from scratch, just the part that broke. None of this needs a query planner or a fancy scheduler behind it, it falls straight out of "small programs, reading and writing bytes, that don't secretly mutate their input." That combination of simple building blocks and easy inspection is exactly what the rest of the chapter carries forward into distributed batch processing, which is where Part 2 of this digest picks up.

Why it matters

It's tempting to treat "just chain some Unix commands together" as a party trick that doesn't generalize, but the chapter's whole argument is the opposite: the properties that make that five-command pipeline good (small single-purpose tools, one shared and boring interface, logic kept separate from wiring, and safe, inspectable, restartable steps) are exactly the properties a distributed batch framework like MapReduce or Hadoop tries to reproduce across a cluster of machines instead of one. So the biggest limitation of the Unix approach isn't a design flaw, it's simply that it runs on a single machine. Once you outgrow one machine, you need something that keeps these same ideas but spreads the input, the computation, and the output across many machines instead, which is exactly where Part 2 of this digest (MapReduce and distributed filesystems) will pick up.

Remember this

  • Batch processing trades "answer this one request fast" for "get through this whole fixed pile of data", so throughput, not response time, is what you optimize.
  • A job's working set (not its total input size) decides whether an in-memory approach is fine or whether you need something that can spill to disk.
  • External mergesort scales past available memory by leaning on sequential disk I/O, which is much cheaper than random access; this is specifically how GNU coreutils' sort behaves, not a universal property of every sort implementation.
  • The Unix philosophy (small tools, each doing one thing, connected through a shared byte-stream interface) is what makes chaining arbitrary programs together actually work, and it's the same idea distributed batch frameworks scale up later in the chapter.
  • Transparency (read-only inputs, inspectable intermediate steps, restartable stages) is what makes these pipelines trustworthy to run and rerun, not just fast.

Try it yourself

  1. Build the five-command pipeline on real data. Find or generate a web server access log (many web frameworks and local dev servers produce one, or write a script that appends fake log lines). Reproduce a "top 5 most-requested pages" pipeline using awk/sort/uniq/head. Done when: you can change one flag (say, sort by client IP instead of URL) and get a different, correct top-5 list without touching the rest of the chain.
  2. Reimplement it as a program and compare. Write the same top-5 analysis in any language using an in-memory hash map/dictionary. Run both versions on the same log file and confirm they agree. Done when: both approaches produce identical output, and you can explain in your own words why the code lengths and mental models differ.
  3. Feel the working-set boundary. Generate two synthetic logs: one with only a handful of distinct URLs repeated millions of times, and one where nearly every line has a unique URL. Run your hash-map version on both and watch memory usage (with top, Activity Monitor, or a language-level memory profiler). Done when: you can point to the moment memory usage tracks "distinct URLs," not "total lines."
  4. Watch an external sort spill to disk. Generate a text file larger than a memory limit you set for yourself (for example, cap available memory with ulimit -v on Linux/macOS, or just pick a file larger than your machine's RAM), then run GNU sort on it while watching disk activity (iostat, Activity Monitor's disk tab, or similar). Done when: you can see disk I/O activity during the sort and the command still completes successfully despite the memory cap.
  5. Build two tiny "loosely coupled" programs. Write two minimal command-line programs (any language) that each only read stdin and write stdout: one that uppercases text, one that reverses each line. Compose them with a pipe in both orders. Done when: you can pipe them together two different ways and get two different correct results, with neither program knowing the other exists.
  6. Practice pipeline transparency. Take any 3-stage pipeline you've built above and deliberately save the output of stage 1 to an intermediate file. Kill/interrupt the pipeline partway through a rerun, then restart it from the saved intermediate file instead of from the very beginning. Done when: you can restart from the middle and get the same final answer as running the whole pipeline from scratch.
