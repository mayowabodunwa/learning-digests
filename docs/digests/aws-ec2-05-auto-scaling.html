AWS EC2 · CONCEPT 5 DIGEST

Auto Scaling in Depth: Launch Templates, Scaling Policies, Lifecycle Hooks and Warm Pools

A load balancer spreads traffic across servers. Auto Scaling decides how many servers exist, replaces broken ones, and adds or removes capacity as demand moves. This digest goes through the pieces: the group, the launch template it copies from, the policies that change its size, hooks that pause an instance mid-launch, and warm pools for slow-booting apps.

In one line

An EC2 Auto Scaling group keeps a fleet of instances between a minimum and maximum size, built from a launch template, resized by scaling policies, and customised at launch and termination with lifecycle hooks and optionally pre-warmed instances.

The big idea

The thing that finally clicked for me: an Auto Scaling group is a desired-state system. You tell it three numbers (minimum, desired, maximum) and what an instance looks like, and it works to make reality match. If an instance dies, the count is below desired, so it launches another. Scaling policies are simply things that change the desired number.

The docs also point out that Auto Scaling isn't only about growth: it's "also useful for maintaining a steady number of servers". There are no extra fees for Auto Scaling itself; you pay for the resources it uses (instances, EBS volumes, CloudWatch alarms). I quote no prices.

This digest extends the earlier EC2 digest (which covered ASG and ELB at pairing level) and the load balancing digest.

Key terms

  • Auto Scaling group (ASG): a collection of EC2 instances managed as a logical unit for scaling and management.
  • Minimum / desired / maximum capacity: the floor, the target and the ceiling for the number of instances.
  • Launch template: a saved set of instance settings (AMI ID, instance type, key pair, security groups and more) the group uses to launch instances.
  • Scale out / scale in: adding / removing instances.
  • Scaling policy: a rule that adjusts capacity in response to a metric or alarm.
  • Target tracking: a policy type where you pick a metric and a target value, and the group works to hold the metric near it.
  • Step / simple scaling: alarm-driven policy types that add or remove capacity by defined amounts.
  • Instance warmup: time a new instance takes to start contributing to metrics; until it ends, it isn't counted in the group's aggregated metrics.
  • Cooldown: a pause after a scaling activity before simple scaling can act again.
  • Health check grace period: time after an instance enters service before the group starts checking its health.
  • Lifecycle hook: a pause point (wait state) during launch or termination where you can run custom actions.
  • Warm pool: pre-initialised instances sitting beside the group, ready for a quick scale-out.

How it works

0. Grounding: the group and its three numbers

The docs' example: a group with minimum 4, desired 6 and maximum 12. Auto Scaling keeps the group from going below 4 or above 12, and tries to hold it at 6 unless policies move the desired number within those bounds.

Built-in features the docs list: health monitoring with replacement of impaired instances; custom health checks; balancing instances evenly across multiple AZs; multiple instance types and purchase options (Spot and On-Demand) in one group; automated replacement of interrupted Spot Instances (including Capacity Rebalancing); automatic registration and deregistration with load balancers; instance refresh for rolling updates; lifecycle hooks; and scale-in protection and custom termination policies for stateful or long-running work.

1. Launch templates: the blueprint

A launch template holds the AMI ID, instance type, key pair, security groups and other parameters. Compared with the older launch configuration, templates are versioned: you can keep a base configuration and create new versions (for example one with a new AMI and user data for testing). The docs recommend launch templates, and some features need them: you can't create a group that mixes Spot and On-Demand, or uses multiple instance types, with a launch configuration. Templates also support newer EC2 features the docs list, such as Systems Manager parameters in place of AMI IDs, io2 volumes, Capacity Reservations and Dedicated Hosts.

Detail worth noting: every parameter in a launch template is optional when creating it, but if the template has no AMI you can't add one when creating the group; if it has an AMI but no instance type, you can add one or more types at group creation. When settings change, new instances use the new template, existing ones aren't touched; instance refresh is the rolling-replacement tool for that. Health replacement likewise launches using the group's current settings.

Connecting threads: the AMI inside the template is what the first digest covered; the purchase options (Spot/On-Demand mix) are from Concept 2; the security groups are what Concept 9 will go deeper on.

2. Scaling methods and the four policy flavours

The docs' scaling overview lists: set scaling limits, a default instance warmup, manual scaling, scheduled scaling, dynamic scaling, predictive scaling, plus controlling termination and suspending processes. I fetched the dynamic and predictive pages but not the dedicated scheduled scaling page, so I describe scheduled scaling only as "change capacity at set times" (a name-level description, flagged below).

3. Target tracking: the thermostat

You pick a metric and a target value; Auto Scaling creates and manages the CloudWatch alarms for you (don't edit or delete them yourself, per the docs). The docs' analogy is a thermostat. Example: target 50% average CPU. Above it, scale out; below, scale in.

Predefined metrics: ASGAverageCPUUtilization, ASGAverageNetworkIn, ASGAverageNetworkOut, ALBRequestCountPerTarget (needs a ResourceLabel to name the target group).

Metric rule: it must be a utilization-style metric that moves in proportion to the number of instances. The docs say these do not work: the load balancer's total RequestCount (doesn't change with group size), Latency, and raw SQS ApproximateNumberOfMessagesVisible; a custom "messages per instance" metric can work instead.

Details: use metrics at one-minute or finer intervals (EC2 metrics default to five-minute unless detailed monitoring is on); scale-in is deliberately more gradual; it rounds conservatively (scale out 1.5 instances' worth by adding 2); multiple target tracking policies are allowed if each uses a different metric, and the group scales out if any says out but in only if all say in; and it can't scale out for a metric below target. If a metric has no data its alarm goes to INSUFFICIENT_DATA and the group can't scale until data returns (this connects to the CloudWatch alarm digest).

4. Step and simple scaling: you own the alarm

With step or simple scaling, you create the CloudWatch alarm and the policy. Step policies define bands relative to the threshold, with a different adjustment per band (bigger breach, bigger response). Simple policies apply one adjustment and then wait out a cooldown. The docs "strongly recommend" target tracking where the metric rises and falls with capacity, and say as a best practice not to use simple scaling and cooldowns.

Adjustment types: ChangeInCapacity (+/- N), ExactCapacity (set to N), PercentChangeInCapacity (rounding: values above 1 round down; between 0 and 1 round to 1; mirrored for negatives; MinAdjustmentMagnitude sets a floor).

The docs' worked example (scale out +10% at 60, +30% at 70; scale in -10% at 40, -30% at 30; start at 10): metric hits 60, +1 to 11; metric hits 70, +30% of 11 = 3.3 rounds down to 3, so 14. Metric hits 40, -10% of 14 = 1.4 rounds down to 1, so 13. Metric hits 30, -30% of 13 = 3.9 rounds down to 3, so 10. I re-did that arithmetic and it matches.

Warmup vs. cooldown. Warmup (target tracking and step) excludes new instances from group metrics and avoids over-reacting; scale-in is blocked while a scale-out is warming up. Cooldown (simple scaling only) defaults to 300 seconds, and the docs list exceptions: target tracking, step and scheduled actions can act without waiting, and an unhealthy instance is replaced without waiting. Also: leave a wide margin between scale-out and scale-in thresholds to avoid flapping.

5. Predictive scaling: scale before the rush

Predictive scaling analyses historical load to find daily or weekly patterns, forecasts demand, and adds capacity ahead of time. The docs say it suits cyclical traffic (business hours), recurring on/off workloads (batch, testing), and apps that take long to initialise. Dynamic scaling is reactive; predictive is proactive. I read only the overview page, so details such as minimum history, forecast-only mode and how it combines with dynamic policies are not covered here.

6. Health checks and replacement

Instances start as healthy; Auto Scaling replaces an InService instance when it's notified of a problem from EC2 status checks, Elastic Load Balancing, VPC Lattice, EBS, or your own custom check. Unexpected terminations (Spot interruption, manual) lead to a replacement too. The health check grace period begins when an instance enters service. I did not fetch the grace-period page, so its default value is not stated here.

7. Lifecycle hooks: pause and do something

A hook puts an instance in a wait state at a transition so you can run a custom action (install software, register in a system, copy logs, etc.). The documented flow:

  1. Scale-out starts a launch; the hook moves the instance to Pending:Wait and runs your action.
  2. It stays there until you complete the lifecycle action or the timeout ends. The timeout is one hour by default, after which the launch continues (Pending:Proceed). Record a heartbeat to restart the timeout if you need longer.
  3. The instance goes InService and the health check grace period starts (and with a load balancer it's registered first).
  4. On scale-in, a load-balanced instance is first deregistered (draining connections if enabled). The hook then holds it in Terminating:Wait, again up to one hour by default, then Terminating:Proceed and terminate.

The docs also note that lifecycle hooks extend cooldowns, since a cooldown begins after the action completes or the timeout ends. I did not fetch the page on default result (continue vs. abandon) so I won't state it.

8. Warm pools: skip the slow boot

For apps with exceptionally long boot times, a warm pool is a set of pre-initialised instances beside the group. On scale-out, instances leave the pool and count toward desired capacity (a warm start). If the pool is empty you get a cold start, launching straight into the group.

  • Pool size default: maximum capacity minus desired capacity (desired 6, max 10 gives a pool of 4). Override with MaxGroupPreparedCapacity; set MinSize for a static floor.
  • Instance state in the pool: Stopped (pay only for volumes and Elastic IPs), Hibernated (RAM saved to the EBS root volume; pay for EBS incl. RAM storage), or Running (highly discouraged due to charges).
  • Lifecycle hooks matter here: without one, a slow-initialising instance could be stopped or put in service before it's ready.
  • Instance reuse policy returns scaled-in instances to the pool instead of terminating them.
  • Limitations from the docs: root device must be EBS to stop or hibernate; no weighted mixed-instance groups; no Spot in mixed-instance groups when using warm pools; the stop/hibernate doesn't wait for user data, so long user data can be interrupted.

Caution from the docs: a warm pool you don't need creates unnecessary cost; if first boot isn't noticeably slow, you probably don't need one. This ties back to Concept 3: Stopped instances still keep their EBS volumes.

Why it matters

Auto Scaling is what makes "replace, don't repair" practical, and it's the usual bridge between a load balancer and a cost-aware fleet. Choosing between target tracking and step scaling, handling warmup, and knowing the hook timeouts is where real incidents (flapping, premature traffic to unready instances) come from.

Remember this

  • An ASG maintains a desired count between min and max; policies change desired, health replacement restores it.
  • Launch templates are versioned blueprints; they're needed for mixed Spot/On-Demand and multiple instance types.
  • Prefer target tracking when the metric moves with capacity; the docs discourage simple scaling and cooldowns.
  • Warmup keeps new instances out of the metric average; cooldown only applies to simple scaling (default 300 s).
  • Lifecycle hooks pause at Pending:Wait and Terminating:Wait for up to an hour by default; warm pools trade standby cost for faster scale-out and are only worth it for slow boots.

Try it yourself

Projects 1 to 3 are local simulations. Project 4 uses the AWS console or CLI and creates billable resources, so use a small group and delete it. I did not run any AWS commands for this digest, and I do not give CLI commands here for that reason: use the console or look up the exact options in the CLI reference.

  1. Desired-state loop. Write a small simulation with min, desired and max, a list of "instances", and a loop that randomly kills one. Done when: the group replaces it and never goes below min or above max even when you try to set desired outside the range.
  2. Step scaling calculator. Implement PercentChangeInCapacity with the docs' rounding rules and MinAdjustmentMagnitude. Done when: your function reproduces 10, 11, 14, 13, 10 from the docs' example.
  3. Thermostat vs. flapping. Simulate load and a group size; implement target tracking (target 50%) and a naive pair of alarms at 50/50 with no gap. Add a warmup delay. Done when: you can show the naive version oscillating and explain, using the docs' flapping advice, how a margin and warmup help.
  4. Real group (small cost). In the console, create a launch template, then a group with min 1, desired 1, max 2 across two AZs, then terminate the instance by hand. Done when: you see the group launch a replacement, and you can find the cause in the group's activity history. Delete the group afterwards.
  5. Lifecycle timeline. Draw (on paper) the timeline for one scale-out with a launch hook and a load balancer: wait state, heartbeat, complete, InService, grace period. Done when: you can say when registration with the load balancer happens relative to InService and what happens at the one-hour default.
