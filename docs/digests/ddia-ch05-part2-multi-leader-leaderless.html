Replication: Multi-Leader, Leaderless, and Concurrent Writes

Part 1 had one node taking every write. This final part asks what happens when more than one node accepts writes, either a handful of leaders or no leader at all. You gain resilience to outages and slow links. You pay with a new class of problem: two people change the same thing at the same time and the system has to decide what the truth is. It covers multi-leader replication, write conflicts, leaderless (Dynamo-style) replication with quorums, and how a database can tell "one write came after the other" from "they were concurrent".

In one line

Letting several nodes accept writes buys availability and low latency, and the price is conflicts: you need a defined way to detect concurrent writes and converge every replica on the same final value.

The big idea

With a single leader, there's one official order of writes, so "last write wins" is a meaningful sentence. Remove the single leader and there is no official order. Two writes made without knowledge of each other are concurrent, and neither is "later" in any meaningful way. Every design in this part is a way of living with that fact: avoid the conflict, resolve it with a rule, merge the values, or keep both and ask someone. A rule that quietly picks a winner and throws the rest away is easy to build, and it is also how data gets lost.

Key terms

  • Multi-leader replication (master-master, active/active): more than one node accepts writes, and each forwards its changes to the others. Each leader acts as a follower of the others.
  • Write conflict: the same record changed on two leaders concurrently.
  • Convergent: resolution that makes all replicas end at the same final value once all changes have replicated.
  • Last write wins (LWW): give each write a timestamp and keep the highest; discard the others.
  • CRDT (conflict-free replicated datatype): data structures for sets, maps, lists, counters, and so on that merge concurrent edits automatically in sensible ways.
  • Operational transformation: the conflict-resolution algorithm behind collaborative editors for ordered lists such as text.
  • Replication topology: the paths along which writes flow between leaders (circular, star, all-to-all).
  • Leaderless / Dynamo-style replication: any replica accepts writes directly from clients; there's no failover.
  • Quorum (n, w, r): n replicas hold a value; a write must be confirmed by w, a read must query r. If w + r > n the read and write sets overlap.
  • Read repair: a client that notices a stale replica during a read writes the newer value back to it.
  • Anti-entropy process: a background job that copies missing data between replicas.
  • Sloppy quorum / hinted handoff: accepting writes on reachable nodes outside a value's usual n "home" nodes, and forwarding them home when the network recovers.
  • Happens-before / concurrent: A happens before B if B knows about or builds on A; two operations are concurrent if neither knows about the other.
  • Siblings: concurrent values for one key that the database keeps side by side (Riak's term).
  • Tombstone: a deletion marker with a version number, so a removal isn't lost in a merge.
  • Version vector: one version number per replica (and per key), used to tell overwrites from concurrent writes. Close to, but not exactly, a vector clock.

How it works

Grounding first. In single-leader replication, if the leader is unreachable you can't write, and every write travels to wherever the leader sits. Two natural fixes: allow several leaders (multi-leader), or drop the leader idea entirely (leaderless). Both increase availability and cut latency. Both mean that two writes to the same data can happen at the same moment in different places. The word to hold on to is conflict.

Multi-leader replication: where it makes sense

Within a single datacenter, the source says the benefits rarely outweigh the added complexity. It shows up in three situations.

  • Multi-datacenter operation. One leader per datacenter, normal leader-follower replication inside each, and the leaders replicate to each other across datacenters. Compared with single-leader across datacenters: (a) performance: writes are handled locally and replicated asynchronously, hiding the inter-datacenter delay, whereas single-leader sends every write to the leader's datacenter; (b) datacenter outages: each datacenter keeps running independently and replication catches up later, whereas single-leader needs failover; (c) network problems: asynchronous cross-datacenter replication tolerates a flaky link better. The downside: concurrent edits in two datacenters must be reconciled. The source adds that multi-leader is often retrofitted onto databases, with pitfalls around autoincrementing keys, triggers and integrity constraints, and is "often considered dangerous territory that should be avoided if possible". Tools mentioned include Tungsten Replicator for MySQL, BDR for PostgreSQL and GoldenGate for Oracle.
  • Clients with offline operation. Think of a calendar app on your phone and laptop. Every device has a local database acting as a leader, and sync is asynchronous multi-leader replication whose lag may be hours or days. The source calls this the datacenter case taken to the extreme: each device is a "datacenter" with a very unreliable link. CouchDB is designed for this mode.
  • Collaborative editing. Each user's edits apply instantly to a local replica and replicate to others. Locking the document first avoids conflicts but equals single-leader with transactions. For faster collaboration, make the unit of change tiny (a keystroke) and drop locking, and you get all the conflict problems of multi-leader.

Handling write conflicts

The biggest problem. Picture a shared document title: user 1 renames it from A to B on leader 1 while user 2 renames A to C on leader 2. Both succeed locally. When the changes replicate, each leader sees a conflict. A single-leader database avoids this because the second writer blocks and waits, or is aborted and retries. In multi-leader, both writes succeed first and the conflict surfaces later, possibly too late to ask the user. You could detect conflicts synchronously (wait for every replica before reporting success), but then you lose multi-leader's main advantage and may as well use single-leader.

Conflict avoidance. Simplest: make sure all writes to a given record go through the same leader. For example, route a user's requests to their "home" datacenter. From that user's view it's single-leader. It breaks down when you reroute (a datacenter failed or the user moved).

Converging. In multi-leader there's no defined order, so replicas applying writes in the order they saw them would end up different (C on one, B on the other). Every scheme must be convergent. Options in the source:

  • Give each write a unique ID (timestamp, random number, UUID, or hash) and keep the highest. With a timestamp this is last write wins, popular but "dangerously prone to data loss".
  • Give each replica an ID and let writes from higher-numbered replicas win. Also loses data.
  • Merge the values somehow (the source's example: sort and concatenate to something like "B/C").
  • Record the conflict in a data structure that keeps all information and let application code (or the user) resolve it later.

Custom resolution logic. Many tools let you write resolution code that runs on write (a handler called as soon as the conflict is detected in the replication log, in a background process, quick, can't ask a user; Bucardo allows a Perl snippet) or on read (all conflicting versions are stored and returned together on the next read, the application resolves and writes back; CouchDB does this). Resolution usually applies per row or document, not per whole transaction.

Automatic resolution is error-prone when hand-written. The source cites a case where a shopping cart's resolution kept additions but not removals, so deleted items reappeared. Research lines it mentions: CRDTs (implemented in Riak 2.0), mergeable persistent data structures that track history like Git and use a three-way merge, and operational transformation behind Etherpad and Google Docs. The source calls database implementations "still young".

What counts as a conflict? Obvious: two different values in one field. Subtle: a room-booking system where two bookings for the same room and time are made on two different leaders, even though each leader checked availability first.

Multi-leader topologies

A topology is the path writes take between nodes. With two leaders there's one option. With more: all-to-all (everyone sends to everyone), circular (each node passes writes to the next; MySQL by default supports only this, per the source) or star (a root forwards to all; generalizes to a tree). In circular and star shapes, writes pass through several nodes, so each node has an ID and each write is tagged with the IDs it passed through; a node that sees its own ID ignores the change, preventing infinite loops. Circular and star have a weakness: one failed node interrupts the flow between others, and reconfiguring is usually manual. All-to-all is more fault tolerant because messages can take different paths. But all-to-all has a hazard: network links differ in speed, so a message can overtake another. An insert might arrive after the update that depends on it, at one replica. That is a causality problem like consistent prefix reads in Part 1, and timestamps don't fix it because clocks can't be trusted to be sufficiently in sync (Chapter 8). Version vectors (below) can. The source says conflict detection is poorly implemented in many multi-leader systems (at the time of writing, PostgreSQL BDR didn't provide causal ordering and Tungsten Replicator for MySQL didn't try to detect conflicts) and advises reading the docs and testing for the guarantees you assume.

Leaderless replication

Some stores drop the leader: any replica accepts writes directly from clients, either via the client sending to several replicas or via a coordinator that doesn't enforce an order. Some of the earliest replicated systems were leaderless; the idea returned after Amazon used it for its in-house Dynamo system, and Riak, Cassandra and Voldemort are open source stores inspired by it ("Dynamo-style"). The source stresses that Amazon's Dynamo is not the same as the AWS DynamoDB product, which uses a different architecture based on single-leader replication (per the book's footnote).

Writing when a node is down. Failover doesn't exist here. With three replicas and one rebooting, the client sends the write to all three in parallel, two accept it, and if two acks count as success the client moves on. When the missed node returns it's stale. So reads also go to several nodes in parallel, and version numbers decide which response is newer.

Catching up takes two mechanisms: read repair (the client sees one replica returned version 6 while the others returned version 7 and writes 7 back to the stale one; works well for frequently read values) and an anti-entropy process (a background process that copies missing data, in no particular order, possibly with significant delay). Not every system has both; per the source Voldemort doesn't have anti-entropy, and without it rarely read values can be missing from some replicas, reducing durability.

Quorums

With n replicas, a write needs w confirmations and a read queries r nodes. If w + r > n, the nodes you wrote to and the nodes you read from must overlap in at least one node, so you generally expect to see the latest value. Reads and writes sent to all n replicas in parallel; w and r say how many replies you wait for. Dynamo-style databases usually make n, w and r configurable. A common choice is odd n (3 or 5) with w = r = (n + 1) / 2 rounded up. A read-heavy workload might use w = n and r = 1: fast reads, but a single failed node makes all writes fail. With n = 3, w = 2, r = 2 you tolerate one unavailable node; with n = 5, w = 3, r = 3, two. If fewer than w or r nodes respond, the operation errors. Quorums need not be majorities; only the overlap matters. You can set w + r ≤ n for lower latency and higher availability, accepting a greater chance of stale reads.

Limits of quorum consistency

Even with w + r > n the source lists edge cases where you can read stale values: a sloppy quorum (the w writes may land on different nodes than the r reads); concurrent writes with no clear order (and picking a winner by timestamp can lose writes through clock skew); a write concurrent with a read, which may show on only some replicas; a write that succeeded on fewer than w replicas isn't rolled back where it did succeed, so later reads may or may not see a "failed" write; a node with the new value being restored from an older replica, dropping the count of new-value replicas below w; and unlucky timing even when everything works. So quorums look like they guarantee the latest value, but in practice w and r mainly adjust the probability of stale reads, and the source advises not treating them as absolute guarantees. Dynamo-style stores are generally for use cases that tolerate eventual consistency, and you usually don't get read-your-writes, monotonic reads or consistent prefix reads from them. Stronger guarantees need transactions or consensus.

Monitoring staleness. In leader-based replication, lag is easy to measure: subtract a follower's log position from the leader's. In leaderless systems there's no fixed write order, so it's harder, and with only read repair there's no bound on how old a value can be. Some research predicts the share of stale reads from n, w and r but it isn't common practice; the source's view is that for operability you want to quantify "eventual".

Sloppy quorums and hinted handoff

A network interruption can cut a client off from many nodes. In a big cluster the client can probably still reach some nodes, just not the n designated for a value. Choice: return errors, or accept the write on reachable nodes outside the usual n. The second is a sloppy quorum: still w and r successful responses, but they may include non-home nodes. (The source's analogy: locked out, you sleep on a neighbour's couch.) When the network heals, the temporary holder forwards the writes to the proper nodes: hinted handoff. This increases write availability, but even with w + r > n you can't be sure of reading the latest value until the handoff is done, so it's only an assurance of durability, not a true quorum. Per the source, sloppy quorums are optional in common Dynamo implementations: enabled by default in Riak, disabled by default in Cassandra and Voldemort (the book's statements).

Multi-datacenter. Leaderless fits multi-datacenter use because it already tolerates conflicts, interruptions and latency spikes. Cassandra and Voldemort count nodes in all datacenters in n and let you set how many per datacenter; writes go to all replicas but the client waits only for a quorum in its local datacenter. Riak keeps client communication local to one datacenter and replicates between clusters asynchronously, similar to multi-leader.

Detecting concurrent writes

Several clients can write the same key at once, so conflicts occur even with strict quorums (and also in read repair and hinted handoff). Because network delay varies, replicas can see the same writes in different orders. If each node just overwrote on receipt, replicas would stay permanently inconsistent. The source warns most implementations are poor at this: to avoid losing data, the developer needs to know a lot about the database's conflict handling.

Last write wins. Keep only the "most recent" value by timestamp. The quotes matter: concurrent writes have no true order, we're just forcing one. LWW converges but costs durability: of several concurrent writes all reported successful, only one survives and the rest are silently discarded, and it can even drop non-concurrent writes (the book points to the clocks chapter). It's the only conflict resolution Cassandra supports and an optional feature in Riak (the book's statements). It can be acceptable for caching. The only safe use is writing each key once and treating it as immutable; the source's example is Cassandra with a UUID as the key.

Happens-before. Operation A happens before B if B knows about, depends on, or builds on A. Two operations are concurrent if neither happens before the other. For any pair there are three possibilities: A before B, B before A, or concurrent. If one happened before the other, the later overwrites; if concurrent, you have a conflict to resolve. Importantly, concurrency isn't about literally overlapping clock time. It's about not knowing about each other. Two operations hours apart can be concurrent if a network problem kept one from learning of the other. (The source draws a comparison to relativity.)

Capturing happens-before with version numbers

Start with one replica. I'll use a shared to-do list (my own illustration, same mechanism as the source's example). The server keeps a version number per key, bumps it on every write, and stores it with the value.

  1. Rules: a client must read before writing. A read returns all values not yet overwritten plus the latest version number.
  2. A write includes the version number from the prior read and must merge together all values from that read.
  3. On receiving a write with version V, the server overwrites all values with version V or below (they've been merged in) and keeps all values with a higher version (they're concurrent with this write).
  4. A write with no version number is concurrent with everything: it overwrites nothing and shows up as another value on later reads.

Walk through: client 1 writes [milk] (version 1). Client 2, unaware, writes [eggs] (version 2) and the server keeps both. Client 1 then writes [milk, flour] based on version 1: it replaces the milk value but is concurrent with eggs, so the server keeps both. And so on. The server learns concurrency by comparing version numbers, without interpreting the values. No writes are lost, but clients end up having to merge the siblings.

Merging siblings. Picking one by timestamp is LWW and loses data. For something add-only (a list where items are only added) taking the union works. If removal is allowed, a union resurrects removed items, so deletions must leave a tombstone with a version number. Hand-merging is error-prone, which is why CRDTs exist; the source says Riak's datatype support uses them, including preserving deletions.

Version vectors. With several replicas accepting writes, a single number isn't enough: you need a version number per replica as well as per key. Each replica increments its own number on a write and tracks what it's seen from the others; the set is a version vector. A variant, the dotted version vector, is used in Riak 2.0, and Riak's encoded form is called causal context. As in the single-replica case, vectors travel to clients on reads and back on writes. They make it safe to read from one replica and write to another: siblings may appear, but no data is lost if siblings are merged correctly. (A version vector is sometimes called a vector clock; they are not quite the same, and for comparing replica state version vectors are the right structure, per the source.)

The chapter in review (its Summary)

  • Why replicate: high availability, disconnected operation, lower latency, and read scalability.
  • Three approaches: single-leader (all writes to one node, reads anywhere but possibly stale); multi-leader (several nodes accept writes and exchange change streams); leaderless (writes to several nodes, reads from several in parallel to detect and fix stale data).
  • Trade-off: single-leader is popular because it's easier to understand and has no conflict resolution. Multi-leader and leaderless can be more robust against faulty nodes, network interruptions and latency spikes, at the cost of being harder to reason about and giving only very weak consistency guarantees.
  • Sync vs async has a big effect during faults: promoting an asynchronously updated follower can lose recently committed data.
  • Lag effects and the guarantees that address them: read-after-write, monotonic reads, consistent prefix reads.
  • Multi-leader and leaderless allow concurrent writes, hence conflicts; an algorithm can tell happens-before from concurrent, and concurrent updates can be merged.

Why it matters

Dynamo-style quorums, "tunable consistency" settings, calendar and note-taking sync, collaborative editors, and multi-region databases all rely on ideas in this part. When a vendor says a database is "eventually consistent" or lets you pick a consistency level, you now know what's being traded and where silent data loss can come from (LWW is the big one).

Remember this

  • Multi-leader suits multi-datacenter, offline clients and collaborative editing, but concurrent writes mean conflicts. Avoiding them (routing a record to one leader) is the simplest cure; otherwise you need a convergent rule.
  • Last write wins converges but silently discards concurrent writes; it's only safe for immutable-key or loss-tolerant uses like caches.
  • Leaderless replication has no failover; clients write to and read from several nodes, with read repair and anti-entropy catching stragglers.
  • With quorums, w + r > n makes read and write sets overlap, but sloppy quorums, concurrency and partial failures mean it isn't an absolute guarantee.
  • Two operations are concurrent if neither knew of the other, regardless of clock time; version numbers (vectors with many replicas) detect this, siblings must be merged, and deletes need tombstones.

Try it yourself

  1. Provoke a conflict. Simulate two leaders that each apply a rename locally and then exchange logs. First apply writes in arrival order and show the replicas diverge. Then add LWW with a (timestamp, replica ID) tiebreak. Done when both end equal, and you have written down which write was silently lost.
  2. Quorum explorer. For n = 5, enumerate every write set of size w and read set of size r and check whether they always overlap. Done when you can print a table for a few (w, r) pairs showing which settings guarantee overlap and which don't.
  3. Leaderless mini-store. Three in-memory replicas, a client that writes to all and counts acks, a node you can switch off, and a read that asks all and returns the highest version. Add read repair. Done when a node that missed writes is brought up to date by reads alone.
  4. Version-number server. Implement the single-replica algorithm: read returns (version, values), write takes (value, based-on version). Replay a two-client scenario and confirm no write is lost and that concurrent values appear as siblings. Done when a client that merges and rewrites collapses them to one value.
  5. Tombstones. Extend project 4 to a set that supports removing items. Show that a union-merge brings a removed item back, then fix it with tombstones. Done when a removal survives merging with a stale sibling.
