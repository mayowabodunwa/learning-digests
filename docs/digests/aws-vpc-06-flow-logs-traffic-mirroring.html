VPC Flow Logs and Traffic Mirroring

Two ways to see what your network is actually doing: Flow Logs keep a ledger of who talked to whom, and Traffic Mirroring hands a copy of the real packets to a tool that can open them.

In one line

Flow Logs record metadata about traffic (addresses, ports, bytes, accept or reject) and publish it to CloudWatch Logs, S3 or Firehose; Traffic Mirroring copies the packets themselves to a monitoring target for deep inspection.

The big idea

When something can't connect, you usually have a guess (security group? NACL? route?) but no evidence. Flow Logs give you evidence at the level of "this source tried this destination port and the answer was REJECT". They're cheap to reason about, they don't touch the traffic path, and they're what you reach for first. Traffic Mirroring is the heavier tool: it duplicates real packets, in full or truncated, to an appliance you run, so you can look inside the traffic (for threat detection, content inspection, or debugging a protocol). Think receipt versus security camera: a flow log is the receipt that says a transaction happened, a mirror is the camera footage.

Key terms

  • Flow log: a configuration that captures information about IP traffic going to and from network interfaces and publishes it as records.
  • Flow log record: one line describing a flow within one time window. A flow is characterised by a 5-tuple (source address, destination address, source port, destination port, protocol) per network interface.
  • Aggregation interval: the window during which packets of a flow are rolled up into one record. Maximum 10 minutes by default, or optionally 1 minute.
  • Subscription: the docs' word for the delivery path and permissions that send flow logs to a destination.
  • ENI: elastic network interface, the virtual network card that flow logs and mirrors attach to.
  • ACCEPT / REJECT: the action field on a record. REJECT includes traffic blocked by security groups or network ACLs.
  • Traffic mirror source / target / filter / session: the four building blocks of Traffic Mirroring. Source is the ENI to copy from, target is where copies go, filter says which traffic, session ties the three together.
  • VXLAN: an encapsulation format. Mirrored packets are wrapped in a VXLAN header so they can be carried to the target.
  • Out-of-band: the monitoring tool sits beside the traffic, not in its path.

How it works

Grounding: observing a network you can't plug into

In a physical data center you could clip a device onto a switch to watch traffic. In a VPC there is no physical wire, so AWS exposes observation as features of the virtual network. The two features differ in how much they capture and what they cost you. Per the docs, flow log data is collected outside the path of your traffic, so it doesn't affect throughput or latency. Traffic Mirroring is likewise described as sending traffic to out-of-band appliances.

1. Flow Logs: what you configure

Where you attach one. A flow log can be created for a VPC, a subnet, or a network interface. For a subnet or VPC, every network interface in it is monitored, including ones launched later (a new log stream or file appears once traffic flows on the new interface). You can also log interfaces that other AWS services created, such as load balancers, RDS, ElastiCache, Redshift, WorkSpaces, NAT gateways and transit gateways. For an individual network interface you must use the EC2 console or API.

What you choose. Three things: the resource, the traffic type (ACCEPT, REJECT or ALL), and the destination. Destinations are CloudWatch Logs, S3, or Data Firehose. Pricing is the "vended logs" charges described on the CloudWatch pricing page; I'm not quoting numbers.

CLI shape (from the reference page's example, with placeholder IDs):

aws ec2 create-flow-logs --resource-type VPC --resource-ids vpc-0123456789abcdef0 --traffic-type ALL --log-destination-type s3 --log-destination arn:aws:s3:::my-flow-log-bucket/vpc-logs/ --max-aggregation-interval 60

For CloudWatch Logs you instead pass --log-group-name plus --deliver-logs-permission-arn (an IAM role that lets EC2 publish). The reference lists --max-aggregation-interval as 60 or 600 seconds, default 600.

Timing. Not real time. After you create one it can take several minutes to start. After the aggregation window closes, delivery typically takes about 5 minutes to CloudWatch Logs and about 10 to S3, on a best-effort basis. Nitro-based instances always use 1 minute or less, whatever maximum you set.

Immutable. Once created you can't change a flow log's configuration or record format (not even the IAM role); delete it and create a new one. Deleting stops new records but leaves existing data in the destination.

2. Reading a flow log record

The default format is the version 2 fields, in this order: version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status. It's one text line with space-separated fields. You can't change the default format; to add or reorder fields you specify a custom format (at least one field).

Here's a made-up record in that shape (documentation addresses, fake IDs), followed by a reading of it:

2 123456789012 eni-0a1b2c3d4e5f60718 198.51.100.23 10.0.1.15 51514 22 6 12 1860 1761400000 1761400060 REJECT OK
  • Version 2, in account 123456789012, on that interface.
  • Source 198.51.100.23 port 51514 to destination 10.0.1.15 port 22. Protocol 6 is the IANA number for TCP (the docs say protocol is the IANA number).
  • 12 packets and 1,860 bytes in the window, start and end in Unix seconds.
  • REJECT with OK log status. Someone tried SSH and something said no. Per the docs REJECT covers security groups or NACLs not allowing it, and also packets arriving after a connection closed.

The log-status values are OK, NODATA (no traffic in the window) and SKIPDATA (some records skipped because of internal capacity or error).

Useful extra fields available in custom formats (all from the fields table): vpc-id, subnet-id, instance-id, tcp-flags (a bitmask: FIN 1, SYN 2, RST 4, SYN-ACK 18; flags can be OR-ed together over the window), pkt-srcaddr and pkt-dstaddr (the original packet addresses when an intermediate layer such as a NAT gateway is involved), flow-direction (ingress or egress) and traffic-path (how egress traffic leaves: same-VPC resource, internet gateway, virtual private gateway, peering, and so on). A "-" means not applicable or couldn't be computed. Some metadata fields are described as best-effort approximations.

Simplification: I describe "a record" as "one connection attempt". It isn't. A record is one flow's activity within one window on one interface, so one long connection can span many records, and a flow crossing two interfaces appears on both.

3. What Flow Logs do not capture, and other gotchas

The docs state flow logs do not capture all IP traffic. Not logged: traffic to the Amazon DNS server (if you use your own DNS server, that traffic is logged); Windows license activation; instance metadata (169.254.169.254); Amazon Time Sync (169.254.169.123); DHCP; traffic to the default VPC router's reserved address; ARP; traffic between an endpoint network interface and a Network Load Balancer network interface; mirrored source traffic (you see the mirrored target traffic only); and traffic on a short-lived regional NAT gateway.

Other limits worth knowing from the same page:

  • You can't enable flow logs for a peered VPC unless the peer is in your own account.
  • If traffic goes to a secondary private IP on an interface, dstaddr shows the primary private IPv4 address. To see the original, add pkt-dstaddr to a custom format.
  • VPC Flow Logs supports a maximum of 250 subscriptions per resource per account.
  • Some records can be skipped (SKIPDATA), so a flow log is a good picture, not a guaranteed complete audit trail.

4. Diagnosing with Flow Logs

The docs list diagnosing overly restrictive security group rules, monitoring what reaches an instance, and determining traffic direction as typical jobs. Here's the reasoning chain that ties back to the earlier security group and NACL topic. Security groups are stateful and NACLs are stateless, so a NACL that forgets the ephemeral return ports can produce REJECT records for the replies. Reading action together with flow-direction and the ports helps you tell which side refused. That last step is my own application of earlier material, not something the flow log page spells out; treat it as a starting hypothesis and confirm with the rules themselves.

To query at scale, the docs have a section on querying flow logs with Athena (not read in detail here).

5. Traffic Mirroring: copies of the packets

The four pieces. A source (an ENI of type interface, such as an EC2 or RDS instance's), a filter (rules), a target, and a session binding source, filter and target. The docs benefits list: no packet-forwarding agents to manage on your instances, capture at the network interface (which "cannot be disabled or tampered with from a user space"), and the freedom to send the copies to any security device.

Targets. A network interface of type interface, a Network Load Balancer with a UDP listener, or a Gateway Load Balancer endpoint. The docs recommend an NLB or GWLB endpoint for high availability, but warn you may see out-of-order delivery of mirrored packets with them; if your appliance can't cope, use a network interface as the target. A target can belong to a different account from the source.

Filters. Inbound and outbound rules, evaluated lowest number first, first match wins, much like NACL ordering. Each rule has an action (accept or reject), protocol, optional port ranges, and source and destination CIDR blocks. Two traps stated in the docs: with no rules, nothing is mirrored; and with no outbound rules, no outbound traffic is mirrored.

Encapsulation. Matching packets are wrapped in a VXLAN header and sent to the target. The destination port is 4789, the well-known VXLAN port. So the target's security group must allow UDP 4789 from the source, the source subnet's route table must be able to reach the target, and your monitoring software must be able to parse VXLAN. The docs also note the VNI is just a label you choose and shouldn't be treated as a trust boundary. Overhead: the Gateway Load Balancer example in the docs says the mirror adds 54 bytes of headers for IPv4 (74 for IPv6) to each packet, which matters against a maximum MTU of 8500 there.

Sessions and interplay with security rules. Each packet is mirrored once, but you can use several sessions on one source, evaluated by ascending session number, to send different subsets to different tools. Per the docs, inbound traffic dropped at the source by security groups or NACLs isn't mirrored, and mirrored outbound traffic isn't subject to the source's outbound security group rules.

Cost and support. You're billed hourly for each active session, even if the source was stopped or detached, until you delete the session, plus data transfer charges. Only certain instance families work as sources (the docs list them; Nitro v2 only for bare metal), so check the list before planning.

Flow Logs versus Traffic Mirroring at a glance

  • Captures: Flow Logs = per-flow metadata. Mirroring = the packets (optionally truncated).
  • Where it goes: Flow Logs = CloudWatch Logs, S3 or Firehose. Mirroring = an ENI, NLB or GWLB endpoint you run.
  • Effort: Flow Logs = a configuration. Mirroring = you operate the appliance and handle VXLAN.
  • Typical question: Flow Logs = "who tried to reach what, and was it rejected?" Mirroring = "what was actually inside that traffic?"

Why it matters

Almost every networking incident eventually comes down to evidence. Flow Logs turn "I think the security group is blocking it" into a REJECT line you can point at. Traffic Mirroring is how security teams feed IDS tools without installing agents. Both also connect straight to CloudWatch (the next area in the rotation), since flow logs can land in CloudWatch Logs and mirroring has its own CloudWatch metrics.

Remember this

  • Flow Logs = metadata records per flow per window, not packets, not real time, and not every kind of traffic.
  • You pick the resource (VPC, subnet or ENI), the traffic type (ACCEPT, REJECT, ALL) and a destination. You can't edit one after creating it.
  • Default record: 14 version-2 fields; a custom format adds things like pkt-dstaddr, flow-direction, traffic-path.
  • Traffic Mirroring = source + filter + target + session, packets wrapped in VXLAN on UDP 4789.
  • Mirror filters need explicit rules in each direction; no rules means nothing is mirrored.

Try it yourself

  1. Create a flow log. In a test VPC create a REJECT-only flow log to an S3 bucket or CloudWatch Logs group. Done when: aws ec2 describe-flow-logs lists it and you've noted the destination.
  2. Cause a REJECT on purpose. From your laptop try to connect to a port your instance's security group does not allow, wait for delivery (several minutes), and find the record. Done when: you can match srcaddr, dstport and action to what you tried.
  3. Write a parser. In any language, split a default-format record into the 14 named fields and print a one-line sentence ("198.51.100.23 -> 10.0.1.15:22 TCP, REJECT"). Done when: it handles - values and NODATA lines without crashing.
  4. Custom format. Create a second flow log with a custom --log-format including ${pkt-srcaddr}, ${flow-direction} and ${traffic-path}. Done when: you can explain what traffic-path says about a request leaving through your NAT gateway. (Remember: you can't edit the first flow log; make a new one.)
  5. Count top talkers. Extend the parser to sum bytes per source address and print the top five. Done when: the totals match a hand count on a five-line sample file you made up.
  6. Mirror a single interface. Create a traffic mirror target (a second instance's ENI), a filter that accepts inbound TCP 80, and a session. Allow UDP 4789 from the source in the target's security group, then run tcpdump -nn udp port 4789 on the target. Done when: you see VXLAN-wrapped packets arriving. Needs a supported instance family and a live account; I haven't run it. Delete the session afterwards because sessions are billed hourly.
