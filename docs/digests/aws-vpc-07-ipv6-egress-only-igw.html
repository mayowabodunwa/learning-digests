IPv6 in a VPC and the Egress-Only Internet Gateway

How a VPC gets IPv6 addresses, why IPv6 changes the "public vs private" conversation, and how the egress-only internet gateway lets private instances call out over IPv6 without letting the internet call in.

In one line

You can add IPv6 to a VPC alongside IPv4 (dual-stack); because IPv6 addresses are globally unique and public by default, the thing that keeps a private subnet private is routing, and the egress-only internet gateway is the IPv6 equivalent of "outbound only".

The big idea

Up to now our private subnets reached the internet through a NAT gateway. NAT exists largely because IPv4 addresses are scarce: many private addresses hide behind one public one. IPv6 has so many addresses that every instance can have its own globally unique one, so there's nothing to translate. That sounds like a security problem, since a public address could be reached from anywhere, but reachability in a VPC is controlled by routes, security groups and network ACLs, not by the address format. If a subnet has no route to the internet for IPv6, its instances are unreachable from the internet no matter how global their addresses are. If you want outbound-only behavior, you add a route to an egress-only internet gateway. Everything in this digest is a variation on that idea.

Key terms

  • IPv6: the newer IP address format. An address is 128 bits, written as 8 groups of 4 hex digits, and may be shortened by dropping leading zeros and replacing one run of all-zero groups with ::. e.g. 2001:0db8:85a3:0000:0000:8a2e:0370:7334 can be written 2001:db8:85a3::8a2e:370:7334.
  • Dual-stack: a VPC or subnet that supports both IPv4 and IPv6, independently of each other.
  • IPv6-only subnet: a subnet with IPv6 only. The docs say there is no migration path from an IPv4-only subnet to an IPv6-only one.
  • GUA: global unicast address, the globally routable kind of IPv6 address.
  • ULA: unique local address, the IPv6 private range (starts with fc or fd).
  • ::/0: the IPv6 "any destination" route, equivalent to 0.0.0.0/0 in IPv4.
  • Egress-only internet gateway (EIGW): a VPC component that allows outbound IPv6 communication to the internet and prevents the internet from initiating IPv6 connections to your instances.
  • Stateful: remembers a connection so the reply is allowed back without a separate rule.
  • BYOIP: bring your own IP addresses; you own the range, AWS advertises it.
  • IPAM: Amazon VPC IP Address Manager, a tool to plan, track and allocate address ranges.

How it works

Grounding: IPv4 recap and what's different in IPv6

In IPv4 every VPC has a CIDR block (a range like 10.0.0.0/16), mostly private ranges, and a public IPv4 address is mapped to a private one through NAT. In IPv6, the docs say the Amazon-provided addresses are "always advertised on the internet" and "globally unique, and therefore reachable over the internet", and you control actual reachability with routing, security groups and network ACLs. IPv4 can't be turned off in a VPC: the docs state you cannot disable IPv4 support for your VPC and subnets, since it is the default addressing system. IPv4 and IPv6 traffic are independent of each other.

1. Addressing: how IPv6 blocks are sized and chosen

Where the range comes from. A VPC must have an IPv4 CIDR block; IPv6 is optional. For IPv6 you can use an Amazon-provided block, a block allocated from an IPAM pool, or a range you bring (BYOIP). With the Amazon-provided option you can't choose the addresses yourself; the docs' example gets a /56, and you then carve a /64 for each subnet (the Step 1 walkthrough says to associate a /64 from that range with each subnet).

Sizes. From the comparison table: IPv4 VPC CIDRs run from /16 to /28, up to 5 per VPC (adjustable). IPv6 VPC CIDRs run from /44 to /60 in increments of /4, also up to 5 (adjustable). The same table gives IPv6 subnet sizes as /44 to /64 in increments of /4, while the migration page says to give each subnet a /64. I'll flag that these two pages read differently and stick with "a /64 per subnet" as the practical example the docs walk through.

Instance addresses. IPv6 addresses are assigned to instances from the subnet's IPv6 range, on the primary network interface. Elastic IPs aren't supported for IPv6; the docs say IPv6 addresses are static by default. All current generation instance types support IPv6 according to the migration page.

Public vs private IPv6. The docs now describe both. Public means advertised on the internet from AWS. Private IPv6 addresses (ULA ranges, or GUA ranges you own and mark private) are not and cannot be advertised; they're only available through IPAM, and the docs say traffic from them is dropped at the internet gateway edge. This digest focuses on the public kind because that's where the egress-only gateway matters.

Simplification: I say "IPv6 addresses are public by default". The docs say Amazon-provided addresses are globally unique and advertised, which is true for the standard setup; the private ULA/GUA option is the exception.

2. Turning IPv6 on: the four steps

The docs' sequence for an existing IPv4 VPC:

  1. Associate a CIDR with the VPC, then a /64 with each subnet.
  2. Update route tables. AWS automatically adds an IPv6 local route when you associate the block. For a public subnet add ::/0 to the internet gateway. For a private subnet add ::/0 to an egress-only internet gateway.
  3. Update firewall rules. Security groups need IPv6 rules (for example ::/0 as the source for HTTP). The docs say an outbound allow-all IPv6 rule is added automatically unless you modified the original outbound rules. The default network ACL gets IPv6 rules automatically; a modified default or custom NACL needs IPv6 rules added by hand. (That's the earlier security group and NACL topic showing up again.)
  4. Assign IPv6 addresses to instances. If an address won't respond, the docs say to check your operating system's IPv6 configuration.

Dual-stack means each step is done in addition to IPv4, not instead of it. A subtle trap: a route table cannot send ::/0 to an internet gateway and an egress-only gateway at the same time. The docs describe an error ("There are existing ipv6 routes with next hop as internet Gateway") that you resolve by removing the first route before adding the second.

3. The egress-only internet gateway

What it does. Per the docs, it is "horizontally scaled, redundant, and highly available", allows outbound IPv6 from your instances to the internet, and prevents the internet from initiating an IPv6 connection with them. It is for IPv6 only; for outbound-only IPv4 the docs point you to a NAT gateway.

How it behaves. It is stateful: it forwards traffic from instances to the internet or other AWS services, then sends the response back. You create one for your VPC and add a route ::/0 (or a narrower IPv6 range) to it in the route tables of the subnets you want to be outbound-only.

What you can't do. You can't attach a security group to an egress-only gateway. You control traffic with network ACLs on the subnet and security groups on the instances. Pricing: the docs say no charge for the gateway itself, but data transfer charges apply to EC2 instances that use internet gateways.

Why this is not "NAT for IPv6". A NAT gateway rewrites addresses. The egress-only gateway does not translate anything; the instance keeps its own global address. What it enforces is the direction in which connections may start. (The IPv4/IPv6 comparison page does list NAT64/DNS64 as a separate feature: a NAT gateway with NAT64 lets instances in IPv6-only subnets reach IPv4-only resources. That is a different thing from this gateway, and I haven't gone into it.)

CLI, both from the reference pages:

aws ec2 create-egress-only-internet-gateway --vpc-id vpc-0123456789abcdef0

aws ec2 create-route --route-table-id rtb-0123456789abcdef0 --destination-ipv6-cidr-block ::/0 --egress-only-internet-gateway-id eigw-0123456789abcdef0

(IDs are placeholders. The first page lists --vpc-id as the only required option; the second lists the IPv6 destination and EIGW options as shown.)

4. IPv4 versus IPv6 side by side

  • Internet access: IPv4 needs an internet gateway. IPv6 needs an internet gateway too, with the outbound-only variant being the egress-only gateway.
  • Outbound from private subnet: IPv4 uses a NAT gateway. IPv6 uses the egress-only gateway (the migration page says NAT gateways do not support IPv6 for this purpose; NAT64 is a separate case, see the flag in Sources).
  • Static addresses: IPv4 uses Elastic IPs. IPv6 has no EIPs because the addresses are static by default.
  • Mandatory? IPv4 is always there. IPv6 is optional in a VPC.
  • Charges: the docs say AWS charges for all public IPv4 addresses, whether on running instances or Elastic IPs. I haven't compared this to IPv6 pricing and am not claiming a number.

Why it matters

IPv6 is how you stop depending on scarce public IPv4 addresses and the per-address charges that come with them, and the egress-only gateway is what keeps database and application tiers unreachable from outside once they have globally unique addresses. It links back to route tables and the internet gateway (Concept 1), security groups and NACLs (Concept 3), and forward to peering and hybrid routing, where overlapping IPv4 ranges are a pain that IPv6 sidesteps.

Remember this

  • Dual-stack: IPv4 stays on, IPv6 is added, and each needs its own routes and firewall rules.
  • Amazon-provided IPv6 addresses are globally unique and advertised; routing plus SG/NACL decides reachability.
  • Private IPv6 subnet that needs to call out: route ::/0 to an egress-only internet gateway.
  • EIGW is IPv6 only, stateful, and takes no security group; NACLs apply at the subnet.
  • The same destination ::/0 can't point at both an IGW and an EIGW in one route table.

Try it yourself

  1. Add IPv6 to a scratch VPC. Associate an Amazon-provided IPv6 block and a /64 per subnet. Done when: the console's CIDRs tab shows the IPv6 block as associated and each subnet has its own /64.
  2. Read the auto-added route. Open a route table and find the IPv6 local route. Done when: you can say which entry covers instance-to-instance IPv6 traffic.
  3. Public IPv6 path. Add ::/0 to the internet gateway in a public subnet, add an IPv6 security group rule for SSH or ICMP, and connect to a test instance by its IPv6 address. Done when: you reach it from an IPv6-capable network. (Your own ISP may not offer IPv6; I haven't verified your network.)
  4. Egress-only path. Create an EIGW, route ::/0 from a private subnet to it, and from that instance run curl -6 https://example.com (or any IPv6-reachable site). Done when: the request succeeds while an inbound IPv6 connection to that instance from outside fails.
  5. Hit the route conflict. Try adding ::/0 to an EIGW in a table that already has ::/0 to an IGW. Done when: you've seen the error and fixed it by removing the first route.
  6. Address practice. Write a small script that expands 2001:db8:85a3::8a2e:370:7334 to full form and compresses it back. Done when: it matches the docs' example in both directions.
