Partitioning: Splitting Data Across Machines

Replication copies the same data to several machines. Partitioning does something different: it splits one big dataset into pieces so that no single machine has to hold or serve all of it. This chapter is about how to choose the pieces, how secondary indexes complicate that choice, what to do when you add or remove machines, and how a request finds the right machine. I'll lean on one picture throughout: a library where the books are shelved across many rooms.

In one line

Partitioning (also called sharding) spreads data and query load across nodes by giving each record to exactly one partition, and almost every design decision is about avoiding hot spots while keeping lookups, range scans, and rebalancing cheap.

The big idea

Past a certain size, one machine can't store the data or keep up with the queries. You break the data into partitions and place different partitions on different nodes. If the split is fair, ten nodes handle roughly ten times the data and throughput. If it's unfair (skew), one node becomes a hot spot and the rest sit idle, which defeats the point. The two main ways to decide which record goes where are by key range (sorted, great for range scans, risky for hot spots) and by hash of the key (even, but range scans are lost). On top of that come secondary indexes (two ways to partition them), rebalancing (don't move more data than necessary), and request routing (how does a client know where to go).

Key terms

  • Partition (shard): one slice of the dataset. The same idea has other names: shard in MongoDB, Elasticsearch and SolrCloud; region in HBase; tablet in Bigtable; vnode in Cassandra and Riak; vBucket in Couchbase.
  • Skew: an unfair split where some partitions get more data or load than others.
  • Hot spot: a partition with disproportionately high load.
  • Key range partitioning: each partition owns a continuous range of keys.
  • Hash partitioning: each partition owns a range of hash values of the key.
  • Compound primary key: a key made of several columns; in Cassandra only the first part is hashed to pick the partition and the rest sorts data within it.
  • Secondary index: an index on something other than the primary key (all cars with color red); it finds occurrences of a value rather than one unique record.
  • Document-partitioned (local) index: each partition keeps an index only over its own documents.
  • Term-partitioned (global) index: one index covering all partitions, itself split up by the indexed term.
  • Scatter/gather: sending a query to all partitions and combining the answers.
  • Rebalancing: moving data and load between nodes when nodes are added, removed, or fail.
  • Pre-splitting: configuring an initial set of partitions on an empty database.
  • Service discovery: the general problem of finding which address handles a request.
  • ZooKeeper: a coordination service many systems use to track which node owns which partition.
  • Gossip protocol: nodes spreading cluster-state changes among themselves.
  • MPP database: a massively parallel processing relational database, usually for analytics, which splits complex queries into parallel stages.

How it works

Grounding first. The chapter's footnote makes one thing clear: partitioning here has nothing to do with a network partition (a netsplit fault between nodes, which Chapter 8 covers). Same word, different thing. Partitioning is a deliberate decision to cut data up. Each partition is, in effect, a small database of its own, although a database may support operations that touch several partitions. Partitioned databases were pioneered in the 1980s by products such as Teradata and Tandem NonStop SQL and later rediscovered by NoSQL databases and Hadoop-based warehouses, for both transactional and analytic workloads.

Partitioning and replication together

Partitioning is usually combined with replication: each record belongs to exactly one partition, but copies of that partition live on several nodes. With leader-follower replication, each partition has its own leader on one node and followers on others, so a node can be leader for some partitions and follower for others. Everything from Chapter 5 applies per partition, and the choice of partitioning scheme is mostly independent of the replication scheme, so the chapter ignores replication from here on.

Partitioning key-value data

The goal: spread data and query load evenly. Randomly assigning records to nodes would spread data evenly, but then you can't tell which node holds an item and must ask all nodes. Better: assume a key-value model where you always access records by primary key, like looking up an entry in a paper encyclopedia, and assign by key.

By key range

Give each partition a continuous range of keys, like encyclopedia volumes. Knowing the boundaries tells you which partition has a key, and knowing which node has the partition tells you where to go. Ranges needn't be evenly spaced, because the data isn't (many words start with some letters). Boundaries can be set by an administrator or automatically. Used by Bigtable, HBase, RethinkDB, and MongoDB before version 2.4 (per the book).

Within a partition, keys can stay sorted, so range scans are easy: for sensor data keyed by timestamp you can fetch a whole month in one query. The downside is hot spots from access patterns. If the key is a timestamp and partitions are days, all of today's writes hit today's partition. A fix: put something else first, such as the sensor name, so writes spread across sensors. The cost is that fetching many sensors over a time range now needs one range query per sensor.

By hash of the key

Because of skew risk, many stores hash the key. A good hash function turns skewed or similar-looking inputs into evenly spread numbers (a 32-bit one gives 0 to 232 − 1). It doesn't need to be cryptographically strong: Cassandra and MongoDB use MD5, Voldemort uses Fowler-Noll-Vo. Be careful with built-in language hashes: in Java's Object.hashCode() and Ruby's Object#hash the same key can hash differently in different processes, so they may be unsuitable. Each partition then owns a range of hashes. Boundaries can be evenly spaced or pseudorandom (the latter is sometimes called consistent hashing).

A naming warning from the source: "consistent hashing" has nothing to do with replica consistency or ACID consistency; it's a particular approach to rebalancing. The book says it doesn't work very well for databases and is rarely used in practice, though some documentation still mentions it, and suggests just saying hash partitioning.

The cost of hashing is that you lose efficient range queries: neighbouring keys are scattered. In MongoDB's hash-based mode, a range query goes to all partitions; the source says Riak, Couchbase and Voldemort don't support range queries on the primary key. Cassandra's compromise: a compound primary key whose first column is hashed to pick the partition, while the other columns sort data within it. You can't range-search the first column, but with a fixed first column you can range-scan the rest. That models one-to-many nicely: key (user_id, update_timestamp) gets one user's updates in a time range, in order, from a single partition.

Skewed workloads and hot spots

Hashing helps but can't eliminate hot spots. If all requests are for one key (say a celebrity's activity), identical IDs hash identically. The source says most data systems cannot compensate for this automatically, so the application must: for a known hot key, add a random number to the start or end of the key. A two-digit random number would split writes across 100 different keys that can live on different partitions. The price: reads must now read all 100 keys and combine them, and you need bookkeeping to know which keys are split, since splitting everything would be wasteful overhead.

Partitioning and secondary indexes

Everything so far assumes access by primary key. A secondary index finds all occurrences of a value (red cars, articles containing a word). They are the bread and butter of relational and many document databases and the raison d'être of search servers like Solr and Elasticsearch. Some key-value stores, such as HBase and Voldemort, avoided them for implementation complexity; Riak began adding them. The problem is that they don't map neatly onto partitions, and there are two approaches. The running example is a used-car site partitioned by listing ID with indexes on color and make.

Document-partitioned (local) indexes. Each partition indexes only its own documents. A write touches one partition. But a read for "red cars" has no reason to find them all in one partition, so you must scatter/gather the query to all partitions and merge. That makes secondary-index reads expensive and prone to tail latency amplification (Chapter 1) even when run in parallel. Still widely used: the source lists MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud and VoltDB, and notes vendors recommend structuring partitioning so secondary-index queries hit one partition, which isn't always possible (especially with several secondary indexes in one query).

Term-partitioned (global) indexes. One index covers all partitions but is itself partitioned, differently from the data: perhaps colors a to r on one index partition and s to z on another. The term (like color:red) decides the partition (the word comes from full-text indexing). You can partition by the term itself (good for range scans, say on price) or by its hash (more even). Reads are more efficient: go to the one partition holding the term. Writes are slower and more complicated, since one document may touch several index partitions on different nodes. Keeping it perfectly in sync would need a distributed transaction, not supported everywhere, so updates are often asynchronous: right after a write, the index may not reflect it yet. The source's example is Amazon DynamoDB's global secondary indexes, which the 2014 developer guide says update within a fraction of a second normally but may have longer propagation delays when infrastructure faults occur. (Other users: Riak's search, and the Oracle data warehouse, which offers local or global.)

Rebalancing partitions

Over time throughput grows, datasets grow, and machines fail, so data and requests must move between nodes: rebalancing. Minimum requirements per the source: afterwards the load is shared fairly; the database keeps accepting reads and writes meanwhile; and no more data than necessary moves.

How not to do it: hash mod N. It looks easy (hash(key) mod 10 picks one of 10 nodes), but if N changes most keys must move. The book's example: a key with hash 123456 is on node 6 with 10 nodes, node 3 with 11, node 0 with 12. In a quick test of my own with 10,000 made-up keys going from 10 to 11 nodes, about 9 in 10 keys changed node. Far too much movement.

Fixed number of partitions. Create many more partitions than nodes (for example 1,000 partitions on 10 nodes, about 100 each). A new node steals a few partitions from each existing node until things are fair; removal reverses it. Only whole partitions move; the key-to-partition assignment never changes, only partition-to-node. The transfer takes time, so the old assignment serves requests meanwhile. More powerful machines can be given more partitions. Used by Riak, Elasticsearch, Couchbase and Voldemort. Catch: the number is usually fixed at setup and is effectively your maximum node count, so choose high enough for growth, but each partition has overhead, and partition size grows with total data. Too big makes rebalancing and recovery costly; too small wastes overhead; with a highly variable dataset size it's hard to hit "just right".

Dynamic partitioning. For key-range partitioning, fixed boundaries are risky (you could end up with everything in one partition), so HBase and RethinkDB create partitions dynamically: when one grows past a configured size (HBase default 10 GB, per the book) it splits in two; if lots of data is deleted, a small one merges with a neighbour, similar to a B-tree's top level. A half can then move to another node. Benefit: the partition count tracks data volume. Caveat: an empty database starts as one partition, so all writes hit one node until the first split; HBase and MongoDB allow pre-splitting, which for key ranges requires knowing the key distribution. It also works with hash partitioning (MongoDB since 2.4 does both).

Proportional to nodes. Cassandra and Ketama use a fixed number of partitions per node. Partitions grow with data while nodes stay fixed, and shrink when nodes are added. A new node randomly picks existing partitions to split and takes half of each. Random splits can be unfair but average out over many partitions (Cassandra default 256 per node, per the book); Cassandra 3.0 added a fairer algorithm. This needs hash partitioning, and matches the original definition of consistent hashing most closely.

Automatic or manual rebalancing

It's a gradient. Fully automatic is convenient but can be unpredictable: rebalancing is expensive (rerouting requests, moving lots of data) and can overload the network or nodes. Combined with automatic failure detection it can cascade: an overloaded node is slow, others declare it dead, rebalancing shifts more load onto the struggling system. Hence a human in the loop can help. Couchbase, Riak and Voldemort generate a suggested assignment but need an administrator to commit it (per the book).

Request routing

After rebalancing, the question is: for key "foo", which IP and port do I contact? That's an instance of service discovery, a general problem for anything reachable over a network. Three approaches:

  1. Clients contact any node (for example via a round-robin load balancer); if it doesn't own the partition it forwards the request and relays the reply.
  2. A routing tier that is partition-aware and forwards requests but handles none itself.
  3. Clients know the partition assignment and connect directly.

The hard part is how that component learns about assignment changes, and everyone must agree or requests go to the wrong place. Consensus protocols exist but are hard to implement (Chapter 9). Many systems use a coordination service like ZooKeeper: nodes register, ZooKeeper holds the authoritative partition-to-node map, and the routing tier or clients subscribe for changes. Per the book: LinkedIn's Espresso uses Helix (built on ZooKeeper) with a routing tier; HBase, SolrCloud and Kafka use ZooKeeper; MongoDB uses its own config servers and mongos routers. Cassandra and Riak use a gossip protocol among nodes (approach 1), avoiding an external dependency at the cost of more complexity in the nodes. Couchbase doesn't rebalance automatically, simplifying its design, and uses a routing tier called moxi. Finding IP addresses changes more slowly than partition assignment, so DNS often suffices.

Parallel query execution

Single-key reads and writes (plus scatter/gather) are about the limit of most NoSQL stores. MPP relational databases for analytics support far richer queries: a typical warehouse query has joins, filters, grouping and aggregation. The MPP optimizer splits it into stages and partitions that run in parallel on different nodes, which especially helps queries scanning large parts of the data. The source calls it a specialized topic and defers some techniques to Chapter 10.

The chapter in review (its Summary)

  • Goal: spread data and queries evenly and avoid hot spots; pick a scheme suited to the data and rebalance as nodes come and go.
  • Key range: sorted, efficient range queries, hot-spot risk if access clusters on nearby keys; usually rebalanced dynamically by splitting.
  • Hash: destroys ordering (range queries inefficient) but spreads load; usually a fixed number of partitions assigned several-per-node, though dynamic is possible. Hybrids with compound keys exist.
  • Secondary indexes: document-partitioned (cheap writes, scatter/gather reads) or term-partitioned (single-partition reads, multi-partition writes).
  • Routing ranges from partition-aware load balancing to parallel query engines. Partitions mostly operate independently, which is what lets them scale, but writes spanning several partitions are hard to reason about (what if one succeeds and one fails?), which the following chapters address.

Why it matters

"Why is one shard on fire?", "why is this query slow across the cluster?", "why did adding a node trigger a storm of data movement?" are all partitioning questions. Choosing a partition key is one of the most consequential schema decisions in a distributed database, and it's hard to change later.

Remember this

  • Partitioning splits the dataset so each record lives in exactly one partition; replication then copies each partition. Don't confuse it with network partitions.
  • Key range keeps order (range scans) but can create hot spots; hash spreads evenly but loses ordering. Compound keys can blend the two.
  • Hashing can't save you from one extremely hot key; the app may have to split it (and then reads fan out).
  • Local secondary indexes: cheap writes, scatter/gather reads. Global (term-partitioned): cheap reads, costlier and often asynchronous writes.
  • Avoid hash mod N for placement; use many fixed partitions, dynamic splitting, or partitions per node. And decide how requests find the owner of a key.

Try it yourself

  1. Mod N damage. Hash 10,000 keys with a stable hash (not your language's per-process one) and assign them by hash mod N. Count how many keys change node going from 10 to 11 nodes. Then use 100 fixed partitions with whole-partition moves and count again. Done when you can report both percentages.
  2. Hot spot lab. Simulate sensor writes keyed by timestamp into 4 range partitions and print writes per partition. Change the key to (sensor, timestamp) and compare. Done when you can show the skew drop and name the query that got more expensive.
  3. Salt a hot key. Send 10,000 writes to one key spread by a random suffix 0 to 9, then write the read that sums all ten. Done when totals match and you have a plan for tracking which keys are salted.
  4. Scatter/gather. Build 3 in-memory partitions of car records, each with a local color index. Write a global query that fans out and merges; then build a term-partitioned index and compare how many partitions each read and write touches. Done when you can print the counts.
  5. Mini router. Keep a partition-to-node map in a dict, a router function that forwards requests, and a rebalance function that moves one partition. Done when requests keep succeeding after the move, and you can describe what would happen if the router's map were stale.

Go deeper (optional)

Take any database you use and find out how it picks a partition for a row and whether its secondary indexes are local or global. Chapter 7 next asks what happens when one write must touch several partitions.
