AWS S3 · CONCEPT 10 DIGEST

S3 Object Lock, Retention & Legal Hold, Inventory and Storage Lens: Locking Data Down and Seeing What You Have

This last S3 concept covers two jobs that sit on top of everything before it. Object Lock makes object versions unchangeable for a time (the WORM model), and Inventory and Storage Lens tell you what's actually in your buckets and whether your settings are what you think they are.

In one line

Object Lock prevents object versions from being overwritten or deleted using retention periods (governance or compliance mode) and legal holds, S3 Inventory produces scheduled flat-file lists of your objects and their metadata, and S3 Storage Lens gives account- and organization-wide dashboards, metrics and recommendations about storage usage and configuration.

The big idea

Earlier digests gave you ways to protect data (versioning, MFA delete, encryption, access control) and to manage cost (storage classes, lifecycle). Two questions remain. How do you make data genuinely unchangeable for a period, even against someone with admin rights? And at scale, how do you find out what you have and whether the protections are actually switched on?

Object Lock answers the first with a write-once-read-many (WORM) model. Inventory and Storage Lens answer the second from two angles: Inventory is a detailed per-object list you can query like data; Storage Lens is an aggregated, dashboard-style view with recommendations.

Simplification label: Object Lock is a compliance-oriented feature with some irreversible settings, so please read the caveats before trying it. I describe the S3 behaviour only; whether it satisfies any regulation is a question for your compliance team. The docs say Object Lock has been assessed by Cohasset Associates for SEC 17a-4, CFTC and FINRA environments, and I don't go beyond that. I quote no prices.

Key terms

  • WORM: write once, read many; data can be read repeatedly but not changed or deleted for a period.
  • Object Lock: the S3 feature that applies WORM protection to object versions.
  • Retention period: a time during which an object version is locked, ending at a retain-until date.
  • Fixed retention: you set the retain-until date up front.
  • Variable retention: you set an event hold and a duration, and S3 fixes the date when you release the hold.
  • Governance mode: protected against most users, but those with a special permission can override.
  • Compliance mode: no user, including the root user, can overwrite or delete the version during retention.
  • Legal hold: protection with no end date, on or off by anyone with the right permission.
  • S3 Inventory: scheduled reports listing objects and metadata.
  • Manifest: a file listing the inventory output files.
  • S3 Storage Lens: analytics with dashboards, metrics and recommendations across buckets, accounts and organizations.
  • Free vs advanced tier: two Storage Lens metric sets; advanced adds metrics and features for an additional charge.

How it works

0. Grounding: what problem each one solves

  • Object Lock: "this data must not change or disappear for N years" (regulatory records, ransomware or accidental-delete protection).
  • Inventory: "list everything, with its encryption, storage class, replication status, lock state" (audits, batch jobs, migrations).
  • Storage Lens: "which buckets lack lifecycle rules, versioning or encryption, and where is my storage growing?" (fleet-level visibility).

1. Object Lock basics

Object Lock works only in buckets with versioning enabled, and it locks object versions, not keys. Key facts from the docs:

  • A version can have a retention period, a legal hold, or both.
  • Locking protects only the version named in the request. It does not stop new versions being written or delete markers being added on top (delete markers themselves aren't WORM-protected).
  • If you upload to a key whose existing version is locked, S3 creates a new version; the locked version stays locked.
  • You must enable Object Lock and versioning on a general purpose bucket before locking anything. After you enable Object Lock you can't disable it or suspend versioning for that bucket. Buckets with Object Lock can't be destinations for server access logs.

2. Retention periods and the two modes

A retention period has a retain-until date; after it passes, the version can be overwritten or deleted. You can set it per object version, or set a bucket default (a duration in days or years applied to each new version; an explicit per-object setting overrides the bucket default). You can extend a retention period later (a later date replaces the current one), but you can't shorten it in compliance mode.

Variable retention is the newer flavour: instead of a date, you turn an event hold on with a duration. While on, the version is protected and S3 shows a moving computed date. When you release the hold, S3 fixes the date at release time plus duration. If you also gave an explicit date, S3 treats it as a minimum and uses whichever is later. Durations run from 1 to 36,500 days or 1 to 100 years (the docs also say 1 year is counted as 365 days for policy conditions).

  • Governance mode: users can't overwrite, delete or alter lock settings unless they have special permissions. To bypass, a caller needs s3:BypassGovernanceRetention and must send x-amz-bypass-governance-retention:true. The docs note the console sends that header by default, so a user with the permission can delete there. Bypass does not affect a legal hold.
  • Compliance mode: the version can't be overwritten or deleted by any user, including the account's root user, for the retention period. The mode can't be changed and the period can't be shortened. The docs state the only way to delete under compliance mode before the date expires is to delete the associated AWS account. Treat that as a design fact: test with governance mode first, as the docs suggest.
  • Legal hold: same protection but no expiry, placed or removed by anyone with s3:PutObjectLegalHold. If a retention period ends but a legal hold is still on, the object stays protected, and vice versa.

What happens on delete attempts: a permanent delete (with a version ID) of a locked version returns 403 Access Denied; a simple delete returns 200 and adds a delete marker. Lifecycle rules keep working normally on locked objects but cannot delete a locked version. Lock settings persist across storage class transitions.

4. Setting it up (CLI shapes from the docs)

# create a bucket with Object Lock enabled
aws s3api create-bucket --bucket {bucket} --object-lock-enabled-for-bucket

# bucket default retention: 50 days, compliance mode
aws s3api put-object-lock-configuration --bucket {bucket} \
  --object-lock-configuration='{ "ObjectLockEnabled": "Enabled",
  "Rule": { "DefaultRetention": { "Mode": "COMPLIANCE", "Days": 50 }}}'

# per-object retention (governance)
aws s3api put-object-retention --bucket {bucket} --key {key} \
  --retention='{ "Mode": "GOVERNANCE", "RetainUntilDate": "2030-01-01T00:00:00" }'

# legal hold on / off
aws s3api put-object-legal-hold --bucket {bucket} --key {key} --legal-hold="Status=ON"

Notes: uploads with a retention period need a Content-MD5 or x-amz-sdk-checksum-algorithm header (the console adds one automatically); bucket policy condition s3:object-lock-remaining-retention-days can cap allowed retention, up to a 100-year maximum; replication of locked objects needs Object Lock on the destination and extra read permissions on the replication role (s3:GetObjectRetention, s3:GetObjectLegalHold), matching the replication digest; and Object Lock does not protect you from losing the encryption keys, because deleting a KMS key can make locked objects unreadable.

5. S3 Inventory

Inventory is a scheduled alternative to calling the synchronous List APIs over and over. It writes flat files listing objects and metadata for a bucket (or a prefix) on a daily or weekly schedule, in CSV, ORC or Parquet, to a destination bucket. The docs say it doesn't use List API calls and doesn't affect your bucket's request rate; weekly reports run every Sunday (UTC), and the first report can take up to 48 hours.

  • Destination bucket: must be in the same Region as the source, can be the same bucket or in another account, and needs a bucket policy letting S3 write (the console adds it for you; with the CLI or SDK you add it yourself).
  • Fields: bucket name and key are always included. Optional fields include size, last modified, ETag, storage class, encryption status, replication status, Bucket Key status, version ID and IsLatest (for all-versions lists), delete marker, multipart flag, Object ACL, checksum algorithm, Intelligent-Tiering tier, Object Lock mode/date/legal hold/event hold, and lifecycle expiration date.
  • Versions: choose current versions only, or all versions.
  • Encryption of the report: SSE-S3 or SSE-KMS with a customer managed key (the AWS managed aws/s3 key is not supported); S3 needs kms:GenerateDataKey in the key policy.
  • Eventual consistency: each list is a snapshot, so recent adds or deletes might be missing; the docs advise a HeadObject check before acting on an object. Objects aren't guaranteed to be in any order, and CSV key names are URL-encoded.
  • Uses: audits (encryption, replication, lock status), feeding S3 Batch Operations (CSV is suggested for that), and SQL queries with Athena and similar tools. The docs recommend a lifecycle policy to delete old inventory lists.

Compared with Storage Lens: Inventory is row-per-object detail you analyse yourself; Storage Lens is rolled-up metrics.

6. S3 Storage Lens

Storage Lens is a cloud-storage analytics feature giving organization-wide visibility into usage and activity, with contextual recommendations. Concepts from the docs:

  • Dashboards: an interactive dashboard with drill-down by organization, account, Region, storage class, bucket, prefix or Storage Lens group. The preconfigured default-account-dashboard covers your whole account, updates daily, and feeds the Account snapshot on the console Buckets page. You can't change its scope or delete it, though you can upgrade or disable it. You can create other dashboards scoped by Region, bucket or account (up to 50 per home Region).
  • Home Region: chosen at creation, can't be changed, and stores that dashboard's metrics.
  • Free tier: summary, cost optimization, data protection, access management (Object Ownership), event and performance metrics, collected daily and queryable for 14 days in the console.
  • Advanced tier (additional charge; I don't quote it): adds advanced cost and data-protection metrics, activity and detailed status-code metrics, prefix aggregation, CloudWatch publishing, contextual recommendations, expanded prefix reports. Data is queryable for 15 months. The docs say all metrics are retained 15 months but free ones are only available to query for 14 days.
  • Exports: a daily metrics export in CSV or Parquet to a general purpose bucket in the same Region as the dashboard configuration, or to an AWS-managed S3 table bucket.
  • Recommendations: suggestions, call-outs (outliers via a z-score over a 30-day trend, and significant-change call-outs) and reminders. The docs caution that a call-out isn't necessarily a problem.
  • Examples of questions it answers: which buckets lack lifecycle rules for incomplete multipart uploads older than 7 days (a link back to the multipart digest), which buckets aren't using versioning or replication, which Object Ownership settings are in use, and how many Object Lock-enabled bytes you have.
  • Scope note: it generates metrics only for general purpose buckets. For organization-wide dashboards you enable trusted access in AWS Organizations and can designate a delegated administrator.

Why it matters

Object Lock turns "we promise not to delete this" into something S3 enforces, which matters for regulated records and for ransomware or insider-delete scenarios, but its irreversibility makes it the S3 feature where a mistake is hardest to undo, so start in governance mode with a short period. Inventory and Storage Lens close the loop on the whole track: you can verify that encryption, versioning, replication, lifecycle and lock settings are really in place, rather than hoping. That completes the S3 area: from keys and consistency, through cost, protection and sharing, to scale and governance.

Remember this

  • Object Lock needs versioning, locks individual versions (not keys), and can't be turned off once enabled on a bucket.
  • Governance mode can be bypassed with a permission and header; compliance mode can't be, even by root; legal holds have no end date and are independent of retention.
  • A simple delete on a locked object adds a delete marker; a version-ID delete of a locked version returns 403.
  • Inventory = scheduled per-object reports (CSV/ORC/Parquet, daily or weekly, snapshot-style and eventually consistent); Storage Lens = aggregated dashboards and recommendations with free and advanced tiers.
  • Start Object Lock experiments in governance mode with short retention; compliance mode is effectively permanent for the period.

Try it yourself

Projects 1 and 2 are offline. Projects 3 to 5 use the AWS CLI on a scratch bucket. Use governance mode only, with a very short retention (for example 1 day), and never compliance mode in a real account you care about. The Object Lock commands are shaped from the docs; I did not verify the Inventory CLI JSON, so use the console for Inventory or check the CLI reference. Storage Lens advanced tier can cost money; stick to the free tier. I haven't run any of this against a live account.

  1. Lock-state evaluator (offline, ~1 hour). Model an object version with (mode, retain-until, legal-hold) and a caller (has bypass permission or not, sends header or not). Output whether delete, overwrite and shorten-retention are allowed. Done when it matches Fig 1 and the rule that a legal hold survives a governance bypass.
  2. Variable retention date calculator (offline, ~30 min). Implement the docs' rules: computed date while the hold is on, fixed at release plus duration, and the "later of the minimum and computed date" rule. Done when it reproduces the docs' examples (for instance release on 2027-01-01 with a 1-year duration fixes 2028-01-01).
  3. Lock one object. Create a bucket with --object-lock-enabled-for-bucket, upload a file, set governance retention to a date a day away with put-object-retention, then try to permanently delete that version. Done when you see the 403 and have also tried a simple delete and found the delete marker.
  4. Legal hold toggle. Put a legal hold on, try deleting the version, remove the hold, try again. Done when the second delete succeeds only once no retention remains and the hold is off.
  5. Inventory and Storage Lens tour. In the console, create an inventory configuration (CSV, daily) for the scratch bucket with the encryption status and Object Lock fields, and open the default-account-dashboard. Done when you've written down the free metrics you can see, and which questions you can answer from each (remember the first inventory report can take up to 48 hours).
