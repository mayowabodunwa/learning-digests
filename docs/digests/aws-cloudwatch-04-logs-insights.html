CloudWatch Logs Insights: The Query Language for Searching and Analysing Logs

Once logs are in CloudWatch, the real skill is asking them questions. Logs Insights is the query tool for that. This digest teaches you its query language from scratch: how a query is a pipeline of small commands, which fields every log event gets for free, and how to go from "something's wrong" to a count, a ranking or a chart.

In one line

A Logs Insights query is a short pipeline, written as commands joined by the pipe character, that picks log events, filters them, optionally pulls fields out of text, and then lists, sorts or aggregates the result.

The big idea

In the last digest we stored logs and used filters to watch them as they arrive. A metric filter can only answer a question you thought of in advance. Logs Insights is for the question you think of afterwards: "which API path produced the most 500s in the last hour?" You choose one or more log groups, choose a time range, and write a query. CloudWatch scans the matching events and returns rows, or a chart if you aggregate.

The language is deliberately small. You build a query by chaining commands, each one taking the output of the previous one. If you've used a Unix shell pipe, the shape will feel familiar. The commands you'll use in nearly every query are fields, filter, parse, stats, sort and limit. Learn those six and you can answer most day-to-day questions.

Key terms

  • Logs Insights: the interactive query feature of CloudWatch Logs. It supports three query languages: its own purpose-built Logs Insights QL, OpenSearch PPL, and OpenSearch SQL. This digest is about Logs Insights QL.
  • Command: one step of a query, such as filter or stats.
  • Pipe (|): the separator between commands. Output of the left side feeds the right side.
  • System field: a field Insights creates automatically, starting with @. For Standard-class groups there are five main ones: @message, @timestamp, @ingestionTime, @logStream and @log.
  • Discovered field: a field Insights finds for you. For JSON logs and some AWS log types (Lambda, VPC flow logs, Route 53, CloudTrail) each key becomes a field you can use directly.
  • Aggregation: turning many events into one number or one row per group, for example count, average, or a percentile.
  • bin(): groups a time field into buckets, such as 5 minutes, so you can get a value over time.
  • Glob / regex (in parse): two ways to describe the shape of text you want to cut a piece out of: simple * placeholders, or regular expressions.
  • Field index: an optional setting that lets queries skip events that don't contain an indexed field, reducing how much data is scanned.

How it works

Grounding: what happens when you run a query

You pick log groups and a time range, then press run. CloudWatch scans the log events in that range, runs your commands over them in order, and shows results. The docs say queries incur charges based on the amount of uncompressed log data scanned (I'm not quoting any prices), and they list best practices that all follow from that: select only the log groups you need, use the narrowest time range you can, cancel queries before closing the console page (otherwise they keep running), and be careful with dashboard widgets that re-run a query on every refresh.

Some limits worth knowing, all from the docs: queries time out after 60 minutes if they haven't completed, and results are available for 7 days. Insights can't see log events with timestamps older than the creation time of the log group. The overview page says you are limited to 100 concurrent Logs Insights QL queries per account, while the start-query CLI page words the same limit as per Region. I'd treat the number as "about a hundred at once" and check the current quota page if it matters.

1. The free fields: what every event already has

For logs in a Standard-class group, the docs say Insights generates system fields, all beginning with @:

  • @message: the raw, unparsed text of the event.
  • @timestamp: the event's own timestamp.
  • @ingestionTime: when CloudWatch Logs received the event.
  • @logStream: the name of the stream the event is in.
  • @log: an identifier of the form account-id:log-group-name, handy when a single query spans several groups.

JSON logs become fields. If your application writes JSON per line, Insights discovers the keys and you reference them by name, using dot notation for nesting: userIdentity.type. Arrays are flattened with numeric positions, as in requestParameters.instancesSet.items.0.instanceId. The docs state a maximum of 200 log event fields extracted from a JSON log; beyond that you use parse on the raw message. This is the strongest argument for logging in JSON from day one.

Some AWS logs come pre-labelled. The docs list discovered fields for VPC flow logs (srcAddr, dstAddr, bytes, action and more), Route 53 logs, and Lambda logs (@duration, @maxMemoryUsed, @requestId, @type). That is why a flow log query can say stats sum(bytes) by srcAddr with no setup.

Caveat: for Lambda, the docs say automatic JSON discovery covers only the first embedded JSON fragment in each log event. And field discovery is supported only for Standard-class log groups.

2. The six everyday commands

fields: choose which fields to show, and create computed ones. Example from the docs: fields @timestamp, @message.

filter (alias where): keep only events matching a condition. Comparison operators are =, !=, <, <=, >, >=; boolean operators are and, or, not. Use like and not like for substrings, in [..] for set membership, and ispresent(field) to test that a field exists.

parse: pull a piece of text out of a field into a new field, with * placeholders or a regular expression.

stats: aggregate. Functions include count, countDistinct, sum, avg, min, max, pct (percentile), stddev, values, plus earliest and latest. Add by to group.

sort: order rows, asc or desc.

limit: cap how many rows come back. With sort it gives "top 20" or "latest 20".

The docs also list many more commands (display, dedup, pattern, diff, unnest, join, lookup, anomaly and others). I'm leaving those for you to explore after the six above feel natural. Comments in a query start with #.

3. Worked queries, read like sentences

These first three come from the docs' sample queries page. I describe each in plain words.

  • fields @timestamp, @message | sort @timestamp desc | limit 25: show time and text, newest first, only 25. This is the "what just happened?" query.
  • filter @message like /Exception/ | stats count(*) as exceptionCount by bin(1h) | sort exceptionCount desc: keep only events containing "Exception", count them in one-hour buckets, and show the worst hours first.
  • fields @message | filter @message not like /Exception/: everything that is not an exception.

A Lambda-flavoured one, also from the docs: filter @type = "REPORT" and @duration > 1000 | sort @timestamp desc | dedup @requestId | limit 20 finds invocations slower than 1000 ms (the docs note @duration is in milliseconds), removes duplicates caused by retries, and shows the 20 most recent.

4. Cutting fields out of plain text with parse

If a log line isn't JSON, Insights has only @message to offer. parse turns slices of it into fields. The docs' glob example:

parse @message "user=*, method:*, latency := *" as @user, @method, @latency | stats avg(@latency) by @method, @user

Read it as: wherever the message has that shape, capture the three starred parts into three fields, then average the latency per method and user. The docs show an equivalent version with a regular expression using named capture groups. Glob is easier to read, regex is more flexible. If a line doesn't fit the shape, I'd expect it simply not to yield those fields, but the pages I read don't spell that out, so try it on a sample.

5. Aggregating over time and drawing charts

stats with an aggregation function can produce charts. Per the docs, a query that aggregates and groups by bin() can show as a line chart, stacked area, bar or pie chart, while an aggregation grouped by a field (without bin) can show as a bar chart, limited to 100 bars. Supported bin units include ms, s, m, h, d, w, mo, q and y, so bin(5m) is five-minute buckets.

Two rules from the docs that trip people up. First, sort and limit must come after the last stats. Second, after a stats, you can only refer to fields that the stats command produced: the original @message is gone. A query can have up to 10 stats commands, a quota the docs say can't be changed.

Simplification: pct(@duration, 95) returns the value that 95 percent of the samples fall below. That's the percentile idea from the metrics digest, now computed over raw log events instead of pre-aggregated metrics.

6. Keeping queries cheap and fast

  • Narrow the inputs. Fewer log groups and a tighter time range means less data scanned, which is what you're charged on.
  • Field indexes. If you've created a field index (for example on requestId), queries using filter requestId = value or filter requestId IN [...] try to skip events without that field. The docs say like filters don't use indexes and always scan all events in the selected groups.
  • Cap the output. limit keeps results manageable. The docs say limit any can stop scanning early once enough results are found.
  • Log classes. Standard supports every Logs Insights QL command; Infrequent Access supports all except pattern, diff and unmask.

7. Running queries from the CLI

The console is the easy path, but queries can be run programmatically. aws logs start-query starts a query and returns a queryId; you then fetch results with get-query-results (I did not open that command's own reference page, so check its syntax). Required options for start-query are --start-time and --end-time in epoch seconds (not milliseconds, unlike put-log-events from the previous digest) and --query-string. You specify log groups via --log-group-name, --log-group-names or --log-group-identifiers (up to 50), or with a SOURCE command inside the query. --limit can be 1 to 100,000 for Logs Insights QL.

Why it matters

During an incident, speed of asking questions is the difference between a ten-minute and a two-hour investigation. Logs Insights also closes the loop with the rest of this track: you can add a query to a dashboard (next concept), and queries are how you decide which pattern deserves a metric filter and alarm.

Remember this

  • A query is commands joined by |. The everyday six: fields, filter, parse, stats, sort, limit.
  • Every Standard-class event gets @message, @timestamp, @ingestionTime, @logStream, @log; JSON keys become fields too.
  • Charges follow data scanned, so use few log groups and a narrow time range.
  • stats ... by bin(5m) gives a value over time; sort and limit go after the last stats.
  • Queries time out at 60 minutes and results are kept 7 days, per the docs.

Try it yourself

  1. Seed a practice log group. Reuse the group from the previous digest or create a new one, and push 20 or so JSON events (fields such as path, status, latencyMs) with aws logs put-log-events, varying them on purpose. Done when: the events appear in the console and the JSON keys show up as discovered fields in Logs Insights.
  2. Write the "latest 25" query. Run the docs' fields @timestamp, @message | sort @timestamp desc | limit 25. Then change limit to 5 and sort ascending. Done when: you can predict the first row before you run each variant.
  3. Rank by count. Write stats count(*) as hits by path | sort hits desc against your data, then add filter status >= 500 before it. Done when: your answer matches a count you did by hand from the events you wrote.
  4. Over time. Spread events across several minutes, then run stats avg(latencyMs), max(latencyMs) by bin(1m) and look at the Visualization tab. Done when: you've viewed a line chart and can explain what each point represents.
  5. Parse plain text. Push a few non-JSON lines in the shape user=ana, method:GET, latency := 120 and use the docs' glob parse pattern. Done when: stats avg(@latency) by @method gives the right averages, and you've tried a line in the wrong shape to see what happens.
  6. Same query from the CLI. Run aws logs start-query with start and end in epoch seconds, then fetch results with aws logs get-query-results --query-id ... (check that command's reference first). Done when: you get the same rows as in the console.
