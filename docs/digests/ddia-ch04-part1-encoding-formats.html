Formats for Encoding Data

Every time your program hands data to a file, a network, or another process, it has to be squeezed out of memory and into a flat sequence of bytes. This part covers the formats that do that squeezing, from plain JSON to schema-based binary formats like Protocol Buffers and Avro, and the small set of rules that keep old code and new code able to read each other's bytes.

In one line

Encoding is the translation from "data your program can work with" to "bytes you can send or store," and the format you pick decides how compact those bytes are and, more importantly, whether old code and new code can still make sense of each other's data once your schema changes.

The big idea

Applications change, and when they change, the shape of the data they read and write usually changes too: a new field shows up, an old one gets removed, a type gets widened. Because you can rarely update every copy of your code and every stored record at the same instant, you end up with old and new versions of both your code and your data coexisting for a while. Encoding formats differ enormously in how gracefully they handle that overlap: some make it easy for a newer reader to understand older data (backward compatibility) and for an older reader to tolerate newer data (forward compatibility), and some make it genuinely hard.

Key terms

  • Encoding (also called serialization or marshalling) — translating an in-memory data structure (an object, a struct, a list) into a self-contained sequence of bytes. e.g. turning a record with a name and a number into a JSON string.
  • Decoding (parsing, deserialization, unmarshalling) — the reverse: turning a byte sequence back into something your program can work with in memory.
  • Schema — a definition of what fields a record has and what type each field is.
  • Schema evolution — the fact that schemas change over time (fields added, removed, renamed, retyped), and the rules a format offers for doing that without corrupting old or new data.
  • Backward compatibility — newer code can read data that was written by older code.
  • Forward compatibility — older code can read data that was written by newer code, even data it's never seen the shape of before.
  • Rolling upgrade (staged rollout) — deploying a new version of a service to a few machines at a time instead of everywhere at once, so a problem is caught before it reaches every user. This is a common reason old and new code end up running side by side.
  • Field tag (field number) — a small integer used by some binary formats to identify a field in the encoded bytes, instead of spelling out the field's name.
  • IDL (interface definition language) — a small language you write a schema in (Thrift and Protocol Buffers each have their own), which a code generator turns into real classes in your programming language.
  • Variable-length integer (varint) — an integer encoding where small numbers take fewer bytes than large ones, so everyday values stay compact.
  • Writer's schema — in Avro, the version of the schema that the process encoding a piece of data was using at the time.
  • Reader's schema — in Avro, the version of the schema that the process decoding a piece of data is expecting.
  • Union type — an Avro way of declaring that a field can be one of several types (including null). Avro doesn't make every field nullable by default the way some languages do; you opt in with a union.
  • Object container file — Avro's own file format for storing many records under one schema, with that schema written once at the start of the file instead of repeated per record.

How it works

Here's the grounding picture before the details. Your program usually works with data in two very different shapes. In memory, while the program is running, data lives in objects, structs, lists, and hash tables, wired together with pointers so the CPU can get at it quickly. The moment you want to write that data to a file or send it to another process over a network, a pointer is useless (the other process doesn't share your memory), so the data has to become a flat, self-contained sequence of bytes instead. Translating from the in-memory shape to that byte sequence is encoding; translating back is decoding. Everything in this part of the material is really about which byte layout you choose for that translation, and what that choice costs you later when the shape of your data needs to change.

1. The trouble with your language's own built-in encoder

Most programming languages ship with a built-in way to turn an object straight into bytes: Java has java.io.Serializable, Ruby has Marshal, Python has pickle, and there are third-party libraries like Kryo for Java. These are genuinely convenient, since they save and restore objects with almost no extra code. But this material flags a handful of deep problems with leaning on them for anything long-lived. First, the encoding is usually tied to one programming language, so reading the data from another language is difficult, which locks you into your current language for potentially a long time. Second, restoring an object generally means the decoder has to be able to instantiate arbitrary classes, and that turns out to be a real source of security problems: if an attacker can get your application to decode a byte sequence they control, they can sometimes get it to construct classes that do damaging things, including remote code execution. Third, versioning is usually an afterthought in these libraries, so forward and backward compatibility get neglected. Fourth, efficiency is often an afterthought too. Java's built-in serialization is specifically called out as notorious for bad performance and bloated output. Put together, the takeaway is that your language's own built-in encoder is usually fine for something short-lived and internal, but a bad choice for anything you'll store for a while or share outside your own language.

2. Textual formats: JSON, XML, and CSV

JSON and XML are the standardized, language-independent formats most people reach for, with CSV as a simpler, less powerful third option. They're textual, so they're somewhat human-readable, and JSON in particular is popular partly because it's built into web browsers as a subset of JavaScript. But underneath the readability, this material points out some subtle problems that catch people out.

The biggest one is number ambiguity. XML and CSV can't distinguish a number from a string that happens to be made of digits without an external schema to tell you which it is. JSON does distinguish strings from numbers, but it doesn't distinguish an integer from a floating-point number, and it doesn't pin down a precision. That matters concretely once numbers get large: an IEEE 754 double-precision float (the number type JavaScript uses) can't exactly represent every integer bigger than 253, so a large integer parsed by a JavaScript-based JSON parser can come out subtly wrong. The material gives a real example: Twitter identifies each tweet with a 64-bit number, well past that 253 ceiling, so Twitter's API includes each tweet ID twice, once as a JSON number and once as a string, specifically to work around JavaScript mangling the numeric version.

The second problem is binary strings. JSON and XML handle Unicode text well, but neither has native support for a plain sequence of bytes that isn't text. The common workaround is to Base64-encode the binary data into a text string, which works, but is a bit of a hack and increases the data's size by about a third.

The third is schemas. Both XML and JSON have optional schema languages, and they're powerful but also complicated to learn and implement. XML schemas are used fairly widely; a lot of JSON-based tooling skips schemas entirely, which means the correct way to interpret a value (is this really a number, is this Base64 binary data) often has to be hardcoded into the application instead of read from a schema. CSV doesn't even have an optional schema: it's up to the application to decide what each column means, adding a new column is a manual coordination problem, and CSV's escaping rules (what happens when a value itself contains a comma) are formally specified but not always implemented correctly by every parser.

None of this makes JSON, XML, or CSV bad choices. This material is explicit that they're good enough for a lot of purposes, especially as a format for exchanging data between organizations that need to agree on something simple, since getting different organizations to agree on anything at all is usually the harder problem.

3. Binary variants of JSON, and where they hit a ceiling

For data that stays inside your own organization, there's less pressure to pick a lowest-common-denominator format, so once a dataset gets into the terabytes, a more compact or faster-to-parse format starts to matter. That observation led to a handful of binary encodings for JSON, among them MessagePack, BSON, and Smile, plus binary variants of XML like WBXML. These extend JSON's datatypes a bit (distinguishing integers from floats, adding binary strings), but they otherwise keep JSON's data model as-is. Crucially, since none of them prescribe a schema, they still have to write every field name into the encoded bytes.

Here's a worked example this material walks through. Take a small record: a username, a favorite number, and a list of interests. Encoded as plain JSON with the whitespace stripped out, that's 81 bytes. Encoded with MessagePack, a binary encoding for JSON, it comes out to 66 bytes: the first byte (0x83) says "an object with 3 fields," the next byte (0xa8) says "an 8-byte string follows," then the 8 ASCII bytes for the field name userName itself, and so on. That's only a modest saving over textual JSON, and the field names (userName, favoriteNumber, interests) are still sitting there in the bytes, spelled out in full. As this material puts it, it's not obvious that saving that little space (or parsing a bit faster) is worth losing human-readability for. The bigger wins come from formats that don't have to write field names into every record at all, which is exactly what the schema-based formats below do differently.

4. Schema-based binary encoding: Thrift and Protocol Buffers

Apache Thrift (originally built at Facebook) and Protocol Buffers, or "protobuf" (originally built at Google), both went open source around 2007–08 and both work on the same principle: you write a schema up front, in a small interface definition language, and a code generator turns it into classes in whatever programming language you're using. A schema for that same username/favorite-number/interests record looks similar in both:

struct Person { 1: required string userName, 2: optional i64 favoriteNumber, 3: optional list<string> interests } in Thrift, and message Person { required string user_name = 1; optional int64 favorite_number = 2; repeated string interests = 3; } in Protocol Buffers.

Notice the small numbers next to each field. Those are field tags, and they're the whole trick: instead of writing the field name favoriteNumber into the bytes, the encoded record just writes the number 2, along with a marker for its datatype and, where needed, a length. That's why the same record comes out so much smaller: Thrift's BinaryProtocol encodes it in 59 bytes, Thrift's more compact CompactProtocol packs the tag and type into a single byte and uses variable-length integers to get it down to 34 bytes, and Protocol Buffers (which only has the one binary format) does its own version of that same bit-packing trick to land at 33 bytes. Note that whether a field was declared required or optional doesn't change anything about how it's encoded; the only difference is that required turns on a runtime check that fails loudly if the field was never set, which is handy for catching bugs early.

5. Field tags and schema evolution

An encoded record in Thrift or Protobuf is just its fields, concatenated one after another, each carrying its own tag number and type marker; if a field is unset, it's simply left out entirely. Because of that layout, the tag numbers are doing all the work of tying the bytes back to a meaning. You're free to rename a field in your schema any time you like, since the encoded data never refers to field names at all. What you can never do is change a field's existing tag number, because that would make every record already encoded with the old tag meaningless.

Adding a new field is safe as long as it gets a tag number nobody has used before. If an old reader (one that doesn't know the new tag) encounters it, the type marker tells the parser how many bytes to skip, so it just ignores the unfamiliar field. That's what makes the format forward compatible: old code can read data written by new code. Going the other way, a new reader can always make sense of old data, because tag numbers keep the same meaning over time, which gives you backward compatibility too, with one catch: a newly added field can never be marked required. If you added a required field and old code (which never wrote it) had written some of the data, a new reader's required-field check would fail. So every field you add after the schema's first release has to be optional or carry a default. Removing a field follows the same logic in reverse: you can only remove a field that was optional (a required field can never be removed), and you can never reuse that tag number again later for something else, because there may still be old data out there using it.

Changing a field's datatype is possible in both formats, but the material flags a real risk of losing precision. Widening a 32-bit integer field to 64 bits is safe for new code reading old data (it just fills the extra bits with zero), but if old code (still expecting 32 bits) reads a 64-bit value written by new code, and that value doesn't fit in 32 bits, it gets truncated. One more detail worth knowing: Protocol Buffers has no dedicated list or array type. Instead a field can be marked repeated, and a repeated field's encoding is just the same tag appearing multiple times in the record. That has a nice side effect: you can safely turn a single-valued optional field into a repeated one later. New code reading old data just sees a list with zero or one items; old code reading new data sees only the last of the repeated values. Thrift instead has a dedicated list type parameterized by its element type, which doesn't support that same single-to-multi evolution, but does support nested lists, which Protobuf's repeated-field trick doesn't handle as cleanly.

6. Avro: schema evolution without tag numbers at all

Apache Avro started in 2009 as a Hadoop subproject, built specifically because Thrift wasn't a good fit for Hadoop's needs. It also uses a schema, written either in a human-friendly IDL or as an equivalent, more machine-readable JSON document, but if you look closely at an Avro schema there's a detail missing: no tag numbers anywhere. Encoded with an Avro schema, that same example record comes out to just 32 bytes, the most compact of every format covered here, and the encoded bytes contain nothing that identifies a field or its type at all: it's genuinely just the values, concatenated in schema order. A string is a length prefix plus UTF-8 bytes, but nothing in those bytes says "this is a string" rather than, say, an integer. The only way to correctly decode an Avro record is to walk through the fields in the exact order the schema declares them, using the schema to know each field's type as you go. That means the code reading Avro data has to know the exact schema the data was written with, or something compatible with it.

That's where Avro's central idea comes in: the writer's schema is whatever schema the encoding side used, and the reader's schema is whatever schema the decoding side expects, and Avro's whole design is built around the fact that those two don't have to be identical, only compatible. When data is decoded, Avro's library lines the writer's schema and the reader's schema up side by side and resolves the difference: fields are matched up by name rather than by position or number, so it's fine if the two schemas list fields in a different order. If the writer's schema has a field the reader's schema doesn't know about, it's ignored. If the reader's schema expects a field the writer's schema never had, Avro fills in whatever default value the reader's schema declares for it.

The compatibility rule that falls out of this is simple to state: you may only add or remove a field that has a default value. Add a field with a default, and a reader using the new schema can still read data an old writer produced, since the default fills the gap; that's backward compatibility (new schema as reader, old schema as writer). Remove a field that has a default, and an old reader can still make sense of data a new writer produced; that's forward compatibility (new schema as writer, old schema as reader). Add a field with no default and you break backward compatibility; remove a field with no default and you break forward compatibility. One Avro-specific wrinkle: unlike some languages where null is an acceptable default for anything, Avro requires you to explicitly declare a field as a union type (for example, "this field is either a number or null") if you want it nullable, and you can only use null as a default if it's one of the union's listed options. It's a little more ceremony than "everything is nullable by default," but this material frames it as a deliberate trade: more explicit, fewer accidental-null bugs. Changing a field's datatype is possible if Avro can convert between the two types. Renaming a field is possible too, using aliases in the reader's schema that map old names to new ones, though that direction only works one way: it's backward compatible but not forward compatible, since an old reader wouldn't know to look for the new name.

So how does a reader even find out which schema a given piece of data was written with, if the bytes themselves don't say? The material walks through three real contexts where this comes up. For a large file holding millions of records that all share one schema (a common Hadoop-era use case), the writer just writes the schema once at the top of the file; Avro has a dedicated file format, the object container file, built exactly for this. For a database where individual records might have been written at very different times under different schema versions, the simplest approach is to store a small version number with every record and keep a lookup table of schema versions elsewhere (this material points to LinkedIn's Espresso document store, which is built this way, using Avro for storage). For two processes talking over a live network connection, they can simply negotiate which schema version to use once, at the start of the connection, and then keep using it; Avro's own RPC protocol works this way.

One more distinction worth pulling out: because Avro schemas carry no tag numbers, they're notably friendlier to being generated automatically. If you wanted to dump a relational database table to a file in Thrift or Protobuf, someone would have to hand-assign a tag number to each database column, and be careful never to reuse an old one as the table's own schema changed over time. With Avro, the field names carry the meaning, so a script can regenerate the Avro schema straight from the current database schema every time it runs, with no manual tag bookkeeping at all. On a related note, Thrift and Protobuf lean on code generation, which is genuinely useful in statically typed languages for compile-time type checking, but is more of an obstacle than a help in dynamically typed languages like Python, Ruby, or JavaScript, where there's no compiler to satisfy in the first place. Avro supports optional code generation but doesn't require it: an Avro object container file carries its own schema, so a dynamically typed tool can just open it and start reading, the same way you'd casually open a JSON file.

7. Why schemas earn their keep

Thrift, Protocol Buffers, and Avro all lean on a schema to describe a binary format, and their schema languages are deliberately much simpler than XML Schema or JSON Schema, which support far more detailed validation (things like "this string must match this pattern"). That simplicity is part of why all three have grown to support a wide range of programming languages. This material notes the underlying idea isn't new: ASN.1, a schema definition language first standardized in 1984, works on similar principles and its binary encoding (DER) is still what's used to encode SSL certificates today, though ASN.1 itself is called out as complex and poorly documented enough that it's not a great pick for something new. Beyond the encoding libraries in this digest, most relational databases also implement their own proprietary binary network protocol for talking to the database, decoded on the client side by a driver (the kind of thing ODBC or JDBC provide).

Pulled together, this material lists four real advantages a schema-based binary format buys you over the "binary JSON" style variants: it can be far more compact, since field names don't have to travel with every record; the schema itself becomes documentation that's guaranteed to be current, because decoding literally depends on it being accurate, unlike a wiki page that can quietly drift out of date; keeping a database of schema versions lets you check forward and backward compatibility before you ever deploy a change; and in statically typed languages, generating code straight from the schema gets you compile-time type checking for free. The overall conclusion drawn here is that schema evolution gives you a lot of the same flexibility schema-on-read ("schemaless") databases offer, while also giving you stronger guarantees about your data and better tooling around it.

Why it matters

This distinction between formats that carry field names and formats that carry only tag numbers or rely on a schema isn't just a size optimization. It's what determines whether you can roll out a new version of a service to a few machines at a time (a rolling upgrade) without the old machines and new machines misunderstanding each other's data, whether a database can hold records written five years apart under completely different schema versions and still make sense of all of them, and whether two teams' services can evolve independently instead of having to deploy in lockstep. Every one of those situations comes down to the same underlying question this part of the material sets up: can the reader make sense of bytes the writer produced, and vice versa, even when they were built from different versions of the same schema.

Remember this

  • Encoding turns in-memory data into bytes; decoding reverses it. Your language's own built-in serializer (Java's, Python's pickle, and similar) is convenient but usually the wrong long-term choice: it locks you to one language, and decoding untrusted bytes with some of these libraries has been a real source of security bugs.
  • JSON, XML, and CSV are easy to read but genuinely ambiguous, especially around large numbers and binary data. Binary variants like MessagePack shave off some size but still write every field name into the bytes, since they don't use a schema.
  • Thrift and Protocol Buffers replace field names with small tag numbers defined in a schema. That's what makes them compact, and the tag number is the one thing you can never change once real data has been written with it.
  • Backward compatible means newer code can read older data; forward compatible means older code can read newer data. In practice this comes down to a couple of habits: never reuse a tag or field number, and give every field you add after the first release a default or make it optional.
  • Avro drops tag numbers entirely and instead matches fields by name between the writer's schema (what encoded the data) and the reader's schema (what's decoding it), filling in defaults for anything the reader expects but the writer never had.

Try it yourself

  1. Encode the same record two ways and weigh the bytes. Pick a small record with a couple of strings and a number, write it out as JSON, then hand-pack it into a small custom binary layout (fixed-width integers, length-prefixed strings) using your language's raw byte tools, such as Python's struct module, or just building the byte string directly. Done when: you can print the byte length of both versions side by side and explain in your own words where the size difference actually comes from.
  2. Hand-decode a tagged binary blob. Invent a tiny schema: 3–4 fields, each with a tag number (1, 2, 3…) and a one-byte type code you make up (say, 0 for integer, 1 for string). Hand-encode one record as a sequence of tag/type/length/value bytes in a text file. Set it aside for a day, then decode it back into field names and values using only your schema key, not memory. Done when: you can decode it correctly using nothing but the tag-to-field-name mapping.
  3. Break forward compatibility on purpose, then fix it. Write a small program that reads a JSON record into a few named fields. Feed it a record with one extra field it doesn't expect and see what happens (an error, or a silent drop). Then rewrite the reader so any unrecognized field is captured and preserved instead of lost. Done when: you can pass a record with an unknown field through your reader and get that field back out unchanged.
  4. Simulate Avro-style writer/reader schema resolution. Define an "old" schema and a "new" schema for the same small record, where the new one adds a field with a default value and removes an old field. Write a function that takes a record encoded under the old schema and reads it as if it were the new schema: the missing new field gets its default, and the removed old field is dropped. Done when: an old-schema record comes out looking exactly like it was always in the new shape.
  5. Reuse a field tag and watch it break. Using the tagged format from project 2, take a working record, then simulate reassigning tag 2 to a completely different field type (say, an integer field where it used to be a string). Try decoding an old record with the new tag mapping. Done when: you've reproduced, at a small scale, the exact "old data decodes into the wrong thing" failure this digest describes, and can explain why in your own words.
  6. Measure the Base64 tax. Take a small chunk of binary data (a tiny image file, or just a handful of random bytes), Base64-encode it, and place the result in a JSON field. Compare the size of the raw bytes to the size of the Base64 string. Done when: you can state the percentage size increase and check it against the roughly 33% figure mentioned in this digest.

Go deeper

If you want a preview of where these ideas get used for real at scale, look up how a schema registry (Confluent's, built around Kafka, is the best-known example) enforces compatibility rules automatically before a new schema is even allowed to be published, instead of leaving it to a code reviewer to catch a broken change. It's a real system built almost entirely around the writer's-schema-versus-reader's-schema idea covered above.
