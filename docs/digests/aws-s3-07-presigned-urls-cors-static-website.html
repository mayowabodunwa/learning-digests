S3 Presigned URLs, CORS and Static Website Hosting: Sharing S3 Content With Browsers and People

So far everything in S3 has been private-by-default and accessed with credentials. This digest is about the three ways S3 content reaches people and web pages that don't have your credentials: a time-limited signed link, a browser permission slip called CORS, and a bucket acting as a basic website.

In one line

A presigned URL lends someone your permissions for one specific request for a limited time, CORS tells browsers which other websites' JavaScript may call your bucket, and static website hosting serves a bucket's public objects over a plain-HTTP website endpoint.

The big idea

These three features look unrelated, but they solve one problem: how do you let outside parties touch your data without handing over a key or making the whole bucket public?

  • A presigned URL keeps the bucket private and gives one person a link that works for one operation, for a while.
  • CORS is about browsers. Even when S3 would allow a request, a browser running JavaScript from one site won't let it call another site's server unless that server says it's okay. CORS is how a bucket says it's okay.
  • Static website hosting is the opposite end: deliberately public content, served from a website address.

The thread running through all three is the access control material from the previous digest: Block Public Access, bucket policies and IAM permissions still apply. None of these features is a bypass.

Simplification label: the docs now steer people toward AWS Amplify Hosting or CloudFront in front of S3 for real websites. I explain the raw S3 website feature because it shows the limits, not because it's the only choice. No prices are quoted.

Key terms

  • Presigned URL: a URL with a signature and expiry baked in, granting time-limited permission for a specific operation on a specific object.
  • Bearer token: something that works for whoever holds it. The docs describe presigned URLs this way.
  • Origin: the combination of scheme, host and port a web page was loaded from (for example https://app.example.com).
  • Same-origin policy: the browser rule that scripts from one origin can't freely read responses from another.
  • CORS: cross-origin resource sharing, the mechanism by which a server tells the browser which other origins may call it.
  • Preflight request: an automatic OPTIONS check some browser requests send first, asking whether the real request is allowed.
  • Website endpoint: the special S3 address that serves a bucket as a website, different from the REST API endpoint.
  • Index document: the page served for the site root or a folder path (for example index.html).
  • Error document: the custom page returned for errors.
  • Static website: pages whose content is fixed files; they may include client-side scripts but no server-side code.

How it works

0. Grounding: private by default, three ways to share

The docs open the presigned URL topic with the baseline: by default all S3 objects are private and only the object owner can access them. The three tools below are three deliberate exceptions, each with a different blast radius:

  • Presigned URL: one object, one operation, limited time, one grantor's permissions.
  • CORS: only affects what browsers will do; it doesn't grant S3 permissions (the docs state that ACLs and policies continue to apply).
  • Website hosting: everyone on the internet, for the objects you make public.

1. Presigned URLs

To create one, you supply your credentials and specify a bucket, an object key, an HTTP method (GET to download, PUT to upload, HEAD for metadata, etc.), and an expiration interval. The result is an ordinary-looking link with a signature in the query string. Anyone holding the link can perform that one request until it expires, with the permissions of whoever signed it. It can be used multiple times until expiry.

Uploads. A presigned PUT lets a third party upload without having AWS credentials. If an object with that key already exists, S3 replaces it, and after upload the bucket owner owns the object. The uploader must match what was signed: the docs' troubleshooting list says the content type in the upload must match what was used to generate the URL.

How long does it last? This is the part people get wrong:

  • Console: between 1 minute and 12 hours.
  • CLI or SDKs: up to 7 days, but only if signed by an IAM user's long-term credentials with Signature Version 4.
  • With temporary credentials (an IAM role, STS, or an EC2 instance role), the URL stops working when those credentials expire, even if you asked for longer. The docs give EC2 role credentials as typically around 6 hours and an AssumeRole session as 1 hour by default.
  • More generally, if the signing credential is revoked, deleted or deactivated, the URL dies.
  • Expiry is checked when the HTTP request is made. A download that starts before expiry continues; a resumed download after expiry fails.

Making one with the CLI (the docs' example; note this CLI command is for downloads):

aws s3 presign s3://{bucket}/{key} --expires-in 604800

The docs add that for Regions launched after March 20, 2019 you need to specify the region and endpoint URL with the request. 604800 seconds is 7 days.

Limiting what a link can do. The docs call presigned URLs bearer tokens and suggest protecting them. Their examples: a bucket policy that denies presigned requests whose signature is older than a threshold using the s3:signatureAge condition (Signature Version 4 only), and network-path restrictions with aws:SourceIp (or aws:SourceVpc / aws:SourceVpce through VPC endpoints) in IAM or bucket policies.

Common errors from the docs' FAQ: a 403 usually means the signer lacked the permission or a policy denies it; SignatureDoesNotMatch is often clock drift, a proxy changing the URL, or mismatched parameters; ExpiredToken means the signing credentials expired.

2. CORS

Picture a web page loaded from https://app.example.com whose JavaScript tries to PUT a file straight to your bucket's address. The browser's same-origin policy blocks it unless the bucket's server says that origin is allowed. The docs' two example scenarios: JavaScript on a website hosted from one bucket that needs to call the bucket's API endpoint, and hosting a web font that browsers insist on a CORS check for.

You configure CORS by attaching a configuration (the bucket's cors subresource) with up to 100 rules. In the console it must be JSON. Each rule has:

  • AllowedOrigins: which origins may call (one * wildcard allowed per string, e.g. http://*.example.com; or * alone for all).
  • AllowedMethods: any of GET, PUT, POST, DELETE, HEAD.
  • AllowedHeaders: request headers the preflight may ask for (each can contain one wildcard).
  • ExposeHeaders: response headers the page's JavaScript is allowed to read (the docs' example exposes x-amz-request-id and similar).
  • MaxAgeSeconds: how long the browser may cache a preflight answer.

How S3 evaluates it: on a preflight request, S3 uses the first rule that matches the origin, method and requested headers. Remember: CORS doesn't give anyone S3 permissions. It only lets a browser proceed to a request that still has to pass IAM, bucket policy and Block Public Access. An example in the docs' JSON shape:

[
  {
    "AllowedOrigins": ["http://www.example.com"],
    "AllowedMethods": ["PUT", "POST", "DELETE"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["x-amz-request-id"],
    "MaxAgeSeconds": 3000
  }
]

3. Static website hosting

A static website is one where pages are fixed files (possibly with client-side scripts). S3 can serve a bucket this way at a Region-specific website endpoint, in one of two formats depending on the Region: http://bucket.s3-website-Region.amazonaws.com or http://bucket.s3-website.Region.amazonaws.com. You configure an index document (and optionally a custom error document and redirects).

Know the differences between the website endpoint and the normal REST API endpoint (the docs give a table):

  • Website endpoint serves only publicly readable content; REST supports public and private.
  • Website supports only GET and HEAD on objects.
  • Website endpoint does not support HTTPS (nor access points). For HTTPS, the docs recommend AWS Amplify Hosting or putting CloudFront in front.
  • The root URL returns the index document instead of a key listing; errors come back as HTML rather than XML; redirects are supported.
  • Requester Pays buckets can't be served through a website endpoint (403).

Making it public takes two deliberate steps (docs): turn off the relevant Block Public Access settings (bucket level, and account level if it's on, since the most restrictive wins), and add a bucket policy granting everyone s3:GetObject on the bucket's objects. If some objects aren't owned by the bucket owner, an object ACL may be needed, though with ACLs disabled (the default), you use policies only. The docs' warning applies: this really does make the content readable by anyone on the internet, and they recommend blocking public access generally.

An important caveat the docs state plainly: a missing object returns 404 and an existing-but-unreadable one returns 403, so visitors can infer which keys exist. If you don't want that, don't enable website support. Another: if the bucket uses SSE-KMS, the website endpoint won't work for anonymous users, so you'd serve through CloudFront with origin access control.

The docs' alternative for keeping Block Public Access on: put a CloudFront distribution in front and let that read the bucket.

4. How the three fit together

A typical modern pattern, as a mental model: a single-page app hosted from a static site (or CDN), whose JavaScript asks your backend for a presigned PUT URL and then uploads a file straight to a private bucket from the browser. For that browser upload to work, the bucket needs a CORS rule allowing your site's origin and the PUT method; the presigned URL supplies the permission; Block Public Access can stay fully on. This is a common pattern, not the only way to do uploads.

Why it matters

Accidentally public buckets and leaked links are two ways S3 data can end up exposed, and both live in this territory (a general observation, not a figure from the docs). Knowing that a presigned URL is a bearer token that dies with its credentials, that CORS is not a permission, and that a website endpoint genuinely requires public data, gives you the vocabulary to pick the right tool: signed links for private sharing, CORS for browser access, and CloudFront or Amplify for public sites.

Remember this

  • A presigned URL is a bearer token carrying the signer's permissions for one request until it expires or the signing credential dies, whichever is first.
  • Expiry limits: console 1 minute to 12 hours; CLI/SDK up to 7 days, but temporary credentials shorten it.
  • CORS only tells browsers which origins may call; IAM, policies and Block Public Access still decide the actual access.
  • The S3 website endpoint is HTTP-only, GET/HEAD-only and public-only; use CloudFront or Amplify for HTTPS.
  • Making a bucket a public website means turning off Block Public Access and granting s3:GetObject publicly, a deliberate choice.

Try it yourself

Projects 1 and 2 are offline. Projects 3 to 5 use the AWS CLI and a scratch bucket in your own account. The aws s3 presign command and the shape of the CORS JSON are from the docs; put-bucket-cors, put-bucket-website and the exact CLI JSON wrapper for CORS I did not verify, so confirm them in the CLI reference. Delete the scratch bucket afterwards and don't leave a bucket public.

  1. Expiry calculator (offline, ~30 min). Given the signer type (IAM user, role session, EC2 role, console) and requested lifetime, return the effective lifetime using the rules above. Done when it returns the shorter of the two for temporary credentials and enforces the 12-hour console cap.
  2. CORS rule matcher (offline, ~1 hour). Implement "first matching rule wins" for origin (with one-wildcard patterns), method and requested headers. Done when your matcher correctly allows and blocks a handful of origins against the docs' three-rule example.
  3. Make and use a link. Upload a small file to a private bucket, run aws s3 presign s3://BUCKET/KEY --expires-in 60, fetch it with curl before and after 60 seconds. Done when the first works, the second fails, and you can name the error you saw.
  4. Prove it's a bearer token. Open the link from a different machine or an incognito window without any AWS credentials. Done when it works there, and you've written down one control from the docs (signature age or network restriction) that could narrow it.
  5. Static site, safely. Enable website hosting on a scratch bucket with an index.html, apply the docs' public-read policy only after adjusting Block Public Access for that bucket, load the HTTP website endpoint, then re-enable Block Public Access and confirm the page stops loading. Done when you've seen both states and noticed the 403 vs 404 behaviour for a missing file.
