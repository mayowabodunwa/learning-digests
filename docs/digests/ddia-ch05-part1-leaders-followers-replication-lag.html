Replication: Leaders, Followers, and Replication Lag

Replication means keeping copies of the same data on several machines. Copying data once is easy. The hard part is that data keeps changing, and the copies must keep up. This first part covers the most common design, where one machine takes the writes and others copy it (leader-based replication), what goes wrong when a leader dies, how the copying is actually implemented, and the odd things users see when a copy lags behind. It stops right before multi-leader replication.

In one line

In leader-based replication, one replica accepts writes and streams its changes to followers; the interesting questions are how long the leader waits for followers, what happens when nodes fail, and what stale reads do to your users.

The big idea

You replicate for three reasons: to keep data close to users (lower latency), to keep working when some machines fail (availability), and to spread read queries over more machines (read throughput). If the data never changed, you would copy it once and be done. All the difficulty is in handling changes. The chapter covers three families of algorithms (single-leader, multi-leader, leaderless), and this part is the first. The big trade-off is already visible here: if the leader waits for followers before saying "done", you get safer data but a more fragile system; if it doesn't wait, you get speed and availability but followers can show old data for a while.

Key terms

  • Replica: any node that stores a copy of the database.
  • Leader (primary, master): the replica designated to accept writes. The older "master" and "slave" terms appear in the source for the leader and follower.
  • Follower (read replica, secondary, hot standby): a replica that applies the leader's changes and, from a client's view, serves reads only.
  • Replication log / change stream: the sequence of data changes the leader sends to followers, applied in the same order.
  • Synchronous / asynchronous replication: the leader waits for a follower's confirmation before reporting success (sync) or sends the change and carries on (async).
  • Semi-synchronous: one follower is synchronous and the rest asynchronous.
  • Durable: a confirmed write survives failures.
  • Catch-up recovery: a returning follower asks the leader for the changes it missed.
  • Failover: promoting a follower to leader after the leader fails, and redirecting everyone.
  • Split brain: two nodes both believing they are the leader.
  • Statement-based / WAL shipping / logical (row-based) / trigger-based replication: four ways of implementing the replication log, covered below.
  • Change data capture: streaming a database's changes to external systems (the source defers detail to Chapter 11).
  • Replication lag: the delay between a write on the leader and its appearance on a follower.
  • Eventual consistency: if writes stop and you wait, followers will eventually match the leader; there is no stated bound on how long.
  • Read-after-write (read-your-writes) consistency: you always see your own submitted updates when you reload.
  • Monotonic reads: you won't see data go backward in time across successive reads.
  • Consistent prefix reads: if writes happened in some order, readers see them in that order.

How it works

Grounding first. Imagine one database server. If it dies, your app is down; if reads outgrow it, you are stuck. Replication fixes both by keeping copies elsewhere. This chapter assumes the dataset is small enough that each machine holds a full copy (splitting data across machines, partitioning, is Chapter 6). The question this part answers: with several copies, how do all the writes reach all the copies, in a way that stays correct?

Leader-based replication

The most common answer: designate one replica the leader. Clients send all writes to it; it saves them locally and also sends each change to every follower as part of a replication log. Each follower applies the changes in the same order the leader processed them. Reads can go to the leader or any follower, but followers are read-only for clients.

The source lists it as a built-in feature in PostgreSQL (since version 9.0), MySQL, Oracle Data Guard and SQL Server's AlwaysOn Availability Groups, and in nonrelational systems such as MongoDB, RethinkDB and Espresso. It also appears outside databases, in message brokers like Kafka and RabbitMQ's highly available queues. (Those are the 2017 statements of the book.)

Synchronous versus asynchronous

Say a user updates a profile photo. The leader gets the write and forwards it to the followers. When does it tell the user "success"? With a synchronous follower, the leader waits for that follower to confirm receipt before reporting success (and before making the write visible to other clients). With an asynchronous follower, the leader sends the message and doesn't wait.

Replication is usually quick (the source says most databases apply changes to followers in under a second) but there is no guarantee. A follower recovering from a failure, a system near capacity, or network problems can leave it minutes behind.

  • Sync advantage: the follower is guaranteed to have an up-to-date copy, so if the leader suddenly dies the data is still there.
  • Sync disadvantage: if that follower doesn't respond (crash, network fault), the write cannot be processed and the leader must block writes until it returns.

So making all followers synchronous is impractical; one outage would stall everything. In practice, enabling synchronous replication usually means one synchronous follower and the rest asynchronous, with an asynchronous one promoted to synchronous if the sync one becomes slow or unavailable. That keeps an up-to-date copy on at least two nodes, and is sometimes called semi-synchronous.

Often the setup is fully asynchronous. Then if the leader fails unrecoverably, writes not yet replicated are lost, so a write is not guaranteed durable even though the client was told it succeeded. The upside is that the leader keeps accepting writes even if every follower is behind. Despite weakening durability, async is widely used, especially with many or geographically spread followers. The source also mentions chain replication, a synchronous variant used in some systems (it names Microsoft Azure Storage), as one line of research into replication that doesn't lose data; I only mention it, the chapter doesn't go further.

Setting up a new follower

You need new followers to add capacity or replace failed ones. Just copying the data files won't do: writes keep arriving, so a plain file copy sees different parts of the database at different moments and may make no sense. Locking the database for writes would hurt availability. The usual approach (details differ by database, and the source says some are automated and some are arcane manual workflows):

  1. Take a consistent snapshot of the leader at one point in time, ideally without locking everything. Most databases can do this since backups need it; sometimes a third-party tool is needed (the source mentions innobackupex for MySQL).
  2. Copy the snapshot to the new node.
  3. The follower connects to the leader and requests every change since the snapshot. That requires the snapshot to be tied to an exact position in the replication log (PostgreSQL calls it the log sequence number; MySQL, binlog coordinates).
  4. When it has worked through that backlog it has caught up and continues streaming.

Handling node outages

Nodes go down by accident and also for planned maintenance such as a kernel patch reboot. The goal is to keep the whole system running and make each outage's impact small.

Follower failure: catch-up recovery. Each follower keeps a local log of changes received. After a crash or a brief network break, it knows the last transaction it processed, asks the leader for everything after that, applies it, and carries on.

Leader failure: failover. Harder. A follower must be promoted, clients must send writes to the new leader, and the other followers must follow the new one. It can be manual (an administrator acts) or automatic. Automatic failover typically has three steps:

  1. Detect the failure. There's no foolproof way to tell what went wrong, so most systems use a timeout: if a node doesn't respond for some period (the source's example is 30 seconds), assume it's dead.
  2. Choose a new leader. By election among the remaining replicas or by a previously chosen controller node. The best candidate is usually the replica with the most up-to-date data, to minimize loss. Getting nodes to agree is a consensus problem (Chapter 9).
  3. Reconfigure. Clients write to the new leader. If the old leader returns and still thinks it is the leader, the system must make it step down and become a follower.

Things that go wrong, per the source:

  • With async replication, the new leader may lack some of the old leader's writes. The most common handling is to discard the old leader's unreplicated writes, possibly breaking durability expectations.
  • Discarding writes is especially dangerous when other systems depend on the database. The source recounts a GitHub incident where an out-of-date MySQL follower became leader, reused autoincrement primary keys the old leader had already handed out, and since those keys were also used in a Redis store, some private data was shown to the wrong users.
  • Split brain: two nodes believe they're leader. If both accept writes without conflict resolution, data is likely lost or corrupted. Some systems shut one node down when they detect two leaders, but a badly designed mechanism can shut down both.
  • Timeout choice: too long means slow recovery; too short means unnecessary failovers, for example from a load spike or network glitch, which can make an already struggling system worse.

There are no easy solutions, and the source notes that some operations teams prefer manual failover even when automatic is available.

How the replication log is implemented

Statement-based. The leader logs each write statement (INSERT, UPDATE, DELETE) and followers execute it as if from a client. Simple, but breaks in several ways: nondeterministic functions like NOW() or RAND() give different values per replica; statements depending on existing data or autoincrement columns must run in the exact same order everywhere; statements with side effects (triggers, stored procedures) may differ. Workarounds exist (the leader can replace nondeterministic calls with fixed values) but edge cases abound, so other methods are generally preferred. MySQL used it before version 5.1 and by default now switches to row-based if a statement is nondeterministic; VoltDB uses it and requires deterministic transactions.

Write-ahead log (WAL) shipping. Storage engines already append every write to a log (the main storage for log-structured engines, a crash-recovery log for B-trees). Send that same log to followers and they build identical data structures. PostgreSQL and Oracle use it. The drawback: the log is low level (which bytes changed in which disk blocks), tying replication to the storage engine. Often that means leader and followers must run the same software version, so a zero-downtime upgrade (upgrade followers, then fail over) isn't possible and upgrades need downtime.

Logical (row-based) log. A separate log format, decoupled from storage internals. For each row it records: new values for an insert; enough to identify the row for a delete (usually the primary key, otherwise all old column values); for an update, the row's identity and new values. A multi-row transaction produces several records followed by a commit record. MySQL's binlog in row-based mode works like this. Because it's decoupled, it's easier to keep backward compatible (leader and follower can run different versions or even different storage engines) and easier for external programs to parse, which enables change data capture into a data warehouse or custom indexes and caches (Chapter 11).

Trigger-based. The others live inside the database. If you need to replicate only a subset, replicate between different kinds of database, or apply conflict-resolution logic, you can move replication into the application layer. Tools like Oracle GoldenGate read the database log; alternatively, triggers run custom code on a data change and can record it in a table for an external process to pick up (the source cites Databus for Oracle and Bucardo for Postgres). It has greater overhead and more bugs than built-in replication, but flexibility.

Problems with replication lag

Fault tolerance is only one reason to replicate; scalability and latency are others. Writes go through the leader but reads can go anywhere, which suits workloads with mostly reads and few writes (a common web pattern): add followers and spread reads over them. The source says this read-scaling architecture realistically works only with asynchronous replication, since a synchronous setup across many followers would be down whenever any one of them was, and the more nodes the likelier that is.

The catch: an async follower may be behind, so the same query on leader and follower at the same time can give different answers. That's temporary; stop writing and wait, and followers catch up. This is eventual consistency. The word "eventually" is deliberately vague: there's no limit to how far a replica can fall behind. Normally lag is a fraction of a second, but near capacity or with network trouble it can reach seconds or minutes. (The source notes eventual consistency isn't only a NoSQL thing; asynchronous followers in relational databases behave the same way.) Three anomalies follow.

1. Reading your own writes

A user posts a comment (sent to the leader), then the page reloads and reads from a follower that hasn't received it yet. To the user their data looks lost. The guarantee that fixes it is read-after-write consistency: users always see their own updates after reload. It makes no promise about other users' updates. Techniques the source lists:

  • Read from the leader anything the user might have modified, and from followers otherwise. A simple rule when only the owner can edit something: always read the user's own profile from the leader, others' from followers.
  • If most things are editable that defeats read scaling, so use other criteria: for example, read from the leader for one minute after the user's last update, or block queries on followers more than a minute behind.
  • The client remembers the timestamp of its latest write, and the system ensures the serving replica has caught up to at least that point, or sends the read elsewhere, or waits. The timestamp can be a logical one such as a log sequence number, or the system clock (making clock synchronization critical).
  • With replicas in several datacenters, requests needing the leader must be routed to the datacenter that has it.

Using several devices adds cross-device read-after-write: write on the phone, read on the laptop. Timestamp-remembering then needs centralized metadata, and different devices may be routed to different datacenters (home broadband versus cellular), so you may need to route all of a user's devices to the same place.

2. Monotonic reads

A user refreshes and each request lands on a random replica: the first reads from a fresh follower and sees a new comment, the second from a lagging follower and the comment vanishes. Time appears to go backward. Monotonic reads guarantees that if one user makes several reads in sequence, they won't read older data after having read newer. It's weaker than strong consistency but stronger than eventual consistency. One way: each user always reads from the same replica (chosen, say, by a hash of the user ID), though if that replica fails the user must be rerouted.

3. Consistent prefix reads

If writes with a causal order (a question, then its answer) are replicated at different speeds, an observer might see the answer before the question. Consistent prefix reads guarantees that if writes happen in a certain order, readers see them in that order. It's a particular problem in partitioned databases (Chapter 6), where partitions operate independently and there's no global write ordering. One fix is to write causally related data to the same partition, which isn't always efficient; other algorithms track causal dependencies explicitly (the source points to a later section on the happens-before relationship).

Solutions for replication lag

With an eventually consistent system, ask what your app does if lag grows to minutes or hours. If "no problem", fine. If users would suffer, design for a stronger guarantee. The source's warning: pretending replication is synchronous when it is async "is a recipe for problems down the line". Handling these in application code (like leader reads) is complex and easy to get wrong. Ideally the database does the right thing, which is why transactions exist. Many distributed databases dropped them, arguing they cost too much performance and availability and that eventual consistency is inevitable at scale; the source calls that partly true but overly simplistic and promises a more nuanced view in later chapters (7 and 9).

Why it matters

Almost every production database you'll touch replicates. Knowing the sync/async trade-off tells you what "committed" actually means in your system; knowing failover's pitfalls explains why teams distrust automatic failover; and the three lag anomalies are the bugs users report as "my comment disappeared". It also sets up the next part, where more than one node accepts writes.

Remember this

  • In leader-based replication one replica takes writes and followers apply its log in order; reads can be served by followers.
  • Synchronous replication protects data but can stall writes; asynchronous keeps writing but can lose unreplicated writes if the leader is lost. A common compromise is one sync follower and the rest async.
  • Failover has three steps (detect, elect, reconfigure) and many hazards: lost writes, split brain, bad timeouts.
  • The log can be statement-based, WAL, logical, or trigger-based; logical logs decouple replication from the storage engine.
  • Lag causes stale reads; three named guarantees (read-after-write, monotonic reads, consistent prefix) address specific anomalies.

Try it yourself

  1. Toy leader and follower. Model a leader with an append-only log and a follower that applies entries in order. Done when you can pause the follower, write three keys, and show a stale read, then resume and show convergence.
  2. Read-your-writes. Have writes return a log position, and make reads carry that position: if the chosen follower has applied less, fall back to the leader. Done when a read right after a write never returns stale data for that client.
  3. Bootstrap a follower. Snapshot the leader's data with its log position, keep writing on the leader, then start a new follower from the snapshot and replay. Done when the new follower equals the leader.
  4. Break statement replication. Using SQLite or plain Python, replay a statement that stores the current time or a random number on two "replicas" and compare. Then replay row values instead. Done when you can explain the difference.
  5. Monotonic reads. Simulate three followers at different lag and a client that picks a random one each time; count the backward-in-time events. Then pin each user to one follower by hashing the user ID. Done when the count drops to zero (and then kill the pinned follower and decide what the client should do).
