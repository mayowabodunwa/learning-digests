EC2 Purchasing Options: On-Demand, Savings Plans, Reserved Instances, Spot and Friends

An EC2 instance is the same machine no matter how you pay for it. What changes is the deal: how long you commit, how much flexibility you keep, whether AWS can take the machine back, and whether a seat is guaranteed to be there when you ask. This digest walks through each deal in plain English so the pricing page stops feeling like a maze.

In one line

EC2 lets you buy the same compute in different ways (pay as you go, commit to usage, commit to a configuration, borrow spare capacity, reserve a seat, or rent dedicated hardware), and each way trades price against commitment, flexibility and certainty.

The big idea

When I first looked at EC2 pricing I assumed "the price" was one number. It isn't. The AWS docs list seven separate ways to pay for EC2, and they answer different questions. Some are about money (can I pay less if I promise something?). Some are about capacity (will a machine actually be there when I ask?). Some are about who else is on the hardware (do I need a server that's just mine?). Mixing those questions up is the most common beginner mistake, so this digest keeps them apart on purpose.

One honest note before we start: this digest deliberately contains no dollar prices and no percentage guarantees of its own. Prices change by Region, instance type and over time, and the docs point you to live pricing pages for them. Where the docs state a discount ceiling ("up to"), I quote it and label it as a ceiling, not a promise.

Key terms

  • On-Demand Instance: an instance you launch and pay for by the second while it runs, with no long-term commitment.
  • Commitment / term: a promise to AWS to use (and pay for) a certain amount for a fixed period, which for Savings Plans and Reserved Instances is 1 or 3 years. e.g. "$X per hour for 1 year".
  • Savings Plan: a billing deal where you commit to a steady spend measured in USD per hour, and get lower rates on matching usage.
  • Reserved Instance (RI): a billing discount (not a physical machine) that applies to matching On-Demand usage, in return for a 1 or 3 year commitment to a configuration.
  • Spot Instance: an instance that runs on spare EC2 capacity at a discount, which EC2 can take back.
  • Spot price: the current hourly price of a Spot Instance, set by EC2 per instance type per Availability Zone and adjusted gradually.
  • Interruption: EC2 reclaiming a Spot Instance by terminating, stopping or hibernating it.
  • Capacity Reservation: a reservation of compute capacity for specific instance attributes in one Availability Zone. It is about having a seat, not about a discount.
  • Tenancy: whether your instance shares physical hardware with other accounts (default) or runs on hardware dedicated to you.
  • Dedicated Host / Dedicated Instance: two ways to run on single-tenant hardware (details below).
  • vCPU: a virtual CPU. The On-Demand quota is counted in these.
  • Availability Zone (AZ): one of the isolated locations inside an AWS Region.
  • Instance metadata: information an instance can read about itself from a special local address, 169.254.169.254. Spot notices show up there.

How it works

0. Grounding: what is actually being "purchased"?

EC2 (Elastic Compute Cloud) rents you virtual servers called instances. If you've read the earlier EC2 digest, you know an instance is launched from an AMI and moves through a lifecycle (pending, running, stopped, terminated). Purchasing options sit on top of that. They don't change what an instance is. They change the commercial terms around it.

The docs' own summary page lists these seven options: On-Demand Instances, Savings Plans, Reserved Instances, Spot Instances, Dedicated Hosts, Dedicated Instances, and Capacity Reservations. A useful way to hold them in your head is to sort them by the question each one answers:

  • "Can I pay less if I promise to use compute?" Savings Plans and Reserved Instances.
  • "Can I pay less if my work can be interrupted?" Spot Instances.
  • "Can I be sure a machine is available?" Capacity Reservations (and zonal Reserved Instances, see below).
  • "Do I need hardware that isn't shared with other accounts, or license rules tied to physical servers?" Dedicated Hosts and Dedicated Instances.
  • "I just want to launch something now and not promise anything." On-Demand.

The docs also give a short decision guide that matches this: if you can't commit to a specific instance configuration but can commit to a usage amount, Savings Plans fit. If you need a capacity reservation, use Reserved Instances (zonal) or Capacity Reservations for a specific AZ. Spot suits you if you can be flexible about when work runs and it can be interrupted. Dedicated Hosts or Instances can help with compliance requirements and with existing server-bound software licenses.

1. On-Demand Instances: the baseline

On-Demand is the default experience. Per the docs, you pay for compute by the second with no long-term commitment, you control the lifecycle (launch, stop, hibernate, start, reboot, terminate), and you pay only for the seconds the instance is in the running state, with a 60-second minimum. The per-second price for a running On-Demand instance is fixed and published on the On-Demand pricing page. The docs recommend On-Demand for short-term, irregular workloads that can't be interrupted.

Not the same as "always available." If EC2 doesn't have capacity when you ask, the docs' Spot comparison table says an On-Demand launch gets an insufficient capacity error (ICE). On-Demand means "no commitment," not "guaranteed seat." That gap is exactly what Capacity Reservations fill.

Quotas count vCPUs. There's a limit on running On-Demand instances per account per Region, and it's measured in vCPUs, not instance counts, grouped by instance family category. The docs' example: with a Standard-family quota of 256 vCPUs, you could run 32 m5.2xlarge (8 vCPUs each) or 16 c5.4xlarge (16 vCPUs each). The table on that page also shows default values: for the Standard families (A, C, D, H, I, M, R, T, Z) the default is 5, while several specialised families (like P, G and VT, X, Inf, Trn) default to 0 and must be raised. Treat those defaults as a snapshot of the docs page; EC2 also raises quotas automatically based on your usage, and you can request increases through Service Quotas. Instances in pending, stopping, stopped and hibernated states don't count, but Capacity Reservations do count, even when unused.

2. Savings Plans: commit to a dollar rate per hour

A Savings Plan gives lower prices than On-Demand in exchange for a commitment to a consistent amount of compute usage, measured in USD per hour, for 1 or 3 years (the docs define a year as 365 days and three years as 1,095 days). You can pay All upfront, Partial upfront or No upfront.

The important thing to grasp is that you're committing to spend, not to a particular machine. That's why it's flexible. The docs describe four plan types; two matter for EC2:

  • Compute Savings Plans: the most flexible. The docs say they apply to EC2 usage regardless of instance family, size, Region, operating system or tenancy, and also to Fargate and Lambda usage. You can move a workload from c5 to m5, or from one Region to another, and keep the lower rate. The docs give "up to 66% off On-Demand" as the ceiling.
  • EC2 Instance Savings Plans: you commit to one instance family in one Region (the docs' example is m5 in Virginia). In exchange you get a deeper discount ceiling ("up to 72%"), and it still applies across sizes, operating systems and tenancy within that family and Region.

The other two types are SageMaker AI Savings Plans and Database Savings Plans, which cover those services and are outside this EC2 digest.

Caveats worth writing down. (1) The commitment can't be changed after purchase, but you can buy additional plans as usage changes. (2) Per the docs, Savings Plans don't reserve capacity. The Capacity Reservations page's comparison table says "No capacity reserved." (3) Spot Instances aren't covered by Savings Plans, and Spot spend doesn't use up your Compute Savings Plan commitment. (4) Dedicated Instance per-Region fees (the docs mention $2/hour in every Region where you have at least one Dedicated Instance running) are not discounted. (5) The percentages are "up to" ceilings from the docs, not what you will definitely save; actual savings depend on your usage.

Where recommendations come from. The docs say to use AWS Cost Explorer to see recommended commitment levels, and to purchase and manage plans.

3. Reserved Instances: commit to a configuration

The docs open this page with a recommendation: AWS recommends Savings Plans over Reserved Instances because they're easier and more flexible, while offering lower prices (up to 72% off, the same ceiling). I'm including RIs anyway, because you'll meet them in existing accounts and on exams, and because they illustrate the idea of "commit to a configuration."

An RI is a billing discount, not a machine. The docs are explicit: Reserved Instances are not physical instances. They're a discount applied to On-Demand usage that matches certain attributes. Four attributes determine the price: instance type (like m4.large), Region, tenancy and platform (operating system).

Term and payment. 1 or 3 years (3 years gives a bigger discount, per the docs). Payment: All Upfront, Partial Upfront or No Upfront; in general, paying more upfront saves more. No Upfront still means you're obligated to pay monthly for the whole term, which is why a billing history is required first. RIs do not renew automatically; when they end you keep running but pay On-Demand rates. You cannot cancel an RI purchase, though you may be able to modify, exchange or sell it.

Standard vs Convertible. Standard RIs give the biggest discount but can only be modified (not exchanged). Convertible RIs give a lower discount, but can be exchanged for another Convertible RI with different attributes, and can also be modified.

Regional vs zonal scope. The scope doesn't change the price, but it changes behavior:

  • A regional RI does not reserve capacity. Its discount applies in any AZ in the Region, and (only for Linux/Unix, default tenancy) across sizes within the instance family.
  • A zonal RI does reserve capacity in the named AZ, but the discount applies only in that AZ and only for that exact family and size.

So "Reserved" in the name is a trap: depending on scope, you may be reserving a discount without reserving any capacity.

4. Spot Instances: borrow spare capacity

A Spot Instance runs on spare EC2 capacity that's available at a lower price than On-Demand. The Spot price is set by Amazon EC2 for each instance type in each AZ, and is adjusted gradually based on long-term supply and demand. Your instance runs whenever capacity is available. The docs recommend Spot when you can be flexible about when work runs and when it can be interrupted, and name data analysis, batch jobs, background processing and optional tasks as good fits.

Vocabulary. A Spot capacity pool is a set of unused instances with the same type and AZ. A Spot Instance request asks for one, and is either one-time or persistent (a persistent request is resubmitted automatically after an interruption).

Why it can be interrupted. The docs give three reasons: capacity (EC2 needs it back, mainly to repurpose capacity, but also for host maintenance or hardware decommission), price (the Spot price rises above a maximum price you set; the docs note that setting a maximum price makes interruptions more frequent than not setting one), and constraints (for example a launch group, which gets terminated together when the constraint can't be met). The docs say it is always possible that a Spot Instance might be interrupted.

Interruption behavior. You choose what EC2 does: terminate (the default), stop, or hibernate. Stop requires a persistent request (and no launch group); only EC2 can restart an interrupted stopped instance, when capacity is available in the same AZ for the same type. While it's stopped you pay only for the preserved EBS volumes.

The two-minute warning (with caveats). The docs describe an interruption notice issued two minutes before EC2 stops or terminates the instance. For hibernation you get the notice but not a two-minute lead, because hibernation begins immediately. The notice appears as an EventBridge event and in instance metadata, and the docs say it is emitted on a best-effort basis, so it's possible to be interrupted before a warning is available. They recommend checking for it every 5 seconds. From inside the instance, the item is spot/instance-action in the metadata; when nothing is planned it isn't there and you get an HTTP 404. When it is there, the docs' example output looks like {"action": "terminate", "time": "2017-09-18T08:22:00Z"} (a time in UTC).

The earlier hint. A rebalance recommendation is a signal that a running Spot Instance is at elevated risk of interruption. It can arrive before the two-minute notice, but the docs warn it isn't always possible, so it may arrive together with it. It is also best-effort, and only supported for Spot Instances launched after November 5, 2020 00:00 UTC. Metadata path: events/recommendations/rebalance.

Preparing, per the docs. Create Spot requests through an Auto Scaling group so replacements launch automatically; use an AMI (and optionally user data) so a new instance is ready quickly; remember instance store data is lost when the instance stops or terminates, so keep important data in S3, EBS or DynamoDB; split work into small tasks or use checkpoints; and test with an On-Demand instance that you terminate yourself, or with AWS Fault Injection Service.

Billing when interrupted. This one has fine print. If EC2 interrupts a Windows or Linux (non-SUSE) Spot Instance in its first hour, there's no charge; after the first hour you pay for the seconds used. If you stop or terminate it, you pay for seconds used. SUSE has different rules (full-hour charging in some cases). Check the billing page before relying on this. Also, Spot is not covered by Savings Plans, and EBS volumes of a stopped Spot Instance still cost money.

Seeing prices. The Spot pricing page shows current lowest prices (updated every five minutes) and the console or describe-spot-price-history shows up to three months of history. A small gotcha from the docs: AZ codes like us-west-2a are mapped independently for each account, so the same code can mean different physical zones in different accounts.

5. Capacity Reservations: pay for the seat, not for a discount

An On-Demand Capacity Reservation reserves compute capacity for specified instance attributes (instance type, platform, AZ, tenancy) in one AZ, for any duration. The docs use it for scaling events, regulatory or disaster-recovery needs, and strict capacity requirements.

  • Immediate-use reservations have no term commitment; you can modify or cancel them at any time, and cancelling stops the charges.
  • Future-dated reservations make capacity available on a date you choose, with a commitment duration you can't shrink below your initial commitment. Cancelling may carry a charge. The docs add some limits: minimum of 32 vCPUs worth of instances, and only certain families (C, G, I, M, R, T, U and X).
  • By default a reservation is open: any instance with matching attributes automatically lands in it. You can instead target it so only chosen instances use it.

The comparison table in the docs puts it neatly: Capacity Reservations have no billing discount on their own (you can combine them with Savings Plans or Regional RIs to get one), whereas Savings Plans and RIs give a discount. Zonal RIs reserve capacity in an AZ; Savings Plans and regional RIs don't. One thing the docs do state: active but unused Capacity Reservations still count against your On-Demand Instance quota. How reserved capacity is billed while unused is on a separate pricing and billing page that I did not read, so check it before relying on any assumption there.

Capacity Blocks for ML are a sibling feature: you reserve GPU instances for a defined period starting on a future date, for training and fine-tuning. Mentioned for completeness; it's outside the core of this topic.

6. Dedicated Hosts and Dedicated Instances

By default, EC2 instances run on shared-tenancy hardware, so other AWS accounts may be on the same physical server (isolated by the platform). Two options put you on hardware that is not shared with other accounts. The docs state there are no performance, security or physical differences between the two; the differences are control and billing:

  • Dedicated Host: a physical server fully dedicated to you. You can see sockets and physical cores, use host affinity (keep an instance on the same server), target placement, and bring per-socket, per-core or per-VM software licenses. Billing is per host.
  • Dedicated Instance: instances on hardware dedicated to a single account, with no visibility or control over placement; stop and start and it might land on a different host. Billing is per instance, and BYOL support is partial. Dedicated Instances might still share hardware with your own non-dedicated instances. Note the docs also say a dedicated-tenancy EBS-backed instance's EBS volume isn't on single-tenant hardware.

One more table row worth remembering: Capacity Reservations are supported for Dedicated Instances but not for Dedicated Hosts (Dedicated Hosts have their own reservation option, Dedicated Host Reservations, for a discount the docs describe as "up to 70 percent" versus On-Demand host pricing). The docs' own decision rule: if you don't need placement control or per-core licensing, consider Dedicated Instances.

7. Putting it together: a worked thought experiment

Imagine a web app with three kinds of work. A small always-on API tier, a nightly batch job that can restart if killed, and a database server that needs to be there at launch every time. A sensible-sounding split, purely illustrative: cover the steady API baseline with a Savings Plan (committing only to what you're confident you'll always run), run the batch workers on Spot with checkpoints, and consider a Capacity Reservation (or zonal RI) only where a failed launch would be costly. Anything spiky or experimental stays On-Demand. This is a mental model, not a recommendation: whether it saves money depends on real prices and real utilization, which this digest intentionally doesn't quote.

Simplification flag: the "baseline vs burst" story above is the common pattern, not the only one. Plenty of workloads run entirely on Spot or entirely On-Demand.

Why it matters

Purchasing choices are where most of the savings (and surprises) in an EC2 bill come from, and they quietly shape architecture. Spot only works if your app tolerates interruption, which links straight to Auto Scaling groups and stateless design (coming up in later EC2 topics). Capacity Reservations remind you that "On-Demand" isn't a guarantee. Commitments (Savings Plans, RIs) can't be cancelled, so understanding what they lock in is worth a minute before clicking buy. A real, dated pointer: the EC2 docs themselves now lead the Reserved Instances page with a recommendation to use Savings Plans, so older blog posts that treat RIs as the default are out of date on that point.

Remember this

  • EC2 has seven ways to pay: On-Demand, Savings Plans, Reserved Instances, Spot, Dedicated Hosts, Dedicated Instances and Capacity Reservations. They answer different questions: discount, interruption, capacity, or hardware.
  • On-Demand bills per second with a 60-second minimum and no commitment, but doesn't guarantee capacity, and quotas are counted in vCPUs.
  • Savings Plans commit you to dollars per hour for 1 or 3 years; Compute plans are the most flexible, EC2 Instance plans trade flexibility for a deeper "up to" discount. They don't reserve capacity, and can't be changed after purchase.
  • Reserved Instances are a billing discount tied to configuration. Regional ones don't reserve capacity, zonal ones do. The docs now recommend Savings Plans over RIs.
  • Spot is spare capacity that EC2 can take back. The 2-minute notice is best effort, so design work that survives losing the instance without warning.

Try it yourself

Heads up: projects 1, 3 and 5 need no AWS account. I ran the logic of projects 1 and 3 in Python locally while writing this. Project 2 uses a read-only AWS CLI call (describe-spot-price-history) whose options I checked against the CLI reference page, but I did not run it against a live account. Nothing here launches paid resources.

  1. Break-even calculator (no AWS needed). Invent your own hourly On-Demand rate (a made-up number, not a real price) and a committed rate that is some fraction of it. Write a script that loops over utilization from 10% to 100% of a month and prints whether a commitment (you pay for every hour) or On-Demand (you pay only for hours used) is cheaper. Done when: you can point to the utilization where the winner flips, and you can explain why a commitment loses at low utilization. (My version flipped between 70% and 90% with a committed rate of 70% of the invented On-Demand rate. Yours will differ.)
  2. Read real Spot price history. With the AWS CLI configured and read permission for EC2, run aws ec2 describe-spot-price-history --instance-types m5.large --product-descriptions "Linux/UNIX" --max-items 20 --query 'SpotPriceHistory[].{Zone:AvailabilityZone,Price:SpotPrice,Time:Timestamp}' --output table. Swap the instance type for any you like. Done when: you can say whether prices differ between AZs, and why the docs say AZ codes may map differently per account.
  3. Simulate a Spot interruption watcher (no AWS needed). Write a small local HTTP server that answers 404 on a path like /latest/meta-data/spot/instance-action for the first few requests, then returns {"action": "terminate", "time": "..."}. Write a watcher that polls it (the docs suggest every 5 seconds; use shorter in the simulation) and, on seeing the notice, saves a checkpoint file and exits cleanly. Done when: the watcher treats 404 as "all clear" and the checkpoint exists after the notice appears. Bonus: kill the watcher at random before the notice and show your job resumes from the last checkpoint.
  4. vCPU quota planner. From the docs' example (a 256-vCPU Standard quota, m5.2xlarge at 8 vCPUs, c5.4xlarge at 16), write a function that takes a quota and a list of (type, vCPUs, count) and says whether it fits, then add a "Capacity Reservation still counts" line item. Done when: it correctly rejects 33 m5.2xlarge at a 256 quota, and shows how an unused reservation eats headroom.
  5. Decision-tree flashcards. Write a function that takes yes/no answers (interruptible? needs guaranteed capacity? needs per-core licensing? steady baseline?) and returns the option(s) the docs' guidance points to. Make it return a list, because combos are valid. Done when: you can run five realistic scenarios through it and justify each result using a sentence from the docs.
  6. Compare the fine print. Open the Reserved Instances, Savings Plans and Capacity Reservations pages and build a one-page table with columns: term, cancellable?, reserves capacity?, flexibility. Fill every cell with a quote-free paraphrase and a link. Done when: no cell says "I think", and you've noted anything the pages don't state.
