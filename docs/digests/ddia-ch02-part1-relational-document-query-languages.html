Data Models and Query Languages, Part 1: Relational vs. Document

Why the same piece of data (a résumé, a user profile) looks completely different depending on whether you store it as rows in tables or as one self-contained document, why that choice barely matters at first and then suddenly matters a lot, and why "declarative" beat "imperative" as the way we ask databases for things.

In one line

Every database forces your data into a shape (relational tables, JSON-like documents, or something else), and that shape quietly decides how painful your future features will be, especially once your data items start pointing at each other.

The big idea

There's no single "best" way to store data. The relational model (rows in tables, joined together) and the document model (self-contained JSON-like blobs) each make a different bet about how your data is shaped and how it'll grow. The relational model bets that your data will end up interconnected and optimizes for that. The document model bets that most of what you need lives together in one tree and optimizes for fetching that tree in one go. Neither bet is wrong, but picking the one that doesn't match your data's real shape is how you end up fighting your database for years.

Key terms

  • Relation (table) / tuple (row) — the relational model's vocabulary: a relation is an unordered collection of tuples. In SQL you just call these a table and its rows.
  • RDBMS — relational database management system: software (PostgreSQL, MySQL, Oracle, and so on) built around the relational model.
  • NoSQL — a loose, retroactively-defined label ("Not Only SQL") for a wave of nonrelational databases that took off in the 2010s. It isn't one technology, it's a hashtag that stuck.
  • Polyglot persistence — using several different kinds of databases side by side in one system, because different parts of your data fit different models.
  • Document model / document database — data stored as self-contained, JSON-like (or XML-like) documents, each holding a whole nested tree of information. MongoDB, CouchDB, and RethinkDB are examples.
  • Object-relational mismatch (impedance mismatch) — the awkwardness of translating between objects in your application code and rows/columns in a relational database.
  • ORM (object-relational mapping) — a library (like ActiveRecord or Hibernate) that automates a lot of that translation, without fully hiding it.
  • One-to-many relationship — one record owns many of another kind (one user has many jobs on their résumé). This is the shape document databases handle naturally.
  • Many-to-one relationship — many records point at one shared record (many users live in one region). This is where documents start to strain.
  • Many-to-many relationship — records on both sides can point at several of the other (users can work at organizations, organizations have many employees).
  • Normalization — storing a piece of information in exactly one place and having everything else reference it by ID, instead of copying it everywhere it's used.
  • Denormalization — the opposite: deliberately duplicating data to avoid a lookup, at the cost of having to keep the copies in sync.
  • Foreign key / document reference — the same idea under two names: an ID stored in one record that points at another record, resolved with a join (relational) or a follow-up query (document).
  • Hierarchical model — an old (1960s-70s) data model where every record has exactly one parent, forming a tree. IBM's IMS used this.
  • Network model (CODASYL) — a 1970s alternative to the hierarchical model where a record could have multiple parents, letting you model many-to-many links. You queried it by physically walking chains of pointers.
  • Access path — in the hierarchical/network model, the specific chain of pointers your code had to follow to reach a record. If you didn't have a path to some data, you were stuck.
  • Query optimizer — the part of a relational database that automatically figures out the fastest way to run your query (which indexes to use, what order to join tables), so you never have to hand-pick an access path yourself.
  • Shredding — splitting one document-like structure across several relational tables (one row here, several rows there, linked by foreign keys).
  • Schema-on-read vs. schema-on-write — whether the structure of your data is enforced when you write it (schema-on-write, classic SQL) or only assumed by whatever code reads it later (schema-on-read, typical of document databases).
  • Data locality — how physically close together related pieces of data are stored, which affects how many disk reads it takes to fetch them all.
  • Declarative vs. imperative (query language) — declarative says what result you want and leaves the "how" to the system (SQL, CSS). Imperative spells out the exact steps to get there (a for-loop).
  • MapReduce — a programming model for processing large amounts of data using a map function (transforms each item) and a reduce function (combines the results), sitting somewhere between declarative and imperative.

How it works

What a "data model" actually is

Before comparing specific models, it helps to notice that almost everything you build is a stack of data models, each one hiding the layer beneath it. As an application developer, you look at messy real-world things (people, orders, sensor readings) and turn them into objects or data structures in your code. When you want to store those, you translate them again into a general-purpose data model the database understands: rows in tables, JSON documents, or a graph. The database engine then translates that, in turn, into bytes on a disk or across a network, and hardware engineers have already turned those bytes into electrical signals underneath that. Each layer only needs to expose a clean interface to the layer above it; nobody writing application code needs to think about magnetic fields, and nobody designing a disk format needs to know what a "résumé" is. This digest is about layer two: the general-purpose data model you choose to represent your application's structures in storage, and specifically the fight between the relational model and the document model for that spot.

The relational model, and why NoSQL pushed back

The relational model, proposed by Edgar Codd in 1970, organizes data into relations (tables), each an unordered collection of tuples (rows). It grew out of 1960s-70s business data processing (bank transactions, airline bookings, payroll) and by the mid-1980s had become the default choice for structured data. Its big selling point was hiding implementation detail: instead of forcing developers to think about how data was physically laid out on disk, the relational model gave them a clean, declarative interface and let the database figure out the rest. That approach turned out to generalize far beyond its original business-processing use case, and relational databases have stayed dominant for roughly 25-30 years, which is close to an eternity in computing.

NoSQL is the most recent serious challenge to that dominance. The name is a bit of an accident: it started in 2009 as a catchy hashtag for a meetup about open-source, nonrelational databases, not as a description of any one technology, and it's since been reinterpreted as "Not Only SQL." A few different pressures drove people toward it: needing more scalability than relational systems could easily give (very large datasets, very high write volume), wanting free and open-source options, wanting query features the relational model didn't support well, and simple frustration with how rigid relational schemas can feel. Because different applications have genuinely different needs, it's common today to use relational databases alongside various nonrelational stores rather than picking one winner for everything, an idea sometimes called polyglot persistence.

The document model and the object-relational mismatch

Most application code today is written in an object-oriented style, and that creates friction with SQL's world of flat tables, rows, and columns: you end up needing a translation layer between "an object in memory" and "a row spread across several tables," a disconnect commonly called the object-relational mismatch. ORMs like ActiveRecord and Hibernate cut down the boilerplate for that translation, but they can't erase the underlying mismatch entirely.

Take a LinkedIn-style résumé: a user has one first name and last name (fits fine as plain columns), but an arbitrary number of past jobs, periods of education, and pieces of contact info (a one-to-many relationship that doesn't fit neatly into fixed columns). The traditional relational fix is to put positions, education, and contact info in their own tables, each row carrying a foreign key back to the user. An alternative is to encode the whole résumé as one JSON document:

{
  "user_id":     251,
  "first_name":  "Bill",
  "last_name":   "Gates",
  "positions": [
    {"job_title": "Co-chair", "organization": "Bill & Melinda Gates Foundation"},
    {"job_title": "Co-founder, Chairman", "organization": "Microsoft"}
  ],
  "education": [
    {"school_name": "Harvard University", "start": 1973, "end": 1975},
    {"school_name": "Lakeside School, Seattle", "start": null, "end": null}
  ],
  "contact_info": {
    "blog":    "http://thegatesnotes.com",
    "twitter": "http://twitter.com/BillGates"
  }
}

(This is an illustrative example in the same spirit as the kind of profile document you'd see modeled this way, not a real captured record.) A résumé is mostly a self-contained thing, so a document fits it well: every one-to-many relationship (user to positions, user to education pieces) just becomes nesting, which makes the tree structure of the data explicit instead of scattered across tables. Document databases like MongoDB, RethinkDB, and CouchDB are built around storing and querying data shaped like this. There's also a real, practical win here: fetching the whole profile takes one query against one document, versus either several queries or one messy multi-table join against the relational version, because all the relevant information already lives in one place. That's a locality advantage, and we'll come back to it below.

Many-to-one and many-to-many relationships (where joins stop being optional)

Look again at that JSON example: region_id and industry_id are IDs, not the plain text "Greater Seattle Area" or "Philanthropy". That's deliberate. Storing an ID instead of a string buys you consistent spelling, no ambiguity between two places with the same name, one place to update the name if it ever changes, easier localization, and better search (a search for "Washington state" can match a profile that only stored "Seattle," because the region list can encode that Seattle is in Washington). The tradeoff is duplication: if you store the text directly on every record, you're copying human-meaningful information everywhere it's used, and every copy needs updating if it changes. Removing that duplication by referencing a shared ID instead is the core idea behind normalization.

Here's the catch: normalizing this kind of data always produces many-to-one relationships (many people live in one region, many people work in one industry), and many-to-one relationships don't fit neatly into a pure document model. Relational databases make referencing another table's rows easy, because joins are a first-class, well-optimized operation. Document databases are built for one-to-many tree structures where joins aren't needed, so their join support is often weak or missing, which means you either emulate the join yourself with multiple queries in application code, or keep a small, slow-changing reference table (like a list of regions) cached in memory in your application instead.

And it tends to get worse over time, not better. Imagine two very reasonable feature requests on that résumé app: first, turning "organization" and "school_name" from plain strings into references to real organization and school entities (so each one can have its own page, logo, and news feed); second, letting one user write a recommendation for another, showing the recommender's name and photo, which has to update automatically if the recommender changes their photo later. Both of these turn what looked like a clean, self-contained document into something with many-to-many relationships: an organization has many employees, a user has written many recommendations and received many, and now those references need joins when you query them, however you're storing the data.

Déjà vu: this argument is older than NoSQL

This exact tension, one-to-many is easy but many-to-many is hard, goes back to the very first database systems. IBM's Information Management System (IMS), the dominant business database of the 1970s, used a hierarchical model that looks a lot like today's JSON documents: everything was a tree of records, each with exactly one parent. Like document databases, it handled one-to-many relationships well and struggled with many-to-many ones, and it didn't support joins.

Two rival fixes were proposed. The network model (standardized by a committee called CODASYL) let a record have multiple parents, which could represent many-to-many links, for example one shared "Greater Seattle Area" record that many different users could each link to. But the links were more like raw pointers than foreign keys, and the only way to reach a record was to physically walk a chain of those pointers starting from some root, an access path. If your data had a lot of many-to-many links, several different paths could lead to the same record, and it was on the programmer to keep track of all of them by hand. If you ever needed a query your existing access paths didn't support, you were stuck rewriting a lot of handwritten traversal code. Even the people on the CODASYL committee reportedly compared it to navigating an n-dimensional space.

The relational model won that 1970s fight by refusing to expose access paths at all: a table is just a flat collection of rows, full stop, and you can read any of them by any condition you like. The trick that made this practical was the query optimizer, a piece of the database that automatically figures out which indexes and join order to use. You only have to build that optimizer once, and then every application using the database benefits, instead of every application separately hand-coding its own access paths. That's also why adding a new relational index doesn't require you to rewrite your existing queries: the optimizer just starts using it where it helps.

Here's the part worth sitting with: relational and document databases actually resolve many-to-one and many-to-many relationships the same underlying way, an ID that points at another record, resolved at read time by a join (relational) or a follow-up query (document, using what's usually called a document reference). Document databases never adopted the network model's pointer-chasing approach. So the real dividing line isn't "documents vs. tables," it's "does this database make joins a cheap, well-optimized, built-in operation, or does the application have to fake them." If your data is mostly one-to-many trees, or has barely any relationships at all, a document model is a genuinely good fit. If many-to-many relationships are common and only going to grow, the relational model handles that far more gracefully, and once the connections get dense enough, even the relational model starts to strain, which is where graph-based models come in (a topic worth its own separate dig, since it deserves more room than fits here).

Relational vs. document today: schema flexibility

Most document databases, and the JSON support built into some relational databases, don't enforce a schema on what you write: you can add arbitrary keys and values to a document, and code reading it back has no guarantee about what fields will actually be present. People often call this "schemaless," but that's a bit misleading. There's still an implicit schema, whatever structure the reading code assumes, it's just not enforced by the database itself. A more accurate pair of terms: schema-on-read (the structure is assumed by the reader, not checked at write time) versus schema-on-write (the traditional relational approach, where the database rejects data that doesn't match the declared structure). It's a similar flavor of tradeoff to dynamic vs. static type checking in programming languages, and like that debate, there's no universally right answer.

The difference shows up clearly when you want to change your data's shape. Say you're storing each user's full name in one field and want to split it into first and last name instead. In a document database, you'd typically just start writing new documents with the new fields and add a small bit of code to handle documents written the old way when they're read back, something like checking whether first_name is missing and deriving it from the old name field on the fly. In a schema-on-write relational database, you'd typically run an explicit migration: an ALTER TABLE to add the column, then an UPDATE to backfill it from the old field. It's worth being precise here rather than repeating a popular myth: most relational systems execute a plain ALTER TABLE ADD COLUMN in milliseconds, it's not inherently slow. MySQL is a specific, named exception that historically rewrote the whole table on certain ALTER TABLE operations, which could mean real downtime on a large table (various tools exist to work around that). Separately, the backfilling UPDATE itself is likely to be slow on a large table on any database, since it has to rewrite every row, so if that's not acceptable, you can leave the new column NULL and fill it in lazily at read time instead, which is effectively borrowing the document database's trick.

Schema-on-read tends to be genuinely useful, not just a shortcut, when your records are naturally heterogeneous, for instance when you're storing many different kinds of objects that don't practically fit one table each, or when your data's structure is dictated by some external system you don't control and that can change on its own schedule. When every record really is expected to have the same shape, an enforced schema is a helpful safety net, not a bureaucratic obstacle, since it documents and checks your assumptions instead of leaving them implicit in whatever code happens to read the data.

Relational vs. document today: data locality

A document is usually stored as one continuous encoded blob (JSON, XML, or a binary variant like MongoDB's BSON). If your application typically needs the whole document at once, say, to render an entire profile page, that locality is a genuine performance win: one read instead of several index lookups across multiple tables, each of which can mean an extra disk seek. But that locality advantage only pays off when you actually need most of the document at once. If you only need a small piece of a large document, the database typically still has to load the whole thing, which can waste effort. And on updates, the whole document usually has to be rewritten in place, since only changes that don't alter the document's encoded size can be applied cheaply. The practical, bounded takeaway (this is a common pattern, not a hard law): keep documents reasonably small, and be cautious about writes that keep growing a document's size.

It's also worth flagging that locality-through-grouping isn't exclusive to documents. Some relational systems offer similar locality by letting you declare that one table's rows should be physically interleaved with a related parent table (Google's Spanner and Oracle's multi-table index cluster tables both support this), and systems built on the Bigtable-style column-family model (Cassandra, HBase) use grouping for a similar purpose. Relational and document databases have also been converging in general: most relational systems now support JSON columns, and some document databases (RethinkDB, for instance) support relational-style joins in their query language. Treating this as an either/or choice is increasingly less accurate than it used to be.

Query languages: declarative vs. imperative

Alongside its data model, SQL introduced a genuinely different way of asking a database for things: declarative, where earlier systems like IMS and CODASYL used imperative query code. The distinction is easiest to see side by side. Imagine filtering a list of animal species down to just the sharks. An imperative approach spells out the steps: loop over every animal, check a condition, and manually collect the matches, something like a JavaScript for loop that pushes matching items into a results array one at a time. A declarative approach just states the pattern of what you want and leaves the "how" up to the system: SELECT * FROM animals WHERE family = 'Sharks';. You never tell the database to loop over anything, sort anything, or manage an index, you just describe the shape of the result you need.

The same contrast shows up outside databases entirely. Styling a web page with CSS is declarative: a selector like li.selected > p just states which elements should be blue, and the browser figures out how and keeps it up to date automatically if the page changes. Doing the same thing with imperative JavaScript DOM code means manually looping over every list item, checking its class, and setting a style, and crucially, if the underlying condition changes later (say, a different item gets marked "selected"), the imperative code doesn't automatically undo its earlier change unless you rerun it; the declarative CSS rule just stops applying on its own.

Declarative query languages have a real practical edge, and it's not just that they tend to be shorter to write. Because a declarative query never specifies exactly how to fetch the data, only what result is wanted, the database is free to change its internal implementation, reorder rows on disk, add new indexes, rewrite its storage format, without breaking any existing query. Imperative code that assumes a particular order or a specific access path can't be changed underneath so freely, because you can never be fully sure what the calling code is silently relying on. Declarative languages also tend to parallelize better: since modern CPUs mostly get faster by adding more cores rather than higher clock speeds, and imperative code that specifies a strict step-by-step order is inherently hard to split across cores or machines, a declarative query, which only describes the result and not the algorithm, gives the database room to execute it in parallel if that helps.

MapReduce querying

MapReduce is a programming model for processing large amounts of data in bulk across many machines, popularized by Google, and a limited form of it shows up in some NoSQL datastores (MongoDB and CouchDB among them) as a way to run read-only queries across many documents. It sits in an interesting middle ground: not fully declarative, not fully imperative either. You write two small snippets of code, a map function and a reduce function, and the surrounding framework calls them repeatedly on your behalf.

Picture logging ocean animal sightings and wanting a report of shark sightings per month. In SQL you'd write one declarative query with a WHERE filter, a GROUP BY, and a SUM. With MongoDB's MapReduce feature, the same report looks like two cooperating JavaScript functions: a map function that runs once per matching document and emits a key (year and month, like "1995-12") paired with a value (the number of animals seen), and a reduce function that's called once per unique key with the full list of values emitted under that key, and just sums them. So if two shark observations in December 1995 recorded 3 and 4 animals, map emits two ("1995-12", 3) and ("1995-12", 4) pairs, and reduce is called with ("1995-12", [3, 4]) and returns 7.

Map and reduce functions come with real restrictions: they have to be pure functions, meaning they can only use the data handed to them, can't fire off extra database queries of their own, and can't have side effects. That restriction is what lets the database run them anywhere, in any order, and safely rerun them after a failure. Despite the restriction, they're still powerful enough to parse strings, call library functions, and do real computation. That said, MapReduce is a fairly low-level tool for distributed execution, and it doesn't have any special monopoly on running at scale: SQL itself has nothing that limits it to a single machine, and plenty of distributed SQL implementations exist that never touch MapReduce at all. Writing two carefully coordinated JavaScript functions is also usually more work than writing one declarative query, and a query optimizer has more room to improve a declarative query's performance than it does a hand-written MapReduce job. For exactly these usability reasons, MongoDB 2.2 added a declarative alternative called the aggregation pipeline, and the same shark report in that language reads as a short list of pipeline stages (a $match filter followed by a $group-and-$sum) rather than two custom functions. It's a nice small lesson on its own: a NoSQL system built to avoid SQL can still end up quietly reinventing something SQL-shaped, just with different syntax.

Why it matters

This isn't a settled argument you can look up once and forget. Every time you start a new project, "what shape is my data actually going to be in a year" is a real design question, not a formality, because the answer changes whether a document database will keep feeling natural or start fighting you. The résumé example is a pattern that repeats constantly: features that look self-contained today (a profile, an order, a support ticket) tend to sprout references to other things (an organization, a recommender, a related ticket) as an application grows, and each new reference is a small vote for the relational model's strengths. Meanwhile, "schema-on-read vs. schema-on-write" and "declarative vs. imperative" aren't relics of the 1970s, they're the same tradeoffs you're making today anytime you pick a database, write a migration, or decide whether a query belongs in SQL or in application code.

Remember this

  • One-to-many is what document databases are built for. Many-to-many is where they start to strain, because joins are the relational model's specialty, not theirs.
  • An ID instead of a plain string isn't bureaucracy, it's normalization: one place to update, no ambiguity, easier search and localization, at the cost of needing a join or lookup to resolve it.
  • "Schemaless" document databases still have a schema, it's just implicit in whatever code reads the data, instead of enforced by the database when it's written.
  • Declarative (SQL, CSS) beats imperative (a for-loop, manual DOM code) mainly because it leaves the database or browser free to change how it gets the answer, without breaking anything that asked for it.
  • MapReduce sits between declarative and imperative, and even MongoDB eventually added a more declarative aggregation pipeline on top of it, because two hand-written functions are more work than one query.

Try it yourself

  • Same data, two shapes. Model a small "résumé" (a name plus a list of jobs and a list of education entries) once as a single JSON document and once as three normalized tables (users, positions, education) with foreign keys. Write the query or queries needed to fetch "everything about user X" in both. Done when: the document version takes one fetch, and you can show exactly how many queries (or how complex a join) the table version needs.
  • Denormalization staleness bug. Store a "recommendation" document that duplicates the recommender's name and photo URL directly inside it. Update the recommender's photo elsewhere and show the recommendation still displays the old one. Done when: you've reproduced the staleness, then fixed it by storing a reference (an ID) instead and resolving it with a lookup at read time.
  • Declarative vs. imperative filter. Given an array of objects (like the shark/animal example), write the same filtering logic two ways: an imperative loop that manually builds a results array, and a single declarative-style call (your language's built-in filter or equivalent). Done when: both return identical results, and you can explain in your own words why swapping the internal implementation behind the declarative version wouldn't break any code that calls it.
  • Access-path simulator. Build a tiny "network model": a handful of records connected by explicit parent/child pointers (including one record with two parents), and write code that can only fetch a record by walking a specific chain of pointers you define in advance. Done when: you can show that reaching a record you didn't build a path to requires writing new traversal code, not just a new query.
  • Toy MapReduce. Implement your own tiny map() and reduce() over an array of fake "sighting" records (a family and a count), reproducing a monthly-totals report, then check it against a plain loop-and-dictionary version of the same report. Done when: both approaches produce identical totals per month.
  • ALTER TABLE timing check. Using any relational database you have handy, create a table with a decent number of rows, then time a plain ALTER TABLE ... ADD COLUMN versus an UPDATE that rewrites every row to backfill it. Done when: you've printed both timings side by side and can say which one scales with table size and which (mostly) doesn't.

Go deeper

The most re-readable idea here is the many-to-one/many-to-many distinction: it's the single fact that predicts almost everything else in this comparison (which model needs joins, which one strains as an app grows, why relational won the 1970s debate). A natural next question to sit with: for an app or side project you're currently building, are the relationships between your main data types mostly one-to-many, or are they quietly turning many-to-many as you add features?
