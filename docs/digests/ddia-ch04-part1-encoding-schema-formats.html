Encoding and Evolution

Your application will change. Its data has to survive that change. This first half looks at what it actually means to turn an object into bytes, and why JSON, Thrift, Protocol Buffers, and Avro each handle a schema changing underneath them very differently.

In one line

How programs turn in-memory data into bytes and back again (encoding), and why the format you pick decides whether old code and new code can keep reading each other's data while your application evolves around them.

The big idea

Applications change constantly, and almost every change to a feature eventually means a change to the data it stores or sends, a new field, a renamed one, a value that used to be required and now isn't. The catch is that code doesn't update everywhere at once: during a rolling upgrade, or because a mobile user hasn't opened the app store in months, old code and new code end up running side by side, reading data written by each other. Whether that works out fine or corrupts something depends almost entirely on the encoding format you chose and how carefully its schema evolved. This half of the chapter walks through the formats themselves, from JSON up through Thrift, Protocol Buffers, and Avro, and the specific rules each one enforces (or doesn't) to keep old and new versions talking to each other safely.

Key terms

  • Encoding (also called serialization or marshalling) — turning an in-memory data structure (an object, a struct, a list) into a self-contained sequence of bytes, so it can be written to a file, stored in a database, or sent over a network. A pointer in memory means nothing to another process, so the bytes have to stand entirely on their own.
  • Decoding (deserialization, parsing) — the reverse: turning that byte sequence back into a usable in-memory structure.
  • Backward compatibility — newer code can correctly read data that was written by older code. Usually the easier direction, since you know exactly what the old format looked like.
  • Forward compatibility — older code can correctly read data that was written by newer code. Trickier, because the old code has to gracefully ignore additions it's never seen before.
  • Rolling upgrade (staged rollout) — deploying a new version of a server-side application to a few nodes at a time, checking it's healthy, then continuing, instead of replacing every node at once. It avoids downtime, but it guarantees old and new code coexist for a while.
  • Schema — a definition of what fields a record has and what type each one is. Thrift, Protocol Buffers, and Avro all require one before they can encode or decode a single byte.
  • Field tag — a small number assigned to a field in a Thrift or Protocol Buffers schema. The encoded bytes carry this number instead of the field's name.
  • Writer's schema / reader's schema (Avro) — the schema the encoding side used to write a record, versus the schema the decoding side is relying on. Avro's whole design is built around reconciling the two instead of requiring them to be identical.
  • Code generation — producing ready-to-use classes or structs in a programming language straight from a schema, so application code can read and write records without hand-writing the parsing logic.

How it works

Here's the grounding picture before the details. Programs keep data in two very different shapes. In memory, it lives in objects, structs, arrays, hash tables, and trees, structures built for the CPU to access and manipulate quickly, usually with pointers stitching pieces together. The moment you want to write that data to a file, store it in a database, or send it over a network, none of that works anymore: a pointer to a spot in your program's memory is meaningless to any other process. You need the data as a self-contained sequence of bytes instead. That translation, from in-memory structure to bytes, is encoding; the reverse is decoding. Everything below is about which byte format to use for that translation, and specifically what happens to already-encoded data sitting on disk or flowing across a network when the schema producing it changes underneath it.

1. Backward and forward compatibility — the ground rule

Whenever a schema or data format changes, application code usually needs to change too. In a large system, that code change can't happen everywhere instantaneously. Server-side applications typically roll the new version out gradually, node by node, so a new version and an old version are both live at once for a while. Client-side applications have it worse: you're at the mercy of a user who might not update for weeks. Either way, old and new versions of the code, and old and new versions of the data, end up coexisting in the same running system.

That's exactly why backward compatibility (newer code reading data written by older code) and forward compatibility (older code reading data written by newer code) both matter. Backward compatibility is usually the easier one: as the author of the new code, you already know what the old format looked like, so you can explicitly handle it. Forward compatibility is harder, because it asks the old code to correctly ignore parts of the data it has never seen before and has no way to interpret.

2. Your language's built-in serializer is a trap for anything long-lived

Many languages ship a built-in way to turn objects into bytes: Java has java.io.Serializable, Ruby has Marshal, Python has pickle, and third-party libraries like Kryo exist too. These are genuinely convenient, saving and restoring an object graph with almost no extra code. But they carry a handful of deep problems that make them a poor choice for anything beyond very short-lived, throwaway use.

First, the encoding is usually tied to one programming language, so reading the data from anything else is difficult or impossible, and choosing it commits you to that language for a long time. Second, decoding often needs to instantiate arbitrary classes to restore the original object types, which is a real security hole: if an attacker can get your application to decode a byte sequence they control, they can potentially get it to construct classes that do damaging things, including remote code execution. Third, versioning tends to be an afterthought in these libraries, since they were built for quick convenience, not for surviving a schema change gracefully. Fourth, efficiency is often an afterthought too. Java's built-in serialization in particular has a reputation for being slow and bloated compared to the alternatives below. None of this means these tools are useless, they're fine for a value that never leaves one process and one version of your code, but for anything you'll store, send across a network, or read back later, it's generally best to avoid them.

3. Text formats: JSON, XML, and CSV are flexible, but vague

JSON and XML are the obvious cross-language, human-readable choices, and CSV is a simpler, less powerful cousin. They're widely known and widely supported, and just as widely criticized: XML for being verbose and complicated, JSON mainly for being simpler than XML and for having built-in support in web browsers. Despite the popularity, all three share some genuinely subtle problems once you look past the readability.

Numbers are the biggest one. XML and CSV can't tell a number apart from a string that happens to be made of digits, short of consulting an external schema. JSON does distinguish strings from numbers, but it doesn't distinguish integers from floating-point numbers, and it never specifies a precision. That matters for genuinely large integers: values bigger than 253 can't be represented exactly by an IEEE 754 double-precision float, so a language that parses JSON numbers into floats (JavaScript, for instance) can silently corrupt them. Twitter's API works around exactly this by sending each tweet's ID twice in its JSON, once as a number and once as a string, purely so JavaScript clients have a version they can read correctly.

Binary data is the second problem: JSON and XML handle Unicode text well but have no native way to represent an arbitrary sequence of bytes without a character encoding. The common workaround is Base64-encoding the binary data as text, with the schema noting that a field should be interpreted that way, which works but inflates the size by about a third. Third, both formats have optional schema languages (XML's more so than JSON's), but they're powerful enough to be genuinely complicated, and plenty of JSON tooling skips schemas entirely, which pushes the burden of correctly interpreting numbers and binary strings back onto hand-written application logic. CSV doesn't even have that option: it has no schema at all, so the meaning of each column is whatever the application decides, adding a column later has to be handled by hand, and its escaping rules for commas and newlines inside values are formally specified but not always implemented correctly by every parser. None of this makes JSON, XML, or CSV bad choices, for exchanging data between organizations especially, getting everyone to agree on any format at all is a bigger win than any of these rough edges. But once a dataset is large enough, or a value like a big numeric ID matters, the vagueness starts to cost you.

4. Binary encoding via a schema: Thrift and Protocol Buffers

Once data is used purely inside your own organization, there's less need for a lowest-common-denominator text format, and more room to pick something compact and fast to parse. That's the appeal of binary encodings. A first, simple step is a "binary JSON" variant like MessagePack, which keeps JSON's data model (objects, strings, numbers, arrays) but encodes it as bytes instead of text. Because it still has no schema, it still has to include every field name in the encoded data. For a small example record with three fields (a user name, a favorite number, and a list of interests), plain JSON with whitespace stripped runs 81 bytes; MessagePack only brings that down to about 66 bytes, since the field names still have to be spelled out somewhere.

Thrift and Protocol Buffers take a fundamentally different approach: both require a schema before you can encode or decode anything. You describe the record's shape in an interface definition language, something like required string userName for Thrift or required string user_name = 1 for Protocol Buffers, and a code generation tool turns that schema into ready-made classes for whatever language you're using. Notice the number after each field in the Protocol Buffers example: that's the field tag. Both formats assign every field a small integer, and instead of writing the field's name into the encoded bytes, they write its tag number. An encoded record is simply the concatenation of its fields, each one carrying a tag number and a type marker (so a parser knows how many bytes to skip), with the field's actual name never appearing anywhere in the bytes at all. That's most of where the size savings come from: the same three-field example record encodes to 59 bytes in Thrift's BinaryProtocol, just 34 bytes in Thrift's more compact CompactProtocol, and 33 bytes in Protocol Buffers.

Field tags are also the whole mechanism behind how these formats handle a changing schema. You can rename a field in the schema freely, since the encoded bytes never referred to its name in the first place, only its tag. What you can never do is change a field's tag once data has been written with it, or reuse a retired tag for something new, because either move makes existing encoded data mean something different than it did. You can add a new field at any time, as long as it gets a brand-new tag: old code reading data written by new code simply doesn't recognize the new tag, and (since every field carries a type marker telling the parser how many bytes to skip) it just skips over it. That's forward compatibility working exactly as intended. The one catch is that a newly added field can't be marked required, only optional or given a default, because old data written before the field existed obviously won't have it, and a required-field check would fail the moment new code tried to read that old data. Removing a field follows the same rule in reverse: you may only remove a field that was optional (a required one can never be removed), and its old tag number can never be reused, since there may still be data sitting somewhere with that tag carrying its original meaning.

Changing a field's datatype is possible in both formats, but it's a genuine risk, not a free move: if you widen a 32-bit integer to 64 bits, new code reading old data can simply zero-fill the extra bits, but old code reading new data is still holding a 32-bit variable, so a large 64-bit value gets truncated. One more difference worth knowing: Protocol Buffers has no dedicated list type, only a repeated marker, which means the same tag can legally appear more than once in a record. That has the pleasant side effect that an optional (single-value) field can safely evolve into a repeated (multi-value) one later: new code reading old data just sees a list of zero or one items, and old code reading new data simply reads the last value in the list. Thrift instead has a dedicated list type, parameterized by the element type, which supports nested lists but doesn't allow that same single-to-many evolution.

5. Avro: no tag numbers, resolved between two schemas at read time

Apache Avro takes a different approach again. It also requires a schema (written either in a human-friendly Avro IDL, or as an equivalent JSON document meant for tooling), but that schema carries no field tags at all, just field names and types in a fixed order. Encoding without any tag numbers or field names in the bytes is what makes Avro's encoding the most compact of the group: that same three-field example record comes to just 32 bytes. The trade-off is that, unlike Thrift or Protocol Buffers, an Avro-encoded byte sequence contains nothing that identifies what each value even is, no type marker, nothing. It's decoded purely by walking through the fields in the exact order the schema lists them and trusting the schema to say what type each one is, which means the code reading the data has to be using a schema that genuinely matches the one used to write it, or the decode will come out wrong.

So how does Avro support schema evolution if reading requires a matching schema? Its answer is to stop assuming there's only one schema in play. Avro distinguishes the writer's schema (whatever version of the schema the encoding side used at the time) from the reader's schema (whatever version the decoding side currently expects), and the two don't have to be identical, only compatible. When a record is decoded, the Avro library looks at both schemas side by side and resolves the differences by matching fields by name: a field that appears in the writer's schema but not the reader's is simply ignored, and a field the reader expects but the writer's schema doesn't have is filled in using a default value declared in the reader's schema. Because matching happens by name rather than by position or tag, the two schemas' fields don't even need to be listed in the same order.

The compatibility rule that falls out of this is simple: you may only add or remove a field that has a default value declared. Add a field with a default, and old data missing that field just gets the default filled in when a new reader reads it. Add a field with no default, and new readers can't correctly read old data, which breaks backward compatibility. Remove a field that has no default, and old readers can't correctly read new data, which breaks forward compatibility. There's a related wrinkle around nulls: in Avro, unlike in some languages, null isn't automatically an acceptable value for every field. To allow a field to be null you declare it as a union type (for example, a value that can be either null or a number), and you can only use null as a default if it's one of the branches listed in that union. It's more explicit than "everything is nullable by default," which is exactly the point: it forces you to say up front which fields are allowed to be absent. Renaming a field is also possible in Avro, through aliases the reader's schema can declare, though this direction is asymmetric: it's backward compatible (new code with the alias can still find old data under the old name) but not forward compatible (old code, without the alias, won't recognize the new name).

One question remains: if there are no tags and the reader genuinely needs the exact writer's schema to decode correctly, how does it get hold of it, given that shipping the entire schema alongside every single record would likely dwarf the encoded data itself? The answer depends on context. For a large file holding millions of records all written with the same schema (a common case with Hadoop-style storage), the writer's schema is simply included once, at the start of the file, in what Avro calls an object container file. For a database, where different records may have been written at very different times with different schema versions, a common approach is to store a small version number with every record and keep a separate table of schema versions the reader can look up by that number. For two processes talking over a live network connection, they can instead negotiate and agree on a schema once, at connection setup, and reuse it for the life of the connection.

6. Why schema-driven binary formats earn their keep

Stepping back, Thrift, Protocol Buffers, and Avro all lean on a schema to define a binary encoding, and their schema languages are deliberately much simpler than something like full XML Schema or JSON Schema (which support fine-grained validation rules like regular expressions or numeric ranges). That simplicity is part of why all three have grown wide language support. The benefits are concrete: they're more compact than binary variants of JSON like MessagePack, precisely because they can leave field names out of the encoded bytes entirely; the schema itself doubles as documentation that can't silently drift out of date, since decoding literally depends on it being accurate; keeping a registry of schema versions lets you check whether a proposed change is actually compatible before you ever deploy it; and for statically typed languages, generating code straight from the schema gets you compile-time type checking and IDE autocomplete for free.

Avro has one extra edge worth calling out: because it has no tag numbers to hand-assign, it's especially friendly to a schema that's generated automatically rather than written by a person, for example, dumping a relational database table to a file by generating an Avro schema straight from the table's columns. If that database table later gains or loses a column, you just regenerate the Avro schema and export again; nothing needs a human to reassign numeric tags. With Thrift or Protocol Buffers, that same table-to-schema mapping would typically need a person (or a very careful piece of tooling) to keep field tags assigned consistently by hand every time the table changes, which simply wasn't a design goal for those two formats the way it was for Avro.

Why it matters

This connects straight back to the idea of evolvability: your ability to ship small, frequent changes instead of rare, risky rewrites depends on old and new versions of your code being able to run side by side safely for a while, and that in turn depends entirely on the encoding format underneath actually supporting it. Pick a format that's vague about compatibility (your language's built-in serializer, or JSON with no schema and no discipline around it), and every schema change becomes a coordination headache or a landmine. Pick one with clear, enforced rules for adding, removing, and retiring fields, and a rolling upgrade becomes routine. The next natural question, once you know how a single record gets encoded, is who's actually doing that encoding and decoding on each end of a real system: a database, a REST or RPC service, or an asynchronous message queue. Each of those has its own extra compatibility quirks on top of everything covered here, and that's exactly where a follow-up digest on this chapter picks up.

Remember this

  • Backward compatible means new code can read old data; forward compatible means old code can read new data. Once more than one version of your app can be running at the same time, which is nearly always, you generally need both.
  • A language's built-in serializer (Java's, Python's pickle, and similar) is convenient but risky for anything long-lived: it's language-locked, it can be a security hole on untrusted input, and it usually treats versioning and efficiency as an afterthought.
  • JSON, XML, and CSV are flexible and readable, but vague about types unless you bolt a schema on top, which is exactly why huge numbers (like Twitter's tweet IDs) and binary data cause real, if subtle, bugs.
  • Thrift and Protocol Buffers identify fields by a numeric tag instead of a name in the actual bytes: rename a field freely, but never change or reuse its tag once data has shipped with it, and new fields must be optional or defaulted, never required.
  • Avro drops tag numbers entirely and instead matches fields by name between the writer's schema and the reader's schema at decode time, which is what makes it unusually friendly to schemas generated automatically, like straight from a database table.

Try it yourself

  1. Encode the same record two ways and weigh the difference. Pick a tiny record (a name, a number, a short list) and encode it once as JSON and once with a binary library available in your language (MessagePack, Protocol Buffers, or Avro all work). Done when: you can state both byte counts from your own run, not from this digest, and explain in your own words where the size difference comes from.
  2. Simulate forward compatibility on purpose. Define a small schema (Protocol Buffers or Avro), encode a record with it, then add a new field to the schema (with a default, or a new tag) and try decoding the old bytes with the new schema. Done when: the old record decodes cleanly and the new field comes back as its default or is simply absent, not an error.
  3. Then break it on purpose. Repeat the exercise above, but this time add the new field as required (Thrift/Protobuf) or with no default (Avro), and try reading the old data again. Done when: you've seen it fail, and can explain exactly why in terms of backward vs. forward compatibility.
  4. Reproduce the big-integer bug. Build a JSON document with an integer larger than 253 (for example, a 19-digit ID), parse it with a language or library that uses floating-point numbers for JSON, and print the value back out. Done when: you've watched the number actually change, and can point to which digits got lost.
  5. Measure the Base64 tax. Take a small binary file (a tiny image works), Base64-encode it, and compare the encoded size to the raw file size. Done when: you've confirmed the roughly one-third size increase for yourself, on your own file.
  6. Rename a field without breaking anything. In a Thrift or Protobuf schema, rename a field but keep its tag number the same, then decode an old, already-encoded record with the renamed schema. Done when: the old data still decodes correctly, proving to yourself that the name genuinely never mattered to the bytes.

Go deeper

Once you're comfortable with how a single record gets encoded and evolved, the natural next thread to pull is who's actually doing that encoding and decoding in a real system, a database writing and reading its own rows, a REST or RPC service handling a request and a response, or a message broker passing bytes between producers and consumers, each of which adds its own extra compatibility wrinkles on top of everything in this digest.
