Serializability: Serial Execution, Two-Phase Locking, and SSI

Part 2 ended on a depressing note: weak isolation levels leave bugs like write skew and phantoms, and the usual advice from researchers has been the same since the 1970s, which is "use serializable isolation". This final part is about how a database actually delivers that: running transactions literally one at a time, locking everything it touches, or letting transactions run optimistically and checking at commit time. It ends with the chapter's own summary, which makes a nice checklist of every anomaly we've met.

In one line

Serializable isolation makes concurrent transactions behave as if they ran one at a time, and databases get there by three routes with different costs: actual serial execution (fast but narrow), two-phase locking (safe but slow under contention), and serializable snapshot isolation (optimistic, with a small penalty over snapshot isolation).

The big idea

Weak isolation levels are hard to understand, are implemented inconsistently across databases, and are hard to test, because concurrency bugs only appear on unlucky timing. Serializability is the cure: if each transaction is correct when run alone, it stays correct when run concurrently, because the database prevents all the race conditions. It isn't more widely used because each implementation pays a price. You can remove concurrency entirely (single thread), you can block conservatively (locks), or you can proceed optimistically and abort on conflict. Which one fits depends on your workload: how fast and short your transactions are, how much contention there is, and how much data fits in memory.

Key terms

  • Serializable isolation: the result is the same as if transactions had executed one at a time, even though they may run in parallel.
  • Actual serial execution: literally running one transaction at a time on a single thread.
  • Interactive transaction: one where the application sends statements one at a time and waits for results between them.
  • Stored procedure: the whole transaction's code submitted to the database ahead of time, so it runs without network round trips.
  • Two-phase locking (2PL): locks are acquired as the transaction runs and all released at the end (commit or abort). Not the same as two-phase commit (2PC), which is about distributed transactions in Chapter 9.
  • Shared / exclusive lock: shared mode for reading (many holders allowed); exclusive mode for writing (one holder, nobody else).
  • Deadlock: transactions each waiting on a lock the other holds.
  • Predicate lock: a lock on all objects (even not-yet-existing ones) matching a search condition.
  • Index-range lock (next-key lock): a cheaper, coarser approximation of a predicate lock attached to an index.
  • Pessimistic / optimistic concurrency control: wait when something might go wrong, versus proceed and check at commit.
  • SSI (serializable snapshot isolation): snapshot isolation plus an algorithm for detecting serialization conflicts and aborting transactions.
  • Premise: a fact a transaction read and based its writes on (such as "two doctors are on call").
  • Phantom: a write that changes the result of another transaction's earlier search.

How it works

Grounding first. The goal of serializable isolation is a promise you can state in one sentence: whatever the database lets happen, there is some order of running the transactions one at a time that would have produced the same result. If you can assume that, you can reason about each transaction on its own. The source describes it as the strongest isolation level, one that prevents all the race conditions of the previous part. So the question is only: at what cost, and which route?

Route 1: actual serial execution

Remove concurrency entirely: one transaction at a time, on a single thread. By definition that's serializable. It looked silly for decades, since multi-threading was thought essential for performance, but around 2007 designers decided it was feasible, for two reasons per the source: RAM became cheap enough to keep the whole active dataset in memory (no waiting on disk), and designers realized OLTP transactions are usually short, with few reads and writes, while long analytic queries are read-only and can run on a snapshot outside the serial loop. The source names VoltDB/H-Store, Redis and Datomic as implementing it. The ceiling is one CPU core's throughput, but it avoids all locking overhead.

Stored procedures. Early designs imagined a whole user flow (search flights, pick seats, enter passenger details, pay) as one transaction. Humans are slow, so transactions that wait for user input would pile up idle. Almost all OLTP apps keep transactions short, committing within one HTTP request. But even then, the usual interactive style (query, read result, query again) spends most time in network round trips. A single-threaded database can't afford to wait on the network, so such systems require the whole transaction to be submitted ahead of time as a stored procedure that runs with no waiting for network or disk when data is in memory.

Stored procedures have a bad reputation (the source gives reasons): each vendor has its own archaic language (PL/SQL, T-SQL, PL/pgSQL); code in the database is harder to debug, version, deploy, test and monitor; and a database is often shared by many application servers, so one badly written procedure hurts more. These can be overcome: VoltDB uses Java or Groovy, Datomic uses Java or Clojure, and Redis uses Lua. VoltDB even replicates by running the same stored procedure on each replica, which requires the procedures to be deterministic (it provides special deterministic APIs for things like the current time).

Partitioning. To go beyond one core, partition the data so each transaction touches only one partition; each partition gets its own thread, and throughput scales with cores. Cross-partition transactions need lock-step coordination and are vastly slower; the source cites VoltDB reporting about 1,000 cross-partition writes per second, far below single-partition throughput and not improved by adding machines. Whether this works depends on data shape: key-value data partitions easily; data with many secondary indexes needs much cross-partition coordination.

The source's summary of when serial execution works: each transaction must be small and fast (one slow one stalls everyone); the active dataset must fit in memory (rarely used data could be moved to disk, but accessing it would slow things badly); write throughput must fit a single core, or be partitionable without cross-partition coordination; and cross-partition transactions are possible but have a hard limit.

Route 2: two-phase locking (2PL)

For about 30 years this was the one widely used serializability algorithm. (The source flags: 2PL is not 2PC.) It strengthens the lock idea behind dirty-write prevention. Many transactions may read an object at the same time, but as soon as anyone wants to write, access must be exclusive:

  • If A has read an object, B wanting to write it must wait for A to commit or abort.
  • If A has written an object, B wanting to read it must wait for A to finish. (Reading an old version isn't acceptable under 2PL.)

So under 2PL, writers block writers and readers, and readers block writers, unlike snapshot isolation's mantra. In return it provides serializability and protects against everything discussed earlier, including lost updates and write skew. The source says it is used for the serializable level in MySQL (InnoDB) and SQL Server, and for the repeatable read level in DB2.

Mechanics. Each object has a lock in shared or exclusive mode. To read: acquire shared (many holders allowed unless someone holds exclusive). To write: acquire exclusive (no other holder of any kind). Read-then-write: upgrade shared to exclusive. And once acquired, hold the lock until the transaction ends. That is the "two phases": acquiring while executing, releasing all at the end. With so many locks, deadlocks are easy: A waits for B and B waits for A. The database detects them and aborts one so the others proceed; the application must retry.

Performance. The big downside, and the reason it wasn't used by everyone from the 1970s. Throughput and response times are significantly worse than under weak isolation, partly from the overhead of locks but mostly from reduced concurrency: if two transactions might race, one waits. Traditional databases don't bound transaction duration (they were built for interactive use), so waits can be unbounded, and queues form around popular objects. Latency can be unstable and slow at high percentiles under contention; one slow or lock-heavy transaction can grind everything down. Deadlocks are much more frequent than under lock-based read committed, and each abort means redoing work.

Predicate locks and index-range locks

A subtle point: to prevent phantoms the database must lock things that don't exist yet. In the booking example, if one transaction searched for bookings of room 123 from noon to 1 p.m., no other transaction may insert a conflicting booking meanwhile (bookings for other rooms or other times are fine). A predicate lock does this: like a shared/exclusive lock but attached to all objects matching a search condition. To read objects matching a condition you take a shared predicate lock on the condition (waiting if anyone holds an exclusive lock on a matching object). To insert, update or delete, you check whether the old or new value matches any existing predicate lock and wait if so. Because it covers objects not yet in the database, 2PL with predicate locks prevents write skew and other races and is serializable.

But checking many predicate locks is slow, so most 2PL databases implement index-range locking (next-key locking), a safe approximation: lock a larger set than the predicate. For room 123 from noon to 1 p.m. you could lock all of room 123's bookings via an index on room_id, or a time range via a time index, or all rooms for that time. Any write that matches the original predicate also matches the bigger lock, so it's safe, though less precise (it may block more than necessary). If no suitable index exists, the fallback is a shared lock on the whole table, safe but bad for performance.

Route 3: serializable snapshot isolation (SSI)

The chapter has painted "a bleak picture": the serializable options either don't perform (2PL) or don't scale (serial execution), while the fast levels allow races. Are they fundamentally at odds? Perhaps not. SSI, first described in 2008, provides full serializability with only a small penalty over snapshot isolation. The source says PostgreSQL has used it for its serializable level since version 9.1, and FoundationDB uses a similar algorithm. Being young, it is still proving itself, but may be fast enough to become a default.

Pessimistic versus optimistic. 2PL is pessimistic: if anything might go wrong, wait. Serial execution is pessimism taken to the extreme (one lock on the whole database, compensated by making transactions fast). SSI is optimistic: transactions go ahead anyway, and at commit the database checks whether isolation was violated; if so the transaction aborts and is retried. Optimistic control does badly under high contention (many aborts, and retries add load when near capacity), and well when there's spare capacity and moderate contention. Commutative atomic operations (like counter increments) can reduce contention. SSI sits on top of snapshot isolation: reads come from a consistent snapshot, and an added algorithm detects serialization conflicts among writes.

Decisions based on an outdated premise. The pattern from write skew: read some data, decide, write. Under snapshot isolation, the thing you read may be out of date by commit time. The database can't see how your code uses a query result, so it must assume any change to the result may invalidate the transaction's writes. Two cases to detect:

  1. Reading a stale MVCC version (an uncommitted write was ignored at read time but has committed since). The database tracks when a transaction ignores another's writes due to visibility rules; at commit, if any of those ignored writes have become committed, abort. Why wait until commit? A read-only transaction wouldn't need to abort, the other transaction may still abort, and at read time the database doesn't know whether you'll write. Waiting avoids unnecessary aborts and keeps long read-only snapshots workable.
  2. Writes that affect earlier reads (another transaction modifies data after you read it). Using an index (or the table, if there's no index), the database records which transactions have recently read a key range, e.g. shift_id = 1234. When a transaction writes, it looks up recent readers of the affected data and notifies them that their read may be outdated. This is like an index-range lock, except it doesn't block; it's a tripwire. In the source's example, two transactions both read and write the on-call doctors; each notifies the other. The first to commit succeeds (the other's write hasn't taken effect yet); when the second tries to commit, the conflicting write has been committed, so it must abort. The database can forget a transaction's read information once it and all concurrent transactions have finished.

Performance of SSI. Tracking granularity is a trade-off: detailed tracking means precise aborts but more bookkeeping; coarse tracking is faster but aborts more than needed. PostgreSQL uses theory showing some overwritten reads are still serializable to reduce unnecessary aborts. Compared with 2PL, transactions don't wait for each other's locks, so latency is much more predictable, and read-only queries run on a snapshot without locks. Compared with serial execution, it isn't limited to one core: FoundationDB distributes conflict detection over several machines, scaling to very high throughput while allowing transactions across partitions. The abort rate matters: a read-write transaction that runs long is likely to conflict, so SSI wants fairly short read-write transactions (long read-only ones may be fine), though the source thinks it's probably less sensitive to slow transactions than 2PL or serial execution.

The chapter in review (its Summary)

  • Transactions let an application pretend certain concurrency problems and faults don't exist: a large class of errors becomes a simple abort and retry. Simple single-record access might manage without them; complex access patterns benefit hugely, and denormalized data in particular goes out of sync without them.
  • Dirty reads: prevented by read committed and stronger. Dirty writes: prevented by almost all implementations. Read skew: prevented by snapshot isolation (usually MVCC). Lost updates: some snapshot-isolation implementations prevent them automatically, others need manual locks like SELECT FOR UPDATE. Write skew: only serializable isolation prevents it. Phantom reads: snapshot isolation prevents straightforward ones, but phantoms in write-skew situations need things like index-range locks.
  • Weak levels protect against some anomalies and leave the rest to you; only serializable protects against all. Three implementations: serial execution (simple and effective if transactions are fast and throughput fits one core); two-phase locking (the standard for decades, but with performance problems); SSI (newer, optimistic, mostly avoids the downsides).
  • This chapter looked at a single machine; distributed transactions raise new difficulties, taken up in the next two chapters.

Why it matters

When you pick an isolation level, set up a database, or debug an intermittent data-corruption bug, you are choosing between these trade-offs. It also explains common production symptoms: sudden latency cliffs under lock contention, deadlock-retry loops, "could not serialize access" errors that must be retried. And it gives you a mental model for why "just make it serializable" is not free.

Remember this

  • Serializable means the outcome matches some one-at-a-time order of the transactions; only it prevents write skew and phantoms across the board.
  • Serial execution works when transactions are short, data fits in memory, and writes fit one core (or partition cleanly); it needs stored procedures.
  • 2PL uses shared/exclusive locks held to the end of the transaction, with predicate or index-range locks for phantoms; readers and writers block each other, deadlocks happen, latency suffers under contention.
  • SSI runs on snapshot isolation, detects outdated premises via stale-read and write-after-read tripwires, and aborts at commit; no blocking, but high contention means more aborts.
  • All three routes make the application retry aborts; design for that.

Try it yourself

  1. Serial executor. Build a single-threaded loop that takes stored-procedure-style functions from a queue and runs each to completion against an in-memory dictionary. Done when 100,000 queued increments from many producers give the exact right total and you can explain why no locks were needed.
  2. Lock table. Implement shared/exclusive locks with upgrade, and detect a deadlock by finding a cycle in a wait-for graph. Done when two transactions locking A then B and B then A are detected and one is aborted.
  3. Phantom guard. For a booking table keyed by (room, start), add a range lock on a room before the availability check. Done when two concurrent bookings of overlapping times for the same room cannot both commit but different rooms still proceed in parallel.
  4. Tiny SSI. On top of a snapshot-based store, record which transactions read which key range, add a tripwire on writes, and check at commit. Done when the on-call scenario aborts exactly one of two concurrent transactions, and a read-only transaction never aborts. (My own quick sketch of the idea does this for two transactions; a real one needs much more care.)
  5. Contention test. Run your lock-based and optimistic versions with 1% and 90% of transactions touching one hot key; plot throughput and abort counts. Done when you can state, with your own numbers, where each one hurts.
