Finetuning: When to Do It, and Why Memory Is the Wall

Chapters 5 and 6 adapted a model by changing what you feed it: instructions, context, tools. Chapter 7 is about changing the model itself. This first part covers what finetuning is, the honest case for and against doing it, how to choose between finetuning and RAG, and then the technical heart of the problem: why finetuning eats so much memory, and how number formats and quantization shrink it. The next part covers the techniques built on top of that (PEFT, LoRA, model merging and practical tactics).

In one line

Finetuning means continuing a model's training so its weights change to fit your task; it's powerful but expensive, so you decide whether it's worth it by asking whether your problem is missing facts (try RAG) or wrong behavior (finetuning may help), and you understand its cost by understanding where memory goes.

The big idea

Prompting and RAG leave the model's weights alone. Finetuning edits them. That buys you things prompting struggles with (a strict output format, a niche dialect, a house style, a small model that punches above its weight), but it also costs you: training data, ML know-how, a way to host the result, and ongoing upkeep as better base models keep arriving. The chapter's practical rule of thumb is that finetuning is mostly for form and RAG is mostly for facts. The second half of this part explains why finetuning is so hungry for memory (weights, activations, gradients, optimizer states) and how using fewer bits per number is the cheapest lever to pull.

Key terms

  • Finetuning: further training a model, after pre-training, so its weights adapt to a specific task or behavior. Any training after pre-training counts.
  • Base model: the starting model you finetune. It has some, but not all, of the capabilities you need.
  • Transfer learning: reusing what a model learned on one task (with lots of data) to learn a related task faster. Finetuning is one way to do it.
  • Sample efficiency: how few examples a model needs to learn a behavior. Transfer learning improves it.
  • Feature-based transfer: a different kind of transfer learning where one model extracts features (often embedding vectors) that another model uses, without changing the first model.
  • Continued pre-training: self-supervised finetuning on cheap, raw, task-related text (for example raw legal documents) before using expensive labeled data.
  • Supervised finetuning (SFT): training on (input, output) pairs, such as (instruction, response).
  • Preference finetuning: training with reinforcement learning on comparisons, in the shape (instruction, winning response, losing response).
  • Infilling finetuning: training a model to fill in a blank using tokens on both sides, handy for text editing and code debugging.
  • Long-context finetuning: extending how much text a model can take in, which usually means changing its positional embeddings.
  • Distillation: finetuning a small model to imitate a larger model using data the larger one generated.
  • Information-based failure: the model is wrong or out of date because it lacks facts.
  • Behavioral failure: the model's facts may be fine but its output is irrelevant, badly formatted, or unsafe.
  • Parameter / weight: one learned number inside the model. A "13B" model has about 13 billion of them.
  • Trainable vs. frozen parameter: a trainable parameter can be updated during finetuning; a frozen one is held unchanged.
  • Forward pass / backward pass: the forward pass computes an output from an input; the backward pass uses the error to update weights.
  • Loss: a number measuring how far the model's output is from the expected one.
  • Gradient: for each trainable parameter, how much it contributed to the loss (the derivative of the loss with respect to that parameter).
  • Optimizer: the rule for how much to adjust each parameter given its gradient. SGD and Adam are the examples named.
  • Activations: the intermediate values computed during the forward pass.
  • Gradient checkpointing (activation recomputation): not storing activations and recomputing them when needed, trading time for memory.
  • FP32, FP16, BF16, TF32, INT8, INT4: number formats. The digits are mostly the bit count (but see the TF32 oddity below).
  • Quantization: storing numbers with fewer bits. Strictly it means converting to an integer format, but the chapter (and this digest) uses it for any precision reduction.
  • PTQ / QAT: post-training quantization (shrink a finished model) and quantization-aware training (train while simulating low precision).
  • Mixed precision: using high precision for the sensitive values and low precision for the rest.

How it works

Grounding: what finetuning actually is (and where it sits)

Let's start from the picture you already have. A foundation model is built in stages: pre-training on a huge pile of unlabeled text, then post-training (supervised and preference tuning) to make it follow instructions and behave. Each of those stages changes the weights. Finetuning is just more of that: you take a model that already has most of what you need and nudge its weights toward your task. Model developers do it before release; you, as an application developer, will most likely finetune a model that has already been post-trained. The more refined the starting model and the closer its knowledge to your task, the less work you have to do.

Why does this work at all? Because of transfer learning. Skills learned on a task with abundant data (predicting the next word across the internet) carry over to tasks with scarce data (answering legal questions, writing text-to-SQL). The chapter's analogy is human: knowing piano makes the next instrument easier. The practical payoff is sample efficiency. Training a legal question answering model from scratch could need millions of examples, whereas finetuning a good base model might need a few hundred. The chapter also relays a framing from the InstructGPT paper: finetuning can be seen as unlocking capabilities the model already has but that are hard to reach by prompting alone.

Simplification: "a few hundred examples" is the chapter's illustration of the order of magnitude, not a promise. How many examples you actually need depends on the task, the base model, and the quality of the data.

The flavors of finetuning

The chapter lists several kinds, all of which count as "training after pre-training":

  • Continued pre-training (self-supervised finetuning). Before you spend money on labeled examples, you can keep training on cheap raw text from your domain. To build a legal assistant you might first continue on raw legal documents. To summarize books in Vietnamese you might first continue on a large pile of Vietnamese text. No labels are needed.
  • Supervised finetuning. You supply (input, output) pairs, such as an instruction and the response you want. The response can be open-ended (summarizing a book) or closed (a classification label). The chapter warns that high-quality instruction data is hard and expensive, especially when it needs factual accuracy or domain expertise. Chapter 8 (next in the book) covers how to get it.
  • Preference finetuning. Reinforcement learning on comparative data: an instruction, a response people preferred, and one they didn't.
  • Infilling finetuning. Language models can be autoregressive (predict the next token from what came before) or masked (fill a blank using both sides). You can finetune a model to do infilling even if it was pre-trained autoregressively, which suits editing and code debugging.
  • Long-context finetuning. Extending the context length. The chapter's example is Code Llama, which grew its context from 4,096 to 16,384 tokens this way. It usually means altering the architecture (positional embeddings) and is harder than the others; the result can get worse on short inputs.

One more distinction worth having: feature-based transfer is a different way to transfer knowledge. Instead of changing the first model, you use it as a feature extractor (producing embedding vectors) and train a separate model on those features. It was very common in computer vision, where people reused image models to extract features for other vision tasks.

When to finetune: the honest case for

Finetuning is generally attempted after extensive prompt experiments, because it needs more of everything: data, hardware, and ML talent. They aren't mutually exclusive either; real systems often use both. The reasons the chapter gives for finetuning:

  • Quality, general or task-specific. Most commonly, better instruction following, especially producing a particular structure such as JSON or YAML.
  • Covering what the base model didn't see. A model might be good at standard SQL but weak on a less common dialect, or good on common queries but fail on a customer's specific ones. Training on that dialect or those queries helps.
  • Bias mitigation. Exposing the model to carefully curated data can counteract biases in its training data. The chapter cites research where finetuning on text written by particular groups reduced measured gender and racial biases in BERT-like models. Treat that as a research result about specific models and measurements, not a general fix.
  • Making small models good. Finetuning small models is much more common than finetuning big ones: they need less memory, cost less, and run faster. A small model finetuned on a narrow task can beat a far larger off-the-shelf model on that task. The chapter's example: Grammarly reported finetuned Flan-T5 models outperforming a GPT-3 variant specialized for text editing across writing-assistant tasks despite being 60 times smaller, using 82,000 (instruction, output) pairs. That's the chapter's account of one company's result.
  • Distillation. A popular recipe: have a large model generate data, then finetune a small model to imitate it. (Data synthesis is in Chapter 8.)
  • Lots of examples. Prompts can only hold so many examples (context limit). Finetuning has no such cap on how many examples you train on. It once also saved tokens by letting you drop the examples from every prompt; the chapter notes prompt caching has largely removed that advantage.

It also helps that high-quality open models of many sizes and domains now exist, so there are more competitive models to start from.

When not to finetune: the honest case against

The chapter is blunt that many gains from finetuning can also be had, to some degree, without it: careful prompts and context improve performance, and other techniques also produce structured output. Then come the real costs:

  • It can hurt other tasks. Say a model handles product recommendations and general feedback but is weak at changing orders. You finetune on order-change data and it gets better at that but possibly worse at the other two. Fixes the chapter offers: finetune on all the query types you care about, or use separate models per task, or merge separate finetuned models into one (merging is covered in Part 2).
  • It needs data. Annotated data is slow and costly, particularly for tasks needing expert judgement. Open-source and AI-generated data can help, but how well varies a lot.
  • It needs ML knowledge. Choosing a base model, learning rates, how much data, overfitting versus underfitting, monitoring training, debugging. Frameworks and APIs automate a lot, but you still need to understand the knobs.
  • You need to serve it. Self-host or use an API provider? Inference optimization for large models is not trivial (Chapter 9 covers it).
  • You inherit a maintenance policy. New base models keep arriving, sometimes improving faster than you can improve yours. How much better must a new base model be before you switch? Would you re-finetune a new one that isn't better yet but might be after finetuning? The chapter says you need a policy and budget for this up front.
  • Lazy prompting is the usual culprit. The chapter shares a common story: someone insists prompting doesn't work, and on inspection their prompt experiments were minimal and unsystematic (unclear instructions, unrepresentative examples, poorly defined metrics). After fixing the experiments, prompting was enough. Test a range of prompts properly first.

The "domain-specific model" trap

A common argument is that general models can't handle specialized domains, so you must train or finetune your own. The chapter's counterexample is BloombergGPT: a 50-billion-parameter finance model announced in March 2023 that, per the chapter, needed about 1.3 million A100 GPU hours, with an estimated compute cost of $1.3 to $2.6 million before counting data. In the same month GPT-4-0314 appeared, and a study by Li et al. found it clearly beat BloombergGPT on financial benchmarks. For instance, zero-shot, 87.15 vs. 75.07 on FiQA sentiment analysis (weighted F1) and 76.48 vs. 43.41 on ConvFinQA (accuracy), as the chapter's table reports. The lesson: as general models improve, they also get better at domains. The chapter adds fair caveats: benchmarks don't capture real-world performance, so BloombergGPT may work well for Bloomberg's own uses, and the team surely gained valuable experience. Also, prompt experiments aren't wasted if you do finetune later, because they build the evaluation pipeline, annotation guidelines and experiment tracking you'll need anyway.

Finetuning vs. RAG: form vs. facts

Suppose prompting has taken you as far as it can. Next: RAG or finetuning? The chapter's test is to look at how the model fails.

  • Information-based failures (wrong or outdated facts; the model never saw your private data) point to RAG. Example in the chapter: a model that says an artist has released 10 albums when the true number is 11, because its training cutoff predates the latest release.
  • Behavioral failures (correct but irrelevant output, wrong format, unsafe responses) point to finetuning. Examples: technically accurate specs that lack the detail your engineers need; HTML that doesn't compile because the model saw too little of it; weak performance on a little-used domain-specific language.

Hence the slogan: finetuning is for form, RAG is for facts. RAG supplies external knowledge and can reduce hallucination. Finetuning teaches syntax and style. The chapter adds a nuance: finetuning can reduce hallucinations with enough high-quality data, and can worsen them with low-quality data.

Evidence it cites (Ovadia et al., 2024): on a current-events question set, RAG with the base model beat finetuned models, and even beat RAG layered on finetuned models, for the three 7B models tested. For instance, Mistral-7B scored 0.481 as a base model, 0.875 with RAG, and 0.504 or 0.588 for the two finetuning approaches. On MMLU categories, RAG also beat finetuning for almost all of them; adding RAG on top of a finetuned model improved results 43% of the time, and 57% of the time did not beat RAG alone. Caveat: these are results for particular small models and particular datasets, not a law of nature.

If your model has both kinds of problem, start with RAG: it's usually easier, with no training data to curate and no finetuned model to host. And start with simple term-based retrieval such as BM25 before reaching for vector databases.

Why finetuning is memory-hungry: the backward pass

Now the technical core. Memory is the number one practical obstacle, and almost every technique in Part 2 exists to shrink it. The chapter says to expect an out-of-memory error early in your career with these models.

Start with what training does. For neural networks trained by backpropagation (the common method today, as the chapter puts it; others exist), each training step has two phases:

  1. Forward pass: run the input through the model to get an output.
  2. Backward pass: compare the output with the expected one. The gap is the loss. Then compute each trainable parameter's gradient (how much it contributed to the error), and let the optimizer use that to adjust the parameter. For transformer models, Adam is described as by far the most widely used optimizer.

During pre-training all parameters are updated, during inference none are, and during finetuning some or all are. The ones you leave alone are frozen. The key insight: each trainable parameter drags along extra baggage in memory (its gradient and optimizer state). So the more trainable parameters, the more memory.

Memory math you can do on a napkin

The chapter gives approximate formulas, with the warning that real usage depends on the workload and on optimizations, so treat them as estimates for choosing hardware. Let N be the parameter count and M the bytes per parameter.

Inference. Weights take N x M. The forward pass also needs memory for activations and (for transformers) the attention key-value vectors, which grow with sequence length and batch size. A common rough assumption in the chapter is that this extra is about 20% of the weights, so inference memory is about N x M x 1.2. Example: a 13B model at 2 bytes per parameter has 26 GB of weights and needs roughly 31.2 GB for inference. A 70B model at 2 bytes needs 140 GB for weights alone. Caveat: the 20% is a rough figure; longer contexts or bigger batches need more.

Training. weights + activations + gradients + optimizer states. Per trainable parameter you store one gradient value plus 0 to 2 optimizer values depending on the optimizer: plain SGD has no state, a momentum optimizer stores one value, Adam stores two. So updating every parameter of a 13B model with Adam at 2 bytes per value costs 13 billion x 3 x 2 bytes = 78 GB just for gradients and optimizer states, on top of the weights. If only 1B parameters are trainable, that falls to 6 GB. This is the entire motivation for parameter-efficient finetuning, which is Part 2.

One honest wrinkle the chapter raises: the formulas assume activations are smaller than the weights, but when activations are stored for gradient computation they can be far larger than the weights. Gradient checkpointing avoids storing them by recomputing when needed, which saves memory but costs extra training time.

Numerical representations: what a "bit" buys you

All those formulas assumed 2 bytes per value. That's a choice, and changing it is the easiest way to change memory. Neural network numbers are traditionally floating point (FP), per the IEEE 754 standard: FP64 (64 bits, double precision), FP32 (32 bits, single), FP16 (16 bits, half). Others popular in AI: BF16 (BFloat16, designed by Google for TPUs) and TF32 (TensorFloat-32, designed by NVIDIA for GPUs). Integer formats like INT8 and INT4 are increasingly popular too. FP64 is rarely used in neural networks because of its memory footprint, even though it is the default in NumPy and pandas.

A float spends one bit on sign and splits the rest between range (how big or small a number can be) and precision (how finely it can be told apart from its neighbors). BF16 and FP16 are both 16 bits, but BF16 spends more bits on range and fewer on precision. The chapter's conversion table makes this concrete: 123456.789 becomes infinity in FP16 (out of range) but survives, roughly, in BF16; meanwhile 1234.56789 becomes 1235.0 in FP16 (a 0.035% change) and 1232.0 in BF16 (0.208%), so BF16 is less precise there.

An oddity the author flags with humor: TF32 actually uses 19 bits, not 32; the name is just a hint of FP32 compatibility.

A cautionary tale: Llama 2's weights were released in BF16, and many teams loaded it in FP16 and were disappointed by the quality. Load a model in the format it was meant for. The best format for you depends on the range of values in your workload, how sensitive it is to small changes, and your hardware.

Quantization: fewer bits, smaller model

The memory arithmetic is direct: a 10B-parameter model needs 40 GB for weights at 32 bits and 20 GB at 16 bits. Reducing precision this way, called quantization, is cheap, straightforward, and generalizes across tasks and architectures. A reminder on vocabulary: strictly, quantization means converting to an integer format, but the chapter uses it for any precision reduction.

What to quantize. Ideally whatever uses the most memory without hurting quality too much. Weights are quantized more often than activations because weight quantization tends to have a more stable effect on accuracy.

When to quantize. Post-training quantization (PTQ) shrinks a finished model and is by far the most common, which makes it the one most relevant to application developers. The chapter notes that serving in 16 bits or lower is now routine, with work reaching 8 bits and 4 bits (LLM.int8(), QLoRA), mixed 2 and 4 bit schemes averaging 3.5 bits per weight for on-device models, and even 1-bit research (BitNet b1.58, reported as comparable to 16-bit Llama 2 up to 3.9B parameters on the benchmarks shown). Below 8 bits, values are more commonly stored as integers.

Bonus: speed. Fewer bits can mean bigger batches and faster arithmetic, lowering latency. But the chapter says reduced precision doesn't always reduce latency, because format conversion adds work.

Downsides. Each conversion nudges values slightly, and many small nudges can add up to a big quality change; out-of-range values can become infinity or garbage. Doing this with minimal damage is an active research area. Frameworks (PyTorch, TensorFlow, Hugging Face transformers) offer PTQ in a few lines, and on-device frameworks offer it too, since some edge devices only support quantized inference.

Training is touchier. Quantizing during training has two goals: make a model that stays good in low precision at inference, and cut training time and cost. Quantization-aware training (QAT) serves the first goal (the model simulates low precision while learning) but doesn't speed training up and can slow it. Training directly in lower precision can serve both goals (the chapter mentions a company training entirely in INT8), but backpropagation is more sensitive to precision. So training usually uses mixed precision: for example, keep a high-precision copy of weights while gradients and activations use lower precision, often chosen automatically by AMP (automatic mixed precision) in ML frameworks. It's also common to train in high precision and finetune in lower precision, since the organization that pre-trains a foundation model usually has more compute than the people finetuning it.

Why it matters

This part gives you a decision procedure and a cost model. The decision procedure stops you from reaching for finetuning when a better prompt or a retriever would do, and tells you which one to try based on the failure you observe. The cost model lets you estimate, before renting any GPU, whether a model even fits: weights times bytes, plus roughly a fifth for inference, plus gradients and optimizer states for each trainable parameter when training. Everything in Part 2 (PEFT, LoRA, QLoRA, merging) is a response to the numbers you just computed.

Remember this

  • Finetuning changes the weights; prompting and RAG change the input. It's usually tried after systematic prompting, not before.
  • Rule of thumb: failing on facts, reach for RAG; failing on form or behavior, consider finetuning. Both can be combined.
  • Finetuning can make a model worse at other tasks, and it comes with data, talent, serving and maintenance costs.
  • Training memory = weights + activations + gradients + optimizer states, and the last two scale with trainable parameters.
  • Fewer bits per value shrinks memory (13B at 4 bytes = 52 GB, at 2 bytes = 26 GB), but training is more precision-sensitive than inference.

Try it yourself

  1. Memory calculator (about an hour). Write a small Python function that takes parameter count (billions), bytes per value, number of trainable parameters and optimizer (SGD, momentum, Adam) and prints estimated inference and training memory using the formulas above. Done when 13B at 2 bytes prints about 31.2 GB for inference and 78 GB for gradients plus Adam states with all parameters trainable, and 6 GB when only 1B are trainable. A starter that I ran locally (Python 3) and that printed exactly those numbers: 
    def weights_gb(params_b, bytes_per_value):
    return params_b * 1e9 * bytes_per_value / 1e9
def inference_gb(params_b, bytes_per_value, overhead=0.2):
    return weights_gb(params_b, bytes_per_value) * (1 + overhead)
def grad_opt_gb(trainable_b, bytes_per_value, optimizer_states=2):
    return trainable_b * 1e9 * (1 + optimizer_states) * bytes_per_value / 1e9

print(inference_gb(13, 2))     # 31.2
print(grad_opt_gb(13, 2))      # 78.0
print(grad_opt_gb(1, 2))       # 6.0
  2. Precision explorer. Use Python's struct module (format 'e' packs a 16-bit float) to convert a list of numbers to FP16, and emulate BF16 by keeping the top 16 bits of an FP32 pattern. Print them next to the originals. Done when 1234.56789 shows 1235.0 in FP16 and 1232.0 in BF16, and 123456.789 overflows to infinity in FP16 only. (I ran this; it reproduced the chapter's table rows for those values.) 
    import struct
def to_fp16(x):
    try: return struct.unpack('<e', struct.pack('<e', x))[0]
    except OverflowError: return float('inf')
def to_bf16(x):
    b = struct.unpack('<I', struct.pack('<f', x))[0]
    b += 0x7FFF + ((b >> 16) & 1)
    return struct.unpack('<f', struct.pack('<I', b & 0xFFFF0000))[0]
  3. One-weight training loop. Train a single weight w so that w * 2 hits 6, using squared error, a hand-computed gradient and a learning rate of 0.05. Done when you can point to the forward pass, the loss, the gradient and the update in your code, and the loss falls each step (mine went from 36 at step 1 to under 0.1 by step 7). Then note: what extra values would Adam keep per weight?
  4. Failure-triage sorter. Collect 15 to 20 real or invented failed model outputs for a task you care about and label each "information" or "behavior" with a one-line reason. Count them. Done when you can say which fix (RAG or finetuning) your tally points to, and what a third bucket (prompt was just bad) would change.
  5. Quantization sanity check. Make an array of random floats, round-trip them through a simulated 8-bit scheme (scale to the range -127..127, round, scale back) and measure the average error. Done when you can show the error and explain why a single outlier value that stretches the scale would hurt every other value. This is a toy of the idea, not how production quantizers work.
  6. Maintenance policy memo. For an imaginary finetuned model, write half a page answering the chapter's questions: who hosts it, how you'd evaluate a new base model, and how much better it must be before you switch. Done when you've named a concrete threshold and a person who owns the decision.
