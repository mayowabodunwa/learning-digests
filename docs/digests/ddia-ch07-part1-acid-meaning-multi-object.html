Transactions: What They Promise (ACID) and What They Don't

A transaction bundles several reads and writes into one unit that either happens completely or not at all. This first part is the "what is it, really" half of the chapter: why transactions exist, what each letter of ACID actually means (and why the acronym is slipperier than it looks), why grouping writes across several objects matters, and what to do when a transaction aborts. It stops right before the section on weak isolation levels.

In one line

Transactions let an application pretend certain failures and race conditions can't happen, at the price of costs and subtleties you should understand; "ACID" is a useful idea but a vague label.

The big idea

Many things go wrong in real systems: databases and applications crash mid-operation, networks cut connections, several clients overwrite each other, and readers see half-updated data. Handling all of that by hand is a lot of careful work. A transaction moves that work into the database: group your reads and writes, and either everything commits or everything is rolled back, so you can retry safely. The catch is that the guarantees are not one thing. The same word, "ACID", means different things in different databases, and some of its letters describe the database while one (the C) describes your application.

Key terms

  • Transaction: a group of reads and writes executed as one logical unit; it either commits (succeeds) or aborts/rolls back (fails).
  • Commit / abort (rollback): finishing successfully, or undoing everything the transaction wrote.
  • Partial failure: some operations succeed and some fail.
  • ACID: Atomicity, Consistency, Isolation, Durability, coined in 1983 by Haerder and Reuter.
  • BASE: "Basically Available, Soft state, Eventual consistency", the label for systems that aren't ACID; the source calls it vaguer still.
  • Atomicity (ACID sense): if a fault happens partway through a transaction, everything it did is undone. Not about concurrency.
  • Invariant: a statement about your data that must always be true (for example, credits and debits balance).
  • Isolation: concurrently running transactions don't step on each other.
  • Serializability: the strongest textbook isolation; the result is as if transactions had run one at a time.
  • Race condition: a bug that depends on the timing of concurrent operations.
  • Durability: once a transaction has committed, its data isn't forgotten even after a crash.
  • Dirty read: seeing another transaction's uncommitted writes.
  • Multi-object transaction: a transaction touching several rows, documents or records.
  • Atomic increment, compare-and-set: single-object operations that avoid read-modify-write races.
  • Deduplication: application-level logic that stops a retried operation from taking effect twice.
  • Exponential backoff: waiting longer after each failed retry.

How it works

Grounding first. Picture an app that records a sale and updates a stock count in a database. If the app crashes between the two writes, you've sold something without reducing stock. If two customers buy the last item at the same instant, both might succeed. Transactions are the database's answer: "do these things as a unit, and I'll handle the messy cases". The source stresses that transactions are not a law of nature. They were created to simplify the programming model, letting the application ignore certain error scenarios and concurrency issues; the source calls these safety guarantees. Not every application needs them, and sometimes weakening or dropping them buys performance or availability.

A short history, and two myths

Most relational databases (and some nonrelational ones) follow the style introduced by IBM System R in 1975. The source says MySQL, PostgreSQL, Oracle and SQL Server have transaction support "uncannily similar" to it. In the late 2000s, NoSQL databases offered new data models plus replication and partitioning by default, and transactions were "the main casualty": many dropped them or redefined them as something much weaker. Two opposing slogans followed: "transactions kill scalability" and "serious data needs ACID". The source calls both "pure hyperbole". The truth is trade-offs.

The meaning of ACID

The source's blunt verdict: when a system says "ACID compliant", it's unclear what you can actually expect; ACID has become "mostly a marketing term". Here are the letters as the chapter explains them.

Atomicity. Careful, the word is overloaded. In multi-threaded programming, an atomic operation means no other thread can see it half-done. In ACID, atomicity is not about concurrency (that's isolation). It's about what happens if a client makes several writes and a fault occurs partway: a crash, a dropped connection, a full disk, or a violated integrity constraint. The transaction is aborted and the database must discard any writes made so far. This matters because without it, after an error you don't know which changes took effect; retrying risks doing something twice. With atomicity, an aborted transaction changed nothing, so retrying is safe. The source says "abortability" might have been a better word.

Consistency. The source lists at least four meanings of the word: replica consistency (Chapter 5), consistent hashing (Chapter 6), the CAP theorem's meaning (which is linearizability, Chapter 9), and the ACID meaning: your application's idea of the data being in a "good state". You state invariants, and if a transaction starts from a valid state and preserves validity, the invariants hold. But that depends on the application defining its transactions correctly; the database can only check some kinds of invariants (foreign key and uniqueness constraints, for example). So atomicity, isolation and durability are properties of the database, while consistency is a property of the application. The source says the C "doesn't really belong in ACID" and cites a remark that it was tossed in to make the acronym work.

Isolation. Imagine two clients incrementing a counter that holds 42: each reads 42, adds 1, writes 43. The counter should be 44 but ends at 43, a race condition. Isolation in the ACID sense means concurrent transactions can't step on each other. The classic formal version is serializability: each transaction can pretend it's the only one running, and the committed result is the same as if they had run one after another. In practice, serializable isolation is rarely used because of its performance cost. The source gives a notable example: in Oracle 11g, the isolation level named "serializable" actually implements snapshot isolation, a weaker guarantee. (Later parts cover snapshot isolation and the weaker levels.)

Durability. Once a transaction has committed, its data won't be forgotten, even after a hardware fault or crash. On a single node that normally means written to nonvolatile storage such as a disk or SSD, usually with a write-ahead log for recovery. In a replicated database it can mean the data has been copied to some number of nodes, and the database waits for that before reporting commit.

Durability is never absolute

Historically durability meant writing to archive tape, then to disk or SSD, and more recently replication. None is perfect. The source lists: disk-only means data is inaccessible until the machine is fixed; a correlated fault (a power outage or a bug triggered by a particular input) can knock out all replicas at once; asynchronous replication can lose recent writes when the leader goes away; SSDs have been shown to sometimes violate guarantees on sudden power loss, so even fsync isn't guaranteed to work; firmware and filesystem interactions have bugs; data on disk can silently corrupt (and then replicas and recent backups may be corrupt too); one study found 30% to 80% of SSDs develop at least one bad block in four years (hard drives have fewer bad sectors but a higher complete-failure rate); and a powered-off SSD can start losing data within weeks, depending on temperature. The upshot: no single technique gives absolute guarantees. Combine writing to disk, replication and backups, and take theoretical "guarantees" with a grain of salt.

Single-object and multi-object operations

Atomicity and isolation assume you modify several objects (rows, documents, records) at once, and often you must keep several pieces of data in sync. The source's example: an email app showing an unread count. Counting with a query could be slow, so you store the count in a separate field (denormalization). A new message must insert the email and increment the counter. Two failure shapes appear. Without isolation, a user can see the new email but a counter that hasn't been incremented yet (the source calls reading another transaction's uncommitted writes a dirty read). Without atomicity, if the counter update fails after the insert, mailbox and counter drift apart; an atomic transaction would roll the email back.

Relational databases usually group operations by the client's connection: everything between BEGIN TRANSACTION and COMMIT on that connection belongs to the transaction. (The source's footnote notes the flaw: if the connection drops after you ask to commit but before you get the acknowledgment, you don't know whether it committed.) Many nonrelational databases have no way to group operations. A multi-put API doesn't necessarily have transaction semantics: it may succeed for some keys and fail for others.

Single-object writes

Atomicity and isolation matter even for one object. If you write a 20 KB JSON document and the connection drops after 10 KB, does the database store the broken fragment? If power fails mid-overwrite, do you get old and new spliced? If another client reads during the write, does it see a half-updated value? Because that would be baffling, storage engines almost universally provide atomicity and isolation at the level of a single object on one node. Atomicity is implemented with a crash-recovery log; isolation with a lock per object. Some databases add atomic operations such as an increment (no read-modify-write needed) and compare-and-set (write only if the value hasn't changed since you read it). They help prevent lost updates, but the source says calling them "lightweight transactions" or "ACID" is misleading, since a transaction normally means grouping multiple operations on multiple objects. (Strictly, "atomic increment" borrows the multi-threading meaning of atomic; per a footnote it would be more accurately called an isolated or serializable increment.)

Why you need multi-object transactions

Many distributed stores dropped them because they're hard across partitions and can hinder high availability or performance. The source says nothing fundamentally prevents distributed transactions (Chapter 9 covers them). Are they needed? Sometimes single-object operations suffice, but often writes must be coordinated:

  • Foreign keys and graph edges: inserting records that refer to each other needs the references to stay valid.
  • Denormalized documents: fields updated together in one document need no multi-object transaction, but document databases without joins encourage denormalization, and updating several documents in one go (like the unread counter) benefits from transactions.
  • Secondary indexes: indexes are separate objects from the transaction's viewpoint. Without isolation, a record might show up in one index but not another.

You can implement such applications without transactions, but error handling gets much more complicated without atomicity, and the lack of isolation causes concurrency problems.

Handling errors and aborts

A key philosophy: if the database is in danger of violating atomicity, isolation or durability, it would rather abandon the transaction than leave it half-finished. Not all systems follow it. The source says leaderless-replication datastores work "best effort": they do what they can and don't undo what's done, leaving recovery to the application. And many developers think only of the happy path. Popular ORMs such as Rails' ActiveRecord and Django don't retry aborted transactions; the error bubbles up as an exception and user input is thrown away, "a shame" since the point of aborts is safe retry. But retrying isn't perfect:

  • If the commit actually succeeded but the acknowledgment was lost, a retry performs the transaction twice unless you have application-level deduplication.
  • If the failure is overload, retrying makes it worse. Limit retries, use exponential backoff, and treat overload errors differently.
  • Only retry transient errors (deadlock, isolation violation, temporary network interruption, failover). After a permanent error such as a constraint violation, retrying is pointless.
  • Side effects outside the database (like sending an email) can happen even if the transaction aborts, so retries repeat them. Two-phase commit (Chapter 9) can help make several systems commit or abort together.
  • If the client dies while retrying, the data it was writing is lost.

Why it matters

Almost every backend developer uses transactions daily without being able to say what exactly they guarantee. Knowing that atomicity is about abortability, that consistency is your job, and that "serializable" may not mean serializable in a given database makes you far better at reading database documentation. And the retry list is a practical checklist for any code that talks to a database.

Remember this

  • A transaction groups reads and writes so they all commit or all abort, letting you retry without worrying about partial failure.
  • ACID atomicity means abortability (not concurrency); isolation covers concurrency; durability is risk reduction, never absolute; consistency is mostly your application's job.
  • "ACID compliant" is mostly marketing; check what isolation level you really get.
  • Single-object atomicity is nearly universal; multi-object transactions keep denormalized data, foreign keys and indexes in sync.
  • Retrying aborts is simple but needs care: duplicates, overload, permanent errors, and outside side effects.

Try it yourself

  1. Atomicity demo. With SQLite (or any SQL database), insert an email row and then increment a counter row, forcing an error between them. Run it with and without BEGIN/COMMIT. Done when you can show the inconsistent state without a transaction and a clean rollback with one.
  2. Lost counter. Write two threads that each read a counter, add 1, and write it back with a short sleep between read and write. Then replace it with a single atomic UPDATE ... SET n = n + 1. Done when the broken version loses an update and the fixed one never does in your runs.
  3. Compare-and-set. Add a version column and write an update that only applies WHERE version = ?. Check the affected-row count to detect a lost race. Done when two competing writers produce exactly one success.
  4. Retry wrapper. Write a function that retries a transaction only for errors you classify as transient, with a maximum count and exponential backoff. Done when constraint violations fail immediately and simulated deadlocks are retried.
  5. Idempotency key. Make a "create payment" operation safe to retry by storing a client-supplied unique ID with a uniqueness constraint. Done when submitting the same request twice, after a simulated lost acknowledgment, creates one payment.
