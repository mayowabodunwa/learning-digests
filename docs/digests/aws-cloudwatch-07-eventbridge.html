Amazon EventBridge: Rules, Event Patterns, Schedules and Their Link to CloudWatch Events

Alarms and dashboards tell humans what's happening. EventBridge is how you make software react: "when an EC2 instance terminates, run this Lambda function", or "every weekday at 6pm, kick off this job". This digest covers events, event buses, rules, event patterns, targets and schedules, and how all of this relates to the older name you'll still see: CloudWatch Events.

In one line

EventBridge receives events (small JSON records saying "something happened"), checks each one against your rules, and delivers the matching events to targets such as Lambda functions, queues or other services, and it can also fire things on a schedule.

The big idea

The usual way to wire two pieces of software together is to have one call the other directly. That makes them tightly coupled: if the second one moves or breaks, the first one must change. EventBridge supports a looser style, called event-driven architecture in the docs: components announce what happened, and other components subscribe to the announcements they care about. The announcer doesn't need to know who is listening.

Inside AWS this is already happening. Many AWS services emit events automatically (an EC2 instance changing state is the docs' recurring example) to a bus that exists in every account. You write a rule with an event pattern describing the events you care about, and attach up to five targets that should be invoked when one matches. That's the whole loop. The scheduled variant just replaces "when an event matches" with "when the clock says so".

Key terms

  • Event: a JSON record describing something that happened. Standard fields include source, detail-type, account, time, region, resources and a free-form detail object.
  • Event bus: a router that receives events and delivers them to zero or more targets. Every account has a default event bus that automatically receives events from AWS services.
  • Rule: attached to a bus; says which events go to which targets. A rule either matches on an event pattern or runs on a schedule.
  • Event pattern: a JSON document with the same shape as the events it matches. An event either matches it or doesn't.
  • Target: the resource EventBridge sends a matching event to: a Lambda function, SNS topic, SQS queue, Step Functions state machine, another event bus, an API destination, and many more.
  • Execution role: an IAM role EventBridge assumes to call a target on your behalf, for target types that need one.
  • Input transformer: a way to reshape the event before it reaches the target.
  • Dead-letter queue (DLQ): an SQS queue where events can be sent if delivery to a target ultimately fails.
  • Rate / cron expression: the two ways to say when a scheduled rule fires.
  • EventBridge Scheduler: a separate, newer scheduling feature that the docs recommend over scheduled rules.
  • Pipes: point-to-point connections from one source to one target with optional filtering and enrichment.

How it works

Grounding: how this relates to CloudWatch Events

The tracker for this area calls this concept "its relation to CloudWatch Events". Here's what I could pin down. CloudWatch Events was the earlier name for this capability. When I fetched the old CloudWatch Events documentation address, it returned the EventBridge user guide's "What is EventBridge?" page, which tells me the old docs now live under EventBridge. The command line group is still called aws events and the console address still contains /events/, which looks like a trace of the earlier name. My reading is that they are the same service under a newer name with extra capabilities (like pipes and scheduler), but I did not find a docs sentence stating that outright in the pages I read, so treat that as my interpretation and check the EventBridge FAQ if it matters to you.

What does connect directly to the rest of this track: the docs say that when a matched event came from CloudWatch Alarms, the alarm state change details can be passed on (their example is an Incident Manager response plan target). So alarms are event sources too. A CloudWatch alarm can drive an EventBridge rule.

1. Events: the thing being routed

The docs' example, an EC2 state-change event, looks like this:

{ "version": "0", "id": "6a7e8feb-b491-4cf7-a9f1-bf3703467718", "detail-type": "EC2 Instance State-change Notification", "source": "aws.ec2", "account": "111122223333", "time": "2017-12-22T18:43:48Z", "region": "us-west-1", "resources": [ "arn:aws:ec2:us-west-1:123456789012:instance/i-1234567890abcdef0" ], "detail": { "instance-id": "i-1234567890abcdef0", "state": "terminated" } }

Notice two kinds of information: fields about the event (source, detail-type, account, time) and fields from the event body, inside detail (instance-id, state). Patterns can look at both.

2. Buses, rules and targets: the routing model

Per the docs, the flow is: a source (an AWS service, your application, or a SaaS provider) sends an event to a bus; EventBridge evaluates the event against each rule on that bus; for each rule that matches, the event goes to that rule's targets. One event can match several rules, and one rule can have up to five targets (which run in parallel). An event that matches no rule is simply not acted on.

Which bus? Per the docs, the default bus in every account automatically receives events from AWS services. You can also create custom buses for your own applications' events, and receive events from SaaS partners. The current docs add a distinction I'll only name: a newer Custom Event Bus (subscriber-based, with event retention, replay and ordered delivery) versus the Custom Event Bus - Classic model of rules and targets that this digest describes. The docs say that for new applications you should start with the newer Custom Event Bus, and that Classic remains available. Treat everything below as the classic rule/target model.

3. Event patterns: deciding what matches

A pattern has the same shape as the event, but each field's value is a list of acceptable values. The docs' example selects EC2 termination events:

{ "source": ["aws.ec2"], "detail-type": ["EC2 Instance State-change Notification"], "detail": { "state": ["terminated"] } }

Matching rules to learn first:

  • Fields you list must all match (AND). Several values in one field's list are alternatives (OR): "PaymentType": ["Credit", "Debit"].
  • Fields you don't mention are ignored, so a short pattern matches many events.
  • Matching is exact on the values, and the docs warn this includes characters in ARNs (a colon and a slash aren't interchangeable).

Content filtering operators from the docs' comparison table (all have an example there):

{"prefix": "us-"}: starts with. {"suffix": ".png"}: ends with.

{"anything-but": "initializing"}: any value except that (also accepts lists, and prefix/suffix/wildcard forms).

{"numeric": [">", 0, "<=", 5]}: a numeric range. {"exists": true} or false: field present or absent.

{"equals-ignore-case": "alice"}: case-insensitive. {"cidr": "10.0.0.0/24"}: IP address range.

{"wildcard": "dir/*.png"}: wildcard match (event bus rules only, not pipes). "$or": [ ... ]: match if any of several field conditions holds.

Simplification: I've left out arrays-in-events, null and empty-string matching, and numeric precision rules. The docs say numeric matching treats numbers as 64-bit floating point, so integers are matched exactly only within a bounded range. Also: comparison operators work on leaf fields (with the docs' exceptions for $or and anything-but).

Test before you ship. The docs point to the EventBridge Sandbox for testing an event pattern against sample events before creating or updating a rule.

4. Targets, permissions and failure handling

A rule can have up to five targets. The console target list in the docs is long: API destinations (HTTPS endpoints), other event buses (same or different account), and AWS services including Lambda (asynchronous), SNS, SQS, Step Functions (asynchronous), Kinesis, Firehose, CloudWatch log groups, ECS tasks, Systems Manager Run Command and Automation, EC2 stop/terminate/reboot API calls, and more.

  • Permissions. EventBridge needs permission to call the target. For many targets you supply an execution role (the trust policy lets events.amazonaws.com assume it). The put-targets reference says Lambda and SNS rely on resource-based policies instead; I'd verify the exact way to grant a Lambda function permission before building one.
  • Shaping what the target receives. By default the whole event is passed. Options: part of the event (InputPath), a constant (Input), or an input transformer with a template. These are mutually exclusive.
  • Retries. The retry policy in the put-targets reference allows MaximumRetryAttempts between 0 and 185 and MaximumEventAgeInSeconds between 60 and 86400. The console text gives the defaults as 24 hours and 185 retries.
  • Dead-letter queue. You can attach an SQS queue to catch events that couldn't be delivered. The docs note SQS queues encrypted with an AWS owned key aren't supported for targets or DLQs.
  • A new rule needs a moment. The docs warn that new or updated rules and targets might not take effect immediately.

The infinite-loop trap. The docs explicitly warn that a rule can trigger an action that triggers the same rule again. Their example: a rule fires when an S3 bucket's ACL changes, and the response changes the ACL back, which fires the rule again. Write rules narrowly (fire only on a bad state, not on every change) and consider an AWS Budgets alert for surprise charges.

5. Scheduled rules (and why Scheduler is preferred)

A scheduled rule fires at intervals instead of in response to an event. Per the docs, the console path calls this "Scheduled rule (legacy)", and they recommend EventBridge Scheduler instead, which supports one-time schedules, flexible delivery windows, retry limits and a wider set of targets. Still, scheduled rules are common in older setups, so you should be able to read them.

  • Rate expression: rate(value unit), with a positive number and a unit of minute(s), hour(s) or day(s). Singular unit for 1, plural otherwise: rate(1 hour) and rate(5 hours) are valid; rate(1 hours) and rate(5 hour) are not.
  • Cron expression: six fields, cron(minutes hours day-of-month month day-of-week year). Example from the docs: cron(0 18 ? * MON-FRI *) means 6:00 pm every Monday through Friday (UTC). You can't give both day-of-month and day-of-week: one of them must be ?.
  • All scheduled events use UTC+0. The minimum precision is one minute, and the docs warn there can be a delay of several seconds between trigger and target run.
  • Scheduled rules can only be created on the default event bus.
  • A rate expression starts counting from when you create the rule.

CLI shapes from the docs: aws events put-rule --schedule-expression "rate(5 minutes)" --name MyRule and, for patterns, aws events put-rule --name EC2InstanceStateChanges --event-pattern "{\"source\":[\"aws.ec2\"],\"detail-type\":[\"EC2 Instance State-change Notification\"]}". A rule needs an event pattern or a schedule (or both). Updating a rule replaces it: omitted arguments reset to null. Then attach targets with aws events put-targets --rule NAME --targets "Id"="1","Arn"="<target ARN>".

6. Pipes and Scheduler, in one paragraph

Two siblings to know by name. Pipes are for point-to-point connections: one source (the docs' example is a DynamoDB stream) to one target, with filtering, enrichment and transformation along the way. They're often used together with buses, for example a pipe whose target is a bus. EventBridge Scheduler is the managed scheduler that replaces scheduled rules for new work. I haven't read their detail pages.

Why it matters

This is the glue that turns monitoring into automation. A CloudWatch alarm tells you something broke; an EventBridge rule can open an ops item, start a runbook or run a remediation function without a person. Scheduled rules (or Scheduler) replace the cron server you'd otherwise have to keep alive. And because patterns can be as loose or tight as you like, the main skill is writing them precisely: too loose and you invoke targets (and pay) for events you didn't want; too tight and you silently miss the one that mattered.

Remember this

  • Event goes to a bus, rules check patterns, matches go to up to five targets per rule.
  • Pattern fields AND together; values in a list OR; unmentioned fields are ignored; matching is exact.
  • Rules can also run on a schedule (rate or cron, UTC, one-minute precision), but the docs recommend Scheduler for new work.
  • Targets need permission (execution role or resource policy) and can have retries and a dead-letter queue.
  • Watch for rules whose action re-triggers the same rule.

Recall questions

  1. What are the three kinds of thing that can send events to a bus?
  2. If a pattern lists "state": ["stopped", "terminated"], which events match?
  3. Why would cron(0 8 1 * 1 *) be rejected? Fix it.
  4. What's the difference between an execution role and a resource-based policy on a target?
  5. Describe a rule that could loop forever, and one change that fixes it.

Try it yourself

  1. Pattern on paper. Using the docs' EC2 event, write patterns that match (a) any EC2 state change, (b) only stopped or terminated, (c) anything except pending. Done when: you can explain for each why the docs' sample event does or doesn't match; test them in the EventBridge Sandbox if you can.
  2. Event to log group. Create a CloudWatch Logs group, then a rule on the default bus matching an event you can trigger cheaply, with the log group as the target (the docs list CloudWatch log groups as a target). Done when: an actual event appears as a log line you can find in Logs Insights.
  3. Schedule to Lambda. Create a tiny Lambda that logs "hello", then put-rule with rate(5 minutes) and put-targets to attach it (check how to grant EventBridge invoke permission on the function). Done when: you see three invocations in the function's log group, then you disable the rule so it stops.
  4. Read the cron table. Translate in words: cron(0 10 * * ? *), cron(0/15 * * * ? *), cron(15 10 ? * 6L 2019-2022). Done when: your answers match the docs' meanings, including the UTC detail.
  5. Alarm to action. Make a rule whose event pattern matches CloudWatch alarm state changes (look up the event shape on the docs first and write the pattern from it), and send them to an SNS topic you subscribe to. Then flip an alarm with set-alarm-state. Done when: you receive the event JSON by email and can find the alarm name in it.
  6. Break it safely. Give a rule an unreachable target (such as a non-existent function ARN) with a dead-letter queue. Done when: you can describe what ends up in the DLQ and how long retries could run, per the docs' defaults.
