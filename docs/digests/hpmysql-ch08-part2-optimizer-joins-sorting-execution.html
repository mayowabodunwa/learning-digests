Inside the Optimizer: Cost, Join Order, Sorting and the Execution Engine

Part 1 followed a query to the server's door. Part 2 goes inside: how MySQL turns your SQL into a plan, how it guesses which plan is cheapest, how it decides the order to join tables, what a "filesort" really is, and how the plan is then carried out one small step at a time.

In one line

MySQL doesn't run your SQL as written; it parses it, rewrites it, estimates the cost of alternative plans, picks one, and then executes that plan with a small set of low-level storage engine calls.

The big idea

You write what you want. The server decides how to get it. The "how" is chosen by a component called the query optimizer, which compares possible plans using estimated costs and picks the cheapest guess. Because it's guessing from statistics, it is usually good and sometimes wrong, and knowing the reasons it can be wrong is what lets you help it (or leave it alone).

The single most important message of this part, in the source's own emphasis, is: don't preemptively try to outsmart the optimizer. You can end up defeating it, or making your queries harder to maintain for no benefit. Learn what it does so you can tell when it genuinely needs help.

This part covers printed pages 205 to 218: "The Query Optimization Process" (parser and preprocessor, the optimizer, cost, static vs dynamic optimizations, the list of optimizations, statistics, join execution, the execution plan, the join optimizer, sort optimizations), "The Query Execution Engine," and "Returning Results to the Client." Part 3 covers optimizer limitations and specific query types.

Key terms

  • Parser: breaks the SQL text into tokens and builds a parse tree, checking it follows the SQL grammar.
  • Preprocessor: checks things the parser can't, such as whether tables and columns exist, whether names are ambiguous, and whether you have the privileges.
  • Query optimizer: the part that turns a valid parse tree into an execution plan.
  • Cost-based: choosing among plans by predicted cost. Cost is an abstract unit, originally "one random 4 KB page read," now more elaborate.
  • Statistics: numbers about tables and indexes (pages, distinct values, row length) that the optimizer uses to guess.
  • Cardinality: the number of distinct values in an index or column. A yes/no column has low cardinality.
  • Static vs dynamic optimization: static can be done once from the query's shape; dynamic depends on actual values and data, so it's re-evaluated every run.
  • Nested-loop join: for each row from table A, look for matching rows in table B, and so on.
  • Hash join: build an in-memory lookup table (a hash) from one input, then probe it with rows from the other.
  • Left-deep tree: a join plan that always starts with one table and joins the next table into the result, one at a time.
  • Search space: the set of all possible plans the optimizer could consider.
  • STRAIGHT_JOIN: a keyword that forces tables to be joined in the order you wrote them.
  • Filesort: MySQL's name for sorting rows itself when an index can't provide the order. Not necessarily a file.
  • Handler (storage engine API): the interface the server uses to ask an engine for rows, e.g. "give me the first row of this index," "give me the next."

How it works

Grounding first: after step 1 of the road from Part 1 (the SQL arrives), the server has two big jobs. The front half (parse, preprocess, optimize) turns text into a plan. The back half (execute) follows the plan. The front half is where nearly all the cleverness, and most of the performance surprises, live. The source says up front that it takes liberties in describing these as separate steps, since in the real server they often overlap.

1. Parser and preprocessor

The parser reads your text, breaks it into tokens, and builds a parse tree using the SQL grammar. It catches things like invalid ordering of tokens or an unterminated quoted string. The preprocessor then checks meaning: do these tables and columns exist, are any column names ambiguous, and do you have the privileges? The source says the privilege check is normally very fast unless the server has a very large number of privileges.

2. The optimizer: cost-based, and only as good as its inputs

A query can usually be run many ways and still give the same answer. The optimizer's job is to choose. MySQL's is cost-based: it predicts the cost of candidate plans and picks the cheapest prediction. You can peek at its guess for the last query you ran in your session by looking at the Last_query_cost status value. I tried it on my made-up 60,000-row orders table:

  • SELECT COUNT(*) FROM orders then SHOW STATUS LIKE 'Last_query_cost' gave about 6,074.7.
  • SELECT COUNT(*) FROM orders WHERE customer_id = 5 (an indexed lookup) gave about 4.0.

Those numbers are specific to my table and server version. The source says the original unit was one random 4 KB page read but that it has since grown to include things like the estimated cost of evaluating a WHERE comparison, so don't read my 6,074 as "6,074 page reads." The point to take: the number is a relative yardstick, and a lookup that uses an index is estimated to be far cheaper than a full scan.

The estimate is built from statistics: pages per table or index, cardinality, row and key lengths, and key distribution. Notably (per the source) it does not account for caching: it assumes every read is a disk I/O.

Why the optimizer can pick a bad plan

The source gives a list of reasons. In my words:

  • Statistics can be off. Engines supply them and they range from exact to wildly wrong. (The source says InnoDB doesn't keep an exact row count because of its MVCC design.)
  • Cost isn't the same as real time. A plan reading more pages might actually be faster if the reads are sequential or the pages are already cached. The optimizer doesn't know which pages are in memory.
  • Its goal differs from yours. You want fastest; it minimizes estimated cost.
  • It ignores concurrency. Other queries running at the same time aren't part of its calculation.
  • It sometimes follows fixed rules instead of costs. The source's example: if there's a full-text MATCH() clause it will use a FULLTEXT index when one exists, even if another approach would be faster.
  • It can't cost what it doesn't control, like stored functions and user-defined functions.
  • It can't consider every possible plan, so it can miss the best one (more on this under join order).

I saw the estimates-aren't-exact point in practice: I ran EXPLAIN ANALYZE (which actually runs the query and prints real numbers beside the estimates, available in MySQL 8.0) on a join. The plan estimated about 200 customers passing a filter and the real count was 250; it estimated about 6,041 joined rows and got 7,500. That's a decent guess, and still not exact.

Static vs dynamic optimizations

The source splits optimizations into two kinds. Static ones depend only on the query's shape (for example, simplifying an expression with algebra) so they can be done once and stay valid even when you rerun with different values. Think compile-time. Dynamic ones depend on context (which constant is in the WHERE, how many rows an index holds), so they must be re-evaluated each execution. Think run-time. The difference matters for prepared statements and stored procedures: MySQL can do the static work once, but has to redo the dynamic work each time. The source even notes MySQL sometimes re-optimizes while executing.

3. A tour of optimizations MySQL knows how to do

The source calls its list "woefully incomplete," and so is mine, but it gives a feel for what the optimizer does without being asked.

  • Reordering joins. Tables don't have to be joined in the order you wrote them (more below).
  • Converting outer joins to inner joins. If the WHERE clause or schema makes an outer join behave like an inner one, MySQL rewrites it, which also makes it eligible for reordering. I saw this: for a LEFT JOIN followed by WHERE o.total > 5 on the right-hand table, the rewritten query shown by SHOW WARNINGS said join, and the plan put orders first.
  • Algebra and constant folding. Expressions are simplified; impossible or trivially true parts are dropped. In my test, WHERE 5=5 AND id>5 AND status=1 was shown back as just status = 1 and id > 5.
  • COUNT(), MIN() and MAX() shortcuts. For the minimum of a column that is the leftmost part of a B-tree index, MySQL can just read the first index entry (and the last for the maximum). When it does this you'll see Select tables optimized away in EXPLAIN, which literally means the table was replaced by a constant. I confirmed that message for MIN(id), MAX(id) and for MIN(placed) on indexed columns.
  • Constants from key lookups. A lookup on a primary key or unique index with a constant can be done at optimization time, and the answer treated as a constant for the rest of the query. That is the const access type. The source also notes constantness can propagate: if a USING or ON clause forces two columns to be equal and one is a known constant, the other is too. (In my test of a join on a primary key, EXPLAIN showed const for the table pinned by WHERE o.id = 5 and then a lookup with ref: const into the second table.)
  • Covering indexes to avoid reading rows (Chapter 7).
  • Subquery optimization. Some subqueries get converted into more efficient forms such as index lookups.
  • Early termination. Stop as soon as the answer is known. The obvious case is LIMIT. Another: an impossible condition aborts the query during optimization, and EXPLAIN says Impossible WHERE (I got this from WHERE 1=0; with a primary key compared to a value that cannot exist, my 8.0 server instead said no matching row in const table). A third kind is "not exists": for a query like "find customers with no orders," written as a LEFT JOIN ... WHERE orders.id IS NULL, MySQL stops looking at a customer's orders after finding one, because that customer is already excluded. My EXPLAIN showed Not exists in Extra.
  • Equality propagation. If two columns are forced equal by a join condition, a filter on one applies to the other. The source says you don't need to repeat a WHERE condition on both tables "to help" the optimizer (that's advice from other databases and just makes queries harder to maintain). I checked that a range filter on orders.id combined with an equality join to item.order_id gave a range scan on one table and a primary key lookup on the other, but the rewritten SQL that 8.0 prints back didn't show the condition copied onto both, so I can't confirm the mechanism from output. Treat that as the source's claim.
  • IN() lists. Per the source, many databases treat IN(...) as shorthand for lots of ORs, but MySQL sorts the list and uses a binary search (about O(log n) in the list size) where a chain of OR is O(n). I did not test this; it's the source's claim.

The takeaway the source wants you to hold: let the optimizer work. If you do know something it doesn't (a fact guaranteed by your application, say, or a missing feature, or a cost estimate that prefers a costlier plan), you can help with a hint, a rewritten query, a schema change or a new index. The source points to the MySQL manual's "Index Hints" and "Optimizer Hints" sections for version-specific options.

Table and index statistics

One design detail explains a lot of behaviour: the server layer holds the optimizer but does not store statistics itself. Each storage engine keeps its own (and may do it differently), so the optimizer asks the engine for figures such as pages per table/index, cardinality, row and key lengths, and key distribution. That's why a stale or inaccurate statistic from an engine feeds directly into a bad plan, and why Chapter 7's advice about keeping statistics fresh (ANALYZE TABLE) shows up here.

4. How MySQL executes joins

The source stresses an unusual use of the word: in MySQL, every query is a join, even a single-table SELECT, a subquery, or reading a temporary table. A UNION is run as a series of separate queries whose results are spooled into a temporary table and read back out; each piece, and that final read, counts as a join. So understanding joins means understanding query execution generally.

The classic strategy is the nested-loop join: loop over a row of the first table, and for each one, loop to find matches in the second, and so on until every table has matched; emit a row; then backtrack to find the next match. The source says that as of MySQL 8.0.20 the older block-nested-loop is gone and a hash join takes its place, and that the change keeps joins as fast or faster, especially when one side fits in memory. I saw both in my tests: a join where an index exists used nested loops with index lookups, while a join between two columns that had no index showed Using join buffer (hash join) in EXPLAIN and Inner hash join in the tree format.

The execution plan is a tree, not bytecode

Many databases compile a query to bytecode. MySQL produces a tree of instructions that the execution engine follows. The plan contains enough information to rebuild the query. You can see this: in MySQL 8.0, put EXPLAIN FORMAT=TREE before a statement to print the tree (the source's footnote says this too). I ran it on a three-table join and got nested "Nested loop inner join" lines with a table scan or index lookup at each leaf, plus an estimated cost on each. The source also mentions EXPLAIN EXTENDED followed by SHOW WARNINGS to see the rewritten query. Version note: on my 8.0.46 server, EXPLAIN EXTENDED gave a syntax error, while plain EXPLAIN followed by SHOW WARNINGS printed the rewritten query (with a note, code 1003). If the keyword fails for you, drop it. That is a difference between the book and my version, not necessarily a book error for the version it targeted.

A join of several tables could be drawn as a balanced tree (pairs joined, then pairs of pairs). The source says MySQL doesn't do that: it always starts with one table and joins the next, so plans are left-deep trees, like a chain of "result so far, plus the next table."

5. The join optimizer: choosing the order

The most important part of the optimizer, per the source, is the join optimizer, which picks the order tables are visited. Often many orders give the same answer at different cost. The source's example joins a film table, a link table, and an actor table, and shows that the order MySQL chose was not the one a human might guess. I rebuilt the idea with my own tables (customer, orders, item), where I filter customers by region:

  • Left alone, MySQL started with customer (scanning 2,000 rows, estimated 200 passing the region filter), then used the customer_id index on orders, then the primary key of item. The tree-format cost for the whole plan was about 4,749.
  • With STRAIGHT_JOIN forcing the order item, orders, customer, MySQL scanned an index on all ~88,651 estimated item rows and looked up each order and customer. Its estimated total cost was about 71,025, roughly 15 times the other plan.

Both are estimates from my one dataset and version, but they show the principle the source makes: starting where you examine the fewest rows means fewer lookups into later tables, so less backtracking and rereading. STRAIGHT_JOIN forces your order and is for the rare cases the optimizer gets wrong; the source says such cases are rare and that in most cases the optimizer beats a human.

When there are too many orders to try

A join over n tables has n factorial (n!) possible orders. The source's example: 10 tables can be joined 3,628,800 ways (that is 10!, and the arithmetic checks out). Trying them all would take longer than the query, so when the table count exceeds the optimizer_search_depth setting, MySQL switches to shortcuts such as greedy searches. On my 8.0.46 server that variable was set to 62; defaults can vary by version, so check yours. The consequence, which the source states plainly, is that on rare occasions MySQL might miss the best plan because it deliberately doesn't look at all of them.

Some joins can't be reordered, which actually helps by shrinking the search. A LEFT JOIN and correlated subqueries are examples, because one table's result depends on another's data.

6. Sort optimizations: what "filesort" means

Sorting can be costly, so avoid it or do it on fewer rows. If MySQL can't get sorted output from an index, it sorts the rows itself. It always calls this a filesort, even if no file is involved. If the data fits in the sort buffer it uses a quicksort in memory; otherwise it sorts in chunks (quicksorting each) and merges them.

The source describes two algorithms:

  • Two-pass (older). Read the row pointers and the ORDER BY columns, sort those, then go back and re-read the rows in sorted order. The second read is lots of random I/O.
  • Single-pass (newer). Read all columns the query needs, sort those, then output. This avoids the second table read and trades random I/O for sequential I/O, but each sort entry is bigger so fewer fit in the buffer, which can mean more merge passes.

A gotcha the source flags: filesort can use far more temporary space than you'd expect, because it allocates a fixed-size record large enough for the largest possible row, including the full declared length of every VARCHAR, and 4 bytes per character with utf8mb4. It reports seeing temporary space many times the table's size on disk. (That's a reminder from Chapter 6: sloppy column lengths have a cost beyond the table.)

When sorting a join, MySQL sorts at one of two points:

  • If the ORDER BY only uses columns from the first table in the join order, it can filesort that table first and then do the join. EXPLAIN shows Using filesort.
  • Otherwise it stores the join result in a temporary table and filesorts that afterward: Using temporary; Using filesort. Per the source, a LIMIT is applied after the filesort, so the temporary table and sort can be large.

My test matched: joining customer (first in the order) and orders, ORDER BY c.name showed only Using filesort, but ORDER BY o.total (a column of the second table) showed Using temporary; Using filesort. And, as Chapter 7 predicted, ORDER BY placed LIMIT 5 on a table with an index on placed needed no filesort at all, while ORDER BY total LIMIT 5 (no index) did.

7. The execution engine and the handler API

With a plan in hand, execution is comparatively simple: the engine follows the instructions. Many instructions call methods in the storage engine interface, called the handler API. Each table instance in a query gets a handler object (three mentions of the same table means three handlers, created early, during optimization, so the optimizer can ask for column and index information). The interface has a lot of functionality but needs only about a dozen "building-block" operations to run most queries, such as "read the first row in an index" and "read the next row in an index," which is already enough for an index scan. That simplicity is what makes pluggable engines possible, and the source adds that it also explains some optimizer limitations (Part 3).

Not everything is a handler call. The server itself manages table locks (the engine may add its own lower-level locks, like InnoDB's row locks, on top) and anything shared by all engines, like date and time functions, views and triggers, lives in the server.

To see the building blocks yourself, I ran FLUSH STATUS, then SELECT COUNT(*) FROM orders WHERE customer_id = 5, then SHOW SESSION STATUS LIKE 'Handler_read%'. The counters read Handler_read_key = 1 and Handler_read_next = 30: one index lookup to find the start, then 30 "next entry" calls, matching the 30 rows. That is my own observation of the idea, not something the book walks through.

8. Returning results to the client

The last step is the reply. Even a statement with no result set still answers (for example, with how many rows it affected). The server sends results incrementally: as soon as the last table produces a row, it can and should send it. Two benefits: the server doesn't hold the row in memory, and the client starts receiving sooner. Each row goes in its own protocol packet, though packets can be batched at the TCP layer. The source points to a hint called SQL_BUFFER_RESULT if you need to influence that behaviour (see "Optimizer Hints" in the manual).

This ties back to Part 1: the server streams, which is why the client can't ask for "just the first few" after the fact.

Why it matters

Almost every confusing EXPLAIN output becomes readable once you hold this picture. A surprising join order is the join optimizer minimizing early rows. Using filesort and Using temporary are the sort rules. A bad plan on a table that changed a lot is probably stale statistics. And "don't outsmart the optimizer" has teeth: forcing orders or hand-copying conditions can lock in a plan that was good yesterday and wrong after the data changes.

It also tells you where to intervene when you must: update statistics, add an index that changes cost, rewrite the query, or (rarely) hint. Part 3 turns this into a list of places the optimizer is known to struggle and rewrites that help.

Remember this

  • The front half (parse, preprocess, optimize) builds a plan; the back half runs it with a few low-level engine calls.
  • MySQL's optimizer is cost-based and guesses from engine statistics, so it can be wrong; it also doesn't know what's cached.
  • Don't preemptively outsmart it. Help only when you know something it doesn't.
  • In MySQL every query is a join; plans are left-deep chains, and the join order is chosen to touch the fewest rows early.
  • "Filesort" means MySQL sorted the rows itself, not necessarily on disk. Sorting by a non-first table needs a temporary table too.
  • Rows stream to the client as they are produced.

Try it yourself

  1. Read a plan as a tree. Pick a three-table join on made-up data and run it three ways: plain EXPLAIN, EXPLAIN FORMAT=TREE, and (on 8.0.18 or later) EXPLAIN ANALYZE. Write down where estimated and actual rows differ most. Done when you can explain one difference.
  2. Join-order duel. Time and cost the same join with and without STRAIGHT_JOIN in the "wrong" order. Record the tree cost and a real timing (repeat three times). Done when you can say whether the cost ratio predicted the time ratio.
  3. Optimization spotter. Write a short query for each: a MIN() on an indexed column, a WHERE 1=0, a primary key equality, a "customers with no orders" LEFT JOIN, and a left join the WHERE turns into an inner join. Run EXPLAIN and SHOW WARNINGS for each and name the optimization you see. Done when each has a one-line note.
  4. Filesort lab. Join two tables and try ORDER BY on a first-table column, a second-table column, and columns from both. Predict Extra before each run. Bonus: check Sort_merge_passes from SHOW SESSION STATUS after sorting a big result with a deliberately small sort_buffer_size (set it only in your session, on a scratch server).
  5. Statistics sabotage. Load a table, run ANALYZE TABLE, capture a plan; then bulk-delete most rows without re-analyzing and capture it again. Done when you can describe whether the estimates drifted and what refreshed them.
  6. Count the handler calls. Use FLUSH STATUS and SHOW SESSION STATUS LIKE 'Handler_read%' around a full scan, an index range, and a primary key lookup. Done when you can match each counter pattern to the access type.
