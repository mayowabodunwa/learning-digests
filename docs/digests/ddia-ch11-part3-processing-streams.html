Processing Streams: Time, Windows, Joins, and Fault Tolerance

The first two parts covered where streams come from and how they travel. This final part is about doing something with them continuously: what stream processing is used for, why "the last five minutes" is a trickier idea than it sounds, how joins work when data never stops arriving, and how a job that runs for years can survive a crash without double-counting. It ends with the chapter's own summary, which doubles as a recap of the whole chapter.

In one line

A stream processor is like a batch job that never finishes, so it must handle time explicitly (event time versus processing time, windows, stragglers), keep state for joins, and recover from failures without making output visible twice.

The big idea

You can do three things with a stream: write it to a store, push it to humans, or run it through a processor to produce another stream. This part is about the third. The processor consumes input read-only and writes output append-only, much like a Unix process or MapReduce job, with similar partitioning and parallelism. The crucial difference is that a stream never ends. That kills sorting and so sort-merge joins, makes "wait for the job to finish before showing output" meaningless, and means a crash can't be fixed by restarting from the beginning of years of data. Everything in this part follows from that.

Key terms

  • Operator / job (stream processor): code that consumes input streams and produces output streams.
  • Complex event processing (CEP): searching a stream for patterns of events, using stored queries; a match emits a "complex event".
  • Stream analytics: aggregations and statistics (rates, rolling averages, comparisons) over windows of events.
  • Window: the time interval over which an aggregation is computed.
  • Materialized view: a derived view of a dataset that is kept up to date as the underlying data changes.
  • Event time vs processing time: when the event actually happened versus when the processor handled it.
  • Straggler: an event that arrives after its window was declared complete.
  • Tumbling / hopping / sliding / session window: four ways to define windows, below.
  • Stream-stream join (window join), stream-table join (enrichment), table-table join: the three join types.
  • Slowly changing dimension (SCD): a warehouse term for a joined table whose values change over time, so you need to know which version applied.
  • Exactly-once (effectively-once) semantics: the visible effect is as if each input were processed exactly once, even if tasks were retried.
  • Microbatching: cutting the stream into tiny batches (about a second) and treating each as a miniature batch job.
  • Checkpoint: a periodic snapshot of operator state on durable storage, used to restart after a crash.
  • Idempotent: an operation that has the same effect whether performed once or many times.
  • Fencing: preventing a node believed dead, but actually alive, from interfering after failover.
  • Probabilistic algorithms (Bloom filter, HyperLogLog): approximate methods that use much less memory than exact ones.

How it works

Grounding first. Chapter 10's pipelines read a fixed pile of files. Stream processors consume events as they arrive. The partitioning, parallelism and basic transform/filter operations are the same as in MapReduce and dataflow engines, so the source doesn't repeat them. The new things are about time and failure.

What stream processing is used for

Historically for monitoring: fraud detection (a card's usage pattern changes, so block it), trading systems (act on price changes by rules), manufacturing (spot a malfunctioning machine quickly), and military or intelligence tracking. These need sophisticated pattern matching and correlation. Over time other uses emerged:

  • Complex event processing (CEP). Developed in the 1990s to search for event patterns, a bit like a regular expression for events. You write rules (often in a SQL-like language or GUI), the engine keeps a state machine, and on a match emits a complex event. The roles of queries and data are reversed relative to a database: queries are stored long-term and events flow past them. The source lists Esper, IBM InfoSphere Streams, Apama, TIBCO StreamBase and SQLstream, and notes distributed processors such as Samza gaining SQL support.
  • Stream analytics. Less about specific sequences, more about aggregations and statistics: event rates per interval, rolling averages, comparison with last week to spot trends. They are computed over windows (for instance, average queries per second and 99th percentile response time over the last 5 minutes, which smooths out second-to-second noise). Some systems use probabilistic algorithms (Bloom filters for set membership, HyperLogLog for cardinality, percentile estimators) to save memory. The source stresses that this doesn't make stream processing inherently approximate: "there is nothing inherently approximate about stream processing, and probabilistic algorithms are merely an optimization". Frameworks named: Storm, Spark Streaming, Flink, Concord, Samza, Kafka Streams; hosted: Google Cloud Dataflow, Azure Stream Analytics.
  • Maintaining materialized views. Keeping caches, indexes and warehouses current from a change stream is view maintenance. In event sourcing, application state is also a materialized view, but unlike analytics it can't use a limited window: you potentially need all events back to the beginning, apart from what log compaction discards. Samza and Kafka Streams support this using Kafka's log compaction.
  • Search on streams. Store the queries and run documents past them (the reverse of a normal search engine), as in media monitoring or "notify me when a matching property is listed". Elasticsearch's percolator is one option. Simplest is testing each document against every query; with many queries, index the queries too.
  • Message passing and RPC. Actor frameworks look similar but differ: they are about concurrency and distributed execution rather than data management, communication is often ephemeral and one-to-one rather than durable and multi-subscriber, and they allow arbitrary (even cyclic) communication while stream processors are usually acyclic pipelines. There is some crossover (Storm's distributed RPC), and many actor frameworks don't guarantee delivery after crashes.

Reasoning about time

"The average over the last five minutes" sounds clear and isn't. A batch job reading a year of history in a few minutes must use the timestamps inside the events (the machine's clock is irrelevant), which also makes it deterministic. Many stream frameworks use the processing machine's clock (processing time) for windowing; that's simple and fine if the delay between event and processing is negligible, but breaks otherwise. Delays come from queueing, network faults, contention at the broker or processor, a consumer restart, or reprocessing old events after a bug fix. They also cause reordering: a user makes request 1 on server A and request 2 on server B, B's event reaches the broker first, and the processor sees them in the wrong order. (The source's analogy: you watched the Star Wars films in release order, which isn't story order; episode number is the event timestamp, the viewing date is processing time.)

The danger: confusing the two produces bad data. If you measure request rate by processing time and the processor is down for a minute then works through the backlog, it looks like a sudden spike though the real rate was steady.

Knowing when you're ready. With event-time windows (say one-minute windows), when do you declare minute 37 finished? You can time out after seeing no events for a while, but some may be buffered on another machine behind a network problem. Two options for stragglers: ignore them (they are probably few; track the dropped count and alert if it grows), or publish a correction, an updated window value, possibly retracting the earlier output. Sometimes a special message says "no more messages before time t will come", but with several producers you must track each one, which complicates adding and removing producers.

Whose clock? A mobile app may buffer events while offline and send them hours or days later. The right timestamp is when the interaction happened by the device clock, but user device clocks can't be trusted; the server's clock is more trustworthy but less meaningful. One approach: record three timestamps (event occurred per device clock, event sent per device clock, event received per server clock). The difference between the last two estimates the device clock's offset (assuming negligible network delay), which you apply to the event timestamp (assuming the offset didn't change in between). Batch processing has exactly the same issue; streaming just makes it more visible.

Types of windows:

  • Tumbling: fixed length, each event in exactly one window (1-minute windows: round each timestamp down to the minute).
  • Hopping: fixed length but overlapping for smoothing (a 5-minute window hopping every minute); can be built from 1-minute tumbling windows aggregated over adjacent ones.
  • Sliding: all events within some interval of each other (events at 10:03:39 and 10:08:12 fall in one 5-minute sliding window, since they're under 5 minutes apart); implemented by a time-sorted buffer that expires old events.
  • Session: no fixed length; groups one user's events that are close together, and ends after inactivity (for instance 30 minutes with no events). Common in website analytics.

Stream joins

Joins matter as much as in batch, and are harder because new events can appear at any time. Three types:

  • Stream-stream (window join). Example: to compute click-through rate you must bring together search events and click events with the same session ID. A click may never arrive; if it does the gap may be seconds or days; and because of network delays the click may even arrive before the search. So you pick a window (such as at most one hour apart). Embedding search details in the click event doesn't replace the join, since you'd lose searches with no click. The processor keeps state: the events from the last hour indexed by session ID; on each event it checks the other index for a match and emits a "clicked" event, and if a search expires with no click it emits a "not clicked" event.
  • Stream-table (enrichment). Take the user-activity-and-profiles join from Chapter 10 and run it continuously: each event with a user ID is augmented with profile data. Querying a remote database per event is slow and risks overloading it, so keep a local copy (in-memory hash table or local disk index), as with a map-side hash join. Because the stream processor is long-running, the copy must stay current, which you do with CDC: subscribe to the profile database's changelog too. Now it's really a join between two streams. The source notes it's very similar to a stream-stream join, except the table's changelog uses a window reaching back to the beginning of time with newer versions overwriting older ones, and the event stream might need no window at all.
  • Table-table (materialized view maintenance). The source's example is the home-timeline cache: when a user tweets, add the tweet to each follower's timeline; on delete, remove it; on follow, add recent tweets of the followee; on unfollow, remove them. The processor needs streams of tweet events and follow events plus a store of followers. Equivalent view: a SQL query joining tweets and follows grouped by follower, with the timeline cache being its materialized result. (A footnote notes that if streams are derivatives of tables, the change stream of a join follows the product rule: tweet changes join with current followers, follow changes join with current tweets.)

Time-dependence of joins. All three keep state from one input and query it on the other, and the order of the state-changing events matters (follow then unfollow is not unfollow then follow). Within a partition order is preserved, but across streams or partitions there's usually no guarantee. So if a user updates their profile, which activity events join the old profile and which the new? If events on different streams have undefined order, the join is nondeterministic: rerunning on the same input may give different results. Example: applying the tax rate on an invoice should use the rate at the time of the sale, not the current one, especially when reprocessing history. In warehouses this is a slowly changing dimension, usually handled by giving each version of the joined record a unique ID and storing that ID in the invoice. This makes the join deterministic, at the price of making log compaction impossible, since all versions must be kept.

Fault tolerance

Batch tolerates faults easily: failed tasks restart elsewhere, inputs are immutable, each task writes to its own output file, and output becomes visible only on success. The result looks like each record was processed exactly once even if tasks were retried; this is exactly-once semantics ("effectively-once" would be more descriptive). Streams can't wait for a task to finish before making output visible, since the stream is infinite.

  • Microbatching (Spark Streaming): break the stream into blocks of about a second, each treated as a mini batch job. A compromise: smaller batches mean more scheduling overhead, larger ones more delay. It implicitly gives tumbling windows equal to the batch size (by processing time); larger windows need state carried between batches.
  • Checkpointing (Apache Flink): periodically write rolling checkpoints of state to durable storage. After a crash the operator restarts from its latest checkpoint and discards output since then. Triggered by barriers in the stream, like microbatch boundaries but without forcing a window size.

Both give batch-like exactly-once semantics inside the framework. But once output leaves it (writing to a database, sending to an external broker, sending email), the framework can't discard a failed batch's output, so a restart repeats the side effect. To appear exactly-once, everything caused by processing an event must take effect if and only if processing succeeds: messages to downstream operators or external systems, database writes, operator state changes, and acknowledging input (advancing the consumer offset). That is the atomic commit problem from Chapter 9. In restricted settings it can be done efficiently by managing both state changes and messaging inside the framework instead of across heterogeneous systems as XA tries; the source cites Google Cloud Dataflow and VoltDB, and plans for Kafka, and says overhead is amortized by handling several messages per transaction.

Idempotence is the other route. An idempotent operation has the same effect repeated as done once. Setting a key to a fixed value is idempotent; incrementing a counter is not. A non-idempotent operation can often be made idempotent with metadata: store with each write the offset of the message that triggered it, so you can tell whether it has already been applied. Assumptions, per the source: restart replays the same messages in the same order (a log-based broker does), processing is deterministic, and no other node concurrently updates the same value; failover may need fencing so a node thought dead can't interfere. With those caveats it can give exactly-once semantics at little overhead.

Rebuilding state after failure. Windowed aggregates, join tables and indexes must be recoverable. Options: keep state in a remote replicated store (slow per message), or keep it local and replicate periodically. Flink snapshots operator state to durable storage such as HDFS; Samza and Kafka Streams send state changes to a log-compacted Kafka topic (like CDC); VoltDB processes each input redundantly on several nodes. Sometimes no replication is needed: short-window state can be rebuilt by replaying that window, and a local database copy can be rebuilt from the compacted change stream. There's no universally best trade-off since it depends on network versus disk latency and bandwidth, which also shift over time.

The chapter in review (its Summary)

  • Stream processing is like batch processing done continuously on unbounded input; message brokers and event logs are the streaming equivalent of a filesystem.
  • Two broker styles. AMQP/JMS-style: individual messages assigned to consumers and individually acknowledged, then deleted; right for an asynchronous form of RPC like a task queue, where order doesn't matter and old messages needn't be re-read. Log-based: all messages in a partition go to the same consumer in order; parallelism comes from partitioning; consumers checkpoint offsets; messages are retained so you can reread them.
  • Streams come from user activity events, sensors, feeds, and database writes. The changelog can be captured implicitly through CDC or explicitly through event sourcing, and log compaction keeps a full copy of the database in the stream. This lets you keep derived systems current and build fresh views by consuming from the beginning.
  • Purposes: pattern search (CEP), windowed aggregation (analytics), and keeping derived data up to date (materialized views). Time is hard: event time versus processing time, and stragglers.
  • Three join types: stream-stream (match related events within a time window), stream-table (events enriched from a changelog-fed local copy), and table-table (changes on one side joined with the latest state of the other, yielding a stream of changes to a materialized join).
  • Fault tolerance needs finer-grained recovery than discarding all output: microbatching, checkpointing, transactions, or idempotent writes.

Why it matters

Real-time dashboards, fraud alerts, search indexing, recommendation freshness and metrics pipelines all rest on these ideas. They also explain familiar surprises: counts that spike after a deploy, late data that changes yesterday's numbers, duplicate emails after a crash, and joins that give different answers when replayed.

Remember this

  • Stream processors read inputs read-only and write append-only output; since streams never end, sorting-based joins and "restart from scratch" don't work.
  • Use event time, not processing time, for windows; expect stragglers and decide whether to drop them or issue corrections.
  • Window types: tumbling (fixed, no overlap), hopping (fixed, overlapping), sliding (within an interval of each other), session (ends after inactivity).
  • Stream joins need state; the order of state-changing events across streams matters, and unordered events make joins nondeterministic.
  • Effectively-once results come from microbatching, checkpoints, atomic commit inside the framework, or idempotent writes (with offsets as the metadata), plus a plan for rebuilding state.

Try it yourself

  1. Window functions. Write tumbling, hopping and session window assignment for a list of timestamps. Done when your session windows split correctly on a 30-minute gap and each hopping window contains the events you expect.
  2. Event time vs processing time. Simulate a steady event stream and a processor that pauses for some seconds, then bucket by processing time and by event time. Done when you can show the fake spike in one and a flat rate in the other.
  3. Stream-table join. Feed a stream of activity events and a stream of profile updates into one loop that keeps a dictionary of profiles and enriches events. Done when moving a profile update earlier or later in the interleaving visibly changes the output, and you can explain why that is nondeterminism.
  4. Search-and-click join. Join search and click events by session ID within a one-hour window; emit "clicked" or "not clicked" events when a search expires. Done when a click that arrives before its search is still matched.
  5. Make it effectively-once. Take a consumer that increments a counter and crashes at random points, replaying from the last saved offset. Show it double-counts, then store the last applied offset with the value and skip replays. Done when the final count matches the number of unique messages every time.
