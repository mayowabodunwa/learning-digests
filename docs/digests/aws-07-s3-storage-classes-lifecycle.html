S3 Storage Classes & Lifecycle Policies: Standard to Glacier, Intelligent-Tiering, and Automatic Transitions

Every object in S3 sits in a storage class, and the class is basically a price-versus-access trade. Cheap storage usually costs you something else: retrieval fees, minimum stay times, fewer data centers, or a wait before you can read the data. Lifecycle rules are how you tell S3 to shuffle objects down that ladder (or delete them) on a schedule so you don't have to.

In one line

A storage class sets how an object is stored and billed (how fast you can read it, how many Availability Zones hold it, what you pay to store versus retrieve it), and an S3 Lifecycle configuration is a set of bucket-level rules that automatically moves objects between classes or expires them as they age.

The big idea

Last time we looked at what S3 is made of: buckets, objects, keys. This time we ask a money question. Data you wrote yesterday and read all day is very different from a backup you'll probably never open again, so paying the same price for both makes little sense. S3 offers a range of storage classes so that the price can follow how you actually use the data.

Two ideas carry the whole topic. First, the classes differ along a few axes (access speed, number of Availability Zones, retrieval fees, minimum storage duration, minimum billable size), and you pick by weighing those against your access pattern. Second, you rarely want to do that picking by hand for millions of objects, so you write lifecycle rules and let S3 do it, or you hand the decision to the S3 Intelligent-Tiering class, which watches access for you.

One honest note before we start: I deliberately don't quote prices in this digest. The docs point to the S3 pricing page for rates, and prices change by Region and over time. Everything below is about the shape of the trade-offs, which is what the docs describe.

Key terms

  • Storage class: a per-object setting that decides how S3 stores and bills that object. If you don't choose one at upload, S3 Standard is used.
  • Availability Zone (AZ): one or more discrete data centers in a Region with separate power and networking. Recap from the last digest.
  • Durability (design target): how unlikely data loss is. The docs list 99.999999999% (eleven nines) as the designed-for figure for most classes. It is a design target, not a contract.
  • Availability (design target): how likely a request is to succeed at a given moment. It varies by class.
  • Infrequent access (IA): the family of classes for data you read rarely, priced with cheaper storage but a per-GB retrieval fee.
  • Retrieval fee: a per-GB charge when you read data out of some classes.
  • Minimum storage duration: if you delete, overwrite or move an object out of some classes before a set number of days, you are still billed as if it stayed that long.
  • Minimum billable object size: some classes bill small objects as if they were 128 KB.
  • Archived object / restore: in the Glacier Flexible Retrieval and Deep Archive classes you can't read the object directly. You first request a restore, which makes a temporary readable copy.
  • Intelligent-Tiering: a storage class that moves each object between internal access tiers based on how recently it was accessed.
  • Access tier: a level inside Intelligent-Tiering (Frequent, Infrequent, Archive Instant, and two optional archive tiers). Moving between tiers does not change the storage class.
  • Lifecycle configuration: the set of rules attached to a bucket (one configuration per bucket, up to 1,000 rules).
  • Transition action: a rule action that moves objects to another storage class.
  • Expiration action: a rule action that makes objects expire; S3 deletes them on your behalf.
  • Filter: the part of a rule that picks which objects it applies to (prefix, tags, object size, or a combination).
  • Noncurrent version: in a versioned bucket, an older version of an object that has been overwritten or deleted. Versioning gets its own digest later; here you only need to know lifecycle has separate actions for these.

How it works

Grounding first. When you upload an object, S3 records which storage class it belongs to as part of the object. You can set it in the request (the CLI and SDKs expose a storage class option) or leave it, in which case you get S3 Standard. Changing it later means either a lifecycle transition or copying the object over itself with a new class. All the classes the docs describe for general purpose buckets are designed for the same eleven-nines durability except the legacy Reduced Redundancy class, so the choice is mostly about cost, speed and how many AZs hold your data, not about whether the data is safe.

Simplification, with a caveat: "same durability" is the designed-for number from the comparison table in the docs. Classes differ in availability and in how many AZs hold the data, and a single-AZ class is, in the docs' words, not resilient to the loss of that Availability Zone. Read the durability column together with the AZ column.

1. The frequently accessed classes

S3 Standard (STANDARD) is the default. The docs list it as designed for data you access more than about once a month with millisecond access, 99.99% availability, three or more AZs, and no minimum storage duration and no minimum object size. Think of it as the "no strings attached" class: you pay more per GB stored than the colder classes, but you pay no retrieval fee and no early-delete penalty.

S3 Express One Zone (EXPRESS_ONEZONE) is a special-purpose class for latency-sensitive applications. The docs say it delivers consistent single-digit millisecond access, stores data in a single AZ that you choose, and lists 99.95% availability. It lives in directory buckets rather than general purpose buckets (we met bucket types last time). It's a performance class, not a cheap-archive class, so I'll mention it here and leave it.

Reduced Redundancy Storage (REDUCED_REDUNDANCY) is a legacy class. The docs recommend not using it because S3 Standard is more cost-effective, and list its design durability as 99.99%. You'll see it in old tutorials; just know it's there.

2. The infrequent-access classes

S3 Standard-IA (STANDARD_IA) and S3 One Zone-IA (ONEZONE_IA) are for long-lived data that you read rarely but still want in milliseconds when you do. The trade: storage is cheaper than Standard, but there's a per-GB retrieval fee. Both have a 30-day minimum storage duration and a 128 KB minimum billable object size.

Concretely, the docs say that an object smaller than 128 KB is billed as 128 KB, and that deleting, overwriting or transitioning an object out before 30 days incurs the normal storage charge plus a prorated charge for the rest of the 30 days. So IA is a poor fit for tiny files and for data that churns quickly.

The difference between the two is the AZ count. Standard-IA spreads data across multiple AZs and is resilient to losing one. One Zone-IA keeps it in one AZ, which is cheaper, but the docs say it isn't resilient to the physical loss of that AZ (for example from a disaster), and list availability as 99.5% versus 99.9%. The docs' guidance: Standard-IA for a primary or only copy that you can't recreate; One Zone-IA for data you can recreate, or for replica copies in cross-Region replication (which we'll cover in the replication digest).

3. The Glacier classes: archive-grade storage

Three classes are built for long-term archives. All three list three or more AZs, and require minimum storage durations plus retrieval fees, so the docs say they are most effective for rarely accessed data.

  • S3 Glacier Instant Retrieval (GLACIER_IR): archive pricing, but still millisecond access. The docs list it for data accessed about once a quarter. 90-day minimum, 128 KB minimum billable size.
  • S3 Glacier Flexible Retrieval (GLACIER): for archives accessed about once a year, where retrieval takes minutes to hours. 90-day minimum. Not readable in real time.
  • S3 Glacier Deep Archive (DEEP_ARCHIVE): the coldest class. The docs list it for data accessed less than once a year, with retrieval measured in hours. 180-day minimum. Not readable in real time.

Where it trips beginners. The docs make three points worth underlining. (1) These objects are still S3 objects in your bucket. You can't reach them through the separate Amazon Glacier service. (2) For Flexible Retrieval and Deep Archive, each archived object carries 40 KB of extra metadata: 32 KB billed at the Glacier rate (to identify and restore the object) and 8 KB billed at the S3 Standard rate (to keep the name and metadata). So archiving millions of tiny objects can cost more than expected, and the docs suggest bundling many small objects into fewer big ones. (3) Each object transitioned into these classes counts as a transition request, which has a cost.

4. Restoring an archived object

An object in Glacier Flexible Retrieval or Deep Archive can't be read directly. You send a restore request, wait, and then S3 holds a temporary copy for the number of days you asked for. After that the temporary copy is removed and the object stays archived. During the restore window, a HeadObject or GetObject still reports the storage class as the archive class, because the restored copy is just a copy.

You pay for both the archived object and the temporary restored copy (charged at the S3 Standard rate) while it exists. If you want a permanent readable object, you restore and then copy it into a new object with a different class (the docs say the console doesn't support copying restored archive objects, so use the CLI, SDKs or REST API for that).

The CLI shape from the docs, restoring for 25 days with the Standard retrieval tier:

aws s3api restore-object --bucket amzn-s3-demo-bucket --key dir1/example.obj \
  --restore-request '{"Days":25,"GlacierJobParameters":{"Tier":"Standard"}}'

aws s3api head-object --bucket amzn-s3-demo-bucket --key dir1/example.obj

The head-object output includes a Restore field: ongoing-request="true" while it works, then ongoing-request="false" with an expiry-date when it's done. The docs list retrieval tiers as Bulk, Standard and Expedited, with Expedited available for Flexible Retrieval (and the Intelligent-Tiering Archive Access tier) but not Deep Archive. I'm not quoting exact wait times for the Glacier classes because I only confirmed the broad "minutes to hours" and "hours" descriptions; check the restore docs for current numbers.

5. S3 Intelligent-Tiering: let S3 watch the access

If you don't know how often data will be read, or the pattern changes, S3 Intelligent-Tiering (INTELLIGENT_TIERING) moves each object between access tiers automatically. You pay a small monthly monitoring and automation fee per object, and the docs say there are no retrieval fees and no minimum storage duration for the class.

Inside the class there are three automatic tiers and two optional ones:

  • Frequent Access: where every object starts.
  • Infrequent Access: objects not accessed for 30 consecutive days move here.
  • Archive Instant Access: objects not accessed for 90 consecutive days move here. Still millisecond access.
  • Archive Access (optional, you opt in): objects not accessed for at least 90 days (configurable up to 730 days) are archived, with Glacier Flexible Retrieval-like performance. Standard retrieval is listed as 3 to 5 hours.
  • Deep Archive Access (optional): at least 180 days of no access (configurable up to 730 days), with Deep Archive-like performance. Standard retrieval is listed as within 12 hours.

The first three tiers have low latency and high throughput. Only turn on the two optional tiers if your application can tolerate asynchronous access, because reading from them requires a RestoreObject first. If an object in Infrequent Access or Archive Instant Access is accessed again, it moves back to Frequent Access automatically. Restoring from the optional archive tiers also returns the object to Frequent Access, and those restores don't take a Days value.

What counts as "access"? This matters because it resets the timers. The docs say downloads, GetObject, PutObject, CopyObject (on the source), RestoreObject and CompleteMultipartUpload count and move an object in Infrequent or Archive Instant Access back up. Calls like HeadObject, tagging calls and list calls do not count. The docs give that as a sample, not a complete list.

Small-object caveat. Objects under 128 KB aren't monitored and aren't eligible for auto-tiering; they sit in the Frequent Access tier permanently. So Intelligent-Tiering is not a good fit for a bucket full of tiny files.

You can make it the default for new data by setting the storage class to INTELLIGENT-TIERING in the upload request header (the docs write that spelling for the x-amz-storage-class header, while the class constant in the API tables is INTELLIGENT_TIERING; I'd copy whichever form the specific API reference shows for the tool you use).

6. Lifecycle configurations: rules that run on the bucket

A lifecycle configuration is attached to a bucket and holds rules. Each rule has an ID, a status (Enabled or Disabled), a filter that selects objects, and one or more actions. There are two main action types: transition (move to another class) and expiration (delete). When you add a configuration, it applies to existing objects as well as new ones: a 30-day expiration rule will queue anything already older than 30 days for removal.

The filter can use a key prefix (like logs/), object tags, an object size range (ObjectSizeGreaterThan and ObjectSizeLessThan, in bytes, both exclusive), or a combination wrapped in And. An empty filter means every object in the bucket. A filter holds only one prefix. To cover two prefixes, write two rules.

Here's a configuration shape built from the CLI reference's syntax: logs move to Standard-IA at 30 days, to Glacier Flexible Retrieval at 90 days, and expire at 365 days.

{
  "Rules": [
    {
      "ID": "tier-and-expire-logs",
      "Filter": { "Prefix": "logs/" },
      "Status": "Enabled",
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 }
    }
  ]
}
aws s3api put-bucket-lifecycle-configuration \
  --bucket amzn-s3-demo-bucket \
  --lifecycle-configuration file://lifecycle.json

Watch out: the CLI reference warns that this call overwrites any existing lifecycle configuration, so include every rule you want to keep.

7. Timing: days, midnight UTC, and delays

The Days value in Transition and Expiration is days since the object was created (the docs treat creation as the same as last-modified, so overwriting resets it). S3 adds that many days to the creation time and rounds the result up to the next midnight UTC. The docs' example: created 1/15/2014 at 10:30 AM UTC with a 3-day rule gives 1/19/2014 00:00 UTC. You can also use a fixed Date in ISO 8601 format; the time is always midnight UTC. A date-based action isn't one-time: it keeps applying to new matching objects while the rule is enabled. The docs also say you can't create date-based rules in the console but you can view, disable or delete them.

The docs also warn that actions run asynchronously, so there can be a delay between the date and the actual transition or removal. For billing, charges switch as soon as the object becomes eligible, even if S3 hasn't acted yet. The docs give one exception: for transitions into Intelligent-Tiering, billing changes only after the transition completes. And a separate Glacier note: for Flexible Retrieval and Deep Archive transitions, the minimum-duration clock and the per-object overhead also start when the rule is satisfied, not when the physical move finishes.

8. Rules and constraints that bite

  • Transitions only go "down the waterfall". The docs describe a waterfall: Standard can go to IA, Intelligent-Tiering, One Zone-IA or any Glacier class; Standard-IA to Intelligent-Tiering, One Zone-IA or Glacier classes; One Zone-IA to Glacier Flexible or Deep Archive; Glacier Instant to Flexible or Deep Archive; Flexible to Deep Archive only. Deep Archive can't be transitioned out by a lifecycle rule at all. To move something back up, restore it and copy it over with a new class.
  • Small objects don't transition by default. Since September 2024 the default stops objects under 128 KB from transitioning to any class, because each transition is a billed request and can cost more than it saves. Configurations created earlier keep the previous behavior (small objects could go only to Flexible or Deep Archive) until you create, edit or delete a rule. You can override with an ObjectSizeGreaterThan/ObjectSizeLessThan filter, or with --transition-default-minimum-object-size (values varies_by_storage_class or all_storage_classes_128K) on general purpose buckets.
  • Minimum durations are enforced on you, not just billed. A single rule can't move an object out of a class before its minimum duration has passed. The docs' example: Glacier Instant Retrieval (90 days) then Deep Archive after 20 days is invalid, so the second transition must be at least 94 days. Two separate rules can force it, but you still pay the minimum-duration charge.
  • Conflict resolution leans cheap. If rules overlap, an object gets only one lifecycle action per day and S3 picks the least costly one: permanent deletion beats transition; transition beats creating delete markers; Glacier Flexible beats an IA transition. If two expirations overlap, the shorter wins. Intelligent-Tiering is favored over other classes except Glacier Flexible and Deep Archive.
  • A bucket policy can't stop lifecycle. For general purpose buckets, even a policy denying all actions to all principals doesn't block a lifecycle rule.
  • Tag filters are evaluated daily and rechecked at run time. If you remove the triggering tag before the queued action runs, it won't proceed, but timing isn't deterministic, so don't rely on tag removal as an instant stop. Rule changes can take up to 15 minutes to propagate.
  • Scale limit: one configuration per bucket, up to 1,000 rules, and the docs say that limit isn't adjustable.

9. Expiration, versioning, and housekeeping actions

What Expiration does depends on the bucket's versioning state. In a non-versioned bucket the object is permanently removed. In a versioning-enabled bucket, if the current version isn't a delete marker, S3 adds a delete marker (the old version becomes noncurrent and is kept). In a versioning-suspended bucket it creates a delete marker with a null version ID. We'll go deep on versioning in the next digest, so treat this as a preview.

For versioned buckets there are extra actions: NoncurrentVersionTransition, NoncurrentVersionExpiration (permanent and unrecoverable), with NoncurrentDays and optionally NewerNoncurrentVersions (1 to 100; requires a filter, otherwise you get an InvalidRequest error), ExpiredObjectDeleteMarker to clean up delete markers with nothing behind them, and AbortIncompleteMultipartUpload with DaysAfterInitiation to clean up abandoned multipart uploads (regular expiration does not remove those). The docs note the last two can't be used in a rule whose filter uses object tags.

Two cost footnotes. Expiring an object that hasn't met its class's minimum duration (30 days for IA, 90 for Flexible, 180 for Deep Archive) is billed for the full minimum. And transitions have no data retrieval charge, but each one is a request with a per-request cost.

10. Choosing a class: a decision sketch

Simplification, with a caveat: this is a mental model, not a recommendation for your workload. Real choices depend on object sizes, pricing in your Region, and how reliably you can predict access.

  • Read often, or unsure, small objects: Standard.
  • Unknown or shifting pattern, objects 128 KB and up: consider Intelligent-Tiering (accept the per-object monitoring fee).
  • Known cooling pattern (logs, reports): Standard, then lifecycle to IA, then a Glacier class, then expire.
  • Rarely read but must be instant: Standard-IA or Glacier Instant Retrieval.
  • Compliance archive, restore wait acceptable: Glacier Flexible Retrieval or Deep Archive.
  • Re-creatable data, want lower cost than Standard-IA: One Zone-IA, accepting single-AZ risk.

The docs also mention S3 analytics Storage Class Analysis as a tool to help you decide when to move data from Standard to Standard-IA. I haven't gone into it here.

Why it matters

Storage cost is usually one of the first things that grows without anyone deciding it should. A bucket of logs and backups with no lifecycle rules keeps every byte at Standard rates forever. A few lines of lifecycle JSON, or switching a bucket's default to Intelligent-Tiering, is one of the most common cost controls in AWS. It also ties into everything coming next in this track: versioning creates noncurrent versions that lifecycle must clean up, replication can target cheaper classes, and Object Lock and Inventory interact with expiration and transitions.

Remember this

  • A storage class is a per-object trade between storage price and access speed, retrieval fees, minimum stay, and AZ count. Standard is the default.
  • Most classes are designed for eleven-nines durability, but One Zone classes keep data in a single AZ, so read durability alongside AZ count.
  • Glacier Flexible Retrieval and Deep Archive need a restore request before you can read an object; the restored copy is temporary and billed on top of the archive.
  • Intelligent-Tiering moves objects between tiers for you, but objects under 128 KB aren't auto-tiered and there's a per-object monitoring fee.
  • Lifecycle rules (filter plus transition or expiration actions) run at midnight UTC granularity, asynchronously, only move down the waterfall, and won't transition objects under 128 KB by default.

Try it yourself

Projects 1 and 2 run offline. Projects 3 to 5 use the AWS CLI against your own account and a scratch bucket. I checked the commands against the CLI reference, but I haven't run them against a live account. Delete the scratch bucket when you're done.

  1. Midnight-UTC calculator (offline, ~20 min). Write a small function that takes a creation timestamp and a number of days and returns the rule's action time using "add the days, round up to next midnight UTC". Test it on the docs' example (1/15/2014 10:30 UTC, 3 days gives 1/19/2014 00:00 UTC). Done when the example matches and you've decided (and noted) what your code does for a timestamp that is exactly midnight, since the docs' wording doesn't settle that edge.
  2. Conflict resolver (offline, ~1 hour). Model a list of rules (prefix, action type, days). For a given object age and key, compute which rules are eligible and pick the winner using the docs' order: delete beats transition, Glacier Flexible beats IA, shorter expiration wins. Done when your resolver gives the same answers as the four overlapping-rule examples in the "conflicts in lifecycle configurations" doc page.
  3. Write and validate a lifecycle config. Create lifecycle.json from section 6, create a scratch bucket, and apply it with put-bucket-lifecycle-configuration, then read it back with aws s3api get-bucket-lifecycle-configuration --bucket .... Done when the returned rules match what you sent. Then add a second rule for a different prefix and notice you must resend both.
  4. Upload straight into a class. Upload three small files with aws s3 cp file s3://bucket/key --storage-class STANDARD_IA (and GLACIER_IR, INTELLIGENT_TIERING), then run aws s3api head-object on each. Done when you can see the StorageClass field in each response and you can explain the 128 KB caveat for each.
  5. Restore drill (optional, may cost money and takes hours). Upload a tiny object with --storage-class GLACIER, run the restore-object command from section 4 with a 1-day restore and the Bulk or Standard tier, and poll head-object to watch the Restore field change. Done when you observed ongoing-request="false" with an expiry date, and confirmed StorageClass still says GLACIER.
