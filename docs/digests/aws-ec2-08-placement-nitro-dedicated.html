Placement Groups, the Nitro System, and Dedicated Hosts vs. Dedicated Instances

So far we've treated an instance as a virtual machine floating somewhere in an Availability Zone. This digest looks at "somewhere": how you can influence which physical hardware your instances land on (placement groups), what that hardware is built from (Nitro), and what it means to be the only customer on a physical server (Dedicated Hosts and Dedicated Instances).

In one line

Placement groups let you pack instances together for speed or spread them apart for resilience, the Nitro System is the AWS-built hardware and software foundation under modern instance types, and Dedicated Hosts and Dedicated Instances are two ways to run on single-tenant servers with different levels of visibility and control.

The big idea

Normally you don't choose hardware. The docs say that without a placement group EC2 tries to spread your instances across underlying hardware to minimise correlated failures (when one thing breaks, several of your instances break together). Placement groups are the knobs for when that default isn't what your workload needs.

Two directions pull against each other: closeness (lower network latency, higher throughput between instances) and separation (less chance that one hardware fault takes out several instances). Cluster groups pick closeness; spread and partition groups pick separation. Dedicated tenancy is a third, separate axis: who else shares the hardware.

I quote no prices; the docs say there's no charge for creating a placement group, and point to pricing pages for dedicated options. Dedicated Hosts are billed per host, Dedicated Instances per instance, per the docs' comparison table.

Key terms

  • Placement group: a logical grouping of instances that influences how EC2 places them on hardware.
  • Cluster / partition / spread: the three main placement strategies (a fourth, precision time, is newer and mentioned briefly).
  • Rack: a physical enclosure of servers; in the docs, each rack has its own network and power source.
  • Correlated failure: a single fault (like a rack losing power) that takes down several instances at once.
  • Partition: a logical segment of a placement group whose instances don't share racks with other partitions.
  • Nitro System: a collection of AWS-built hardware and software components under many EC2 instance types.
  • Hypervisor: software that divides a physical server's CPU and memory among virtual machines.
  • Bare metal instance: an instance with direct access to the host's hardware, without a virtualization layer.
  • Tenancy: whether your instance shares physical hardware with other accounts (default) or not.
  • Dedicated Host: a physical server fully dedicated to you, with visibility into sockets and cores.
  • Dedicated Instance: an instance on hardware dedicated to a single account, without host-level control.
  • Host affinity: keeping an instance tied to the same specific host across stops and starts.
  • BYOL: bring your own license, using software licenses you already own.

How it works

0. Grounding: what are we placing?

EC2 instances are slices of physical servers sitting in racks in a data center in an Availability Zone. An instance can be in only one placement group at a time; groups can't be merged. Some interactions the docs list: capacity reserved through On-Demand Capacity Reservations or zonal Reserved Instances is used automatically if a launch matches, even into a placement group; Dedicated Hosts can't be launched into placement groups; and a Spot Instance configured to stop or hibernate on interruption can't go in one.

1. Cluster placement groups: close together, fast

A cluster group packs instances close together inside a single Availability Zone (it can span peered VPCs in the same Region). Instances get a higher per-flow throughput limit and sit in the same high-bisection-bandwidth segment of the network. Intended for tightly coupled workloads such as HPC, or whenever most of the traffic is between group members.

  • Single-flow bandwidth: for instances with enhanced networking, up to 10 Gbps for a single flow inside a cluster group versus up to 5 Gbps outside one (docs numbers; both are ceilings, and the slower instance of a pair limits the pair).
  • Capacity gotcha: the docs recommend launching all instances in one request and using the same instance type. Adding more later or mixing types raises the chance of an insufficient capacity error. If you hit one, the docs suggest stopping and starting all instances in the group and retrying, which might migrate them to hardware with room for all.
  • Stopped instances stay in the group; restarting can fail if capacity isn't there. Reserving capacity inside the group with an On-Demand Capacity Reservation is recommended; zonal Reserved Instances can't reserve capacity in a placement group.
  • Not supported for burstable (T2-style) instances among others; internet or Direct Connect traffic is limited to 5 Gbps for cluster groups.

2. Partition placement groups: separate failure domains for big distributed systems

EC2 divides the group into partitions, each with its own set of racks (own network and power). No two partitions share racks, so a hardware failure is contained to one partition. Designed for large distributed and replicated systems such as HDFS, HBase, Cassandra (the docs' examples) and Kafka. Facts:

  • Up to seven partitions per Availability Zone, and a group can have partitions in multiple AZs of a Region. The number of instances is limited only by your account limits.
  • EC2 tries to distribute instances evenly but doesn't guarantee an even split; you can also launch into a specific partition.
  • You can see which instance is in which partition, so topology-aware software can place replicas in different partitions.
  • If there isn't enough unique hardware, the request fails; trying later may work. With Dedicated Instances, a partition group is limited to two partitions. Capacity Reservations don't reserve capacity in one.

3. Spread placement groups: a few critical instances, each alone

Each instance goes on distinct hardware (distinct racks, each with own network and power), for a small number of critical instances you want kept apart. They suit mixing instance types or launching over time. The key limit: a rack-level spread group supports at most seven running instances per Availability Zone (it can span AZs, so three AZs give you up to 21). Need more? Use multiple spread groups. Host-level spread is for AWS Outposts only. Not supported for Dedicated Instances, and Capacity Reservations don't reserve capacity in one.

4. The Nitro System: what the hardware is made of

The docs define the Nitro System as a collection of AWS-built hardware and software components for high performance, availability and security. Its parts:

  • Nitro cards: offload local NVMe storage, networking hardware support, management, monitoring and security.
  • Nitro security chip, integrated into the motherboard.
  • Nitro hypervisor: a lightweight hypervisor that manages memory and CPU allocation and, per the docs, delivers performance "indistinguishable from bare metal for most workloads". For most workloads is the docs' own bound.

Nitro also enables bare metal instances, which suit workloads needing low-level hardware features or a non-virtualized environment for licensing or support. Cost of that: a bare metal instance may take up to 20 minutes or more from running to reachable because the server boots and verifies hardware and firmware.

Why you've been seeing "Nitro" in earlier digests: the highest gp3/io2 IOPS need Nitro-based instances; the IPv6 metadata endpoint is Nitro-only; and Nitro instances retrieve only metadata categories available at launch. Requirements for Nitro instances per the docs: ENA for enhanced networking and storage exposed as NVMe devices, so you need the right drivers (current AWS AMIs generally handle this; check the docs for kernel and driver minimums). The docs also describe versions v2 to v6 with different network capabilities (for example, v6 reduces the default idle TCP timeout from 432,000 to 350 seconds and doesn't support Traffic Mirroring), which I'm only noting, not teaching in depth, since instance lists change often.

5. Dedicated Hosts vs. Dedicated Instances

By default, instances run on shared-tenancy hardware: multiple accounts may share a physical server. Two ways to avoid that:

  • Dedicated Instance: runs on hardware dedicated to your single account (even separate accounts under one payer don't share). It may share that hardware with your own non-dedicated instances. No visibility or control over placement, no host affinity (stop and start may land on a different host), and only partial BYOL support (the docs name SQL Server with License Mobility and Windows VDA). Billed per instance. Supports Auto Scaling, automatic recovery, Reserved Instances, Capacity Reservations, Spot. You get it by launching with tenancy dedicated, or into a VPC whose instance tenancy is dedicated.
  • Dedicated Host: a physical server with its capacity fully dedicated to you (optionally shared with other accounts you choose). You see sockets, physical cores and host ID, can target which host an instance goes on, and use host affinity. Comprehensive BYOL for per-socket, per-core or per-VM licenses. Billed per host. Capacity Reservations are not supported. Reservations (Dedicated Host Reservations) can discount billing; the docs state up to 70 percent compared with On-Demand Dedicated Host pricing, a ceiling and not a promise.

The docs state there are no performance, security or physical differences between the two; the differences are visibility, control, licensing and billing. Dedicated Host restrictions include: RHEL and SUSE need your own AMIs (with a high-memory exception), quotas per instance family per Region, no placement groups, and you can't switch a host between virtualized and .metal types after allocation. A caveat on Dedicated Instances: EBS volumes attached to them don't run on single-tenant hardware.

Why it matters

Placement groups are a performance tool (cluster) and a resilience tool (spread, partition); picking the wrong one either stalls an HPC job or leaves your three critical servers in one rack. Tenancy choices are mostly driven by licensing and compliance, and are easy to get expensive. And knowing "Nitro" means you can read instance docs: much of the fine print (EBS limits, ENA, metadata behaviour) is conditional on it.

Remember this

  • Cluster = packed in one AZ for latency and throughput; partition = separate rack sets (max 7 per AZ); spread = distinct hardware (max 7 running per AZ per rack-level group).
  • For cluster groups, launch together with one instance type to avoid insufficient-capacity errors.
  • Nitro = Nitro cards + security chip + lightweight hypervisor; "indistinguishable from bare metal for most workloads"; bare metal exists too.
  • Dedicated Host: whole server, visible sockets and cores, affinity, per-host billing, full BYOL. Dedicated Instance: single-account hardware, no placement control, per-instance billing, partial BYOL.
  • Placement groups and Dedicated Hosts don't mix; one instance, one placement group.

Try it yourself

Projects 1 to 3 run locally. Projects 4 and 5 touch AWS and may cost money (do not allocate a Dedicated Host for practice: it is billed per host); I did not run any AWS command here. The create-placement-group example is from the CLI reference page.

  1. Blast-radius simulator (no AWS). Model racks as failure units. Place 9 instances using cluster (all one rack), spread (each own rack, max 7 per AZ) and partition (3 partitions). Randomly fail one rack many times. Done when: you can print the average number of instances lost per failure for each strategy and explain the trade-off with latency.
  2. Limit checker (no AWS). Write a function that validates a plan against the docs' limits (spread: 7 per AZ; partition: 7 partitions per AZ; Dedicated Instances: partition max 2, spread unsupported). Done when: it correctly rejects an 8th instance in one AZ for spread and explains the multi-group workaround.
  3. Choose-a-strategy flashcards (no AWS). Write 8 workloads (HPC job, 3-node quorum database, Cassandra ring, single-instance app) and map each to a strategy using only the docs' wording. Done when: every answer cites a sentence from the docs.
  4. Create and delete a group. Run aws ec2 create-placement-group --group-name my-cluster --strategy cluster, then aws ec2 describe-placement-groups (the second command is from my own knowledge, not verified), then delete it in the console. Creating a group has no charge per the docs. Done when: you can see it and have removed it.
  5. Observe tenancy. Launch a small instance and find its tenancy in the console details (default expected). Read the Dedicated Instance pricing page (don't launch one) and note which pricing items differ. Done when: you can state in one sentence why you'd pick a Dedicated Host over a Dedicated Instance for a per-socket-licensed product.
